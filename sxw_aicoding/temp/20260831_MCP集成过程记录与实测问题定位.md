## 一、这件事的起因：一次真实的内网实测失败

用户在内网环境跑「访问网页 → 归档」任务，**第一步就断**：页面提示需要内网登录，流程中断。

回源码定位，这个任务撞上的是 `fetch_url` **两条已拍板【定】的交集**，两条都不是 bug、都是设计如此：

| 断点 | 位置 | 行为 |
|---|---|---|
| A | `tools/common/src/net/url-guard.ts`（阶段 3 决 3 · 护栏 2） | 内网域名解析到私网地址 → 拒绝，且错误带 `retryability: "NEVER"` |
| B | `tools/common/src/net/fetch-url.ts` 文件头【定】 | 「不做登录态、不做 Cookie、不做浏览器」 |

`NEVER` 的语义是「换个写法访问同一个内网地址不该成功」，所以模型**不会重试**——它只能放弃。

**结论：这不是修 bug 能解决的，它要求反转一条已经拍板的决定。** 因此走 ADR 流程
（[ADR-0011](../ADR/0011-通过外部-MCP-接入浏览器能力.md)）。

### 为什么选 MCP，而不是给 `fetch_url` 加 cookie 参数

**凭证从头到尾不进 Atlas。** 人在浏览器里登录，Atlas 只拿渲染后的内容。

给 `fetch_url` 加 cookie 会立刻要求一整套凭证解析、脱敏与 Trace 隔离机制——而全仓没有那个东西
（`SecretResolverPort` 那个空壳在 2026-08-31 的 current-only 清理里刚被删掉，注释写着
「要做的那天先写实现」）。走 MCP 一行凭证代码都不用写。

### 用户提出的硬要求

> 换一个不是 Playwright 的本地浏览器 MCP，**不改 Atlas 代码、只改配置**就能正常工作。

这条要求决定了后面几乎所有设计取舍。

## 二、参照 opencode，以及必须分叉的地方

实施前读了用户本地的 opencode 源码（`/Users/shixiangweii/WebstormProjects/opencode`，
`packages/opencode/src/mcp/`）。

### 2.1 opencode 能通用的秘密：**不翻译 schema**

`catalog.ts` 的 `convertTool` 是它全部的抽象，约 40 行：

```ts
const inputSchema: JSONSchema7 = {
  ...(mcpTool.inputSchema as JSONSchema7),   // ← 原样展开，不解析
  type: "object",
  properties: mcpTool.inputSchema.properties ?? {},
  additionalProperties: false,
}
return dynamicTool({ description, inputSchema: jsonSchema(inputSchema), execute })
```

两边的结构差别：

```
opencode :  MCP schema ────────────────────→ AI SDK jsonSchema() → provider
Atlas    :  MCP schema → 【JsonSchema 子集 + validateAndNormalize】→ 形状适配器 → provider
```

Atlas 中间那层不是冗余——它撑着 `normalizedInput` / `inputDigest` / action identity /
Policy 的 `readPointer`。**但它就是「换个 MCP 就得改代码」的风险点。**

> **【定】不要枚举支持哪些 JSON Schema 构造。**
> 最自然的处置是「扩校验器支持 array / object / enum」。不能这么写：
> 枚举就永远有下一个构造（`$ref` / `oneOf` / `prefixItems`…），而下一个构造就是
> 下一次「接个新 MCP 得改 Atlas 代码」。
>
> 改成**最小翻译**：认识的照校，**不认识的原样放行**。失败方向按外部工具定——
> 拒绝一个不认识的构造，后果是**整个工具废掉**（模型看得见它、调得动它、
> 每次被 Runtime 挡在门口，且它无从改对）。

### 2.2 从 opencode 抄来的四条实战细节（读协议想不到，踩过才知道）

1. **`tools/list` 是分页的** —— cursor 翻页，还要防重复 cursor 死循环
2. **`outputSchema` 会解析失败** —— 真实服务器发得出 SDK 解不开的 `$ref`，处置是把
   `outputSchema` 整个 omit 掉重试。**这条是引 SDK 最好的论据**：手写客户端不会预见到它，
   症状是「某个 server 一接就崩」
3. **`resetTimeoutOnProgress` 必须配一个空的 `onprogress`** —— SDK 只在这个回调存在时
   才发 progress token，少写它另一行静默失效
4. **`structuredContent` 兜底** —— content 空但有结构化结果时要 stringify 回去

### 2.3 必须分叉的四条

| opencode 的做法 | Atlas 抄不了的原因 | Atlas 的处置 |
|---|---|---|
| `tools/list_changed` → 重新 list ＋ 发事件 | 工具面在 Run 启动时冻结进 `RunSpec` | **登记 handler 但只记日志**，不重新 list |
| `isError` → `throw new Error(text)` | Atlas 要 `ok` ＋ `sideEffectState` 二维 | 按档位分流（见 3.2） |
| 无 effect / reversibility 概念 | Policy 判 Allow/Deny 需要 | 配置层补，默认最保守 |
| 无恢复分支 | §18.2 三条分支需要 | `execute` 档天然落分支三 |

第一条值得展开：跟着服务器改工具面的后果是**同一条 transcript 上的同一次 tool_use，
resume 时会走进另一条恢复分支，而盘上看不出来**。

## 三、方案要点

### 3.1 配置形态（与 opencode 的 `opencode.json` 几乎一致）

位置 `.workagent-state/mcp.json`（**跨 workspace**），`--mcp-config <path>` 可覆盖，
**文件不存在不是错误**。

```jsonc
{
  "servers": {
    "playwright": {
      "type": "local",
      "command": ["npx", "-y", "@playwright/mcp@latest"],
      "environment": { "PLAYWRIGHT_HEADLESS": "false" },
      "timeout": { "startup": 90000, "request": 120000 },
      "tools": { "browser_snapshot": "read" }   // 可选，不写 = 全部 execute
    }
  }
}
```

> **为什么 `mcp.json` 跨 workspace，与库 / trace 的规则刻意不同**：
> MCP 进程绑 Atlas 会话、跨 Run 存活（登录态在浏览器进程里）。放进 `<ws>/.workagent/`
> 的话，界面上切一次工作空间就等于**关掉浏览器、丢掉登录态**，而用户不会把这两件事联系起来。
> 换句话说：库跟着 workspace 走，因为 Run 属于某个 workspace；
> MCP 不跟着走，因为那个浏览器窗口不属于任何一个 workspace。

### 3.2 声明的来源：**只能是人**

MCP 协议**一个** Atlas 必填字段都不提供。`Tool.annotations` 里有 `readOnlyHint` /
`destructiveHint` / `idempotentHint`，看起来正好能填上。

> **【定】不读 `annotations`，一行都不读。**
> 它们是**服务器自述**的（MCP 规范自己写着是 untrusted hint）。拿它决定审批档位，
> 等于让**被审计方书写自己的审计规则**——与本仓已拍板的两条同源：
> `shouldUseSandbox` 的「命令名匹配不是安全边界」、以及「审批界面可被 ANSI 伪造」。

配置里**一个词说三件事**：

| 档位 | 含义 |
|---|---|
| `"read"` | 只读 ＋ 幂等 ＋ 自动放行 ＋ 报错时记 `NO_EFFECT` |
| `"execute"`（默认） | 非只读 ＋ 非幂等 ＋ 逐次审批 ＋ 报错时记 `UNKNOWN` |

**用 `read` 而不是 opencode 的 `allow`**：`allow` 表达偏好（"别问我"），`read` 表达属性
（"它只读"）。从「别问我」推出「所以它只读」是一次不成立的合并——一个人完全可能想给某个
写工具免审批，那时 Atlas 会跟着把它记成「没有副作用」，**而那是在事实表里写假话**。

> **`execute` 必须是默认，而它有一个已回源码确认的后果**：
> ```
> sideEffectState === "UNKNOWN"
>   → settle-batch.ts:590   push 一个 RecoveryItem
>   → settle-outcome.ts:77  kind 降成 COMPLETED_WITH_LIMITS
> ```
> **不会**触发 `RECOVERY_REQUIRED`（那只在 resume 时由分支三产生），但
> **execute 档每报错一次，这个 Run 就再也拿不到 `SUCCESS`**。
> 浏览器自动化里报错很常见，所以用户跑几次之后**应该**把只读工具标成 `"read"`——
> 不是嫌审批烦，是不想让那个降级信号变成**一盏永远亮着的灯**。

### 3.3 七个必填字段的来源

| `ToolDefinition` 字段 | 来源 |
|---|---|
| `name` | `mcp__<sanitize(server)>__<sanitize(tool)>` |
| `version` | `"mcp-" + 服务器声明的 version` |
| `description` | MCP 原文 ＋ Atlas 追加一段（外部服务器 / 返回内容不可信 / Atlas 不提供沙箱与回滚） |
| `inputSchema` | **MCP 原样**，一个字不解析 |
| `effectResolution` | `RESOLVER`，**每个 MCP 工具注册一个实例** |
| `redaction` | `STANDARD`（与 `fetch_url` 一致，理由见 3.5） |
| `idempotency` | `read` → 只读＋幂等；`execute` → 两个都 false |
| `timeoutPolicy` | 配置的 `timeout.request`，缺省 120s |
| `progressReporting` | `NONE`（**不是 HEARTBEAT**，理由见下） |
| `verification` | `{ mode:"NONE", requiredForSuccess:false }` |
| `recoveryObservation` | `{ requiresPreFingerprint: true }` |

**`progressReporting: NONE` 的理由**：MCP 的 progress notification **由服务器自行决定发不发**，
不保证节奏。声明 `HEARTBEAT` 就是承诺一个可能不存在的节奏（`fetch_url` 因为一模一样的
理由从 HEARTBEAT 改回过 NONE）。仍然接了 `onprogress → ctx.onProgress`，`NONE` 的语义
恰好是「允许偶尔报，不承诺节奏」。

**恢复分支自动正确，不需要额外代码**（已核对 `facade/index.ts:460`）：

```
execute 档：isReadOnly=false, isIdempotent=false
         → 不进 IDEMPOTENT_RETRY
         → canObserve = requiresPreFingerprint(true) && pre===undefined → false
         → RECOVERY_REQUIRED（分支三）✓ 与 run_shell 同档
read 档：isReadOnly=true → IDEMPOTENT_RETRY（重跑）✓ 只读工具重跑是对的
```

**每个 MCP 工具一个 Resolver 实例**的理由：`TrustedEffectResolver.resolve(normalizedInput,
workspaceRoot)` **拿不到 toolName**（`ports/index.ts:312`），一个共享实例说不出自己在解析
哪个工具，而 Trace 与审批面上「这次要动的是哪个外部工具」必须说清楚。

### 3.4 一处非做不可的类型改动：`EffectScope.kind` 新增 `EXTERNAL_TOOL`

审批展示**按 `scope.kind` 分派**，而 `PROCESS` 那一支是 `run_shell` 专属的
（`main.ts:262` 与 `human-channels.ts:193` 两处）：它读 `input["command"]`，并打印

```
沙箱：只能写 workspace 与本次调用的 $TMPDIR；禁止联网
```

**MCP 工具没有任何沙箱。** 复用 `PROCESS` 的后果是人在批准的那一刻看到一句
**方向相反的保证**，而命令原文那栏是 `(读不到命令原文)`。

`main.ts:259` 的注释写着「按 scope.kind 判而不是按工具名判——将来任何一个 PROCESS scope
的工具都自动获得同样的展示」。**那句话是对的，而这正是它的陷阱**：展示按 scope 泛化，
内容却按工具特化。

新分支打印：服务器名 ＋ 工具名 ＋ **完整入参 JSON** ＋ 一行

> 此工具由外部 MCP 服务器执行，**不在沙箱内**——Atlas 不解析它的参数，也不约束它能读写什么。

**整份入参、不挑字段**：Atlas 不解析 MCP 的参数（那正是"换个 MCP 只改配置"的代价），
所以没有哪个字段能被认定为「关键字段」——挑就等于 Atlas 假装看懂了它。

### 3.5 脱敏用 `STANDARD` 不用 `STRICTEST`（反直觉，但有先例）

`fetch_url` 也是 `STANDARD`，而它返回的同样是任意外部网页正文。

`SimpleRedaction` 的 `STRICTEST` 比 `STANDARD` 多四条正则，其中一条是
`/\b[A-Za-z0-9]{32,}\b/g`（高熵串），注释自己写着「会误伤 hash 与 UUID」。
**一份现代网页的快照里到处是 32 位以上的字母数字串**（CSS class hash、data 属性、
内联 base64）。走 STRICTEST 的后果是归档产物被打成一片 `[REDACTED:high_entropy]`，
**而模型没有任何办法发现自己拿到的内容被改过**，然后把它写进交付物。

残余风险如实记：非 `sk-` / `sk-ant-` / `Bearer` 形态的 session token 会原样进 transcript。

### 3.6 四条代价（ADR-0011 逐条写明，一条都不许假装没有）

1. **沙箱不在** —— `run_shell` 有 seatbelt，MCP 子进程是 `npx` 拉起的任意进程，零约束。
   唯一还在的闸门是**审批和人**。
   （一处 SDK 默认做对了的事：`getDefaultEnvironment()` 是环境变量白名单，
   POSIX 上只有 `HOME/LOGNAME/PATH/SHELL/TERM/USER`，所以 `.env` 里的 API Key
   不会进子进程。配置里的 `environment` 是与它**合并**而非替换——只传自定义变量会让
   子进程拿不到 PATH，`npx` 直接找不到。）
2. **护栏 2 被绕过，而这正是它有用的原因** —— `fetch_url("http://10.x")` 拒绝，
   `browser_navigate("http://10.x")` 放行。两个工具对同一件事给出相反答案，
   必须写明是刻意的，否则下一个人会来「统一」其中一个。
3. **登录态是 transcript 之外的隐藏状态** —— 与阶段 3.5 拒绝持久 cwd 同形态，
   区别是这次那个隐藏状态**就是用户要的东西本身**。
4. **Atlas 的 workspace 边界对 MCP 子进程不成立** —— 不是弱，是不存在：
   `riskFacts` 永远不会出现 `OUTSIDE_WORKSPACE`，因为没有任何东西在解析那些参数。

### 3.7 v1 明确不做

- remote / SSE / streamable-http 传输（配置保留 `type` 字段，加时不是破坏性变更）
- MCP `resources` / `prompts` / `sampling` / `roots`（`initialize` 里如实声明不支持）
- OAuth
- image / resource 块进上下文（与 ADR-0010 同形态的类型层洞；v1 丢掉正文但**点名说出丢了什么**）
- `--user-data-dir` 持久化登录态 → **CLI 入口每个 Run 都要重新登录，浏览器任务请用 `npm run ui`**
- 审批时「以后都放行」写回配置（等实测反馈说「问得太烦」再做）

### 4.4 判据

`verify:mcp` **17 条**，用**手写的假 MCP 服务器**，不依赖 Playwright、不联网、不弹窗口。

> **为什么夹具不用 Playwright**：拿一个真实服务器当夹具，测的就成了「Atlas 能不能接
> **Playwright**」，而这一批要答的是「能不能接**任意** MCP」——用一个真实服务器校准
> 正是本仓反复清理的过拟合形态。夹具刻意造出真实服务器的那些难处：分页、数组参数、
> 嵌套对象、`isError`、image 块、运行中的 `list_changed` 通知。

**九条做过外部注入实测**（改坏实现 → 跑脚本 → 退出码必须非 0 → 改回）：
边界 12 · 默认档位 · read/execute 分流 · schema 放宽 · 分页 · isError 分流 · image 块 ·
连不上硬失败 · `tools` 段拼错工具名。

## 六、问题定位分析

### 6.1 我的第一个假设被证据推翻了

**最初判断**：MCP 走 live DOM 的 `img.src`，带 CDN 变换参数 `@3840w_360h_1c`；
而 Case A 走 `fetch_url` 拿服务端 HTML，不带这些参数。

**回源核对：错的。** 从 Case A 的 transcript 里提取模型见过的所有 `hdslb.com` 图片 URL：

```
共 14 条，其中带 @ 处理参数的：12
https://i0.hdslb.com/bfs/archive/632eff7a415a833fb94196b0e135fe1a1b65a505.png@3840w_360h_1c?mirror_report_banner=1
https://i0.hdslb.com/bfs/archive/29b00d5a0fd1d344d46886811dc791fc02f176a5.jpg@672w_378h_1c_!web-home-common-co…
```

**两次的 URL 形态完全一样**，同一张图（hash `632eff7a…`）在两次运行里都出现过。

### 6.2 真正的根因：模型在两次运行里写了不同的文件名推导代码

| | 代码（模型自己写的） | 结果 |
|---|---|---|
| **Case B** | `filename.replace('@','_')` | `...png_3840w_360h_1c` ← **把 `@` 换成 `_`，CDN 参数留在了扩展名后面** |
| **Case A** | `perl -pe 's{.*/([^/@?]+)[@?].*}{$1}'` ＋ 显式补 `.$ext` | `...png` ← **在 `@` 处截断** |

Case B 的原始脚本（transcript seq154）：

```python
base = url.split('?')[0].split('/')[-1]     # → "632eff7a....png@3840w_360h_1c"
if '.' not in base: base = base + '.jpg'    # 有 '.'，不触发
filename = f'img_{i:03d}_{base}'
filename = filename.replace('@','_')        # ← 元凶：sanitize 而非截断
```

**而且 Case A 多花了 4 轮自己兜底**，Case B 一轮都没做：

| Case A 的额外动作 | seq |
|---|---|
| 重命名 pass：「extract prefix and hash, then determine real extension」 | 244 |
| 手工修 3 个文件：`.jpg`→`.png`、`.jpg`→`.ico` | 267 |
| **跑 `file *` 逐个验证文件类型** | 267 |

**两次都是自然 `COMPLETED`、都没撞预算**（B 用了 12/预算轮数，A 用了 16）。
所以 Case B **有轮次可以自我修正，只是没想起来**。

> **结论：这是模型行为的方差，不是 MCP 集成的缺陷。**
> 但它暴露了 Atlas 侧一个真缺口——见 6.3。

### 6.3 【最重要】Atlas 有一个**专门为这个失败方向设计**的检查器，而它一次都没跑

`artifactKindOf()`（`tools/common/src/artifact-checks/index.ts:159`）：

```ts
export function artifactKindOf(path: string): string {
  const ext = lower.includes(".") ? lower.slice(lower.lastIndexOf(".") + 1) : "";
  if (ext === "json") return "json";
  if (ext === "zip") return "zip";
  if (Object.prototype.hasOwnProperty.call(BINARY_MAGIC, ext)) return "binary";
  return "text";          // ← 未知扩展名落这里
}
```

对 `img_000_...png_3840w_360h_1c`：
```
ext = "png_3840w_360h_1c" → 不是 json/zip、不在 BINARY_MAGIC 里 → 落 "text"
                          → 编码检查 → PNG 二进制不是合法 UTF-8 → 翻红
```

而那段【定】写的正是这件事：

> 未知扩展名默认 `text`。二进制落进 text 会在编码检查上**翻红** ——
> 失败方向是看得见的，比默认 `binary`（什么都不检查、静默通过）好。

**它没跑，因为那 49 个文件从头到尾没有被登记成 artifact。**
`run_shell` 的 `artifact_path` 只声明了最后那个 `images.zip`，中间产物零登记 →
`ArtifactRegistered` 没发生 → 第二层检查没有触发点。

> **这不是「要新增机制」，是「已有机制没有触发路径」。**
> 它与 CLAUDE.md 里 R1 那条【定】互为正反面：那次讨论的是「已知扩展名不该静默通过」，
> 这次是「**未知扩展名压根进不了检查器**」。
>
> **【2026-09-01 纠偏】「只缺触发路径」说轻了**（两份评审各自定位到同一处，成立）。
> 缺的不止是一条路径，是**契约层的入口**：
> `ToolExecutionOutcome.artifact` 是**单个**（`ports/index.ts`），
> 而 `run_shell` 的 `collectDeclaredArtifact` **只接受普通文件**
> （`run-shell.ts`：「不是一个普通文件，未登记」）。
> 也就是说一次批量 shell 调用**在类型上就没有办法**把 49 个成员逐个登记 ——
> 不是「模型少填了一个字段」。
> 要补它得先设计 Case-agnostic 的批量产物契约（manifest / member 级证据），
> 那不是补丁，所以本批仍然只登记不修。

### 6.4 `ArtifactVerified ok=true` ＋ `SUCCESS`，而交付物按文件名打不开

zip 检查只看结构（PK 魔数 ＋ 末尾 66KiB 内的 EOCD），**不看里面**。
这是 ADR-0010 明确声明过的边界（「一条都不等于内容是对的」），**所以不是回归**。

但这次实测把代价具体化了：**一个 49 张图全部有效的 zip，和一个里面全是坏文件名的 zip，
在 Atlas 的事实表里完全不可区分。**

### 6.5 【本次实现的真实缺陷】一条**靠巧合成立**的耦合，无判据覆盖

`browser_evaluate` 的结果 Playwright **不返回内容，只返回文件链接**：

```
### Result
- [Evaluation result](./image_urls.json)
```

模型必须再调一次 `read_file` 才拿得到内容（11 次调用里 seq46、seq81 两次是这个往返）。

**而 `read_file` 能成功，是因为 `resolveServerCwd()` 在没配 `cwd` 时返回 `workspaceRoot`**
——Playwright 的相对输出路径正好落进 Atlas 的 workspace。

> **这是巧合式兼容，不是设计。** 用户一旦在 `mcp.json` 里配了 `cwd`，或 Playwright 改了
> 默认输出目录，这条链路当场断，而模型除了瞎猜路径没有别的办法。
>
> **【2026-09-01 纠偏】触发条件比这里写的近得多**（两份评审都指出，回源确认成立）：
> MCP 连接**跨 workspace 复用**（`service/main.ts` 只在启动时连一次），
> 所以它的 cwd = **服务启动时**那个 workspace。
> **在界面上切一次工作空间，零配置改动，今天就断。**
> Case B 能跑通只因为当时活跃 workspace 恰好就是启动根。
> 已处置：`switchTo()` 在有 MCP 连接时返回一条警告并在界面上以错误样式显示。
> `verify:mcp` 一条判据都没覆盖它。

### 6.6 MCP 往 workspace 里写了 4 个文件，Atlas 全程不知道

```
.playwright-mcp/page-2026-08-31T14-19-12-581Z.yml   (18 KB)
.playwright-mcp/console-2026-08-31T14-19-10-861Z.log
image_urls.json                                     (2.8 KB)
all_image_urls.json                                 (5.7 KB)
```

> **【2026-09-01 纠偏】这句话原来写的是「零 `ActionProposed`、零审批、零 artifact 登记」——
> 前两项不准确**（codex 指出，回 trace 复核成立）：`browser_evaluate` 等 MCP 调用
> **确实**产生了 `ActionProposed` 与 `ApprovalRequested`，也确实经过了批准，
> Web 审批卡还显示了完整的 `externalArgs`。
>
> 准确说法是：**MCP 调用本身有 Action 与审批，但 MCP 子进程在调用内部写出的
> 那些文件没有 FILE scope、没有逐文件 Artifact 记录、也没有清理事实。**
> 审批面上人批准的是「跑 browser_evaluate」，不是「往 workspace 写四个文件」。

**零 FILE scope、零逐文件 artifact 登记、跑完也没清理。**

这是 ADR-0011 代价 ④（workspace 边界对 MCP 不成立）的第一个实例。ADR 里现在只有抽象论断，
**建议把这四个文件名写进去**——一句「边界不存在」和「它刚往你的 workspace 里写了 4 个文件」
对读者的分量不一样。

### 6.7 审批 trace 里查不到模型关掉了 SSL 校验

seq154 的脚本里有：

```python
ctx.check_hostname = False
ctx.verify_mode = ssl.CERT_NONE
```

而 trace 事件只记了 `EXECUTE programs:1,mkdir,python3,set`（§12.4「不以自由文本作为
授权边界」的结果）。

命令原文**在审批面上是显示的**（人有机会看到），也**在 transcript 库里**——所以「可审计」
成立。但 **trace JSONL 单独不够**。不算 bug，算一个需要知道的边界。

### 6.8 排除项：SSL 失败不是 Atlas / 沙箱的问题

Case B 的 seq141 因 `CERTIFICATE_VERIFY_FAILED` 浪费了一轮。已实测确认**沙箱外同样复现**：

```
沙箱外 python urllib：失败 → [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed
沙箱外 curl：200
```

是 python.org 版 Python 3.14 没装根证书（经典的 `Install Certificates.command` 问题），
与 seatbelt 无关——同一沙箱里 `curl` 走系统钥匙串正常。

### 6.9 顺带的观察：MCP 链路的 plumbing 开销

Case B 的 11 次调用里，**6 次是拿到图片 URL 之前的开销**
（navigate → evaluate → read_file → evaluate → read_file，＋最后 close）。
Case A 是 2 次 `fetch_url`。

但整体 token 反而更省（B: 233,906 vs A: 321,881），因为 A 花了 4 轮在自我修正上。
**两者不可直接比较**——这一点写进记录，避免后人拿这两个数字得出「MCP 更省」的结论。

## 六补、二次评审的处置（2026-09-01）

两份评审（zcode GO / **codex NO-GO**）逐条回源码复核后：实质发现基本全部成立。
`verify:all` **183 → 193 条**，新增判据**每条都做过注入实测**。

### 二次反思：三条 P1 不是三个 bug，是同一个形态

这一批的**全部设计前提**是「Atlas 不理解 MCP 的参数与返回」，
而实现里有三处让系统说了**「理解了才能说的话」**：

| | Atlas 说了什么 | 它实际知道什么 |
|---|---|---|
| A1 | `safeMessage` 的契约写着「**已脱敏**，可以展示给用户」 | 塞进去的是未经任何处理的服务器原文 |
| A2 | 伪造 `properties: {}`，再按这份伪造**裁剪模型入参** | 服务器根本没声明 properties（根 `$ref` / `oneOf` / `additionalProperties`） |
| A3 | `riskFacts` 有、`dataMovement` 无 → 等于「这次调用没有数据外发」 | 一个能开浏览器的工具，去向完全未知 |

**A2 最刺眼**：本文档第四节原本写着「未声明字段仍然丢弃 —— **这条不用改**」，
理由是「模型不该发未声明字段」。**那句话只有在 `properties` 完整覆盖所有参数时才成立，
而那恰恰是一个需要解析过 schema 才能下的判断。** 我一边写着「从不试图理解那个 schema」，
一边用一个需要理解才成立的假设去改写模型的意图。

**Case B 的 SUCCESS 是同一形态的第四个实例**：Atlas 宣称「成功」，
它实际知道的只有「zip 的 PK 魔数与 EOCD 完好」。

> 由此得到一个可复用的动作：**凡是 Atlas 对 MCP 说出的每一句话，
> 先问「这句话需要理解参数才能成立吗」** —— 需要，就不许说，或者如实说「我不知道」。

### 逐项处置

| 项 | 处置 | 注入实测 |
|---|---|---|
| **A1** 服务器原文绕过脱敏 | 原文改走 `output`（过脱敏管道）；`settle-batch` 失败分支把脱敏后的正文一并交给模型（**本批唯一的 Runtime 行为改动**，对既有工具是 no-op） | 原文写回 `safeMessage` → 翻红 |
| **A2** 开放 schema 参数被裁 | `JsonSchema.properties` 改可选；`validateAndNormalize` 按 **JSON Schema 标准语义**（只有显式 `additionalProperties:false` 才丢弃）；自家 14 个工具显式加上那一行 | 改回「一律丢弃」→ 4/4 开放 schema 全红 |
| **A3** 无 `dataMovement` | 如实记「无法解析」＋ 两档都加 `DATA_LEAVES_HOST` | 删掉 → 翻红 |
| **B1** call 结果 schema 过严 | 改走 SDK 的 `ResultSchema`（passthrough），与 `tools/list` 的 tolerant 回退对称 | 换回 `CallToolResultSchema` → 翻红 |
| **C1** 建连失败泄漏子进程 | `connectServer` 失败路径 `await transport.close()`；`startup` 改成覆盖 connect ＋ tools/list 的**真 deadline** | 摘掉 close → **6 → 8 个孤儿进程**，翻红 |
| **C2** 切 workspace 后 cwd 不跟 | 注释与行为对齐；`notices` 打印输出目录；`switchTo()` 带警告并在界面上以错误样式显示 | — |
| **C3** CLI exit 钩子等不了 Promise | 正常/异常出口 `await mcp.close()`，exit 钩子降为兜底并注明它依赖的 SDK 实现细节 | — |
| **D1** 信任边界表述自相矛盾 | ADR 改写：**写 `mcp.json` = 授予宿主用户级代码执行权**；审批只约束单次 tool call | — |
| **D2/D3** 示例配置 | 锁版本（不用 `@latest`）＋ 推荐档位表 ＋ **`browser_evaluate` 不是只读工具**的警告 | 判据 K2：示例必须真能被解析器接受，且 `browser_evaluate` 不得标 read |
| **E1/E2** resume 与工具身份 | 用过 MCP 的 Run，resume 发 `ResumeExternalToolsUnverifiable`；工具 version 加 schema/description/档位的 digest | 两侧各注入一次 → 各自翻红 |

### 一条注入实测推翻的因果（值得单独记）

方案里写的 A2 注入靶子是「把 `normalizeSchemaShell` 伪造 `properties: {}` 的写法加回去」。
**实测：判据照样全绿。**

回源才看清：真正承重的只有 `validateAndNormalize` 那一处。
只要它按 `additionalProperties` 判，伪不伪造 `properties` 都不改变结果 ——
`{}` 与 `undefined` 在那条路径上等价。

`normalizeSchemaShell` 的改动仍然保留（它不该向**模型**谎报一份带空 `properties`
的 schema），但**不能声称它是 A2 的守卫**。这与阶段 3.5 收口批那次
「几条 `kills` 声称的因果不成立」是同一形态：**一条不准的因果比没有更糟 ——
它让人以为某处改坏会被抓住，而真去改的时候不会。**

### 明确不做（本批）

- **完整 Browser Session 身份**（codex P1-3 的退出门槛）：它要求先做 `--user-data-dir`，
  而上一轮已拍板不做。取最小诚实处置 —— **说出「我无法核对」**，与 workspace 闸门的
  `UNKNOWN_LEGACY` 同形态：不硬拒，但不允许默不作声。
- **同 logicalId 旧 Deliverable 字节保留**（codex Existing-P1）：既有缺陷，非本批引入，单独收口。
- **批量产物契约**（本文档 6.3）：要设计，不是补丁。

### 新发现与处置

**🔴 发现 1（用户指定提优先级）：同一个 Run 把另一个 Run 的产物当成自己的交付物盖章**

```
上个 Run 留下 images.zip（6.25MB/49 文件）→ `zip -9 ../images.zip …` **追加**
  → v2 = 49 个 ＋ 2 个 = 6.4MB，内容错  →  登记、检查通过、进交付集合
  → 模型看 stdout 发现不对，rm 重做 → v3 = 155KB，正确
  → deliveredArtifactIds = [v2, v3]，SUCCESS，而 v2 的 6.4MB 已不可取回
```

处置 **F1**：`splitArtifactChecks` 按 logicalId 只把**最终版本**放进交付集合。
失败方向分流：最终版本坏 → `FAILED`；被取代的版本坏 → `COMPLETED_WITH_LIMITS`
（不许丢掉——丢了就分不出「修好过」与「一次做对」）。

处置 **F2**：新增 `ProducedArtifact.replacedBytes` ＋ 上 `ArtifactRegistered` 事件。
`run_shell` 早就在 `artifactNote` 里说了这句话，模型也确实靠它发现了问题 ——
**缺的是它只活在 tool result 文本里，人在 Trace 上查不到**。

> ⚠️ **我在评审里有一处错判，已纠正**：我曾说「seq161 没有 artifactNote」，
> 那是我截断读漏了。**两次都有**。所以引导面本来就是有效的，
> 这一批不需要新造警告，只需要把已有的事实抬上事实表。

**🔴 发现 2：文档里「不做 `--user-data-dir`」是假的**（只改表述，功能不做——用户决定）

Playwright MCP 默认就在做：`~/Library/Caches/ms-playwright-mcp/mcp-chrome-*`
两份共 **63MB**，含 `Default/Cookies`、`Login Data`。
**「我们不做」与「它不发生」是两回事。** 代价 ③ 升级为「在磁盘上、workspace 之外、
跨 Atlas 重启存活、Atlas 不读也不清理」。

**🟡 发现 3**：MCP 写入跨 Run 累积（`.playwright-mcp/` 5 个文件 ＋ 两个 Run 的 json）。
**而这正是发现 1 的直接成因** —— 残留会成为下一次的输入。已补进 ADR 代价 ④，不加机制。

**🟡 发现 4（F4）**：用户配置没有 `tools` 段 → 24 个工具全 execute → **11 次调用 11 次审批**。
这次没出事只因为零错误。已在 notices 里提示，且**说的是真正的理由**
（execute 档报错一次就让 Run 永远拿不到 SUCCESS），不是「问得烦」。

**⚪ 发现 5**：模型仍先试 `/tmp`（被沙箱拒）。但这次**失败是响亮的**
（`set -euo pipefail` ＋ 非零退出码），一轮就改对——正是引导面想要的形态，不算回归。
