# Trace、Run 界面与预算展示优化改动说明

> 整理日期：2026-09-02  
> 项目：WorkAgent（沟通代号 Atlas）  
> 范围：预算配置与回显、Run 结果/顶栏展示、Trace 逐轮检查器  
> 关联提交：`23fbfd1`、`233abdb`、`1a2e733`

## 1. 文档目的

本文梳理近期三组连续改动的背景、实施计划和最终代码落点，说明它们如何共同解决以下问题：

1. 用户虽然为任务配置了最大轮次、最大模型调用等预算，但 Run 详情页不能直观看到“本次实际冻结的预算”和权威用量。
2. `COMPLETED_WITH_LIMITS` 容易被误读成“达到最大轮次”，页面没有直接解释恢复项或未完成项。
3. 顶栏品牌文案占据固定水平空间，端点、模型、workspace 等真正需要关注的运行事实被挤压。
4. Trace Tab 直接铺开 JSONL，长 Run 中难以按轮次、操作生命周期和异常点快速定位。
5. Trace 页面显示的“事件数”和文件原始行数口径不同，但旧界面没有解释 `ModelStreamDelta` 与 header/footer 的存在。

本文描述的是已经落地的实现，不将 UI 投影描述成新的 Runtime 事实源。

## 3. 总体设计原则与边界

三组改动共同遵循以下原则：

- Runtime 仍是 Outcome、预算判定、状态迁移和 Trace 事实的唯一权威来源。
- UI 只解释和组织已有事实，不重新结算 Outcome，不自行累计模型调用或工具调用。
- Run 详情预算只读取 `UiRunDetail.budgetAxes`；下一个 Run 的默认预算读取 `UiServiceInfo.budgetDefaults`，两者不混用。
- Trace 优化只消费现有 `/api/runs/:runId/trace` 数据，不修改 Trace JSONL、数据库或 HTTP API。
- 中文语义用于提高可读性，原始 Outcome/Event 枚举始终保留作为白盒追溯锚点。
- 动态页面内容继续使用 `textContent`，不引入框架、构建步骤、`innerHTML` 或内联 `style` 属性。
- 页面保持 `#view` 为详情区唯一纵向滚动容器，不在 Trace 内部增加嵌套纵向滚动。

## 4. 背景与问题分析

### 4.1 预算“配置值、实际值、停止原因”混在一起

实际 Run 排查中出现过这样的认知冲突：

- 启动任务时预期最大轮次为 40、最大模型调用为 80；
- 页面最终在第 20 轮显示 `COMPLETED_WITH_LIMITS`；
- 旧页面只有 Outcome 枚举和分散的逐轮数据，无法快速确认本 Run 冻结的限额到底是多少；
- `COMPLETED_WITH_LIMITS` 又容易被字面理解成“预算用完”。

进一步检查表明，预算至少涉及三个不同事实：

1. `DEFAULT_BUDGETS`：仓库默认值；
2. Service/CLI 启动参数：后续新 Run 的默认覆盖；
3. 单次 Run 覆盖：创建 Run 时写入并冻结到 RunSpec 的值。

已有 Run 在 resume 时继续使用原 RunSpec 的冻结预算，不能被今天的新默认值覆盖。旧界面没有把这三层关系讲清楚。

### 4.2 Outcome 缺少面向人的解释

`COMPLETED_WITH_LIMITS` 不等于 `BUDGET_EXHAUSTED`。它可能来自：

- 某次 execute 工具失败后副作用状态为 `UNKNOWN`，形成 `RecoveryItem`；
- 仍存在未完成或未通过验证的项目；
- Runtime 已经结束，但结算条件不足以得到 `SUCCESS`。

旧界面只显示枚举，用户需要自己翻时间线和恢复页才能判断原因。

### 4.3 顶栏空间利用率低

旧顶栏左侧固定展示 `Atlas / 白盒界面 · Layer 1`，服务事实从品牌块右侧开始。宽屏下这块空间每一行都会被浪费；窄屏下又会挤压端点、模型、workspace、审批档位和 MCP 警告。

### 4.4 Trace 原始 JSONL 难以扫描

旧 Trace 页的优势是原始事实完整，但存在明显的使用成本：

- 事件按 JSONL 顺序平铺，缺少轮次边界和阶段语义；
- 同一 `actionId` 的提议、审批、执行、验证分散在多处；
- 大量 `ModelStreamDelta` 会制造 DOM 和视觉噪声；
- 不能快速筛出异常、预算、恢复、审批或产物事件；
- 多执行段 resume 的 header/footer 与普通事件没有清晰区分；
- 未知事件没有面向未来版本的稳定降级展示。

以实际 Trace 为例，209 行由 116 个业务事件、91 个 `ModelStreamDelta` 和 2 条执行段边界组成。旧页面只展示单一“事件数”，容易让人误以为数据丢失。

## 5. 实施 Plan

### 5.1 阶段一：打通预算配置和权威读数

计划目标：

1. 八条预算轴统一使用 Runtime 中的一张 `axis → field → used → limit` 映射。
2. CLI 和 Service 暴露同一组 `--max-*` 参数。
3. 白盒界面允许创建 Run 时做逐 Run 覆盖。
4. 合并顺序固定为：

   ```text
   DEFAULT_BUDGETS ← 启动参数 ← 本次 Run 覆盖
   ```

5. 所有覆盖值在 RunSpec 中冻结；resume 不修改历史 Run 的冻结预算。
6. 非法值在启动 Run 之前 fail-fast，不能先占用运行槽位再返回错误。
7. UI 的默认值和详情读数均来自 Runtime 提供的同一张预算轴表。

### 5.2 阶段二：优化 Run 顶部结果、预算和顶栏

计划目标：

1. Run 详情顶部增加常驻的“执行结果 + 核心预算”摘要。
2. 核心预算展示轮次、模型调用、工具调用、活跃时间四项，提供实际值、冻结上限和百分比。
3. 完整八轴继续保留在现有“预算”Tab，通过“查看全部预算”进入。
4. Outcome 改为“中文主结论 + 原始枚举”，并直接解释恢复项或未完成项。
5. 明确提示 `COMPLETED_WITH_LIMITS` 不表示达到轮次或模型调用上限。
6. 移除顶栏品牌占位，让端点、模型、workspace 等服务事实从屏幕左侧开始排列。
7. 核心预算达到 80% 使用警告色，达到或超过 100% 使用错误色；窄屏自动降列。

### 5.3 阶段三：Trace 逐轮检查器

计划目标：

1. 默认提供“逐轮检查器”，同时保留“原始事件”模式。
2. 通过纯展示投影将 Trace 行整理为执行段、轮次、操作生命周期、批次和产物组。
3. `ModelStreamDelta` 默认只统计数量和字符数，不逐条创建 DOM；用户可手动打开。
4. 顶部提供统计、搜索、分类筛选、轮次跳转、全部展开/折叠等操作。
5. 每轮展示序号范围、事件跨度、模型耗时、工具名、审批/验证/预算/恢复状态和最终迁移原因。
6. 默认展开最后一轮、异常轮和已完成轮中事件跨度最长的一轮。
7. 未识别事件和异常 payload 必须保留原始内容，不能丢弃或阻断整页。
8. 异步读取 Trace 后校验当前 runId 和 Tab，防止旧请求覆盖新页面。

## 6. 实际改动点

### 6.1 预算配置与冻结语义

#### 6.1.1 Runtime 预算轴成为唯一映射

文件：`packages/harness-runtime/src/budget/index.ts`

实际实现：

- `BudgetAxisReading` 增加 `field`，把每条轴与 `RunBudgets` 字段绑定在同一张表里。
- `readBudgetAxes()` 返回八条轴的 `axis / field / used / limit / unit`。
- 新增 `readBudgetLimits()`，从 `readBudgetAxes()` 派生“只含上限”的视图，供 Service 默认预算使用。
- 新增 `applyBudgetOverrides()`，按 axis id 覆盖预算：
  - 未知 axis 直接报错并列出合法轴；
  - 只接受大于 0 的有限整数；
  - 不静默截断小数；
  - 缺失字段表示“用户没有覆盖”，继续使用上层默认值。

这部分没有复制第二份预算判定逻辑；`checkBudgets()` 仍是执行期唯一判官。

#### 6.1.2 CLI 与 Service 共用八条参数

文件：

- `apps/cli/src/compose.ts`
- `apps/cli/src/main.ts`
- `apps/workagent-service/src/main.ts`

新增参数：

```text
--max-turns
--max-wallclock
--max-total-wallclock
--max-model-calls
--max-tool-calls
--max-billed-input-tokens
--max-output-tokens
--max-consecutive-failures
```

实际实现：

- `BUDGET_FLAG_BY_AXIS` 以 `Record<BudgetAxis, ...>` 穷举所有轴，新增轴时 TypeScript 会要求同步入口。
- `BUDGET_VALUE_FLAGS`、`budgetFlagHelp()`、`parseBudgetFlags()` 从这张表派生，CLI 和 Service 不各自手写参数名。
- 启动档预算在 `compose()` 时校验，非法参数使服务直接启动失败。
- `Composed.makeRunSpec(task, entry, budgetOverrides)` 支持逐 Run 覆盖。
- RunSpec 创建时完成三层合并，并把最终值冻结到 `spec.budgets`。
- CLI resume 会明确打印：继续使用原 Run 冻结预算，本次命令上的 `--max-*` 对旧 Run 无效。

#### 6.1.3 Service API 与 UI 创建 Run

文件：

- `apps/workagent-service/src/api-types.ts`
- `apps/workagent-service/src/run-host.ts`
- `apps/workagent-service/src/server.ts`
- `apps/workagent-ui/public/index.html`
- `apps/workagent-ui/public/app.js`

实际实现：

- `UiServiceInfo.budgetDefaults` 提供“下一个 Run”的默认预算。
- `UiRunDetail.budgetAxes` 提供“当前 Run”的冻结上限和权威用量。
- `POST /api/runs` 接收可选的 `budgets` 对象，按 axis id 索引。
- HTTP 层在 `startRun()` 前使用同一个 `applyBudgetOverrides()` 试算，非法输入返回 400，不占用前台运行槽位。
- 新任务区域增加默认折叠的预算表单，字段由 `budgetDefaults` 动态生成。
- 表单留空表示不覆盖；毫秒轴在 UI 中按秒展示，提交时由 `unfmt()` 转回毫秒。
- 表单提示预算仅对本次 Run 生效，并随 Run 冻结。

### 6.2 Run 结果与预算摘要

文件：`apps/workagent-ui/public/app.js`

#### 6.2.1 Outcome 展示映射

新增纯展示函数 `outcomePresentation()`：

| Runtime 枚举 | 中文主结论 | 严重级别 |
|---|---|---|
| `SUCCESS` | 任务已完成 | 绿色 |
| `COMPLETED_WITH_LIMITS` + recovery | 任务已完成，但有待确认项 | 黄色 |
| `COMPLETED_WITH_LIMITS` + incomplete | 任务已完成，但仍有未达成项 | 黄色 |
| `USER_REJECTED` | 部分操作被用户拒绝 | 黄色 |
| `BUDGET_EXHAUSTED` | 执行因预算或资源保护停止 | 黄色 |
| `CONTEXT_EXHAUSTED` | 模型上下文容量已用尽 | 黄色 |
| `QUOTA_EXHAUSTED` | 模型调用配额已用尽 | 黄色 |
| `CANCELLED` | 任务已取消 | 中性 |
| `FAILED` | 任务执行失败 | 红色 |

补充行为：

- 原始枚举继续作为 chip 展示。
- 有恢复项时展示数量、首项 `what` 和 `sideEffectState`。
- 有未完成项时展示数量、首项 `what` 和 `why`。
- `COMPLETED_WITH_LIMITS` 下固定提示“此结果不表示达到轮次或模型调用上限”。
- 未知 Outcome 使用中性兜底，不篡改 Runtime 结论。

#### 6.2.2 四项核心预算摘要

新增 `coreBudgetPresentation()` 和 `renderRunSummary()`：

- 固定展示 `turns`、`modelCalls`、`toolCalls`、`activeWallClockMs`。
- 每项显示“实际 / 冻结上限 / 百分比”。
- `limit` 缺失时显示“未设上限”，不伪造成 0 或 Infinity。
- 低于 80% 为普通色，达到 80% 为黄色，达到或超过上限为红色。
- 标题明确写“本 Run 冻结预算”，同时展示 RunSpec id。
- “查看全部预算”按钮切换到原有预算 Tab，查看 Token、连续失败等完整八轴。
- 运行中继续根据后端返回的权威读数刷新；终态展示最后一次事实读数。

文件：

- `apps/workagent-ui/public/index.html`
- `apps/workagent-ui/public/app.css`
- `apps/workagent-ui/public/app.js`

实际实现：

- `.svcinfo` 占满可用宽度，从屏幕左侧开始换行排列端点、模型、声明、工具数、workspace、审批和执行档位。

### 6.4 Trace 只读投影

文件：`apps/workagent-ui/public/app.js`

#### 6.4.1 状态与事件词典

新增 `S.traceUi`，记录：

- 当前 runId；
- `turns` / `raw` 视图模式；
- 分类筛选和搜索词；
- 是否显示流式增量；
- 用户手动展开/折叠过的轮次。

新增 `TRACE_EVENT_META`：

- 中文名称为主标题；
- 原始事件枚举作为次级白盒标签；
- 为模型、工具、审批、验证、迁移、预算/恢复等事件分配展示分类和颜色；
- 未识别事件回退为中性卡片，同时保留原始枚举与 payload。

#### 6.4.2 执行段、轮次和关联关系

新增纯展示函数 `buildTracePresentation(rawLines)`：

- 按 header/footer 划分执行段；缺 header、缺 footer 或运行中未完成段均可展示。
- 以 `TurnStarted` 作为轮次边界，段首事件存入 `prelude`。
- 同一轮内按 `actionId` 聚合操作生命周期。
- 按 `batchId` 聚合操作批次。
- 按 `artifactId` 聚合产物生命周期。
- 产物只按 `artifactId` 展示，不推断不存在的 action → artifact 关系。
- 统计每轮事件序号范围、事件时间跨度、模型调用数量/耗时、工具名、流式增量数量/字符数和最终迁移原因。
- 事件时间差明确称为“事件跨度”，不冒充 Runtime 的活跃墙钟。

#### 6.4.3 统计口径

顶部同时展示：

- 业务事件数：排除 `ModelStreamDelta`；
- 流式增量数；
- 轮次数；
- 执行段数；
- 原始行数：包含事件与 header/footer。

因此示例中的 209 行可以被明确解释为：

```text
116 个业务事件 + 91 个 ModelStreamDelta + 2 条执行段边界 = 209 行
```

#### 6.4.4 逐轮检查器

每轮卡片头部展示：

- `Tn`；
- 原始事件序号范围；
- 事件跨度；
- 模型调用次数和模型耗时；
- 工具调用数量和工具名；
- 审批、验证、预算、恢复、失败和终止徽章；
- 最终迁移原因，例如 `NEXT_TURN`、`COMPLETED_WITH_LIMITS`。

展开后按实际出现的阶段组织：

```text
上下文 → 模型 → 审批/交互 → 工具执行 → 验证 → 产物 → 迁移
```

每个事件保留：

- 中文摘要；
- 原始枚举；
- `#sequence`；
- 关键字段；
- 可折叠的格式化 payload；
- 复制 JSON 操作。

连续工具进度会折叠成摘要，避免长时间 `run_shell` 产生大量重复卡片；原始事件模式仍保留每一条事件。

#### 6.4.5 搜索、筛选和默认展开

顶部工具栏支持：

- 逐轮检查器 / 原始事件切换；
- 搜索中文名称、原始枚举、序号、工具名、actionId、batchId 和 payload；
- 单选筛选：全部、重点、异常、模型、工具、审批/交互、验证/产物、预算/恢复；
- 显示流式增量开关，默认关闭；
- 轮次跳转；
- 全部展开 / 全部折叠。

搜索和分类筛选使用 AND 关系。默认展开：

- 当前或最后一轮；
- 包含失败、拒绝、验证异常、预算、恢复、无进展或 Runtime Error 的轮次；
- 已完成轮次中事件跨度最长的一轮。

普通审批成功不会单独标为异常。用户手动选择在 Tab 切换和实时刷新后保留；切换到新 Run 时重置。

#### 6.4.6 原始事件和实时刷新

- 原始事件模式继续按 JSONL 顺序展示全部事实。
- header/footer 使用执行段边界卡片。
- 完整 JSON 默认折叠，但始终可访问。
- 运行中沿用已有的非流式业务事件刷新机制。
- `ModelStreamDelta` 不触发每条 DOM 重绘；后续业务事件到达时重新读取 Trace 并更新汇总。
- 异步响应返回后检查当前 runId、当前 Tab 和容器连接状态，防止旧 Run 结果覆盖当前页面。

### 6.5 Trace 视觉样式

文件：`apps/workagent-ui/public/app.css`

新增样式覆盖：

- sticky Trace 工具栏；
- 视图切换、统计 chip、搜索框、筛选按钮；
- 执行段、轮次卡片和阶段条；
- action/batch/artifact 生命周期组；
- payload 和工具进度折叠区；
- 模型、工具、迁移、成功、警告、失败和内部事件的颜色体系。

颜色只用于辅助扫描，文字状态和原始枚举始终存在。900px 以下工具栏取消 sticky 并换行，650px 左右使用单列事件布局，不引入第二个纵向滚动区。

## 7. 关键数据流

### 7.1 预算配置与回显

```text
CLI --max-* / Service --max-* / UI budgets
                │
                ▼
       applyBudgetOverrides()
                │
                ▼
  DEFAULT ← 启动档 ← 单次 Run 覆盖
```

## 10. 没有改动的边界

Trace 与结果展示优化没有改动：

- `packages/harness-runtime/` 的 Run Loop；
- Outcome 结算语义；
- 审批、执行、验证或恢复流程；
- Trace 事件产生方式和 JSONL 格式；
- SQLite 表结构；
- `/api/runs/:runId/trace` HTTP 接口。

预算配置功能只增加已有预算轴的覆盖入口、统一校验和权威读取能力，没有让 UI 成为预算判官，也没有允许 resume 改写历史 RunSpec。

## 11. 已知限制和后续关注点

1. Trace 仍在业务事件刷新时读取整份文件，当前没有增量分页或虚拟列表；默认隐藏流式增量可以显著降低 DOM 压力。
2. `ModelStreamDelta` 默认隐藏但没有删除，查看全部流式事件时长 Run 仍可能产生较多节点。
3. artifact 与 action 之间没有权威关联字段，因此页面刻意不建立推断关系。
4. Trace 展示的“事件跨度”只是事件时间戳差值，不能替代预算页的活跃墙钟。
5. `maxTotalWallClockMs` 默认仍未设置；这是为了避免隔夜 resume 在第一次迭代立即耗尽总墙钟，只有调用方显式设置时才生效。
6. `--max-output-tokens` 是整个 Run 的累计输出预算，不是单次 Provider 请求的 `max_tokens`。
7. `@playwright/mcp@latest` 可能随重启改变工具声明；该风险由工具 version digest 和 resume 漂移提示暴露，不属于 Trace UI 的处理范围。

## 12. 最终效果

三组改动完成后，用户可以在一个 Run 页面里按以下顺序完成排查：

1. 先看中文结果摘要，区分成功、预算停止、恢复项和未完成项；
2. 直接确认本 Run 冻结的轮次、模型调用、工具调用和活跃时间预算；
3. 需要完整数据时进入预算 Tab 查看八条轴；
4. 进入 Trace 后先按轮次、异常和操作生命周期扫描；
5. 必要时切到原始事件和完整 payload，回到未被 UI 改写的事实。

这样既提高了长 Run 的定位效率，也保留了 Atlas 白盒界面的核心约束：展示层可以解释事实，但不能成为第二个事实来源。
