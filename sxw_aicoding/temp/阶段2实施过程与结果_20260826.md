| 决 6 | **恢复可观测性拆成 Action 级事实** | 阶段 2 的研究问题靠 `verification.mode` 分流，而那个字段说的是「执行后能不能验」——测量仪器和被测对象是同一个旋钮。详见 [ADR-0002](../ADR/0002-恢复可观测性改为-action-级事实.md) |
| 决 7 | 方案先行 | 与阶段 1 同体例 |

### 2.2 三处影响实现形状的修订

**修订 1（事实性错误，作者自查）**：方案原文写「Node 22 上 `node:sqlite` 在 `--experimental-sqlite` 后面」——
**实测证伪**，v22.22.3 上无 flag 就能用，WAL / busy_timeout / 跨连接读全部正常。

> 教训是方法论的：这条断言是**凭记忆写的**。原则十三「证据先于冻结」管的不只是端点行为，
> **工具链行为同样是可实测的事实**。决 5 因此从「必须升」降级为「升了有实测收益且已验证无代价」。

**修订 3（同一个洞的两半）**：
作者发现「前置指纹无处安放」（`TranscriptEntryKind` 只有四个值），
评审 P1-2 发现「谁去取指纹没指定」（依赖方向禁止 Runtime 认识 Case 包）。
两半的答案：扩 `ACTION_FACT` ＋ **复用 `VerificationPort`**（不新增 Port）——
理由是前置观察与崩溃后观察必须是同一个实现，否则两次测的不是同一个量。

**修订 2（评审 P1-1，最硬的一条）**：评审翻出两条代码里的历史实测记录：

- `compose.ts:227-229`【定】：「光靠 prompt 约束，模型只会从**编一个日期**换成**回避日期**，两次实跑各出现过一种。事实必须真的在上下文里。」
- `compile.ts:189-193`：「为什么不做成 now 工具——工具要模型记得调，**它上次就没调，直接编了一个**。」

这两条把决 3 推得更远：`now` 工具**不能当主机制**，且改提示词有**第二种**失败模式（回避）。

### 2.3 四批的依赖顺序

```
批 1  跨进程 resume 成立        ← 招牌能力的硬前提
批 2  预算与时间的口径          ← 不做这批，批 1 的成果当场作废
```

## 4. 实际改动验证出来的关键事项

**这一节是本文的重点。** 六条全部来自脚本第一次运行时的红灯，没有一条是设计阶段想到的。

### 4.1 `RUN_META.lastSequence` 在真崩溃下不足以恢复取号器

`verify:persistence` 首跑打出 **「重号 5」**。

根因：号按**事件**粒度消耗（每 emit 一次取一个），而 `RUN_META` 只在**轮边界**由
`persistFacts()` 写一次。崩溃落在两者之间时，那批事件用掉的号在盘上**没有任何痕迹** ——
transcript 的 MAX 看不到（事件不落 transcript），RUN_META 也还没更新。
resume 于是从一个偏小的下界继续，把已经发出去的号又发了一遍。

**为什么阶段 1 测不出来**：那时的「崩溃」是往 transcript 注入形态，
**注入的时候顺手把 RUN_META 也写对了**。

修法：加 `sequence_counters` 表，**取号器自己持久化高水位**（M002）。
D-2 说 `nextSequence()` 是唯一取号点——既然如此，耐久性就该由它自己承担，而不是借 RUN_META 的。

> 这不是「第二份权威」：`sequence_counters` 是**分配器状态**（下一个发什么号），
> `RUN_META.lastSequence` 是**事实**（那一刻已经发到哪了）。两者回答的不是同一个问题。

### 4.2 恢复观察被记成「失败的 required Verification」会永久污染 outcome

批 1 实测：真 SIGKILL 之后恢复，**两份产物都正确落盘**，outcome 却是 `COMPLETED_WITH_LIMITS`。

根因：恢复时那次「观察到 a.txt 不存在」被当成一条失败的 required Verification 记进事实表，
而结算只查事实表（§10.4【定】），于是模型随后补写成功也翻不了案。

这正是决 6 要拆的混用：「执行后验证失败」与「崩溃后观察到没发生」是两件事。
S11 落地后（`observePost` 产出的结果标 `required: false`），同一场景变成 **`COMPLETED / SUCCESS`**。

### 4.3 前置指纹拍摄的位置错了

第一版把 `observePre` 放在 `AttemptStarted` 事件**之后**。
`verify:crash` 立刻打出一个自相矛盾的结果：**崩在窗口 A（`AttemptStarted` 处）时永远拍不到指纹** ——
而窗口 A 恰恰是最需要它的场景（工具没跑，只有靠前置状态才判得出「没发生」）。

指纹描述的是「attempt 开始之前的世界」，位置错了语义就错了。

### 4.4 `countTokensAccuracy: "EXACT"` 与 D-3 的本地补估互相矛盾

U-1 一接线，漂移规则 3 **每轮都判漂移**，Run 被打成 `MODEL_ERROR`。

两条声明都对：

- profile 说 EXACT——那描述的是**端点的** count_tokens 在**不含推理块**的帧上的精度（Spike p4：5/5 项 0.00%）；
- D-3 证实端点对推理块**一个 token 都不算**，于是 `countTokens()` 会本地补一个估算顶上去（D-4 的系数 1.9）。

合起来意味着**复合结果不是精确的，而且故意不精确**（宁可高估，让阈值判定偏安全那侧）。
拿它去判「端点漂移了」是错的靶子——偏差来自我们自己的补估。

修法：有本地补估时只 RECORD 不 FAIL_FAST，20% 以内不报。

同一次接线还暴露了一个**夹具错误**：`fakeEndpointProfile` 声称 `countTokensAccuracy: "EXACT"`，
而一个虚拟端点根本没被测量过。改成 `APPROXIMATE` 不是为了让脚本变绿，是因为它是真的。

### 4.5 收紧判据当场抓到真问题

`verify:resume` 的 C 段判据原本只有三条：都到终态、无未配对、transcript 只增。
按存量清单 §4 第 2 条收紧后（加「产物逐字一致」），**立刻发现恢复路径根本没产出 `note.txt`**。

根因是**夹具**没有模拟真 Agent 的行为：被 cancel 的 `tc_2` 会合成一个 SKIPPED result，
配对完好，所以 resume 不走三条恢复分支，直接问模型「接下来做什么」——
真 Agent 会看到 SKIPPED 然后补写，而两轮脚本直接说「都做完了」就收工。

> 「都到了终态」和「结果一致」差得很远：一个把文件写坏了的恢复同样能到终态。

同类的还有一条：M-7 给错误值域接上 `assertActiveErrorDomain()` 之后，
**当场抓到 `source=VERIFICATION` 未登记**（R-4 的 guard 产生的）。
一个不可验证的值域声明等于没有声明，而这两个常量在阶段 1 就是那样存在了整整一个阶段。

### 4.6 `.env` 里有一行死了整个项目周期的配置

M-5 的断言接上后，`npm run dev` 当场被挡下：

```
.env 的 dashscope_model（deepseek-v4-flash）与端点声明里的 modelId（qwen3.7-plus）不一致。
实际发出的请求用的是**声明里的** qwen3.7-plus —— .env 那个值一直没有生效。
```

这**不是新引入的 bug，而是 M-5 描述的那个缺陷的实例**：这个字段被读进 `cfg.modelId` 之后
从来没有消费点。两份评测报告写的模型都对（用的是 profile 里的），`.env` 那行是死配置。

> 处置：**发请求时硬失败，其余情况进 notices**。与凭证断言、U-6 的 baseUrl 断言同一口径。
> 未代为修改 `.env`——那是用户的凭证文件，且「改回 qwen3.7-plus」与「为 deepseek-v4-flash 补声明」
> 是两个不同的意图，只有用户知道要哪个。

### 4.7 顺带记：一个夹具的脆弱性

加 `now` 工具（4 个工具）之后 `verify:compact` 当场翻红——
阈值是**帧级**的，而 `fixedOverheadTokens` 是「工具数 × 180」，多一个工具就挤掉留给 messages 的额度。

修法不是调阈值，而是让夹具**只注册它自己需要的那一个工具**。
夹具不该对「case 包里现在有几个工具」敏感——它要验的是 Compact 的落地，不是工具清单。

| 覆盖写**执行后**崩溃 | `AttemptCompleted#1`（窗口 B） | 是 | `OBSERVE_FIRST` |
| 追加 ＋ 关掉指纹 | `AttemptStarted#1` | 否 | `RECOVERY_REQUIRED` |
| **同一个追加 ＋ 开着指纹** | `AttemptStarted#1` | 是 | **`OBSERVE_FIRST`** |

最后两行是关键：**工具声明一个字没改**，改的是 Runtime 侧的 Verifier 能不能拍指纹。
在此之前，「有多少次 resume 落进第三条分支」的分流依据就是被测对象身上的一个静态字段。
