## 一、表象问题：语法对，数据错

大模型写 SQL 的真正难点，不是语法、函数，也不是表名——这些它都能从元数据里找到，查错率极低。真正的问题是：语法都对了，跑出来的数据却对不上。

这类问题在日常开发中很常见：表选对了，函数也用对了，但结果就是和业务方预期不一致——AI 不知道"剔除试购"、"排除子品"、"用父订单关联"这些隐性规则。

**根因不在模型能力，而在业务语义的缺失。** AI 能看到表结构，却看不到"这张表怎么用、有哪些坑、业务上到底该过滤什么"。这些规则散落在老员工脑子里、生产代码的 CASE WHEN 里、文档的角落中，从未被系统沉淀。

> 模型不知道"试购单"要剔除，不知道"异常价格"要过滤，不知道"类目映射表"在某个时间点之后必须切到新版。这些隐性规则，才是写对 SQL 的真正门槛。

---

## 二、根因在哪：语义不通，规则不清

### 2.1 同一个指标，口径不唯一

同样一句"计算 GMV"，在不同业务语境下含义完全不同：是否剔除试购？是否剔除退款？是否包含运费？用下单口径还是支付口径？

这些差异不体现在表结构里，而是藏在生产 SQL 的 `CASE WHEN` 和 `WHERE` 里。AI 只从元数据出发，无法分辨哪个口径才是当前需求要的。

> 指标名一样，口径却不一样——这是 AI 写错 SQL 的头号原因。

### 2.2 跨平台类目对齐，规则复杂

国际行业的"apple"和淘宝的"tea"，各自有一套类目体系。要把它们对齐到统一类目，不是简单 JOIN 一张维表就能搞定：不同时间段要切不同版本的映射表；类目层级要多级关联；部分映射要按店铺、品牌粒度特殊处理。

> 这种"分时段切表 + 多层级关联"的复合规则，AI 靠猜是猜不出来的。

## 三、关键解法：本体让 AI 写对 SQL

### 3.1 为什么本体如此重要

要让 AI 写对 SQL，必须把业务语义显式沉淀下来——不是写进 prompt 的一句话描述，而是结构化、可校验、可迭代的**业务本体**。

> 本体（Ontology）是对"业务概念、关系、规则"的形式化描述。它回答的不是"有哪些表"，而是"这些表怎么用、什么时候用、有哪些约束"。

本体之于 AI，相当于"业务专家经验"之于新人。它把散落在人脑、代码、文档里的规则显式沉淀，让 AI 有章可循。

### 3.2 本体与相邻概念的区别

| 概念 | 解决什么问题 | 典型形态 |
|------|------------|---------|
| 元数据 | 有哪些表、哪些字段 | DDL、字段注释 |
| 数据字典 | 字段的业务含义 | 字段说明文档 |
| 血缘 | 表之间的上下游关系 | 血缘图 |
| **本体** | **表怎么用、规则是什么、约束有哪些** | **结构化规则集（JSON / YAML / 知识图谱）** |

> 元数据告诉 AI"有什么"，本体告诉 AI"怎么用"。这是 OntSQL Agent 的核心差异。

### 3.3 本体的三层架构

OntSQL Agent 的本体分三层：

- **基础语义层**：表、字段、血缘，对应"有哪些资产"
- **业务规则层**：指标口径、过滤规则、关联规则，对应"怎么用这些资产"
- **场景约束层**：具体需求场景下的特殊处理，对应"在这个场景下要注意什么"

> 这三层不是人工整理的静态文档，而是从生产 SQL 中自动抽取、持续迭代的结构化资产。

## 四、怎么落地：本体进入 AI 生成链路

### 4.1 本体自动构建，而非人工整理

#### 4.1.1 不同方案对比

构建本体有几条路可以走：

| 方案 | 做法 | 优点 | 缺点 |
|------|-----|------|------|
| 人工梳理 | 业务专家逐表写规则 | 质量高 | 不可持续，覆盖率低 |
| 从文档抽取 | 解析 PRD、wiki | 来源广 | 文档滞后、口径不一致 |
| **从生产 SQL 抽取** | **解析线上 SQL，提取 CASE WHEN / WHERE / JOIN 中的规则** | **可验证、可追溯、覆盖面广** | 需要过滤噪声 |

> 我们选择了"从生产 SQL 抽取"——因为代码是最好的文档，线上跑着的 SQL 就是最真实的业务规则。

#### 4.1.2 自动化构建以核心表为入口

以核心业务表为入口，沿血缘向上游追溯，逐层抽取规则：

> 核心步骤：
> 1. 选定核心表（如经营控比的 apple/tea 订单表）
> 2. 沿血缘向上追溯，收集所有相关生产 SQL
> 3. 用 LLM 从 SQL 中抽取结构化规则（CASE WHEN、WHERE、JOIN 条件）
> 4. 合并去重，形成该表的本体

#### 4.1.3 抽成结构化规则而不是一句话

> 硬规则（强制）：规则必须抽成结构化形式（如 `条件: ds > '20260510'`，`动作: 关联 dim_q99_apple_intl_cate_mapping_202605_v2`），而不是"用新版类目映射表"这种自然语言描述。

自然语言描述无法校验、无法比对，结构化规则才能被机器执行和验证。

#### 4.1.4 三道关验证，专防模型瞎编

本体构建最大的风险是"模型编了一条看似合理但实际不存在的规则"。为此设置三道关：

> 1. **血缘一致性校验**：抽取的规则必须能指回具体 SQL 节点和行号，找不到出处的规则自动丢弃
> 2. **SQL 语法校验**：用 sqlglot 校验规则对应的 SQL 片段能否通过语法解析
> 3. **人工抽检**：对抽取结果进行抽样 review，发现问题反馈到抽取逻辑

> 核心思路：宁可漏抽，不可错抽。漏了的规则后续可以补，编的规则一旦入库会污染整个本体。

#### 4.1.5 人工只在两处介入

1. **规则确认**：对本体自动构建的规则进行最终确认
2. **场景补充**：补充 AI 无法从 SQL 中抽取的隐性规则（如"这个字段在特定场景下要忽略"）

> 人工介入的目的是"兜底"，而不是"从头写"。80% 以上的规则由 AI 自动抽取完成。

### 4.2 本体资产构成

> 核心步骤
> - 基础语义：表结构、字段注释、血缘关系（来自元数据系统）
> - 业务规则：指标口径、过滤规则、关联规则（来自生产 SQL 自动抽取）
> - 场景约束：特定场景的处理逻辑（来自人工补充 + AI 辅助）

> 硬规则（强制）：每条规则必须带"证据"——指回哪个 SQL 节点的哪几行。没有证据的规则不允许入库。

> 本体资产以核心表为维度组织，每张核心表对应一份本体文件。

### 4.3 按需召回

> 核心步骤：
> 1. 解析用户需求，提取关键词（表名、指标名、业务概念）
> 2. 从本体库中召回相关表的本体文件
> 3. 将召回的本体作为上下文注入 prompt，指导 AI 生成 SQL

### 4.4 飞轮闭环：让本体越用越准

> 核心步骤：
> 1. AI 生成 SQL 后，与生产 SQL 进行比对
> 2. 差异点自动归因：是本体缺失规则，还是 AI 理解偏差
> 3. 缺失的规则自动回流到本体库，补充本体
> 4. 下次遇到类似需求，本体更完整，生成质量更高

> 这是一个"生成 → 评测 → 归因 → 修正"的自动闭环，本体随使用不断扩充。

### 4.5 技术复用：跨场景跨平台

本体构建能力不限于经营控比场景，已在多个场景复用：

> - 情报数据资产：跨部门的数据查询场景
> - 直播数据：直播间的 GMV、UV 等指标计算
> - 位置与用户：LBS 相关的业务规则

同时支持跨平台调用：

> - 本地 IDE：通过 Skill 调用
> - 钉钉群：通过机器人调用
> - Otter 平台：在线数据查询

> 技术架构统一：规则抽取 → 本体构建 → 按需召回 → SQL 生成，不同场景只需替换本体资产。

## 五、效果如何：评测技术验证

### 5.1 评测集构建：真实需求，持续扩充

评测集的 case 全部来自真实业务工单，每条 case 包含需求信息、依赖表、agent 需求输入等完整上下文，并绑定已上线的生产 SQL 作为 Ground Truth。评测集不是一次性维护的静态集合，而是通过 Omega 定时抓取 + LLM 自动分类实现自动入库，随业务需求增长持续扩充。

### 5.2 评测规则：五层递进检测

我们设计了五层递进检测，从语法、表、字段、业务规则到最终数据结果，逐层校验。不通过时自动归因到具体层级和原因，结果回流飞轮，形成"生成 → 评测 → 归因 → 修正"的自动闭环。

| 检测项 | 检测说明 |
|-------|---------|
| 语法对不对 | 关键字拼写、括号闭合、函数参数完整性 |
| 表找得对不对 | 所选表是否正确 |
| 字段找得对不对 | 字段有无缺漏、指标口径是否一致、聚合方式是否正确 |
| 业务规则对不对 | 提取 GT 的 CASE WHEN / WHERE / JOIN 节点，逐条在生成 SQL 中定位 |
| 跑出的数据对不对 | 对比输出表与 GT 运行结果是否一致 |

> 评测链路由 /pull-eval-set（拉取评测集 + 预处理）和 /eval-run（生成 SQL + 五维打分）两个 Skill 串联。

#### 5.2.1 拉取线上评测集

从 ODPS 表 `drival_ai.dim_dapan_demand_eval_202607` 增量拉取评测集，为每个新 case 在 `docs/eval_cases/<case_key>/` 生成三份文件。

#### 5.2.2 AI 生成 SQL

每条评测 case 按本体版本（v0 无本体 / v1～v5 各版本）用 LLM 生成 SQL，作为待评测代码。

> 硬规则（强制）
> ① 禁读 groundtruth.sql（也禁通过 `get_node_code` 查 `metadata.ground_truth` 节点代码）：不能抄答案。
> ② 只读当前版本本体：禁读其他版本 / shared 生产版本 / workspace 个人版本。

#### 5.2.3 五维评测

> 评分规则（按五层递进检测评分）

### 5.3 评测效果：有无本体对比

整体看，语法和选表已经稳定通过，瓶颈集中在复杂业务规则的完整还原上，这正是本体与飞轮下一步重点补强的方向。

| 检测项 | 无本体版本 | 本体版本 | 变化 |
|-------|----------|---------|------|
| 语法对不对 | 8/8 | 8/8 | 持平 |
| 表找得对不对 | 7/8 | 8/8 | ↑ 1 |
| 字段找得对不对 | 4/8 | 7/8 | ↑ 3 |
| 业务规则对不对 | 2/8 | 3/8 | ↑ 1 |
| 跑出的数据对不对 | 2/8 | 2/8 | 持平 |

以上述"2.2 餐线分赛道控比看板"需求为例：

> - 无本体时，AI 生成的类目映射规则基本错误，代码不可用，且遗漏了隐性的异常价格识别和过滤规则。
> - 引入 OntSQL Agent，类目映射规则仍有部分偏差，但只需少量改动即可上线，代码可用性大幅提升。

## 六、效果如何：业务场景验证

本章用数据开发场景的实际效果与经营控比业务方的真实反馈，从业务侧回答 OntSQL Agent 的落地情况：已常态化承接需求并持续交付结果，完成了从技术验证到业务价值的闭环。

### 6.1 数据开发模式的变化

引入 OntSQL Agent 后，数据开发的工作方式发生了明显变化：AI 承接业务理解并撰写代码初稿，研发从"逐行手写代码"转向"审核与兜底"。

**需求承接统计**

从需求交付节奏看，引入 OntSQL Agent 前 8 个月累计交付 51 个，而近 3 个月就交付了 60 个，月均需求处理量 20 个，开发提效 3.9 倍。这说明 AI 不仅提升了单需求开发效率，更实质性放大了整体的需求吞吐量。

> - 月均交付量：6个/月跃升至20个/月
> - 需求处理量：前8个月51个 VS 近3个月 60个
> - AI承接需求占比：54.7%（35 / 64）
> - 单表开发时长：人工开发134h → AI辅助开发34h
> - 开发效率：效率提升约3.9倍

**AI行占比统计**

月均 AI 代码行占比也在持续提升。经营控比场景从 4.75% 提升到 51%；"情报数据资产"部门从 3.11% 提升到 9.74%。这些数字共同说明，AI 已经从辅助工具升级为数据开发的实际生产力。

> - 经营控比：月均AI行占比 4.75% → 51%
> - 情报数据资产：AI行占比 3.11% → 9.74%

### 6.2 自助取数，不写SQL

除了服务于数据研发同学，也将 OntSQL Agent 部署到 Otter 在线平台，支持 BI 日常数据分析，改变了业务的取数方式：

| 对比维度 | 引入 AI 前（流通中心） | 引入 AI 后（Otter） |
|---------|-------------------|------------------|
| 支持场景 | 数据查询 | 数据查询、自助排查、AI 分析报告 |
| 使用方法 | 申请数据上架 → 审批 → 手写 SQL | 一键启用，自然语言交互 |
| 用户体验 | 链路长、门槛高 | 自助取数、即时响应、灵活多样 |

**推广应用案例：**

- **服饰行业**：业务发现"美洋"核心店铺成交异常后，自助借助 Otter 下钻到商品粒度，定位到商品价格异常，判断为原始数据采集问题；基于业务反馈，数据开发同学剔除商品表中异常价格，完成数据修复。

- **国际行业**：通过搭建包含类目 → 品牌 → 店铺 → 商品的逐层下钻的AI分析报告，帮助不同角色快速看清竞对控比情况，定位数据异动情况，识别竞对爆品和行业机会点。

### 6.3 真实使用中问题与改进

我们对 Otter 执行日志做了系统性分析，覆盖 113 个会话、7 位研发用户、2025-01 至 2026-08 的完整使用记录，发现当前 AI 在处理业务需求时，输出结果不理想主要集中在三个方面：

| 问题类型 | 占比 | 具体表现 |
|---------|------|---------|
| 用户输入模糊 | 55% | 首轮需求缺参数、缺维度、缺口径，导致 AI 按默认值开跑，需要用户多轮追加补充信息 |
| 本体覆盖不足 | 23% | 业务表覆盖率仅 59%，大量常用规则和先验知识未登记，AI 反复试错 |
| 平台配置缺失 | 13% | 平台代号到表前缀的映射关系缺失，出现"查tea数据却跑到apple表"的错配 |

针对这些问题，我们在短期和长期两个层面推进改进：

- **短期**：将"本体覆盖不足"问题分 P0-P3 优先级补齐本体缺口，在 `CLAUDE.md` 中补齐平台代号映射；
- **长期**：让每一次用户纠偏和业务补充都沉淀回本体，为AI提供更精准的业务本体资产。

## 七、展望

OntSQL Agent 下一步有两个迭代方向：

① 横向扩展更多场景：采购场景、内容域、位置与用户，复用本体构建与 SQL 生成能力；

② 纵向与执行层、权限层结合：当前权限依赖 D2 AK/SK，执行依赖 ODPS，未来希望把资产更新、动作执行、权限管理统一到本体框架下，实现语义层、动力层、动态层的完整架构。

## 八、结语

OntSQL Agent 是把本体引入数据研发的一次实践。它证明了一件事：当 AI 拥有结构化、可召回、可迭代的业务知识资产，复杂 SQL 的生成质量就能持续提升，数据开发领域的人机分工也将被重新定义。
