## 0. 实验设计与版本矩阵

**没有版本号的证据等于没有证据。** 本文全部结论仅对下表成立。

第二轮回答了「同平台换 API 形状，会变什么」。它留下的另一半是：**同模型换平台，会不会也变。**
本轮把这一半补上——两个平台恰好都提供 `deepseek-v4-flash`，于是构成一个 2×2：

| | OpenAI 兼容形状 | Anthropic 兼容形状 |
|---|---|---|
| **DeepSeek 官方** | `api.deepseek.com` | `api.deepseek.com/anthropic` |
| **阿里云百炼** | `…/compatible-mode/v1` | `…/apps/anthropic` |

> **四个端点、同一个模型 ID（`deepseek-v4-flash`）、同一套探针。**
> 因此任何差异都只能归因于「平台」或「形状」这两个因子之一，不能归因于模型能力。

| 项 | 值 |
|---|---|
| 模型 | `deepseek-v4-flash`（四个端点完全相同） |
| SDK | `openai` 6.49.0 / `@anthropic-ai/sdk` 0.65.0 |
| 运行时 | Node v22.22.3 |
| 实测日期 | 2026-08-23 |
| 探针 | P0–P8（沿用）＋ **P9 / P10（本轮新增）** |

**证据文件命名**：`raw/p<N>-<deepseek|bailian>-<openai|anthropic>-shape-<时间戳>.jsonl`，
本轮共 59 个文件，全部为 `2026-08-23T02:*`。第二轮（qwen3.7-plus）的文件为 `2026-08-22T*`，两轮不要混引。

**同一探针有多个时间戳时，以最新的为准。** P3/P4/P5/P7/P8/P9 都在修掉 §0.2 的缺陷后重跑过，
早于修复时间的那几份**结论文案是错的**（原始请求/响应仍然可信，错的是 `finding` 那几行）。

### 0.1 本轮新增的两个探针，都是被冲突逼出来的

| 探针 | 起因 | 产出 |
|---|---|---|
| **P9** assistant 回合的最小合法形态 | P2 说「推理块可删」，P3/P4/P8 却因为缺推理块被 400。同一平台上两条结论直接打架 | §3：DeepSeek 的推理块约束是**服务端有状态**，不是协议宽松 |

### 0.2 本轮修掉的四个探针缺陷

第二轮的教训是「结论文案本身要当成代码来评审」。本轮又抓到四处，全部会写出**错误的**架构输入：

| 缺陷 | 错误结论会是 | 修法 |
|---|---|---|
| P4 只比 `usage.input_tokens`，不含命中缓存的部分 | 「countTokens 偏差 **-600%**」——实际是 0.00% | 计费输入 = 未命中 + 命中读 + 写入 |
| P8 把任何 400 都读成「超过单块上限」 | 「单块上限 < 200KB」——实际 200KB 正常接受 | 拒绝原因必须由错误文案判定，判不出登记未解答 |
| P8 的大小判据把 429 `quota exceeded` 也算成大小超限 | 同上，且百炼侧会稳定误报 | 先排除配额/限流类错误 |
| P5 只判「命中归零 / 非零」二分 | 「DeepSeek 缓存不以严格前缀匹配为准」——实际是**部分失效**，掉到公共前缀 384 | 与基线比较，加入「部分失效」档 |
| P3 把任何 400 都读成「入参完整性被校验」 | 「Provider 校验了 tool 入参完整性」——实际是推理块缺失 | 同 P8，按文案归因 |

**这四条的共性**：探针把「失败」当成了「假设被证实」。负向实验里，**失败原因必须被独立确认**，否则每一个无关的错误都会变成一条自信的伪结论。

## 1. 一句话结论

> **协议不变量的外部兜底与上下文的可重建性，在这两个平台上是一对此消彼长的取舍。**
>
> DeepSeek 校验协议不变量（缺 tool_result、错 id 一律 400），但**服务端持有推理状态**，凭空构造的历史会被拒；
> 百炼什么都不校验（第二轮结论在本轮完全复现），但**完全无状态**，任何历史都能重放。
>
> 对 WorkAgent 这种「以重写上下文为核心职责」的 Harness，这不是「谁更好」，而是**两条不同的实现路径**。

## 2. 协议不变量：本轮最大的平台差异

> 影响：V03 §8.6 不变量 2、§12.5 toolCallId 锚点、§9.4（第二轮结论）
> 证据：`raw/p1-*-2026-08-23T*.jsonl`

| 负向实验 | DeepSeek(OpenAI) | DeepSeek(Anthropic) | 百炼(OpenAI) | 百炼(Anthropic) |
|---|---|---|---|---|
| 缺 3 个 tool_result | **400** | **400** | 200 接受 | 200 接受 |
| tool_call_id 篡改 | **400** | **400** | 200 接受 | 200 接受 |
| tool_result 逆序 | 200 接受 | 200 接受 | 200 接受 | 200 接受 |
| 入参不合 schema | 放行 | 放行 | 放行 | 放行 |
| 入参为空的 tool_use | 200 接受 | 200 接受 | 200 接受 | 200 接受 |

DeepSeek 的报错还指名道姓：

```
messages.1: `tool_use` ids were found without `tool_result` blocks immediately after:
call_01_NInA4xuRcRy8HLb7uHub9183, call_02_zYjLG838…
```

```
unexpected `messages.2.content.0: tool_use_id` found in `tool_result` blocks: toolu_bogus_id_000000
```

### 结论：第二轮的 §9.4 被证伪

第二轮写的是：

> 「宽松校验是**平台属性**，不是形状属性……换形状不能解决这个问题。」

前半句对，后半句的推论范围错了。**换平台可以解决。** 同一个模型、同样两种形状，DeepSeek 四格里有两格给出了外部兜底，百炼四格全部放行。

因此 §8.6 不变量 2 的理据要写成**两条并列**，而不是二选一：

> 1. 在有兜底的实现上：否则 Provider 直接 400，Run 立刻失败；
> 2. 在无兜底的实现上：否则模型看到的是一个失真的世界。
>
> **Runtime 必须按第 2 条实现**（它是下限，且换端点不会退化），第 1 条只是额外的早失败信号。

**但兜底的存在改变了错误分类**：在 DeepSeek 上，配对错误会以 `source=MODEL_PROVIDER, status=400` 出现；在百炼上永远不会。§13.1 的映射表必须允许同一个逻辑错误在不同端点有不同 `source`。

## 3. 【本轮最重要】DeepSeek 的推理块是服务端状态，不是协议字段

> 影响：V03 §11.5 `REQUIRED_VERBATIM`、§11.6 Compact 硬约束、原则十一、`:1505`【验】
> 证据：`raw/p9-deepseek-anthropic-shape-2026-08-23T02-45-36-431Z.jsonl`

### 冲突

P2 结论：删除推理块**被接受** ⟹ 推理块不属于 `REQUIRED_VERBATIM`，Compact 可以丢弃它。
P3 / P4 / P8 却都因为同一个 400 失败：

```
The `content[].thinking` in the thinking mode must be passed back to the API.
```

OpenAI 形状上是同一件事的另一副面孔：

```
The `reasoning_content` in the thinking mode must be passed back to the API.
```

两条观测不可能同时为真。P2 的结论是 §11.6 的直接输入，不解决就会把一条错误结论写进架构。

### P9：2×3 矩阵先排除了错误的解释

| assistant content 形态 | thinking 参数缺省 | thinking 显式 enabled |
|---|---|---|
| 仅 `tool_use` | **400** | **400** |
| `text` + `tool_use` | **400** | **400** |
| `thinking` + `tool_use` | 200 | 200 |

请求里的 `thinking` 参数**完全不影响**判定。决定因素是 assistant 回合里有没有 thinking 块。

但这还是解释不了 P2——P2 的负向 A 正是 `text + tool_use`，却过了。

### P9 阶段 2：唯一剩下的变量是 id

P2 回传的是**上一轮真实响应里的 id**，P9 阶段 1 用的是伪造 id。控制这一个变量：

| 条件 | 结果 |
|---|---|
| 真实 id + 删掉 thinking（＝ P2 负向 A） | **200** |
| 伪造 id + 删掉 thinking（其余完全相同） | **400** |

再看推理块里那个字段的**值**：

| | DeepSeek | 百炼 |
|---|---|---|
| Anthropic 形状 `signature` | `e1eecbda-9531-48f9-9064-b4d15d05e0ab` | `""`（空串） |
| OpenAI 形状 `encrypted_content` | `e5ccb644-…-0`（38 字符） | `null` |
| OpenAI 形状 `summary` | `[]`（空） | 有摘要正文 |

DeepSeek 那两个「签名」字段装的是 **UUID 句柄**，不是加密载荷；而推理正文的摘要**不回传给客户端**。
百炼恰好相反：不给句柄，但把摘要正文完整给你。

### 结论

**DeepSeek 的推理内容保存在服务端，按 id 索引。** 「推理块可删」不是协议宽松，而是服务端替你补回来了。
一旦重放的 id 不是该端点生成的——跨会话、换端点、或 Compact 之后重构历史——约束立刻重新出现。

这直接推翻第二轮对 `:1505`【验】的处置。第二轮写的是「当前部署下可按『无 verbatim 约束』实现」，
**该结论只对百炼成立，对 DeepSeek 不成立。**

**可落地的规避办法（已实测）**：assistant 回合只要带一个 thinking 块就能通过，而且

- 内容可以是 Runtime 合成的任意文本；
- `signature` 可以是空串。

也就是说 Runtime 不必保存真实推理内容，但**必须保留一个占位块**。这条比「推理块可自由丢弃」弱，比「必须逐字回传」强，是一条 V03 目前没有的中间档：

> `protocolRole` 需要第三种取值：`PLACEHOLDER_REQUIRED`——
> 内容可替换、可摘要、可清空，但**块本身不能消失**。
> `REQUIRED_VERBATIM` / 可自由丢弃这个二分不足以表达当前两个平台的并集。

`irreducibleTokens` 的量级因此改变：不是 0（第二轮结论），而是「每个带工具调用的历史回合 × 一个占位块的最小 token 数」。

### 未解答

- DeepSeek 服务端保留推理内容的 **TTL** 与跨会话可见性（本轮全部在同一分钟内完成，未测边界）；
- 占位块的最小合法尺寸（本轮用的是一句中文，未逼近下界）。

## 4. Token 会计：两家的 Anthropic 形状都精确到 0.00%

> 影响：V03 §11.6 阈值精度、§16.1 预算、`:2383`【验】
> 证据：`raw/p4-*-2026-08-23T*.jsonl`

| payload | 预估 | 实际 | 偏差 |
|---|---|---|---|
| 纯文本，无 tool 定义 | 88 | 88 | 0.00% |
| ＋2 个工具定义 | 448 | 448 | 0.00% |
| ＋system prompt | 468 | 468 | 0.00% |
| ＋一轮完整 tool_use/tool_result 往返 | 555 | 555 | 0.00% |
| 长文本 | 3283 | 3283 | 0.00% |

**两个平台的五行数字完全一致**（同一个模型、同一套 tokenizer）。`count_tokens` 在两家的 Anthropic 形状上都可用、都精确；两家的 OpenAI 形状都没有预估端点（`/tokenize` 404）。

**tool 定义固定开销 = 360 tokens**（2 个只有一个字符串参数的工具），四个端点一致（百炼 OpenAI 形状测得 361，差 1）。

### 差异在 usage 字段与固定底数

```
DeepSeek (Anthropic) ：input_tokens / output_tokens
                       cache_creation_input_tokens / cache_read_input_tokens / service_tier
DeepSeek (OpenAI)   ：prompt_tokens / completion_tokens / total_tokens
                       prompt_tokens_details{cached_tokens}
                       completion_tokens_details{reasoning_tokens}
                       prompt_cache_hit_tokens / prompt_cache_miss_tokens   ← 百炼没有
百炼 (Anthropic)     ：input_tokens / output_tokens
                       cache_creation_input_tokens / cache_read_input_tokens
                       prompt_tokens_details{cached_tokens}                 ← 混进了 OpenAI 风格字段
百炼 (OpenAI)        ：prompt_tokens / completion_tokens / total_tokens
                       prompt_tokens_details{cached_tokens}
                       completion_tokens_details{reasoning_tokens}
```

**每请求固定底数差 17 倍**：DeepSeek 单字符请求计 **84** prompt tokens，百炼计 **5**。
本地估算叠加的常量是**端点属性**，不是模型属性——同一个模型换平台就变。

**一个必须写进 `ModelProtocolPort` 的陷阱**：Anthropic 形状的 `usage.input_tokens` **不含命中缓存的部分**。
只读这一个字段会在缓存命中时低估计费输入（本轮实测 448 → 只读到 64）。
计费输入必须写成 `input_tokens + cache_read + cache_creation`。**这正是本轮 P4 的探针缺陷本身**（§0.2）。

### `:2383`【验】的处置

- **两家的 Anthropic 形状：可解除。** 0.00%，`estimated` 恒为 false；
- **两家的 OpenAI 形状：维持【验】。** 无端点可对标。
  但两家 Anthropic 形状的口径完全一致，可直接拿它作为本地 tokenizer 的对标基准。

## 5. 缓存：本轮唯一一个「两家都变好、但方式不同」的维度

> 影响：V03 §11.8、§11.6 Compact 策略、`:1594`【验】
> 证据：`raw/p5-*-2026-08-23T*.jsonl`

第二轮在 qwen3.7-plus 上测到的是「缓存不可预期」（基线就抖，Anthropic 形状只缓存固定的 378 tokens）。
换成 `deepseek-v4-flash` 后，四个端点的基线**全部 4/4 稳定命中**，命中量 4096–4864 tokens（约 98%）。

本轮新增一个对照条件来区分两种缓存实现——前缀是同一句话重复 500 次，只改第一处**区分不出**「严格前缀匹配」和「分块哈希匹配」：

| 端点 | 基线 | 只改第一处 | 全量改写 | 判定 |
|---|---|---|---|---|
| DeepSeek(Anthropic) | 4864 ×4 | **384** | 384 | **严格前缀**，回落到 tools+system 公共前缀 |
| 百炼(Anthropic) | 4096 ×4 | **0** | 0 | **严格前缀**，全量失效 |
| 百炼(OpenAI) | 4096/4864 ×4 | **0** | 0 | **严格前缀**，全量失效 |
| DeepSeek(OpenAI) | 4864 ×4 | 4864 | **4864** | **未判定**（见下） |

DeepSeek(Anthropic) 的 384 不是噪声：它**恰好等于** P4 独立测得的 tools + system 固定前缀。
即缓存正确地失效到了改写点之前的公共前缀——这给了 §11.8 一个比「成立/不成立」更有用的形态：

> **Compact 重写中部的代价 ∝ 改写点有多靠前。** 改写点之后的缓存全丢，之前的保留。
> 这把「追加式外置优于重写式压缩」从一句倾向变成了一条可估价的规则。

`:1594`【验】：**在三个端点上可升【定】**（严格前缀匹配，基线 4/4 稳定）。

### 未解答

**DeepSeek 的 OpenAI 形状：全量改写前缀后仍报告命中 4864 tokens。** 前缀被逐字换掉却仍满额命中，
这与任何基于内容的缓存都不相容。要么该形状的 `cached_tokens` 报的不是本次请求的实际命中，
要么命中来自本轮之外的条目。**在查清之前，不能用该端点的 `cached_tokens` 做成本核算。**
同平台的 Anthropic 形状行为正常，因此这是形状级问题，不是平台级问题。

缓存 TTL 两家都未测（需间隔重跑）。

## 6. 强制单条开关：差异是真的，3/3 稳定

> 影响：V03 §30 D-01
> 证据：`raw/p10-*-2026-08-23T*.jsonl`

「返回几个 tool call」是模型采样的结果，天然可能抖动，因此每档采样 3 次而不是 1 次：

| 端点 | 参数 | 参数缺省 | 显式关闭 | 判定 |
|---|---|---|---|---|
| 百炼(OpenAI) | `parallel_tool_calls:false` | 4/4/4 | **1/1/1** | **生效** |
| DeepSeek(OpenAI) | `parallel_tool_calls:false` | 4/4/4 | 4/4/4 | 被接受，**完全无效** |
| DeepSeek(Anthropic) | `disable_parallel_tool_use` | 4/4/4 | 4/4/4 | 被接受，**完全无效** |
| 百炼(Anthropic) | `disable_parallel_tool_use` | 4/4/4 | 4/4/4 | 被接受，**完全无效** |

四个端点全部**静默接受**该参数，其中三个不生效。**没有任何一个端点会告诉你「我不支持」。**

**D-01 的结论**：四格里只有一格有协议层保障，且它是最不可移植的那一格。
方案 C（接口按并发设计、v0.1 只实现串行）仍然成立，**理据只能是 Runtime 自持**。
把开关当保障会在换端点时静默失效——而且因为参数被接受，连报错都没有。

## 8. 错误分类：判别式四个端点各不相同

> 影响：V03 §13.1、§13.2
> 证据：`raw/p6-*-2026-08-23T*.jsonl`

| 触发 | DeepSeek(OpenAI) | DeepSeek(Anthropic) | 百炼(OpenAI) | 百炼(Anthropic) |
|---|---|---|---|---|
| 无效模型名 | 400 / `invalid_request_error` | 400 | **404 / `model_not_found`** | 400 |
| 无效 API Key | 401 / `invalid_request_error` | 401 | **401 / `invalid_api_key`** | 401 |
| 请求体格式错 | 400 / `invalid_request_error` | — | **400 / `invalid_parameter_error`** | 400 |
| 缺 `max_tokens` | — | **200 接受** | — | 400 |
| **tool 定义 schema 非法** | **400 ＋ 精确诊断** | **400 ＋ 精确诊断** | **200 接受** | **200 接受** |
| 超大单请求 | 接受 | 接受 | **429 `insufficient_quota`** | 接受 |

**DeepSeek 的 message 最有用，code 最没用。** 报错会列出全部合法模型名、指出 schema 具体哪里错
（`"not-an-object" is not of type "object"`），但 `type` 和 `code` **两个字段恒为 `invalid_request_error`**，
判别度为零——只能靠 HTTP status 加文本匹配。

**百炼的 OpenAI 形状 code 判别度最好**（`model_not_found` / `invalid_api_key` / `invalid_parameter_error`），
但 Anthropic 形状**连 type/code 都没有**，message 也最简短（`Model not exist.`）。

**§13.1 的映射表必须按端点维护，而不是按形状或按平台。** 四个端点没有任何两个可以共用一张表。

**tool 定义 schema 的校验是平台属性**（第二轮判定为形状属性，本轮证伪）：DeepSeek 两个形状都校验，百炼两个都不校验。

**tool 入参的校验仍是共性**：四个端点都放行不合 schema 的入参。
> §13.1 中 `source: TOOL_INPUT` 的错误**永远不会**来自 Provider。这是本轮唯一一条四格全等的负向结论。

**一个运行现实**：百炼的 OpenAI 形状对 60 万 token 的单请求返回 429 `insufficient_quota`（可稳定复现），
而同平台的 Anthropic 形状接受同一个 payload。长上下文场景下，配额是先于上下文窗口撞上的那堵墙。

## 9. 修正第二轮的 D-07 答案

第二轮的答案是：

> `ModelProtocolPort` 的抽象边界应当按 **API 形状**切分，而不是按模型家族切分。

本轮的 2×2 说明这句话**只对了一半**。把本轮全部差异按因子归类：

| 差异 | 归因 |
|---|---|
| 有无 token 预估端点 | **形状** |
| 有无流式闭合事件 | **形状** |
| 有无 `is_error` 带外字段 | **形状** |
| 推理块的载体形态 | **形状** |
| 协议不变量是否被校验 | **平台** |
| tool 定义 schema 是否被校验 | **平台** |
| 推理块是否服务端有状态 | **平台** |
| 错误判别式（status/type/code） | **端点**（四格各不相同） |
| 强制单条开关是否生效 | **端点** |
| 每请求固定底数（5 vs 84） | **端点** |
| 缓存匹配方式与命中量 | **端点**（同平台两形状都能不同） |
| tool 定义开销、计费口径、入参不校验 | **模型/共性** |

修正后的答案：

> **形状决定「协议长什么样」，平台决定「协议被执行到什么程度」，端点决定「具体数值」。**
>
> `ModelProtocolPort` 按 **API 形状**切分适配器是对的——它管的是解析与构造。
> 但**校验强度、有状态性、错误判别式、各项常量必须做成端点级的能力声明**，不能编译进适配器。
>
> 一个形状适配器 ＋ 一份端点能力声明，两者的生命周期完全不同：
> 前者随 SDK 版本变，后者**随时可能在没有任何通知的情况下变**（本轮七条里六条失效就是证据）。

这也意味着 §12 的「能力声明」不是可选项，而是 D-07 的落地形态。

并发开关 1/5：静默接受但完全无效（§6）。

**百炼 · Anthropic 形状 —— 73**
协议兜底 3/15：缺 result、错 id 全部 200 放行，零外部兜底（§2）。
错误可分类 4/10：连 `type`/`code` 字段都没有，message 最简短（§8）。
缓存 11/15：严格前缀匹配成立，但改写后的后续采样在 4096/4864 之间抖动。
容量 4/5：本轮触发过一次 429，重试后恢复。

**百炼 · OpenAI 形状 —— 65**
Token 会计 7/15：无预估端点，且 usage 缺 `prompt_cache_hit/miss` 拆分（§4）。
流式闭合 5/10：无 `content_block_stop`，只能靠「JSON 可解析 ＋ 后继 index 出现」推断。

**DeepSeek · OpenAI 形状 —— 57**
Token 会计 8/15：无预估端点，但 usage 字段是四家里最全的（含 hit/miss 拆分）。

目录广度 3/10、并发开关 1/5：同平台的 Anthropic 形状。

### 10.4 打分之外的一句话

**76 与 73 的差距没有实际意义**，两者是**取舍不同**而非优劣不同：

- 选 **DeepSeek(Anthropic)**：拿到协议兜底和最好的缓存形态，代价是接受「服务端有状态」，
  Runtime 必须为每个工具回合保留推理占位块，且被锁在 3 个模型上；
- 选 **百炼(Anthropic)**：拿到完全无状态的上下文（Harness 想怎么重写就怎么重写）和 241 个模型的退路，
  代价是所有协议不变量 100% 自持，且错误分类只能靠 status 加文本匹配。

**两个 OpenAI 形状都不建议作为 v0.1 的主力**——缺预估端点、缺流式闭合事件这两条是结构性的，
与平台无关，第二轮已经得出同样结论，本轮换模型换平台后依然成立。这是本轮**唯一一条跨两轮都没被推翻的建议**。

## 11. 方法论：本轮的教训

第二轮的教训是「结论文案要当成代码评审」。本轮的教训更具体：

**一、负向实验里，失败原因必须被独立确认。**
本轮四个探针缺陷（§0.2）全都是同一个形状：探针拿到一个 400，就把它当成「我的假设被证实了」。
实际那个 400 来自完全无关的原因（推理块缺失、账号配额）。
**一个负向实验只有在能说清「为什么失败」时才算数**，否则它比不做更糟——它会产出一条自信的伪结论。

**二、两条互相矛盾的观测是最有价值的信号，不要挑一条信。**
P2 说推理块可删，P3/P4/P8 说必须回传。如果当时选择相信 P2（它是「必答」探针，看起来更权威），
就会把「推理块可自由丢弃」写进 §11.6，而这在 DeepSeek 上是错的。
P9 完全是被这个矛盾逼出来的，而它产出了本轮最重要的一条结论。

**三、变量隔离做得再干净，结论依然不可移植。**
第二轮的「同平台同模型同 Key，只换形状」是个很干净的设计，但它的七条结论有六条换个模型/平台就不成立（§7）。
**Provider Facts 必须带端点粒度的版本号，并且要有过期意识。**

**四、抖动信号上，单次采样会给出自信的错误答案——这条第二轮就写过，本轮又用上了。**
P1 单次采样在两个平台上给出相反结果，P10 用 3 次采样确认差异是真的。
如果不复采，D-01 有 50% 的概率被写反。
