## 0. 一条贯穿全程的原则

**阶段划分的重心是「每阶段回答一个研究问题」，不是「每阶段交付一批功能」。**

这是这个项目区别于普通功能开发的地方，也是它作为学习导向项目的核心。每个阶段结束时，应该能说出「我们验证了 X」，而不只是「我们做完了 Y」。

## 2. Spike 0：Provider 协议现实核对 ✅

### 核心目标

V03 架构设计是在**零次真实 Provider 调用**的前提下写出来的。先把推测换成证据。

### 做成了什么

三轮，覆盖 **2 平台 × 2 形状 = 4 个端点**，75 份原始证据，11 个探针（P0–P10）。

**产出**

- `WorkAgent调研/ProviderProtocolFacts_V20260822.md`（第一、二轮）
- `WorkAgent调研/ProviderProtocolFacts_V20260823_R3.md`（第三轮）
- `spikes/s0-provider-protocol/raw/*.jsonl`（原始证据）
- 实测结论已全部吸收进当前架构设计 V05

### 最有价值的产出

不是那些数字，是一条方法论结论：

> **第二轮十条结论有六条换端点就不成立**，而第二轮的变量隔离已经做得很干净（同平台、同模型、同 Key，只换 API 形状）。

这直接催生了架构设计的 §8.6（端点能力声明）与【端点】状态标记。

### 遗留未答

缓存 TTL；OpenAI 形状本地 tokenizer 误差；加密推理块签名校验；SDK partial message 累积行为；429 错误体；DeepSeek OpenAI 形状 `cached_tokens` 异常。

对应条款保持【验】标记。

## 3. 阶段 1：Headless Walking Skeleton ✅

### 核心目标

主循环能跑通，且**端点差异一行都不进主循环**。

### 研究问题

> 端点差异能否被完全挡在主循环之外？批内配对不变量在没有状态机的情况下能否守住？

### 做完是什么样子

终端一条命令，真实百炼 Anthropic 端点，真做事：

```text
模型一次要多个工具
  → ActionBatch 串行执行
  → 每个 call 恰好一个 result
  → 回灌继续
  → 模型不再要工具
  → 具名 Terminal 退出
```

写文件前会停下来等确认，Ctrl+C 能取消。

> ⚠️ **「执行中能插话」当前不可用。** `runtime.interject()` API 与主循环第 ⓪ 步的排空逻辑都在，但 **CLI 没有任何调用点**，运行期间不监听 stdin。补 CLI 入口成本不高，归入阶段 2 的随手项。

**关掉终端就忘了**——transcript 只在内存里。

### 最小实现范围

- 主循环（`LoopState` ＋ 具名 `Continue` / `Terminal`）
- 形状适配器 `shape-anthropic-messages` ＋ 端点能力声明（Recorded 与 Live 双模式）
- In-memory transcript、FakeClock
- `resume()`：丢弃 `LoopState`，从 transcript 重建后继续
- 一个只读 Tool ＋ 一个**可控慢的**可验证写 Tool
- ActionBatch（`SEQUENTIAL` + `PER_ACTION`）
- 最小 ResolvedEffect、ErrorRecord、ContextFrame
- WAITING_FOR_USER / APPROVAL / Interject（均为进程内）
- 基本 Budget / Cancel

**10 个 Port 实现，4 个只留接口**（详见架构设计 §8.7 与 §30.1 D-14）。

### 不得绕过

Effect 解析、错误副作用状态、批内配对不变量、边界脱敏、`outcome.kind` 结算、端点能力声明的读取路径。

### 判据：三条可运行脚本（不写单测）

| 脚本 | 验证什么 | 挂了意味着 |
|---|---|---|
| `verify:endpoint-profile` | 用 `fake-endpoint-profile` 构造「校验配对＋推理块需占位」的虚拟端点，Runtime 行为正确改变而**主循环代码不变** | 端点能力声明没有真正落地，换端点仍需改主循环 |
| `verify:pairing` | 分别注入流式中断、工具执行中断和模型错误，transcript 中不存在无 result 的 tool_use | 消息级恢复下的批内配对代价比预估更大 |
| `verify:resume` | 批执行中途丢弃 `LoopState`，从 transcript 重建后继续，与不中断跑完的结果一致 | 消息级恢复粒度的选择不成立 |

这些脚本**输出可读证据供人判断**，不是断言绿灯——与 Spike 0 的探针形态一致。
（2026-08-25 起是四条：新增 `verify:compact`，见下方完成情况表。）

**第三条最关键：消息级恢复是当前架构最大的取舍，不验证它，阶段 1 结束时这个选择仍然没有运行证据。**

> ⚠️ **「三条中断路径全覆盖」这句原先的表述不成立。** §9.2 的三条是流式中断 / 工具执行中断 / 模型错误，脚本用「第二个 Action 被审批拒绝」代偿了「工具执行中被 cancel」那一条。脚本抬头已加免责说明，真正的注入还没补——`write_note` 支持 `delay_ms`，补一条「执行到一半 cancel」成本很低。详见[存量清单第 4 节第 1 条](../存量BUG/存量问题清单_V20260824.md)。

**边界判据（可 grep 复核）**：Provider SDK 只在形状适配器里；端点名不进 Runtime 代码；主循环不读 `profile.*`；Runtime Core 不 import Case Package。

#### 两个跑出来才发现的事实

1. **优雅 cancel 不会留下未配对的 tool_use** —— `finalize()` 已经补齐了。
   真正会留下未配对的只有进程硬崩。`verify:resume` 因此拆成两段，
   第二段直接往 transcript 注入硬崩状态，才真正走到 §18.2 的三条分支。
2. **`ApiShape` 类型定义会命中「形状名不进 Runtime」的 grep** ——
   但那是数据字段的定义域，不是端点行为编译进代码。判据需要区分注释、
   类型定义与真实依赖。

### 收尾复核（2026-08-24）

进阶段 2 之前重跑了一遍门槛，并在活端点上补了两次实跑。

**门槛复跑**：`tsc --noEmit` 干净；`npm run verify:all` **13 条判定全绿、退出码 0**；四条边界 grep 结论不变。

**活端点实跑两次**——这是原来缺的那一块：存量清单成稿时「没有对真实端点发起请求」，所有结论都是源码推断。

| 实跑 | 任务 | 结果 |
|---|---|---|
| A | 访问外网 URL → 转 Markdown ＋ 下载图片 ＋ 打 zip | 2 轮。工具集里没有网络能力，模型枚举完三个工具后正确拒绝 |
| B | 盘点 `2026Q2归档/` 四个子目录 → 写交接清单 ＋ 追加归档日志 | 4 轮完成。一次响应 4 个 call、`[Settled] 4/4`、WRITE 审批闸门、`✓ Verification（必需）`、IRREVERSIBLE 追加，产物落盘正确 |

实跑 B 是**阶段 1 工具集下一个完整的真实办公任务**，它一次压到了阶段 1 的四条关键路径（批内多 call 配对、审批闸门、必需验证、不可逆写）。这也标定了阶段 1 的能力边界：`list_dir` 只返回名字/大小/是否目录，**没有 read_file**，所以射程是「目录元数据 → 模型加工 → 文本产物」，凡是要读文件内容的都不在内。

**两次实跑各带出一条新缺口**，已写进存量清单：

- **R-7**（来自 A）：模型明确声明「做不了」、一个必需操作都没跑，仍然结算 `Outcome: SUCCESS`。A-1 修的是「跑过但没通过」，事实表为空时它按定义查不出东西。连带 `outcome.summary` 全仓无写入点，拒绝理由既不进 outcome 也打不到终端。
- **D-3**【验】（来自 A ＋ B 的逐轮 token 对比）：`count_tokens` 精确路径从第二轮起系统性低估（−103 / −133 / −139 / −393，随轮次放大），推断差额是**推理块**——它被回传、被计费，却不出现在 `count_tokens` 里，也因为主循环只 yield `text_delta` 而在终端上完全不可见。**这条必须先于 R-3 改阈值做**，否则是在一个不可信的基准上调阈值。

#### 三个跑出来才发现的事实

这三条都不是设计时想到的，是脚本或实跑撞出来的 —— 记在这里因为它们比结论本身更有价值。

1. **`verify:compact` 的 C 段判据两个方向都会骗人。**
   老判据是「帧内条目数出现过一次下降」。它在 HEAD 上是绿的，但压缩发生在
   `compileFrame` **内部** —— `ContextFrameCompiled` 报的永远是压缩**后**的帧，
   回不回写那一帧都是压过的。判别力实测（把回写那一行删掉）显示它**照样全绿**。
   换成看「每轮压缩的工作量」之后才有判别力：无回写时 freedTokens 单调递增
   （128→295→462→629→796，同一批老消息每轮被重压一遍），有回写时进入平台期。
   **一条绿了一个阶段的判据，其实一直没在测它声称在测的东西。**

2. **E-3 的自动放行规则从来没覆盖过它唯一为之而写的那个工具。**
   E-3 原文写「可逆（**覆盖写可逆**；追加、删除不可逆）」，实现写的是
   `reversibility !== "REVERSIBLE"` 就拒，而 `write_file` 声明 `PARTIALLY_REVERSIBLE`。
   2026-08-28 真实端点实跑撞出来：模型正确读完文档、正确生成汇总，两次写入都被
   「非交互环境下无人应答」挡掉，Run 结算 `USER_REJECTED` —— 而全程没有任何人拒绝过任何东西。
   与 §0.7 记的 U-6 同形：**一条闸门被另一条挡在后面，它想放行的东西从来没被放行过。**

3. **Progress Guard 一上线就照出两条验收脚本里的死循环形状。**
   `verify:compact` 与 `verify:budget` 的夹具都在逐字重复同一个调用，
   于是第 3 轮就被判成原地打转 —— 预算轴一条都还没撞到。
   这不是 Guard 太严：**那两个夹具本来就长得像死循环**，只是此前没有任何东西会说出来。

| 对破坏性行为的结构性盲区 | 检查以 `if (logBefore && logAfter)` 为前提 —— Agent 把日志整个删掉时该检查被静默跳过，`hardPassed` 仍为 true | 必须有一条「不该消失的东西消失了」的判据，且**前提不能是它还在** |
| provenance 不自洽 | `gitDirty` 含 untracked 而 `diffHash` 不含；live 模式 trace header 的 `modelId` 写死 `"live"` | 花钱实跑的 artifact 必须能回答「当时到底用的哪个模型、哪份工作树」 |
| **硬查任务没要求的数字** | 硬查 `20223`（全局合计字节），而任务原文只要求子目录级合计 —— 5 个 trial 里 4 个是模型自愿多给的 | 判据只能来自**任务原文**；逐 Run 变化的用户要求不得写死成硬门槛 |

|---|---|

### 研究问题

1. **一个通用 EXECUTE 能替掉多少专用工具？**
   —— 实测同时暴露四个缺口（打包 / 建目录 / 删除 / 移动），四个专用工具会让
   起步价一次涨 720 token。决 4 因此只加 `run_shell` 一个，让数据回答这个问题。
2. **既有的 Effect → Policy → 审批三段式，能不能吸收一个「本质上不可静态分析」的工具？**
   —— 这是 `effectResolution` 的 `RESOLVER` 分支第一次被真正需要
   （它从阶段 1 起就在类型里、一直抛错）。

### 做完了什么

- **`run_shell`** —— seatbelt 沙箱内执行 shell。两道闸门职责分离：
  静态判定只管审批档位，`sandbox-exec` 才是边界。
- **`ask_user`** —— 问用户一道选择题（ADR-0008）。
- **`fetch_url` 的 `as` 参数** —— HTML 默认转 Markdown（ADR-0007）。
- 打通 `RESOLVER` 分支；`EffectScope.kind: "PROCESS"` 第一次有消费者。
- 边界 grep 新增第 7 条（沙箱与命令解析不得进 Runtime）。

**14 个工具 / 起步价 2520 token；13 条验收脚本 / 115 条判据全绿。**

### 退出门槛（已达成）

原题复跑 3 次，逐项与基线对比：

| | 基线 | 复跑（×3） |
|---|---|---|
| zip | **不存在** | 3/3 生成，`unzip -l` 结构合格 |
| 轮数 | 19 | **12, 12, 12** |
| 打包脚本绕行 | 5 个 | **0** |

### 三个跑出来才发现的事实

1. **沙箱一度把 workspace 内的写也拒了。** macOS `tmpdir()` 是 `/var/folders/…`
   符号链接，而 seatbelt 按**真实路径**匹配 `subpath`。
   它**只在验了「能写的那一侧」时才暴露** —— 一个拒绝一切的沙箱与一个正确的沙箱，
   在「越界写被拦」那条判据下**不可区分**。
2. **仪器污染了自己。** 故障注入摘掉 `deny file-write*` 那次真的在 `$HOME`
   建出了探针文件；文件名写死，之后每次 `existsSync` 都为真，判据被**永久毒化**。
   → 仪器不得在被测系统之外留痕。
3. **`renderError(outcome.error!)` 这个非空断言掩着一条崩溃路径。**
   任何工具返回 `ok:false` 而忘了带 `error`，整个 Run 抛 TypeError，
   且批内配对被破坏（不变量 8）。而 `tools/` 这一层的全部意义就是让工具包
   能被独立地写、独立地接进来。已修（合成 `TOOL_CONTRACT_NO_ERROR`）。

### 一条被回源核对推翻的既有结论

存量清单把 **U-8**（不存在的 ask-user 工具）记为阶段 3 **已关**，
依据是 `request_handoff` 的文件头「两个洞是同一个」。

**回源核对 U-8 原文后：那句话对了一半。** U-8 说的是 `WAITING_FOR_USER`
这个枚举值零产出点 —— 状态机那一半确实关了；
「问一个没有外部动作的问题」那一半没关。判别它们的是 `expected_completion`
这个**必填**字段：用 handoff 问偏好，模型必须**编造**一个可观察结果，
而那个字段的全部意义就是「别信口头声明，去核实」。

> 【定】教训比结论重要：**「两个洞是同一个」这类判断要回源核对原文**，
> 不能因为它们表面上都「停下来等人」就合并。见 ADR-0008。

### 明确不做

- **`Glob`** —— 本仓 `search kind=name` 是子串不是 glob，缺口是真的。
  但 `run_shell` 现在能跑 `find`，**这正是研究问题 1 的下一个观察点**：
  先看数据，再决定要不要加。
- **`WebSearch`** —— 要外部 API ＋凭证，挡在 `SecretResolverPort`（决 2 判定 ⏸）上。
- **图片 / PDF 进上下文** —— 不是工具层能解决的：`ModelContent` 只有
  text / reasoning / tool_call / tool_result 四种，没有 image 块。
  要动 Runtime 类型 ＋ 形状适配器 ＋ 端点能力声明（不是所有端点支持 vision）。
- **`TodoWrite` / `Goal` / `Agent` / `Task*`** —— Planner 与 Sub-agent 是决 6 不做。
  `Goal` 的 Completion Audit 尤其危险：通用 Completion Gate 的论据
  **已被 `probe:requirement-extraction` 推翻**，抄回来等于把被证伪的东西请回去。

### 带进下一阶段的

- ⚠️ **默认档位下无人值守跑批时 EXECUTE 全灭**（非 TTY 审批按拒绝处置）。
  本批**不新增 `--yes-exec`** 去绕它 —— 那会又造一条没有证据支撑的闸门。
  等复跑数据说话。

   **阶段 3.5 记过同一条教训（「记进教训里的装饰会被抄到第二处去」），
