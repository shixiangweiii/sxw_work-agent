## 0. 一条贯穿全程的原则

**阶段划分的重心是「每阶段回答一个研究问题」，不是「每阶段交付一批功能」。**

这是这个项目区别于普通功能开发的地方，也是它作为学习导向项目的核心。每个阶段结束时，应该能说出「我们验证了 X」，而不只是「我们做完了 Y」。

## 2. Spike 0：Provider 协议现实核对 ✅

### 核心目标

V03 架构设计是在**零次真实 Provider 调用**的前提下写出来的。先把推测换成证据。

### 做成了什么

三轮，覆盖 **2 平台 × 2 形状 = 4 个端点**，75 份原始证据，11 个探针（P0–P10）。

**产出**

- `WorkAgent调研/ProviderProtocolFacts_V20260822.md`（第一、二轮）
- `WorkAgent调研/ProviderProtocolFacts_V20260823_R3.md`（第三轮）
- `spikes/s0-provider-protocol/raw/*.jsonl`（原始证据）
- 实测结论已全部吸收进当前架构设计 V05

### 最有价值的产出

不是那些数字，是一条方法论结论：

> **第二轮十条结论有六条换端点就不成立**，而第二轮的变量隔离已经做得很干净（同平台、同模型、同 Key，只换 API 形状）。

这直接催生了架构设计的 §8.6（端点能力声明）与【端点】状态标记。

### 遗留未答

缓存 TTL；OpenAI 形状本地 tokenizer 误差；加密推理块签名校验；SDK partial message 累积行为；429 错误体；DeepSeek OpenAI 形状 `cached_tokens` 异常。

对应条款保持【验】标记。

## 3. 阶段 1：Headless Walking Skeleton ✅

### 核心目标

主循环能跑通，且**端点差异一行都不进主循环**。

### 研究问题

> 端点差异能否被完全挡在主循环之外？批内配对不变量在没有状态机的情况下能否守住？

### 做完是什么样子

终端一条命令，真实百炼 Anthropic 端点，真做事：

```text
模型一次要多个工具
  → ActionBatch 串行执行
  → 每个 call 恰好一个 result
  → 回灌继续
  → 模型不再要工具
  → 具名 Terminal 退出
```

写文件前会停下来等确认，Ctrl+C 能取消。

> ⚠️ **「执行中能插话」当前不可用。** `runtime.interject()` API 与主循环第 ⓪ 步的排空逻辑都在，但 **CLI 没有任何调用点**，运行期间不监听 stdin。补 CLI 入口成本不高，归入阶段 2 的随手项。

**关掉终端就忘了**——transcript 只在内存里。

### 最小实现范围

- 主循环（`LoopState` ＋ 具名 `Continue` / `Terminal`）
- 形状适配器 `shape-anthropic-messages` ＋ 端点能力声明（Recorded 与 Live 双模式）
- In-memory transcript、FakeClock
- `resume()`：丢弃 `LoopState`，从 transcript 重建后继续
- 一个只读 Tool ＋ 一个**可控慢的**可验证写 Tool
- ActionBatch（`SEQUENTIAL` + `PER_ACTION`）
- 最小 ResolvedEffect、ErrorRecord、ContextFrame
- WAITING_FOR_USER / APPROVAL / Interject（均为进程内）
- 基本 Budget / Cancel

**10 个 Port 实现，4 个只留接口**（详见架构设计 §8.7 与 §30.1 D-14）。

### 不得绕过

Effect 解析、错误副作用状态、批内配对不变量、边界脱敏、`outcome.kind` 结算、端点能力声明的读取路径。

### 判据：三条可运行脚本（不写单测）

| 脚本 | 验证什么 | 挂了意味着 |
|---|---|---|
| `verify:endpoint-profile` | 用 `fake-endpoint-profile` 构造「校验配对＋推理块需占位」的虚拟端点，Runtime 行为正确改变而**主循环代码不变** | 端点能力声明没有真正落地，换端点仍需改主循环 |
| `verify:pairing` | 分别注入流式中断、工具执行中断和模型错误，transcript 中不存在无 result 的 tool_use | 消息级恢复下的批内配对代价比预估更大 |
| `verify:resume` | 批执行中途丢弃 `LoopState`，从 transcript 重建后继续，与不中断跑完的结果一致 | 消息级恢复粒度的选择不成立 |

这些脚本**输出可读证据供人判断**，不是断言绿灯——与 Spike 0 的探针形态一致。
（2026-08-25 起是四条：新增 `verify:compact`，见下方完成情况表。）

**第三条最关键：消息级恢复是当前架构最大的取舍，不验证它，阶段 1 结束时这个选择仍然没有运行证据。**

### 实际完成情况（2026-08-25 复核）

| 项 | 结果 |
|---|---|
| 代码 | 57 个 TS 文件 / 9337 行，`tsc --noEmit` 干净 |
| Port | 14 个接口，10 个实现（与 D-14 一致）。`TranscriptStorePort` 新增 `nextSequence()`（D-2） |
| 真实端点 | 百炼 Anthropic 形状跑通多轮多工具任务，具名 Terminal 退出；归档盘点任务 **4 轮**完成（评测基线 7 轮） |
| `verify:endpoint-profile` | ✅ 换端点声明 → Runtime 行为改变，主循环文件字节未变 |
| `verify:pairing` | ✅ **8 个场景** call/result 一一对应（含 R-4 四条 Port 异常注入）；⚠️ 中断路径仍是**两条真注入 ＋ 一条代偿**（见下） |
| `verify:resume` | ✅ 丢弃 LoopState 后仅凭 transcript 重建并继续到终态；B3 段验 ABORT 决策的收尾，C2 段验 D-2 序列跨 resume 不重号 |
| `verify:compact` | ✅ **新增**。Compact 真的落地：回写 `state.messages`、写 `COMPACT_BOUNDARY`、`targetTokens` 收敛、块级剥离推理块 |
| `probe:reasoning-tokens` | ✅ **新增**（一次性、真实端点、不在 `verify:all` 里）。D-3 结论：`count_tokens` 对 thinking 块一个 token 都不算 |
| 事件流落盘 | ✅ CLI 默认写 `.workagent-runs/*.jsonl`（`--no-trace` 关） |

> ⚠️ **「三条中断路径全覆盖」这句原先的表述不成立。** §9.2 的三条是流式中断 / 工具执行中断 / 模型错误，脚本用「第二个 Action 被审批拒绝」代偿了「工具执行中被 cancel」那一条。脚本抬头已加免责说明，真正的注入还没补——`write_note` 支持 `delay_ms`，补一条「执行到一半 cancel」成本很低。详见[存量清单第 4 节第 1 条](../存量BUG/阶段1存量问题清单_V20260824.md)。

**边界判据（可 grep 复核）**：Provider SDK 只在形状适配器里；端点名不进 Runtime 代码；主循环不读 `profile.*`；Runtime Core 不 import Case Package。

#### 两个跑出来才发现的事实

1. **优雅 cancel 不会留下未配对的 tool_use** —— `finalize()` 已经补齐了。
   真正会留下未配对的只有进程硬崩。`verify:resume` 因此拆成两段，
   第二段直接往 transcript 注入硬崩状态，才真正走到 §18.2 的三条分支。
2. **`ApiShape` 类型定义会命中「形状名不进 Runtime」的 grep** ——
   但那是数据字段的定义域，不是端点行为编译进代码。判据需要区分注释、
   类型定义与真实依赖。

### 收尾复核（2026-08-24）

进阶段 2 之前重跑了一遍门槛，并在活端点上补了两次实跑。

**门槛复跑**：`tsc --noEmit` 干净；`npm run verify:all` **13 条判定全绿、退出码 0**；四条边界 grep 结论不变。

**活端点实跑两次**——这是原来缺的那一块：存量清单成稿时「没有对真实端点发起请求」，所有结论都是源码推断。

| 实跑 | 任务 | 结果 |
|---|---|---|
| A | 访问外网 URL → 转 Markdown ＋ 下载图片 ＋ 打 zip | 2 轮。工具集里没有网络能力，模型枚举完三个工具后正确拒绝 |
| B | 盘点 `2026Q2归档/` 四个子目录 → 写交接清单 ＋ 追加归档日志 | 4 轮完成。一次响应 4 个 call、`[Settled] 4/4`、WRITE 审批闸门、`✓ Verification（必需）`、IRREVERSIBLE 追加，产物落盘正确 |

实跑 B 是**阶段 1 工具集下一个完整的真实办公任务**，它一次压到了阶段 1 的四条关键路径（批内多 call 配对、审批闸门、必需验证、不可逆写）。这也标定了阶段 1 的能力边界：`list_dir` 只返回名字/大小/是否目录，**没有 read_file**，所以射程是「目录元数据 → 模型加工 → 文本产物」，凡是要读文件内容的都不在内。

**两次实跑各带出一条新缺口**，已写进存量清单：

- **R-7**（来自 A）：模型明确声明「做不了」、一个必需操作都没跑，仍然结算 `Outcome: SUCCESS`。A-1 修的是「跑过但没通过」，事实表为空时它按定义查不出东西。连带 `outcome.summary` 全仓无写入点，拒绝理由既不进 outcome 也打不到终端。
- **D-3**【验】（来自 A ＋ B 的逐轮 token 对比）：`count_tokens` 精确路径从第二轮起系统性低估（−103 / −133 / −139 / −393，随轮次放大），推断差额是**推理块**——它被回传、被计费，却不出现在 `count_tokens` 里，也因为主循环只 yield `text_delta` 而在终端上完全不可见。**这条必须先于 R-3 改阈值做**，否则是在一个不可信的基准上调阈值。

### 预期 ADR（待补写）

主循环形态与消息级恢复粒度的取舍；ActionBatch 执行模式与结算默认值；完成判定为循环终止规则；端点能力声明的最小字段集。

### 已知会跑不到的路径

主循环第 ① 步有 Compact，但普通任务撞不到上下文墙。阶段 1 结束时应当明确知道：**Compact 写了但没被真跑过。**

> 存量清单 R-6 在这句话上补了一层，性质不同，不要混为一谈：**跑到了也不对。** 压缩只作用于 `compileFrame` 内的局部变量，不回写 `state.messages`；从不写 `COMPACT_BOUNDARY`；`targetTokens` 收了但一次没读。前者是覆盖率问题，后者是正确性问题——所以 R-6 是阶段 2 的开工前置，必须早于 Replay。

## 4. 阶段 2：持久化与 Resume ⬜（下一步）

### 开工前置（四条，做完再动 SQLite）

这四条不是「重要」，是**不做会污染后续、事后收不回来**。功能缺失可以后补，结构性污染补不回来。

| 前置 | 必须早于 | 不做会怎样 |
|---|---|---|
| **D-2** event / transcript 序列统一 | SQLite 落盘 | 带病进库，§23.2 的 Layer 2 投影游标没法收拾 |
| **R-6** Compact 落地 | Replay | 不回写 `state.messages`、不写 `COMPACT_BOUNDARY`，Replay 的重建语义从第一天起就对不上 |
| **R-4** Port 异常收敛 | 换 Port 实现 | in-memory → SQLite 就是换实现，异常口径不先收敛，出问题分不清是存储还是 Runtime |
| **D-3** 推理块 `count_tokens` 探针【验】 | R-3 改阈值 | R-3 要改的阈值基准建立在「精确路径可信」上，这条如果成立，前提不成立 |

前三条出自[存量清单第 7 节](../存量BUG/阶段1存量问题清单_V20260824.md)的处置顺序，第四条是 2026-08-24 活端点实跑的新增。

### 核心目标

从「能干活但记不住」变成「记得住、崩了能接上」。

### 研究问题

> 消息级恢复够不够用？哪些工具因为非幂等而无法安全 resume？

### 做完是什么样子

transcript 落 SQLite。关掉终端明天再开，`resume` 能接上昨天那个 Run。Artifact 有登记，Replay 能从 transcript 任意一条消息重放，故障注入 Eval 全集能跑。

**同时接上 DeepSeek Anthropic 端点做对照测试**——把 Runtime 产出的请求打到一个真正会校验的端点上，是一次免费的正确性检查。

### 范围

SQLite transcript、Blob；timeout / cancel / retry / error taxonomy 全集；Capability live lease（含 PARKED）、Policy、Approval；`resume()` 与 Recorded Replay；Artifact Registry；数据保留与 GC 最小实现；故障注入 Eval 全集；端点能力回归 ＋ DeepSeek 对照测试。

### 退出门槛

三个 crash 窗口、cancel race、未配对 tool_use 的三条处置分支均有可重复验证；对照端点未发现自持逻辑的系统性缺陷。

### 本阶段真正要回答的问题

比退出门槛更重要的一条：

> 跑够多真实任务，**统计有多少次 `resume()` 落进了「非幂等且不可观察」那条分支。**

比例低到可忽略，说明当前消息级恢复粒度选择成立；比例不低，再考虑把恢复粒度往细里推。

**但那时会有真实数据支撑，而不是推演。**

#### ⚠️ 开工前先定：这个统计的样本从哪来

**阶段 2 不加工具。** 能跑的「真实任务」就是 2026-08-24 实跑 B 那种目录盘点类——三个 Micro Case 工具里只有 `append_log` 落在「非幂等且不可观察」那一格。用这个工具集去统计分支比例，样本天然偏斜。

两条路，开工前必须选一条：

- **A. 靠故障注入 Eval 造样本**——在阶段 2 范围内、可行，但那是**构造的分布，不是真实分布**，用它下「恢复粒度选对了」的结论不成立；
- **B. 承认这个问题要等阶段 3 有真工具才能真答**，阶段 2 只把**测量装置**建好（分支计数落 transcript、Eval 能导出分布），不出结论。

**当前倾向 B**，并建议把退出门槛相应改成「测量装置可用」而不是「比例低于某个值」。否则门槛会卡在一个当前工具集根本给不出的数据上——那正是 D-03 / D-15 / D-08 三个决策点「被取消而非回答」的同一类毛病（见 §7）。

## 5. 阶段 3：Case 01 网页归档 ⬜

### 核心目标

第一个真实业务 Case 端到端，并且**跟确定性 Workflow Baseline 比一次**。

### 做完是什么样子

登录态网页抓下来，归档成 Markdown ＋ Manifest ＋ Report ＋ ZIP，Action 级与 Artifact 级两层 Verification 通过。

浏览器 Capability 有并发 lease，登录态经 RedactionProfile 处理，遇到验证码能人工接管（PARKED lease 全链路），长媒体下载能取消、能报进展，大结果外置到 Blob 再按需取回。

**Workspace × Endpoint 数据边界在这一阶段落地**——因为这是第一次有真正敏感的内容要发给第三方端点。

### 判据

> **Agent 编排相对确定性 Baseline 是否有增益？**

这是整个项目「Agent 到底值不值」的第一次真实回答。没有这个对比，Case 01 只证明了「能做」，没证明「值得用 Agent 做」。

⚠️ **V05 §28.4 将这一判据标为当前倾向，正式研究问题与退出门槛仍待补齐。** 真走到这一阶段之前应当完成冻结。
