# 08. 源码实战阅读路线

## 1. 目标：不是“看完”，而是能独立解释一次 Run

完成这条路线后，你应该能拿一个真实 Run 的 runId，回答：

- 它从哪个入口创建，用了什么冻结条件；
- 每轮模型看到了什么，花了多少 token；
- 每次工具调用如何被解析、批准、执行和验证；
- 最终哪些产物被 Atlas 背书，为什么；
- 如果在任意关键窗口杀掉进程，resume 会走哪条分支；
- UI 上一张卡片的数据来自 transcript、RunEvent、SQLite、Trace 还是进程内状态。

建议按“一个纵向切片 + 六个横向专题”完成，不要一开始逐文件从头读到尾。

## 2. 准备一个专用学习 workspace

不要用仓库根做第一个实验。先创建一个专用目录，避免阅读实验污染源码：

```bash
mkdir -p /tmp/atlas-source-reading
npm run ui -- --workspace /tmp/atlas-source-reading --approval default --sandbox on
```

浏览器打开终端打印的带 Token URL。第一个任务建议足够短，但必须经历读、写和交付：

```text
列出当前工作目录；写一份 reading-demo.md，包含目录中文件数量、文件名清单和生成时间；写完后重新读取核对内容，并把它作为最终交付物。
```

这个任务会让你看到：list_dir / now / write_file / read_file、自动审批、Action Verification、Artifact 登记、逐轮预算和最终 outcome。

## 4. 第二遍：在网页上把源码与白盒面板对起来

### 时间线

打开网页“时间线”，找一张工具活动卡。对应数据由 [`projectTimeline()`](../../apps/workagent-service/src/projection.ts#L53-L68) 投影：

- tool call 的 name/input 主要来自 transcript assistant MESSAGE；
- result 来自 transcript tool MESSAGE；
- effect、审批、Attempt、Verification、Artifact 等来自 RunEvent；
- 两条轨道用 sequence 合并。

练习：在同一张卡片上分别指出一个 transcript 字段和一个 event 字段。

### 逐轮解剖

对应 [`projectTurns()`](../../apps/workagent-service/src/projection.ts#L501-L670)。重点看：

- ContextFrameCompiled → frame token；
- ModelInvocationCompleted → usage、stopReason、duration；
- RUN_META → `budgetAfter`；
- LoopContinued/LoopTerminated → 具名迁移；
- 同一 turn 可有多次 model call，不能按 turn 覆盖。

练习：找到一轮的 billed input token，并解释它为何不一定等于 input token。

### 预算

UI 不自己拼轴；RunHost 调 [`readBudgetAxes()`](../../packages/harness-runtime/src/budget/index.ts#L202-L259) 返回 Runtime 的同一张权威映射。练习：找到 total wall-clock 与 active wall-clock 的差异，并解释等待审批时哪个会继续增长。

### 产物

从 UI 里的 artifactId 回到：

1. `ArtifactRegistered` 事件；
2. SQLite `artifacts` 行；
3. `ArtifactVerified` 事件；
4. outcome 的 `deliveredArtifactIds`。

练习：解释“登记过但不在 deliveredArtifactIds”至少有哪三种可能：INTERMEDIATE、检查失败、被后续版本取代。

### Trace

Trace 是 `header / event / footer` JSONL。RunHost 使用与 CLI 相同的 [`FileTraceSink`](../../apps/cli/src/trace/file-sink.ts#L1)，本段 sink 创建在 [`run-host.ts:1210-1253`](../../apps/workagent-service/src/run-host.ts#L1210-L1253)，footer 在 [`run-host.ts:1256-1271`](../../apps/workagent-service/src/run-host.ts#L1256-L1271)。

练习：在 Trace 里定位 `RunStarted → TurnStarted → ContextFrameCompiled → ModelInvocationCompleted → ActionBatchPlanned`。

### 模型调用审计

只展开一次 invocation，核对四层：

- 实际 request body；
- SDK 解码 Provider events；
- Runtime 规范化结果；
- UI 派生的易读上下文。

练习：找出 request body 中的 tools、system、messages 和 `cache_control`；再在 Runtime 结果中找 toolCalls。

## 5. 第三遍：六个横向专题

### 专题 A：一次工具调用

从 [`settle-batch.ts:203`](../../packages/harness-runtime/src/action/settle-batch.ts#L203) 开始，只跟一个 `write_file`：

```text

→ effects.resolve
→ ActionProposed
→ evaluatePolicy
→ approvalDecider
→ observePre
→ CommonToolHandler.execute
→ redaction
→ CommonVerifier.verify
→ ArtifactStore.register
→ ArtifactChecker.check
→ ledger.settle
```

在纸上画出每一步输入/输出类型，特别标记哪里还是模型输入、哪里已经是可信 Runtime 事实。

### 专题 B：一次模型调用

从 [`compileFrame()`](../../packages/harness-runtime/src/context/compile.ts#L91) 到 [`AnthropicModelPort.invoke()`](../../adapters/shape-anthropic-messages/src/client.ts#L55)：

```text
ContextMessage[]
→ ContextFrame
→ Anthropic body
→ Provider SSE events
→ PartialBlock map
→ ModelInvocationResult
```

练习：找出 reasoning 增量为什么不实时 yield，但最终仍可能进入 content。

### 专题 C：一次 UI 刷新

从 [`connectSSE()`](../../apps/workagent-ui/public/app.js#L3079) 跟到：

```text
EventSource message
→ ModelStreamDelta 立即绘制 / 其他事件 scheduleRefresh
→ GET /api/state
→ GET /api/runs/:id
→ RunHost.detail
→ projectTimeline + projectTurns
→ renderView
```

练习：解释为何非 delta 不做客户端增量合并。

### 专题 D：一次 Compact

把 context policy 的阈值想象得很小，跟：

```text
count > soft
→ compactMessages
→ 并查集 protocolUnits
→ Resource recovery index prepare
→ 新 frame 精确计数与校验
→ COMPACT_BOUNDARY commit
→ state.messages 替换
```

练习：手写三条包含两个 tool calls 的消息，自己运行一遍并查集合并结果。

### 专题 E：一次 crash + resume

跟 [`HarnessRuntime.resume()`](../../packages/harness-runtime/src/facade/index.ts#L242)：

```text
frozen spec gates
→ transcript/messages/facts
→ unpaired scan
→ idempotent / observe / recovery-required
→ pair result
→ inherited runLoop
```

练习：分别判断 read_file、write_file、edit_file、append_log、MCP execute 在“没有 result”时可能走哪条分支，以及前置指纹如何改变答案。

### 专题 F：一次最终结算

从 [`finish()`](../../packages/harness-runtime/src/loop/run-loop.ts#L318) 跟到 [`settleOutcome()`](../../packages/harness-runtime/src/verification/settle-outcome.ts#L42)。

练习：构造四组事实：全部通过、用户明确拒绝、坏 DELIVERABLE、只有坏 INTERMEDIATE，写出预期 kind。

## 7. 不开调试器也能做的“事实取样”

### 查 SQLite 表

Node 24 自带 `node:sqlite`，但本仓没有要求安装 sqlite3 CLI。更推荐通过白盒 Query 和已有 verify 脚本观察，避免自己打开第二个句柄误判并发状态。

如果本机已有 `sqlite3`：

```bash
sqlite3 /tmp/atlas-source-reading/.workagent/runs.db '.tables'
sqlite3 /tmp/atlas-source-reading/.workagent/runs.db \
  'select run_id,status,task,updated_at from runs order by updated_at desc limit 5;'
sqlite3 /tmp/atlas-source-reading/.workagent/runs.db \
  'select sequence,kind,created_at from transcript_entries where run_id="你的runId" order by sequence;'
```

不要修改这些行；本练习只读。

### 查 Trace

```bash
sed -n '1,80p' /tmp/atlas-source-reading/.workagent/runs/你的runId.jsonl
rg -n 'RunStarted|ContextFrameCompiled|ActionProposed|ArtifactVerified|LoopTerminated' \
  /tmp/atlas-source-reading/.workagent/runs/你的runId.jsonl
```

### 查模型审计

```bash
find /tmp/atlas-source-reading/.workagent/model-invocations/你的runId -type f -maxdepth 1 -print
```

这些文件含真实请求内容，不要提交或分享。

## 8. 用验收脚本学习，而不只是跑绿灯

每个专题先读脚本的“判据”，再运行。Atlas 的验收脚本会打印人可读证据，不只是断言。

| 专题 | 脚本 | 重点 |
|---|---|---|
| 主循环配对 | `npm run verify:pairing` | 三条中断路径是否都有 result |
| Compact | `npm run verify:compact` | 压缩是否真的回写并可恢复 |
| 跨进程 | `npm run verify:persistence` | 真 kill -9 后只凭 SQLite 能否接上 |
| 恢复分支 | `npm run verify:resume` / `verify:crash` | 三分支与三个崩溃窗口 |
| 预算 | `npm run verify:budget` | 八条轴逐一撞墙 |
| 工具边界 | `npm run verify:tools` | 声明、依赖、路由、恢复观察 |
| shell | `npm run verify:shell` | 命令只读判定与沙箱 |
| UI | `npm run verify:ui` | Layer 2 不推进语义、投影、并发与恢复可见性 |
| MCP | `npm run verify:mcp` | 通用桥接、档位、schema、生命周期、漂移 |
| 产物/资源 | `verify:artifact` / `verify:resource` | 两层验证、二进制与外置取回 |

最有学习价值的做法：在临时分支上故意改坏脚本注释指出的“一行”，观察它如何由绿变红，再撤销自己的实验改动。不要在当前 main 工作区直接做破坏实验。

## 9. 四个源码练习

### 练习 1：增加一个无副作用工具（只做设计，不一定提交）

写出它需要的完整 `ToolDefinition`，回答：

- schema 是否显式禁额外字段；
- Effect 是 NONE 还是 READ；
- redaction 档位；
- 幂等/只读；
- timeout/progress；
- Verification 是否有真实消费者；
- recoveryObservation 是否诚实；
- 它是场景工具还是机制工具。

若任何字段只是“先填着”，却找不到 Runtime 消费点，重新评估是否应该存在。

### 练习 2：手推一次 write_file

给定 `path="out/a.md"`，从 resolve 到 policy：

1. 绝对 scope 是什么；
2. riskFacts 有哪些；
3. SANDBOXED + DEFAULT 是否自动批准；
4. observePre 拍到文件不存在时 fingerprint 是什么；
5. 执行后 Action Verification 比什么；
6. Artifact Checker 还会多检查什么；
7. 最终 artifactId 如何形成版本。

### 练习 3：手推一次崩溃

分别假设崩在：

- AttemptStarted 之前；
- 工具已写完但 result 未落盘；
- result 已落盘但 RUN_META 未落盘。

回答 transcript 能看到什么，sequence_counter 能看到什么，resume 会如何处理。

### 练习 4：给 UI 加一个只读指标（只做设计）

先问：

- 这个事实 Runtime 已经产生了吗；
- 它在 transcript 还是 event；
- RunHost.detail 能否原样转述；
- projection 是否能从两条轨道唯一推出；
- UI 是否会误把“当前值”展示成“历史冻结值”。

如果必须让 Layer 2 自己猜执行语义，应该先停下来重新定位事实缺口。

## 10. 阅读源码时的常见误区

1. **把长注释当实现。** 一定继续找生产者、消费者和验收判据。
2. **把类型联合中的值当可达行为。** 用 `rg` 找实际写入点。
3. **把 UI 显示值当权威。** 追到 RunHost.detail、projection，再追到 Runtime/SQLite。
4. **把 `ok: true` 当任务成功。** 继续看 sideEffectState、Verification、ArtifactCheck、RunOutcome。
5. **把“有沙箱”泛化到 MCP。** shell seatbelt 与外部 MCP 是不同边界。
6. **把 role 当来源。** 来源读 `origin`。
7. **把当前 compose 配置当历史 Run 条件。** 历史条件读冻结 RunSpec。
8. **把 Trace 当恢复日志。** 恢复只读 transcript + RunSpec/RUN_META。
9. **把自动批准当没有 Policy。** Policy 仍产生 REQUIRE_APPROVAL，decider 才自动批准并留下来源事实。
10. **试图一次看完 30k 行。** 始终带着一个问题和一条链路读。

## 11. 四周学习节奏建议

### 第 1 周：纵向链路

- 完成第 2、3 篇；
- 真实跑 3 个小任务；
- 能手画 Web → loop → tool → UI 的序列图；

- 完成第 4 篇；
- 手推一次 Compact 并查集；
- 对照一次真实模型审计；
- 运行 compact、endpoint-profile、model-audit。

### 第 3 周：持久化与恢复

- 完成第 5、6 篇；
- 手推三个崩溃窗口；
- 运行 persistence、resume、crash；
- 能解释每张 SQLite 表的唯一职责。

- 完成第 7 篇；

- 运行 shell、artifact、resource、mcp；
- 选一个验收脚本，做一次真正的红→绿实验。

## 12. 最终自测

不看指南，用 15 分钟讲清以下故事：

> “我从网页提交一个需要抓网页、写 Markdown、打 ZIP 的任务。Atlas 如何冻结执行条件，如何在每轮构造模型请求，如何把模型工具意图变成受控副作用，如何处理大结果与二进制，如何验证交付物，如何把过程投影回网页；如果打 ZIP 后进程突然被 kill，为什么下次 resume 有时会重试、有时先观察、有时必须问我？”

能准确讲清，而且能指出相应源码入口，说明你已经从“会使用 Atlas”进入“掌握 Atlas 的执行模型”。
