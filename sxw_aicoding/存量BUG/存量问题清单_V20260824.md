## 0.3　同批新发现（清单原先没有登记）

1. **Compact 的保护规则让消息级压缩在本架构下不可达** —— 已随 R-6 修掉。
   原规则是「任何一条消息只要含 `tool_call` 或 `tool_result` 就整条保护」。理由正当（拆开配对违反不变量 8），
   但在工具调用循环里，assistant 消息都含 `tool_call`、tool_result 消息又都是 `role: "user"`，**于是每一条都被保护**。
   `targetTokens` 与 `COMPACT_BOUNDARY` 两条路径因此都是走不到的死代码。
   修法是把粒度从「消息」改成「协议单元」：用并查集把共享 `toolCallId` 的消息聚成单元，整个单元原子地丢或不丢
   （传递性是必要的 —— 一次响应多个 call 时，A 和 B 会通过同一条 assistant 消息互相牵连）。
   同时把「用户输入」的判据从 `role === "user"` 改成「有 text 块」—— 前者会把每条工具结果都当成用户约束永久保护。

2. **`compactTargetTokens` 是帧级预算，却被拿去卡消息级估算** —— 已随 R-6 修掉。
   工具定义开销 540 ＋ system prompt ＋ 时间事实都不在 messages 里，不先扣掉就永远「目标已达成」，一条都不丢。
   这与 R-3 的「固定开销重复相加」是同款单位错配，方向相反：那边多减一次，这边少减一次。

3. **全仓无 `cache_control`，profile 的 `cacheMatching` 无任何读取点** —— **本批未修**，归入第 2 节。
   评测报告 5.2 记录的 cache read 2,176 / billed 14,109（约 15%）完全来自端点隐式缓存，Harness 从未主动做过前缀缓存。
   `cacheMatching: "STRICT_PREFIX"` 与 `supportsExplicitCacheBreakpoints: true` 两个字段除类型定义与 testkit 外零消费，
   性质与 U-1…U-8 同族。注意它与时间事实注入有耦合：受信时间每次都变，所以被刻意放成 system block 之后的独立 item，
   好让 system block 在将来接 `cache_control` 时保持稳定前缀。

另有一项已随 `list_dir` 改造修掉：**`names.slice(0, 200)` 静默截断，但 output 写的是 `共 ${names.length} 项`**。
目录超 200 项时模型会看到「共 350 项」却只拿到 200 条且无提示 —— 它会以为自己盘点完了。现在 `total`/`returned`/`truncated` 三个字段显式给出。

### 一条**仪器**缺陷，当场被判别力思维抓住

`verify:ui` E 段第一次跑，「非 loopback Host 应当被拒」这条判据打了 **200（绿不了）**，
而同一个服务用 `curl -H "Host: evil.example"` 打是 **403**。

> **代码是对的，仪器是坏的。**
>
> `Host` 是 fetch 规范里的 **forbidden header** —— Node 的 `fetch` 会**静默丢掉**它
> 并按 URL 重填。也就是说这条用 `fetch` 写的判据**连那个错误的值都送不出去**，
> 它只可能是绿的（如果我没顺手用 curl 对照过，我会以为它在守着什么）。
>
> 处置：改用裸 `net.Socket` 手写 HTTP 请求，并**补一条配对判据**
> 「Host 正确时必须 200」—— 少了它，一个拒绝一切的服务与一个正确的服务
> 在那条判据下**不可区分**（阶段 3.5 的沙箱就是这么一度把 workspace 内的写
> 也拒了而判据全绿）。

这条比它修掉的那个问题更值得记：**摸底考试那条纪律「这条判据要区分的两个值，
在夹具里相等吗」，在这里遇到了更糟的一档 —— 夹具连那个错误的值都造不出来。**

### 又一条 E-3 形状的 bug，**只在第二段出现**（本批写出来又当场修掉）

`aborterFor()` 对同一个 runId 返回**同一个** AbortController，而上一段收尾时
`finally` 里刚 `abort()` 过它。于是 resume 起来的第二段里，`PendingHub.wait()`
一进去就看到 `signal.aborted === true` → 立刻按「等待被中断」处置 →
**审批闸门在第二段是死的**。

这是 E-3 那个坑的第三次显形（前两次：`REVERSIBLE` vs `PARTIALLY_REVERSIBLE`、
非 TTY 无人应答），共同形态是**结算里出现「拒绝」，而没有任何人拒绝过任何东西**。
它的新花样是**只在第二段出现，第一段全绿** —— 所以判据必须专门跑一次
「取消 → resume → 再要审批」。修法是 `beginSegment()`：每段换一个新的 controller，
**事件缓冲不清**（它是这个 Run 的完整轨迹，跨段累积才对得上 trace 文件）。

> ### 【定】而我为它写的第二条判据是装饰 —— 判别力实测当场拆掉

> | 判据 | 注入后 |

> | 「resume 之后审批仍然停下来等人」 | **翻红** ✅ 有判别力 |

### 一个实测翻车的设计（记过程，不只记结论）

`server.ts` 里原本写着【定】「首屏也要鉴权」。**一跑就翻车**：浏览器拿着带
`?t=` 的 URL 打开首页之后，`<link href="/app.css">` 与 `<script src="/app.js">`
是**不带任何凭据**发出去的 —— 两个 401，页面变成一张没有样式、没有脚本的白纸。

补救只有两条路，都更差：发 Cookie（CSRF 载体，而我们刚把跨源挡掉），
或把 Token 注进 HTML（等于把它从 URL 搬进页面源码）。
处置是让静态壳公开、Token 只校验 `/api/` —— 那三个文件里没有任何运行数据。
**过程留在代码注释里**，因为「为什么不是首屏鉴权」这个问题下一个人一定会再问一遍。

## 0.14　2026-08-30：workspace 选择与切换（S4-5 同批关闭）

> 需求是「选目录 → 新建 / 切换 workspace」。**做的顺序是反过来的：先关 S4-5 的
> 安全闸门，再放开切换** —— 倒过来等于把一个已登记的坑做成一键可达。

### 一、先关 S4-5：workspace 身份冻结 ＋ resume 一致性闸门

| 项 | 内容 |
|---|---|
| **洞** | `RunSpec.workspace` 从阶段 1 起就在类型里、**一直是 undefined**；而 `resume()` 用的 `workspaceRoot` 来自**当前 compose**。于是在 `/A` 起的 Run 用 `--workspace /B` 恢复，未配对工具的观察、幂等重试、后续所有相对路径的读写、以及自动放行的 workspace 判定，**全部以 /B 为根** |
| **归属** | **非阶段 4 引入** —— CLI 的 `--resume X --workspace /B` 一直如此。界面把它从「要手打 runId」变成「列表里一个按钮」，是放大暴露面 |
| **修法** | 新增 `packages/harness-runtime/src/workspace/`：`freezeWorkspace()` 填进 RunSpec，`assertResumeWorkspaceMatches()` 排在端点闸门之后、生命周期闸门之前（§18.3 的**第二维**） |
| **身份** | 由 **realpath** 推出（`ws_<sha256(realpath)[0:12]>`）。macOS 上 `/tmp` → `/private/tmp`，用字面量比会把同一个目录判成两个；而 `isInsideWorkspace` 与 seatbelt 沙箱都按真实路径判 —— 三处口径必须一致 |

> ### 【定】存量 Run 那一档不能硬拒，也不能静默放行
>
> 闸门返回**三态**：一致 → 放行；不一致 → **拒绝**；**缺失**（闸门上线前创建的 Run）
> → 放行，但由 facade 发一条 `RESUME_WORKSPACE_UNVERIFIED` 事件把「我无法核对」
> 说出来。
>
> 硬拒会把库里所有存量 Run 一次性变成不可恢复，而它们当初没做错什么；
> 静默放行则正是这个洞原来的样子。**一条放行了但没验过的闸门，如果不说话，
> 与「验过并通过」在事后完全不可区分** —— 而这两者对复盘的意义相反。

### 二、再做 workspace 注册表与切换

| 项 | 内容 |
|---|---|
| 注册表 | `apps/workagent-service/src/workspace-registry.ts` → `.workagent-state/workspaces.json`。**Layer 2 产品状态，不进 Layer 3 的库**（§26.3：「Layer 2 不修改 Layer 3 表」）；读坏了当空的，不抛（它可重建，§22.5 的口径） |
| **存储隔离** | **一个 workspace 一套存储**：`<ws>/.workagent/{runs.db,runs/}`。于是「A 的 Run 出现在 B 的列表里」在**物理上**不成立 |
| 向后兼容 | **启动时用 CLI 参数登记的那一个保留旧路径**（`.workagent-state/runs.db`）。换成新默认等于让已有的 Run 一夜之间从界面消失 —— **迁移的代价不该由已经存在的数据来付** |

> 只做**闸门**也不够：那样每次切目录都要靠一条报错来教育用户，
> 而正确的默认应该是**根本不会撞上**。

### R-3　Context 硬限可被超长用户输入绕过，且固定开销重复相加

**位置**：[`context/compile.ts`](../../packages/harness-runtime/src/context/compile.ts)

两个方向相反的缺陷在同一段代码里：

1. **可以超限发出**：`count.tokens > hardInputLimitTokens` 时，只有 `irreducible + fixedOverhead` 也超限才返回 `COMPACTION_INSUFFICIENT`，否则继续返回 READY。而 Compact 永久保留全部 `role === "user"` 的消息（[`context/compact.ts`](../../packages/harness-runtime/src/context/compact.ts)），`computeIrreducible()` 又不把它们计入 irreducible。于是「压缩完仍然超硬限」的帧会被照常发给 Provider。
2. **可能提前触发**：`computeIrreducible()` 起手就是 `sum = fixedOverheadTokens`，调用方判定时又加了一次；`BudgetHardLimitReached` 事件里的 `used` 同样重复相加。

**还有第三层**：`fixedOverheadTokens()` 是 `工具数 × 180` 的本地估算，而当前端点的 `count_tokens` 返回值**已经包含**工具定义开销（Spike p4 实测：无 tool 15 → 有 tool 374，差 359 就是工具）。精确路径上再扣一次，阈值基准本身是错的。

**阶段 2 建议**：把「阈值判定」抽成一个函数并配一张判定表（估算/精确 × 是否含工具开销），三种口径显式区分，不要混算。

### R-7　「一个必需操作都没跑」必然结算 SUCCESS，且拒绝理由不进 outcome

**位置**：[`verification/settle-outcome.ts`](../../packages/harness-runtime/src/verification/settle-outcome.ts)、[`loop/run-loop.ts`](../../packages/harness-runtime/src/loop/run-loop.ts) 的两个 `settleOutcome()` 调用点、[`facade/index.ts`](../../packages/harness-runtime/src/facade/index.ts) 的 cancel 路径

**发现方式**：2026-08-24 一次真实端点实跑。任务要求访问外网 URL、转 Markdown、下载图片、打 zip；工具集里没有任何网络能力，模型正确地枚举了三个工具后拒绝了任务，一个写工具都没调。终端打出 `Terminal: COMPLETED / Outcome: SUCCESS`。

两个半独立的缺口叠在一起：

1. **结算只查事实表，而事实表为空时无从查起。** A-1 修的是「跑过但没通过」——`unmetRequired()` 筛的是 `v.required && v.status !== "PASSED"`。本次唯一执行的 `list_dir` 是 `mode: "NONE"` / `requiredForSuccess: false`，`verifications` 与 `recoveryItems` 双双为空，`unmet.length === 0` → SUCCESS。**A-1 的判据按定义发现不了「一个必需操作都没发起」这一类。**

2. **`RunOutcome.summary` 与 `deliveredArtifactIds` 全仓无写入点。** `SettleInput.summary` 字段在，三个调用点（`run-loop.ts` 的 `finish()`、同文件第 ③ 步的预判、facade 的 cancel 路径）没有一个传它；`deliveredArtifactIds` 恒为 `[]`。于是模型那段「我无法完成，原因如下」既不进 outcome，CLI 也就打不出来——用户看到的只有一个 `SUCCESS`。

**定级说明**：不是活跃 bug。结算逻辑严格按 V05 §10.4 执行，实现没有错。这是**规格缺口**——现有 `RunOutcome.kind` 值域里没有一个能表达「模型明确声明做不了」。`USER_REJECTED` 是最近的邻居但语义不对：那是用户拒绝，不是模型拒绝。

**为什么不在阶段 1 修**：改法取决于 U-8 怎么定。两条问的是同一个问题——**`outcome.kind` 的值域要不要区分「是谁没做成」**。分开修会得到两套互不兼容的语义。

**阶段 2 建议**：与 U-8 合并讨论。无论 kind 怎么定，先把 `summary` 接上（成本几乎为零：把 `invocation.content` 里的文本传进 `settleOutcome`），这样即便 kind 判不准，人也能从 outcome 里读到究竟发生了什么。

**验收判据**：脚本化一个「模型第一轮就 `end_turn` 且不调任何工具」的 Run，断言 outcome 能反映「什么都没做」。具体断言什么取决于 U-8 的结论。

**评审的两处表述需要修正**：

1. 「最长稳定前缀只剩 system block」低估了 —— `tools` 也在 messages 之前且完全稳定，实测固定开销 **540 token**。稳定前缀是 tools ＋ system 约 640，不是只有 system。会长大的**历史**确实缓存不到，这一点成立。
2. 「A1 落地后隐式命中大概率更低」**当前没有证据**。三次实跑 `cacheRead` 全为 0，但那不是佐证：

**真正值得记的性质（评审没点破）**：分钟粒度让失效**不确定** —— 跑得快就不失效，跨了分钟边界就在某个说不准的轮次失效一次。对 Replay 与成本估算来说，这比确定性失效更难处理。

**做 U-9 时的选项**（不要现在改，取舍要一起定）：

- 把时间渲染**冻结在 run 级**（`timezone` 已随 RunSpec 冻结，`startedAt` 同理可冻结）。run 内前缀稳定、可复现，代价是长时运行的 Run 会看到过期时间；
- 或降低粒度到「日」——办公类产物大多只需要日期，代价是需要精确时刻的任务失去支持；
- 或保持每轮更新，接受历史不可缓存。

**【定】不要在没定 U-9 之前单独动 `renderTimeFact` 的粒度** —— 它是这三个选项之间的取舍，不是一个可以顺手调的常量。

### D-1　`perRequestBaseTokens` 的数据来源错配

**位置**：[`adapters/endpoint-profiles/bailian-anthropic.json`](../../adapters/endpoint-profiles/bailian-anthropic.json)、`adapters/shape-anthropic-messages/src/protocol.ts` 的 `countTokens()`

- `perRequestBaseTokens: 5` 这个数出自 **`p4-bailian-openai-shape`** 的探针，原文是「单字符请求计 5 prompt tokens…**本地估算**必须叠加这个常量」；

也就是说：一个在 **OpenAI 形状**上测出来的、**给本地估算用**的常量，被填进了 **Anthropic 形状**的声明，并且叠加在**已经精确**的 `count_tokens` 结果上。

数值影响只有 5 token，可忽略；**要紧的是数据来源纪律**——端点能力声明的每个字段都应能追溯到一次针对该端点 × 该形状的实测。建议阶段 2 给 profile 的字段加上 `evidenceRef` 粒度（现在 `sourceEvidenceRefs` 是整份声明一个数组，追不到字段）。

### D-4　推理块估算系数 1.9 只有一个数据点，且是中文特化的　【端点】

**位置**：[`adapters/shape-anthropic-messages/src/protocol.ts`](../../adapters/shape-anthropic-messages/src/protocol.ts) 的 `estimateReasoningTokens()`

**发现方式**：2026-08-25 修 D-3 时自己引入，同日 [Bugfix 批次评审](../代码评审/2026-08-25/阶段1Bugfix批次评审-zcode.md) 复核后登记。

D-3 证实 `count_tokens` 完全不算推理块之后，`countTokens()` 会本地补一个估算顶上去，系数是 **1.9 字符/token**。这个数是从**一次**探针反推的：229 字符的中文推理，端点按 123 token 计费，229 / 123 ≈ 1.86。

两个已知局限：

1. **样本量为 1。** 同一段文本、同一个模型、同一次调用。它够回答「算没算」，不够回答「差多少」。
2. **它是中文特化的。** 英文约 4 字符/token，用 1.9 会高估一倍有余。同文件的通用估算 `estimateTokens()` 用的是 2.5（中英混排粗系数），两个系数并存但依据强度不同。

**为什么现在可以接受**：方向是保守的（高估 → 提前压缩 → 阈值判定偏安全那侧），而 D-3 修复前是**系统性低估且随轮次放大**，两害相权。实测复跑第 4 轮从 −393 变成 ＋39，量级已经可控。

**为什么仍要登记**：代码注释里标了【端点】说明换语种可能不成立，但**光有注释不构成待办**。这与 D-1 是同一类问题——端点能力声明的每个字段都应能追溯到一次针对该端点 × 该形状 × **该语种**的实测。建议与 D-1 的字段级 `evidenceRef` 一起做。

**验收判据**：用中文 / 英文 / 中英混排三段等长推理各跑一次探针，看反推系数的分布；若英文显著偏离，系数就不能是常量。
