## 一、总体评价

**结论：方向正确、分层优秀，可作为基线推进；但存在一处结构性偏科和约 5 个 P0 级语义缺口，建议补齐后再冻结 Contract。**

文档在**控制面与领域模型**上质量很高：三层依赖、Workspace/Session/Run 三中心、配置冻结为快照、Action 生命周期细分、事实表 + Event + Snapshot 混合持久化，均与业界成熟方案（Claude Agent SDK 的 "harness as library"、LangGraph checkpoint、火山 AgentKit Runtime、Anthropic Managed Agents 的 event-sourcing session）高度同构，且有更好的严格性（如 `actionDigest` 防 TOCTOU 是多数方案没做好的细节）。

**结构性偏科**：全文约 90% 笔墨在对象关系与状态机正确性上，而调研报告已认定"上下文工程"是**核心胜负手**，当前设计里这条主轴只有一节（第 10 章）且只覆盖 Session 级 Compact。外部实证：工具输出占 Agent 上下文的 67%~80%+，未治理的 Agent 约 15~20 步后崩溃——这发生在 **Run 内部**，恰是当前设计的空白区。

## 二、做得对的地方（有外部印证，应坚持）

| 设计决策 | 外部印证 |
|---|---|
| Kernel（纯决策）与 Coordinator（durable shell）分离 | LangGraph 纯函数节点 + checkpoint；Anthropic Managed Agents"无状态执行器 + append-only 事件日志" |
| RunSpec / 快照冻结、配置变更建新 Run | AML 评测"合同版本哈希"、Eval 可复现的行业共识 |
| WAITING_FOR_USER 续原 Run、普通 follow-up 建新 Run | Mastra 的 channel/steer 模式、LangGraph interrupt |
| Transcript 为可重建投影 + sourceEventId | "原始 chunk → 语义事件 → reducer 折叠"的同构做法 |
| 粗粒度语义 Tool、确定性细节在 Handler 内 | 银行级"动态推理与确定性执行分离"架构共识 |
| Plugin / MCP / Skill 内部保类型区别、产品层统一心智 | Claude（tools/subagents/skills/plugins）概念面一致 |

## 三、P0 缺口（不补会在阶段 2/3 爆炸）

### P0-1 Kernel 纯函数模型与流式/异步的冲突未解决

`advance(state, input): KernelTransition` 是同步纯转换，但 ModelInvocation 是**分钟级异步流式过程**，期间要出 Delta、可被 cancel、会超时。文档未回答：

- Model 调用生命周期归谁（Model Runtime 还是 Coordinator）；
- Delta 流如何穿透 Kernel 而不破坏其纯度（建议：Delta 是 ModelPort 的 transient 旁路，Kernel 只消费最终 InvocationResult）；
- 流式中途 cancel / timeout 的半截结果语义。

这是 Kernel 接口能否成立的前提。

### P0-2 ToolResult → ContextItem 闭环缺失（Run 内上下文工程）

`ContextItem` 在 7.1 出现一次后再无定义。缺整条链路：

- 大结果**截断 / 外置 Blob + 预览 + 取回工具**（AgentScope / Deep Agents / OpenClaw 四家趋同：>20K token 外置留路径 + 预览，文件读取硬上限 + 分页）；
- **Run 内 compaction 触发策略**（工具循环内按真实 token 数阈值静默触发，双阈值错开防抖动）；
- **绝不拆 tool_call/result 对**（拆了直接 HTTP 400）。

这不是实现细节，是 `context/` 模块的核心架构，应与 Session Context Compiler 同级设计。

### P0-3 Tool 参数 → Capability Scope 映射机制缺失

Policy 要拦截"Workspace 外的写操作"，前提是能从 Tool 入参中**提取效应载体**（如 `filesystem.write` 的 `path` 参数）。`ToolDefinition` 需声明效应参数提取规则（JSONPath → scope 维度），否则 Policy 只能对整个 Tool 放行/拦截，上位基线 11.4 的细粒度拦截全部落空，路径逃逸检查（设计文档 23.1）也没有执行点。`EffectDescriptor` 应扩为含 `scopeExtractors`。

### P0-4 错误分类学缺失

重试、降级、上浮用户、终止全部依赖错误分类。业界四分类共识：

1. **transient**（指数退避重试）；
2. **model-recoverable**（错误作为 tool result 回传让模型自纠）；
3. **user-fixable**（转 WAITING_FOR_USER）；
4. **fatal**（立即失败）。

`retryPolicy` 有了，但没有它依赖的错误 taxonomy，ToolResult 的 error shape 也没定义。最差反模式就是所有错误同等对待。

### P0-5 信号与推进的并发协议缺失

`signal()` 是异步投递，但未定义：

- 信号缓冲与消费时机（cancel 到达时正在模型流式中 / Tool 执行中怎么办）；
- Approval 决策到达时 Run 已 crashed 怎么办；
- WAITING_FOR_USER 下用户连续发多条输入的语义。

需要"Run Lock + 信号队列 + 与 advance 串行化"的明确协议，否则阶段 2 故障注入集必然暴露竞态。

## 四、P1 缺口（架构缝未预留，后期返工成本高）

1. **策略扩展缝**：上位基线 5.3 要求 Planner / Verifier / Sub-agent 可插拔，但单 loop 的 `AgentKernel` 无注入点。建议借鉴 Claude **Hooks 模式**（PreToolUse / PostToolUse / Stop 等确定性注入点）——这是被验证的最小扩展面，阶段 6 引入策略时不必动 Kernel 核心。
2. **Observation / Verification 的执行者未定义**：`VerificationDescriptor` 由谁执行（内置 Verifier / Tool / Hook）？环境重观察的成本很高，需要"何时值得重新观察"的粒度策略。
3. **Resume 时外部世界失效**：18.3 只覆盖"副作用是否已发生"，未覆盖"恢复时快照已过期"（文件被改、Grant 过期）。需要 fingerprint 比对失败后的决策路径：重解析 / 问用户 / 失败。
4. **Cancel 语义不完整**：CANCELLED 后已执行副作用与已注册 Artifact 的处置；长 Tool（媒体下载）的协作式取消；`Approval EXPIRED` 由谁触发。
5. **失控保护未入 Run 不变量**：预算四轴（steps / wall-clock / tokens / cost）+ **优雅降级**（耗尽时让 Agent 总结交接而非 kill）+ 循环检测（相同调用 hash 连续 N 次熔断）应是 Kernel 强制职责（上位基线 8.4 已拍板，本文未吸收完）。
6. **Eval 确定性基础设施**：Eval 复现需要 **RecordedModelPort（模型响应 record/replay）**、FakeClock、GoldenTrace 对比。`testkit` 应从目录名升格为一等设计项。
7. **Skill 无渐进披露**：`SkillSnapshot` 全量注入 instructions；Skill 一多上下文即膨胀（业界：初始只载 name/description 按需加载）。
8. **人工接管（Human Takeover）通道缺失**：上位基线 Case 01 明确需要动态页面人工接管，架构中无此对象（Run 挂起 → 用户操作浏览器 → 交还）的机制。
9. **dry-run 缺位**：上位基线 11.2 拍板"优先 dry-run 降摩擦"，`ToolDefinition` 无 dryRun 支持。

## 五、P2 缺口（记录即可）

1. `AgentProfile` 无归属：WorkSession 引用了它，但 Layer 2 模块列表无 `agents/` 模块；
2. `run_events` 无 `schemaVersion`（UI 事件有），影响 Trace 演进与旧 Run 可读性；
3. **Replay**（区别于 Resume，用于调试 / Eval 重放）语义未定义——事件日志的复利价值所在；
4. `conversationContext.messageSnapshots` 全量快照，长 Session 会膨胀 RunSpec（cursor + delta 即可）；
5. KernelState 与 `run_snapshots` 表的对应关系未说明；
6. 多 Session 并发 Run 共享 Capability（浏览器互斥、Handle 引用计数）未提；
7. ModelInvocation 事件应携带 usage（token / 耗时），支撑上位基线 9.3 的记录要求；
8. 提示注入标记只写了"Context Compiler 标记来源"，**谁消费标记**未闭环（Policy 检查 Action 输入是否源自不可信内容）。

## 六、与外部方案的关键差异提醒

1. **不要引入预定义 DAG**（LangGraph / AutoGen 路线）：单 loop + 模型自决路径与 Claude Agent SDK 同构，符合"Case 无关"目标，坚持即可；多 Agent 已列为非目标，正确。
2. **Sub-agent 上下文隔离模式值得现在埋缝**：子 Agent 独立上下文 + 只回传摘要，是未来解决上下文污染的主路径，`Run` 模型预留 `parentRunId` 即可，成本极低。
3. **记忆投毒风险**：未来跨 Session Memory 时，"记住我是管理员"类声明持久化即提权——记忆写入应视为特权操作，现在不必做，但 `trusted_personal` 的演进说明里应记录该风险。

---

## 七、修改建议（按优先序）

1. 新增「Run 内 Context 管理」章节：ContextItem 模型 + 大结果外置链路 + compaction 策略与触发点 + tool_call/result 配对不变量（对应 P0-2）；
2. 扩充 Kernel 接口章节：ModelInvocation 生命周期、transient 旁路、cancel / timeout 中间语义、信号串行化协议（对应 P0-1 / P0-5）；
3. 扩充 `EffectDescriptor` / `ToolDefinition`：scopeExtractors、错误分类枚举、dryRun、usage 记录（对应 P0-3 / P0-4）；
4. 在 Kernel 不变量中补预算四轴、循环检测、优雅降级；`Run` 预留 `parentRunId`；Kernel 周边预留 Hook 位（对应 P1）；
5. testkit 升格为一节：RecordedModelPort、FakeProvider、GoldenTrace；
6. 补 Human Takeover 对象与 Approval 过期触发机制。

---

## 八、评审结论

总体而言：初稿的**骨架是对的且相当扎实**，主要问题是"重控制面、轻数据面（上下文）"的偏科，以及五处执行语义留白——它们都不需要推翻分层，但必须在冻结 Contract 前补齐。

建议下一版架构文档（V20260821_02 或 V02）以本报告第三、四章为必改清单，第五章作为 backlog 记录，第六章作为决策提醒纳入 ADR。
