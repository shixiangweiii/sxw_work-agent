## 1. 评审结论与总体评估

### 1.1 总体评级：【有条件通过 / 需补充关键闭环设计】

本实施方案在**战略定位、北极星对齐和架构边界防御**上做出了极其重要且正确的纠偏：
1. **坚决贯彻上位基线北极星**：明确“阶段 3 不建 `cases/web-archive/`”，坚守“Case 是尺子不是模具”的纪律，拒绝将通用的 Agent Harness 矮化为某个特定任务的专用脚本；
2. **立足通用能力面**：开辟 `tools/common`（`@workagent/tools-common`），建立三场景（办公 / 代码 / 聊天）通用筛选标准，推动四大未实现 Port 在真需求驱动下逐步落地；
3. **保持工程纪律与防过拟合闸门**：引入第 6 条边界 grep、双工具包装配路由、机械判据退出等设计，延续了项目一贯的高质量工程底色。

**但方案在“如何真正支撑强大的通用思考与执行能力”上存在若干关键盲区、断头链路与机制性缺口**。如果不加修正地直接开工，会导致系统虽然拥有了 8 个基础文件与网络工具，但在面对稍微复杂、长链路、多依赖的通用办公任务时，依然频繁出现**大结果信息黑洞、修改冲突无所适从、遗漏关键要求却盲目结算成功、进程中断后交互状态断裂、长任务被错误计费超时**等系统性问题。

## 2. 核心维度深度剖析（Critical & Major Findings）

---

### 维度 1：通用思考能力（Reasoning & Context Loop）的机制性缺位

#### 1. 认知偏差：将“简单任务的偶然顺畅”过度泛化为“思考机制无需 Harness 支持”
方案在 §0.1 声称：*“实测规划与自纠没有暴露短板；瓶颈不在思考，在能看到什么、能做什么；所以本阶段不加编排模块。”*

**评审判定：这一推断存在以偏概全的风险。**
- **证据反思**：评测报告中模型表现良好的任务是**极小规模、单目录、结构简单的目录盘点**（3~4 轮、7~8 工具调用）。
- **通用办公现实**：真实的通用办公场景（如跨多篇长会议纪要交叉比对并提取决议、跨模块代码重构方案设计、根据模糊要求从海量文件和网页中排查证据并产出交付文档）具有**高不确定性、多阶段依赖、大跨度信息提取**的特征。在这些场景中，模型的注意力衰减、多轮工具反馈后的上下文污染、遗漏关键约束是业界公认的常态。
- **阶段 2 评测硬失败的真相**：阶段 2 评测中出现的那次硬失败（5 次中失败 1 次，漏掉了用户显式要求的总字节数 `20223`），恰恰暴露了：**模型在没有机制约束的情况下，容易在生成最终总结时产生“认知盲区”或“伪完成感知”**。

#### 2. 通用 Harness 级“Closure（任务收敛核对）机制”被误杀
阶段 2 评测报告明确指出建议：*“在通用 harness 层考虑可配置的 completion checklist / postcondition 机制，让模型在 final 前获得一次受预算约束的‘验证目标产物’机会，而不是直接盲目进入终态。”*

方案 §1.2 / §S8 将这一通用 Harness 诉求错误地归类为“任务级规则”并一棍子打死。
- **澄清边界**：
  - **业务特化规则（禁止）**：例如在 Runtime 里写死“清单里必须包含合计字节数字段”。这确实是 Case 级规则，坚决不能进通用 Runtime；
  - **通用思考收敛机制（必须）**：例如 Harness 在模型意图结束前，驱动一个受控的**通用自检思考步（Self-Verification Loop / Completion Gate）**——让模型根据初始任务 prompt 和已落盘的 Artifact 事实，做一次显式的“要求回溯与交付物核对”。
- **结论**：缺乏通用收敛思考机制，通用办公任务的交付可靠性将永远停留在“看模型当天发挥的概率分布”，无法满足高质量解决办公场景的要求。

### 维度 2：大结果与 Materialization 链路存在严重“断头路”

#### 致命缺陷：缺少 Retrieval Tool 契约，大结果外置将直接演变成“信息黑洞”
方案 §S6 / §S7 规划了 `BlobStorePort` 和大结果外置（ToolResult Materialization：小结果 inline，大结果存入 BlobStore，ContextFrame 中仅保留 stub + preview + ref）。方案在批 2 验收 A 段写道：*“断言外置发生、Frame 里留下结构合法的 stub、模型可经 retrieval 取回完整内容”*。

**评审判定：链路存在致命缺失！**
- 查看方案规划的 8 个通用工具：`list_dir`, `read_file`, `stat`, `write_file`, `edit_file`, `search`, `fetch_url`, `now`。
- **全表中没有任何一个工具支持读取 BlobStore 中的 ref！**
- 模型在 ContextFrame 中看到了 stub（例如 `[Blob: ref_123, size: 500KB, type: html]`），但当模型想要深入分析其中的某一部分时，**它在工具层没有任何手段去获取该 Blob 的内容或切片**。
- **后果**：大结果外置在没有 Retrieval Tool（如 `read_blob` / `get_blob_slice`）的情况下，实质上退化成了比静默截断更糟糕的**信息完全阻断**。这直接摧毁了通用办公中处理大文件、长网页分析的思考链条。

### 维度 3：通用工具面（`tools/common`）抽象颗粒度与边界审查

方案规划的 8 个工具是通用能力的基础，但在工程契约与办公实战场景中存在以下缺陷：

| 工具 | 方案规划 | 评审发现的问题与隐患 | 改进要求 |
|---|---|---|---|
| **`read_file`** | `offset / limit` 分页，显式 `total / returned / truncated` | 分页维度未定义：按**字节**还是按**行号**？若按字节，UTF-8 多字节字符在边界被劈断会导致乱码；若按行号，超长单行文件（如单行 JSON/压缩代码）会爆内存。 | 明确契约：默认以**行**为单位分页，并防御单行超长（设定单行最大安全字符数）；同时返回行号范围 `startLine / endLine`，便于与 `edit_file` 和 `search` 联动。 |
| **`search`** | `(pattern, path?, kind: "name" \| "content", cursor?)` | 1. 缺乏大文件、二进制文件（图片/音视频/编译产物）、`.git` / `node_modules` 等无关目录的**通用过滤策略**，极易导致搜索超时或扫出海量无意义字符；<br>2. content 搜索缺乏**上下文行（context before/after）**，返回单个孤立行会导致模型无法理解上下文，必须再次发起多次 `read_file`，浪费大量 token 与轮次。 | 增加通用 ignore 过滤机制（自动忽略大二进制与常见版本控制目录）；content 匹配支持返回匹配行及前后 1~2 行上下文，并标注明确行号。 |
| **`edit_file`** | 仅支持精确字符串替换（`old_string -> new_string`，强制全局唯一匹配） | 1. 在通用长文档和代码中，若目标片段在多处存在微小重复（如重复的 Markdown 标题、相同的函数闭包模板、表格占位符），唯一匹配将直接失败且模型无法局部定位；<br>2. 模型输出大段 `old_string` 极易由于空格、换行符（CRLF vs LF）微小差异导致匹配失败。 | 保持唯一字符串替换作为主力，但必须在错误返回中提供**结构化诊断**（如“未找到匹配项，相近度最高的候选位于第 X 行”或“找到 N 处匹配，请扩大上下文匹配范围”），给模型提供足够的自纠线索。 |
| **`fetch_url`** | 仅做公开 HTTP GET，不做正文提取 | 契约未定义以下通用场景的处置：<br>1. HTTP 状态码 4xx/5xx 或网络超时的结构化 ToolResult 返回；<br>2. 响应类型是二进制大文件（如 PDF/ZIP/图片）时的处理；<br>3. 重定向跟踪与安全限制（防 SSRF，如 `localhost` / 私网 IP 探测）。 | 明确 HTTP 状态码和响应头（`status`, `contentType`, `headers`）的规范化返回；限制私网 IP 访问保护安全性；对 HTML/文本返回原始文本，对二进制返回元数据并外置 Blob。 |

### 维度 4：Artifact 级 Verification 的有效性与降级设计

方案 §1.2 / §S8 将 Artifact 级验证限定为通用产物类型的静态结构约束（JSON / Markdown / ZIP 解析）。

**评审判定：方向正确，但必须澄清产物登记与验证的语义边界。**
- **当前设计的优点**：成功防止了业务特化逻辑污染通用工具包与 Runtime。
- **存在的漏洞**：
  1. **产物登记时机**：方案未定义 Artifact 是由模型显式调用工具登记，还是由 Runtime 扫描 workspace 自动登记。方案写着“`Deliverable` 原则上必须 Verified，`Runtime Blob` 不自动升级为 `Artifact`”。如果模型只是用 `write_file` 写出了一个 `report.md`，它何时以及如何成为一个被追踪的 Artifact？
  2. **验证失败的 Outcome 映射**：方案提出“若非法 JSON/损坏 ZIP，Artifact 验证失败，Outcome 降级为 `COMPLETED_WITH_LIMITS`”。但如果该产物是本次 Run 的核心交付物（Primary Deliverable），降级为 `COMPLETED_WITH_LIMITS` 是否妥当？在语义上，核心产物损坏应当明确标识为 `FAILED` 或在 `incompleteItems` 中带出具名失败原因。

### 维度 5：状态机、持久化与人工接管（`WAITING_FOR_INTERACTION`）的断裂

方案 §S10 规划了人工接管：`Runtime 请求接管 → 进入 WAITING_FOR_INTERACTION（阻塞在 await） → 用户在终端操作 → 回车 → 重新 Observation`。同时 §决5 明确不做 PARKED lease。

**评审判定：在持久化与跨进程崩溃恢复上存在状态未闭合漏洞！**
- **漏洞场景**：
  1. Agent 执行到某一阶段，向用户发出接管请求（例如“请在外部系统确认审批，完成后在控制台按回车”），进程进入 `WAITING_FOR_INTERACTION` 并在 await 处等待用户输入；
  2. 此时用户电脑休眠、终端被误关，或用户直接杀掉了进程；
  3. 用户稍后执行 `npm run dev -- --resume <runId>` 尝试接续执行。
- **代码现实检查**：
  - 当前 `packages/store-sqlite/` 和 `run-loop.ts` 仅对轮次边界、Tool 执行中等异常做了恢复处理；
  - 如果在 `WAITING_FOR_INTERACTION` 处重启，Runtime 读出的 `lastRunStatus` 是什么？
  - 在没有恢复逻辑的情况下，新进程将无法感知“上次是在等人工交互完成”，可能直接进入主循环再次调用模型，或者判定为不合法状态退出。
- **改进要求**：方案必须在 §S10 补齐 **`WAITING_FOR_INTERACTION` 在 SQLite 中的持久化事实与 Resume 语义**——即重启后能识别出处于等待交互状态，并给用户重新提示交互引导，而不是让其成为未定义的崩溃窗口。

### 维度 6：存量高危缺陷分拣失误（不可将长任务地基推至 bugfix）

方案在 §1.3 中选择将大部分存量问题（如 R-1、R-2、P2-1、N-7 等）后移至 bugfix 阶段。

**评审判定：部分存量缺陷是阶段 3 通用能力建设的直接地基，必须在阶段 3 同批解决，否则新功能将立即踩坑。**

1. **R-1（预算硬墙大半失效）与 R-2（等待时间计入活跃时间）**：
   - 阶段 3 引入了 `fetch_url`、大文件读取、人工接管等**真实长耗时任务**；
   - 一旦用户人工接管等待了 5 分钟，由于 R-2 未修，离开等待后下一轮模型调用立刻因超时被判定为 `BUDGET_EXHAUSTED`；
   - 复杂通用任务需要多轮搜索与编辑，若 R-1 未修（`maxToolCalls` / `maxTotalWallClockMs` 零消费），死循环将无法在 Harness 层面被硬截断。
2. **P2-1（`--yes` 与 `--yes-all` 参数语义混乱）**：
   - 阶段 3 要跑跨场景真实任务（S13）。如果命令行参数语义不清晰，在无人值守或多步骤执行不可逆工具（`edit_file`, `write_file`）时会频频卡死在 stdin，严重干扰自动化验证。

### 维度 7：S13 跨场景 Smoke 判据的有效性审查

方案 §S13 规划了办公任务 A（多文档汇总）和代码任务 B（模块分析与方案输出），并写明：*“判据是跑通，不是产物质量”*。

**评审判定：存在典型的“假通过（False Positive）”风险。**
- **风险分析**：
  如果 Agent 调了 2 次工具，生成了一个 0 字节的空文件或者一段答非所问的文字，然后正常结束退出，进程退出码为 0，配对不变量全部守住——按照方案当前的判据，S13 就会被标为 ✅。
- **北极星背离**：
  这与“**高质量解决具体办公场景的常见 case 问题**”完全相悖。虽然阶段 3 推迟了完整的 Eval 矩阵，但跨场景 Smoke 必须具备**最基本的业务有效性硬门槛**（如目标产物必须包含指定的关键信息段落、产物大小必须大于基线阈值、日志中必须有对应的操作事实记录）。只验退出码 0 无法证明通用能力真正成立。

## 4. 关键不得绕过清单（评审增补版）

在方案原有的 12 条不得绕过清单基础上，**强制增补以下 4 条核心红线**：

1. **【红线 13】大结果外置必须配对 Retrieval 工具**：严禁仅实现外置 stub 而不提供模型检索手段，模型必须拥有自主按需读取 Blob 片段的协议工具（`read_blob`）；

3. **【红线 15】人工交互等待必须可持久化与恢复**：`WAITING_FOR_INTERACTION` 必须具备清晰的 SQLite 落盘与 Resume 契约，不得依赖“进程永远存活”的脆弱假设；
4. **【红线 16】文件与搜索工具必须防御资源耗尽**：`read_file` 与 `search` 必须具备文本行号感知与二进制/大目录安全过滤机制，严禁将不可读的二进制流或超长单行直接灌入 Context。
