## 0. 七个决定

### 决 1：本阶段只做**产品化半边**，Case 02 不做

Roadmap §6 的阶段 4 有两件事：**Case 02 反证抽象** 与 **桌面产品化 ＋ Trace / Eval Inspector**。
本批只做后者。

理由不是工作量，是**两类发现会互相污染**：

- Case 02 回答的是「前三阶段抽出来的东西是真通用，还是只是某个 Case 的形状」；
- 本批回答的是「执行事实能不能被投影成界面」。

两件事同时做，一旦某个字段拿不到，分不清是「抽象漏了」还是「事件流漏了」——
而这两种漏洞的处置完全相反（一个要改抽象，一个要加事件）。

另外 Case 02 按上位基线 §10.4 要**先写出完整 Case 定义**才谈得上取舍（D-11），
那是一份独立的设计输入，不是开工就能开始的编码任务。

> 【定】Case 02 留在阶段 4 的范围里，只是不在本批。Roadmap §6 不改写。

### 决 2：不引入前端框架、打包器与 Electron

界面是 `node:http` 提供的静态 HTML / CSS / 原生 JS，用系统浏览器打开一个 loopback 页面。
**运行期依赖仍是 3 个**（`@anthropic-ai/sdk` / `dotenv` / `turndown`），一个不加。

三条理由，按重要性排：

1. **本阶段的研究问题是投影完整性，不是前端选型。** 引入 React ＋ Vite 会让第一周
   花在构建配置上，而它一个判据都答不了。
2. **有 build step 之后，「UI 有没有偷读 Runtime」这条边界要靠打包器配置来守。**
   现在这条边界是物理的：UI 是浏览器里的静态资源，它**没有办法** import 后端模块，
   边界 grep 第 8 条因此是一条能红的判据而不是君子协定。
3. **Electron 是为了「打开一个本地页面」引入几百 MB。** 而系统浏览器已经在那儿了。
   §27.1【定】说的是「只有出现崩溃隔离 / 沙箱 / 多客户端需求后才评估拆进程」——
   同一条纪律用在这里就是：只有出现「必须是原生窗口」的需求后才评估 Electron。

**代价明说**（不要等第二个人来发现）：没有热更新、没有组件复用、CSS 与 DOM 手写、
状态管理是一个全局对象加几个 render 函数。界面复杂到某个程度这套写法会撑不住 ——
那一天到了再换，并且那时会有真实的界面需求当选型依据。

见 [ADR-0009](../ADR/0009-阶段4-UI-不引入前端框架与-Electron.md)。

### 决 3：它是**白盒**界面，不是聊天窗

默认视图不是气泡对话，是**一次 Run 的解剖**：

| 视图 | 回答的问题 |
|---|---|
| 时间线 | 这个 Run 依次发生了什么（两条轨道合并后的全序） |
| 逐轮解剖 | 每一轮的帧怎么构成的、花了多少 token、停在哪个 stopReason、走了哪条 transition |
| 预算 | 八条轴各用了多少、离墙有多远 |
| 产物 | 登记了什么、第二层验证过没有、hash 与磁盘对不对得上 |
| Trace | 原始 JSONL，按段（segment）分组 |
| 恢复 | §18.2 三条分支各命中几次、有哪些未销账项、决策按钮 |

理由：一个聊天界面会把 Harness 的全部特征藏起来，而那些特征是这个项目**唯一的产出**。
市面上的 Agent 产品都有聊天界面，没有一个能告诉你「这一轮的固定开销是 2520 token、
上下文里有 3 条外部不可信内容、这次写入是被自动放行还是有人点过同意」。

### 决 4：三条「等人」的通道搬到浏览器，用的是**同一批注入点**

`ApprovalDecider` / `HandoffChannel` / `QuestionChannel` 三个接口一个字不改，
浏览器侧提供另一套实现。

**这是本阶段研究问题的判别力所在。** `compose.ts` 里那句
「只有这一层知道『人在哪』（终端、GUI、还是一个没有人的 CI）」写了一个阶段，
而在此之前**只有终端这一种人**。如果那三个真是注入点，Runtime 一行不改；
如果不是，这一步会当场逼出改动 —— 而那本身就是本阶段最有价值的发现。

> 【定】浏览器与终端有一处**语义差别**，必须写在代码注释里：
> 无 TTY = 真的没有人（审批按拒绝、接管按没人）；
> 浏览器没连 = 人可能只是关了标签页，稍后回来。
> 所以 Web 侧的等待**不按拒绝处置**，它一直等到有人应答或 Run 被取消。
> 把这两者做成同一种处置，会让「关掉标签页」变成「拒绝了这次写入」。

### 决 5：两条轨道必须合并，能对齐它们的只有 D-2 那条统一序列

事件流与 transcript 各自都**不足以**画出白盒界面：

| 只看事件流 | 只看 transcript |
|---|---|
| 有循环迁移、预算、审批、验证、产物 | 有工具入参原文、工具结果原文、模型正文 |
| **没有工具入参**（`ActionProposed` 只有 toolName / effect） | **没有循环迁移与预算**（RUN_META 只有累计量） |
| **没有工具结果原文**（`AttemptCompleted` 只有 status / 时长） | 没有 stopReason / usage / 帧构成 |

合并的唯一依据是 **D-2**（事件与 transcript 条目共用一条单调序列）。
阶段 2 把它列为「不做会污染后续、事后收不回来」的四条开工前置之一，理由写的是
「§23.2 的 Layer 2 投影游标没法收拾」——**本批就是那个 Layer 2 投影**，
这条前置在这里第一次有了消费者。

> 【定】投影**只做合并与排序，不做推算**。UI 上的每一个数字都必须能指回
> 一个 RunEvent 或一条 transcript 条目。理由见不得绕过 #6。

### 决 6：Layer 2 不得推进执行语义

§6.1【定】：Layer 2「不推进 Run 状态、不判定 Action 合法性、不解析 Effect」。
§5.2【定】列了九条 UI 不拥有的语义。

这两条在阶段 4 之前**没有任何机械判据**，因为没有 Layer 2。本批给它一条：
**边界 grep 第 9 条**（见 §4）。

它要防的具体形态是这个：界面上看到一个 Run 状态是 `RUNNING` 但其实进程早死了，
最自然的「修复」是在服务里补一句 `ports.runs.setStatus(runId, "FAILED")` ——
那一行会让 Layer 2 成为第二个状态推进者，而 §23.1 的裁决规则
（执行语义以 Runtime 事件为准）从此不成立。

> 正确的处置是**如实显示**：状态是 RUNNING 但没有活着的循环，就显示
> 「RUNNING（本进程内没有在跑 —— 可能是上次崩了，可以 resume）」。
> **投影不修正事实，它转述事实。**

### 决 7：本地通信按 §22.6 落地，四条一起做

只监听 `127.0.0.1`；默认随机端口；会话级 Token；Origin ＋ Host 校验。

Host 校验那条不是 §22.6 原文写的，是它「禁止外部网页调用本地 API」的必要条件：
只校验 Origin 挡不住 DNS rebinding（攻击者把自己的域名解析到 127.0.0.1，
浏览器发的是同源请求，`Origin` 就是他自己的域名 —— 而如果我们只在
`Origin` 存在时校验，一个 `no-cors` 的表单提交连 `Origin` 都可以不带）。
校验 `Host` 必须是 loopback 字面量，才能把这条路堵上。

## 1. 研究问题与退出门槛

### 研究问题

> **前三阶段产出的执行事实，能不能只靠既有的事件流、transcript 与三个 Port 注入点，
> 投影出一个完整的白盒界面 —— 而 Runtime Core 一行不改？**

它是可证伪的：只要界面上有任何一个字段必须靠「改 Runtime 才拿得到」，
或者必须靠「Layer 2 自己算」，答案就是「不能」，而那个字段就是事件流的缺口。

### 退出门槛（结构性，不依赖评测）

| 门槛 | 判据 | 段 |
|---|---|---|
| Runtime 未被 UI 反向定义 | 边界 grep **12 条**全过，第 8 / 9 / 10 条做判别力实测（注入即翻红） | A |
| 投影可重建、幂等 | 同一份数据分两段投影再按 id 合并，与一次全量投影**逐字一致** | B |
| 白盒完整性 | 每个投影项都带 `source`，且其 sequence 落在真实轨道范围内；工具入参与结果非空 | C |
| 不自己算 | UI 拿到的预算数字与 `runtime.inspect()` **逐字一致**（不是近似） | C |
| 三条等人通道在浏览器上可达 | 审批 / 提问 / 接管各真跑一次，走 HTTP 应答，用的是与 CLI 同一个接口 | D |
| 本地通信边界 | 无 Token → 401；错 Token → 401；跨 Origin → 403；非 loopback Host → 403 | E |
| 凭证不外泄 | 往 env 塞一个假凭证，扫描**所有** API 响应体，一个字节都不得出现 | E |
| SSE 重连不重不漏 | 断开后带 `since` 重连，收到的事件集合与不断开时逐条相同 | F |
| 无回归 | `verify:all` 全绿；`typecheck` 干净 | — |

## 3. 不得绕过（10 条）

1. **UI 不得拥有 §5.2 的九条语义**（合法状态迁移、Action 是否允许执行、
   Cancel 后副作用是否发生、outcome 结算、未配对 tool_use 如何处置……）；
2. **Layer 2 不得推进执行语义**：不写 `runs.status`、不自建循环、不解析 Effect、
   不自行结算 outcome（决 6，判据是边界 grep 第 9 条）；
3. **投影游标是 transcript sequence，幂等、至少一次**（§23.2 第 2 条）；
4. **Layer 3 不查询 Layer 2，Layer 2 不修改 Layer 3 表**（§26.3）——
   本批 Layer 2 只经 Facade 与 Port 读，一条 SQL 都不自己写；
5. **响应体不得出现凭证**（§22.3）；
6. **事件流不足以支撑的展示，如实记为事件流的缺口**，不得靠 Layer 2 推算补上。
   推算出来的数与权威副本对不上时，事后没人分得清哪个对 —— 这是
   `readLastBudget` 那条注释已经写过的教训（「凑出来的数和权威副本万一对不上，
   事后没人分得清哪个是对的」），本批把它升成硬约束；
7. **不新增运行期依赖**（决 2）；
8. **模型产出的文本一律以 `textContent` 渲染，不得 `innerHTML`**。
   与 CLI 的 `forTerminal()` 同源：审批是 EXECUTE 唯一的人工边界，
   而它要显示的东西全部由模型给。**一个可以被展示内容伪造的边界不再是边界**；
9. **Composition Root 不复制第二份**（见 §5 的说明）；
10. **新增判据前先问「这条判据要区分的两个值，在夹具里相等吗」**
    （摸底考试批的教训，原样适用）。

## 4. 边界 grep：8 → 11 条（收口批再 +1 = 12 条目）

```bash
grep -rn "@workagent/" apps/workagent-ui                       # 8. UI 不得依赖任何后端模块
grep -rnE "\.setStatus\(|runLoop\(|executeBatch\(|settleOutcome\(|settleWallOutcome\(|compileFrame\(|findUnpairedToolUses\(" \
     apps/workagent-service/src                                # 9. Layer 2 不得推进执行语义
grep -rn "innerHTML" apps/workagent-ui/public                  # 10. 模型产出不得走 innerHTML
```

三条各自的「违反了会怎样」：

| 条 | 违反的形态 | 后果 |
|---|---|---|
| 8 | UI 直接 import `@workagent/harness-runtime` 的类型或函数 | 界面开始读 Runtime 内部状态，§5.5 保留的那条约束（UI 通过 RunEvent 流驱动）失效，将来换任何 UI 协议都要重写 |
| 9 | 服务里补一句 `setStatus` 去「修正」看起来不对的状态 | Layer 2 成为第二个状态推进者，§23.1 的裁决规则不成立，而盘上看不出来 |
| 10 | 审批面板用 `innerHTML` 拼命令原文 | 模型可以在命令里塞 HTML 把上面几行盖掉 —— 与 ANSI 伪造是同一件事，只是换了渲染器 |

> 【定】第 8 条**不是**恒真式。它现在成立靠的是「UI 是浏览器资源」这个物理事实，
> 而这个事实随时可以被一次「给 UI 加个构建步骤」的改动破坏 —— 那一刻这条 grep
> 就是唯一会说话的东西。
>
> ⚠️ **收口批修正**：它当时只扫 `public/`，撑不起上面那句话（打包器的源码在 `src/`，
> 产物里包名已被消解）。已放宽到整个 `apps/workagent-ui/`，并用**行级**豁免
> 只放行本包自己的 `name` 声明。**同批新增第 11 条**：界面不得用内联 `style` 属性
> —— 它会被我们自己的 CSP（`style-src 'self'`）静默丢弃，而八条预算轴正是
> 这么全部渲染成满格的。

## 5. 一处名实不符，登记为欠账而不是顺手改

服务复用 `apps/cli/src/compose.ts` 这个 Composition Root，**不抄第二份**。
抄一份的直接后果是「两个入口的工具集 / 端点枚举 / system prompt 迟早不一致」，
而那种不一致在绿灯下看不出来 —— `parseEndpointArg` 的注释里已经记过一次同样的教训。
`eval/suite/index.ts` 早就这么做了（相对 import `../../apps/cli/src/compose.js`），
本批沿用同一条路。

那它为什么不搬进 `packages/`？**因为边界 6 会当场翻红** ——
`compose.ts` 必须 import `@workagent/tools-common`，而
`grep -rnE "@workagent/tools-|tools/common" packages adapters` 要求零命中。

> **这条 grep 反过来正好证明了 Composition Root 属于 app 层。**
> 名字里带 `cli` 是历史，不是设计。登记为欠账（存量清单 S4-1），
> 等 Case 02 那批真的需要第三个入口时再动 —— 现在改要动 18 个 import 点，
> 收益只是一个名字。

## 6. 明确不做

- **Case 02**（决 1）；
- **Electron / 原生窗口 / 打包分发**（决 2）；
- **Layer 2 的 22 张产品表**（§26.1）—— Workspace / Session / Message 这些聚合
  在单人本地、一次一个 Run 的用法下没有消费者。**建了就是 8 项「未接线」的第 9 项**；
- **Eval Inspector 的独立视图** —— `eval:suite` 的 `report.json` 已经有可读输出，
  本批只做 Trace Inspector。Eval 视图要等评测阶段真的跑起来、有多份报告要横向比时才有需求；
- **多客户端并发编辑同一个 Run** —— 单人本地产品，两个标签页同时点审批是一个
  没有真实场景的复杂度（§27.1【定】同源）；
- **写操作的 UI 编辑器**（改文件、改 prompt）—— 那是产品功能，不是白盒。
