### 0.1 三处连锁修正

**决 1 让 M-4 换了理由但仍留在阶段 2。** 原理由「Replay 前置」失效，新理由更硬：**RunSpec 要落库，就必须真的可序列化且真的不可变。** `freezeProfile()` 现在只冻浅层——评审核实 `errors` 完全未冻、`tokens.usageFieldMap` 与 `sourceEvidenceRefs` 数组仍可变（`profile-loader.ts:50-59`）。RunSpec 进库之后，「盘上那份」与「内存里被改过的那份」会分叉，而 §18.3【定】要求 resume 时校验「端点能力声明是否仍与 RunSpec 冻结的一致」——拿一份可变对象做这个校验没有意义。

> **记账**：决 1 的代价是 **M-4 失去了它最强的验收场景**。真正能证伪深冻结的是 Replay 那种「三个月后拿旧 RunSpec 重跑」。阶段 2 只能做到「逐层写入尝试必须抛错」（见 S4），这比序列化往返强，但仍比 Replay 弱。**这是决 1 的已知减弱，不是疏漏。**

**决 1 让架构 §28.6 的 Contract 冻结门槛跟着改，且冻结范围要收窄。** `Replay` 那一行从阶段 2 移到阶段 3；`TranscriptEntry` 留在阶段 2——但**只冻「已被 resume 真实用到」的部分**（`sequence`、`kind` 现有四值 ＋ 新增的 `ACTION_FACT`、`schemaVersion` 逐条 upcast）。Replay 相关的语义（起始位置定位、exact recorded 的字节级要求）保持【验】不冻：**冻结它的人现在还不知道 Replay 会怎么用它，冻早了就是冻错。**

**决 4 与决 1 不打架。** §24.1【定】说 grader 独立实现、**不复用生产 Run 的 outcome 结算路径**。grader 的 golden truth 来自冻结的 workspace manifest，不来自 `deliveredArtifactIds`——后者继续恒空不阻塞 grader。

### 0.2 研究问题的结论边界（不因 suite 而放宽）

Roadmap §4 提过 A / B 两条路，**本方案取 B**：阶段 2 只把测量装置建好，不出「比例低所以恢复粒度选对了」的结论。

有了 suite runner 也不改变这一点——故障注入跑出来的是**构造分布**，不是真实分布。真实分布要等阶段 3 有真工具。这条直接写进退出门槛，免得 suite 一跑出数字就有人拿它下结论。

### 0.3 二次反思与评审的修订记录

上一版 V20260826 定稿后做了一次二次反思，并收到一份逐条核源码的评审。**评审确认了方案的 20 条源码断言全部属实**，同时两侧各自发现了对方没发现的问题——合并后共 17 处修订，逐条记在这里。

#### A. 事实性错误（1 条，作者自查，评审未覆盖）

**修订 1　`node:sqlite` 无需 flag——决 5 的成本对比是编的。**

上一版 §2.1 与决 5 的选项描述都写着「当前 Node v22.22.3 上 `node:sqlite` 在 `--experimental-sqlite` 后面」「每个入口脚本都得带 flag」。**实测证伪**：

```text
Node v22.22.3，无 flag：
  DatabaseSync(":memory:")     OK
  PRAGMA journal_mode=WAL      → 'wal'
  busy_timeout                 OK
  两个连接读同一 .db 文件       OK
  唯一影响：一条 ExperimentalWarning
```

决 5 原本的成本对比是「不升就得全局带 flag」，实际只是「不升会有一条 warning」。升 Node 24 仍有独立理由（LTS、API 更定型、少一条警告），但**弱得多**。故决 5 一度改标【待复核】。

**教训是方法论的，值得单独记**：这条断言是**凭记忆写的**，没跑过。原则十三说「证据先于冻结」，它管的不只是端点行为——**工具链行为同样是可实测的事实**，不该靠记忆填进方案。这与 Spike 0 那条「第二轮十条结论有六条换端点就不成立」是同一类毛病的两个领域。

> **决 5 复核结果（2026-08-26）：仍升，理由换过。**
>
> 原理由（不升要带 flag）作废，换成实测得到的两条真实收益：`ExperimentalWarning` 消失、npm 一并升到 11。用户已在本机装好 v24.19.0，**升级后零回归**（§2.1 的对照表）。
>
> 决 5 因此从【待复核】回到【已定】，但**它的理据强度和上一版不同**——上一版是「必须升」，现在是「升了有实测收益，且已验证无代价」。

#### B. 方案内部矛盾（3 条）

**修订 2　决 3 的冻结粒度会让跨天 resume 写错日期，且被系统指令背书。**

作者反思发现前半：批 1 的招牌能力就是「今晚关机、明早接上」，「长时运行的 Run 看到过期时间」从边角情况变成常态——周一起的 Run 周三 resume，交接清单上会写周一。这正是复评 P1「Agent 编造 2025 年」修复要解决的那类问题换了个方式回来。

**评审 P1-1 补上了更硬的后半**：`DEFAULT_SYSTEM_PROMPT` 明确指示模型「日期与时间一律以上下文中的『[系统事实] 当前时间』为准」（`compose.ts:229`）。于是过时的日期不是模型猜错，而是**被系统指令背书的错误**。

**评审还翻出一条决定性的历史实证**：`compile.ts:189-193` 白纸黑字记录着「为什么不做成 now 工具——**工具要模型记得调，它上次就没调，直接编了一个**」。

三条合起来：`now` 工具**不能当主机制**。修订后的决 3 是三件事，落点见 S9。

**修订 3　前置指纹无处安放（作者）＋ 谁去取指纹没指定（评审 P1-2）——同一个洞的两半。**

上一版 §1.2 / S11 说「Runtime 在执行前把所需指纹落进 transcript」，但 `TranscriptEntryKind` 只有 `RUN_META | MESSAGE | COMPACT_BOUNDARY | BLOB_REF` 四个值，per-Action 的指纹**一个都放不进去**；塞进 `RUN_META` 语义是错的（它是滚动聚合，不是逐 Action 事实）。

评审同时指出：**谁去算指纹也没指定**。给任意工具的目标算指纹是工具域知识，而依赖方向禁止 Runtime import case 包；现有的 `ResolvedEffect.targetFingerprints`（`tool.ts:28-32`）只装了 `[{ target: 路径 }]`，没有 hash（`effect-resolver.ts:49`）。

两半的答案都在 §1.2 修订后的正文里。

**修订 4　`runs` 表存「序号高水位」踩了方案自己划的线（评审 P1-3）。**

§2.3 不建九张事实表的理由是「建了就是第二份权威」，而 S5 却给 `runs` 表安排了「序号高水位」——`lastSequence` 的权威副本已经在 transcript 的 `RUN_META` 里（`run.ts:101-118`，resume 侧 `facade:187` 取 max 消费）。

**处置：`runs` 表不存高水位。** 见 §2.3 修订后的表定义与 S3 的取号规则。

## 1. 阶段 2 要解决的问题总账

### 1.1 跨进程 resume 有三处硬阻断，都不是存储

**① `resume()` 根本进不去。** [`facade/index.ts:128-129`](../../packages/harness-runtime/src/facade/index.ts) 第一行就是 `this.specs.get(key)`，取不到直接抛「阶段 1 的 RunSpec 只在内存里」。`specs` / `status` / `runs` / `running` 四个 Map 全在进程内（`:78-82`）。**transcript 落了 SQLite，跨进程 resume 仍然是零。**

这条不在存量 29 项里——M-2 把这四个 Map 记成了「长驻进程内存泄漏」，性质记轻了。架构 §26.2 其实列了 `run_specs` / `agent_spec_snapshots` / `runs` 三张表，是 Roadmap §4 那句「SQLite transcript、Blob」把范围写窄了。

而且 **AgentSpecSnapshot 必须是冻结的那一份**：[`facade/index.ts:280-296`](../../packages/harness-runtime/src/facade/index.ts) 的三条恢复分支判定完全读 `spec.agentSpec.toolSnapshots` 的 `idempotency` 与 `verification.mode`。若 resume 时用今天 compose 出来的工具声明，改一次 `append_log` 的 verification 就会让同一条 transcript 走进不同分支，而盘上看不出来。

**② 跨天 resume 会立刻 `BUDGET_EXHAUSTED`。** [`run-loop.ts:261`](../../packages/harness-runtime/src/loop/run-loop.ts) 是 `elapsed = now() - state.budgetUsage.startedAt`，`startedAt` 由 A-7 从 `RUN_META` 原样继承，`DEFAULT_BUDGETS.maxActiveWallClockMs` 是 **10 分钟**（`budget/index.ts:33`）。今晚关机、明早 resume → 第一次迭代就撞墙。

R-2 在存量清单里是「等审批的时间被计入 active」这种边角场景，**跨进程之后它 100% 触发**。它不是可选项，是批 2 的头一条。

**③ CLI 没有 `--resume`。** [`main.ts`](../../apps/cli/src/main.ts) 只有 start 路径。`--list-runs` / `--resume <id>` / `--recovery-decision` 三个入口都得新建，否则 §18.2 的三条分支在真实使用里一条都走不到。

### 1.2 决 6 的落地：分流依据、指纹落点、捕获机制

**病理判断有代码自证。** `write_note` 的 idempotency 注释自己承认：**「覆盖写严格说是幂等的，标成非幂等是为了让分支二有工具可测」**。测量仪器就是被测对象身上的旋钮，这不是推断。

**分流依据改成 Action 级事实。** 现在的判定链（[`facade/index.ts:290`](../../packages/harness-runtime/src/facade/index.ts)）第三行用 `verification.mode`（**执行后**能不能验）回答了「**崩溃后**能不能观测」。这两件事真的不同——`append_log` 执行后验不了（验证器不知道「该有几行」），但崩溃后能不能观测，取决于**执行前有没有落下前置指纹**。

> **可观测性不是工具的内在属性，而是「执行前有没有留下足够的前置指纹」。**

于是 `append_log` **同一个工具**可以两种都跑——带指纹落分支二、不带落分支三。故障注入因此能独立控制分流。

**落点：新增 `TranscriptEntryKind = "ACTION_FACT"`。**（修订 3 的前半）

per-Action 的指纹在现有四个 kind 里无处安放。扩 `TranscriptEntryKind` 是对 §18.5【定】的 Contract 变更，必须写 ADR——好在 §28.6 本就把 TranscriptEntry 的冻结放在阶段 2，扩它正好在窗口内。同时按 §0.1 收窄冻结范围：只冻 resume 真实用到的部分。

**捕获机制：复用 `VerificationPort`，不新增 Port。**（修订 3 的后半）

三个候选里选它，理由是**前置观察与崩溃后观察必须是同一个实现**——否则两次测的不是同一个量，比对没有意义。而 `VerificationPort` 已经是「独立观察外部世界」的那个 Port，`facade.observe()` 里已经在用它做崩溃后观察。

落地形态：

- `ToolDefinition.recoveryObservation?: RecoveryObservationDescriptor`，声明「崩溃后要观测什么、需要哪些前置指纹」；

#### S9　决 3【修订】落地：三件事，`now` 工具排最后

**这一步的顺序有讲究**：前两件是主机制，第三件是补充。反过来做就是重演 `compile.ts:189-193` 记下的那次失败。

**① 时间事实冻结在「进程段」级。**

```text
start()  → 段起始时刻 = RunSpec.createdAt
resume() → 段起始时刻 = resume 时刻（重新冻结）
```

`ResumableRunFacts` 增加 `segmentStartedAt`，每段的第一条 `RUN_META` 落它。段内前缀稳定（缓存收益保住），段间如实反映日期（跨天 resume 不再写错日期）。`renderTimeFact()` 改读它，不再每轮用 `deps.now`（`compile.ts:201/257`）。

**② 系统提示词同步改写。**（评审 P1-1）

`DEFAULT_SYSTEM_PROMPT`（`compose.ts:229`）现在说「日期与时间一律以上下文中的『[系统事实] 当前时间』为准」。**「不得自己推断日期」这条强约束必须保留**——它是复评 A1 修复的核心，削弱它会让「编造 2025 年」回来。要改的是补充说明：

> 该事实是**本次执行段开始时刻**。若任务需要精确到分钟，或本次运行可能持续较长时间，先调用 `now` 取当前时刻；**任何情况下都不得自行推断日期**。

**改这句话之前先读 `compose.ts:227-229` 的【定】**：

> 「光靠 prompt 约束，模型只会从『编一个日期』换成『回避日期』，两次实跑各出现过一种。**事实必须真的在上下文里。**」

它管两件事：

- **封死一个诱人的简化**——不得把注入的时间事实删掉、改成「让模型自己调 `now`」。事实注入是零轮次、零 token 往返、**不可能被跳过**的那条路径（`compile.ts:189-193`）；`now` 工具三条都不占。
- **点出第二种失败模式**——改提示词的风险不只是「编造回归」，还有「回避回归」（模型索性不写日期）。告诉模型「该事实可能过时」恰好是往回避那侧推的措辞。批 2 验收的「时间事实段」必须**同时**断言这两种：既不能写错日期，也不能不写日期。

**③ `now` 工具（补充机制，不是主机制）。**

只读、幂等、`verification.mode = "NONE"`——这是阶段 2 唯一新增的工具，属于对「阶段 2 不加工具」的刻意例外，理由是它只读且幂等，不会扰动三条分支的分布统计。

代码注释里必须引 `compile.ts:189-193` 的历史实证（「工具要模型记得调，它上次就没调」），写明**它为什么不能当主机制**——否则下一个读代码的人会以为时间问题靠这个工具解决。

**④ 接上 `cache_control`**（U-9 的另一半）。稳定前缀是 tools ＋ system 约 640 token（实测固定开销 540）；时间事实冻结到段级后可以并入稳定区。评审核实 `cache_control` 现在只存在于 `compile.ts:186` 的注释里。

#### 批 2 验收：`verify:budget`

每条预算轴各注入一个必然撞墙的脚本化 Run，断言 Terminal 与 `BudgetHardLimitReached.axis` 一致；外加三段：
