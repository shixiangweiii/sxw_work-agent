# 阶段 1 实施方案：Headless Walking Skeleton

> 文档版本：V20260823
> 依据：`架构设计/WorkAgent架构设计_V20260823_05.md` §28.2
> 阶段目标：主循环跑通，且**端点差异一行都不进主循环**
> 研究问题：端点差异能否被完全挡在主循环之外？批内配对不变量在没有状态机的情况下能否守住？

## 0. 执行约束

来自 D-25 与本次目标设定：

| 约束 | 含义 |
|---|---|
| **Node ＋ npm** | 不引入 pnpm / turbo / nx 等 monorepo 工具链 |

**凭证纪律**【定】：`.env` 已在 `.gitignore` 中。凭证只能发往它所属 Endpoint 的 `baseUrl`（V05 §22.3），实现上必须有显式断言——Spike 0 期间真实踩过一次。

## 1. 工程形态

### 1.1 为什么用 npm workspaces

V05 §27.2 的目录结构把 `packages/` / `adapters/` / `apps/` / `cases/` 分开，这不是排版偏好——它是**单向依赖**（§4.2）的编译期表达。用单一 `src/` 树会让「主循环 import 了 Provider SDK」这类违规无法被工具发现。

npm workspaces 是 npm 自带能力，不算「引入工具链」。

### 1.2 目录

```text
package.json                     ← workspaces 根，唯一的依赖声明处
tsconfig.base.json               ← 共享编译选项
tsconfig.json                    ← 引用全部 workspace，供 tsc --noEmit

packages/
├── harness-runtime/             ← Layer 3 全部
│   └── src/
│       ├── facade/              HarnessRuntime 实现
│       ├── loop/                主循环、LoopState、Continue / Terminal
│       │   └── interrupt/       AbortController 与 Interject 队列
│       ├── transcript/          消息追加与重建（恢复的唯一来源）
│       ├── context/             ContextItem / ContextFrame / 编译
│       ├── model/
│       │   ├── shapes/          形状适配器接口
│       │   └── capability/      端点能力声明的消费与校验、漂移检测
│       ├── action/              ActionBatch / PreparedAction / Effect / Policy
│       ├── tool-runtime/        Tool 注册与执行
│       ├── verification/
│       ├── budget/
│       ├── trace/
│       ├── ports/               14 个 Port 接口
│       └── types/               跨模块共享类型
└── testkit/
    ├── fake-endpoint-profile/
    ├── fake-clock/
    ├── deterministic-id-generator/
    ├── in-memory-transcript-store/
    └── scripted-approval-decider/

adapters/
├── shape-anthropic-messages/    ← v0.1 主力形状适配器
└── endpoint-profiles/           ← bailian-anthropic.json 等（数据，非代码）

cases/
└── micro-cases/                 ← 只读 Tool ＋ 可控慢的可验证写 Tool

apps/
└── cli/                         ← Composition Root ＋ 三条验收脚本
```

### 1.3 依赖

仅三个运行时依赖：

```text
@anthropic-ai/sdk    形状适配器唯一使用者
dotenv               读根 .env
tsx / typescript     开发期
```

**`@anthropic-ai/sdk` 只允许出现在 `adapters/shape-anthropic-messages/`。** 这是 §4.2 禁止项「主循环 → Provider SDK」的落点，实现完成后用 grep 核对。

## 2. 实施步骤

按依赖顺序分 12 步。每步结束跑一次 `npm run typecheck`。

### S1　工程骨架

根 `package.json`（workspaces ＋ scripts）、`tsconfig.base.json`、各 workspace 的 `package.json` 与 `tsconfig.json`、`.gitignore` 补充。

**产出判据**：`npm run typecheck` 在空实现下通过。

### S2　共享类型与 14 个 Port

`packages/harness-runtime/src/types/`：Id 类型、`RunSpec`、`ContextItem`、`ContextFrame`、`RuntimeErrorRecord`、`ActionBatch`、`PreparedAction`、`RunOutcome`、`RunStatus`、`ToolDefinition`、`VerificationDescriptor` 等。

`packages/harness-runtime/src/ports/`：14 个接口，**10 个带实现契约注释，4 个标注「阶段 1 只留接口」**（V05 §8.7）。

**关键**：`RuntimeErrorRecord` 四维全建，**值域按 D-22 裁剪**——枚举全写，但注释标明阶段 1 只产生哪几个。

### S3　端点能力声明

`packages/harness-runtime/src/model/capability/`：

- `EndpointCapabilityProfile` 及 `protocol` / `context` / `tokens` 三组（D-17，`errors` / `limits` 留类型不实现）
- `profile-loader.ts`：从 `adapters/endpoint-profiles/*.json` 加载
- `drift-detector.ts`：三条最小规则（V05 §8.6）

`adapters/endpoint-profiles/bailian-anthropic.json`：V05 §8.6 的实测声明，逐字段照抄。

**这一步先于形状适配器**，因为适配器要消费它。

### S4　形状适配器

`adapters/shape-anthropic-messages/`：

| 方法 | 左边（形状） | 右边（端点声明） |
|---|---|---|
| `buildRequest(frame, profile)` | Anthropic Messages 请求体 | `perRequestBaseTokens` 等常量 |
| `parseStream(stream)` | `content_block_*` 事件 | `hasExplicitBlockCloseEvent` |
| `normalize(response)` | 解析出 toolUses / 文本 / 推理块 | `reasoningBlockRule` 决定保留策略 |
| `validateFrame(frame)` | 协议规则 | `validatesToolResultPairing` 等校验强度 |
| `countTokens(frame)` | `/v1/messages/count_tokens` | `countTokensAccuracy` |
| `classifyError(err)` | — | `discriminators` |

**凭证断言**：`assertCredentialGoesWhereIntended()`——baseUrl 必须与 profile 所属 endpoint 一致。

### S5　transcript

`packages/harness-runtime/src/transcript/`：`TranscriptEntry`、append-only store、`rebuildMessages()`（从最后一个 `COMPACT_BOUNDARY` 之后取）。

`packages/testkit/in-memory-transcript-store/`：阶段 1 的实现。

**不变量 5**：`append()` 返回后才允许更新内存 `messages`——由 store 的接口形态强制（async append 先于 return）。

### S6　Context 层

`context/`：`ContextItem`、`ContextFrame`、`compileFrame()`。

阶段 1 范围：协议角色三档判定（**读端点声明，不推断**）、`fixedOverheadTokens` 单列、`countTokens` 调用、`validateFrame` 调用。

**Compact 写但预期跑不到**（V05 §28.2 已知项）——写一个最简实现并在日志里标明「本次未触发」。

### S7　Tool Runtime 与两个工具

`tool-runtime/`：`ToolRegistry`、`normalizeInput`、**`inputSchema` 校验（Runtime 自持，四端点全放行）**、执行与超时。

`cases/micro-cases/tools/`：

| 工具 | 性质 | 用途 |
|---|---|---|
| `list_dir` | 只读，快 | 触发多 tool call |
| `write_note` | 写，**可注入延迟**，有 Verification | D-23 要求的「可控慢工具」，三条中断路径靠它注入 |

`write_note` 的慢是参数化的（`delayMs`），默认 0，验收脚本传大值。

### S8　Action 与 ActionBatch

`action/`：`ProposedAction` → `PreparedAction` → `ExecutionAttempt`；`EffectResolver`（声明式最小实现）；`Policy`（`TRUSTED_PERSONAL` preset）；`ApprovalDecider` 接口。

`ActionBatch`：`SEQUENTIAL` ＋ `PER_ACTION` ＋ `CONTINUE_REMAINING`（D-01、D-21）。

**核心：`settleBatch()` 保证每个 call 恰好一个 result。** 三条中断路径的合成 result 都收敛到这个函数。

### S9　Verification 与 outcome 结算

`verification/`：`Verifier` 接口、`REOBSERVE` 模式最小实现。

`settleOutcome()`（V05 §10.4）：

```ts
const failed = verifications.filter(v => v.required && v.status === "FAILED");
return failed.length === 0
  ? { kind: "SUCCESS" }
  : { kind: "COMPLETED_WITH_LIMITS", incompleteItems: failed.map(toIncompleteItem) };
```

### S10　主循环

`loop/`：`LoopState`、`Continue`、`Terminal`、`runLoop()`。

`loop/interrupt/`：`AbortController` 封装、Interject 队列。

**循环纪律五条必须在代码里可见**：每个 `continue` 站点构造完整 `LoopState`（用一个 `nextState()` 帮助函数强制），每个 `return` 是具名 `Terminal`。

`facade/`：`HarnessRuntime` 实现，含 `resume()`（D-24）。

### S11　Composition Root ＋ CLI

`apps/cli/`：读 `.env`、装配 10 个 Port、构造 `RunSpec`、消费事件流、交互式 `ApprovalDecider`、Ctrl+C 接 cancel。

### S12　三条验收脚本

| 脚本 | 做什么 |
|---|---|
| `verify:endpoint-profile` | 加载 `fake-endpoint-profile`（`validatesToolResultPairing: true` ＋ `reasoningBlockRule: PLACEHOLDER_REQUIRED`），跑同一任务，**对比 Runtime 行为变化，并 diff 主循环文件哈希证明未改** |
| `verify:pairing` | 三条中断路径各注入一次，扫描 transcript 断言无「无 result 的 tool_use」 |
| `verify:resume` | 批执行中途丢弃 `LoopState`，从 transcript 重建后继续，与不中断跑完对比 |

三条都**打印可读证据**，不是断言绿灯。

## 3. 不得绕过清单

V05 §28.2【定】。实现时逐条对照：

| 项 | 落点 |
|---|---|
| Effect 解析 | `action/effect-resolver.ts`，`PreparedAction` 必须有 `resolvedEffect` |
| 错误副作用状态 | `RuntimeErrorRecord.sideEffectState`，`UNKNOWN` 不得自动重试 |
| 批内配对不变量 | `action/settle-batch.ts` 单点收敛 |
| 边界脱敏 | `RedactionPort.redact()` 在 ToolResult 进 Context 之前 |
| `outcome.kind` 结算 | `verification/settle-outcome.ts` |
| 端点能力声明的读取路径 | 主循环不 import capability 模块，只经 `ModelProtocolPort` |

## 4. 完成判据

1. `npm run typecheck` 干净；
2. `npm run dev -- --task "..."` 能对真实百炼 Anthropic 端点跑通一个多轮多工具任务，具名 `Terminal` 退出；
3. 三条 `verify:*` 脚本可运行并输出证据；
4. `grep -r "@anthropic-ai/sdk" packages/ apps/ cases/` 无结果——SDK 只在 `adapters/shape-anthropic-messages/`；
5. `grep -rn "bailian\|dashscope\|百炼" packages/harness-runtime/src/loop/` 无结果——端点名不进主循环。

第 4、5 条是**研究问题「端点差异能否被完全挡在主循环之外」的机械判据**。
