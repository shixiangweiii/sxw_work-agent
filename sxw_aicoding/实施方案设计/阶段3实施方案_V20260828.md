## 0. 七个前置决定

2026-08-28 讨论确定。这七条的共同指向只有一句话：

> **Atlas 做的是通用的思考与执行能力，网页归档只是将来众多评测 Case 中的一个。
> 能力面不由任何一个 Case 定义。**

| # | 决定 | 理由摘要 |
|---|---|---|
| **决 1** | **阶段 3 不建 `cases/web-archive/`，一行都不建** | Case 是尺子，不是模具。上位基线 §10.1 已明写网页归档「主要是 Runtime 可靠性综合 Case，**不能独立证明** Agent 的规划和决策效果」。它进入项目的时机是评测阶段，不是能力建设阶段 |
| **决 2** | **新建 `tools/common`（`@workagent/tools-common`），分拣标准是「办公 / 代码 / 聊天三场景常用」** | 今天**所有**工具住在 `cases/micro-cases/` 里，连 `list_dir` 也是；V05 §27.2 的目录树里根本没有「通用工具」这一层。不开这个柜子，工具会按 Case 的形状长出来，阶段 4 就是重写而不是重构 |
| **决 3** | **不接 Capability 授权层；审批默认放行。但 workspace 边界对「写」保留、对「读」放开** | 先做能力，授权走 bugfix。边界保留的理由是不对称的：**读错文件是信息问题，写错文件是不可逆损失** |
| **决 4** | **Eval 层与 Replay 全部推到「开发完成后统一评测」** | Replay 服务的是 Eval 与调试，不是能力本身。§28.6 里 Replay 那行的 Contract 冻结门槛随之继续挂着（V05 §18.5 本来就写着 Replay 语义保持【验】不冻） |
| **决 5** | **PARKED lease 不做；人工接管本身要做** | Lease 的真需求来自**多 Run 并发**，不是来自浏览器。当前是单进程、一 Run 一循环（§18.6【定】「等待就是 await，进程死了所有等待一起死」），三个场景里找不到一个通用工具需要独占。**而人工接管三场景都有**：办公要人去外部系统确认、代码要人解冲突、聊天要人确认发送 |
| **决 6** | **不新增任何编排层**（Planner / Memory / Sub-agent / Verifier Strategy） | 上位基线与 V05 §28.5 的抑制规则原文：「**只有 Eval 证明需要时才引入**」。而实测指向的瓶颈不在编排——见 §0.1 |
| **决 7** | **研究问题的判据是结构性的，不依赖评测** | 决 4 把评测推后了。判据换成边界 grep ＋ 跨场景 smoke，见 §5 |

### 0.1 决 6 的证据：瓶颈不在「思考」，在「能看到什么、能做什么」

「加强通用思考能力」最容易走偏的一步，是加一个 Planner 模块。本阶段明确不这么做，理由是**实测**：

| 观察 | 出处 |
|---|---|
| 归档盘点任务，模型 **4–5 次调用 / 7–8 次工具**完成，中位 9,905 token、16.3 秒 | 回归评测 §5 |
| 37 次工具调用只失败 1 次，且模型**自己纠正后完成**任务 | 回归评测 §5.2 |
| 那一次失败是**把文件路径传给了 `list_dir`** —— 因为工具集里**没有**查看单个对象的能力 | 回归评测 P2-2 |
| 阶段 1 的射程被工具卡死：「`list_dir` 只返回名字/大小/是否目录，**没有 read_file**，所以射程是『目录元数据 → 模型加工 → 文本产物』」 | Roadmap §3 |
| 模型从任务原文抽取显式要求：**5/5 稳定、条目一致、且有判别力**（加一句要求 → 0/5 变 5/5） | `probe:requirement-extraction`（2026-08-28） |

**四条合起来的结论**：模型的规划与自纠能力在当前任务规模上没有暴露短板；短板全在**它能看到什么、能做什么**。

> 所以本阶段提升「思考能力」的方式是**扩能力面与上下文质量，不是加编排模块**。
> 这与上位基线 §9.6【定】「不把轨迹复杂度当作效果」是同一条纪律：
> 一次正确判断加一次确定性执行就够时，不该人为拆成多轮。

### 0.2 反过拟合的三道机械闸门

「不做定制」这句话必须有机械判据，否则半年后没人能复核。三道闸：

1. **第 6 条边界 grep**（§2.3）——`packages/` 与 `adapters/` 不得 import `tools/`；`tools/common` 不得 import `cases/*`；
2. **三场景声明**（§2.2）——每个进 `tools/common` 的工具，文件头必须写出它在办公 / 代码 / 聊天三个场景的各自用例，不适用要写明为什么；
3. **跨场景 smoke**（§5）——**两个来自不同场景、互不相干的真实任务，用同一套工具都跑通**。这是唯一能真正证伪「通用」的东西：前两道只能防止显式依赖，防不了「形状是照着某个任务长的」。

还有一道**免费的经济闸**：§16.1【定·实测】每个工具约 180 token 固定开销，已单列在 `ContextFrame.fixedOverheadTokens` 里。「一个 Case 一套工具」的做法会让工具数膨胀并直接反映在每次请求上——**这是个随时可读的过拟合警报**。

### 0.3 本阶段开工前已经处置掉的两件事

- **开发环境曾经完全起不来**（2026-08-28 实测）。`npm run dev` 被两道闸门连续挡下：先是 M-5（`.env` 模型名 vs 声明），修掉后是 U-6（`expectedBaseUrlHost` 写 `dashscope.aliyuncs.com`，而实际用的是专属部署 `llm-*.cn-beijing.maas.aliyuncs.com`）。已改声明字段并实跑通过。
  > **值得记一笔**：U-6 这条断言**从未对真实 `.env` 生效过**——M-5 排在它前面一直先失败，把它遮住了；而 `verify:drift` D 段用的是**故意错配**的组合，测不到真实配置。**闸门排在另一个闸门后面，等于没有闸门。**
- **DeepSeek 对照端点当前 401**。已核实：磁盘 `.env` 的 key 与用户提供的一致、`dotenv` 读取正确、无 shell 覆盖、仓库只有一个 `.env` —— 是端点侧拒绝。它只服务 §24.6 的对照测试（属评测），**按决 4 不阻塞本阶段**。

## 1. 阶段 3 要解决的问题总账

### 1.1 能力面的四个空格，都是「没有工具需要它」造成的

四个 Port 至今零实现。把代码里写的不实现理由抄下来，会发现是**同一句话**：

| Port | 代码里的原话 |
|---|---|
| `BlobStorePort` | 「大结果外置**要到 Case 01 才有真实的大结果**」 |
| `ArtifactStorePort` | 「**阶段 1 Micro Case 不产出 Artifact**」 |
| `SecretResolverPort` | 「**阶段 1 没有需要 secret 的工具**」 |
| `CapabilityLeasePort` | 「lease 语义**要到 Browser Capability 才有真需求**」 |

同族的还有：`ToolProgress` 事件无生产点（U-3）、`WAITING_FOR_INTERACTION` 全仓只出现在类型定义里、Artifact 级 Verification 从未实现。

**不是忘了做，是没有工具需要它们。** 所以本阶段的顺序是：**先建工具面，让机制被真需求逼出来**——而不是先实现 Port 再找用例，那正是决 1 / D-14 反复警告的「盲写」。

按决 2 的三场景标准逐个过一遍，四个 Port 的判定是：

| Port | 三场景谁会用到 | 本阶段 |
|---|---|---|
| BlobStore | 办公读大文档 / 代码读大文件 / 聊天拉长会话 | ✅ 做 |
| ArtifactStore | 办公产文档 / 代码产方案 / 聊天产纪要 | ✅ 做 |
| SecretResolver | 网盘凭证 / git 凭证 / 钉钉 token | ⏸ 本阶段工具不需要凭证，**不做**（首批工具明确不含需要凭证的） |
| CapabilityLease | —— | ❌ 决 5，不做 |

### 1.2 质量的空格：两层 Verification 只实现了一层

V05 §10.4【定】的原文：

| 层 | 问题 | 触发点 | 现状 |
|---|---|---|---|
| Action 级 Verification | 这一步的副作用是否达成 | Attempt 完成后 | ✅ 已实现 |
| **Artifact 级 Verification** | **这个产物本身是否完整合法** | ArtifactRegistered 之后 | ❌ **零实现** |

> 【定】两者不得互相替代。**Run 层不提出自己的问题，只汇总前两层已经产生的事实。**

Action 级验证的参照物是**模型自己的意图**（`write_file` 验的是「磁盘内容 == 计划内容」），所以它对「模型的意图本身不全」在结构上是盲的——不是恰好没查到。§28.4 把「两层 Verification」列在阶段 3，而第二层的触发点是 `ArtifactRegistered`，所以它与 ArtifactStore 是**同一块，不能拆开排**。

**【定】Artifact 级检查器的通用/专用分界**：产物**类型**的静态结构约束（Markdown 是否合法、ZIP 能否解开、JSON 能否解析、hash 是否对得上）属于通用，进 `tools/common`；某个具体任务的业务规则属于 Case，进 `cases/`。**本阶段只做通用那半**——决 1 之下，没有 Case 包可写。

### 1.3 从阶段 2 带进来、本阶段必须一起处理的

| 项 | 为什么在本阶段 |
|---|---|
| **P1-1** 官方入口不能选端点 | 开发期要频繁换端点验证工具行为。且它是「装配完成 ≠ 可达」的第三次显形（前两次：`interject` API 在而 CLI 零调用点；U-1…U-9 声明了不接线） |
| **`interject` CLI 入口** | 从阶段 1 挂到现在。人工接管与它共用同一条运行期交互通道，**先有通道才谈得上接管** |
| **N-8** `list_dir` 错误分类 | 一切异常统一映射成 `NOT_FOUND / AFTER_MODEL_CORRECTION`。新工具会照抄这个形状，**必须在写新工具之前修** |
| **P3-26** redaction 打花文件名 | STANDARD 档 email 正则作用于所有工具输出。办公场景文件名含 `@` 是常态，`read_file` 一上就会撞 |
| **U-3** Progress Guard | `fetch_url` / 大文件读取是它的第一个真需求 |

其余存量（N-7 `usageFieldMap`、P3-28 CLI 退出码、P2-3 审批超时口径等）**按用户决定走 bugfix 阶段**，不进本方案。

## 2. 工程形态变化

### 2.1 新增目录

```text
tools/
└── common/                       ★ 本阶段新增。@workagent/tools-common
    └── src/
        ├── index.ts              工具快照数组 ＋ Handler ＋ Verifier
        ├── fs/                   list_dir / read_file / stat / write_file / edit_file / search
        ├── net/                  fetch_url
        ├── time/                 now
        └── artifact-checks/      通用产物类型检查器（Markdown / JSON / ZIP / 文本编码）
```

**不分子包**（决 2）。将来若要拆 `tools/office/`、`tools/code/`，目录形态已经留出位置。

留在 `cases/micro-cases/` 的：`append_log`（存在的唯一理由是让 §18.2 第三条恢复分支可达）与 `delay_ms`（测量「执行到一半取消」的旋钮）。**它们是测量工具，不是办公工具**——三场景标准一条都不满足。

### 2.2 工具声明的两条硬要求

**【定】文件头必须写三场景用例。** 形态与 §2.5 规格纪律第 4 条（「每新增一个 Port 必须同时指出强制它存在的不变量」）同构：

```ts
/**
 * read_file —— 读取文件内容。
 *
 * 三场景：
 *   办公：读 Word/Excel 导出的文本、读会议纪要
 *   代码：读源文件、读配置
 *   聊天：读消息导出、读附件正文
 *
 * 形态：只读、幂等 → §18.2 分支一；**可能产大结果 → 触发 Blob 外置**
 */
```

**【定】`ToolDefinition` 必须完整填写**，尤其三个最容易漏的：

- `redaction` **必填**（V05 §12.3【定】：不声明的 Tool 走默认最严格 profile，而不是默认放行）；
- `idempotency`——消息级恢复下它**是恢复正确性的前提**，不是可选优化（原则十五）；
- `recoveryObservation`——决 6 的分流依据，声明它不等于崩溃后一定观察得了，真正的判据是 Action 级事实。

### 2.3 第 6 条边界 grep

```bash
grep -rn "@anthropic-ai/sdk" packages apps cases tools      # 1. Provider SDK 只在形状适配器里
grep -rn "dashscope" packages/harness-runtime/src            # 2. 端点名不进 Runtime 代码
grep -n "profile\." packages/harness-runtime/src/loop/run-loop.ts   # 3. 主循环不读端点声明
grep -rnE "micro-cases|tools-common" packages/harness-runtime/src   # 4. Runtime Core 不 import 工具实现
grep -rn "node:sqlite" packages apps cases adapters tools    # 5. 只允许 packages/store-sqlite/
grep -rnE "@workagent/tools-|tools/common" packages adapters # 6. ★新增：Runtime 与适配器不得依赖工具包
grep -rn "cases/" tools/                                     # 6b. ★新增：通用工具不得依赖任何 Case 包
```

第 4 条从「不 import Case Package」推广为「**不 import 任何工具实现**」——工具是给 Composition Root 装配的，Runtime 只认 `ToolDefinition` 类型。

第 6b 是「通用」这个词的机械含义：**通用工具一旦依赖某个 Case，它就不通用了**，而这件事从代码上看不出来，只能靠 grep。

### 2.4 装配变化：两个工具包共存

`compose.ts` 现在把 `MicroCaseToolHandler` 与 `MicroCaseVerifier` 写死。两个包共存之后需要**按 `toolName` 路由的组合器**：

```text
CompositeToolHandler([commonHandler, microCaseHandler])
CompositeVerifier([commonVerifier, microCaseVerifier])
```

**【定】组合器住在 Composition Root（`apps/cli/`），不进 Runtime。** 路由逻辑认识具体工具名，而 Runtime 不许认识任何工具——这是边界 4 的直接推论。

现有 8 条 `verify:*` 脚本依赖 `write_note` / `append_log` / `list_dir`。它们改为装配 `[...commonTools, ...microCaseTools]`，**不需要跨包 import**（`compose()` 的 `tools` 参数本来就支持传入工具列表）。

### 2.5 迁移的一处真实代价

`resume` 分支一是「**真的重新执行**」，判定读的是 RunSpec 里**冻结的** `agentSpec.toolSnapshots`（存在 SQLite 里）。工具改名换包后，老 Run 的快照里还是 `write_note`，而注册的是 `write_file`。

**【定】不做别名表，接受「迁移前的 Run 不能 resume」，给一条明确的错误信息。** 库里只有开发期 Run，代价接近零；别名表是会一直背下去的永久负担。

## 3. 实施步骤

四批 ＋ 一个跨批小步，每批一条验收脚本。**每步结束跑 `npm run typecheck`。**

### 批 1 · 通用能力面立起来

做完这批，Atlas 第一次有了「读得到内容、改得动文件、找得到东西」的射程——阶段 1 的天花板（只能看目录元数据）被打掉。

#### S1　`--endpoint` ＋ 两条阻塞存量

先做它，因为后面每一步都要换端点验证工具行为。

- CLI 与 `eval/suite` 都加**受枚举约束**的 `--endpoint bailian|deepseek`，`compose()` 本来就支持，只是入口没暴露；
- 启动时打印**解析后**的端点 / 声明 id / 模型 id（**绝不打印 key**）；
- **保留现有 fail-fast**（M-5、U-6）——修的是可选择性与诊断，不是绕过能力声明；
- 顺带补 **`interject` 的 CLI 入口**：运行期监听 stdin，回车提交插话。主循环第 ⓪ 步的排空逻辑与 `runtime.interject()` 都在，缺的一直只是调用点。

**产出判据**：`npm run dev -- --endpoint bailian --task "..."` 与 `--endpoint deepseek` 都能起来（后者受端点侧 401 影响时，判据降为「参数被正确解析并走到凭证断言」）；运行期敲入一句话，下一轮 ContextFrame 里能看到它。

#### S2　`tools/common` 骨架 ＋ 三个迁移

建包、进 workspaces / tsconfig paths / include，迁 `list_dir`、`write_file`（原 `write_note`，**去掉 `delay_ms`**）、`now`。

同批修 **N-8**：`list_dir` 的错误分类。现在一切异常统一映射成 `NOT_FOUND / AFTER_MODEL_CORRECTION` —— EACCES 被报成「目录不存在」模型无从纠正；一个断链符号链接能让整页列举失败。**必须在写新工具之前修，否则五个新工具会照抄这个形状。**

同批修 **P3-26**：`SimpleRedaction` 的 STANDARD 档 email 正则作用于所有工具输出，`user@example.com.txt` 这种文件名会被打成 `[REDACTED:email]`，模型随后拿损坏路径去调工具 → NOT_FOUND 循环。办公场景一上 `read_file` 就会撞。

**产出判据**：`typecheck` 干净；`verify:all` **51 条判据仍全绿**（装配换成两个包之后）；六条边界 grep 全过。

#### S3　`read_file` ＋ `stat`

两个只读幂等工具（§18.2 分支一），但形态不同：

- **`stat`**——单对象元信息。它的直接依据是回归评测 P2-2 的实测：**模型缺这个能力时，会拿 `list_dir` 去探测文件**。
- **`read_file`**——**本阶段第一个可能产大结果的工具**。必须带 `offset` / `limit` 分页，且**显式给出 `total` / `returned` / `truncated`**。
  > 这条是阶段 1 的血泪：`list_dir` 曾 `names.slice(0, 200)` 静默截断而 output 写「共 350 项」——模型会以为自己盘点完了。**静默截断让模型看到一个失真的世界，而它没有任何办法发现。**

**【定】工具内部不得为了「结果太大」而自行截断内容**。超限交给 §11.4 的 Materialization 流程（批 2 的 Blob 外置），工具只如实上报大小。两者的区别是：分页是**模型可控**的（它知道还有多少、可以再取），截断是**模型不可见**的。

#### S4　`search`

三场景各自的形态：办公找文档、代码 grep、聊天找消息。最小接口：

```text
search(pattern, path?, kind: "name" | "content", cursor?)
  → { total, returned, truncated, cursor?, matches: [{ path, line?, preview }] }
```

沿用 `list_dir` 的稳定排序 ＋ cursor 分页（E-4 的成果），错误分类沿用 S2 修好的形状。

#### S5　`edit_file`

**选精确字符串替换**（`old_string` → `new_string`，要求唯一匹配），不选行范围。理由是形态而非偏好：

- **可验证**——Verification 能读回文件确认替换发生了；
- **非幂等 ＋ 可观察**——目标状态取决于起始状态，前置指纹（文件 hash）能回答「那次替换发生没发生」，正好落在 §18.2 **分支二**；
- 行范围在文件被并发改动后语义会漂，而唯一匹配失败是**显式错误**。

它是首批工具里唯一天然落在分支二的**通用**工具（此前只有为测量而生的 `write_note`）。

#### 批 1 验收：`verify:tools`（新增）

| 段 | 判据 |
|---|---|
| A | 六条边界 grep 全过；**判别力实测**：往 `tools/common` 注入一行 `import ... from "@workagent/micro-cases"`，第 6b 条当场翻红并指出行号 |
| B | 每个 `tools/common` 工具的文件头都含三场景声明（机械扫描：文件头注释必须匹配「办公」「代码」「聊天」三个词或写明不适用） |
| C | 每个工具的 `ToolDefinition` 三个必填项齐全（`redaction` / `idempotency` / `recoveryObservation`），缺一即红 |
| D | 分页与截断语义：构造超限目录/文件，断言 `total` / `returned` / `truncated` 三个字段**都出现且自洽**；断言**不存在静默截断** |
| E | 工具固定开销：打印 8 个工具的 `fixedOverheadTokens`，作为过拟合警报的基线读数 |
| F | `verify:all` 原 51 条判据在双工具包装配下仍全绿 |

### 批 2 · 大结果与产物

批 1 的 `read_file` 一上，第一个真实的大结果就出现了。这批把它接住，并第一次让「产物」成为系统里的一等对象。

#### S6　`BlobStorePort` 实现 ＋ ToolResult Materialization 接线

按 §11.4 的流程接线：脱敏 → schema validate → normalize/hash → countTokens → **小结果 inline / 大结果外置 Blob ＋ preview ＋ retrieval 引用**。

【端点·百炼】200KB 的单个 tool_result 被接受、计 34576 token，**所以外置阈值由上下文预算决定，不存在协议硬上限**。阈值走 `ContextBudgetPolicy.inlineToolResultLimitTokens`（字段已存在，从未被消费）。

**【定】外置必须保留协议合法的结构化 stub**（§11.5 不变量 5），且 retrieval 必须让模型能按需取回——否则外置就成了另一种形式的静默截断。

> 顺带记一笔：§22.7 说大结果外置**同时是数据最小化机制**（外置的内容不进模型也就不出境）。本阶段按预算口径设阈值即可；数据边界矩阵（D-19）按用户决定推到真做登录态抓取那天。

#### S7　`fetch_url`

**首批工具里形态覆盖最高的一个**——它一个人同时压出三件事：

| 它是什么 | 逼出什么 |
|---|---|
| 产大结果 | S6 的 Blob 外置 |
| 内容来自外部 | trust 链路**已经接线**（`compile.ts:366` 所有 tool_result 默认 `EXTERNAL_UNTRUSTED`，`run-loop.ts:719` 把 `trustSummary` 喂给 Policy）。变的是**标记第一次名副其实**——此前流过的全是用户自己放进 workspace 的内容，`fetch_url` 带来第一份真正不受控的输入 |
| 慢、可取消 | 批 3 的 Progress Guard |

**【定】不做登录态、不做 Cookie、不做浏览器。** 本阶段就是一个公开 HTTP GET ＋ 内容类型识别。登录态属于「需要凭证」，而 SecretResolver 按 §1.1 本阶段不做。

**【定】`fetch_url` 不得内置任何「正文提取」逻辑。** 从 HTML 里挑正文是**网页归档这个 Case 的业务语义**，一旦写进通用工具，决 1 就被从内部绕过去了。工具只负责取回内容并如实上报类型与大小。

#### S8　`ArtifactStorePort` ＋ Artifact 级 Verification

- Artifact 登记（§17）：关联来源 Run、内容变化形成新版本、删除优先 Tombstone、**Deliverable 原则上必须 Verified**、**Runtime Blob 不自动升级为 Artifact**；
- 接上恒空至今的 `RunOutcome.deliveredArtifactIds`（R-7 登记过这一半）；
- **Artifact 级 Verification**（§1.2）：Runtime 拥有生命周期与结算语义，检查器由工具包提供。**本阶段只做通用产物类型的静态结构约束**：Markdown 可解析、JSON 可解析、ZIP 可解开、文本编码合法、hash 与登记一致。

**【定】不得在检查器里写任何任务级规则。** 「清单里要有合计字节数」这类是**逐 Run 变化**的用户要求，既不是产物类型的固有属性，也不该由 Runtime 判断——2026-08-27 回归评测那次唯一的硬失败，经探针证实正是把这类要求写死成硬门槛导致的误判。

#### 批 2 验收：`verify:artifact`（新增）

| 段 | 判据 |
|---|---|
| A | 构造超阈值的 `read_file` 结果：断言外置发生、**Frame 里留下结构合法的 stub**、模型可经 retrieval 取回完整内容 |
| B | 外置前后帧的 `validateFrame()` 都通过；配对不变量不被外置破坏 |
| C | `fetch_url` 取回的内容标 `EXTERNAL_UNTRUSTED` 且 `trustSummary` 汇总正确；**并断言不可信内容不能创建授权、不能改变 Policy、不能自动批准 Action**（§22.4【定】。链路已接线，但从未用真正不受控的输入验过） |
| D | Artifact 登记 → 通用检查器执行 → 结果进事实表 → `deliveredArtifactIds` **非空** |
| E | **判别力**：喂一个损坏的 ZIP / 非法 JSON，断言 Artifact 级 Verification 判 FAILED，且 outcome 降级为 `COMPLETED_WITH_LIMITS` |
| F | **反向判别力**：喂一个正常产物，断言**不**误判失败（只测「拒绝」的话，一个永远拒绝的闸门也能变绿——`verify:drift` E 段的教训） |

### 批 3 · 长任务与人机通道

#### S9　Progress Guard（U-3）

- `ToolProgress` 事件第一次有生产点：`fetch_url` 与大文件读取周期性回报（低频，30s 量级）；
- Progress Guard 消费它判定「还活着」；
- **【定】不基于流式 delta**（§16.2）——否则长下载会被误判无进展；
- **【定】进展回报不持久化**，它只服务进程内的 Guard 与 UI（§16.2：进程死了 Run 就结束，没有「恢复后判断上次进展到哪」这个需求）。

同批把 §16.2 列的无进展形态接上至少两条：**相同 Tool ＋ 相同 normalized input ＋ 相同 effect digest 连续重复**、**多次不同调用但外部状态无变化**。

#### S10　人工接管（不含 lease）

`WAITING_FOR_INTERACTION` 至今只出现在类型定义里。本步让它第一次可达：

```text
Runtime 请求接管 → Run 进入 WAITING_FOR_INTERACTION（循环阻塞在 await）
    ↓ 用户在终端操作外部世界，完成后回车
Runtime 重新 Observation ＋ Verification → continue / re-plan / ask user / fail
```

**【定】完成信号不等于任务成功，必须重新 Observation**（§20.3）。这是接管与「盲目继续」的唯一区别。

复用 S1 的运行期 stdin 通道。**不做 PARKED lease**（决 5）——单 Run 下「等人操作完再观察」就是一个 `await`，不需要防抢占，这正是 §18.6【定】说的。

#### S11　取消与超时在新工具上真正生效

`fetch_url` 是第一个**真的慢**的工具（此前只有 `delay_ms` 这个假的慢）。步骤级 `AbortSignal`（U-2 已做）要在它身上验证一次真实生效，且中断后合成的 result 必须守住配对不变量。

#### 批 3 验收：`verify:progress`（新增）

| 段 | 判据 |
|---|---|
| A | 长任务途中 `ToolProgress` 事件真的发出、Guard 真的消费；**长任务不被误杀** |
| B | 无进展形态：构造「同一工具同一输入连续三次」，断言 Guard 触发并具名终止 |
| C | 真实慢工具执行中 cancel：transcript 中不存在无 result 的 tool_use |
| D | `WAITING_FOR_INTERACTION` 可达；完成信号之后**确实重新做了 Observation**（断言观察调用发生，而不只是状态流转） |
| E | 运行期 interject：插话进入下一轮 ContextFrame |

#### S12　审批策略落地（决 3）

#### S13　跨场景 smoke（决 7 的判据）

**两个来自不同场景、互不相干的真实任务，用同一套工具都跑通。**

| 任务 | 场景 | 压什么 |
|---|---|---|
| A | **办公**：读一批文档内容 → 汇总 → 产出结构化文档 ＋ 追加日志 | `read_file` / `search` / `write_file` / Artifact |
| B | **代码**：分析本仓某个模块 → 找出某类形状 → 产出说明文档 | `search` / `read_file` / `stat` / `edit_file` |

**【定】判据是「跑通」，不是「产物质量」**——质量判定属于评测，已按决 4 推后。跑通的含义是：具名 Terminal 退出、配对不变量守住、无未配对 tool_use、产物落盘、Artifact 级检查通过。

> **这是本阶段唯一能真正证伪「通用」的判据。** 边界 grep 只能防止显式依赖，防不了「工具的形状是照着任务 A 长的」——只有任务 B 用同一套工具跑通，才说明形状是通用的。

## 8. 风险

| 风险 | 表现 | 处置 |
|---|---|---|
| **工具悄悄长出 Case 形状** | `fetch_url` 里混进正文提取、`search` 里混进特定文件格式假设 | 第 6b 条 grep 拦不住语义层面的过拟合，**只有 S13 的跨场景 smoke 能** |
| **大结果外置成为新的静默截断** | 外置了但模型取不回来，等于内容消失 | 批 2 验收 A 段强制验「可经 retrieval 取回完整内容」 |
| **Artifact 级检查器滑向业务规则** | 从「ZIP 能否解开」滑到「清单里要有合计」 | 不得绕过清单第 8 条；回归评测那次误判是现成的反面教材 |
| **闸门排在闸门后面** | 新增的校验被已有的 fail-fast 遮住，永远不生效 | §0.3 的 U-6 就是活例。**新增校验必须有一条能单独触发它的判据** |
| **验收脚本膨胀但判别力下降** | 三条新脚本全绿，实际什么都没测 | 每条新判据都要做**判别力实测**（改坏实现必须翻红），并写进脚本抬头 |
| **八个工具不够，中途加工具** | 加工具时按当下任务的形状加 | 加任何工具都要过三场景标准 ＋ 文件头声明，且要重新读一次 `fixedOverheadTokens` 基线 |
