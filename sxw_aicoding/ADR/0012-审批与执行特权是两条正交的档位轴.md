# ADR-0012：审批与执行特权是两条正交的档位轴

- 日期：2026-09-01
- 状态：已采纳
- 相关：[ADR-0008](0008-ask-user-与-request-handoff-是两个洞.md)（两条通道的失败语义相反）、
  [ADR-0011](0011-通过外部-MCP-接入浏览器能力.md)（MCP 工具没有沙箱）、
  阶段 3 决 3（有限自动放行）、阶段 3.5 决 1（两道闸门）、
  存量清单 S3.5-6（无人值守 EXECUTE 全灭）、S4-6（`approvalMode` 硬编码串）

## 起因：一次实测，不是路线图

真实端点 ＋ Web 入口跑「把 B 站 opus 页的图片下载下来打包成 images.zip」
（Run `run_75f0d6afafa6`）。产物完全正确，而人被要求点了十几次确认。

逐条回源，问的是谁：

| 谁 | 为什么问 | 那次问了几遍 |
|---|---|---|
| `run_shell` | `autoGrantVerdict` 第一句：`EXECUTE 类操作不在自动放行范围内`。而 `analyzeCommand` 判 EXECUTE 的规则是「有任一 shell 元字符」，那次 **10 条命令每条都含元字符** | ≈10 |
| MCP 浏览器工具 | `tierOf` 默认 `execute` → 逐次审批 | 每次导航/点击 1 次 |
| workspace 内的普通写 | 决 3 已经自动放行 | 0 |

**而那次跑的是 Web 入口，那一侧一个逃生口都没有。** CLI 有 `--yes-all`
（`main.ts` 的第一个分支），Web 的 `RunHost` 把 `autoGrantVerdict` 写死注入，
`workagent-service/src/main.ts` 的参数表里根本没有这个开关。
浏览器任务又必须用 `npm run ui`（MCP 进程绑会话，`npm run dev` 一结束浏览器就关）。

**所以用户被逼到了唯一没有逃生口的那个入口上。**

这件事仓里登记过：S3.5-6 写着「默认档位下无人值守 EXECUTE 全灭…**等复跑数据说话**」。
这次就是那个数据。

## 决定

### 一、两条轴，两个参数，不做一键预设

```
--approval confirm|default|auto     审批：要不要停下来问人
--sandbox  on|off                   执行：跑起来能碰到什么
```

**【定】不做 `--yolo`。** codex 有那个预设，本仓不做 —— 阶段 3.5 决 1 那张表
（`command-analysis` 判「要不要问人」／`sandbox` 判「能碰到什么」，
只有后者是边界）的全部意义就是这两件事不能合并。一个单词同时拆两道闸门，
下一次读它的人不会想起来它拆了哪两道。想要完全权限就打两个参数，
**那个决定应该有两个名字**。

`--confirm` / `--yes-all` 一并删除，`assertKnownArgs` 里留迁移提示 ——
照 `--yes` 那条的写法（本仓已经因为别名分叉栽过两次：`STAGE1_ACTIVE_*`，
以及那个「从来没被解析过、能用只因为默认档位本来就是它」的 `--yes`）。

### 二、拆哪几条：七条限制里只拆三条

"拆沙箱"这三个字底下捆着七件彼此独立的事。逐条决定：

| # | 限制 | 住在哪 | 决定 |
|---|---|---|---|
| 1 | `run_shell` 写不出 workspace ＋ `$TMPDIR` | `sandbox.ts` `deny file-write*` | **拆** |
| 2 | `run_shell` 默认禁网 | 同上 `deny network*` | **拆** |
| 3 | 子进程 env 白名单 | `run-shell.ts` `sanitizedEnv` | **不拆** |
| 4 | 读不到 `.env` / `.ssh` / `.aws` | `sandbox.ts` `toSandboxDenyRules()` | **不拆** |
| 5 | workspace 外的写被 policy `DENY` | `policy.ts` | **拆**（改为走审批） |
| 6 | `read_file` / `search` 读黑名单 | `fs/read-guard.ts` | **不拆** |
| 7 | `fetch_url` 拒私网 | `net/url-guard.ts` | **不拆** |

**第 5 条的真实理由（二次复核更正过一次，值得连错一起记）**

这里第一版写的是「第 5 条必须一起拆，否则第 1 条白拆 —— `policy.ts` 在工具执行
之前就 DENY 了」。**回源之后不成立**：`OUTSIDE_WORKSPACE` 这个 riskFact 只由
`effect-resolver.ts` 为**路径域**的工具产出，而 `ShellEffectResolver` 从不产出它
（它只给 `MUTATES_EXTERNAL_STATE` / `IRREVERSIBLE` / `DATA_LEAVES_HOST`）——
**`run_shell` 从来没有被那条 policy 拦过**，它一直只被沙箱拦。

真实的消费者是另外四个**路径域的写工具**（`write_file` / `edit_file` /
`append_log` / `slow_write`）：不拆第 5 条，它们的越界写连审批面都到不了。

这条错误因果的形态与 M4 那次一模一样（「清 effect 噪声能减少审批」，
回源后发现收益为零）：**一个听起来很顺的因果，导出的处方做完之后没有人会回头量。**
这次是判据把它量出来的 —— 见下面第三节。

**第 3/4/6 条不拆的理由是同一条：它们对任何一个真实任务零收益。**
下载图片、打包 zip，一次都用不上读 `.env`。拆了只增加凭证泄漏面 ——
而第 3 条是有实测的（`printenv dashscope_api_key` → `sk-ws-…`）。

**第 7 条明确不动。** ADR-0011 的整个处置就是「不给 `fetch_url` 加私网/Cookie，
改走 MCP」，那份 ADR 还专门写了「两个工具对同一件事给出相反答案是刻意的，
否则下一个人会来统一其中一个」。auto 模式去拆它，就是那个"下一个人"。

### 三、UNRESTRICTED 不是「不套沙箱」，是一份只剩凭证读禁的窄 profile

> **这一条是被自己的判据逼出来的，写在这里因为它比它修掉的问题更值得记。**

第一版实现的是「档位为 UNRESTRICTED 就直接 `spawn("/bin/bash")`」，
理由写得也很像那么回事：

> 留着 `sandbox-exec`、给一份 allow-all 的 profile，会让它在 `ps` 里、
> 在读代码的人眼里都还是"跑在沙箱里"。一个名义上存在、实际什么都不拦的沙箱，
> 比明摆着没有沙箱危险得多。

那段话本身没错 —— **但它论证的是 allow-all profile，而上面那张表里
凭证读禁是「不拆」的。** 直接 spawn 的后果是把它一起拆了：
`verify:shell` B10 一跑就红，`cat .env.local` 当场读到 SECRET。

也就是说那个看起来"更诚实"的写法，恰恰让实现与**同一批里我自己刚写下的
范围表**不符。本仓管这叫「声明与实现不符」，而这次两边都是我写的。

现在的 UNRESTRICTED profile 真的在拦一件事，所以它不是装饰：

```
拆掉：(deny file-write*)   写边界
      (deny network*)      网络
保留：(deny file-read* …)  .env / .ssh / .aws 那批
```

连带的一条：**`isSandboxAvailable()` 那道闸门两档都要过**。UNRESTRICTED 仍然
要靠 seatbelt 挡住凭证读取，所以「没有沙箱就拒绝执行」一个字没改 ——
少了它，UNRESTRICTED 会在非 darwin 上悄悄退化成"连凭证读禁也没有"。

### 四、两条轴的生命周期不同，这不是设计偏好，是代码事实

| | 启动参数 | 提交任务时选 | 运行中切 | 「本次 Run 不再问」 |
|---|---|---|---|---|
| 审批 | ✅ | ✅ | ✅ | ✅ |
| 执行特权 | ✅ | ✅ | ❌ 只对下一个 Run 生效 | 不适用 |

**审批档位**住在 `ApprovalDecider` 这个注入点上，不进 RunSpec，不参与任何恢复
语义 —— 每一次决定的真实来源由 `ApprovalDecided.decidedBy` 逐条记着，
那比一个 Run 级的概括字段准确（人可以跑到一半才切）。
技术前提是**档位传的是读函数不是值**：decider 在 `compose()` 那一刻建出来、
之后整个 Run 都用同一个闭包，传值进来就等于把档位钉死在那一刻。

**执行特权不行。** `commonTools` 是模块级常量数组，工具没有构造期依赖注入口；
`run_shell` 拿得到的只有执行期的 `ctx`。而 `ToolExecutionContext.timezone`
正好是现成的先例，它的注释写着「随 AgentSpec **冻结**…Replay 要求时区随 Run
冻结而不是随重放机器变」。执行特权是同一个形状，**而且理由更硬**：
它决定的是「那些副作用当时有没有边界」。

于是 §18.3 多了**第三维**闸门（`assertResumeExecutionPrivilegeMatches`），
与端点、workspace 两道并排。两个方向都很难看：

- 冻结 UNRESTRICTED → 用 SANDBOXED 接：模型接着一个"没有沙箱"的计划往下写，
  命令突然开始被内核拒，而拒绝理由指向一条它读不到的规则；
- 冻结 SANDBOXED → 用 UNRESTRICTED 接：一条**在有沙箱的前提下被批准过**的
  计划，后半段跑在没有沙箱的机器上 —— 人当时批准的不是这件事。

它同时是 `ShellEffectResolver` 那个构造期档位的正确性前提：resolver 拿的是
当前进程装配的档位、policy 与工具拿的是冻结的那一档，闸门保证两者必然相等。

**旧库里没有这个字段时按 `SANDBOXED` 读，而那不是猜测**：`UNRESTRICTED`
这一档之前在本仓不存在，任何一条没有这个字段的 transcript 当时必然跑在沙箱里。
所以它与 `assertResumeWorkspaceMatches` 那个 `UNKNOWN_LEGACY` 不同类
（那一条是"我无法核对"，这一条是"我知道当时是什么"）。

### 五、必须同时付的那笔账：谁批的，事后要能区分

在此之前 `--yes-all` 的无条件批准与一个人亲手敲 `y`，在 `ApprovalDecided`
事件上**一个字都不差**（两者都是不带 reason 的 `{approved:true}`）。
于是一条自动跑完的 Run 与一条被逐步审视过的 Run，在 Trace、事件流、界面上
事后完全不可区分 —— 正是本仓反复在修的那个形态（`dataMovement` 那次、
`replacedBytes` 那次都是同一条）。

`ApprovalDecision.decidedBy` / `ApprovalDecided.decidedBy`：

| 值 | 含义 |
|---|---|
| `HUMAN` | 人当场做的决定（终端敲 y/n、界面上点了按钮） |
| `AUTO` | 档位性的无条件放行（AUTO 档、或人对本次 Run 说过「不再问」） |
| `AUTO_GRANT` | 有限自动放行（`autoGrantVerdict`） |
| `UNDECLARED` | 决策者没有声明来源（脚本化 decider 多半如此）。**不猜** |

**【定】Runtime 不给它兜底成 `HUMAN`。** 没声明就记 `UNDECLARED`，那是一句真话；
记 `HUMAN` 是一句假话，而假话在事实表里比空白贵得多。

「本次 Run 不再问」的第一次仍记 `HUMAN`（人确实看了这一条），之后记 `AUTO`。
把两者都记成 `HUMAN`，等于替他宣称"我逐条批准过全部"—— 而后面那些他没看过。

### 六、AUTO 档下另外两条通道的处置**相反**

这是 ADR-0008 的直接后果：

| | 语义 | AUTO 档下 |
|---|---|---|
| `ask_user` | 「你来定」，没人回答**不是**失败 | 立刻返回 NO_ANSWER，不停下来 |
| `request_handoff` | 「你去做」，没人接管**就是**失败 | **照样等人** |

自动化的是"要不要问你"，不是"要不要有人去做那件事"。
具体到用户场景：AUTO 档跑浏览器任务时模型请你去登录一下，那一停是有价值的
—— 人就在浏览器前面，而 Atlas 登不了那个录。

把它们做成同一种处置，正是 ADR-0008 那张对照表存在的理由。

### 七、UNRESTRICTED 档下「这条命令没联网」是一句说不出口的话

`allow_network` 在 SANDBOXED 档下是一个**被内核强制**的开关：没传，
`(deny network*)` 就在那儿，所以「没传 ＝ 没联网」是事实。

UNRESTRICTED 档下没有那条 deny —— 进程无条件有网。此时若照旧只按
`allow_network` 记 `DATA_LEAVES_HOST`，一条没传这个参数、却 `curl` 了
半个互联网的命令，在 `riskFacts` 上会与一条纯本地命令**完全一样**。

处置是**如实记「无法排除」**，不是不记、也不是假装没联网
（先例：`effect-resolver.ts` 对解析不了的 URL 写 `"(无法解析)"`）。
代价是这一档下 `run_shell` 全部带 `DATA_LEAVES_HOST` —— 那正是实情。
`dataMovement.scope` 的两句措辞必须能被区分：一句是模型声明了要联网，
另一句是没人知道它联没联网。

### 八、description 是模块级常量，档位是随 Run 冻结的值

`run_shell` 的 description 里写着四条沙箱规则，它们在 UNRESTRICTED 档下
**全部不成立**。而静态文本没有办法只在某一档出现。

两条路：让工具面按档位产两份 snapshot（要动 `commonTools` 那个常量数组，
且工具 version 得跟着档位变，牵动 §18.2 的分支判定前提），或者在 description
里留一个指针、由**受信事实**去更正它。

选后者。代价如实记：那句话从"我保证"降级成"默认如此，以系统事实为准"。
不留这个指针的后果是 M1 原样重演 —— 模型照着一句已经不成立的承诺规划命令，
而**模型是那句话唯一的读者**。

受信事实（`compile.ts` 的 `UNRESTRICTED_FACT`）排在时间事实**之前**：
时间事实每段都变、是前缀缓存的第一个断点，而这一条在一个 Run 内恒定。

## 代价，一条都不许假装没有

① **AUTO ＋ UNRESTRICTED 时没有任何闸门。** 模型生成的 `rm -rf` 会真的作用在
宿主账号下 —— codex 的 `danger-full-access` 通常跑在容器里，本仓跑在你的 Mac 上。
处置是**响一声**（`fullAccessWarning()`，CLI 红字横幅 ＋ 界面常驻徽章），
且档位**不进任何持久配置**（不写 `workspaces.json`、不做"记住我的选择"）——
重启一律回到启动参数那一档。

② **AUTO 档下 `ask_user` 的犹豫对模型是无声的。** 它会自己定，而人事后只能
从一条 NO_ANSWER 的 tool_result 看出来。两个入口都在这一刻打印一行，
但那一行不进事件流。

③ **UNRESTRICTED 下交付物登记仍限 workspace 内。** `artifact-checks` 的
第二层检查读的是 `workspaceRoot` 下那一份，放开它是另一件事。
所以命令可以写到任何地方，但只有落在 workspace 内的才进得了交付集合。

④ **非 darwin 上 UNRESTRICTED 仍然没有 `run_shell`。** 工具面那道闸门
（`isSandboxAvailable()` 决定进不进 `commonTools`）是模块级的，看不到档位。
这在实践中不改变任何事（`run_shell` 本来就只在 darwin 上有），但它意味着
"UNRESTRICTED 让 run_shell 到处能跑"这句话是不成立的。

⑤ **切 workspace 会把界面上拨过的审批档位弹回启动值。** 那是刻意的：
新 workspace 是一个新的执行环境，把上一个目录里的免打扰承接过来，
等于替用户做了一个他没做过的决定。

`verify:all` **198 → 221 条**（v1 交付 +10，自查 +4，二次评审处置 +9）。新增的每一条都做过注入实测（改坏实现 → 必须翻红 → 改回）：

| `verify:ui` D4b | AUTO 下 `ask_user` 不停 ＋ `request_handoff` **仍然**等人（配对） | 两个方向各注入一次 → 各翻红 |

### 二次复核补的四条（2026-09-01 同日）

**这一批最值钱的产出不是任何一条判据，是它们各自抓到的东西：**

| 发现 | 形态 |
|---|---|
| policy 放行了越界写，**四个写工具自己那道 `isInsideWorkspace` 没跟着改** | 探针原始输出：`policy(UNRESTRICTED)=REQUIRE_APPROVAL` → 工具 `TOOL_PATH_ESCAPE` → 文件没写出来。**停下来问了人，人批准了，然后照样失败** —— 比原来的 DENY 更糟 |
| 我给第 5 条写的因果**本身是错的** | 见上面第二节的更正。与 M4「清 effect 噪声能减少审批」同形态 |
| CLI 在「无人应答」时记 `decidedBy: "HUMAN"` | **我自己写的【定】禁止的那句假话**（没有任何人做过这个决定），而同一批里 Web 那侧写对了。一个新字段最容易错的地方是它的**缺省分支** |
| D4b 第一版是**装饰判据** | 夹具给 `ask_user` 传了数组，而它的 `options` 是换行分隔的字符串 → `executeAskUser` 在到达 `QuestionChannel` **之前**就报错返回。摘掉 AUTO 那一支做注入，判据照样绿 —— 与 `read_blob.line_offset` 那次一字不差：**判据打在下游，跨不过出事的那一跳** |

**【定】四个写工具的边界判定收敛成 `fs-common.ts` 的 `writeBoundaryRefusal()` 一份。**
各写一遍的后果不是重复，是**分叉**：加了 `executionPrivilege` 这一维之后，
四处里漏改任何一处，就会出现「同一个越界写，`write_file` 放行而 `edit_file` 拒绝」——
而两边都不会报错，只是行为不同。

**【定】B9 与 D4/D5 都必须是成对判据。** 只验「没弹卡片」的话，一个
"Run 根本没跑到那一步"的实现照样全绿 —— 那正是 D3 上一版栽的跤
（空数组的 `every()` 恒真）。只验 B2 的话，一个"`--sandbox off` 根本没接线"的
实现照样全绿 —— 那是 `sandbox.ts` 文件头那条教训的镜像
（一个拒绝一切的沙箱与一个正确的沙箱，在「越界写被拦」那条判据下不可区分）。

**【定】B9 的探针写在临时目录并清理，不写 `$HOME`。** B2 那条的教训是实测出来的：
故障注入摘掉 `deny file-write*` 的那一次真的在 `$HOME` 建出了文件，之后每次
`existsSync` 都为真，判据被**永久毒化**。而 B9 是**故意**要让写成功的 ——
写 `$HOME` 就不是"万一"，是每次都留痕。

### 这一轮最值得记的，是三次「判据落在守卫重叠区」

修的过程中有三条新判据第一次写出来**没有判别力**，全靠注入实测发现：

| | 症状 |
|---|---|
| `verify:ui` P2-3 那条 | 单摘 kind 校验**不红**（被失败回滚兜住），单摘回滚也**不红**（被 kind 校验挡住），两道同摘才红。**两道防的是不同的事**（伪造 kind ／ 两步之间被 cancel），只是在「最终有没有留下提升」这一个可观察量上重合 —— 已在判据里如实写明它测的是合取 |
| `verify:shell` P2-4 那条 | 三个用例全被 `parseApprovalMode` 的**枚举校验**先接走，缺值检查从没被触发。真正只有它能挡的形态是「参数是 argv 最后一项」（那时 `get()` 返回 `undefined`，枚举校验把它当成"没传"） |
| `verify:pairing` 归责那条 | 夹具用了 `append_log`（`requiredForSuccess: false`），拒绝它根本不产生未完成的必需项，**两侧都判 SUCCESS** —— 又一次「夹具让正确值与错误值恰好相等」 |

**M4 那条教训（一条不准的 kills 比没有更糟）在同一天出现了三次。**
结论不是"要记住"，是**每加一条判据就必须做一次注入实测** —— 三次我都是跑完才发现的。
