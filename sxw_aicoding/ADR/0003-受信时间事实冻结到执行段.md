# ADR-0003：受信时间事实冻结到「执行段」，`now` 工具只作补充

> 状态：ACCEPTED
> 日期：2026-08-26
> 对应决策点：存量清单 U-9（与 A1 的时间事实耦合）；阶段 2 实施方案「决 3」
> 影响的架构条款：V05 §11.8【定·实测】（缓存可估价规则）、§11.2（ContextItem）、§18.4（Resume）
> 证据来源：`context/compile.ts:189-193` 与 `compose.ts:227-229` 两条历史实测记录；`verify:budget` C–E 段

## Problem

注入给模型的「当前时间」事实**每轮用 `deps.now` 重渲染**，且含时分。
端点声明 `cacheMatching = STRICT_PREFIX`，而这条事实是 `messages[0]` 的首个 text 块 ——
前缀从这里就分叉了，历史永远缓存不到。

更麻烦的是**分钟粒度让失效不确定**：跑得快就不失效，跨了分钟边界就在某个说不准的
轮次失效一次。对 Replay 与成本估算来说，这比确定性失效更难处理。

**为什么现在必须决**：阶段 2 要接 `cache_control`（U-9），而存量清单标了
**【定】不要在没定 U-9 之前单独动 `renderTimeFact` 的粒度** —— 两者是同一个取舍的两面。

## Hypothesis

做决策时的认知状态：

- 已知这条事实**不能删**。`compose.ts:227-229` 的【定】记着：光靠 prompt 约束，
  模型只会从「编一个日期」换成「回避日期」，**两次实跑各出现过一种**；
- 已知 `now` 工具这个方案**已经被否决过一次**。`compile.ts:189-193` 记着理由：
  「工具要模型记得调。**它上次就没调 —— 直接编了一个。**」
- **当时低估**的一件事：把时间冻结到 Run 级，在跨进程 resume 成为常态之后
  会产生一个新问题（见下）。

## Alternatives

| 方案 | 优点 | 代价 | 何时会后悔 |
|---|---|---|---|
| A. 冻结到 **Run** 级 | 前缀在整个 Run 内稳定，缓存收益最大 | 周一起的 Run 周三 resume 时会把**周一的日期**写进产物。而那是被 system prompt 背书的错误（prompt 明写「日期一律以系统事实为准」）——**比编造更糟** | 立刻。跨进程 resume 是阶段 2 的招牌能力，「长时运行」从边角变成常态 |
| **B. 冻结到「执行段」级** | 段内前缀稳定（缓存收益保住）；段间如实反映日期（跨天 resume 不写错） | 段内最多过时「本段已跑的时长」。一个跑了两小时的段，末尾看到的仍是两小时前的时刻 | 出现单段就跑很久、且需要分钟级精度的任务 |
| C. 降到「日」粒度 | 前缀在一天内稳定 | 需要精确到分钟的任务失去支持；跨零点仍有一次不确定失效 | 第一个要写时间戳的任务 |
| D. 保持每轮更新 | 时间最准 | 历史不可缓存；失效时机不确定 | 上下文变大、缓存收益变得重要时 |

## Decision

**取 B：冻结到执行段级。** `start()` 与每次 `resume()` 各重新冻结一次。

配套两件事，**顺序不能颠倒**：

1. **系统提示词改写**（补充说明，不是替换）。
   「不得自行推断日期」这句强约束**原样保留** —— 它是 A1 修复的核心。
   加的是：「那条事实是本次执行开始时的时刻；需要精确到分钟时调用 `now` 工具」。
   **不写「这个时间可能不准」** —— 那是往「回避日期」那侧推的措辞，
   而回避是两种失败模式里更难在产物上发现的那一种。
2. **`now` 工具是补充，不是主机制。** 注入仍然是零轮次、零 token 往返、
   **不可能被跳过**的那条路径。`now` 只读、幂等（§18.2 分支一），
   所以它不会扰动阶段 2 要统计的分支分布 —— 这是它能破「阶段 2 不加工具」这个例的前提。

**【定】不得反过来**：删掉注入的事实、改由模型自己调 `now`。
那正是 `compile.ts:189-193` 记录的、已经被实测否决过的方案。

## Consequences

### 接受的代价

- 单段内时间最多过时「本段已跑的时长」。当前任务的量级是几十秒到几分钟，可忽略；
  长时段任务需要精确时刻时，靠 `now` 工具 —— 而模型可能不调它（那条实测记录仍然有效）。
- 多了一个工具，`fixedOverheadTokens` 从 3×180 增到 4×180。
  这个变化当场打翻了 `verify:compact` 的夹具 —— 顺带把那个夹具改成只注册它自己
  需要的那一个工具，不再随 case 包增删工具而漂移。

### 适用条件

任务的时间精度要求在「日期 ＋ 执行段起始时刻」这个粒度上够用。

### 重新评估的触发条件

1. 出现单段运行超过一小时、且产物需要分钟级时间戳的任务；
2. `eval:suite` 的 grader 报出时间相关的检查失败（「未出现错误年份」这一条已经在跑）；
3. 观测到模型确实会主动调 `now` —— 那会推翻 `compile.ts:189-193` 的历史结论，
   届时可以重新考虑把注入的粒度降到「日」。

## Eval Evidence

- `verify:budget` D/E 段：`compileFrame` 收的是段级时刻，且每段（含 resume）重新冻结；
- `verify:budget` 的时间事实段**同时断言两种失败模式**：既不能写错日期，也不能
  「回避日期」（该写的地方是空的）。只测前者会漏掉 `compose.ts:227-229`
  记录的第二种实跑失败形态；
- `eval:suite` 的 grader 有一条「未出现错误年份」的硬判据，来自复评报告 P1
  （Agent 曾把盘点时间写成 2025 年）。

## Interview Narrative

模型不知道今天几号 —— 它只有训练时的先验，没有任何事实覆写它。不给它，它要么编一个，
要么绕开不写；这两种我们都实测遇到过。所以我们在上下文里注入一条受信时间事实。

问题出在这条事实每轮都重新渲染。端点的缓存是严格前缀匹配，而这条事实排在最前面 ——
时间一变，整段历史的缓存就作废了。更难受的是它含时分：跑得快就不失效，
跨了分钟边界就在某个说不准的轮次失效一次，成本估不准，重放也对不上。

直觉的解法是把时间冻结在 Run 启动那一刻。但阶段 2 刚做完的招牌能力恰恰是
「今晚关机、明早接上」—— 冻在 Run 级，周一起的任务周三恢复时会把周一的日期写进交接清单，
而且那个错误是被系统提示词背书的，比模型自己编还糟。

所以粒度落在「执行段」：每次启动或恢复重新冻一次。段内稳定，缓存收益保住；
段间如实，跨天恢复写的是恢复当天。至于「段内跑久了会过时」——
补了一个只读的 `now` 工具兜底，但明确写清它是补充：主机制仍然是注入，
因为工具要模型记得调，而它上次就没调。
