# ADR-0009：阶段 4 的白盒界面不引入前端框架、打包器与 Electron

> 状态：ACCEPTED
> 日期：2026-08-30
> 对应决策点：阶段 4 决 2
> 影响的架构条款：V05 §5（Layer 1）、§27.1（进程与部署模型）、§27.2（目录）、§27.4（工程基线 D-25）
> 证据来源：`verify:ui` A / D / E 段；边界 grep 第 8 / 10 条的判别力实测

## Problem

阶段 4 要交付 GUI（Roadmap §6：「桌面产品化 ＋ Trace / Eval Inspector，**GUI 在这里**」）。
§27.1 的进程模型里写的是「Process A：Desktop Renderer / React UI」。

于是开工第一件事是选型：React ＋ Vite ＋ Electron，还是别的什么。

**它必须现在决**，因为选型会决定后面所有代码的形状，而且它一旦引入就很难退回去 ——
`turndown` 那 8.6M 传递依赖是阶段 3.5 花了一个 ADR 才说服自己接受的，
而一个前端工具链是它的两个数量级。

## Hypothesis

做决策时的认知状态：

1. 我**不知道**这个界面最终要长什么样。阶段 4 之前没有任何 UI 需求被写下来过，
   §5.1 那一段列的是「职责」不是「形态」。
2. 我**知道**这个界面的第一位读者是我自己，用途是「看清楚 Harness 里发生了什么」。
3. 我**不确定**手写 DOM 能撑到多复杂。这一条到今天仍然不确定 —— 见「重新评估的触发条件」。

## Alternatives

| 方案 | 优点 | 代价 | 何时会后悔 |
|---|---|---|---|
| **A. React ＋ Vite ＋ Electron**（§27.1 的原文） | 组件复用、热更新、生态；原生窗口 | 运行期依赖从 3 个变成几百个；引入构建步骤；**「UI 有没有偷读 Runtime」这条边界要靠打包器配置来守** | 当界面复杂到手写 DOM 明显吃力时 |
| **B. 原生 JS ＋ `node:http` 静态资源**（选中） | 零新增依赖；无构建步骤；**边界物理成立**；系统浏览器已经在那儿了 | 没有热更新、没有组件复用、CSS 与 DOM 手写；状态管理是一个全局对象 ＋ 几个 render 函数 | 同上 |
| C. 只做一个 JSON dump 端点，用别的工具看 | 最省事 | 白盒界面的价值在**把两条轨道合并后按时间线摆出来**，而那正是要写的那部分 | 立刻 |

## Decision

**取 B：原生 JS ＋ `node:http`，运行期依赖仍是 3 个，一个不加。**

三条理由，按重要性排：

### 1. 本阶段的研究问题是投影完整性，不是前端选型

阶段 4 要回答的是「执行事实能不能只靠既有的事件流与注入点投影成界面」。
React 一个判据都答不了，而它会把第一周花在构建配置上。

这与 §2.3「当前明确不做」是同一条纪律：**没有被研究问题逼出来的东西不进主干。**

### 2. 边界因此是**物理**的，不是君子协定

§5.5 保留了一条约束：

> UI 通过 RunEvent 流驱动，**不直接读 Runtime 内部状态** —— 这使得将来接入任何 UI 协议都只是新增一个投影器。

在 B 方案下这条约束不需要任何人遵守：`apps/workagent-ui/public/` 里是浏览器直接跑的
静态资源，它**没有办法** import 一个 TS 模块。边界 grep 第 8 条是这件事的机械判据。

> **【定】第 8 条不是恒真式。** 它成立靠的是「UI 没有构建步骤」这个事实，
> 而这个事实随时会被一次「给界面加个打包器」的改动破坏 —— 那一刻这条 grep
> 是唯一会说话的东西。恒真式是「无论代码怎么改都为真」；这条不是：
> 往被扫的目录里放一个 import Runtime 的文件，它立刻红（`verify:ui` A 段实测过）。
>
> ⚠️ **这句话在收口批之前是过度声明。** 原文写的是「加了构建步骤再 import 一个
> Runtime 类型，它立刻红」，而当时那条 grep **只扫 `public/`** ——
> 引入打包器之后源码会在 `src/`（不扫），产物落进 `public/` 时包名早被
> 打包器消解掉了。也就是说注入实测证明的是「往 public 放文件会红」，
> **不是**这句话声称的那件事（评审 codex 5.2 指出）。
> 收口批把扫描范围放宽到整个 `apps/workagent-ui/`，并用**行级**豁免
> 只放行本包自己的 `name` 声明 —— 现在 `src/` 里的 import 与 `package.json`
> 里新增的前端依赖都会被扫到，这句话才对得上。

### 3. Electron 是为了「打开一个本地页面」引入几百 MB

而系统浏览器已经在那儿了。§27.1【定】的原话是「只有出现 Runtime 崩溃隔离、
长任务独立守护、Browser/Shell 沙箱、多客户端共享或显著资源隔离需求后，
才评估拆分 Runtime 进程」—— 同一条纪律用在渲染层就是：
**只有出现「必须是原生窗口」的需求后才评估 Electron。**

目前没有。托盘图标、全局快捷键、文件拖放都还不是需求。

## Consequences

### 接受的代价

**明说，不要等第二个人来发现：**

- 没有热更新（改完刷新页面 —— 静态资源是每次请求现读的，至少不用重启服务）；
- 没有组件复用，重复的 DOM 构造靠一个 12 行的 `el()` helper 兜；
- CSS 手写，没有设计系统；
- 状态管理是一个全局 `S` 对象 ＋ 几个 `render*()` 函数，更新策略是**全量重取**；
- **没有原生窗口**：它是浏览器里的一个标签页，关掉标签页服务还在跑。

一条**没有**被计入代价的：安全。反而更好 —— 没有构建步骤就没有供应链面，
而 §22.6 要求的四条（随机端口 / 会话 Token / Origin / 禁止外部网页调用）
在一个 60 行的 `security.ts` 里就全落地了。

### 适用条件

1. **单人本地使用**。多客户端共享会立刻推翻它（那时要考虑真正的状态同步）；
2. **界面复杂度停留在「看」＋「按几个按钮」**。一旦要做拖拽编排、可视化编辑器、
   或者需要虚拟滚动才撑得住的长列表，手写 DOM 会开始吃力；
3. 与 §5.5 的 A-01（不引入外部 Agentic UI 协议）同源 —— 两者都是
   「不把 UI 语义提前冻结在一个尚未验证的抽象上」。

### 重新评估的触发条件

具体、可观测，任一条成立就重新评估：

- **`app.js` 超过 1500 行**，或出现第三处「同一块 DOM 在两个地方各构造一遍」；
- 需要**多客户端同时看同一个 Run**（那时全量重取的策略也要一起换）；
- 需要**原生能力**：托盘常驻、系统通知、文件拖放、全局快捷键；
- 出现**第二个界面消费者**（比如手机上看）—— 那时 `api-types.ts` 该升成
  §27.2 规划里的 `packages/application-api-contracts/`，现在不升是因为它只有一个消费者，
  而「类型都在但运行时从不执行」是本仓明令要避免的形态。

## Eval Evidence

`verify:ui`（**36 条判据全绿**（收口批 20 → 29，workspace 批 → 36））里与本决策直接相关的：

| 段 | 证据 |
|---|---|
| A | 往 `public/` 注入一行 `import … from "@workagent/harness-runtime"`，第 8 条**当场翻红并指出行号** —— 边界有判别力 |
| A | 往 `public/` 注入一行**内联 style 写法**，第 11 条当场翻红（收口批新增，见下） |
| A | 往 `public/` 注入 `node.innerHTML = modelText`，第 10 条当场翻红 |
| D | 三条「等人」通道走真实 HTTP 各跑一次，Run 跑到终态 —— 零依赖不妨碍功能完整 |
| E | §22.6 四道闸门全部生效（无/错 Token → 401；跨 Origin → 403；非 loopback Host → 403） |

**一次人工视觉核对**（不是判据，是证据）：给审批面板喂一条命令原文
`rm -rf /` ＋ `<img src=x onerror=alert(1)>`，界面把那段 HTML **原样当文本显示**。
这是第 10 条在真实渲染路径上的兑现 —— grep 证明代码里没有 `innerHTML`，
这一次证明**看起来也确实没有**。

## Interview Narrative

阶段 4 要给这个 Agent Harness 做一个白盒界面。架构文档里写的是 React ＋ Electron，
我没有照做 —— 因为这一阶段的研究问题是「执行事实能不能只靠既有的事件流投影成界面」，
而前端框架一个判据都答不了，却会把运行期依赖从 3 个变成几百个。

真正让我确信的是第二条理由：不引入构建步骤之后，「UI 不许读 Runtime 内部状态」
这条架构约束从一句需要人遵守的话，变成了一个**物理事实** ——
浏览器里的原生 JS 根本 import 不到 TS 模块。我为它写了一条 grep 并做了注入实测，
它能红。

代价我列在 ADR 里了：没有热更新、没有组件复用、DOM 手写。
以及四条重新评估的触发条件，其中第一条是「`app.js` 超过 1500 行」——
它现在 **1000 行左右**（收口批之后）。
