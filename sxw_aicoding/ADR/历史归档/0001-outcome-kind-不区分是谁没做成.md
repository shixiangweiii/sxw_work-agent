# ADR-0001：`outcome.kind` 不扩值域，只接上 `USER_REJECTED`

> 状态：ACCEPTED
> 日期：2026-08-26
> 对应决策点：存量清单 R-7 ＋ U-8（两条是同一个设计问题）；阶段 2 实施方案「决 2」
> 影响的架构条款：V05 §10.1（RunOutcome）、§10.4【定】（Run 完成判定）、不变量 12
> 证据来源：2026-08-24 真实端点实跑（R-7 的发现方式）；`verify:pairing` 的审批拒绝场景

## Problem

`RunOutcome.kind` 的值域里没有一个能表达「**模型明确声明做不了**」。

2026-08-24 的一次真实端点实跑：任务要求访问外网 URL、转 Markdown、下载图片、打 zip；
工具集里没有任何网络能力，模型正确地枚举了三个工具之后拒绝了任务，一个写工具都没调。
终端打出 `Terminal: COMPLETED / Outcome: SUCCESS`。

同一个值域问题的另一半是 U-8：`USER_REJECTED` 在类型里有值，`settle-outcome.ts`
**从不产出它** —— 用户拒绝一个必需的写操作时，Run 结算成 `COMPLETED_WITH_LIMITS`。

**为什么现在必须决**：阶段 2 要把 `summary` 之外的结算语义定下来，而 R-7 与 U-8
若分开修会得到两套互不兼容的语义（存量清单原文就是这么警告的）。

## Hypothesis

做决策时的认知状态：

- 已知 §10.4【定】把结算规则定为「只查事实表，不再调用模型」，且明确用三条理由
  拒绝了独立于模型判断的声明式验收机制；
- 已知 `USER_REJECTED` 与「模型拒绝」是两件事 —— 前者有明确的事实来源（审批环节的一次
  拒绝），后者只存在于模型说的话里；
- **当时不确定**的是：批内多个 action 混合失败时该判什么。这一条在实现时才想清楚。

## Alternatives

| 方案 | 优点 | 代价 | 何时会后悔 |
|---|---|---|---|
| **A. 不扩值域，只接 `USER_REJECTED`** | 结算路径保持「只查事实表」；`USER_REJECTED` 第一次有了事实来源；改动面小 | 「模型声称做不了」仍然结算成 `SUCCESS`，只能靠 `summary` 说清楚。无人值守场景下这个 SUCCESS 会误导自动化判断 | 出现定时任务 / 自动化触发，没有人在回路里看 summary 的那天 |
| **B. 新增 `MODEL_DECLINED`** | outcome 能直接表达「模型拒绝了」 | 结算必须判断模型的话语意图 —— 把「只查事实表」拖回「读模型说了什么」，**直接违反不变量 12**。而且「拒绝」与「做完了但没什么可说的」在自然语言里没有可靠边界 | 立刻。第一个把「我先看看目录」误判成拒绝的 Run 就会暴露它 |
| **C. 引入 Run 级必需操作清单** | 能真正回答「该做的做了没有」 | §10.4【定】已用三条理由拒绝过它：criterion 要在第一个 token 之前就知道「什么算做完」，而那个信息不存在 | 若将来 Case 的交付物有明确、静态、与用户输入无关的结构约束 —— 那时形态应是 Case Package 里的检查器，不是 RunSpec 的必填字段 |

## Decision

**取 A：不扩 `outcome.kind` 的值域，只把已有的 `USER_REJECTED` 接上事实来源。**

理由与证据：

1. **B 会破坏不变量 12。** 这不是风格偏好 —— §10.4 敢采用「模型不再请求工具即完成」
   这条极简规则，前提之一就是结算不读模型的话。一旦读了，Run 就在给自己打分。
2. **事实来源必须是「谁拒的」而不是「文案像不像拒绝」。** 实现上给
   `VerificationResult` 加了 `unmetCause`，在**事情发生的那一刻**写下
   （`USER_REJECTED` / `POLICY_DENIED` / `TOOL_FAILED` / `CANCELLED` / `NOT_OBSERVED`），
   而不是事后解析 result 正文 —— 解析文案的判据会在改一句提示语时静默失效。
3. **语义边界：仅当所有未达成的必需项都因用户拒绝时，才判 `USER_REJECTED`。**
   批内 3 个 action、1 个被用户拒、2 个因工具挂了没做成 —— 判 `USER_REJECTED`
   等于把责任栽给用户，而就算他全批准那个 Run 也做不成。混着的时候
   `COMPLETED_WITH_LIMITS` 才是诚实的：**它不声称自己知道该怪谁。**

## Consequences

### 接受的代价

- 「模型声称做不了」继续结算为 `SUCCESS`。缓解是 R-7 的另一半（2026-08-25 已接线）：
  `outcome.summary` 现在会带上模型最后那段话，CLI 会打出来。**人能看到，机器判不出。**
- 这个代价在**无人值守**场景下会变成真问题。届时正确的解法是 C 的受限形态
  （Case Package 里注册的检查器），不是 B。

### 适用条件

单人使用、人在回路里（§10.4 的第三条理由）。

### 重新评估的触发条件

具体且可观测，满足任一即重评：

1. 出现定时任务或自动化触发，Run 结束时**没有人**会看 summary；
2. `eval:suite` 显示「grader 判 FAIL 而 Runtime 自报 SUCCESS」的比例超过 10%
   —— 该指标现在就在报告里（「Runtime 自报与 grader 一致 N/k」这一行），不必新建观测；
3. 某个 Case 的交付物出现明确、静态、与用户输入无关的结构约束。

## Eval Evidence

- `verify:pairing` 的「审批拒绝：必需操作未完成」场景：期望值从
  `COMPLETED_WITH_LIMITS` 改为 `USER_REJECTED`。**这条断言的翻红是预期变更不是回归** ——
  A-1 修复当时判 `COMPLETED_WITH_LIMITS`，是因为那时 `USER_REJECTED` 有值域、无事实来源。
- `eval:suite` 的「Runtime 自报与 grader 一致」列：脚本化模式 3/3。
  这是本 ADR 第 2 条重评触发条件的常设观测点。

## Interview Narrative

Run 结束时要打一个标签说明「成没成」。有一类情况标不准：模型看了一圈工具，
说「这事我干不了」，然后结束 —— 循环正常终止、没有任何失败的验证，
按规则就是 SUCCESS。

诱人的解法是加一个 `MODEL_DECLINED`。但那要求结算逻辑去判断模型那段话是不是拒绝，
而我们整套完成判定的前提恰恰是「结算只查事实表、不读模型说了什么」——
一旦读了，就变成让被测对象给自己打分。

所以我们只接了有明确事实来源的那一半：用户在审批环节按了「否」，
这是一个发生过的、有时间戳的事实，可以放心地判 `USER_REJECTED`。
「模型自己说不行」维持 SUCCESS，但把它那段话原样放进 outcome 的 summary 里，
让人一眼看到。代价写在明处：等哪天没有人在回路里看这行字了，这个决定就得重来。
