# ADR-0005：PARKED lease 不做，人工接管走 WAITING_FOR_INTERACTION

> 状态：ACCEPTED
> 日期：2026-08-28
> 对应决策点：阶段 3 实施方案 决 5；连带 D-14 里 `CapabilityLeasePort` 的「不实现理由」
> 影响的架构条款：V05 §8.7（Ports）、§20（人工接管）、§18.6（等待语义）、§28.4
> 证据来源：`verify:progress` D / E / F 段；三场景工具清单的逐个复核

## Problem

`CapabilityLeasePort`（含 `park` / `unpark`）从阶段 1 起就有接口、零实现。
阶段 1 写下的不实现理由是一句**时间承诺**：

> 「lease 语义**要到 Browser Capability 才有真需求**（阶段 3）。」

阶段 3 到了。这句话到期了，必须兑现或撤销 —— 一个反复延期的「下阶段再说」，
和「未接线」是同一类东西：它让人以为问题已经被安排好了。

同时，**人工接管本身**是这一阶段真实需要的：办公场景要人去外部系统确认、
代码场景要人解冲突、聊天场景要人确认发送。三个场景都有。

所以真正要决的是：**人工接管必须走 PARKED lease 吗？**

## Hypothesis

做决策时的认知状态：

- 原设计把「人工接管」和「lease 的 PARKED 状态」绑在一起，是因为原计划的接管场景是
  **浏览器遇到验证码** —— 那时浏览器是一个独占资源，人接手期间不能让别的步骤动它，
  于是「停下来等人」自然被表达成「把 lease 停在 PARKED」；
- **当时没有分清的是**：绑定关系里有两个独立的需求。
  「等人」是一个，「等人期间别人不许碰这个资源」是另一个。
  第二个需要 lease，第一个不需要。

## Alternatives

| 方案 | 优点 | 代价 | 何时会后悔 |
|---|---|---|---|
| A. 实现完整 `CapabilityLeasePort`（含 PARKED），接管走它 | 与原设计一致；将来多 Run 并发时现成 | **盲写**：当前没有任何用例能检验 lease 设计得对不对（这正是 D-14 反复警告的）；三个场景里找不到一个通用工具需要独占 | 真正需要 lease 时发现当初的设计是按浏览器猜的，而浏览器最后没进来 |
| B. 只实现 `acquire` / `release`，不做 PARKED | 比 A 小 | 同样是盲写，而且做了一半的机制最容易被误以为可用 | 同 A |
| **C. 不做 lease；接管走 `WAITING_FOR_INTERACTION` ＋ 一个触发工具** | 只做真需求；`WAITING_FOR_INTERACTION` 本来就在 `RunStatus` 值域里且**从未被写入过**，正好补上 | 将来多 Run 并发时要重新设计并发保护 | 出现「两个 Run 抢同一个外部资源」的真实场景时 |

## Decision

**不做 PARKED lease，也不实现 `CapabilityLeasePort`；人工接管走
`request_handoff` ＋ `WAITING_FOR_INTERACTION`。**

理由必须引用证据：

1. **lease 的真需求来自多 Run 并发，不是来自浏览器。**
   当前是单进程、一 Run 一循环 —— §18.6【定】写得很干脆：
   「等待就是 await，进程死了所有等待一起死」。
   逐个复核阶段 3 的 12 个工具，**没有一个需要独占**：文件读写有 workspace 边界，
   `fetch_url` 是无状态 GET，`read_blob` 只读。
2. **接管不需要 lease 就能完整实现**，而且实现之后闭合了三个此前开着的洞：
   - `WAITING_FOR_INTERACTION` 从「全仓只出现在类型定义里」变成真的会被写入；
   - `resume` 对该状态**从没有任何处理分支**（会一路走到主循环直接调模型）
     变成能识别并重新发起接管；
   - 接管的等待此前**全额计入 active 墙钟**（`waitingSince` 只在审批事件对上设置）。
3. **U-8 与它是同一个洞。** 存量清单里的「`WAITING_FOR_USER` 指向一个不存在的
   ask-user 工具」，落点就是 `request_handoff`。

## Consequences

### 接受的代价

- **多 Run 并发时要重新设计并发保护。** 现在的保护是 `runs.status` ＋
  「一个 Run 一个循环」（不变量 4），跨进程靠库里的状态。它挡得住重复 resume，
  挡不住「两个 Run 同时写同一个文件」—— 而当前不存在这个场景。
- **`CapabilityLeasePort` 接口继续留着但零实现。** 这一条要说清楚：
  它现在的注释**不再是时间承诺**（「阶段 3 再说」），而是一个有理由的判定
  （「需求不在这里」）。两者的区别很实在：前者会自动延期，后者需要新证据才能推翻。
- **接管期间没有任何东西阻止 Agent 自己继续动那个资源** —— 因为循环阻塞在
  `await` 上，它压根没在跑。这在单进程下是充分的，多进程下不是。

### 适用条件

- 单进程、一 Run 一循环（§18.6【定】）；
- 工具集里没有需要独占的外部资源。

**两条任意一条不成立，这个决策就要重新评估。**

### 重新评估的触发条件

具体、可观测：

- 引入浏览器 Capability、`run_command`、或任何持有长生命周期外部句柄的工具；
- 出现「同时跑多个 Run」的需求（Layer 2 的调度，阶段 4）；
- 出现两个 Run 需要写同一个 workspace 的场景。

## Eval Evidence

- `verify:progress` **D 段**：接管期间去库里读状态，确实是 `WAITING_FOR_INTERACTION`；
  完成信号被如实标成「用户的声明，不是已核实的事实」并要求下一步先核实（§20.3）。
  判别力：不注入接管通道时返回 `TOOL_HANDOFF_NO_CHANNEL`，不静默挂起。
- `verify:progress` **E 段**：真 `kill -9` 打在 `InteractionRequested` 那一刻，
  盘上状态是 `WAITING_FOR_INTERACTION`；新进程 resume 认出它、走 §18.2 分支一
  重新发起接管，拿到应答后跑到终态。**这个崩溃窗口此前是未定义的。**
- `verify:progress` **F 段**：等 1200ms，`activeWallClockMs` 只记 5ms。

## Interview Narrative

阶段 1 给 lease 留了接口，理由是「等浏览器来了才有真需求」。阶段 3 到了，
我们逐个看了新加的 12 个工具，发现**没有一个需要独占**——
lease 的真需求其实来自多 Run 并发，而我们是单进程、一个 Run 一个循环。

但「人工接管」这件事三个场景都要：办公要人去外部系统确认、代码要人解冲突、
聊天要人确认发送。原设计把它和 lease 的 PARKED 状态绑在一起，
是因为原来的例子是浏览器验证码 —— 那里确实有个独占资源。拆开看，
「等人」和「等人期间别人别碰」是两个需求，我们只有前一个。

所以接管走了一条更轻的路：一个触发工具，加上 `WAITING_FOR_INTERACTION` 这个
从阶段 1 就在值域里、却从来没被写入过的状态。做完之后顺带闭合了三个洞，
其中一个是：崩在等人那一刻，resume 此前会直接去调模型 —— 人被请求做的那件事根本没做。
