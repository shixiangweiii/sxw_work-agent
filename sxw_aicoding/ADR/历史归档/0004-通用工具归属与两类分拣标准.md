# ADR-0004：通用工具归属与两类分拣标准

> 状态：ACCEPTED
> 日期：2026-08-28
> 对应决策点：阶段 3 实施方案 决 2（含修订 1）
> 影响的架构条款：V05 §27.2（目录）、§27.3（Composition Root）、§12.3（ToolDefinition）
> 证据来源：阶段 2 回归评测 §5 / P2-2；Roadmap §3「阶段 1 的射程被工具卡死」；`verify:tools` A / B 段

## Problem

阶段 3 要把 Agent 的射程从「只能看目录元数据」扩到「能读、能搜、能改、能取网页、能交付」。
新工具放哪，是一个**现在必须决**的问题：它阻塞第一行代码。

三个候选位置各有支持者：

- 放 `cases/web-archive/` —— 那是原计划里阶段 3 的 Case；
- 继续放 `cases/micro-cases/` —— 现有工具都在那儿；
- 新建一层。

选错的代价不对称。放进任何一个 Case 包，工具的形状就会**被那个任务反向定义**，
而这件事**从代码上看不出来**：没有任何编译错误、没有任何 grep 会响，
半年后只能靠人读代码去判断「这个参数当初是为谁加的」。

而阶段 3 的研究问题恰恰是：**能力面能不能不被任何一个任务反向定义。**
也就是说，工具归属不是工程口味问题，它就是研究问题本身的一部分。

## Hypothesis

做决策时的认知状态：

- 相信「三场景常用」（办公 / 代码 / 聊天）是一条够硬的标准 —— 一个工具如果三个
  互不相干的场景都要用，它多半不是照着某一个任务长的；
- **当时不知道的**：这条标准有一个盲区。评审给方案补出的三个必需工具
  （`read_blob`、`request_handoff`、以及接替 `write_note.delay_ms` 的可控慢工具）
  **一个都过不了三场景标准** —— 它们服务的是 Harness 机制，不是业务场景。
  这个盲区是二次反思时才发现的，见下面的「修订」。

## Alternatives

| 方案 | 优点 | 代价 | 何时会后悔 |
|---|---|---|---|
| A. 放进 `cases/web-archive/` | 零新增结构；与原计划一致 | 工具形状被网页归档定义，而这**看不出来**；决 1 从内部被绕过 | 第二个 Case 到来时发现工具全带着第一个 Case 的假设 |
| B. 继续放 `cases/micro-cases/` | 零新增结构；现有工具都在那儿 | 「Micro Case」这个名字会变成谎言 —— 一个装着 11 个通用工具的包不是 Micro Case；测量工具与能力工具混在一起，`delay_ms` 这种测量旋钮会长进通用工具的入参 | 想拆的时候已经分不清哪个是能力、哪个是测量 |
| C. 新建 `tools/common`，只用「三场景常用」一条标准 | 归属清晰；有机械判据（边界 grep） | **盲区**：机制工具过不了这一关，会被硬塞进来或塞回 `cases/`，两条路都破坏标准的纯度 | 加 `read_blob` 的那天 —— 它三场景一个都不常用，但没有它大结果外置就是信息阻断 |
| **D. 新建 `tools/common`，工具分两类，各有各的声明义务** | 覆盖 C 的盲区；两类的声明都可机械扫描 | 多一条规则要记；判断「它属于哪一类」偶尔要想一下 | 出现第三类工具时（目前想不出是什么） |

## Decision

**新建 `tools/`（`@workagent/tools-common`）；工具分两类，各有各的声明义务。**

| 类 | 判据 | 声明义务 |
|---|---|---|
| **场景工具** | 办公 / 代码 / 聊天三场景常用 | 文件头写出三场景各自用例，不适用要写明为什么 |
| **机制工具** | 服务某一条 Harness 机制 | 文件头**必须指出是哪一条机制、以及不做它会怎样** |

第三类（**测量工具**）留在 `cases/`：它服务的是**对机制的测量**，不是能力本身。

理由必须引用证据：

1. **射程问题是实测的，不是推测的。** Roadmap §3 记着「没有 `read_file`，射程是
   『目录元数据 → 模型加工 → 文本产物』」；回归评测 P2-2 记着模型**把文件路径传给了
   `list_dir`** —— 因为工具集里没有查看单个对象的能力。短板在「它能看到什么、能做什么」，
   不在「会不会想」。
2. **第二类的形态不是新发明的**，它照抄 §2.5 规格纪律第 4 条（「每新增一个 Port
   必须同时指出强制它存在的不变量」）。同一条纪律换个对象。
3. **两条声明都能机械扫描**（`verify:tools` B 段），所以它们不是口号。

## Consequences

### 接受的代价

- **迁移前的 Run 不能 resume。** `write_note` 改名 `write_file` 并迁包之后，
  老 Run 的 `agentSpec.toolSnapshots` 里还是 `write_note`，而注册的是 `write_file`。
  **【定】不做别名表** —— 库里只有开发期 Run，代价接近零；别名表是永久负担。
- **`verify:pairing` 的中断判据要换载体。** 它原本挂在 `write_note.delay_ms` 上，
  而通用工具的入参里不该有「请慢一点」这种只服务测量的旋钮。改由 `cases/` 里新建的
  `slow_write` 承担 —— 【定】必须是**可控慢的写**而不是可控慢的空转：
  纯延迟的 noop 永远 `NO_EFFECT`，`sideEffectState` 的诚实上报测不到。
- **多一层目录、多一套依赖方向规则**（`cases → tools` 允许，两个反方向禁止）。
- **判断归属偶尔要停下来想**。这是刻意的：想不清楚它属于哪一类，多半说明它不该加。

### 适用条件

三场景（办公 / 代码 / 聊天）是当前产品语境下的场景集合。
产品语境变了（比如加进「运维」），这条标准要重新拟。

### 重新评估的触发条件

- 出现一个既不是三场景常用、也说不出服务哪条 Harness 机制、却又确实必要的工具
  —— 那说明存在第三类，标准要扩；
- `tools/common` 的工具数超过 ~15，或 `fixedOverheadTokens` 起步价超过 ~2700 token
  —— §16.1【定·实测】每工具约 180 token，这是一条**免费的经济闸**：
  「一个 Case 一套工具」会直接反映在每次请求上；
- 边界 6b 被加白名单 —— 那等于这条 ADR 被架空。

## Eval Evidence

- `verify:tools` A 段：六条边界 grep 全过；**A2 段判别力实测** ——
  往 `tools/common` 注入一行 `import … from "@workagent/micro-cases"`，
  第 6b 条当场翻红并指出行号（注入文件随后删除）。
- `verify:tools` B 段：扫 `tools/common` 的 **10 个**工具文件头，场景工具 8 / 机制工具 2，缺一即红。
  （**收口批更正**：此前写「11 个工具、机制工具 1」，两个数都不对 —— B 段只扫 `tools/common`，
  而 `cases/micro-cases` 的两个测量工具不在它的范围里。）
- `verify:tools` **B2 段（收口批新增）**：`progressReporting.mode !== "NONE"` 的工具，
  源码里必须有 `ctx.onProgress(` 调用点 —— 它一上来就抓到两个死声明（`read_file` / `search`）。
- `verify:tools` G 段：固定开销基线读数 **12 工具 = 2160 token**（默认装配；`tools/common` 10 个 = 1800）。
  （**收口批更正**：此前写「11 工具 ≈ 1980」—— 8＋2＋2 = 12，是一处算术错误。）
  **本段刻意不设阈值** —— 设一个「不许超过 N」的门槛，等于在没有证据的情况下
  先给能力面画一条线。
- `verify:scenarios`：三个互不相干的任务（办公 / 代码 / 聊天）用同一套工具全部跑通。

## Interview Narrative

阶段 3 要给 Agent 加一批通用工具，第一个问题是放哪。放进任何一个业务 Case 包，
工具的形状就会被那个任务悄悄定义 —— 而这件事从代码上完全看不出来，没有任何检查会响。
所以我们新建了一层 `tools/`，并且给「通用」这个词配了机械判据：
一条 grep 禁止它依赖任何 Case 包，加上每个工具文件头必须声明它凭什么在这里。

声明分两类，是因为第一版标准（「三场景常用」）有盲区：像「按 ref 取回被外置的大结果」
这种工具，办公、代码、聊天场景里没人会这么说，但没有它，大结果外置就变成了
比截断更糟的信息阻断。所以第二类的声明义务是「指出你服务哪条 Harness 机制、
以及不做它会怎样」—— 形式上照抄了我们对新增 Port 的要求。

真正能证伪「通用」的不是这两条 grep，是三个来自不同场景、互不相干的任务用同一套工具都跑通。
前两道只能防显式依赖，防不了「形状是照着某个任务长的」。
