# ADR-0018：带上传的断网云沙箱调用，经部署配置里的显式信任声明才放行

- 日期：2026-10-16
- 状态：已采纳
- 关联：[ADR-0017](0017-可证明无外部副作用的云沙箱执行自动放行.md)（把这个问题登记为待定）、
  [ADR-0012](0012-审批与执行特权是两条正交的档位轴.md)（「显式的、有名字的范围授权不是单次审批」）

## Problem

ADR-0017 让「断网 ＋ 没有上传」的 `cloud_shell` 自动放行，live 实测后发现覆盖面很窄：
**绝大多数有用的调用都带 inputs**，因为要算的数据就在 workspace 里。
于是它把「带上传的断网调用要不要放行」登记为待定，并写明：
这一步要另一套论证，而「池子与云账号没被攻破」不是 Atlas 能证明的事。

这句话现在仍然成立。所以问题不是「能不能证明安全」，而是**谁来做这个信任决定**。

## Decision

`cloud-sandbox.json` 新增 `trustUploadsToPool`（布尔，**默认 false**）。
为 true 时，断网的 `cloud_shell` 即使带 inputs 也自动放行；为 false 时行为与 ADR-0017 完全一致。

### 为什么是配置项，而不是 Atlas 自己判定

ADR-0017 那一支能自动放行，靠的是**机械可证明**：断网 ＋ 无上传 ⇒ 等价于一次 workspace 写。
带上传之后，剩下的风险落在 Atlas 证明不了的地方 —— 池子与云账号本身。
**证明不了的东西不能由 Atlas 宣称成立**（本仓 MCP 那批的教训：「凡是需要理解才成立的话，不许说」）。

但这个风险对部署者是**可知的**：池子是他自己搭的、云账号是他自己的。
「我信任我自己的池子」是一个只有他能做、而且他完全有依据做的判断。

这与 ADR-0012 对 `UNRESTRICTED` 的论证一字不差：
> 那句「不能通过单次审批放行」推翻的不是它的理由，而是它的**适用前提**。
> `UNRESTRICTED` 恰恰是一次**显式的、有名字的、写在启动参数里的**范围授权 —— 它不是单次审批。

`trustUploadsToPool` 同样是一次显式的、有名字的、写在部署配置里的范围授权。

### 放行之后已有事实依然成立

| 已有的测量 | 依据 |
|---|---|
| 断网是彻底的（连 DNS 一起断） | ADR-0016 阶段 0 实测；池子下发后读回平台回显核对，对不上不执行 |
| 凭证文件上传不了 | `inputs` 过读黑名单那一份（`verify:cloud` C1） |
| 沙箱用完即销毁 | 归还即销毁；`probe:cloud-live` E 段确认无借出残留 |
| 数据能落回本机的唯一通道是声明过的 outputs | handler 只取回 outputs，且 outputs 不得逃出 workspace |

所以开了这个声明，**上传的数据被限定在部署者自己的池子里**；它不再需要逐次审批，
是因为部署者已经事先、整体地对这件事做了授权。

### 【定】事实表**一个字不改**

放行只动审批这一道。`riskFacts` 照记 `DATA_LEAVES_HOST`、`dataMovement` 照记
「上传 N 个 workspace 文件」，`decidedBy` 记 `AUTO_GRANT`。
**「放行了」不等于「没有发生」** —— 数据确实离开了本机，事后必须查得到。
把它从事实表里抹掉，等于让一次授权替事实作证。

### 【定】只放开「上传」这一条，不放开「出网」

开了网的调用**无论如何不放行**，信任声明管不到它。
理由是范围：信任的对象是「我的池子」，而开了网的命令能把数据送到池子之外的任何地方 ——
那已经不是部署者信任过的东西了。

### 【定】它不进 RunSpec、不进工具版本

它是**审批**侧的配置，与 `--approval` 同一条轴（ADR-0012：审批档位住在 ApprovalDecider
注入点上，不进 RunSpec）。工具本身的行为没有变，所以也不进工具快照的版本。

## Consequences（代价，一条都不许假装没有）

1. **workspace 里的非凭证文件会在无人过问下上传到云上。** 读黑名单只挡凭证类
   （`.env` / `.ssh` / `.aws`…）；业务数据、客户名单这类文件它不认识。
   打开这个声明之前要想清楚：workspace 里放了什么。
2. **信任的是整个池子与云账号。** 池子被攻破、云账号凭证泄漏，这个声明都挡不住 ——
   它本来就没打算挡，它只是把「我信不信」这个问题交还给能回答它的人。
3. **默认关闭意味着大多数人用不到它。** 这是故意的：一个会让数据无人过问地离开本机的开关，
   不该在没人做过决定的情况下生效。
4. **配置拼错会被拒**（未知键报错，与既有规则一致），但**写成字符串 `"true"` 也会被拒** ——
   这个字段只接受布尔，不做宽松解析。宽松解析的失败方向是「以为关着，其实开着」。

## Eval Evidence

- `verify:cloud` K 段：
  - 未声明信任：断网 ＋ 有 inputs → **不放行**（ADR-0017 行为不变）；
  - 声明信任：断网 ＋ 有 inputs → **放行**；
  - 声明信任：**开了网** → 仍然不放行（信任管不到出网）；
  - 声明信任时事实表照记 `DATA_LEAVES_HOST` 与 `dataMovement`；
  - 配置解析：只接受布尔，`"true"` 被拒。
- 注入实测：信任声明一律当 true、信任声明放开出网、信任声明抹掉事实表，各自翻红。
- 顺带的一处：声明信任时，`net=none` 成为唯一的闸门 —— ADR-0017 里它与
  `DATA_LEAVES_HOST` 互相遮蔽的那一对，在这个模式下**变得可以单独触发**。
- live（真实端点 ＋ 真实云沙箱，`--approval default`、**非 TTY** —— 没放行就等于被拒），
  同一道带 inputs 的题：

  | | 云沙箱调用 | 审批 | 结果 |
  |---|---|---|---|
  | 未声明 | `net=none;in=1;out=1` | 被拒 ×3，`decidedBy=UNDECLARED`；理由里点名 `trustUploadsToPool` | 模型**退回 read_file ＋ 心算 ＋ write_file** |
  | 已声明 | 同上 | `decidedBy=AUTO_GRANT` | `cloud_shell` 执行成功 |

  已声明那一跑里，模型随后发起的本机 `run_shell` 仍被拒 —— 放行只开给断网的 `cloud_shell`。

### 实测里冒出来的一条：未声明时模型会**悄悄降级成心算**

未声明那一跑，结果数值碰巧是对的（三个地区六行数据，心算得过来），但它**不是由真实代码算出来的**
—— 而那恰恰是用户要云沙箱的理由。规模一大或口径一复杂，这种降级就会给出错的数，
而且 Run 照样结算 `SUCCESS`（没有任务级完成契约，S5-7 / CU-9 那条老账）。

这不是本 ADR 引入的，但它说明了**默认关**的真实代价：不是「多问一次」，而是
「在没人应答的环境里，模型会换一条不那么可信的路把事做完」。如实登记，不在这里修。
