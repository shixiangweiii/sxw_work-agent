# ADR-0010：二进制交付物走字节通道，由工具在执行前按路径声明

> 状态：ACCEPTED
> 日期：2026-08-31
> 对应决策点：无（由实测逼出）
> 影响的架构条款：V05 §17（Artifact 登记）、§10.4（两层 Verification）、§1.2 第 3 条（outcome 映射）
> 证据来源：Run `run_75f0d6afafa6`（真实端点、Web 入口、2026-08-30）；三份评审（zcode P1 / codex P1-1）逐条回源复核；存量 S3-21 / S3-27

## Problem

**一个 58MB 的交付物完整正确地产生了，而 Harness 手里没有任何事实能证明它。**

实测：任务「把网页里的图片都下载下来打包成 images.zip」，模型用 `run_shell`
下载 11 张图并 `zip` 打包，产物经外部审计确认完全正确。而同一次运行的事实链是：

```text
artifacts 表            0 行
ArtifactRegistered      0 次
ArtifactVerified        0 次
VerificationCompleted   13 次，全部 SKIPPED / required=false
deliveredArtifactIds    []
Outcome                 SUCCESS
```

`SUCCESS` 在这里准确表达的是「运行顺利收敛」，**不能**扩展成「交付物正确」——
后者这次是由报告阶段的外部后验审计给出的，不是 Atlas 自己证明的。
ZIP 缺失、损坏、或装进 11 个 404 错误页，现有事实链会结算出**同样的** SUCCESS。

### 为什么现在必须决

三条回源确认的事实说明这不是「run_shell 少声明了一个字段」：

1. **产物通道在类型层是字符串通道。** `ProducedArtifact.content: string`、
   `ArtifactRegistration.content: string`、`ArtifactCheckerPort.check(record, content: string)`。
2. **全 `tools/` 与 `cases/` 里发出 `artifact:` 的只有一处** —— `fs/write-file.ts`，
   而它写的是模型手打的 UTF-8 字符串。
3. **`kind:"zip"` 这个检查器因此没有任何生产者。** 唯一能触发它的路径是
   「模型用 `write_file` 写一个叫 `x.zip` 的文本文件」，那条路上它只可能红。

第 3 条是这次最刺眼的：仓里有一个写得挺仔细的 ZIP 结构检查器（`PK` 魔数 ＋
EOCD ＋「归档被截断了」的具名理由），**它从上线起就不可达**。
这与本仓反复猎杀的「未接线比不写更糟」是同一个形态，只是它藏在类型签名里。

### 顺手排掉的一个错误修法

「给 `run_shell` 的 outcome 加个 `artifact` 字段，把 zip 的内容塞进去」——
**这个修法会让正确的 Run 被判 FAILED。** 回源：

- `artifact-store.ts` 的 `register()` 算的是 `sha256(input.content, "utf8")`，
  `sizeBytes` 是 `Buffer.byteLength(content, "utf8")`；
- 而 `artifact-checks` 的第 ① 项检查读的是**磁盘上那一份**的字节
  （`diskHashReason`，它被明确设计成不做同源比较）。

于是二进制经过一次 UTF-8 往返之后，登记的 hash 与磁盘字节必然不等 →
`DELIVERABLE` 检查失败 → §1.2 第 3 条 → **`FAILED`**。
一个把交付物做对了的 Run 会因为登记通道的编码口径被判成失败。

## Hypothesis

做决策时的认知状态：

- 我们**知道**：字符串通道是共同根因，`BlobStorePort.put({content: string})`
  已经因为同一件事被登记为 S3-21（`fetch_url` 取不回二进制），
  两个互不相干的场景撞到同一个洞；
- 我们**知道**：不扫 workspace 猜交付物这条（§17 语义 1）是对的，
  自动派生会把用户自己放进目录的文件误当成本次产出，本次 workspace 里就有
  `react-agent-demo.zip` 这种无关文件；
- 我们**不知道**：模型会不会真的去声明产物。`write_file` 的 `artifact_role`
  实测三次跑同一道题得到 **未登记 / INTERMEDIATE / DELIVERABLE** 三种结果
  （S3-27）—— 声明由模型自愿这件事本身就是个待决问题，本 ADR **不解决它**，
  只保证「声明了就一定进得去」；
- 我们**不知道**：一次登记要读多大的文件才算过分。本次 58MB，上限凭直觉定。

## Alternatives

| 方案 | 优点 | 代价 | 何时会后悔 |
|---|---|---|---|
| **A. 给 `run_shell` 加 artifact 字段，内容按字符串传** | 改一处，最省事 | **正确的 Run 会被判 FAILED**（见上）；二进制经 UTF-8 往返被破坏 | 第一次真的登记一个二进制产物时，立刻 |
| **B. `content` 放宽成 `string \| Uint8Array`，工具把字节交上来** | 类型面变化最小；hash / size 按真实字节算；磁盘复核仍然是**独立**的一道（工具交的字节要与盘上一致才过） | 整个文件要进一次内存；`ArtifactCheckerPort` 签名变更 | 需要登记一个超出内存的产物时 |
| **C. 只传 `path`，由 Runtime 从磁盘流式算 hash** | 完全不占内存 | 存储层（`packages/store-sqlite`）**不知道 workspaceRoot**，相对路径解析不了；把绝对路径塞进 Port 会让存储层认识 workspace | 想支持 GB 级产物时会想回来拿它 |
| **D. 由工具自报 `contentHash`** | 不占内存、不改 Port | **把磁盘复核变成同源比较** —— 那正是阶段 3 收口批刚拆掉的「永远绿灯的闸门」 | 立刻。这个方案不能选 |

## Decision

**选 B：`content` 放宽为 `string | Uint8Array`；`run_shell` 增加
`artifact_path` ＋ `artifact_role` 两个入参，在执行前声明、执行成功后由工具
从磁盘读回字节交给 Runtime 登记。**

三条理由，都能指到证据：

1. **B 是唯一保住「磁盘复核有判别力」的方案。** 工具交上来的字节与
   `diskHashReason` 读到的字节是两次独立取数，不一致就红。D 会把这条闸门
   变成恒真式；C 保不住是因为存储层解析不了相对路径，而给它绝对路径等于
   让存储层认识 workspace。
2. **「执行前声明」满足 §17 语义 1，且顺带改善审批。** 路径是**命令入参的一部分**，
   在审批卡上和命令原文一起给人看 —— 人批准的不只是「跑这条命令」，
   还有「它自称要交付这个文件」。Runtime 仍然不扫 workspace、不从 output 里猜。
3. **`kind` 的词表挪到检查器旁边，只留一份。** `write-file.ts` 原本有一个私有的
   `kindOf`；`run_shell` 需要同一件事。抄第二份的后果是两个工具对同一个扩展名
   给出不同 kind、跑不同检查器，而两边都是绿的 —— 本仓已经在读黑名单上栽过
   一次「唯一事实源在两个实现里各说各话」。

## Consequences

### 接受的代价

- **登记一次产物要把它整个读进内存一次。** 上限定在 **256 MiB**，超过则
  **不登记**并在工具结果里显式说明（`artifactNote`）—— 不是静默跳过。
  这个上限是拍的，没有证据，重估触发条件见下。
- **一次 `run_shell` 只能声明一个产物。** `ToolExecutionOutcome.artifact` 是单数，
  改成复数要动 `settle-batch` 的结算循环。「zip ＋ manifest」这类双产物场景
  当前表达不了，登记为欠账。
- **`kind` 由扩展名推。** 未知扩展名的二进制会落进 `text` 并在编码检查上翻红 ——
  失败方向是**看得见**的（红一条判据），不是静默通过，可以接受。
- **模型不声明就还是没有产物。** 本 ADR 只保证「声明了就进得去」，
  「怎样让它一定去声明」是 S3-27，另案。

### 适用条件

- 产物落在 workspace 内的真实文件上（`isInsideWorkspace` 的 realpath 判定）。
  不落盘的产物走不了这条路径。
- 单人本地开发期，内存不是稀缺资源。

### 重新评估的触发条件

1. 真的出现需要登记 **> 256 MiB** 产物的任务 → 回头取方案 C，
   并同时解决「存储层不认识 workspaceRoot」这件事；
2. 出现需要**一次声明多个产物**的任务（zip ＋ manifest 是最可能的第一个）
   → 把 `ToolExecutionOutcome.artifact` 改成复数；
3. S3-27 定了「谁来声明产物」之后 —— 如果结论是「不由模型声明」，
   `artifact_path` 这个入参要跟着改形态。

## Eval Evidence

**问题侧的证据是硬的**，来自一次真实端点运行：

| 事实 | 出处 |
|---|---|
| artifacts 0 行 / deliveredArtifactIds `[]` / Outcome SUCCESS | `/Users/shixiangweii/Desktop/temp/.workagent/runs.db`、`runs/run_75f0d6afafa6.jsonl` footer |
| 13 次 Verification 全 SKIPPED | 同上，RUN_META 的 `verifications` |
| 交付物其实完全正确（11 项、CRC 通过、逐字节匹配来源） | 外部后验审计（`unzip -t` ＋ 页面比对） |
| `OBSERVED_TOOLS = {write_file, edit_file}` | `tools/common/src/index.ts:399` |
| 发出 `artifact:` 的只有一处 | `grep -rn "artifact:" tools cases` → `fs/write-file.ts:192` |
| hash 口径 `sha256(content,"utf8")` | `packages/store-sqlite/src/artifact-store.ts:50` |

**方案侧的证据由本批的判据与注入实测提供**（`verify:artifact`）：
二进制 zip 声明 → 登记 → ZIP 结构检查跑到 → `deliveredArtifactIds` 非空；
以及三条注入：把内容改成字符串往返、把磁盘上的产物改坏、声明一个不存在的路径。

## Interview Narrative

我们跑了一个真实任务：抓网页图片、打成 zip。东西做对了，Harness 结算 SUCCESS ——
但那个 SUCCESS 和 zip 之间没有任何机械纽带：产物表是空的，13 次验证全跳过。
挖下去发现根因不在 shell 工具，而在类型签名：整条产物通道的 `content` 是 `string`，
所以二进制在类型层就进不去，连仓里那个写得挺仔细的 ZIP 检查器都从上线起没有生产者。

最诱人的修法——给 shell 工具加个 artifact 字段——是错的：登记时按 UTF-8 算 hash，
而检查时读磁盘字节，二进制经一次编码往返必然对不上，结果是**把做对了的 Run 判成失败**。
所以我们把通道放宽到字节，并让工具在执行前按路径声明产物：路径进命令入参，
人在审批时就能看到「它自称要交付什么」，而磁盘复核仍然是独立的第二次取数——
工具交上来的字节要和盘上那份对得上才算过，这样这道闸门才不是同源自比。
