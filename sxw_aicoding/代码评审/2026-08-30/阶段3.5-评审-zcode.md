## 1. P1 — 必须先修（无人审批的真实执行路径）

### P1-1 只读白名单会自动放行「带参数的写操作」

**位置**：`tools/common/src/exec/command-analysis.ts:61-65`（`READONLY_PROGRAMS`）、`:74-78`（`GIT_READONLY_SUBCOMMANDS`）。

**证据（第二轮实测，直接执行 `analyzeCommand`，非推测）**：

```
READ/ALLOW "find . -delete"                          ← 递归删除 workspace 文件
READ/ALLOW "git config user.email attacker@evil.com" ← 写 .git/config
READ/ALLOW "git tag v1.0"
READ/ALLOW "git branch evil"
READ/ALLOW "git remote add origin https://evil.example"
READ/ALLOW "sort -o notes_out.txt notes.txt"         ← 任意路径覆盖写
READ/ALLOW "rg --pre \"touch /tmp/pwned\" pattern f" ← 任意命令执行，见下
```

判定只看 `argv[0]` 是否在白名单（git 只多看第二个词），不看参数。其中：

- **`find`**：`-delete` 动作标志不带任何元字符。判别力用例里 `find . -name '*.txt' -delete` 因带 `*` 被拦，**裸 `-delete` 是漏的**；同类还有 `-fprint` / `-fprintf`。
- **`git branch` / `git tag` / `git config` / `git remote`**：读/写多态子命令，只看第二个词判不出来。文件头注释写「`git status` 与 `git push` 的后果差着整个远端仓库」——写远端的 push 被拦了，写本地的这四个没拦。
- **`sort`**：`-o` 把输出重定向到任意路径，无元字符。
- **`rg --pre`（第二轮新发现，本批 7 条里唯一的任意命令执行）**：ripgrep 的 `--pre` 会让 rg 用 shell 执行指定预处理命令。参数里的命令被单引号包着也不行——`'` 不在 `SHELL_METACHARS` 里。`find -exec` 因带 `\;` 元字符被拦，`rg --pre` 什么都不带。

**影响面**：这些命令落 `READ` 后按决 3 自动放行。沙箱仍然生效（写被限定在 workspace ＋ tmp、默认禁网），所以 `find . -delete` 炸不掉 workspace 外的东西——但「不经过人就改写 workspace」本身违反决 3 的语义（判定为只读才自动放行）。在 `--yes-all` 下连审批提示都跳过。

**修法方向**（与文件头自己定的失败方向一致，代价只是多问一次）：

- `find` / `sort` / `rg` 移出白名单（落 EXECUTE）；
- git 只读子命令表收敛到**恒只读**的子命令（status/log/diff/show/rev-parse/describe/blame/shortlog/ls-files/ls-tree/cat-file/whatchanged/reflog），`branch`/`tag`/`remote`/`config` 挪出去。

**回归阻力为零**：verify:shell A 段 13 条用例没有任何一条断言 `find`/`sort`/`rg` 是只读，收紧不会假红。建议同时补三条新用例进 A 段（含 `kills` 自陈）。

### P1-2 `timeout_ms` 上限 600s 是永远达不到的死数字，且超时被误报为「取消」

**位置**：`tools/common/src/exec/run-shell.ts:55-56,141` ＋ `packages/harness-runtime/src/action/settle-batch.ts:428-430,496-512`。

**机制链**（第二轮逐环核实）：

1. schema description 告诉模型 `timeout_ms` 可传到 `MAX_TIMEOUT_MS = 600_000`；
2. 但 Runtime 步级超时用的是 `timeoutPolicy.timeoutMs = DEFAULT_TIMEOUT_MS = 120_000`（`settle-batch.ts:428`），通过 `ctx.signal` 下发；
3. run_shell 收到 abort 走 `onAbort → killedBy="cancel"` 分支，返回 `ok:false TOOL_SHELL_CANCELLED`；
4. `settle-batch.ts:496` 有个把步级超时改判成 `TOOL_TIMEOUT` 的路径，但它**只在工具返回 ok:true 时生效**——run_shell 自己 abort 后返回 ok:false，改判永远轮不到它。

净效果：模型传 `timeout_ms: 600000` 跑长构建，120 秒必然被杀，收到的是 **`TOOL_SHELL_CANCELLED`**——症状（「总在 2 分钟被取消」）直接误导排查方向。

**verify:shell 没抓到它是必然的**：C3 用 `timeout_ms: 2000`、C4 用 60_000 ＋ 800ms abort，取值区间都远小于 120s，两条判据的结构恰好躲开了矛盾。

**修法**：`timeoutPolicy.timeoutMs` 提到 `MAX_TIMEOUT_MS`（600s），让工具内超时先到并如实报 `TOOL_SHELL_TIMEOUT`，步级超时退为兜底；或者把 schema 上限改到 120s 并说清。二选一，不能两头都留着。

## 2. P2 — 应处理（不破坏边界，但失真/泄漏/口径错）

### P2-1 `shell-effect-resolver.ts:95-101` 的 digest 注释描述了一个不存在的机制

注释（及 `verify:shell.ts:199` 的 verdict 文案）说：「审批授权是按 digest 认的——只哈希程序名等于『批准过一次 git，之后所有 git 都算批过』」。

**第二轮核实的事实**：main.ts 的 `interactiveApproval` **没有任何审批记忆**，每次 EXECUTE 都是新鲜问（`--yes-all` 则无条件批）；`resolvedEffect.digest` 的唯一消费者是 Progress Guard 的打转检测（`run-loop.ts:952-958`，与 `inputDigest` 配合）。

命令原文进 digest 本身无害，还让打转指纹更准（同一条命令重试会被认出来）——**行为是对的，理由是错的**。但这个仓库自己的教训（实施记录 §7）就是：「一处结论被抄进第二个地方之后，它就不再有人回源了」——这次写在一处权威的实现注释里，且已被 verify 文案抄了第二处。下一个读代码的人若据此真去实现「按 digest 记审批」，会引入它自己声称要防的那个问题。

**修法**：注释改写为真实理由（打转检测的指纹精度），同步修 `verify:shell.ts:199`。

### P2-2 ask_user 的 NO_ANSWER 会让 Trace 记「人应答了」

**位置**：`packages/harness-runtime/src/action/settle-batch.ts:465-471`。

`answered: outcome.ok`——ask_user 的 NO_ANSWER 分支是 `ok:true`（决 3 的刻意设计），于是 `InteractionCompleted.answered = true`，而 468 行注释自己写着「`answered` 说的是『人应答了没有』」。两条各自正确的决定（决 3 的 ok:true ＋ answered 的语义定义）在乘积处产生了错误事实。

**影响**：目前无行为破坏——等待时间扣除（`run-loop.ts:917`）只看事件对、不看 `answered`；但 §20.3 的 Trace 语义失真：非交互跑批里每次 ask_user 都会在 Trace 上留下「人应答了」。

**判据盲区**：verify:progress H 段 ① 断言了应答场景 `answered===true`，② NO_ANSWER 场景恰恰没断言这个字段——判据照不到它。

**修法**：H 段 ② 补 `answered` 断言 ＋ 打通可辨别信号（如从 output JSON 解析 `status`，或给 Outcome 加显式字段）。

### P2-3 per-run 临时目录从不清理

**位置**：`tools/common/src/exec/run-shell.ts:207`。

每次调用 `mkdtempSync(join(tmpdir(), "wa-shell-"))`，全文件没有任何 `rmSync`/`rmdirSync`。命令写进 tmp 的东西（解包产物、git 临时对象）会永久留在盘上。应在 `cleanup()` 里随心跳/定时器一并清掉。

### P2-4 `afterChars` 口径与实际返回不符

**位置**：`tools/common/src/net/html-to-markdown.ts:88-90`。

实际返回的 markdown 是经过 `\n{3,}` 压缩再 trim 的，但 `afterChars` 取的是压缩前的 `markdown.length`。`renderText` 把这组数拼进 note（「转换省了多少」），系统性低估，且与模型实际拿到的内容长度对不上。压缩后再取长度即可。

### P2-5 `probe-binary-chain.ts` 未入实施报告清单

`apps/cli/src/verify/probe-binary-chain.ts` 真实存在于未跟踪文件中，但实施记录 §九「新增文件（7 个）」没有它：一次性探针、内含 `as any`、未注册 npm script。要么进报告清单，要么在报告里标注「用后即弃」。留一个看起来像验收实为一仪器的文件在 verify/ 目录，第一个读到的人要靠猜。

### P2-6 （自一轮保留，升级依据补充）—— 无

> 一轮的 P2 #7「外部信号杀进程被报成成功」二轮维持原判：非 killedBy 路径下 `code ?? -1` → `exitCode: -1, ok:true, APPLIED`，`signal` 字段在 body 里但模型大概率读不懂 -1 的含义。维持 P3（见 §3），不升级——它需要 OOM killer 这类外因才触发，且 body 里确实带了 `signal` 事实。

## 5. 值得肯定的设计（两轮均维持）

- **`errorOf` 沿用工具自报的 `sideEffectState`**而不硬编 NO_EFFECT——工具说不清错误，不代表它说不清有没有写下去，恢复线索保住了（`settle-batch.ts:1008-1048`）。
- **`readOnly && !allowNetwork` 独立于白名单判联网**（`shell-effect-resolver.ts:42`）——防的是「将来有人往白名单加了能联网的程序」，这条判定独立存在是对的。
- **沙箱 profile 对 deny 与 allow 的 `realpath` 失败取相反取舍**（`sandbox.ts:152-158`）——deny 靠默认兜、allow 报看得见的错，这个不对称是对的。
- **verify:shell B 段坚持「内核真的拒了」的实测**而非 profile 字符串断言；B2 的唯一命名＋事前断言＋事后清理把实施记录 §6.2 的仪器毒化教训制度化进了代码。
- **verify:tools I 段**：「导航必须仍在」钉住 ADR-0007 的线；⑦ 削减比例只打印不断阈值，理由站得住。
- **E2 不写死工具数**，断言关系（`overhead === count × 180`）而非常数——实施记录 §十一 自己犯过的错，判据层面已免疫。
