## 3. P1 阻断问题

### P1-1：“只读命令”可实际写删 workspace，并绕过审批

**位置**

- `tools/common/src/exec/command-analysis.ts:61-65, 104-147`
- `tools/common/src/exec/shell-effect-resolver.ts:42-54`
- `packages/harness-runtime/src/action/policy.ts:53-89`
- `tools/common/src/exec/sandbox.ts:118-120`
- `apps/cli/src/verify/shell.ts:115-178`

**问题**

`READONLY_PROGRAMS` 包含 `find`、`sort`、`uniq`、`tree` 和 `git`，但分析器只校验 shell 元字符、`argv[0]` 以及 `git argv[1]`，不判断参数的写入/删除语义。例如：

```text
find . -maxdepth 1 -delete
sort input.txt -o output.txt
uniq input.txt output.txt
tree -o tree.txt
git branch new-branch
git tag v1
git config --file x.cfg a.b c
```

上述命令不含当前黑名单元字符，会被解析为 `READ`，随后被 Policy 直接 `ALLOW`。沙箱又明确允许 workspace 内写入，所以它不会阻止真实副作用。

**影响**

- `--confirm` 也无法触发审批；
- Trace 会把真实写删记为 `READ/REVERSIBLE`；
- 实施报告“判不出来就落 EXECUTE，只会多问一次”的安全结论不成立：当前错误方向恰好是少问一次。

**验收缺口**

`verify:shell` A 段只测试程序名、明显元字符与 `git push`，没有任何“白名单程序＋写参数”反例。

### P1-2：白名单没有绑定真实可执行文件，Shell 同时继承了 Harness 凭证

**位置**

- `tools/common/src/exec/command-analysis.ts:117-129`
- `tools/common/src/exec/run-shell.ts:219-237`
- `apps/cli/src/compose.ts:107-115, 170-206`
- `apps/cli/src/compose.ts:632-714`

**问题**

实现拒绝 `/bin/ls` 这种显式路径，却自动信任裸程序名 `ls`。真实执行目标由继承的 `PATH` 决定；CLI 通常由 `npm run` 启动，workspace 的 `node_modules/.bin` 可优先于系统目录。如果存在同名 `ls` shim，模型调用 `ls -la` 时会在 `READ/ALLOW` 下执行任意代码。

`spawn()` 未指定净化后的 `env`，因此子进程继承：

- `PATH`；
- `BASH_ENV`（非交互 Bash 会在命令前 source）；
- 经 `loadEnv()` 注入的全部真实端点密钥。

沙箱拦截凭证文件不等于拦截已存在于进程环境中的明文。`STANDARD` 脱敏只识别少数密钥形态，编码后的凭证或非标准形态可被落盘。

**影响**

- 无审批任意代码执行；
- Harness 自身的模型凭证可进入 Shell 子进程；
- 违反 V05 §22.3 “Secret 明文只在对应 Adapter 执行阶段短暂解析”的契约。

### P1-4：`fetch_url` 私网护栏存在两条可利用的 SSRF 路径

**位置**

- `tools/common/src/net/url-guard.ts:31-107`
- `tools/common/src/net/fetch-url.ts:156-218`
- `apps/cli/src/verify/artifact.ts:436-458`

#### 路径 A：IPv4-mapped IPv6 十六进制形式

URL parser 会将 `::ffff:127.0.0.1` 规范化为 `::ffff:7f00:1`。当前实现只用正则识别 `::ffff:127.0.0.1` 这种点分十进制形式，随后 IPv6 分支只拦截 `::1`、`fc/fd`、`fe8-feb`。

最小实测：

```text
executeFetchUrl({ url: "http://[::ffff:7f00:1]:<loopback-port>/private" }, ctx)
```

结果：

```json
{"ok":true,"reached":true,"content":"LOOPBACK-REACHED"}
```

#### 路径 B：自动跟随重定向后才检查终点

`fetch()` 使用 `redirect: "follow"`。当公网 URL 返回 `302 -> http://127.0.0.1:<port>/mutate` 时，内网 GET 已在 `fetch()` 返回 `Response` 之前发出。事后的 `finalGuard` 只能丢弃响应，无法撤销请求。如果链路是“公网 -> 私网 -> 公网”，最终 URL 仍为公网，当前实现连报警都不会产生。

**影响**

- 读取本机调试端口、内网服务与 mapped 地址；
- blind SSRF 与内网 GET 副作用；
- 直接推翻工具 description 和实施报告“拒绝私网与 localhost”的安全声明。

**属性说明**

这两个漏洞主体上属于既有 `fetch_url` 实现，不是 HTML 转换本身新引入；但阶段 3.5 报告将该护栏作为自动放行策略的前提，因此它们仍是本次收口阻断项。

### P1-5：`ask_user` / `request_handoff` 不是 ActionBatch 内的执行屏障

**位置**

- `packages/harness-runtime/src/action/settle-batch.ts:187-196, 451-471, 714-735`
- `packages/harness-runtime/src/loop/run-loop.ts:854-965`
- `tools/common/src/mech/request-handoff.ts:202-219`
- `apps/cli/src/verify/progress.ts:899-960`

**最小触发**

同一次模型响应返回：

```text
1. ask_user（A 还是 B）
2. write_file（按 A 方案写入）
```

用户在第一个工具中选择 B 后，`executeBatch()` 仍会继续执行第二个预先形成的调用。模型要到整批结束、结果被追加到 transcript 后才看到用户选择。

`request_handoff` 具有更明确的违约：V05 §20.3 要求“完成信号 -> 重新 Observation + Verification -> continue/re-plan”，但同批后续 Action 可在模型重新规划前直接执行。

**影响**

- 产生与用户明确选择相反的产物或写入；

**验收缺口**

`verify:progress` 中的 `q1` 批只有一个 `ask_user` 调用，没有“交互工具＋同批后继副作用”反例。

### P1-6：CLI 丢弃工具级 signal，交互超时不生效

**位置**

- `packages/harness-runtime/src/action/settle-batch.ts:428-430, 461-511`
- `tools/common/src/mech/ask-user.ts:123, 198-233`
- `tools/common/src/mech/request-handoff.ts:126, 187`
- `apps/cli/src/main.ts:425-440, 591-607, 637-654`
- `packages/harness-runtime/src/budget/index.ts:58-89`

**问题**

Runtime 会为每一步构造 `AbortSignal.timeout(stepMs)`，`ask_user` 和 `request_handoff` 也把 `ctx.signal` 放入 channel request。但 CLI 的 `terminalQuestion()` 和 `terminalHandoff()` 捕获并传递的是组合时的全局 SIGINT signal，而不是 `request.signal`。

交互式 CLI 中，用户如果不输入：

- `ask_user` 声明的 30 分钟超时不能唤醒 stdin；
- `request_handoff` 的 2 小时超时同样无效；
- 等待时间被从 active wall-clock 扣除，默认又未设 `maxTotalWallClockMs`，Run 可无期限停在 `WAITING_FOR_INTERACTION`。

还存在一个二次语义冲突：即使仅将 `request.signal` 正确传给 stdin，超时后 channel 返回 `undefined`，`ask_user` 会合法返回 `NO_ANSWER/ok:true`；但 Runtime 又会因 step signal 已 aborted 将它覆写为 `TOOL_TIMEOUT/ok:false`。所以该问题不能通过只换一根 signal 简单修复，还需决定“等待超时是 NO_ANSWER 还是工具失败”。

**验收缺口**

`verify:progress` 使用立即返回的 fake channel，未经过真实 `StdinChannel`，也没有推进步骤超时。

### P1-7：重复 `toolCallId` 会破坏批内配对与 resume 事实链

**位置**

- `packages/harness-runtime/src/action/settle-batch.ts:135-146, 187-205, 737-761`
- `packages/harness-runtime/src/transcript/index.ts:164-181`
- `packages/harness-runtime/src/facade/index.ts:104-145, 405-468`
- `adapters/shape-anthropic-messages/src/protocol.ts:190`
- `apps/cli/src/verify/pairing.ts:407-469`

**最小触发**

模型在同一轮返回两个不同工具调用，但 ID 都是 `dup`。

1. 第一个 Action 可已产生副作用并在 ledger 中写入 `dup`；
2. 第二个 Action 结算时因 ledger 已有同键而抛异常；
3. 整批 results 尚未被追加到 transcript；
4. Run 异常退出会绕过终态写入，投影可残留 `RUNNING`；
5. resume 中的 `findUnpairedToolUses()` 使用 `Map/Set` 按 ID 折叠，只保留最后一个 call；
6. 补一条 result 后，扫描器可返回“未配对为 0”，但实际已丢失一次调用与副作用归属。

**影响**

直接违反 V05 不变量 8“批内每个 Tool Call 必须有且仅有一个 result”。选定端点对 `toolCallId` 又没有外部校验，这是 Runtime 必须自己守住的边界。

**验收缺口**

新增 pairing 用例只测试 `ok:false` 但不带 `error`，所有测试调用均使用唯一 ID。

### P2-2：`run_shell.timeout_ms` 的 600 秒承诺在真实 Runtime 链路中不可达

**位置**

- `tools/common/src/exec/run-shell.ts:54-56, 100-103, 141, 203, 276-285, 320-344`
- `packages/harness-runtime/src/action/settle-batch.ts:428-430`
- `apps/cli/src/verify/shell.ts:206-410`

输入 schema 承诺最长 600000ms，但 ToolDefinition 的静态 `timeoutPolicy` 始终是 120000ms。Runtime 会在 handler 外层先生成 120 秒 step signal，所以一个 `timeout_ms=600000` 的三分钟构建仍会在约 120 秒被终止。

handler 把任何 `ctx.signal` abort 都标为 `cancel`，因此外层步骤超时会被误报为 `TOOL_SHELL_CANCELLED`。默认 120 秒路径还同时存在内外两个定时器竞争。

此外，代码未在 spawn 之前检查 `ctx.signal.aborted`。如果取消发生在注册监听器之前，`addEventListener()` 不会回放已发生的 abort，命令仍会启动。

`verify:shell` 直接调用 `executeRunShell()`，未经过 Runtime 的静态步骤超时，因此全绿不能证明 600 秒链路可用。

### P2-3：临时目录和 Git 只读能力与实现声明不符

**位置**

- `tools/common/src/exec/run-shell.ts:206-212, 225-237, 287-291`
- `tools/common/src/exec/sandbox.ts:118-126`
- `tools/common/src/fs/read-guard.ts:46-80`
- `tools/common/src/exec/command-analysis.ts:74-78`

#### 临时目录

每次调用都创建 `wa-shell-*` 目录并在 seatbelt profile 中放行，但 spawn 未设置 `TMPDIR`。zip、tar、git、编译器等进程仍使用继承的系统临时目录，它们并不知道新创建并被放行的子目录。`cleanup()` 也只清理 timer/listener，不删除临时目录。

#### Git

read guard 将 `.git` 列为拒绝读取的目录，沙箱将它翻译为内核级 `file-read*` deny；同时命令分析器又声称 `git status/log/diff/show` 是可自动放行的代码场景。Git 读取 `.git/HEAD`、`index` 或 worktree 实际 gitdir 时会被沙箱拒绝。

`verify:shell` 只验证 `git status` 被分类为 `READ`，没有在真实 Git workspace 中执行它。

### P2-4：`NO_ANSWER` 被事件层记录为“用户已回答”

**位置**

- `tools/common/src/mech/ask-user.ts:198-233`
- `packages/harness-runtime/src/action/settle-batch.ts:461-471`
- `packages/harness-runtime/src/types/event.ts:58-60`
- `apps/cli/src/verify/progress.ts:965-1023`

`ask_user` 在无 channel 或没有人回答时刻意返回：

```json
{"ok":true,"status":"NO_ANSWER"}
```

Runtime 却使用 `answered: outcome.ok` 产生 `InteractionCompleted`。事件契约明确说明 `answered` 表示“人是否应答”，不是“工具是否成功”。

结果是 tool result 说“没人回答”，Trace/UI 却说“人已回答”，影响人工参与率、审计与评测解读。

新增的无回答验收只检查 tool result 和 Run outcome，没有检查该事件字段。

### P2-5：`TOOL_CONTRACT_NO_ERROR` 只修复了最终渲染，没有规范化完整事实链

**位置**

- `packages/harness-runtime/src/action/settle-batch.ts:549-560, 610-632, 729-734, 1011-1048`
- `apps/cli/src/verify/pairing.ts:407-469`

工具返回 `{ok:false,error:undefined}` 时：

1. `ExecutionAttempt` 先被记录为 `status: FAILED, error: undefined`；
2. 原始畸形 outcome 被传给 `VerificationPort`；
3. 只有最终构造 tool result 时才调用 `errorOf()` 合成 `TOOL_CONTRACT_NO_ERROR`。

如果 Verifier 在中间读取 `outcome.error.code`，它会抛异常，模型最终看到的可能是 `PORT_VERIFICATION_THREW`，而不是承诺的工具契约违反；Attempt 事实也仍没有 error。

新增 pairing 用例使用了能容忍缺失 error 的既有 Verifier，并只检查最终文案/code/配对数，所以没有覆盖该失真。

### P2-6：HTML 转 Markdown 会静默丢失结构与正文

**位置**

- `tools/common/src/net/html-to-markdown.ts:34-66, 82-94`
- `tools/common/src/net/fetch-url.ts:311-336`
- `apps/cli/src/verify/tools.ts:981-1055`
- `node_modules/turndown/README.md:121-139`

#### 表格结构丢失

当前只使用 Turndown core，没有引入或启用 `turndown-plugin-gfm` 的 tables 规则。

输入：

```html
<table><tr><th>A</th><th>B</th></tr><tr><td>1</td><td>2</td></tr></table>
```

```text
A

B

1

2
```

行列关系完全丢失，但转换器不会抛异常，`fetch_url` 仍标记 `format: "markdown"`，不会进入 raw fallback。

#### `<noscript>` 正文丢失

`getService()` 会删除 `noscript`。但 `fetch_url` 本身不执行 JavaScript，`noscript` 恰可能是当前客户端唯一能获得的用户内容。完整删除它已经是语义选择，不是纯结构转换。

**影响**

实施报告“转不动则回原文、不返回半成品”的声明只覆盖抛异常，不覆盖转换器成功返回但结构静默丢失的情形。

**验收缺口**

I 段 fixture 只包含标题、链接、强调、列表、nav/footer 和 script/style，不包含 table、noscript 或 template。

- `packages/harness-runtime/src/action/settle-batch.ts:262-270`
- `packages/harness-runtime/src/facade/index.ts:661-683`

`ResolvedEffect` 中的 `riskFacts`、`dataMovement`、`resolverVersion` 都是效果身份的组成部分，但当前 digest 只哈希：

```text
effectType | operation | scope.value | command
```

对一条本来就被分类为 `EXECUTE` 的命令，`allow_network=false` 和 `allow_network=true` 时 effectType、operation、scope 和 command 均可相同，但数据外发风险已变，digest 却不变。

普通执行的 `actionDigest` 另外包含 normalized input，所以这不是立即的审批复用绕过；但 Resolver 声称的 effect identity 已经错误，而 resume 的部分构造路径只使用工具名、版本和 effect digest。

## 7. 次要问题与已知欠账确认

以下问题不单独改变 NO-GO 结论，但应在后续收口中处置或明确登记：

1. `fetch_url` 在完整 `arrayBuffer()` 后才判断 8MB 上限，该上限不是传输/内存上限；该项已登记为存量问题。
2. `fetch_url` 忽略 `Content-Type` 中的 charset，统一 `buf.toString("utf8")`，GBK 等页面会静默乱码后再转 Markdown。
3. `html-to-markdown.ts` 所谓“懒构造避免加载 domino”不成立：顶层静态 import Turndown 时，其 CJS 已 `require("@mixmark-io/domino")`。
4. `afterChars` 记录的是换行归一前 `markdown.length`，而实际返回文本已经 `replace(...).trim()`，报告的削减字符数可不准。
5. sandbox 将 `.env` 前缀翻译成未加后缀边界的 `/\.env` 正则，会额外拒绝 `.environment.md`、`.envfoo/child`；“规则数量相等”不能证明三个消费者语义一致。
6. Shell 输出截断只保存 30000 字符并返回 `truncated` flag，没有实现注释所称的“真实总字节数”。
7. Shell 非零退出码一律可返回 `ok:true/APPLIED`、`verification:NONE`。这一设计有其“工具成功取回世界事实”的理由，但也意味着模型在 `zip` 退出非零后直接结束时，Runtime 仍可能再次得到“SUCCESS 但 zip 不存在”。

## 8. 正向确认

本次评审也确认了以下方向是合理的：

1. `TrustedEffectResolver` 只在 Runtime 中定义 Port 类型，Shell 语义实现位于 `tools/common`，通过 Composition Root 注入；Runtime 未直接导入 Shell 实现。
2. Resolver 未注册时会抛错，没有回退为 `NONE`，避免因组合漏项自动放行副作用。
3. 非 Darwin 或 `sandbox-exec` 不可用时，`run_shell` 按设计 fail-closed，不降级为无沙箱执行。
4. Shell 被取消/超时时将 `sideEffectState` 记为 `UNKNOWN`，比伪造 `NO_EFFECT` 更符合恢复契约。
5. `run_shell` 明确声明非幂等、不自动重试，并诚实落入 `RECOVERY_REQUIRED` 分支，方向正确。
6. `package-lock.json` 中 Turndown 及传递依赖记录与 `package.json` 一致。
7. 评审时 `git diff --check` 通过，未发现 diff 空白或 patch 格式错误。
