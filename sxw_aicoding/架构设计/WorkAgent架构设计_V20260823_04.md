## 0. 本版说明与阅读约定

### 0.1 本版的性质

V03 是在**零次真实 Provider 调用**的前提下写的。Spike 0 跑了三轮，覆盖 2 个平台 × 2 种 API 形状 = 4 个端点，产出 75 份原始证据。

结果比预期严重：

> **第二轮的十条结论里，有六条换个模型/平台就不成立。**

而第二轮已经做了非常干净的变量隔离（同平台、同模型、同 Key，只换 API 形状）。这说明问题不在实验设计，而在**Provider 事实本身的保质期比想象的短得多**。

因此 V04 分两轮改写。

**第一轮：回填实测（加法）**

1. **回填三轮实测**——解锁 3 个【验】标记、拍板 4 个决策点、修正 9 条条款、新增 6 条 V03 完全没有的约束；
2. **选定 v0.1 主力端点**并写明理由与重新评估条件（§0.4）；
3. **把「端点能力声明」提升为一等架构对象**（§8.7）——这是 D-07 的落地形态，也是对「事实会过期」的架构级回应；
4. **引入第四种状态标记【端点】**，把「仅对某端点成立的结论」与「跨端点不变量」在文档层面分开。

**第二轮：删减无证据支撑的机制（减法）**

5. **删除声明式验收机制**（§10.4）——`RunAcceptance` 及其配套的 Port、表、扩展点全部移除，完成判定回到标准 Harness 循环：**模型不再请求工具即完成**；
6. **删除纯 Kernel 与 durable orchestration**（§8.3、§9、§18）——`advance()`、KernelState、15 条 Directive、RuntimeActivity、Run Lock、Signal Inbox、Durable Timer、KernelState Snapshot 全部移除，代之以 `while` 循环 ＋ 具名迁移；
7. **恢复粒度定为消息级**（§18.1）——transcript 是唯一恢复来源，明确放弃 mid-turn 恢复并写明代价。

**两轮判据是同一条**（§2.5 规格纪律第 1 条）：**冻结前必须能指出支撑它的证据来源。** 第一轮是证据来了、条款跟着改；第二轮是找不到证据、机制就得撤。

第二轮的直接参照是 Claude Code 的 `query.ts`——一个真实在跑的 Harness 主循环。它印证了两件事：`while` 循环写到足够复杂会自己长出「显式状态对象 ＋ 具名迁移 ＋ 具名终止原因」（本版 §8.3 循环纪律的来源），以及**它的持久化就是消息级的**，跨迭代状态里带着 `Promise` 与 `AbortController`，根本不可序列化。

**规格规模从 V03 净收缩**（§2.6）：逻辑表 38 → 35，Port 19 → 14，Directive 16 → 0。唯一增长的是端点相关规格——**来自实测的活下来了，来自推演的被删了。**

### 0.4 已拍板：v0.1 主力端点 = 百炼 Anthropic 形状【定】

第三轮对四个端点按 WorkAgent 的实际需要做了加权打分：

| 端点 | 得分 |
|---|---|
| DeepSeek · Anthropic 形状 | 76 |
| **百炼 · Anthropic 形状** | **73** |
| 百炼 · OpenAI 形状 | 65 |
| DeepSeek · OpenAI 形状 | 57 |

**选择 73 分的那个，不是 76 分的那个。** 3 分差距在噪声范围内，两者是取舍不同而非优劣不同：

| | 百炼 Anthropic | DeepSeek Anthropic |
|---|---|---|
| 协议不变量兜底 | **零**（缺 result、错 id 全部 200 放行） | **有**（一律 400，报错指名道姓） |
| 上下文可重建性 | **完全无状态**，任何历史都能重放 | **服务端按 id 持有推理内容**，凭空构造的历史被拒 |
| 模型目录 | **241 个** | 3 个 |

选百炼的三条理由：

1. **阶段 1 的核心是把主循环、Context 重写、Replay 跑通。** 服务端有状态会在最核心的地方添乱——跨会话、Compact 后重构历史、Replay，这些场景下 id 都不是该端点生成的；
2. **241 个模型是退路。** 阶段 1 还不知道最终要什么模型，现在锁在 3 个上太早；
3. **零兜底反而是开发期的优势。** V03 已拍板「协议不变量 100% 由 Runtime 自持」。用一个什么都不校验的端点开发，能逼出自持逻辑的全部漏洞；用会校验的端点开发，反而可能让人误以为自持逻辑是对的，换端点时才爆。

**DeepSeek Anthropic 形状作为阶段 2 的对照端点**：把 Runtime 产出的请求打到一个真正会校验的端点，是一次免费的正确性测试（§24.6）。

**重新评估的触发条件**【定】：

- 百炼出现稳定的配额或可用性问题；
- 阶段 2 的对照测试显示自持逻辑有系统性缺陷，需要外部兜底兜住；
- 出现必须使用 DeepSeek 独有模型的 Case；
- 端点能力声明的实测结果与本文记录出现重大偏离（§8.7 的漂移检测）。

**这个选择不进主循环。** 它是一份端点能力声明 + 一个形状适配器的组合（§8.7），换端点是配置变更，不是架构变更。

## 1. 文档目的

本文档回答：

1. 主循环的状态、迁移与终止如何显式表达，恢复粒度定在哪一级；
2. 一次模型响应产生多个 Tool Call 时，批的原子性、审批、取消与配对如何成立；
3. **模型上下文中哪些结构不可被上下文治理破坏，以及这个清单从哪来**；
4. Cancel 与 Interject 如何中断长时步骤，中断后配对不变量如何维持；
5. Run 正常完成的判定条件是什么，交付由谁验收；
6. Run 执行期间用户插话如何安放；
7. ToolResult 如何进入 Run 内 Context，大结果如何外置、预览、取回和 Compact；
8. 脱敏发生在哪一个点；**每次模型调用本身就是一次数据外发，边界在哪**；
9. Tool 参数如何解析为可信 EffectScope；
10. 错误如何分类，如何决定重试、模型自纠、等待用户、人工恢复或终止；
11. Cancel、Timeout、Crash Resume、Replay 与外部世界变化分别具有什么语义；
12. Budget、无进展检测、循环检测和优雅停止如何成为 Runtime 不变量；
13. 执行事实与产品聚合跨层时，权威状态归谁；
14. 哪些数据永不删除，哪些可以回收；
15. 在不实现多 Agent 的前提下，如何避免写死单层 Run 假设；
16. **哪些结论是跨端点不变量，哪些只对当前端点成立，以及后者如何被架构表达而不是被硬编码**。

第 16 条是本版新增，也是三轮 Spike 最大的收获。

## 2. V04 核心结论

### 2.1 主架构保持不变【定】

```text
Workspace：资源、授权和工作环境中心
Session：持续交互和意图演进中心
Run：Agent 单次执行、恢复和评测中心
```

```text
Layer 1  WorkAgent UI
    ↓
Layer 2  Application Service / Harness Host
    ↓ immutable snapshot + typed signal/event
Layer 3  Harness Runtime
```

三轮实测**没有推翻任何一条分层结论**。被推翻的全部是「Provider 会怎么表现」这一类假设——它们本来就不该被当成架构不变量，这正是 §8.7 要解决的问题。

### 2.3 只采纳目标、不照搬实现

继承 V03 并确认：

- 不把 JSONPath 作为所有 EffectScope 的唯一提取机制；
- 不把四分类当作完整错误分类学；
- 不引入可绕过不变量的通用 Hook；
- 不用可变 cursor 替代不可变 Conversation Snapshot；
- 不假设 LLM 可靠传播污点标签；
- 不用孤立的 `parentRunId` 冒充 Sub-agent 支持；
- 不引入外部 Agentic UI 协议作为线上协议。

本版新增一条：

- **不把任何一个端点的行为编译进主循环或形状适配器。** 端点行为只能以数据形式存在（§8.7）。理由是实测：第二轮十条结论六条换端点失效。

### 2.4 多 Agent 的当前边界【定】

v0.1 不实现 Sub-agent、并行 Agent 或 Run Group，但禁止写死：Runtime 要求 Run 必须属于 Session；「一个 Session 一个 Foreground Run」是 Layer 3 不变量；Run 的因果来源只绑定 Session Message；Child/Background 执行直接写 Session Transcript；Context/Budget/Capability/Cancel 隐式全量继承。

**继续强调**：「一次模型响应产生多个 Tool Call」不属于多 Agent，四个端点实测全部默认返回 4 个，必须在 v0.1 建模（§8.6）。

### 2.5 规格纪律【定】

1. 任何 Contract 冻结前，必须能指出支撑它的证据来源；
2. 无法指出证据来源的条目标记【验】或【议】；
3. 阶段 1 只实现能被当阶段 Micro Case 覆盖的最小面；
4. 每新增一个 Port，必须同时指出强制它存在的不变量；
5. **【新增】跨端点未经验证的结论一律标记【端点】，且必须写明对哪个端点成立。**

#### 关于事实的保质期

第三轮的教训值得单列：

> **变量隔离做得再干净，结论依然不可移植。**

第二轮的实验设计（同平台、同模型、同 Key，只换形状）非常干净，但十条结论有六条换个模型/平台就不成立。这不是方法论失败，是 Provider 事实的固有属性。

架构层面的三条应对：

1. **端点事实以数据形式存在**（端点能力声明），不编译进代码；
2. **端点能力声明进 RunSpec 冻结**，使 Replay 能重现当时的端点行为；
3. **实际行为与声明不符时 fail fast**，而不是静默继续（§8.7 漂移检测）。

### 2.6 本版规格规模

| 指标 | V03 | V04 |
|---|---|---|
| 逻辑表 | 38（19 + 19） | **35**（22 + 13） |
| Port | 19 | **14** |
| Directive | 16 | **0**（概念删除） |
| Run 不变量 | 17 | **14** |
| Runtime 模块目录 | 18 | **14** |

**本版整体是净收缩。** 两次删除叠加：

**其一，声明式验收机制**（§10.4）。V03 的 `RunAcceptance` 在没有任何运行经验的前提下推演出来，假设「Run 是否完成」需要一套独立判定。标准 Harness 循环里完成条件就是**模型不再请求工具**，再叠一层验收是在解决尚未出现的问题。

**其二，纯 Kernel 与 durable orchestration**（§8.3、§18）。`advance()`、KernelState、16 条 Directive、RuntimeActivity 生命周期、Run Lock、Signal Inbox、Durable Timer、KernelState Snapshot 全部删除，代之以 `while` 循环 ＋ 消息级 transcript 恢复。

删除的表：Layer 3 从 19 张减至 13 张——`run_snapshots`、`runtime_activities`、`runtime_signals`、`durable_timers`、`acceptance_evaluations`、`run_events`、`context_items` 不再需要（详见 §26.2）。

Layer 2 新增三张端点相关表（`endpoints`、`endpoint_capability_profiles`、`endpoint_probe_results`）——**端点能力声明是产品配置，不是执行事实**，这部分不受简化影响。

**唯一保持增长的是端点相关规格。** 这个对比本身说明了问题：**来自实测的规格活下来了，来自推演的规格被删了。**

## 3. 架构原则

原则一至十继承 V03，此处只列有改动与新增的。

### 原则十一：模型协议要素不可被上下文治理破坏【定·改写】

Context Runtime 的裁剪、外置、Compact 与重排，**不得**破坏 Provider 协议要求的结构完整性。

**改写点**：V03 写的是「哪些结构属于此类由 `ModelProtocolPort` 声明」。三轮实测表明这个清单**同时依赖形状和端点**：

- 形状决定**载体**（`thinking` 块 vs `reasoning` item）；
- 端点决定**强度**（可自由丢弃 / 必须留占位块 / 必须逐字回传）。

因此清单的来源必须是**形状适配器 ＋ 端点能力声明**的组合，而不是任一单方（§8.7、§11.5）。

### 原则十二：脱敏发生在离开执行边界的第一个持久化点【定】

未脱敏的原始 Tool 输出、Provider 原始响应和诊断数据，不得离开 Adapter 边界写入任何 Blob、事实表或 Event。

**本版补充**：每次 ModelInvocation **本身就是一次数据外发**（§22.7）。V03 只把脱敏当作「不进 Trace」的手段，现在它还是「不进第三方」的手段，优先级更高。

### 原则十三：证据先于冻结【定】

未经运行证据支持的 Contract 不得冻结。

### 原则十四：端点行为是数据，不是代码【定·新增】

任何「某个 Provider 会怎么表现」的结论，**只能以端点能力声明的形式存在**，不得编译进主循环、Context 模块或形状适配器。

判据很简单：**如果换一个端点这条结论可能变，它就是数据。**

三轮实测里属于「数据」的至少有：协议不变量是否被校验、推理块的约束强度、错误判别式、每请求固定底数、缓存匹配方式、强制单条开关是否生效、配额上限。

这条原则的代价是多一层间接。收益是换端点时改配置而不是改代码——而实测表明换端点会让六成结论失效。

## 8. Harness Runtime 执行模型

### 8.1 内部模块

```text

│   └── interrupt/        ← Cancel（AbortController）与 Interject 队列

│   └── capability/       ← 端点能力声明的消费与校验
├── action/
├── tool-runtime/
├── policy/
├── verification/
├── budget/
├── artifact/
├── trace/

```

**本版删除了 `kernel/`、`coordinator/`、`activity/`、`signals/`、`timer/`、`durability/` 六个模块**，代之以 `loop/` 与 `transcript/`。理由见 §8.3。

### 8.2 Runtime Facade

```ts
interface HarnessRuntime {
  start(spec: RunSpec): AsyncGenerator<RunEvent, Terminal>;
  resume(runId: RunId): AsyncGenerator<RunEvent, Terminal>;
  interject(runId: RunId, input: UserInput): void;
  cancel(runId: RunId, reason?: string): void;
  inspect(runId: RunId): RunSnapshot;

```

**事件通过 generator 直接 yield，不再有独立的 subscribe 通道。** 调用方 `for await` 消费，UI 投影与 Trace 落盘都在这一条流上。

命名区分【定】：`resume()` 从 transcript 重建消息后继续 / `Replay` 调试重放。

**「State Rebuild」与「Unpause」两个概念随 Kernel 一并删除**——前者的对象（KernelState）不存在了，后者退化为「`resume()` 之前不启动循环」。

### 8.3 主循环【定·本版重写】

V03 与 V04 初稿设计了一个纯函数 Kernel（`advance(state, input): KernelTransition`）加 Coordinator durable orchestration。**本版删除整套，回到 `while` 循环。**

#### 循环状态

```ts
// 跨迭代携带的可变状态。每个 continue 站点构造完整的一份。
type LoopState = {
  messages: ContextMessage[];
  turnCount: number;
  consecutiveFailures: number;
  compactTracking: CompactTrackingState | undefined;
  budgetUsage: BudgetUsage;
  maxOutputTokensOverride: number | undefined;
  // 上一次为什么 continue。首次迭代为 undefined。
  // 让测试能断言某条恢复路径确实走了，而不必去翻消息内容。
  transition: Continue | undefined;
};
```

```ts
type Continue =
  | { reason: "NEXT_TURN" }
  | { reason: "COMPACT_RETRY" }
  | { reason: "CONTEXT_OVERFLOW_RECOVERY" }
  | { reason: "OUTPUT_LIMIT_RECOVERY"; attempt: number }
  | { reason: "MODEL_ERROR_RETRY"; attempt: number }
  | { reason: "APPROVAL_RESUMED" }
  | { reason: "INTERJECTION_ACCEPTED" };

type Terminal =
  | { reason: "COMPLETED" }
  | { reason: "COMPLETED_WITH_LIMITS"; incompleteItems: IncompleteItem[] }
  | { reason: "ABORTED_STREAMING" }
  | { reason: "ABORTED_TOOLS" }
  | { reason: "CONTEXT_EXHAUSTED" }
  | { reason: "BUDGET_EXHAUSTED" }
  | { reason: "QUOTA_EXHAUSTED" }
  | { reason: "MODEL_ERROR"; error: RuntimeErrorRecord }
  | { reason: "MAX_TURNS"; turnCount: number };
```

#### 循环骨架

```ts
async function* runLoop(spec: RunSpec): AsyncGenerator<RunEvent, Terminal> {
  let state: LoopState = initialState(spec);

  while (true) {
    const { messages, turnCount, compactTracking } = state;

    // ① 上下文治理：外置大结果 → Compact → 协议校验
    let frame = await compileFrame(messages, spec.endpointProfile);
    if (frame.overBudget) { /* Compact 或 DETERMINISTIC handoff */ }

    // ② 调模型（流式，delta 直接 yield 给 UI，不进 state）
    const { assistantMessages, toolUses } = yield* invokeModel(frame);

    // ③ 模型不再请求工具 → 结算 outcome，退出（§10.4）
    if (toolUses.length === 0) {
      return settleOutcome(state);
    }

    // ④ 执行 ActionBatch：批内每个 call 恰好一个 result（§8.6）
    const toolResults = yield* executeBatch(toolUses, assistantMessages);

    // ⑤ 构造下一轮完整状态，显式写明原因
    state = {
      ...state,
      messages: [...frame.messages, ...assistantMessages, ...toolResults],
      turnCount: turnCount + 1,
      compactTracking,
      transition: { reason: "NEXT_TURN" },
    };
  }
}
```

#### 循环纪律【定】

1. **每个 `continue` 站点必须构造完整的 `LoopState`**，不做零散字段赋值。漏赋一个字段就是一条隐藏的状态泄漏；
2. **每个 `continue` 必须带具名 `transition.reason`；每个 `return` 必须是具名 `Terminal`。** 理由是可测试性：测试断言的是「哪条恢复路径触发了」，不是「消息内容长什么样」；
3. **消息先落盘再进 `messages` 数组**（§8.4）。这是消息级恢复的全部基础——崩溃后 transcript 只可能与内存一致或领先，不可能落后；
4. **流式 delta、进度、心跳不进 `LoopState`**，直接 yield 给消费方；
5. **循环不读取端点能力声明。** 端点差异必须在形状适配器与 Context 层消化完毕，循环只看见规范化结果。否则「换端点」会变成「改主循环」。

第 5 条是**原则十四在新形态下的表达**，与 §8.7 完全无关地保留。删掉 Kernel 不改变端点差异必须被挡在外面这件事——只是挡它的边界从「纯函数」换成了「主循环文件」。

#### 为什么删掉 Kernel

`advance()` 与这个 `while` 循环是同一个循环的两种写法，业务逻辑完全一致。区别只有一处：`advance()` 把「现在走到哪了」放在一个可序列化对象里，`while` 放在调用栈里。

放在可序列化对象里，换来的是 mid-turn 崩溃恢复；代价是纯函数的全套仪式——Directive 中间层、Activity 生命周期、generation 校验、Run Lock、Snapshot 与 hash。

**本版判定这个交换不划算**，理由两条：

1. **恢复粒度选在消息级**（§18），mid-turn 恢复本来就不要了。可序列化 KernelState 的唯一硬收益随之消失；
2. **可测试性可以在 `while` 里拿到大部分。** 具名 `transition` 与具名 `Terminal` 让恢复路径可断言，这是纯函数收益里最实用的一份，而它不需要纯函数。

**代价必须写明**：不变量「批内每个 Tool Call 恰好一个 result」（§10.3 不变量 10）**失去了在纯函数里被穷举测试的可能**，退化为分散在三个中断路径上的手写纪律（§8.6）。选定端点对此零外部兜底，所以这三处是本项目最需要被反复审视的代码。

### 8.4 循环内的一步与持久化【定】

```ts
type StepKind =
  | "CONTEXT_COMPILE" | "COMPACT" | "MODEL_INVOCATION"
  | "TOOL_EXECUTION" | "OBSERVATION" | "VERIFICATION";
```

每一步有超时与取消，但**不再有 durable 生命周期**——没有 PLANNED/STARTED、没有 generation、没有心跳、没有 Run Lock。崩溃时整个循环终止，恢复由 §18 的 transcript 重建承担。

推进协议简化为：

```text
append 消息到 transcript（落盘）
→ 更新内存 messages
→ 执行下一步（Port 调用，signal 传播 cancel）
→ Redact at adapter boundary
→ append 结果消息到 transcript
→ 更新内存 messages，构造 next LoopState
```

【定】取消通过**单个 `AbortController`** 传播，signal 传给所有 Port 调用。中断后**必须为已发出的 tool_use 合成 result**（§8.6）——这是配对不变量在没有状态机时的唯一保障。

【定】Interject 通过**进程内队列**投递，在每轮迭代开始处排空，转为 ContextMessage 进入 `messages`。队列本身不持久化；已排空并落盘的消息才是事实。

### 8.5 ModelInvocation 生命周期

1. 循环进入第 ② 步；
2. **形状适配器**按当前端点的形状构造请求；
3. ModelPort 开始异步流式调用；
4. Delta 直接 yield 给消费方，不进 `LoopState`；
5. **形状适配器**规范化响应，识别全部 Tool Call 与协议要素；
6. **端点能力声明**参与判定哪些块必须保留（§11.5）；
7. 只有完整且协议合法的结果进入 `messages`；
8. 响应消息落盘（transcript）后才更新内存；
9. Usage、耗时、Provider request ID 记入 Trace。

流式中断规则【定】：

- Cancel/timeout 后半截文本默认不进入后续 Context；
- 半截内容脱敏后可外置保存用于诊断，标记 `INTERCEPTED/PARTIAL`；
- **已闭合的块可以保留**（§0.3 的 `:906` 已升【定】），闭合判据由端点能力声明给出；
- 未闭合的 Tool Call 不得转为 ProposedAction；
- UI 可展示「响应已中断」，但不得把半截输出投影为 FINAL Assistant Message。

### 8.6 ActionBatch：一次 ModelInvocation 的多个 Tool Call

#### 实测基础

四个端点**全部**在一次响应中返回 4 个 tool call（`stop_reason=tool_use` / `finish_reason=tool_calls`）。这是默认行为，不是边缘情况。

```ts
interface ActionBatch {
  id: ActionBatchId;
  runId: RunId;
  invocationId: ModelInvocationId;
  actionIds: ActionId[];
  executionMode: "SEQUENTIAL" | "CONCURRENT_LIMITED";
  maxConcurrency?: number;
  approvalMode: "PER_ACTION" | "BATCH_SINGLE";
  batchDigest: string;
  settlement: BatchSettlementPolicy;
  status: "PLANNED" | "IN_PROGRESS" | "SETTLED";
  settledAt?: Timestamp;
}

interface BatchSettlementPolicy {
  onActionFailure: "CONTINUE_REMAINING" | "SKIP_REMAINING" | "ABORT_BATCH";
  onApprovalRejected: "SKIP_REMAINING" | "CONTINUE_REMAINING";
  onCancel: "ABORT_UNSTARTED";
}
```

【定】v0.1 默认值为 `CONTINUE_REMAINING` / `CONTINUE_REMAINING` / `ABORT_UNSTARTED`（D-21）。**任何取值都不影响不变量 2**——它只决定后续 Action 的 result 是真实结果还是 `SKIPPED`。

#### 不变量【定】

1. 一次 ModelInvocation 产出的全部 Tool Call 构成一个 ActionBatch；
2. **批内每个 Tool Call 在返回模型前必须拥有恰好一个协议合法的 result**。成功、失败、被 Policy 拒绝、被用户拒绝、被跳过、被取消——每种终局都必须合成结构化 result；
3. 批未 `SETTLED` 前不得发起下一次 ModelInvocation；
4. 批内每个 Action 独立经过 Effect Resolution、Capability 三层校验与 Policy 判定；
5. `approvalMode = BATCH_SINGLE` 时，`batchDigest` 任一变化即失效；
6. 批内 EXCLUSIVE / KEYED lease 冲突时，冲突子集自动降级为串行；
7. Cancel 落在批中间时：已完成 Action 事实保留，未启动 Action 标记 `SKIPPED` 并合成 result；
8. `decisionStep` 按批计一次（§16.5）。

#### 不变量 2 的理据【改写】

V03 隐含的理据是「否则 Provider 会 400」。**在选定端点上这是错的**：

| 负向实验 | 百炼(Anthropic) | DeepSeek(Anthropic) |
|---|---|---|
| 缺 3 个 tool_result | **200 接受** | 400 |
| tool_call_id 篡改 | **200 接受** | 400 |

因此理据必须改为：

> **否则模型看到的是一个失真的世界**——它会以为某个工具没被调用过，或者把 A 的结果当成 B 的。

同理 §12.5 的 `toolCallId` 锚点，在选定端点上是 Runtime 的自我约定，**无外部校验**。

**这不降低不变量的重要性，反而提高了**：没有任何外部兜底会替你发现违反。

#### v0.1 执行模式【定】

`executionMode = SEQUENTIAL`、`approvalMode = PER_ACTION`。

**这是 D-01 的拍板结果，理据是 Runtime 自持。** 实测（每档 3 次采样）：

| 端点 | 参数 | 缺省 | 显式关闭 | 判定 |
|---|---|---|---|---|
| 百炼(OpenAI) | `parallel_tool_calls:false` | 4/4/4 | **1/1/1** | 生效 |
| **百炼(Anthropic)** | `disable_parallel_tool_use` | 4/4/4 | **4/4/4** | **静默接受，完全无效** |
| DeepSeek(OpenAI) | `parallel_tool_calls:false` | 4/4/4 | 4/4/4 | 静默接受，无效 |
| DeepSeek(Anthropic) | `disable_parallel_tool_use` | 4/4/4 | 4/4/4 | 静默接受，无效 |

【端点·四格均成立】**四个端点全部静默接受该参数，其中三个不生效，没有任何一个会告诉你「我不支持」。**

【定】批内串行**必须由 Runtime 自己保证**。协议开关只是可有可无的加成，**不得作为设计前提**——把它当保障会在换端点时静默失效，而且因为参数被接受，连报错都没有。

### 8.7 端点能力声明【新增·D-07 的落地形态】

#### 问题

第三轮把第二轮的十条结论重测了一遍，**六条只在原来那个端点上成立**。这些结论包括「协议是否被校验」「推理块能否丢弃」「错误怎么分类」「缓存怎么匹配」——全都是 Context 层与错误处置层每天都要用的东西。

如果它们以 `if (provider === 'x')` 的形式散落在代码里，换端点就是一次全局重构。

#### D-07 的答案

> **形状决定「协议长什么样」，平台决定「协议被执行到什么程度」，端点决定「具体数值」。**

按因子归类三轮全部差异：

| 差异 | 归因 |
|---|---|
| 有无 token 预估端点 / 流式闭合事件 / `is_error` 带外字段；推理块载体形态 | **形状** |
| 协议不变量是否被校验；tool 定义 schema 是否被校验；推理块是否服务端有状态 | **平台** |
| 错误判别式；强制单条开关是否生效；每请求固定底数；缓存匹配方式 | **端点** |
| tool 定义开销、计费口径、入参不校验 | **模型/共性** |

因此：

> `ModelProtocolPort` 按 **API 形状**切分适配器——它管解析与构造。
> **校验强度、有状态性、错误判别式、各项常量做成端点级能力声明**，不编译进适配器。
>
> 两者生命周期完全不同：适配器随 SDK 版本变，声明**随时可能在没有任何通知的情况下变**。

#### 模型

2. **Run 启动时冻结进 RunSpec**（§7.7）。Replay 使用冻结版本，不使用当前配置；
3. **`confidence` 必须如实标注。** `ASSUMED` 的字段在被依赖时应产生 SYSTEM_NOTICE；

5. **声明的粒度是端点 × 模型**，不是平台，也不是形状。实测表明同平台两形状可以在缓存、校验、错误判别式上完全不同；

- `honorsDisableParallelToolCalls: false` 却收到单条 → 记录，不失败；
- `validatesToolResultPairing: false` 却收到配对相关 400 → **fail fast**，说明声明过期；
- `countTokensAccuracy: "EXACT"` 却出现非零偏差 → 记录偏差分布，超阈值告警。

完整的漂移检测策略待阶段 2 设计。

## 9. 中断与用户输入

> **本章随主循环改写大幅简化。** V04 初稿的 Durable Signal Inbox（持久化投递、全局幂等、优先级队列、离线消费）服务的是「Runtime 不在线时信号也不丢」这个需求。消息级恢复下这个需求不存在：进程死了 Run 就结束，恢复时读 transcript 重来。

### 9.1 三种中断，三种机制【定】

| 中断 | 机制 | 生效时机 |
|---|---|---|
| **Cancel** | 单个 `AbortController`，signal 传给所有 Port | 立即，协作式 |
| **Interject** | 进程内队列 | 每轮迭代开始处排空 |
| **Approval 决策** | `canUseTool` 回调的 `await` | Action 执行前 |

三者都**不持久化**。已排空并落盘为消息的才是事实，队列里的不是。

**Pause / Unpause 作为独立状态删除。** 产品能力保留，实现为 `cancel()` ＋ 稍后 `resume()`——消息级恢复下两者行为一致，多一个状态只多一份状态迁移表。

### 9.2 Cancel 的处置【定】

```text
cancel() → AbortController.abort()
→ Port 协作式停止
→ 为已发出但无 result 的 tool_use 合成中断 result（§8.6）
→ 落盘
→ return Terminal { reason: "ABORTED_STREAMING" | "ABORTED_TOOLS" }
```

【定】副作用无法确认时，合成的 result 必须标记为**状态未知**而非失败，并写入 `recoveryItems`。迟到的成功结果不得把已终止的 Run 拉回运行态，但必须作为诊断事实落盘。

**合成 result 这一步是配对不变量的唯一保障点。** 三条中断路径（流式中断、工具执行中断、模型错误）各需要一遍，缺任何一条都会在 transcript 里留下无 result 的 tool_use，下次 `resume()` 时发给模型就是一个失真的世界——而选定端点会 200 放行（§8.6）。

### 9.3 执行期间的用户输入

```ts
interface WaitRequest {
  id: WaitRequestId;
  runId: RunId;
  prompt: string;
  inputSchema?: JsonSchema;
  mode: "SINGLE" | "ACCUMULATE_UNTIL_SUBMIT";
  expiresAt?: Timestamp;
  status: "OPEN" | "FULFILLED" | "EXPIRED" | "CANCELLED";

interface InterjectSignal {

}
```

插话语义【定】：排空后成为 `USER_MESSAGE` ContextItem（`trust = USER_PROVIDED`）并落盘；不解除任何等待；`NEXT_SAFE_POINT` 时在当前步骤完成后进入下一轮迭代重新决策；必须在 Transcript 可见且与「启动新 Run 的消息」视觉可区分；**不得创建 Grant、改变 Policy、批准 Action**；计入 Budget。

Layer 2 路由表【定】：

| 当前 Run 状态 | 输入去向 |
|---|---|
| `RUNNING` | 进 Interject 队列 |

| `RECOVERY_REQUIRED` | 恢复决策；其余进 Interject 队列 |
| Terminal | 创建新 follow-up Run |

**表从五列七行收缩为两列五行**，因为不再需要 `targetRequestId` 与 `expectedRunRevision` 做跨进程匹配——等待就是一个 `await`，匹配它的输入直接 resolve 那个 Promise。

## 10. Run 领域模型与状态机

### 10.1 RunStatus 与 RunOutcome

```ts
type RunStatus =
  | "CREATED" | "RUNNING"
  | "WAITING_FOR_USER" | "WAITING_FOR_APPROVAL" | "WAITING_FOR_INTERACTION"
  | "RECOVERY_REQUIRED"
  | "COMPLETED" | "FAILED" | "CANCELLED";
```

【定】终态性：**非终态** `CREATED` / `RUNNING` / `WAITING_FOR_*` / `RECOVERY_REQUIRED`；**终态** `COMPLETED` / `FAILED` / `CANCELLED`。

**`PAUSED` 已删除**（§9.1）——消息级恢复下它与「`cancel()` 后稍后 `resume()`」行为一致。

`WAITING_FOR_*` 在新形态下不是「循环停下来等一个 durable request」，而是**循环阻塞在一个 `await` 上**。状态值保留是给 Layer 2 与 UI 用的，不再驱动调度。`RECOVERY_REQUIRED` 是 `resume()` 时发现 transcript 里存在无 result 的 tool_use、且副作用状态未知时进入的状态。

**新增 `QUOTA_EXHAUSTED`**：实测发现配额可能先于上下文窗口撞墙（§16.6），它与 `CONTEXT_EXHAUSTED` 的处置完全不同——前者等一会儿可能就好了，后者必须压缩。

### 10.3 Run 不变量【定】

1. 一个 Run 绑定一个不可变 RunSpec；
2. 配置变化需要创建新 Run；
3. 每个外部副作用关联 Action 和 Attempt；
4. **一个 Run 同时只有一个循环在跑**；
5. **消息先落盘再进内存 `messages`**（§8.4）——transcript 只可能与内存一致或领先；
6. 每次 ModelInvocation 前必须形成通过协议校验的 ContextFrame；
7. 上一批 Tool Call 全部有 result 之前不得发起新的 ModelInvocation；
8. **批内每个 Tool Call 必须有且只有一个 result**；
9. 每次 Action 执行前必须具有 ResolvedEffect、Capability Evidence 和实时 Lease；
10. 未知副作用状态不得自动重试；
11. Budget hard limit、Cancel 和 revoked Capability 不得由模型决定忽略；
12. Run 进入 `COMPLETED` 前必须结算一次 `outcome.kind`，且结算依据必须来自事实表（§10.4）；
13. 未脱敏内容不得写入 transcript 或任何持久化存储；
14. Run 执行期间使用的端点能力声明必须与 RunSpec 冻结的一致；不一致时产生漂移事件并按策略处置（§8.7）。

**从 17 条减至 14 条。** 删除的四条（durable transition 单一提交者、Activity generation 匹配、单调 sequence 的 Durable Event、等待关联可寻址 Request）全部是 durable orchestration 的约束，随 Coordinator 一起消失。新增的第 5 条是消息级恢复的核心约束。

不变量 7 与 8 的**执行方式变了但内容没变**：V04 初稿由 Kernel 在纯函数里保证，本版由循环结构保证（第 ④ 步不结束就到不了第 ⑤ 步）加三处中断路径的合成 result（§9.2）。**保证强度下降了**——这是 §8.3 末尾写明的代价。

### 10.4 Run 完成判定

#### 循环终止规则【定·本版简化】

```text
ModelInvocation 完成
    ↓
响应中是否包含 Tool Call？
    ├── 是 → 执行 ActionBatch（§8.6），构造下一个 LoopState，continue
    └── 否 → return settleOutcome(state)
                ↓
        结算 outcome.kind（只查事实表，不再调用模型）
        ├── 存在未决 RecoveryItem          → RECOVERY_REQUIRED（非终态）
        ├── 存在失败的 required Verification → COMPLETED_WITH_LIMITS + incompleteItems
        └── 其余                            → COMPLETED / SUCCESS
```

**模型不再请求工具即完成。** 这是标准 Harness 循环的做法，本版从 V03 的声明式验收机制回退到它。

#### 为什么删掉 `RunAcceptance`【定】

V03 设计了 `RunAcceptance`（`mode` × `criteria[]` × `requireDeliverablesVerified`），假设「Run 是否完成」需要一套独立于模型判断的声明式判定。本版删除整套机制，理由三条：

1. **它要求在发出第一个 token 之前就知道「什么算做完」，而这个信息不存在。** 用户说「把这三篇文章归档」，`minCount: 3` 里的 `3` 只存在于自然语言里。要把它变成结构化 criterion，只能在 Run 创建前先调一次模型——那次调用不属于任何 Run，没有 budget 归属、没有失败处置、没有状态机；
2. **它解决的问题已被其他机制覆盖。** 副作用状态未知由 `RECOVERY_REQUIRED` 这个独立非终态处理（§10.1 状态机、§10.5），它先于完成判定生效，不需要一条 criterion 去表达；Eval 的成败判定由 `eval/graders/` 独立实现（§24），本来就不复用生产 Run 的判定路径；
3. **单人使用场景下，人在回路里。** 用户本人在屏幕前，看一眼输出就知道行不行。为一个随时能亲自判断的东西建一套声明式机制，投入产出比是反的。

#### 保留的一条底线【定】

结算 `outcome.kind` 时**必须查一次 required Verification 的结果**。

这条与「信不信模型」无关：Verification 已经跑过、扣了 token、结果已经写进 `verifications` 表。如果结算时忽略它，等于**花钱测出一个事实然后扔掉**。

典型场景：工具报错，模型在总结里写「已完成，其中一项遇到问题但已跳过」，然后不再调用工具。此时 Run 应结算为 `COMPLETED_WITH_LIMITS` 并把失败项写进 `incompleteItems`，而不是 `SUCCESS`。

全部实现约十行：

```ts
const failed = verifications.filter(v => v.required && v.status === "FAILED");
return failed.length === 0
  ? { kind: "SUCCESS" }
  : { kind: "COMPLETED_WITH_LIMITS", incompleteItems: failed.map(toIncompleteItem) };
```

**注意这不改变循环何时终止**，只改变终止后打什么标签。终止条件仍然严格是「模型不再请求工具」。

#### 两层 Verification 的关系【定】

| 层 | 问题 | 触发点 |
|---|---|---|
| Action 级 Verification | 这一步的副作用是否达成 | Attempt 完成后 |
| Artifact 级 Verification | 这个产物本身是否完整合法 | ArtifactRegistered 之后 |

两者不得互相替代。V03 的第三层「Run 级 Acceptance」已删除——**Run 层不再提出自己的问题，只汇总前两层已经产生的事实。**

#### 什么情况下需要把它加回来【验】

不排除将来需要，但必须由证据触发，而不是由推演触发。可能的触发条件：

- 出现无人值守运行（定时任务、自动化触发），此时没有人在回路里看输出；
- Eval 发现「模型声称完成但实际未完成」的比例高到无法靠人工发现；
- 某个 Case 的交付物有明确、静态、与用户输入无关的结构约束（此时 criterion 可以完全来自 Case Package，不需要解析自然语言）。

加回来的形态应当是**在 Case Package 里注册的检查器**，而不是 RunSpec 上的必填字段——因为它逐 Case 变化，不逐 Run 变化。

### 10.5 Cancel 后事实处置【定】

已完成的 Action、Attempt、Event 和 Audit 不删除；已登记 Artifact 保留 lineage 并按验证结果标记；未完成的临时资源按 cleanup/compensation policy 处理；自动 Compensation 必须是新的显式 Action；副作用未知时进入 `RECOVERY_REQUIRED` 或带 `recoveryItems` 的 CANCELLED；用户可见结果必须明确区分**已完成**、**未完成**和**状态未知**三部分。

### 11.5 Provider 协议要素不变量【改写】

#### 不变量【定】

1. 属于同一 `protocolGroupId` 的 ContextItem 构成**不可拆分单元**；
2. `REQUIRED_VERBATIM` 的项不得被改写、摘要、截断或重排；
3. **`PLACEHOLDER_REQUIRED` 的项内容可替换，但块本身不得消失**；
4. 一个模型 Tool Call 与其 result 属于同一 protocolGroup；批内每个 call 必须有恰好一个 result；
5. Pair 过大时外置 result 正文，但保留协议合法的结构化 stub；
6. **哪些结构属于哪一档，由「形状适配器 ＋ 端点能力声明」共同给出**，不由 Context 模块猜测；
7. ContextFrame 构建后必须执行 `validateFrame()`，失败不得发起模型调用。

#### 实测清单

| 项目 | 百炼 Anthropic【端点】 | 跨端点情况 |
|---|---|---|
| 推理块可否删除 | **可** | DeepSeek 需占位块 |
| 推理块可否改写 | **可** | 同上 |
| `signature` 可否删除 | **可**（本就是空串） | — |
| 较早轮次推理块可否删 | **可** | DeepSeek 依赖服务端 id |
| tool_result 顺序 | 组间无序要求 | 四端点一致 |
| 闭合事件 | **有 `content_block_stop`** | OpenAI 形状无 |

【端点】**在选定端点上 `reasoningBlockRule = DROPPABLE`，`irreducibleTokens` 只需覆盖配对组。**

但 Contract 必须能表达另外两档——因为这正是三轮实测中变化最剧烈的一项。

### 11.8 缓存：从倾向升级为可估价规则【改写】

#### 实测

第二轮在 qwen3.7-plus 上测到「缓存不可预期」；第三轮换 `deepseek-v4-flash` 后，四个端点基线**全部 4/4 稳定命中**（4096–4864 tokens，约 98%）。

第三轮新增一个关键对照条件——**只改前缀第一处** vs **全量改写**：

| 端点 | 基线 | 只改第一处 | 全量改写 | 判定 |
|---|---|---|---|---|
| **百炼(Anthropic)** | 4096 ×4 | **0** | 0 | **严格前缀，全量失效** |
| 百炼(OpenAI) | 4096/4864 ×4 | 0 | 0 | 严格前缀 |
| DeepSeek(Anthropic) | 4864 ×4 | **384** | 384 | 严格前缀，回落到公共前缀 |
| DeepSeek(OpenAI) | 4864 ×4 | 4864 | 4864 | **未判定** |

DeepSeek(Anthropic) 的 384 不是噪声——它恰好等于独立测得的 tools + system 固定前缀。

#### 结论【定】

> **Compact 重写中部的代价 ∝ 改写点有多靠前。** 改写点之后的缓存全丢，之前的保留。

这把「追加式外置优于重写式压缩」从一句倾向变成了**可估价规则**：

- 把大结果移到尾部并留引用（不动前缀）→ 缓存全保住；
- 重写中部 → 损失改写点之后的全部命中，损失量可由 `count_tokens` 精确预估。

`CACHE_BREAKPOINT` 的价值因此明确：**标记「此处之前不得改写」**，Compact 优先在断点之后动刀。

`:1594`【验】**在三个端点上升【定】**（严格前缀匹配，基线稳定）。

【端点】DeepSeek(OpenAI) 形状全量改写前缀后仍报满额命中，与任何基于内容的缓存都不相容。**在查清之前，不得用该端点的 `cached_tokens` 做成本核算。**

#### 未解答

缓存 TTL（需间隔重跑）；`cacheMatching = "UNKNOWN"` 时的保守策略。

支持 preview 的 Tool 在 APPLY 前生成确定性 Plan、Diff、目标列表或外发摘要。【定】Preview 本身不得执行声明之外的副作用；APPLY 前重新校验 precondition fingerprint；actionDigest 改变必须重新 preview / policy / approval；不支持 preview 的 Tool 必须显式声明。

### 12.8 Capability 并发与 Lease

```ts
type LeaseStatus = "HELD" | "PARKED" | "RELEASED" | "EXPIRED";

interface CapabilityLease {
  id: LeaseId;
  capabilityBindingId: CapabilityBindingId;
  concurrencyKey?: string;
  ownerRunId: RunId;
  parkedForInteractionId?: InteractionRequestId;
```

【定】Browser Session、交互式终端使用 EXCLUSIVE/KEYED lease；Crash 后通过过期释放，不依赖进程内引用计数；`PARKED` 用于人工接管期间（§20.3），绑定 `parkedForInteractionId`，其他 Run 不可获取。

**过期判定改为惰性**：获取 lease 时比对 `expiresAt`，不再需要独立定时器（§18.6）。单进程下持有者死亡即进程死亡，lease 靠过期自然释放。

#### 新增 `MODEL_SDK` 的实测依据

`max_tokens: 99999999` 被 Anthropic SDK **自己拦截**（提示需要流式），根本没发出请求。

V03 的 `source` 枚举无法表达「错误来自 SDK 而非 Provider」，这类错误会被误归类为 `MODEL_PROVIDER`——进而影响 retryability 判断（SDK 层的参数校验错误重试多少次都没用）。

#### 新增 `QUOTA` 的实测依据

见 §16.6。配额与 rate limit 的处置不同：前者可能需要等很久或换端点，后者退避重试即可。

### 13.2 判别式按端点维护【改写】

四个端点的错误判别式**没有任何两个可以共用一张表**：

| 触发 | 百炼(Anthropic)【选定】 | 百炼(OpenAI) | DeepSeek(两形状) |
|---|---|---|---|
| 无效模型名 | 400，无 type/code | **404 / `model_not_found`** | 400 / `invalid_request_error` |
| 无效 API Key | 401，无 type/code | 401 / `invalid_api_key` | 401 / `invalid_request_error` |
| 请求体格式错 | 400，无 type/code | 400 / `invalid_parameter_error` | 400 / `invalid_request_error` |
| tool 定义 schema 非法 | **200 接受** | **200 接受** | **400 ＋ 精确诊断** |
| 缺 `max_tokens` | 400 | — | **200 接受** |

【端点·百炼 Anthropic】**连 `type` / `code` 字段都没有**，message 也最简短（`Model not exist.`）。判别式只能是 `HTTP_STATUS + MESSAGE_MATCH`。

【定】`ErrorTaxonomyProfile.discriminators` 与 `mappingRulesRef` 是端点能力声明的一部分（§8.7）。**映射表按端点维护，不按形状也不按平台。**

### 13.3 ErrorDisposition

```ts
type ErrorDisposition =
  | "RETRY_AUTOMATICALLY" | "RETURN_TO_MODEL" | "SKIP_REMAINING_BATCH"
  | "WAIT_FOR_USER" | "WAIT_FOR_RECOVERY" | "DEGRADE"
  | "FAIL_RUN" | "CANCEL_RUN";
```

【定】Disposition 由 Tool Contract、ErrorRecord、Attempt 历史、Batch Settlement Policy、Budget 和 Idempotency 共同计算。

### 13.4 自动重试规则【定】

只有同时满足才可自动重试：retryPolicy 允许；retryability 允许；未超过 attempt / wall-clock / budget 限制；`sideEffectState` 为 `NOT_STARTED` / `NO_EFFECT` 或幂等键证明安全；Capability 与 preconditions 仍有效；Cancel/Pause 未待处理。

`UNKNOWN`、`PARTIALLY_APPLIED` 默认进入 Observation、Recovery 或人工处理。

### 13.5 返回模型的错误

结构化、脱敏的 Tool Result，包含稳定错误 code、哪些字段不合法、允许的修正方向、已执行副作用状态、是否允许再次调用。【定】内部堆栈、凭证、绝对敏感路径和 Provider 私密响应不得进入模型。

## 16. Budget、进展与优雅停止

### 16.1 RunBudgets

```ts
interface RunBudgets {
  maxDecisionSteps: number;
  maxActiveWallClockMs: number;
  maxTotalWallClockMs?: number;
  maxModelCalls?: number;
  maxToolCalls?: number;
  maxInputTokens?: number;
  maxOutputTokens?: number;
  maxEstimatedCost?: Money;
  maxConsecutiveFailures: number;
  maxCompletionAttempts: number;
  softLimitRatio: number;
  handoffReserve?: HandoffReserve;
}
```

【定】墙钟拆分：`maxActiveWallClockMs` 只累计 `RUNNING` 且有在途步骤的时间；`WAITING_*` / `RECOVERY_REQUIRED` 不累计。

#### 新增预算轴：固定开销【实测】

实测四个端点：

| 项 | 数值 |
|---|---|
| **tool 定义固定开销** | **360 tokens**（2 个只有一个字符串参数的工具，四端点一致，百炼 OpenAI 测得 361） |
| **每请求固定底数** | 百炼 **5** tokens；DeepSeek **84** tokens（**差 17 倍**） |

折合每工具约 180 token。**20 个工具就是约 3600 token 的起步价，与任务内容无关。**

【定】`ContextFrame.fixedOverheadTokens` 单列，§11.6 的阈值判断必须先扣除它，否则「还剩多少上下文可用」算错。

【端点】每请求固定底数是**端点属性**，同一个模型换平台就变，进端点能力声明的 `tokens.perRequestBaseTokens`。

#### `reservedOutputTokens` 必须覆盖推理【实测】

```
max_completion_tokens: 64
finish_reason: "length"
content: ""                          ← 正文为空
completion_tokens_details.reasoning_tokens: 64   ← 预算全被推理吃掉
```

在两个独立探针中复现。**接口成功、无错误码、内容为空。**

【定】两处约束：

1. `reservedOutputTokens` 必须**同时覆盖推理与正文**；
2. 主循环消费 `ModelInvocationResult` 时，把「`finish_reason=length` 且无内容且无 tool call」识别为明确错误条件（`source: MODEL_PROVIDER, category: CAPACITY`），**而不是正常完成**。

否则 Runtime 会把空回复当作模型的正常回答继续推进，产生一次静默的错误决策。

### 16.2 Progress Guard

至少检查：轮次数与连续失败；相同 Tool + normalized input + effect digest 连续重复；多个不同调用但状态无变化；相同错误和相同模型修正循环；Compact 后仍无法满足窗口；**长时间没有进展证据**。

```ts
interface ProgressReportingDescriptor {
  mode: "NONE" | "HEARTBEAT" | "MONOTONIC_PROGRESS";
  intervalMs?: number;
}
```

【定】声明 `HEARTBEAT` / `MONOTONIC_PROGRESS` 的长时 Tool 必须周期性回报进展（低频，30s 量级）。Progress Guard 基于这个回报判定「还活着」，**不基于流式 delta**——否则长媒体下载会被误判无进展。

**进展回报不再需要持久化。** 它只服务进程内的 Progress Guard 与 UI；进程死了 Run 就结束，没有「恢复后判断上次进展到哪」这个需求。

### 16.3 Soft 与 Hard Limit【定】

Soft limit：阻止启动普通新步骤，可用预留预算生成 handoff、请求用户缩小范围或交付部分结果。
Hard limit：不得再调用模型或有副作用 Tool，立即形成稳定 Outcome。
没有 handoff reserve 时不得为「优雅总结」突破 hard limit。

### 16.4 两类 Handoff【定】

```ts
type HandoffKind = "MODEL_AUTHORED" | "DETERMINISTIC";
```

| 类型 | 触发 | 生成方式 |
|---|---|---|
| `MODEL_AUTHORED` | Budget soft limit | 用 `handoffReserve` 发起受限模型调用 |
| `DETERMINISTIC` | Context hard limit、模型不可用、配额耗尽 | 由模板从 durable facts 生成，**不经模型** |

`DETERMINISTIC` handoff 的内容全部来自事实表：已完成 Action、已注册 Artifact 及验证状态、失败的 required Verification、`incompleteItems`、`recoveryItems`、错误摘要。

**注意 `DETERMINISTIC` handoff 恰好是「模型不再请求工具」这个信号缺席的场景**——Context 撞墙、模型不可用、配额耗尽时，模型没有机会说完成。此时 outcome 由 §16.1 的墙决定（`CONTEXT_EXHAUSTED` / `QUOTA_EXHAUSTED` / `BUDGET_EXHAUSTED`），不走 §10.4 的循环终止路径，handoff 负责把「做到哪了」讲清楚。

### 16.5 计数口径【定】

**decisionStep** = 一次成功完成的 ModelInvocation，无论其后产生 0 个还是 N 个 Action。ContextFrame 编译、Compact、Observation、Verification 不计入，各有独立上限。失败后重试的 ModelInvocation 计入。

**consecutiveFailures** 归零条件：任一 Action 执行成功且其 required Verification 通过。Context 编译失败、Compact 失败不计入；模型协议错误计入；被 Policy/用户拒绝的 Action 不计入失败。

### 16.6 配额可能先于上下文窗口撞墙【新增·实测】

【端点】百炼的 **OpenAI 形状**对 60 万 token 的单请求稳定返回 `429 insufficient_quota`；同平台的 **Anthropic 形状接受同一个 payload**。

这是 V03 完全没有的运行现实：

> **在长上下文场景下，配额是先于上下文窗口撞上的那堵墙。**

【定】三条应对：

1. `EndpointLimits.quotaBeforeContextLimit` 进端点能力声明；
2. `category: QUOTA` 与 `RATE_LIMIT` 分开——前者可能需要等很久或换端点，后者退避重试即可；
3. `RunOutcome.kind` 新增 `QUOTA_EXHAUSTED`，与 `CONTEXT_EXHAUSTED` 区分：后者必须压缩上下文，前者压缩没用。

**选定端点的 `quotaBeforeContextLimit = false`**，但这一条随时可能变——它取决于账号配额而非协议。

## 18. 持久化、Resume 与 Replay

> **本章随主循环改写重定级。** V04 初稿设计的是 mid-turn durable execution：12 个 crash 窗口、每个窗口一条恢复分支、Snapshot ＋ Event 双轨重建。本版把恢复粒度定在**消息级**，整章随之收缩。

### 18.1 恢复粒度的选择【定】

```text
transcript（消息级 append-only 日志） + immutable Blob
```

**恢复的唯一来源是 transcript。** 没有 KernelState Snapshot，没有 Event 重放重建，没有 generation 校验。

`resume(runId)` = 读该 Run 的 transcript → 重建 `messages` 数组 → 从下一轮迭代继续。

**代价必须写明**：**崩溃时正在执行的工具，那次执行丢失。** 恢复后从上一条已落盘的消息边界重来——如果那个工具做了非幂等的写，它会被执行第二次。

这不是疏漏，是本版明确选择的权衡。理由：单人使用、单进程、绝大多数工具幂等或可验证；换取的是整章从 12 条恢复分支缩到 3 条。

### 18.2 剩下的三个 crash 窗口

消息级恢复把 12 个窗口合并成 3 个，因为「消息是否落盘」是唯一的一致性边界：

| 窗口 | 现象 | 处置 |
|---|---|---|
| **A** | 模型响应已落盘，工具尚未执行完 | transcript 里有 tool_use 无 result |
| **B** | 工具已执行，result 未落盘 | 同上——盘上看不出区别 |
| **C** | Blob 已写入但引用消息未落盘 | 孤儿 Blob，由 GC 清理 |

**A 与 B 在 transcript 上无法区分**，这正是消息级恢复的本质限制：**你不知道那个工具到底跑没跑。**

因此 `resume()` 的处置规则【定】：

```text
transcript 末尾存在无 result 的 tool_use
    ├── 该 Tool 声明为幂等或只读 → 合成中断 result，重新执行
    ├── 该 Tool 有可用的 Observation → 先观察外部世界，据结果决定
    └── 其余（非幂等、无法观察）    → RECOVERY_REQUIRED，交用户决定
```

【定】未知副作用状态不得自动重试（不变量 10）。第三条分支是这条不变量在消息级恢复下的落点——**Tool 是否声明幂等，从一个可选属性变成了恢复正确性的前提**。

### 18.3 外部世界重新校验【定】

`resume()` 时必须检查：Capability Binding 是否撤销或降级；Grant / Secret / Browser Session / Lease 是否过期；输入 Resource contentHash 是否变化；Action target fingerprint 是否变化；Artifact 或外部对象是否被用户修改；Verification 结果是否已过 `staleAfterMs`；**端点能力声明是否仍与 RunSpec 冻结的一致**（§10.3 不变量 14）。

**这一节完全不受简化影响。** 恢复粒度变粗只改变「从哪继续」，不改变「继续之前世界可能已经变了」——`resume()` 之间的间隔反而可能更长。

```text
unchanged                      → continue
changed but safely resolvable  → re-resolve / re-observe / re-prepare
effect or digest changed       → policy + approval again
endpoint profile drifted       → 按 §8.7 漂移策略处置
requires user choice           → WAITING_FOR_USER / RECOVERY_REQUIRED
cannot establish safe state    → fail or cancel with recovery report
```

### 18.4 Resume 与 Replay 的区别【定】

四个概念收缩为两个。

**Resume**：继续同一个非 Terminal Run，保留 RunId、RunSpec、已完成副作用和预算使用。从 transcript 重建 `messages`，按 §18.2 处置末尾的未配对 tool_use。

**Replay**：为调试或 Eval 创建隔离的重放执行。使用 RecordedModelPort / RecordedToolHandlerPort；默认不触发真实副作用；从 transcript 的任意消息位置开始；产生新的 replay identity，引用原 Run 但不改写；区分 exact recorded replay 与 live rerun；**live rerun 必须创建新 RunSpec/Run，并重新经过 Capability 和 Policy**。

**已删除的两个**：`State Rebuild`（对象是 KernelState，不存在了）、`Unpause`（PAUSED 状态已删，见 §9.1）。

**【定】Replay 使用 RunSpec 冻结的端点能力声明，不使用当前配置。** 这是 §7.7 冻结 `endpointProfile` 的直接理由：三个月后重放一个旧 Run，如果用今天的端点行为去判断当时的帧是否合法，结论没有意义。

**Replay 反而变简单了。** 它的起点从「某个 Event sequence ＋ 对应 Snapshot」变成「transcript 的第 N 条消息」——一个人能直接看懂的位置。

### 18.5 transcript 格式

```ts
interface TranscriptEntry {
  runId: RunId;
  sequence: number;              // 单调递增，同一 Run 内唯一
  schemaVersion: number;
  kind: "MESSAGE" | "COMPACT_BOUNDARY" | "BLOB_REF" | "RUN_META";
  message?: ContextMessage;      // 已脱敏
  createdAt: Timestamp;
}
```

【定】append-only，每行一个 JSON。**只追加，不改写**——Compact 通过写入 `COMPACT_BOUNDARY` 表达，重建时从最后一个 boundary 之后开始取，boundary 之前的原文保留供 Trace 与 Replay 使用。

【定】`schemaVersion` 不兼容时，重建器必须能跳过或 upcast 单条，而不是整个 transcript 失效。**这是 Snapshot 方案换成日志方案后最实在的一个收益**：Snapshot 是全有或全无，日志可以逐条降级。

### 18.6 等待与超时

**Durable Timer 整套删除。**

在单进程循环里，等待就是 `await`：Approval 等待是 `await canUseTool(...)`，工具超时是 `AbortSignal.timeout()`，墙钟预算是循环里比一个时间戳。进程死了，所有等待一起死——这与「进程死了 Run 就结束」是一致的。

| 原 Timer kind | 新形态 |
|---|---|
| `APPROVAL_EXPIRY` / `WAIT_EXPIRY` / `INTERACTION_EXPIRY` | `await` ＋ `AbortSignal.timeout()` |
| `ACTIVITY_TIMEOUT` | 每步的 signal timeout（§8.4） |
| `ACTIVE_WALL_CLOCK` | 循环内比对时间戳（§16.1） |
| `LEASE_EXPIRY` / `OBSERVATION_STALE` | `resume()` 时重新校验（§18.3） |

**【议】D-08 随之取消**——「真定时器 vs 惰性判定」这个问题的前提是存在跨进程的定时需求，而这个前提没有了。§30.4 早已把 D-08 标为「前提未经验证，建议推迟」，现在可以直接划掉。

## 19. Event、Trace、Audit 与 Usage

### 19.1 Runtime Event Envelope

```ts
interface RunEvent {
  schemaVersion: number;
  type: string;
  runId: RunId;
  sequence: number;          // 与 transcript 同一条序列（§18.5）
  batchId?: ActionBatchId;
  actionId?: ActionId;
  occurredAt: Timestamp;
  payload: JsonValue;
}
```

**Event 不再是独立的持久化轨道。** V04 初稿有事实表、Durable Event、Snapshot 三条轨道互相校验；本版只有 transcript 一条。Event 从 generator yield 给消费方（§8.2），由 Trace 侧自行落盘用于诊断，**恢复不读它**。

`eventId` / `correlationId` / `causationId` / `directiveId` / `activityId` 随之删除——它们服务的是「从事件重建状态」与「跨 Activity 追因果」，两个需求都没有了。

### 19.2 事件清单

Run 生命周期：RunStarted / StatusChanged / Completed / Failed / Cancelled。
循环迁移：**TurnStarted / LoopContinued（带 `transition.reason`）/ LoopTerminated（带 `Terminal.reason`）**。
模型与批：ModelInvocationCompleted / ActionBatchPlanned / ActionBatchSettled。
Action：ActionProposed / ActionRejected / ActionPrepared / AttemptStarted / AttemptCompleted。
审批与交互：ApprovalRequested / Decided / Expired；InteractionRequested / Completed / Expired。
Context：ContextFrameCompiled / ContextCompacted / BlobExternalized。
验证与产物：ObservationCompleted / VerificationCompleted；ArtifactRegistered / Verified / Superseded。
预算与限额：BudgetSoftLimitReached / BudgetHardLimitReached / ContextLimitReached / **QuotaExhausted**。
恢复与安全：RecoveryRequired / RecoveryDecisionApplied；RedactionApplied；**EndpointBehaviorDrift**（§8.7）。

**新增 `LoopContinued` / `LoopTerminated` 两个事件**，携带 §8.3 的具名 `transition.reason` 与 `Terminal.reason`。这是循环纪律第 2 条在可观测侧的落点：**Trace 里能直接读出走了哪条恢复路径**，不必去比对消息内容。

删除的：SignalAccepted / Consumed / Rejected、DirectiveIssued、Activity 系列七个、ActivityProgressCheckpoint、TimerScheduled / TimerFired——对应的机制都已删除。

流式 delta、细粒度 Tool Progress、Download Progress 仍然只 yield 不落盘。

【定】进展回报不参与恢复（§16.2）。

### 19.3 Model usage 与计费输入公式【改写】

```ts
interface ModelUsage {
  inputTokens?: number;
  cacheCreationInputTokens?: number;
  cacheReadInputTokens?: number;
  outputTokens?: number;
  reasoningTokens?: number;
  billedInputTokens: number;      // 本版新增：计算得出，不是直接读
  estimated: boolean;
  estimatedCost?: Money;
  latencyMs: number;
  providerRequestId?: string;
}
```

#### 一个必须写进 `ModelProtocolPort` 的陷阱【实测】

**Anthropic 形状的 `usage.input_tokens` 不含命中缓存的部分。**

实测：一个 448 token 的请求在缓存命中时，`input_tokens` 只报 64。只读这一个字段会在缓存命中时**低估计费输入 85%**。

【定】计费输入必须写成：

```text
billedInputTokens = input_tokens + cache_read_input_tokens + cache_creation_input_tokens
```

具体公式由端点能力声明的 `tokens.billedInputFormula` 给出——OpenAI 形状的 `prompt_tokens` 已含缓存部分，公式是 `INPUT_ONLY`。

**这个陷阱本身就是第三轮 P4 探针的缺陷。** 它让探针一度报出 `-600%` 的预估偏差，实际偏差是 0.00%。写进架构是为了让实现不再踩一次。

#### usage 字段名四端点各不相同

```
百炼(Anthropic)【选定】：input_tokens / output_tokens
                        cache_creation_input_tokens / cache_read_input_tokens
                        prompt_tokens_details{cached_tokens}   ← 混进了 OpenAI 风格字段
百炼(OpenAI)          ：prompt_tokens / completion_tokens / total_tokens
                        prompt_tokens_details{cached_tokens}
                        completion_tokens_details{reasoning_tokens}
DeepSeek(Anthropic)   ：＋ service_tier
DeepSeek(OpenAI)      ：＋ prompt_cache_hit_tokens / prompt_cache_miss_tokens
```

【定】字段映射进端点能力声明的 `tokens.usageFieldMap`，不硬编码。

【定】没有精确数据时 `estimated = true`，不得伪装为零。

## 20. Human Takeover / External Interaction

### 20.1 定位【定】

Human Takeover 是显式的**等待—人工操作—重新观察**协议，不是绕过 Runtime 的隐藏操作。

### 20.2 ExternalInteractionRequest

```ts
interface ExternalInteractionRequest {
  id: InteractionRequestId;
  runId: RunId;
  actionId?: ActionId;
  capabilityId: CapabilityId;
  resourceHandleRef: ResourceHandleRef;
  parkedLeaseId: LeaseId;
  interactionType: "BROWSER_TAKEOVER" | "TERMINAL_TAKEOVER" | "MANUAL_RECOVERY";
  instructions: string;
  expectedCompletion: string;
  expiresAt?: Timestamp;
  status: "OPEN" | "COMPLETED" | "EXPIRED" | "CANCELLED";
}
```

### 20.3 运行语义【定】

```text
Runtime requests interaction
    ↓ persist request
    ↓ PARK the capability lease（不释放回池，绑定 interactionRequestId）
Run → WAITING_FOR_INTERACTION
    ↓ Layer 2/UI grants scoped human control
User operates external resource（进入 Product Audit）
    ↓ completion signal with requestId
Runtime UNPARKS the lease（原 owner 重获）
    ↓ re-observe + verify environment
continue / re-plan / ask user / fail
```

`PARKED` 而非释放，是为了防止释放与重获之间被其他 Run 抢占 EXCLUSIVE lease。PARKED 有独立过期定时器——接管超时则释放并让 Run 进入恢复路径。

完成信号不等于任务成功，**必须重新 Observation**。

## 21. Skill、MCP、Plugin 与策略扩展

### 21.1 内部语义保持区分【定】

## 22. 安全、脱敏与数据边界

### 22.1 Workspace Scope【定】

文件操作使用 ResourceRef；验证 Workspace、Mount、规范化路径和 symlink；CapabilityGrant 不能扩大 Binding Scope；ResolvedEffect 必须是 Grant Scope 的子集；Adapter 执行时再验证实际目标；Workspace 外写入必须由新的明确授权覆盖。

### 22.2 脱敏发生点【定】

```text
Tool Handler 原始输出（仅存在于 Adapter 进程内存）
    ↓ RedactionPort.redact(raw, profile)     ← 强制，不可跳过
RedactedOutcome + RedactionReport
    ├── 持久化为 Activity outcomeRef Blob        ← 已脱敏
    ├── 进入 Context Materialization             ← 预算与表示裁剪
    ├── 进入 Trace / 诊断 Blob                   ← 已脱敏
    └── 进入 Event payload                       ← 已脱敏
```

1. 未脱敏原文不得离开 Adapter 边界；
2. `RedactionProfile` 来自 `CapabilityBinding.redactionProfileRef` 与 `ToolDefinition.redaction` 的合并；
3. Tool 必须声明 `redaction`，未声明走最严格 profile；
4. **脱敏失败 = Tool 失败**（`source: TOOL_HANDLER, category: REDACTION`），不得降级为原样保存；
5. `RedactionReport` 记录脱敏字段与字节数，不记录被脱敏的内容本身；
6. Context Materialization 的过滤是**预算边界，不是安全边界**。

【议】D-06：是否允许在任何情况下保留未脱敏原文。

### 22.3 Secret 与敏感数据【定】

数据库、RunSpec、Context、Trace 只保存 SecretRef；Secret 明文仅在 Adapter 执行阶段短暂解析；Cookie、Token、浏览器存储不进入模型；向外发送本地数据时 ResolvedEffect 明确记录 data movement、目的地和数据范围。

### 22.4 不可信内容【定】

网页、文件、邮件和 ToolResult 默认 `EXTERNAL_UNTRUSTED`；ContextItem 保存来源与 trust，ContextFrame 汇总为 `trustSummary`；不可信内容中的文字不能创建 Grant、改变 Policy 或自动批准 Action；用户插话同样不能；高影响副作用独立经过 Effect Resolution、Policy 和 Approval；Approval UI 展示真实目标与 preview；不把「Policy 能可靠判断每个参数是否由某段网页导致」作为安全前提。

### 22.5 数据保留与回收【定】

| 类别 | 策略 |
|---|---|
| Durable Event、事实表行 | **永不删除** |
| Artifact lineage | 永不物理删除，Tombstone |
| Deliverable Artifact 内容 | 永久保留，除非用户显式删除 |
| 非交付 Runtime Blob | 超期可回收，**必须留 hash + size + 摘要 stub** |
| 诊断 Blob | 按 `maxAgeDays` 回收 |
| Transcript 投影 | 可重建，可回收 |
| 孤儿 Blob | 定期扫描回收 |

参与 Eval fixture 或 GoldenTrace 的 Run 与 Artifact 标记 `PINNED`，不进 GC。Runtime Host 监测存储水位，低于阈值进入 `DEGRADED` 并拒绝启动新 Run。

【议】D-10：默认保留窗口与回收倾向。

### 22.6 本地前后端通信【定】

随机端口或受控 Socket；会话级鉴权 Token；Origin 校验；禁止外部网页调用本地 API；SSE/WS 重连游标；人工接管通道绑定 InteractionRequest 和 ResourceHandle。

### 22.7 第三方模型端点的数据边界【新增】

#### 问题

V03 的安全模型是「凭证不进 Trace」。但本项目的运行环境是第三方 SaaS 端点，因此：

> **每一次 ModelInvocation 本身就是一次数据外发。**

V03 §22.3 说「向外发送本地数据时 ResolvedEffect 记录 data movement」——但那指的是 Tool 的副作用（上传文件之类），**模型调用在 V03 里被当成纯计算，不是数据移动**。

后果具体：脱敏只针对凭证。网页正文、本地文件内容、Git 仓库内容不是凭证，不会被脱敏，会完整发给第三方。Case 01 是登录态网页归档——登录后的页面可能是私人邮件或内部文档。

#### 规则【定】

1. **模型端点是一个 data movement 目的地**，与「上传文件到外部系统」同类，只是发生频率高得多；
2. `EndpointCapabilityProfile` 所属的 Endpoint 定义必须声明数据边界属性（地域、是否用于训练、留存策略），作为 Workspace 绑定端点时的展示信息；
3. **Workspace 级配置决定哪些 Mount 的内容允许外发给哪个端点**；超出范围的内容进入 Context 前必须被 Policy 拦截或降级为摘要；
4. §11.4 的「大结果外置到 Blob + 只发 preview」**同时是数据最小化机制**——外置的内容不进模型也就不出境。V03 只把它论证为上下文预算手段，本版确认其双重价值，阈值调整需同时考虑两个方向。

【验】具体的 Workspace × Endpoint 授权矩阵形态待阶段 3（Case 01 引入真实敏感内容时）设计。v0.1 只需在 Endpoint 定义上记录属性并在 UI 展示。

## 23. 跨层聚合的所有权与一致性

### 23.1 原则【定】

> **Layer 3 拥有执行事实，Layer 2 拥有产品聚合，通过 outbox 单向投影。**

| 对象 | Layer 3（权威执行状态） | Layer 2（权威产品状态） | 冲突裁决 |
|---|---|---|---|
| Approval | ApprovalRequested / Decided / Expired 事件 | `approvals` 表 | 执行语义以 Runtime 事件为准 |
| Artifact | ArtifactRegistered / Verified / Superseded 事件 | `artifacts` 表 | 注册与验证以 Runtime 为准；**用户手工标记以 Layer 2 为准** |
| ExternalInteraction | InteractionRequested / Completed / Expired 事件 | `external_interactions` 表 | 同 Approval |

### 23.2 一致性协议【定】

1. **Layer 3 在同一事务内提交**：Run transition + Durable Event + Activity Intent + 已消费 Signal + 相关 Timer。这是不变量，不是「尽量」；
2. 跨层投影通过 `run_events.sequence` 游标拉取，幂等，至少一次；
3. Layer 2 聚合中的执行语义字段是投影结果，不得独立推进；
4. Layer 2 可拥有的独立字段：用户可见标题、手工标记、归档状态、UI 排序、retention PIN；
5. Runtime 需要读取 Layer 2 状态时只能通过 Port，且只能作为 **precondition fingerprint**，不能作为状态机输入——否则 Layer 3 的可恢复性会依赖 Layer 2 当前状态，破坏 Replay。

【议】D-04：Artifact 的用户手工操作如何回流到 precondition 校验。

## 25. 关键运行流程

### 25.1 新 Session Message 启动 Run

```text
persist UserMessage
    ↓ extend / freeze ConversationSourceSnapshot（分段内容寻址）
    ↓ resolve AgentSpec + WorkspaceExecutionSnapshot
    ↓ 从 Endpoint Registry 取 EndpointCapabilityProfile 并冻结
    ↓ persist immutable RunSpec
    ↓ Runtime.start → 进入主循环第 ① 步
    ↓ for await (RunEvent)
    ↓ Layer 2 projects Transcript and final AssistantMessage
```

### 25.2 ActionBatch 执行

```text
ModelInvocation 完成
    ↓ 形状适配器识别全部 Tool Call
    ↓ 形成 ActionBatch（PLANNED）
    ↓ 逐条：normalize → schema validate（Runtime 自持）→ 落库 PROPOSED
    ↓ 逐条：resolve effect + preconditions → PREPARED
    ↓ 逐条：frozen grant check → live capability check → lease
    ↓ preview / policy / approval
    ↓ 逐条：persist Attempt Intent → 执行
    ↓ 边界脱敏 → materialize ToolResult or ErrorRecord
    ↓ Observation / Verification
    ↓ 为每个 call 合成恰好一个 result
    ↓ 全部 result 落盘（transcript）
    ↓ ActionBatchSettled
    ↓ state = { ...next, transition: { reason: "NEXT_TURN" } }; continue
```

### 25.3 WAITING_FOR_USER

```text
主循环 await 用户输入（+ AbortSignal.timeout）
    ↓ 状态标记 WAITING_FOR_USER，Layer 2 投影问题
    ↓ 用户消息 resolve 该 Promise
    ↓ 消息落盘 → 进 messages → 继续本轮
```

不匹配当前等待的用户消息按 §9.3 路由表处理——在非终态 Run 上进 Interject 队列。

**进程死亡则该等待消失。** `resume()` 时主循环重新走到同一位置，重新提问。

### 25.4 Approval

```text
PreparedAction / ActionBatch + preview + digest
    ↓ await canUseTool(...)（+ AbortSignal.timeout）
    ↓ Run WAITING_FOR_APPROVAL，Layer 2 投影待批
    ↓ 用户决策 resolve
    ↓ validate approval / target / digest / live capability
    ↓ execute / reject（合成 result）/ timeout / re-prepare
```

### 25.5 Cancel

```text
cancel() → AbortController.abort()
    ↓ 当前步骤协作式停止
    ↓ 批内未启动 Action → SKIPPED + 合成 result
    ↓ determine side-effect state
    ├── known safe → CANCELLED
    ├── applied    → preserve fact/artifact, then CANCELLED
    └── unknown    → RECOVERY_REQUIRED or CANCELLED with recoveryItems
```

### 25.6 Run 完成

```text
ModelInvocation 完成且无 Tool Call
    ↓ return settleOutcome(state)
    ↓ 结算 outcome.kind（只查事实表）
    ├── 存在未决 RecoveryItem           → RECOVERY_REQUIRED
    ├── 存在失败的 required Verification → COMPLETED_WITH_LIMITS + incompleteItems
    └── 其余                             → SUCCESS
```

### 25.7 Resume

```text
读 transcript，重建 messages（从最后一个 COMPACT_BOUNDARY 之后）
    ↓ revalidate capability / environment / preconditions / endpoint profile（§18.3）
    ↓ 检查末尾是否存在无 result 的 tool_use
    ├── 幂等或只读       → 合成中断 result，重新执行
    ├── 有 Observation   → 先观察外部世界，据结果决定
    └── 非幂等且不可观察  → RECOVERY_REQUIRED，交用户决定
    ↓ 进入主循环第 ① 步
```

**注意这里没有「不重复已证明完成的副作用」这一步。** 消息级恢复下，「工具跑没跑」在 transcript 上不可区分（§18.2），所以这个保证做不到——只能靠幂等声明与 Observation 逼近。

### 28.2 阶段 1：Headless Walking Skeleton

**研究问题**：端点差异能否被完全挡在主循环之外？批内配对不变量在没有状态机的情况下能否守住？

### 29.1 已对齐【定】

- **端点行为是数据不是代码**（原则十四）；
- **端点能力声明进 RunSpec 冻结**，Replay 使用冻结版本；
- **协议角色三档**，`PLACEHOLDER_REQUIRED` 是实测逼出来的中间档；

这是 §2.5 规格纪律第 1 条的反向用例：**「冻结前必须指出证据来源」同样适用于「某个机制必须存在」这类主张。** 三者都拿不出这样的证据。

**V03 的 15 个决策点，最终有 3 个是不该问的。** 这个比例本身是个信号——规格在没有运行经验时会长出自己的问题。

### 30.2 阶段 1 切面【已拍板】

#### D-14　实现哪些 Port

阶段 1 实现 10 个，4 个只留接口不实现。

| 实现（10） | 强制它的理由 |
|---|---|
| `ModelPort` | 调模型 |
| `ModelProtocolPort` | 端点声明读取路径，验收项 1 靠它 |
| `TranscriptStorePort` | 恢复的唯一来源；in-memory 实现，接口按最终形态定 |
| `ToolHandlerPort` | 两个工具 |
| `RedactionPort` | §28.2【定】不得绕过边界脱敏 |
| `EffectResolverPort` | §28.2【定】不得绕过 Effect 解析 |
| `VerificationPort` | §10.4 `outcome.kind` 结算要查 required Verification |
| `ClockPort` | FakeClock |
| `IdGeneratorPort` | 确定性测试 |
| `TraceSinkPort` | 先 console，接口留对 |

| 不实现（4） | 理由 |
|---|---|

**四个不实现的共同点：阶段 1 没有任何用例能检验它们设计得对不对。** 实现了也是盲写——这正是 §2.5 规格纪律第 3 条要防的事。

其中前四个「实现」项不是选择而是推论：§28.2 那条【定】「不得绕过」直接锁定了它们。

#### D-17　端点能力声明的最小字段集

阶段 1 实现 `protocol` + `context` + `tokens` 三组；`errors` / `limits` 推到阶段 2。

理由：前三组是**每次 ModelInvocation 都要读**的（构帧、校验、计数），后两组只在出错和撞墙时读，而阶段 1 的 Micro Case 不覆盖那些路径。

#### D-20　`LoopState` 的字段集

参照 `query.ts` 的十字段量级；**大对象外置，只留必要引用**。

`LoopState` 可以放 `Promise`、`AbortController`、完整 `Message[]`——它不需要存盘（§18.1），所以没有可序列化约束。唯一的纪律是**每个 continue 站点必须写全**（§8.3 循环纪律第 1 条）。

**D-20 与被取消的 D-15 问的不是同一件事**：D-15 问「哪些字段能被序列化并 hash」，D-20 问「哪些字段需要在每个 continue 站点被显式携带」。后者宽松得多。

### 30.3 阶段 1 其余决策【已拍板】

#### D-21　批结算默认值

```ts
{ onActionFailure: "CONTINUE_REMAINING",
  onApprovalRejected: "CONTINUE_REMAINING",
  onCancel: "ABORT_UNSTARTED" }
```

**依据是 `query.ts` 的实际行为**，已核对源码：`runTools()` 遍历全部 tool block，**不 break、不短路**；失败与拒绝在 `runToolUse()` 内部变成 tool_result，循环继续。

与不变量 8 的关系：不管哪一个 Action 出了什么事，**批内 4 个 call 仍然各有一个 result**。`onActionFailure` 只决定后续 Action 的 result 是真实执行结果还是 `SKIPPED`，不决定有没有 result。

> **顺带一个观察，不改变 D-01**：`query.ts` 没有批级 `executionMode`，它按**每个 Tool 的 `isConcurrencySafe()`** 把批切成段——连续的只读工具并发跑，非只读工具单独串行。这比本文的批级二选一更细。v0.1 仍按 D-01 全串行，将来若要放开并发，这个分段模型是现成的参考。

#### D-22　错误记录的维度切面

**四个维度全部保留**（`source` × `category` × `retryability` × `sideEffectState`）——结构经 Spike 三轮验证，是对的。

**值域裁剪到 Micro Case 能真正触发的**。未触发的枚举值留在类型定义里但阶段 1 不产生，避免写出没有任何用例检验过的分类逻辑。

这是 D-14 的类型级延伸：D-14 切 Port（有「不实现」这个选项），D-22 切类型内部（只能裁值域）。

#### D-23　Micro Case 具体任务：推迟

阶段 1 按抽象设计开发，**不先固定具体任务**。两个 Tool 按接口形态实现即可。

【定】但有一条形态约束不能推迟：**必须有一个可控慢的工具**，否则 §28.2 验收项 2 的三条中断路径注入不进去——快工具没有「执行到一半」这个状态。

#### D-24　`resume()` 进阶段 1

形态：**丢弃内存中的 `LoopState`，从 transcript 重建 `messages`，继续跑，结果一致。**

阶段 1 是 In-memory transcript，跨进程崩溃测不了，但上述过程在进程内完全可测。

**理由**：消息级恢复是本版删掉 Kernel 的主要理由（§18.1）。阶段 1 不测它，这个取舍到阶段 1 结束时仍然零证据——那就等于用一个没验证过的理由删掉了一整套机制。

#### D-25　工程基线

**Node ＋ npm**，不引入 monorepo 工具链。

**不写单测、不跑单测**——由人工实际验证。

【定】因此 §28.2 的两条验收项**以可运行脚本形式交付**，不是测试套件：

```bash
npm run verify:endpoint-profile    # 验收项 1：fake-endpoint-profile
npm run verify:pairing             # 验收项 2：三条中断路径注入
```

这与 Spike 0 的形态一致（`npm run p1` ~ `p10`）——**探针脚本，人读输出下判断**，而不是断言通过即绿灯。选择它的代价是回归靠人，收益是每次运行都产出可读的证据而不是一个布尔值。

## 31. 最终架构摘要

```text
Workspace 冻结资源、配置与授权证据
        ↓
Session 冻结不可变 ConversationSourceSnapshot
        ↓
Layer 2 生成自包含 RunSpec（含端点能力声明）
        ↓
主循环单线推进，每轮迭代显式构造下一个 LoopState
        ↓
形状适配器构造与解析协议，端点能力声明给出校验强度与常量
        ↓
主循环只消费规范化结果（不读端点声明）
        ↓
一次模型响应的全部 Tool Call 构成 ActionBatch，每个 call 恰好一个 result
        ↓
Context Runtime 管理 ToolResult、Blob、协议组、预算和 Compact
        ↓
Action Runtime 解析真实 Effect，经过 Grant / Lease / Policy / Approval
        ↓
Observation 与 Verification 判断外部世界是否达到目标
        ↓
模型不再请求工具即终止循环，outcome.kind 由事实表结算
        ↓
transcript 逐条落盘，resume 从消息边界继续，Replay 从任意消息位置重放
        ↓
Layer 2 将执行事实投影为 Message、Tool、Approval、Interaction 和 Artifact
```

### V02 确立的四条执行边界

1. ~~纯决策与异步活动分离，但通过 durable Activity 闭环~~ → **本版改写为**：循环状态与迁移原因必须显式，恢复粒度必须写明代价；
2. 模型看见的 Context 必须经过可追踪、可预算、协议合法的编译；
3. 所有副作用必须先得到可信的 EffectScope，再谈 Policy、Approval 和重试；
4. 恢复不是重新跑一遍；取消、未知副作用、实时撤权和外部变化都有明确处置。

### V03 补齐的三条

5. 一次模型响应可能产生多个动作。批的原子性、审批粒度、配对完整性和取消语义必须一起定义；
6. Run 必须知道自己什么时候算做完了。每一步都验证过，不等于整件事做成了；
7. 安全边界在数据离开执行边界的那一刻，而不是在它进入模型的那一刻。

### V04 补齐的三条

8. **协议不变量没有外部兜底。** 选定端点上缺 tool_result、错 tool_call_id 一律 200 放行。不变量的理据不是「否则接口会报错」，而是「否则模型看到的世界是错的」——执行责任 100% 在 Runtime，且**没有任何东西会替你发现违反**。

9. **端点行为是数据，不是代码。** 第二轮十条结论有六条换端点失效，而第二轮的变量隔离已经做得很干净。任何「某个 Provider 会怎么表现」的结论只能以端点能力声明的形式存在，冻结进 RunSpec，并在实际行为偏离时 fail fast。

10. **恢复粒度是一个显式取舍，不是一个默认值。** 本版选择消息级：`resume()` 从上一条已落盘的消息继续，代价是崩溃时在跑的工具会重跑。这个代价必须写在架构里（§18.1），而不是等实现时才发现——因为它把「Tool 是否幂等」从一个可选属性变成了恢复正确性的前提。

### 一条方法论边界

> **证据先于冻结，且证据本身有保质期。**
>
> V03 用【定】/【验】/【议】三种标记强制前半句。
> V04 增加【端点】标记强制后半句——把「仅对某端点成立的结论」与「跨端点不变量」在文档层面分开，
> 并用 §8.7 让前者以数据形式存在，用 §24.6 让它被定期重新验证。

在此基础上，WorkAgent 可以先用单 Agent Loop、单形状适配器、单端点完成 Walking Skeleton 和真实 Case；换端点是配置变更，换形状是新增一个适配器，都不需要推翻当前三层架构。
