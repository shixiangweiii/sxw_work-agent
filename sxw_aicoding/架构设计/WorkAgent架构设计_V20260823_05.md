### 0.2 状态标记约定

| 标记 | 含义 | 处理方式 |
|---|---|---|
| **【定】** | 已拍板不变量，跨端点成立 | 不再讨论；实现违反即架构错误；变更需独立 ADR |
| **【验】** | 当前方向，待证据验证 | 必须由 Micro Case / Eval 确认后才能冻结 |
| **【议】** D-xx | 待决策 | 见第 30 章；拍板前不得在代码中固化任一候选 |
| **【端点】** | **仅对特定端点成立** | 必须写明对哪个端点成立；换端点前必须重新验证；不得编译进代码，只能进端点能力声明（§8.6） |

【端点】的存在理由是一组具体数字：Spike 0 第三轮把第二轮的十条结论重测了一遍，**六条只在原来那个端点上成立**——而第二轮的变量隔离已经做得很干净（同平台、同模型、同 Key，只换 API 形状）。

没有这个标记，这类结论会被实现当成普适不变量。

### 0.3 v0.1 主力端点【定·D-16】

**百炼 Anthropic 形状（`qwen3.7-plus`）。**

第三轮对四个端点按 WorkAgent 的实际需要加权打分：

| 端点 | 得分 |
|---|---|
| DeepSeek · Anthropic 形状 | 76 |
| **百炼 · Anthropic 形状** | **73** |
| 百炼 · OpenAI 形状 | 65 |
| DeepSeek · OpenAI 形状 | 57 |

**选了 73 分的那个，不是 76 分的。** 3 分在噪声范围内，两者是取舍不同而非优劣不同：

| | 百炼 Anthropic | DeepSeek Anthropic |
|---|---|---|
| 协议不变量兜底 | **零**（缺 result、错 id 全部 200 放行） | **有**（一律 400，报错指名道姓） |
| 上下文可重建性 | **完全无状态**，任何历史都能重放 | **服务端按 id 持有推理内容**，凭空构造的历史被拒 |
| 模型目录 | **241 个** | 3 个 |

三条理由：

1. **阶段 1 的核心是把主循环、Context 重写、Resume 跑通。** 服务端有状态会在最核心的地方添乱——跨会话、Compact 后重构历史、Replay，这些场景下 id 都不是该端点生成的；
2. **241 个模型是退路。** 阶段 1 还不知道最终要什么模型，现在锁在 3 个上太早；
3. **零兜底反而是开发期的优势。** 协议不变量 100% 由 Runtime 自持（§8.5）。用一个什么都不校验的端点开发，能逼出自持逻辑的全部漏洞；用会校验的端点开发，反而可能让人误以为自持逻辑是对的，换端点时才爆。

**DeepSeek Anthropic 形状作为阶段 2 的对照端点**：把 Runtime 产出的请求打到一个真正会校验的端点，是一次免费的正确性测试（§24.6）。

**重新评估的触发条件**【定】：

- 百炼出现稳定的配额或可用性问题；
- 阶段 2 的对照测试显示自持逻辑有系统性缺陷，需要外部兜底；
- 出现必须使用 DeepSeek 独有模型的 Case；
- 端点能力声明的实测结果与本文记录出现重大偏离（§8.6 漂移检测）。

**这个选择不进主循环。** 它是一份端点能力声明 ＋ 一个形状适配器的组合，换端点是配置变更，不是架构变更。

### 0.4 Spike 0 证据闭环

三轮，2 平台 × 2 形状 = 4 个端点，75 份原始证据，11 个探针。

### 0.5 相对 V04 的核心变化

**执行模型从「纯 Kernel ＋ durable orchestration」换成「`while` 主循环 ＋ 消息级恢复」。**

参照物是 Claude Code 的 `query.ts`——一个真实在跑的 Harness 主循环。它印证了两件事：

1. `while` 循环写到足够复杂会自己长出「显式状态对象 ＋ 具名迁移 ＋ 具名终止原因」（§8.2 循环纪律的来源）；
2. 它的持久化就是**消息级**的——跨迭代状态里带着 `Promise` 与 `AbortController`，根本不可序列化，因此不支持 mid-turn 恢复。

完整变更清单见附录 A。

## 2. 结论与规格纪律

### 2.1 一句话结论

> WorkAgent 是一个**单进程、消息级持久化的 Agent Harness**：主循环驱动模型与工具，端点差异以数据形式隔离在外，协议不变量 100% 由 Runtime 自持。

### 2.2 三个中心【定】

**Workspace**（资源、配置与授权证据的边界）／ **Session**（对话与产品语境）／ **Run**（一次可追踪、可预算、可恢复的执行）。

Session 是产品基础能力，**Runtime 支持无 Session 的 Run**——Eval Lab 依赖这一点。

### 2.3 当前明确不做【定】

预定义业务 DAG；多 Agent 默认架构；通用无约束的生命周期 Hook；跨 Session 自动长期 Memory；企业多租户、RBAC、计费和云端 Runtime；为假想外部 Engine 设计万能 Adapter；引入 AG-UI / A2UI / MCP Apps 作为线上协议；无条件保存所有 Provider 原始流或所有 Tool 原始大结果；**把任何端点行为编译进主循环或形状适配器**；**mid-turn 崩溃恢复**（§18.1 明确放弃）。

### 2.4 多 Agent 的当前边界【定】

v0.1 不实现 Sub-agent、并行 Agent 或 Run Group，但禁止写死：Runtime 要求 Run 必须属于 Session；「一个 Session 一个 Foreground Run」是 Layer 3 不变量；Run 的因果来源只绑定 Session Message；Child/Background 执行直接写 Session Transcript；Context/Budget/Capability/Cancel 隐式全量继承。

**「一次模型响应产生多个 Tool Call」不属于多 Agent**，四个端点实测全部默认返回 4 个，必须在 v0.1 建模（§8.5）。

### 2.5 规格纪律【定】

1. 任何 Contract 冻结前，必须能指出支撑它的证据来源；
2. 无法指出证据来源的条目标记【验】或【议】；
3. 阶段 1 只实现能被当阶段 Micro Case 覆盖的最小面；
4. 每新增一个 Port，必须同时指出强制它存在的不变量；
5. 跨端点未经验证的结论一律标记【端点】，且必须写明对哪个端点成立。

**第 1 条有一个容易被忽略的反向用法**：它同样适用于「某个机制必须存在」这类主张。V03 的 15 个决策点里，最终有 3 个被证明**问题本身不该问**——`RunAcceptance`、`KernelState` 序列化边界、Timer 真定时器 vs 惰性，它们的前提都不成立。

#### 关于事实的保质期

> **变量隔离做得再干净，Provider 结论依然不可移植。**

架构层面的三条应对：

1. **端点事实以数据形式存在**（端点能力声明），不编译进代码；
2. **端点能力声明进 RunSpec 冻结**，使 Replay 能重现当时的端点行为；
3. **实际行为与声明不符时 fail fast**，而不是静默继续（§8.6 漂移检测）。

### 2.6 规格规模

| 指标 | 数量 |
|---|---|
| 逻辑表 | 35（Layer 2 22 ＋ Layer 3 13） |
| Runtime Port | 14（阶段 1 实现 10） |
| Run 不变量 | 14 |
| Runtime 模块目录 | 14 |
| 状态标记 | 【定】/【验】/【议】/【端点】 |

## 3. 架构原则

原则一至十继承上位基线与 V03，此处只列有实测支撑或本版改动的。

### 原则十一：模型协议要素不可被上下文治理破坏【定】

Context Runtime 的裁剪、外置、Compact 与重排，**不得**破坏协议要求的结构完整性。

该清单的来源必须是**形状适配器 ＋ 端点能力声明**的组合，不是任一单方：

- 形状决定**载体**（`thinking` 块 vs `reasoning` item）；
- 端点决定**强度**（可自由丢弃 / 必须留占位块 / 必须逐字回传）。

### 原则十二：脱敏发生在离开执行边界的第一个持久化点【定】

未脱敏的原始 Tool 输出、Provider 原始响应和诊断数据，不得离开 Adapter 边界写入任何 Blob、事实表或 transcript。

**每次 ModelInvocation 本身就是一次数据外发**（§22.7）——脱敏不只是「不进 Trace」的手段，还是「不进第三方」的手段。

### 原则十三：证据先于冻结【定】

未经运行证据支持的 Contract 不得冻结。

### 原则十四：端点行为是数据，不是代码【定】

任何「某个 Provider 会怎么表现」的结论，**只能以端点能力声明的形式存在**，不得编译进主循环、Context 模块或形状适配器。

判据很简单：**如果换一个端点这条结论可能变，它就是数据。**

实测里属于「数据」的至少有：协议不变量是否被校验、推理块的约束强度、错误判别式、每请求固定底数、缓存匹配方式、强制单条开关是否生效、配额上限。

代价是多一层间接。收益是换端点时改配置而不是改代码——而实测表明换端点会让六成结论失效。

### 原则十五：恢复粒度是显式取舍【定·新增】

恢复粒度必须写在架构里并写明代价，而不是在实现时才发现。

本版选择**消息级**：`resume()` 从上一条已落盘的消息继续，代价是崩溃时正在执行的工具会重跑（§18.1）。

这条原则的落点很具体：**它把「Tool 是否幂等」从一个可选属性变成了恢复正确性的前提。**

## 4. 总体架构

### 4.1 三层

```text
┌────────────────────────────────────────────────────────────┐
│ Layer 1：WorkAgent UI                                      │
│ Transcript / Approval / Artifact / Trace & Eval Inspector  │
└────────────────────────────┬───────────────────────────────┘
                             │ HTTP / SSE / scoped WebSocket
                             ▼
┌────────────────────────────────────────────────────────────┐
│ Layer 2：Application Service（控制平面）                    │
│ Workspace / Session / Message / Transcript Projection      │
│ Skill / MCP / Plugin / Artifact / Approval / Audit         │
│ Endpoint Registry / RunSpec Factory / Projection / API     │
└────────────────────────────┬───────────────────────────────┘
                             │ In-process Runtime Facade
                             │ RunSpec / RunEvent / Interrupt
                             ▼
┌────────────────────────────────────────────────────────────┐
│ Layer 3：Harness Runtime（执行数据平面）                    │
│ Loop / Transcript / Context / Model                        │
│ Action / Tool / Policy / Verification                      │
│ Budget / Artifact / Trace / Runtime Ports                  │
└──────────────┬──────────────────────────────┬──────────────┘
               │                              │
               ▼                              ▼
        Runtime Adapters              Case Packages
```

### 4.2 单向依赖【定】

允许：

```text
UI → Application Service
Application Service → Harness Runtime（Facade / RunSpec / RunEvent）
Harness Runtime → Runtime Ports → Adapters
Case Package → 公开 SDK
```

禁止：

```text
Harness Runtime → Application Service Repository
Harness Runtime → UI
Harness Runtime → Eval Dataset / Grader
Harness Runtime → 具体 Case Package
主循环 → SQLite / Electron / Browser / Provider SDK
Context 模块 → Provider SDK（必须经 ModelProtocolPort）
形状适配器 → 任何端点特定的行为常量（必须经端点能力声明）
Policy → 未经解析的模型自然语言副作用声明
```

最后一条是**原则十四的编译期表达**：形状适配器只能知道「Anthropic Messages 协议长什么样」，不能知道「百炼这个端点会不会校验配对」。

## 5. Layer 1：WorkAgent UI

### 5.1 职责

Workspace / Session / 配置管理；User / Assistant Message；Assistant 文本流式展示；Tool、ActionBatch、Attempt、Verification 和进度展示；Approval 展示与决策；Run 恢复/取消/插话/重新执行；ExternalInteractionRequest 与人工接管；Artifact 预览与交付标记；Trace 和 Eval Inspector。

**图形界面在阶段 4。** 阶段 1–3 全部是 headless / CLI。

### 5.2 UI 不拥有的语义【定】

Run 合法状态迁移；Action 是否允许执行；EffectScope 是否落在 Grant 内；Tool 是否可安全重试；Cancel 后副作用是否已发生；Postcondition 是否通过；Run 的 outcome 结算为哪一种；`resume()` 时未配对的 tool_use 如何处置；**当前端点是否支持某项能力**。

### 5.3 Transcript

```ts
type TranscriptEntry =
  | UserMessageEntry
  | AssistantMessageEntry
  | ToolActivityEntry
  | ApprovalEntry
  | InteractionEntry
  | ArtifactEntry
  | SystemNoticeEntry;
```

每个投影项保存 `sourceRunId` 与至少一个 `sourceSequence / sourceActionId`（`sourceSequence` 即 Runtime transcript 的条目序号，§18.5）。

### 5.4 前后端协议

HTTP Command / Query；SSE 推 Assistant Delta、Run 状态、ActionBatch/Tool 状态、Approval、Artifact；WebSocket 只用于终端与浏览器人工接管；所有命令携带 idempotency key；SSE/WS 重连使用 transcript sequence 作为游标。

### 5.5 决策记录 A-01：不引入外部 Agentic UI 协议【定】

v0.1 不引入 AG-UI / A2UI / MCP Apps 作为线上协议。理由：单人本地产品没有跨厂商互操作需求；引入会把 UI 语义提前冻结在一个尚未验证的抽象上。

保留的约束是：**UI 通过 RunEvent 流驱动，不直接读 Runtime 内部状态**——这使得将来接入任何 UI 协议都只是新增一个投影器。

## 6. Layer 2：Application Service

### 6.1 职责边界【定】

拥有产品语义与聚合：Workspace、Session、Message、Transcript 投影、Skill/MCP/Plugin 安装与绑定、Artifact 产品视图、Approval 产品视图、Audit、**Endpoint Registry**。

不拥有执行语义：不推进 Run 状态、不判定 Action 合法性、不解析 Effect。

### 6.2 Endpoint Registry【定】

```ts
interface Endpoint {
  id: EndpointId;
  name: string;
  shape: "ANTHROPIC_MESSAGES" | "OPENAI_CHAT" | "OPENAI_RESPONSES";
  baseUrl: string;
  credentialRef: SecretRef;
  dataBoundary: EndpointDataBoundary;   // §22.7
  status: "ACTIVE" | "DEGRADED" | "DISABLED";
}

interface EndpointDataBoundary {
  region?: string;
  usedForTraining: "NO" | "YES" | "UNKNOWN";
  retentionPolicy?: string;
}
```

【定】`credentialRef` 只存引用。**凭证只能发往它所属 Endpoint 的 `baseUrl`**——这条在 Spike 0 期间被实际违反过一次（第三方 Key 因环境变量优先级问题发往官方端点），因此升为不变量而非注意事项。

### 6.3 RunSpec Factory

从 Workspace / AgentProfile / Session / Endpoint Registry 组装**自包含**的 RunSpec（§7.7）。「自包含」意味着 Runtime 执行期间不需要回查 Layer 2。

### 6.4 Session 与 Run 的关系

v0.1 一个 Session 同时只允许一个 Foreground Active Run【议】D-09。

### 6.5 Capability Control Plane

Definition Catalog、Workspace Binding、Provider 配置、Scope、SecretRef、健康检查、撤销。Run 启动生成冻结 CapabilityGrant；执行前取短生命周期 Lease 并检查实时状态。

### 6.6 Runtime Host

创建并配置 Harness Runtime；注入全部 Port；从 Workspace / Agent / Session / **Endpoint Registry** 创建 RunSpec；`resume()` 未结束 Run；把用户输入、插话、Approval 决策、Cancel、Interaction Completion、Recovery Decision 路由到对应的等待或 Interject 队列（§9.1）；消费 RunEvent 流并投影；监督进程退出与 AbortController 传播。

## 7. Workspace、Session 与 Snapshot 模型

### 7.1 Workspace

```ts
interface Workspace {
  id: WorkspaceId;
  name: string;
  status: "ACTIVE" | "ARCHIVED";
  resourceScopeId: ResourceScopeId;
  policyBindingId: PolicyBindingId;
  revision: number;
  createdAt: Timestamp;
  updatedAt: Timestamp;
  archivedAt?: Timestamp;
```

### 8.2 主循环【定】

#### 循环状态

```ts
// 跨迭代携带的可变状态。每个 continue 站点构造完整的一份。
type LoopState = {
  messages: ContextMessage[];
  turnCount: number;
  consecutiveFailures: number;
  compactTracking: CompactTrackingState | undefined;
  budgetUsage: BudgetUsage;
  maxOutputTokensOverride: number | undefined;
  // 上一次为什么 continue。首次迭代为 undefined。
  // 让测试能断言某条恢复路径确实走了，而不必去翻消息内容。
  transition: Continue | undefined;
};
```

```ts
type Continue =
  | { reason: "NEXT_TURN" }
  | { reason: "COMPACT_RETRY" }
  | { reason: "CONTEXT_OVERFLOW_RECOVERY" }
  | { reason: "OUTPUT_LIMIT_RECOVERY"; attempt: number }
  | { reason: "MODEL_ERROR_RETRY"; attempt: number }
  | { reason: "APPROVAL_RESUMED" }
  | { reason: "INTERJECTION_ACCEPTED" };

type Terminal =
  | { reason: "COMPLETED" }
  | { reason: "COMPLETED_WITH_LIMITS"; incompleteItems: IncompleteItem[] }
  | { reason: "ABORTED_STREAMING" }
  | { reason: "ABORTED_TOOLS" }
  | { reason: "CONTEXT_EXHAUSTED" }
  | { reason: "BUDGET_EXHAUSTED" }
  | { reason: "QUOTA_EXHAUSTED" }
  | { reason: "MODEL_ERROR"; error: RuntimeErrorRecord }
  | { reason: "MAX_TURNS"; turnCount: number };
```

**`LoopState` 不需要可序列化**，可以放 `Promise`、`AbortController`、完整 `Message[]`——恢复走 transcript，不走状态快照（§18.1）。

【定·D-20】字段集参照 `query.ts` 的十字段量级；**大对象外置，只留必要引用**。

#### 循环骨架

```ts
async function* runLoop(spec: RunSpec): AsyncGenerator<RunEvent, Terminal> {
  let state: LoopState = initialState(spec);

  while (true) {
    const { messages, turnCount, compactTracking } = state;

    // ⓪ 排空 Interject 队列，转为 ContextMessage 落盘后进 messages
    drainInterjections(state);

    // ① 上下文治理：外置大结果 → Compact → 协议校验
    const frame = await compileFrame(messages, spec.endpointProfile);
    if (frame.status === "COMPACTION_INSUFFICIENT") { /* §11.6、§16.4 */ }

    // ② 调模型（流式，delta 直接 yield 给消费方，不进 state）
    const { assistantMessages, toolUses } = yield* invokeModel(frame);

    // ③ 模型不再请求工具 → 结算 outcome，退出（§10.4）
    if (toolUses.length === 0) {
      return settleOutcome(state);
    }

    // ④ 执行 ActionBatch：批内每个 call 恰好一个 result（§8.5）
    const toolResults = yield* executeBatch(toolUses, assistantMessages);

    // ⑤ 构造下一轮完整状态，显式写明原因
    state = {
      ...state,
      messages: [...frame.messages, ...assistantMessages, ...toolResults],
      turnCount: turnCount + 1,
      compactTracking,
      transition: { reason: "NEXT_TURN" },
    };
  }
}
```

#### 循环纪律【定】

1. **每个 `continue` 站点必须构造完整的 `LoopState`**，不做零散字段赋值。漏赋一个字段就是一条隐藏的状态泄漏；
2. **每个 `continue` 必须带具名 `transition.reason`；每个 `return` 必须是具名 `Terminal`。** 理由是可测试性：验收断言的是「哪条恢复路径触发了」，不是「消息内容长什么样」；
3. **消息先落盘再进 `messages` 数组**（§8.3）。这是消息级恢复的全部基础——崩溃后 transcript 只可能与内存一致或领先，不可能落后；
4. **流式 delta、进度、心跳不进 `LoopState`**，直接 yield 给消费方；
5. **循环不读取端点能力声明。** 端点差异必须在形状适配器与 Context 层消化完毕，循环只看见规范化结果。否则「换端点」会变成「改主循环」。

第 5 条是**原则十四在执行层的落点**。挡住端点差异的边界从「纯函数」换成了「主循环文件」，约束强度不变。

#### 这个设计放弃了什么【定】

不变量「批内每个 Tool Call 恰好一个 result」（§10.3 不变量 8）**没有在纯函数里被穷举测试的可能**，它退化为分散在三条中断路径上的手写纪律（§9.2）。

选定端点对此**零外部兜底**，所以这三处是本项目最需要被反复审视的代码，也是阶段 1 验收项 2 的对象（§28.2）。

> 这不是疏漏，是消息级恢复这个选择的连带代价。写在这里是为了让它无法被悄悄忽略。

### 8.3 循环内的一步与持久化【定】

```ts
type StepKind =
  | "CONTEXT_COMPILE" | "COMPACT" | "MODEL_INVOCATION"
  | "TOOL_EXECUTION" | "OBSERVATION" | "VERIFICATION";
```

每一步有超时与取消，但**没有 durable 生命周期**——没有 PLANNED/STARTED、没有 generation、没有心跳、没有 Run Lock。崩溃时整个循环终止，恢复由 §18 的 transcript 重建承担。

推进协议：

```text
append 消息到 transcript（落盘）
→ 更新内存 messages
→ 执行下一步（Port 调用，signal 传播 cancel）
→ Redact at adapter boundary
→ append 结果消息到 transcript
→ 更新内存 messages，构造 next LoopState
```

【定】取消通过**单个 `AbortController`** 传播，signal 传给所有 Port 调用。

### 8.4 ModelInvocation 生命周期

1. 循环进入第 ② 步；
2. **形状适配器**按当前端点的形状构造请求；
3. ModelPort 开始异步流式调用；
4. Delta 直接 yield 给消费方，不进 `LoopState`；
5. **形状适配器**规范化响应，识别全部 Tool Call 与协议要素；
6. **端点能力声明**参与判定哪些块必须保留（§11.5）；
7. 只有完整且协议合法的结果进入 `messages`；
8. 响应消息落盘后才更新内存；
9. Usage、耗时、Provider request ID 记入 Trace。

流式中断规则【定】：

- Cancel/timeout 后半截文本默认不进入后续 Context；
- 半截内容脱敏后可外置保存用于诊断，标记 `INTERCEPTED/PARTIAL`；
- **已闭合的块可以保留**，闭合判据由端点能力声明给出；
- 未闭合的 Tool Call 不得转为 ProposedAction；
- UI 可展示「响应已中断」，但不得把半截输出投影为 FINAL Assistant Message。

【端点·百炼 Anthropic】有 `content_block_stop` 事件，闭合可直接判定。OpenAI 形状无独立闭合事件，判据退化为「参数 JSON 可解析」＋「后继 index 出现 ⟹ 前一 index 已闭合」。

### 8.5 ActionBatch：一次响应的多个 Tool Call

#### 实测基础

四个端点**全部**在一次响应中返回 4 个 tool call（`stop_reason=tool_use` / `finish_reason=tool_calls`）。**这是默认行为，不是边缘情况。**

```ts
interface ActionBatch {
  id: ActionBatchId;
  runId: RunId;
  invocationId: ModelInvocationId;
  actionIds: ActionId[];
  executionMode: "SEQUENTIAL" | "CONCURRENT_LIMITED";
  maxConcurrency?: number;
  approvalMode: "PER_ACTION" | "BATCH_SINGLE";
  batchDigest: string;
  settlement: BatchSettlementPolicy;
  status: "PLANNED" | "IN_PROGRESS" | "SETTLED";
  settledAt?: Timestamp;
}

interface BatchSettlementPolicy {
  onActionFailure: "CONTINUE_REMAINING" | "SKIP_REMAINING" | "ABORT_BATCH";
  onApprovalRejected: "SKIP_REMAINING" | "CONTINUE_REMAINING";
  onCancel: "ABORT_UNSTARTED";
}
```

#### 不变量【定】

1. 一次 ModelInvocation 产出的全部 Tool Call 构成一个 ActionBatch；
2. **批内每个 Tool Call 在返回模型前必须拥有恰好一个协议合法的 result**。成功、失败、被 Policy 拒绝、被用户拒绝、被跳过、被取消——每种终局都必须合成结构化 result；
3. 批未 `SETTLED` 前不得发起下一次 ModelInvocation；
4. 批内每个 Action 独立经过 Effect Resolution、Capability 三层校验与 Policy 判定；
5. `approvalMode = BATCH_SINGLE` 时，`batchDigest` 任一变化即失效；
6. 批内 EXCLUSIVE / KEYED lease 冲突时，冲突子集自动降级为串行；
7. Cancel 落在批中间时：已完成 Action 事实保留，未启动 Action 标记 `SKIPPED` 并合成 result；
8. 一轮迭代按批计一次 `turnCount`（§16.5）。

#### 不变量 2 的理据【端点·实测】

一个直觉的理据是「否则 Provider 会 400」。**在选定端点上这是错的**：

| 负向实验 | 百炼(Anthropic)【选定】 | DeepSeek(Anthropic) |
|---|---|---|
| 缺 3 个 tool_result | **200 接受** | 400 |
| tool_call_id 篡改 | **200 接受** | 400 |

因此正确的理据是：

> **否则模型看到的是一个失真的世界**——它会以为某个工具没被调用过，或者把 A 的结果当成 B 的。

**这不降低不变量的重要性，反而提高了**：没有任何外部兜底会替你发现违反。

#### v0.1 执行模式与结算【定】

`executionMode = SEQUENTIAL`、`approvalMode = PER_ACTION`（D-01）。

```ts
settlement = {
  onActionFailure: "CONTINUE_REMAINING",
  onApprovalRejected: "CONTINUE_REMAINING",
  onCancel: "ABORT_UNSTARTED",
}
```

**结算默认值依据 `query.ts` 的实际行为**（D-21，已核对源码）：`runTools()` 遍历全部 tool block，**不 break、不短路**；失败与拒绝在 `runToolUse()` 内部变成 tool_result，循环继续。

【定】**任何结算取值都不影响不变量 2**——它只决定后续 Action 的 result 是真实执行结果还是 `SKIPPED`，不决定有没有 result。

**串行的理据是 Runtime 自持，不是协议保障。** 实测（每档 3 次采样）：

| 端点 | 参数 | 缺省 | 显式关闭 | 判定 |
|---|---|---|---|---|
| 百炼(OpenAI) | `parallel_tool_calls:false` | 4/4/4 | **1/1/1** | 生效 |
| **百炼(Anthropic)** | `disable_parallel_tool_use` | 4/4/4 | **4/4/4** | **静默接受，完全无效** |
| DeepSeek(OpenAI) | `parallel_tool_calls:false` | 4/4/4 | 4/4/4 | 静默接受，无效 |
| DeepSeek(Anthropic) | `disable_parallel_tool_use` | 4/4/4 | 4/4/4 | 静默接受，无效 |

【端点·四格均成立】**四个端点全部静默接受该参数，其中三个不生效，没有任何一个会告诉你「我不支持」。**

【定】批内串行**必须由 Runtime 自己保证**。协议开关只是可有可无的加成，**不得作为设计前提**——把它当保障会在换端点时静默失效，而且因为参数被接受，连报错都没有。

> **一个可供将来参考的更细模型**：`query.ts` 没有批级 `executionMode`，它按每个 Tool 的 `isConcurrencySafe()` 把批切成段——连续的只读工具并发跑，非只读工具单独串行。v0.1 仍按 D-01 全串行，将来放开并发时这是现成的参考。

### 8.6 端点能力声明【定·D-07 的落地形态】

#### 问题

三轮实测的六条结论换端点即失效，它们包括「协议是否被校验」「推理块能否丢弃」「错误怎么分类」「缓存怎么匹配」——全都是 Context 层与错误处置层每天都要用的东西。

如果它们以 `if (provider === 'x')` 的形式散落在代码里，换端点就是一次全局重构。

#### 答案

> **形状决定「协议长什么样」，平台决定「协议被执行到什么程度」，端点决定「具体数值」。**

按因子归类全部实测差异：

| 差异 | 归因 |
|---|---|
| 有无 token 预估端点 / 流式闭合事件 / `is_error` 带外字段；推理块载体形态 | **形状** |
| 协议不变量是否被校验；tool 定义 schema 是否被校验；推理块是否服务端有状态 | **平台** |
| 错误判别式；强制单条开关是否生效；每请求固定底数；缓存匹配方式 | **端点** |
| tool 定义开销、计费口径、入参不校验 | **模型/共性** |

因此：

> `ModelProtocolPort` 按 **API 形状**切分适配器——它管解析与构造。
> **校验强度、有状态性、错误判别式、各项常量做成端点级能力声明**，不编译进适配器。
>
> 两者生命周期完全不同：适配器随 SDK 版本变，声明**随时可能在没有任何通知的情况下变**。

#### 模型

```ts

  },
  limits: {
    quotaBeforeContextLimit: false,         // 同平台 OpenAI 形状为 true
  },
  confidence: "PROBED",
};
```

#### 不变量【定】

1. **端点能力声明是数据，不是代码。** 任何端点特定行为不得出现在主循环、Context 模块或形状适配器中；
2. **Run 启动时冻结进 RunSpec**（§7.7）。Replay 使用冻结版本，不使用当前配置；
3. **`confidence` 必须如实标注。** `ASSUMED` 的字段在被依赖时应产生 SYSTEM_NOTICE；
4. **漂移检测**：Runtime 观察到与声明不符的行为时，产生 `EndpointBehaviorDrift` 事件，并按配置 fail fast 或降级——**不得静默继续**；
5. **声明的粒度是端点 × 模型**，不是平台，也不是形状。实测表明同平台两形状可以在缓存、校验、错误判别式上完全不同；
6. 主循环不读取声明（§8.2 循环纪律第 5 条）。

#### 漂移检测的最小实现【验】

阶段 1 只需三条：

- `honorsDisableParallelToolCalls: false` 却收到单条 → 记录，不失败；
- `validatesToolResultPairing: false` 却收到配对相关 400 → **fail fast**，说明声明过期；
- `countTokensAccuracy: "EXACT"` 却出现非零偏差 → 记录偏差分布，超阈值告警。

完整策略见【议】D-18。

#### `ModelProtocolPort` 的职责


## 9. 中断与用户输入

### 9.1 三种中断，三种机制【定】

| 中断 | 机制 | 生效时机 |
|---|---|---|
| **Cancel** | 单个 `AbortController`，signal 传给所有 Port | 立即，协作式 |
| **Interject** | 进程内队列 | 每轮迭代开始处排空（§8.2 第 ⓪ 步） |
| **Approval 决策** | 审批回调的 `await` | Action 执行前 |

三者都**不持久化**。已排空并落盘为消息的才是事实，队列里的不是。

**没有 Pause / Unpause 状态。** 产品上的「暂停」实现为 `cancel()` ＋ 稍后 `resume()`——消息级恢复下两者行为一致，多一个状态只多一份状态迁移表。

### 9.2 Cancel 的处置【定】

```text
cancel() → AbortController.abort()
→ Port 协作式停止
→ 为已发出但无 result 的 tool_use 合成中断 result
→ 落盘
→ return Terminal { reason: "ABORTED_STREAMING" | "ABORTED_TOOLS" }
```

【定】副作用无法确认时，合成的 result 必须标记为**状态未知**而非失败，并写入 `recoveryItems`。迟到的成功结果不得把已终止的 Run 拉回运行态，但必须作为诊断事实落盘。

#### 合成 result 的三条路径

**这是配对不变量的唯一保障点**（§8.2 末尾）。三条路径各需要一遍：

| 路径 | 触发 |
|---|---|
| 流式中断 | 模型响应流被 abort |
| 工具执行中断 | 批执行到一半被 abort |
| 模型错误 | 已发出 tool_use 后请求失败 |

缺任何一条，transcript 里就会留下无 result 的 tool_use。下次 `resume()` 时发给模型就是一个失真的世界——**而选定端点会 200 放行**（§8.5）。

> `query.ts` 在三处分别实现了这件事（fallback 重试、异常、abort），这不是巧合，是这个形态的必然要求。

### 9.3 执行期间的用户输入

```ts
interface InterjectSignal {
  type: "INTERJECT";
  content: string;
  intent: "ADD_CONTEXT" | "CONSTRAIN" | "REDIRECT";
  urgency: "NEXT_FRAME" | "NEXT_SAFE_POINT";
}
```

插话语义【定】：排空后成为 `USER_MESSAGE` ContextItem（`trust = USER_PROVIDED`）并落盘；不解除任何等待；`NEXT_SAFE_POINT` 时在当前步骤完成后进入下一轮迭代重新决策；必须在 Transcript 可见且与「启动新 Run 的消息」视觉可区分；**不得创建 Grant、改变 Policy、批准 Action**；计入 Budget。

Layer 2 路由表【定】：

| 当前 Run 状态 | 输入去向 |
|---|---|
| `RUNNING` | 进 Interject 队列 |
| `WAITING_FOR_USER` / `WAITING_FOR_APPROVAL` / `WAITING_FOR_INTERACTION` | 匹配当前 `await` 的输入直接满足它；其余进 Interject 队列 |
| `RECOVERY_REQUIRED` | 恢复决策；其余进 Interject 队列 |
| Terminal | 创建新 follow-up Run |

不需要 `targetRequestId` 与 `expectedRunRevision` 做跨进程匹配——等待就是一个 `await`，匹配它的输入直接 resolve 那个 Promise。

【议】D-02：`intent = REDIRECT` 且存在 PENDING Approval 时是否自动撤回。

## 10. Run 领域模型与完成判定

### 10.1 RunStatus 与 RunOutcome

```ts
type RunStatus =
  | "CREATED" | "RUNNING"
  | "WAITING_FOR_USER" | "WAITING_FOR_APPROVAL" | "WAITING_FOR_INTERACTION"
  | "RECOVERY_REQUIRED"
  | "COMPLETED" | "FAILED" | "CANCELLED";
```

【定】终态性：**非终态** `CREATED` / `RUNNING` / `WAITING_FOR_*` / `RECOVERY_REQUIRED`；**终态** `COMPLETED` / `FAILED` / `CANCELLED`。

`WAITING_FOR_*` 不是「循环停下来等一个 durable request」，而是**循环阻塞在一个 `await` 上**。状态值保留是给 Layer 2 与 UI 用的，不驱动调度。

`RECOVERY_REQUIRED` 是 `resume()` 时发现 transcript 里存在无 result 的 tool_use、且副作用状态未知时进入的状态（§18.2）。

```ts
interface RunOutcome {
  kind:
    | "SUCCESS" | "COMPLETED_WITH_LIMITS" | "USER_REJECTED"
    | "BUDGET_EXHAUSTED" | "CONTEXT_EXHAUSTED" | "QUOTA_EXHAUSTED"
    | "CANCELLED" | "FAILED";
  summary?: string;
  deliveredArtifactIds: ArtifactId[];
  incompleteItems: IncompleteItem[];
  recoveryItems: RecoveryItem[];
  error?: RuntimeErrorRecord;
}
```

**`QUOTA_EXHAUSTED` 与 `CONTEXT_EXHAUSTED` 分开**：实测发现配额可能先于上下文窗口撞墙（§16.6），两者处置完全不同——前者等一会儿可能就好了，后者必须压缩。

### 10.2 RunSnapshot

```ts
interface RunSnapshot {
  runId: RunId;
  runSpecId: RunSpecId;
  status: RunStatus;
  currentBatchId?: ActionBatchId;
  waitingOn?: "USER" | "APPROVAL" | "INTERACTION" | "RECOVERY";
  turnCount: number;
  consecutiveFailures: number;
  budgetUsage: BudgetUsage;
  progressState: ProgressState;
  messageCount: number;
  updatedAt: Timestamp;
}
```

**这是一个只读投影，不是恢复来源。** 它服务 UI 展示与 `inspect()`，恢复走 transcript（§18）。

### 10.3 Run 不变量【定】

1. 一个 Run 绑定一个不可变 RunSpec；
2. 配置变化需要创建新 Run；
3. 每个外部副作用关联 Action 和 Attempt；
4. **一个 Run 同时只有一个循环在跑**；
5. **消息先落盘再进内存 `messages`**（§8.3）——transcript 只可能与内存一致或领先；
6. 每次 ModelInvocation 前必须形成通过协议校验的 ContextFrame；
7. 上一批 Tool Call 全部有 result 之前不得发起新的 ModelInvocation；
8. **批内每个 Tool Call 必须有且只有一个 result**；
9. 每次 Action 执行前必须具有 ResolvedEffect、Capability Evidence 和实时 Lease；
10. 未知副作用状态不得自动重试；
11. Budget hard limit、Cancel 和 revoked Capability 不得由模型决定忽略；
12. Run 进入 `COMPLETED` 前必须结算一次 `outcome.kind`，且结算依据必须来自事实表（§10.4）；
13. 未脱敏内容不得写入 transcript 或任何持久化存储；
14. Run 执行期间使用的端点能力声明必须与 RunSpec 冻结的一致；不一致时产生漂移事件并按策略处置（§8.6）。

不变量 7 与 8 由**循环结构**保证（第 ④ 步不结束就到不了第 ⑤ 步）加**三条中断路径的合成 result**（§9.2）。

### 10.4 Run 完成判定【定】

#### 循环终止规则

```text
ModelInvocation 完成
    ↓
响应中是否包含 Tool Call？
    ├── 是 → 执行 ActionBatch（§8.5），构造下一个 LoopState，continue
    └── 否 → return settleOutcome(state)
                ↓
        结算 outcome.kind（只查事实表，不再调用模型）
        ├── 存在未决 RecoveryItem          → RECOVERY_REQUIRED（非终态）
        ├── 存在失败的 required Verification → COMPLETED_WITH_LIMITS + incompleteItems
        └── 其余                            → COMPLETED / SUCCESS
```

> **模型不再请求工具即完成。**

这是标准 Harness 循环的做法。没有独立于模型判断的声明式验收机制，理由三条：

1. **它要求在发出第一个 token 之前就知道「什么算做完」，而这个信息不存在。** 用户说「把这三篇文章归档」，`minCount: 3` 里的 `3` 只存在于自然语言里。要把它变成结构化 criterion，只能在 Run 创建前先调一次模型——那次调用不属于任何 Run，没有 budget 归属、没有失败处置、没有状态机；
2. **它要解决的问题已被其他机制覆盖。** 副作用状态未知由 `RECOVERY_REQUIRED` 这个独立非终态处理，它先于完成判定生效；Eval 的成败判定由 `eval/graders/` 独立实现（§24），本来就不复用生产 Run 的判定路径；
3. **单人使用场景下，人在回路里。** 用户本人在屏幕前，看一眼输出就知道行不行。

#### 保留的一条底线【定】

结算 `outcome.kind` 时**必须查一次 required Verification 的结果**。

这条与「信不信模型」无关：Verification 已经跑过、扣了 token、结果已经写进 `verifications` 表。如果结算时忽略它，等于**花钱测出一个事实然后扔掉**。

典型场景：工具报错，模型在总结里写「已完成，其中一项遇到问题但已跳过」，然后不再调用工具。此时 Run 应结算为 `COMPLETED_WITH_LIMITS` 并把失败项写进 `incompleteItems`，而不是 `SUCCESS`。

```ts
const failed = verifications.filter(v => v.required && v.status === "FAILED");
return failed.length === 0
  ? { kind: "SUCCESS" }
  : { kind: "COMPLETED_WITH_LIMITS", incompleteItems: failed.map(toIncompleteItem) };
```

**这不改变循环何时终止**，只改变终止后打什么标签。终止条件严格是「模型不再请求工具」。

#### 两层 Verification 的关系【定】

| 层 | 问题 | 触发点 |
|---|---|---|
| Action 级 Verification | 这一步的副作用是否达成 | Attempt 完成后 |
| Artifact 级 Verification | 这个产物本身是否完整合法 | ArtifactRegistered 之后 |

两者不得互相替代。**Run 层不提出自己的问题，只汇总前两层已经产生的事实。**

#### 什么情况下需要加一层【验】

不排除将来需要，但必须由证据触发：

- 出现无人值守运行（定时任务、自动化触发），此时没有人在回路里看输出；
- Eval 发现「模型声称完成但实际未完成」的比例高到无法靠人工发现；
- 某个 Case 的交付物有明确、静态、与用户输入无关的结构约束。

形态应当是**在 Case Package 里注册的检查器**，而不是 RunSpec 上的必填字段——因为它逐 Case 变化，不逐 Run 变化。

### 10.5 Cancel 后事实处置【定】

已完成的 Action、Attempt、transcript 条目和 Audit 不删除；已登记 Artifact 保留 lineage 并按验证结果标记；未完成的临时资源按 cleanup/compensation policy 处理；自动 Compensation 必须是新的显式 Action；副作用未知时进入 `RECOVERY_REQUIRED` 或带 `recoveryItems` 的 CANCELLED；用户可见结果必须明确区分**已完成**、**未完成**和**状态未知**三部分。

## 11. Run 内 Context 管理

### 11.1 两级 Context

```text
Session / Product Facts
    ↓ freeze（分段内容寻址，§7.5）
ConversationSourceSnapshot
    ↓ select / cite / compact
Run Working Context
    + Model Responses（含受端点约束的协议块）

    + Observation / Verification
    + User Input & Interjection within this Run
    ↓ materialize under budget，protocol-validate
ContextFrame for one ModelInvocation
```

### 11.2 ContextItem 与协议角色

```ts
type ContextItemKind =
  | "SYSTEM_INSTRUCTION" | "SKILL_DESCRIPTOR" | "SKILL_INSTRUCTION"
  | "USER_MESSAGE" | "USER_INTERJECTION"
  | "ASSISTANT_MESSAGE" | "MODEL_REASONING" | "MODEL_TOOL_CALL"
  | "TOOL_RESULT" | "OBSERVATION" | "VERIFICATION"
  | "ARTIFACT_REFERENCE" | "SUMMARY" | "RESOURCE_EXCERPT" | "SYSTEM_NOTICE";

type ContextTrust =
  | "SYSTEM_TRUSTED" | "USER_PROVIDED" | "MODEL_GENERATED" | "EXTERNAL_UNTRUSTED";

type ContextProtocolRole =
  | "ORDINARY"
  | "PROTOCOL_GROUP_MEMBER"
  | "PLACEHOLDER_REQUIRED"
  | "REQUIRED_VERBATIM"
  | "CACHE_BREAKPOINT";
```

#### 协议角色为什么是三档【实测】

DeepSeek 的 Anthropic 形状上，assistant 回合**不能只有 `tool_use`**——必须带一个 thinking 块。但那个块：

- 内容可以是 Runtime 合成的任意文本；
- `signature` 可以是空串。

也就是说 Runtime **不必保存真实推理内容，但必须保留一个占位块**。这一档比「可自由丢弃」强、比「必须逐字回传」弱：

| 档位 | 含义 | 实测端点 |
|---|---|---|
| 可丢弃（`ORDINARY`） | 块可以整个消失 | 百炼 Anthropic / OpenAI |
| **`PLACEHOLDER_REQUIRED`** | **内容可替换、可摘要、可清空，但块本身不能消失** | DeepSeek Anthropic |
| `REQUIRED_VERBATIM` | 内容必须逐字保留 | 尚未实测到 |

这一档的根因是 **DeepSeek 服务端按 id 持有推理内容**——「推理块可丢弃」在别处成立，是因为那些端点无状态，不是因为协议宽松。

【定】档位由**端点能力声明**的 `context.reasoningBlockRule` 给出，不由 Context 模块推断。

### 11.4 ToolResult Materialization

```text
Raw ToolResult（仅存在于 Adapter 进程内存）
    ↓ RedactionPort.redact()          ← 强制，§22.2
    ↓ schema validate
    ↓ normalize and hash
    ↓ ModelProtocolPort.countTokens()
    ├── small result → inline ContextItem
    └── large result → immutable Blob + preview + retrieval reference
```

【定】脱敏在进入本流程之前已完成；本流程是**预算与表示边界，不是安全边界**。

【端点·百炼 Anthropic】200KB 的单个 tool_result 被接受，计 34576 tokens。因此外置阈值当前由上下文预算决定，**不存在协议硬上限**。

### 11.5 协议要素不变量【定】

1. 属于同一 `protocolGroupId` 的 ContextItem 构成**不可拆分单元**；
2. `REQUIRED_VERBATIM` 的项不得被改写、摘要、截断或重排；
3. **`PLACEHOLDER_REQUIRED` 的项内容可替换，但块本身不得消失**；
4. 一个模型 Tool Call 与其 result 属于同一 protocolGroup；批内每个 call 必须有恰好一个 result；
5. Pair 过大时外置 result 正文，但保留协议合法的结构化 stub；
6. **哪些结构属于哪一档，由「形状适配器 ＋ 端点能力声明」共同给出**，不由 Context 模块猜测；
7. ContextFrame 构建后必须执行 `validateFrame()`，失败不得发起模型调用。

#### 实测清单

| 项目 | 百炼 Anthropic【选定】 | 跨端点情况 |
|---|---|---|
| 推理块可否删除 | **可** | DeepSeek 需占位块 |
| 推理块可否改写 | **可** | 同上 |
| `signature` 可否删除 | **可**（本就是空串） | — |
| 较早轮次推理块可否删 | **可** | DeepSeek 依赖服务端 id |
| tool_result 顺序 | 组间无序要求 | 四端点一致 |
| 闭合事件 | **有 `content_block_stop`** | OpenAI 形状无 |

【端点】**选定端点 `reasoningBlockRule = DROPPABLE`，`irreducibleTokens` 只需覆盖配对组。**

但 Contract 必须能表达另外两档——这正是三轮实测中变化最剧烈的一项。

| Compact 后仍超限 | **主循环决策** |

```ts
}
```

触发策略【定】：优先 Offload 大 Tool Result → soft limit 后自治 Compact → Compact 目标低于 soft limit 形成滞回 → hard limit 且 `irreducibleTokens` 超窗时返回 `COMPACTION_INSUFFICIENT` 交主循环 → Compact 结果是带 source refs 与 hash 的派生对象 → 原始事实不被删除 → 必须保留当前目标、用户约束与插话、未完成 Action、Approval/Wait 状态、关键 Artifact、错误恢复状态、以及全部受协议约束的组。

#### 不可压缩时的默认动作【定·D-05】

`COMPACTION_INSUFFICIENT` 时主循环默认执行**更激进的 Compact**，仍不足则产出 `DETERMINISTIC` handoff（§16.4）。

理由：选定端点的 `count_tokens` **精确到 0.00%**，「即将超限」可以在发请求前精确判定，激进压缩有可靠触发点。

【端点】此结论依赖 `tokens.hasCountTokensEndpoint = true`。切到无预估端点的形状时，触发点退化为本地估算，阈值须相应放宽。

### 11.7 Skill 渐进披露

```ts
interface SkillSnapshot {
  skillId: SkillId;
  version: string;
  contentHash: string;
  name: string;
  description: string;
  activation: "EAGER" | "ON_DEMAND";
  instructionBlobRef: BlobRef;
  resourceRefs: ResourceRef[];
}
```

初始 Context 默认只注入 name/description；v0.1 可以只实现 EAGER，但 Contract 不等同于全量注入。

### 11.8 缓存：可估价规则【定·实测】

四个端点基线全部 4/4 稳定命中（4096–4864 tokens，约 98%）。关键对照条件是**只改前缀第一处** vs **全量改写**：

| 端点 | 基线 | 只改第一处 | 全量改写 | 判定 |
|---|---|---|---|---|
| **百炼(Anthropic)** | 4096 ×4 | **0** | 0 | **严格前缀，全量失效** |
| 百炼(OpenAI) | 4096/4864 ×4 | 0 | 0 | 严格前缀 |
| DeepSeek(Anthropic) | 4864 ×4 | **384** | 384 | 严格前缀，回落到公共前缀 |
| DeepSeek(OpenAI) | 4864 ×4 | 4864 | 4864 | **未判定** |

DeepSeek(Anthropic) 的 384 不是噪声——它恰好等于独立测得的 tools + system 固定前缀。

#### 结论

> **Compact 重写中部的代价 ∝ 改写点有多靠前。** 改写点之后的缓存全丢，之前的保留。

这把「追加式外置优于重写式压缩」从倾向变成**可估价规则**：

- 把大结果移到尾部并留引用（不动前缀）→ 缓存全保住；
- 重写中部 → 损失改写点之后的全部命中，损失量可由 `count_tokens` 精确预估。

`CACHE_BREAKPOINT` 的价值因此明确：**标记「此处之前不得改写」**，Compact 优先在断点之后动刀。

【端点】DeepSeek(OpenAI) 形状全量改写前缀后仍报满额命中，与任何基于内容的缓存都不相容。**在查清之前，不得用该端点的 `cached_tokens` 做成本核算。**

【验】未解答：缓存 TTL（需间隔重跑）；`cacheMatching = "UNKNOWN"` 时的保守策略。

### 13.1 多维 RuntimeErrorRecord


【定·D-22】**四个维度全部保留**——结构经三轮实测验证。**阶段 1 值域裁剪到 Micro Case 能真正触发的**，未触发的枚举值留在类型定义里但不产生，避免写出没有任何用例检验过的分类逻辑。

#### `MODEL_SDK` 的实测依据

`max_tokens: 99999999` 被 Anthropic SDK **自己拦截**（提示需要流式），根本没发出请求。

没有这个 source，这类错误会被误归类为 `MODEL_PROVIDER`——进而影响 retryability 判断（SDK 层的参数校验错误重试多少次都没用）。

#### `QUOTA` 的实测依据

见 §16.6。配额与 rate limit 处置不同：前者可能需要等很久或换端点，后者退避重试即可。

### 13.2 判别式按端点维护【定·实测】

四个端点的错误判别式**没有任何两个可以共用一张表**：

| 触发 | 百炼(Anthropic)【选定】 | 百炼(OpenAI) | DeepSeek(两形状) |
|---|---|---|---|
| 无效模型名 | 400，无 type/code | **404 / `model_not_found`** | 400 / `invalid_request_error` |
| 无效 API Key | 401，无 type/code | 401 / `invalid_api_key` | 401 / `invalid_request_error` |
| 请求体格式错 | 400，无 type/code | 400 / `invalid_parameter_error` | 400 / `invalid_request_error` |
| tool 定义 schema 非法 | **200 接受** | **200 接受** | **400 ＋ 精确诊断** |
| 缺 `max_tokens` | 400 | — | **200 接受** |

【端点·百炼 Anthropic】**连 `type` / `code` 字段都没有**，message 也最简短（`Model not exist.`）。判别式只能是 `HTTP_STATUS + MESSAGE_MATCH`。

【定】映射表进端点能力声明的 `errors.mappingRulesRef`，**不写进适配器**。

### 13.3 处置

```ts
type ErrorDisposition =
  | "RETRY_AUTOMATICALLY" | "RETURN_TO_MODEL" | "SKIP_REMAINING_BATCH"
  | "REQUEST_APPROVAL" | "REQUEST_USER_INPUT"
  | "ENTER_RECOVERY" | "FAIL_RUN";
```

【定】`sideEffectState = "UNKNOWN"` 时**不得** `RETRY_AUTOMATICALLY`（不变量 10）。

【定】错误分类与副作用状态是**两个独立维度**，不得合并——「请求超时」不告诉你副作用发没发生。

## 15. Observation 与 Verification

### 15.1 所有权【定】

主循环决定何时需要 Observation 与 Verification；Verification Runtime 按 Descriptor 选择 Verifier；Verifier 通过受限 Port 读取环境或调用只读 Tool；Case Package 提供业务 verifier，Runtime Core 拥有执行、超时、Trace 和处置语义。

**Tool Handler 的 "success" 不能替代独立 Verification。**

### 15.2 VerificationDescriptor

```ts
interface VerificationDescriptor {
  mode: "NONE" | "INLINE_RESULT" | "REOBSERVE" | "CUSTOM_VERIFIER";
  verifierRef?: VersionedRef<Verifier>;
  requiredForSuccess: boolean;
  observationCost: "LOW" | "MEDIUM" | "HIGH";
  timeoutMs?: number;
  staleAfterMs?: number;
  retryPolicy?: RetryPolicy;
}
```

`requiredForSuccess` 直接决定 §10.4 的 outcome 结算——这是 Verification 在本版被抬高的地方：它是**唯一一个能把 `SUCCESS` 降级为 `COMPLETED_WITH_LIMITS` 的信号**。

### 15.3 何时重新观察【定】

高影响副作用、外部状态写入、Artifact 交付原则上重新观察；纯函数或带可验证返回对象的低风险 Tool 可用 inline result；Observation 成本高时可指定采样或延迟验证；`resume()` 后超过 `staleAfterMs`、precondition 变化或 Grant 变化必须重新观察；Verification 失败不自动等于可重试。

**Observation 在消息级恢复下有额外职责**：它是 §18.2 那三条分支里唯一能回答「那个工具到底跑没跑」的手段。

## 16. Budget、进展与优雅停止

### 16.1 RunBudgets

```ts
interface RunBudgets {
  maxTurns: number;
  maxActiveWallClockMs: number;
  maxTotalWallClockMs?: number;
  maxModelCalls?: number;
  maxToolCalls?: number;
  maxInputTokens?: number;
  maxOutputTokens?: number;
  maxEstimatedCost?: Money;
  maxConsecutiveFailures: number;
  softLimitRatio: number;
  handoffReserve?: HandoffReserve;
}
```

【定】墙钟拆分：`maxActiveWallClockMs` 只累计 `RUNNING` 且有在途步骤的时间；`WAITING_*` / `RECOVERY_REQUIRED` 不累计。

#### 固定开销轴【定·实测】

| 项 | 数值 |
|---|---|
| **tool 定义固定开销** | **360 tokens**（2 个只有一个字符串参数的工具，四端点一致，百炼 OpenAI 测得 361） |
| **每请求固定底数** | 百炼 **5** tokens；DeepSeek **84** tokens（**差 17 倍**） |

折合每工具约 180 token。**20 个工具就是约 3600 token 的起步价，与任务内容无关。**

【定】`ContextFrame.fixedOverheadTokens` 单列，§11.6 的阈值判断必须先扣除它，否则「还剩多少上下文可用」算错。

【端点】每请求固定底数是**端点属性**，同一个模型换平台就变，进 `tokens.perRequestBaseTokens`。

#### `reservedOutputTokens` 必须覆盖推理【定·实测】

```text
max_completion_tokens: 64
finish_reason: "length"
content: ""                                       ← 正文为空
completion_tokens_details.reasoning_tokens: 64    ← 预算全被推理吃掉
```

在两个独立探针中复现。**接口成功、无错误码、内容为空。**

两处约束：

1. `reservedOutputTokens` 必须**同时覆盖推理与正文**；
2. 主循环消费 `ModelInvocationResult` 时，把「`finish_reason=length` 且无内容且无 tool call」识别为明确错误条件（`source: MODEL_PROVIDER, category: CAPACITY`），**而不是正常完成**。

否则 Runtime 会把空回复当作模型的正常回答继续推进，产生一次静默的错误决策。

### 16.2 Progress Guard

至少检查：轮次数与连续失败；相同 Tool + normalized input + effect digest 连续重复；多个不同调用但状态无变化；相同错误和相同模型修正循环；Compact 后仍无法满足窗口；长时间没有进展证据。

```ts
interface ProgressReportingDescriptor {
  mode: "NONE" | "HEARTBEAT" | "MONOTONIC_PROGRESS";
  intervalMs?: number;
}
```

【定】声明 `HEARTBEAT` / `MONOTONIC_PROGRESS` 的长时 Tool 必须周期性回报进展（低频，30s 量级）。Progress Guard 基于这个回报判定「还活着」，**不基于流式 delta**——否则长媒体下载会被误判无进展。

**进展回报不持久化**：它只服务进程内的 Progress Guard 与 UI；进程死了 Run 就结束，没有「恢复后判断上次进展到哪」这个需求。

### 16.3 Soft 与 Hard Limit【定】

Soft limit：阻止启动普通新步骤，可用预留预算生成 handoff、请求用户缩小范围或交付部分结果。
Hard limit：不得再调用模型或有副作用 Tool，立即形成稳定 Outcome。
**没有 handoff reserve 时不得为「优雅总结」突破 hard limit。**

### 16.4 两类 Handoff【定】

```ts
type HandoffKind = "MODEL_AUTHORED" | "DETERMINISTIC";
```

| 类型 | 触发 | 生成方式 |
|---|---|---|
| `MODEL_AUTHORED` | Budget soft limit | 用 `handoffReserve` 发起受限模型调用 |
| `DETERMINISTIC` | Context hard limit、模型不可用、配额耗尽 | 由模板从事实表生成，**不经模型** |

`DETERMINISTIC` handoff 的内容全部来自事实表：已完成 Action、已注册 Artifact 及验证状态、失败的 required Verification、`incompleteItems`、`recoveryItems`、错误摘要。

**注意 `DETERMINISTIC` handoff 恰好是「模型不再请求工具」这个信号缺席的场景**——撞墙时模型没有机会说完成。此时 outcome 由 §16.1 的墙决定，不走 §10.4 的循环终止路径，handoff 负责把「做到哪了」讲清楚。

### 16.5 计数口径【定】

**turn** = 一轮完整迭代（编译 → 调模型 → 执行批）。ContextFrame 编译、Compact、Observation、Verification 不单独计数，各有独立上限。失败后重试的 ModelInvocation 计入 `maxModelCalls` 但不增加 `turnCount`。

**consecutiveFailures** 归零条件：任一 Action 执行成功且其 required Verification 通过。Context 编译失败、Compact 失败不计入；模型协议错误计入；被 Policy/用户拒绝的 Action 不计入失败。

### 16.6 配额可能先于上下文窗口撞墙【定·实测】

【端点】百炼的 **OpenAI 形状**对 60 万 token 的单请求稳定返回 `429 insufficient_quota`；同平台的 **Anthropic 形状接受同一个 payload**。

> **在长上下文场景下，配额是先于上下文窗口撞上的那堵墙。**

三条应对：

1. `EndpointLimits.quotaBeforeContextLimit` 进端点能力声明；
2. `category: QUOTA` 与 `RATE_LIMIT` 分开——前者可能需要等很久或换端点，后者退避重试即可；
3. `RunOutcome.kind` 的 `QUOTA_EXHAUSTED` 与 `CONTEXT_EXHAUSTED` 区分：后者必须压缩上下文，前者压缩没用。

**选定端点的 `quotaBeforeContextLimit = false`**，但这一条随时可能变——它取决于账号配额而非协议。

```ts
    attemptId?: AttemptId;
  };
  kind: ArtifactKind;
  role: "INTERMEDIATE" | "RESULT" | "DELIVERABLE";
  resourceRef: ResourceRef;
  checksum: string;
  mediaType?: string;
  status: "REGISTERED" | "VERIFIED" | "PARTIAL" | "INVALID" | "SUPERSEDED" | "DELETED";
  lineage: {
    inputResourceRefs: ResourceRef[];
    parentArtifactIds: ArtifactId[];
  };
  verification?: ArtifactVerification;
  retention: "PINNED" | "NORMAL";
  version: number;
  createdAt: Timestamp;
}
```

【定】Artifact 必须关联来源 Run；内容变化形成新版本；删除优先 Tombstone；Deliverable 原则上必须 Verified；Cancel 不删除 lineage；Runtime Blob 不自动升级为 Artifact。

## 18. 持久化、Resume 与 Replay

### 18.1 恢复粒度的选择【定】

```text
transcript（消息级 append-only 日志） + immutable Blob
```

**恢复的唯一来源是 transcript。** 没有状态 Snapshot，没有事件重放重建，没有 generation 校验。

`resume(runId)` = 读该 Run 的 transcript → 重建 `messages` 数组 → 从下一轮迭代继续。

#### 代价【定】

> **崩溃时正在执行的工具，那次执行丢失。**

恢复后从上一条已落盘的消息边界重来——如果那个工具做了非幂等的写，它会被执行第二次。

这不是疏漏，是明确选择的权衡：

| 换来 | 付出 |
|---|---|
| 整章从 12 条恢复分支缩到 3 条 | mid-turn 保证消失 |
| 无 Directive / Activity / generation / Run Lock / Snapshot | `idempotency` 从可选属性变成前提 |
| Replay 起点是「第 N 条消息」而不是「Event sequence ＋ 对应 Snapshot」 | 配对不变量失去纯函数可测性 |

理由：单人使用、单进程、绝大多数工具幂等或可验证。

**这个取舍是否成立，由阶段 2 用真实数据回答**（§28.3）。

### 18.2 三个 crash 窗口

消息级恢复把窗口合并成 3 个，因为「消息是否落盘」是唯一的一致性边界：

| 窗口 | 现象 | 处置 |
|---|---|---|
| **A** | 模型响应已落盘，工具尚未执行完 | transcript 里有 tool_use 无 result |
| **B** | 工具已执行，result 未落盘 | 同上——盘上看不出区别 |
| **C** | Blob 已写入但引用消息未落盘 | 孤儿 Blob，由 GC 清理 |

**A 与 B 在 transcript 上无法区分**，这是消息级恢复的本质限制：**你不知道那个工具到底跑没跑。**

因此 `resume()` 的处置规则【定】：

```text
transcript 末尾存在无 result 的 tool_use
    ├── 该 Tool 声明为幂等或只读 → 合成中断 result，重新执行
    ├── 该 Tool 有可用的 Observation → 先观察外部世界，据结果决定
    └── 其余（非幂等、无法观察）    → RECOVERY_REQUIRED，交用户决定
```

【定】未知副作用状态不得自动重试（不变量 10）。第三条分支是这条不变量在消息级恢复下的落点。

### 18.3 外部世界重新校验【定】

`resume()` 时必须检查：Capability Binding 是否撤销或降级；Grant / Secret / Browser Session / Lease 是否过期；输入 Resource contentHash 是否变化；Action target fingerprint 是否变化；Artifact 或外部对象是否被用户修改；Verification 结果是否已过 `staleAfterMs`；**端点能力声明是否仍与 RunSpec 冻结的一致**（不变量 14）。

```text
unchanged                      → continue
changed but safely resolvable  → re-resolve / re-observe / re-prepare
effect or digest changed       → policy + approval again
endpoint profile drifted       → 按 §8.6 漂移策略处置
requires user choice           → WAITING_FOR_USER / RECOVERY_REQUIRED
cannot establish safe state    → fail or cancel with recovery report
```

**恢复粒度变粗不改变这一节**——`resume()` 之间的间隔反而可能更长。

### 18.4 Resume 与 Replay【定】

**Resume**：继续同一个非 Terminal Run，保留 RunId、RunSpec、已完成副作用和预算使用。从 transcript 重建 `messages`，按 §18.2 处置末尾的未配对 tool_use。

**Replay**：为调试或 Eval 创建隔离的重放执行。使用 RecordedModelPort / RecordedToolHandlerPort；默认不触发真实副作用；从 transcript 的任意消息位置开始；产生新的 replay identity，引用原 Run 但不改写；区分 exact recorded replay 与 live rerun；**live rerun 必须创建新 RunSpec/Run，并重新经过 Capability 和 Policy**。

【定】**Replay 使用 RunSpec 冻结的端点能力声明，不使用当前配置**（§7.7）。三个月后重放一个旧 Run，如果用今天的端点行为去判断当时的帧是否合法，结论没有意义。

### 18.5 transcript 格式

```ts
interface TranscriptEntry {
  runId: RunId;
  sequence: number;              // 单调递增，同一 Run 内唯一
  schemaVersion: number;
  kind: "MESSAGE" | "COMPACT_BOUNDARY" | "BLOB_REF" | "RUN_META";
  message?: ContextMessage;      // 已脱敏
  createdAt: Timestamp;
}
```

【定】append-only，每行一个 JSON。**只追加，不改写**——Compact 通过写入 `COMPACT_BOUNDARY` 表达，重建时从最后一个 boundary 之后开始取，boundary 之前的原文保留供 Trace 与 Replay 使用。

【定】`schemaVersion` 不兼容时，重建器必须能跳过或 upcast 单条，而不是整个 transcript 失效。**这是日志方案相对 Snapshot 方案最实在的收益**：Snapshot 是全有或全无，日志可以逐条降级。

### 18.6 等待与超时【定】

在单进程循环里，等待就是 `await`：Approval 等待是 `await decider(...)`，工具超时是 `AbortSignal.timeout()`，墙钟预算是循环里比一个时间戳。进程死了，所有等待一起死——这与「进程死了 Run 就结束」是一致的。

| 需要定时的场景 | 实现 |
|---|---|
| Approval / Wait / Interaction 过期 | `await` ＋ `AbortSignal.timeout()` |
| 单步超时 | 每步的 signal timeout（§8.3） |
| 墙钟预算 | 循环内比对时间戳（§16.1） |
| Lease 过期 / Observation 过期 | **惰性判定**——使用时比对 `expiresAt`（§18.3） |

## 19. Event、Trace 与 Usage

### 19.1 RunEvent

```ts
interface RunEvent {
  schemaVersion: number;
  type: string;
  runId: RunId;
  sequence: number;          // 与 transcript 同一条序列（§18.5）
  batchId?: ActionBatchId;
  actionId?: ActionId;
  occurredAt: Timestamp;
  payload: JsonValue;
}
```

**Event 不是独立的持久化轨道。** 它从 generator yield 给消费方（§8.1），由 Trace 侧自行落盘用于诊断，**恢复不读它**（§18.1）。

### 19.2 事件清单

Run 生命周期：RunStarted / StatusChanged / Completed / Failed / Cancelled。
**循环迁移：TurnStarted / LoopContinued（带 `transition.reason`）/ LoopTerminated（带 `Terminal.reason`）**。
模型与批：ModelInvocationCompleted / ActionBatchPlanned / ActionBatchSettled。
Action：ActionProposed / ActionRejected / ActionPrepared / AttemptStarted / AttemptCompleted。
审批与交互：ApprovalRequested / Decided / Expired；InteractionRequested / Completed / Expired。
Context：ContextFrameCompiled / ContextCompacted / BlobExternalized。
验证与产物：ObservationCompleted / VerificationCompleted；ArtifactRegistered / Verified / Superseded。
预算与限额：BudgetSoftLimitReached / BudgetHardLimitReached / ContextLimitReached / QuotaExhausted。
恢复与安全：RecoveryRequired / RecoveryDecisionApplied；RedactionApplied；**EndpointBehaviorDrift**（§8.6）。

**`LoopContinued` / `LoopTerminated` 携带 §8.2 的具名 reason。** 这是循环纪律第 2 条在可观测侧的落点：**Trace 里能直接读出走了哪条恢复路径**，不必去比对消息内容。

流式 delta、细粒度 Tool Progress、Download Progress 只 yield 不落盘。

### 19.3 Model usage 与计费输入公式【定·实测】

```ts
interface ModelUsage {
  inputTokens: number;
  outputTokens: number;
  cacheCreationInputTokens?: number;
  cacheReadInputTokens?: number;
  reasoningTokens?: number;
  billedInputTokens: number;      // 派生
}
```

**计费输入公式**：

```text
billedInputTokens = inputTokens + cacheReadInputTokens + cacheCreationInputTokens
```

【定】**只读 `input_tokens` 会在缓存命中时严重低估**——实测缓存命中时 `input_tokens` 只剩非缓存部分，低估可达 85%。

这个陷阱本身就是 Spike 第三轮探针的一个缺陷，写进架构是为了让实现不再踩第二次。

【端点】公式与形状相关，进端点能力声明的 `tokens.billedInputFormula` 与 `usageFieldMap`。

## 20. Human Takeover / External Interaction

### 20.1 定位【定】

Human Takeover 是显式的**等待—人工操作—重新观察**协议，不是绕过 Runtime 的隐藏操作。

### 20.2 ExternalInteractionRequest

```ts
interface ExternalInteractionRequest {
  id: InteractionRequestId;
  runId: RunId;
  actionId?: ActionId;
  capabilityId: CapabilityId;
  resourceHandleRef: ResourceHandleRef;
  parkedLeaseId: LeaseId;
  interactionType: "BROWSER_TAKEOVER" | "TERMINAL_TAKEOVER" | "MANUAL_RECOVERY";
  instructions: string;
  expectedCompletion: string;
  expiresAt?: Timestamp;
  status: "OPEN" | "COMPLETED" | "EXPIRED" | "CANCELLED";
}
```

### 20.3 运行语义【定】

```text
Runtime 请求接管
    ↓ PARK the capability lease（不释放回池，绑定 interactionRequestId）
Run → WAITING_FOR_INTERACTION（循环阻塞在 await）
    ↓ Layer 2/UI 授予受限的人工控制
用户操作外部资源（进入 Product Audit）
    ↓ 完成信号 resolve 该 await
Runtime UNPARK the lease（原 owner 重获）
    ↓ 重新 Observation ＋ Verification
continue / re-plan / ask user / fail
```

`PARKED` 而非释放，是为了防止释放与重获之间被其他 Run 抢占 EXCLUSIVE lease。

**完成信号不等于任务成功，必须重新 Observation。**

```ts
type LeaseStatus = "HELD" | "PARKED" | "RELEASED" | "EXPIRED";

interface CapabilityLease {
  id: LeaseId;
  capabilityBindingId: CapabilityBindingId;
  concurrencyKey?: string;
  ownerRunId: RunId;
  parkedForInteractionId?: InteractionRequestId;
  status: LeaseStatus;
  expiresAt: Timestamp;
  lastHeartbeatAt: Timestamp;
}
```

【定】Browser Session、交互式终端使用 EXCLUSIVE/KEYED lease；Crash 后通过过期释放，不依赖进程内引用计数；`PARKED` 期间其他 Run 不可获取。过期判定是惰性的（§18.6）。

## 22. 安全、脱敏与数据边界

### 22.1 Workspace Scope【定】

文件操作使用 ResourceRef；验证 Workspace、Mount、规范化路径和 symlink；CapabilityGrant 不能扩大 Binding Scope；ResolvedEffect 必须是 Grant Scope 的子集；Adapter 执行时再验证实际目标；Workspace 外写入必须由新的明确授权覆盖。

### 22.2 脱敏发生点【定】

```text
Tool Handler 原始输出（仅存在于 Adapter 进程内存）
    ↓ RedactionPort.redact(raw, profile)     ← 强制，不可跳过
RedactedOutcome + RedactionReport
    ├── 落盘为 transcript 条目 / Blob            ← 已脱敏
    ├── 进入 Context Materialization             ← 预算与表示裁剪
    ├── 进入 Trace / 诊断 Blob                   ← 已脱敏
    └── 进入 RunEvent payload                    ← 已脱敏
```

1. 未脱敏原文不得离开 Adapter 边界；
2. `RedactionProfile` 来自 `CapabilityBinding.redactionProfileRef` 与 `ToolDefinition.redaction` 的合并；
3. Tool 必须声明 `redaction`，未声明走最严格 profile；
4. **脱敏失败 = Tool 失败**（`source: TOOL_HANDLER, category: REDACTION`），不得降级为原样保存；
5. `RedactionReport` 记录脱敏字段与字节数，不记录被脱敏的内容本身；
6. Context Materialization 的过滤是**预算边界，不是安全边界**。

【议】D-06：是否允许在任何情况下保留未脱敏原文。

### 22.3 Secret 与凭证【定】

数据库、RunSpec、Context、Trace 只保存 SecretRef；Secret 明文仅在 Adapter 执行阶段短暂解析；Cookie、Token、浏览器存储不进入模型；向外发送本地数据时 ResolvedEffect 明确记录 data movement、目的地和数据范围。

**【定】凭证只能发往它所属 Endpoint 的 `baseUrl`**（§6.2）。这条在 Spike 0 期间被实际违反过一次——环境变量优先级导致第三方 Key 发往官方端点。它是不变量，不是注意事项，实现上应有显式断言。

### 22.4 不可信内容【定】

网页、文件、邮件和 ToolResult 默认 `EXTERNAL_UNTRUSTED`；ContextItem 保存来源与 trust，ContextFrame 汇总为 `trustSummary`；不可信内容中的文字不能创建 Grant、改变 Policy 或自动批准 Action；用户插话同样不能；高影响副作用独立经过 Effect Resolution、Policy 和 Approval；Approval UI 展示真实目标与 preview；**不把「Policy 能可靠判断每个参数是否由某段网页导致」作为安全前提**。

### 22.5 数据保留与回收【定】

| 类别 | 策略 |
|---|---|
| transcript、事实表行 | **永不删除** |
| Artifact lineage | 永不物理删除，Tombstone |
| Deliverable Artifact 内容 | 永久保留，除非用户显式删除 |
| 非交付 Runtime Blob | 超期可回收，**必须留 hash + size + 摘要 stub** |
| 诊断 Blob | 按 `maxAgeDays` 回收 |
| Transcript 投影（Layer 2） | 可重建，可回收 |
| 孤儿 Blob | 定期扫描回收 |

参与 Eval fixture 或 GoldenTrace 的 Run 与 Artifact 标记 `PINNED`，不进 GC。

【议】D-10：默认保留窗口与回收倾向。

### 22.6 本地前后端通信【定】

随机端口或受控 Socket；会话级鉴权 Token；Origin 校验；禁止外部网页调用本地 API；SSE/WS 重连游标；人工接管通道绑定 InteractionRequest 和 ResourceHandle。

### 22.7 第三方模型端点的数据边界【定】

#### 问题

本项目的运行环境是第三方 SaaS 端点，因此：

> **每一次 ModelInvocation 本身就是一次数据外发。**

「向外发送本地数据时记录 data movement」通常指 Tool 的副作用（上传文件之类），**模型调用容易被当成纯计算**。

后果具体：脱敏只针对凭证。网页正文、本地文件内容、Git 仓库内容不是凭证，不会被脱敏，会完整发给第三方。Case 01 是登录态网页归档——登录后的页面可能是私人邮件或内部文档。

#### 规则

1. **模型端点是一个 data movement 目的地**，与「上传文件到外部系统」同类，只是发生频率高得多；
2. Endpoint 定义必须声明数据边界属性（`EndpointDataBoundary`，§6.2），作为 Workspace 绑定端点时的展示信息；
3. **Workspace 级配置决定哪些 Mount 的内容允许外发给哪个端点**；超出范围的内容进入 Context 前必须被 Policy 拦截或降级为摘要；
4. §11.4 的「大结果外置到 Blob + 只发 preview」**同时是数据最小化机制**——外置的内容不进模型也就不出境。阈值调整需同时考虑预算与数据边界两个方向。

【验】具体的 Workspace × Endpoint 授权矩阵形态待阶段 3（D-19）。v0.1 只需在 Endpoint 定义上记录属性并在 UI 展示。

## 23. 跨层聚合的所有权与一致性

### 23.1 原则【定】

> **Layer 3 拥有执行事实，Layer 2 拥有产品聚合，通过单向投影。**

| 对象 | Layer 3（权威执行状态） | Layer 2（权威产品状态） | 冲突裁决 |
|---|---|---|---|
| Approval | ApprovalRequested / Decided 事件 | `approvals` 表 | 执行语义以 Runtime 事件为准 |
| Artifact | ArtifactRegistered / Verified 事件 | `artifacts` 表 | 同上 |
| Transcript | transcript 条目 | `transcript_entries` 投影 | 同上 |

### 23.2 一致性协议【定】

1. **消息追加到 transcript 必须先于内存 `messages` 更新**（不变量 5）；
2. 跨层投影通过 transcript `sequence` 游标拉取，幂等，至少一次；
3. Layer 2 聚合中的执行语义字段是投影结果，不得独立推进；
4. Layer 2 可拥有的独立字段：用户可见标题、手工标记、归档状态、UI 排序、retention PIN；
5. Runtime 需要读取 Layer 2 状态时只能通过 Port，且只能作为 **precondition fingerprint**，不能作为循环输入——否则 Layer 3 的可恢复性会依赖 Layer 2 当前状态，破坏 Replay。

【议】D-04：Artifact 的用户手工操作如何回流到 precondition 校验。

### 24.3 故障注入集

至少覆盖：Model 流式中断、timeout、rate limit、**quota**；一次响应多个 Tool Call 且部分失败/被拒/中途取消；响应含受约束协议块且随后触发 Compact；Tool 在副作用前/中/后崩溃；**tool_use 已落盘但 result 未落盘**；批部分结算时崩溃；执行中/等待审批中的用户插话；Approval 到达时 Action 已变化；Cancel 与步骤完成竞态；Capability 撤销、Grant/Lease 过期、**PARKED lease 超时**；文件变化、Artifact 冲突、浏览器 Session 失效；Context 过大、protocol group compact、Blob 取回；上下文 hard limit 且不可压缩；Budget soft/hard limit 与无进展循环；长下载期间无进展检测不误杀；磁盘空间不足；脱敏失败；**transcript 条目 schema 不兼容**；**端点能力声明漂移**。

### 24.4 Micro Cases

**Session 与 Run 基础**：第二轮正确引用上一轮事实；Session A/B 上下文隔离；Compact 后保留关键约束；WAITING_FOR_USER 后继续原 Run；普通 follow-up 创建新 Run；Session 归档后拒绝新输入；`resume()` 后继续等待状态；修改 Skill 配置不影响已启动 Run。

**Harness 核心**：多 Tool 选择；信息不足时请求用户输入；Tool Schema 错误与自动修正；Tool 失败后的替代路径；执行后的环境验证；Approval 的拒绝与恢复；中途崩溃后 `resume()` 继续；无进展检测与安全停止。

**不变量对应**：

- 一次响应两个 Tool Call，全部执行且各有 result；
- 一次响应两个 Tool Call，第二个被 Policy 拒绝，仍合成合法 result 且**第三个继续执行**（D-21）；
- 执行中插话，下一次决策采纳了插话内容；
- 模型声称完成但存在失败的 required Verification，Run 结算为 `COMPLETED_WITH_LIMITS` 而非 `SUCCESS`；
- 上下文不可压缩，产出 DETERMINISTIC handoff 且未调用模型；
- Tool 未声明 redaction，走最严格 profile；
- 端点声明 `reasoningBlockRule = PLACEHOLDER_REQUIRED` 时，Compact 保留占位块；
- 端点声明 `validatesToolResultPairing = false` 时，Runtime 自己发现配对缺失；
- 实际行为与端点声明不符时产生漂移事件；
- **`resume()` 遇到无 result 的 tool_use，按幂等性走三条分支中的正确一条**。

### 24.5 Eval 记录

Case、Dataset、AgentSpec、RunSpec、**EndpointCapabilityProfile**；Provider、模型、Prompt、Skill、Tool 和 Adapter 版本；ContextFrame、Compact、retrieval 轨迹与 `irreducibleTokens` / `fixedOverheadTokens`；RunEvent、ActionBatch 结算、Tool 输入输出、ErrorRecord；Capability、ResolvedEffect、Approval；Verification、`outcome.kind` 结算依据、Artifact、BudgetUsage；Token、耗时、调用次数、`billedInputTokens`、估算成本；确定性检查、LLM Judge 和必要人工评价。

### 24.6 端点能力回归【定】

端点声明是快照，**必须定期重新验证**。`packages/endpoint-probe/` 从 Spike 0 的探针演化而来但**进主干**——因为这是长期需要。

回归内容：重跑探针套件，与冻结声明比对，差异形成报告。

**阶段 2 增加 DeepSeek Anthropic 形状作为对照端点**：它会校验协议不变量，因此能作为 Runtime 自持逻辑的免费正确性测试（§0.3）。

【验】回归频率与自动化程度待阶段 2 确定。阶段 1 手工触发即可。

## 25. 关键运行流程

### 25.1 新 Session Message 启动 Run

```text
persist UserMessage
    ↓ extend / freeze ConversationSourceSnapshot（分段内容寻址）
    ↓ resolve AgentSpec + WorkspaceExecutionSnapshot
    ↓ 从 Endpoint Registry 取 EndpointCapabilityProfile 并冻结
    ↓ persist immutable RunSpec
    ↓ Runtime.start → 进入主循环第 ⓪ 步
    ↓ for await (RunEvent)
    ↓ Layer 2 projects Transcript and final AssistantMessage
```

### 25.2 ActionBatch 执行

```text
ModelInvocation 完成
    ↓ 形状适配器识别全部 Tool Call
    ↓ 形成 ActionBatch（PLANNED）
    ↓ 逐条：normalize → schema validate（Runtime 自持）→ 落库 PROPOSED
    ↓ 逐条：resolve effect + preconditions → PREPARED
    ↓ 逐条：frozen grant check → live capability check → lease
    ↓ preview / policy / approval
    ↓ 逐条：persist Attempt Intent → 执行
    ↓ 边界脱敏 → materialize ToolResult or ErrorRecord
    ↓ Observation / Verification
    ↓ 为每个 call 合成恰好一个 result
    ↓ 全部 result 落盘（transcript）
    ↓ ActionBatchSettled
    ↓ state = { ...next, transition: { reason: "NEXT_TURN" } }; continue
```

### 25.3 WAITING_FOR_USER

```text
主循环 await 用户输入（+ AbortSignal.timeout）
    ↓ 状态标记 WAITING_FOR_USER，Layer 2 投影问题
    ↓ 用户消息 resolve 该 Promise
    ↓ 消息落盘 → 进 messages → 继续本轮
```

不匹配当前等待的用户消息按 §9.3 路由表处理——在非终态 Run 上进 Interject 队列。

**进程死亡则该等待消失。** `resume()` 时主循环重新走到同一位置，重新提问。

### 25.4 Approval

```text
PreparedAction / ActionBatch + preview + digest
    ↓ await approvalDecider(action)（+ AbortSignal.timeout）
    ↓ Run WAITING_FOR_APPROVAL，Layer 2 投影待批
    ↓ 用户决策 resolve
    ↓ validate approval / target / digest / live capability
    ↓ execute / reject（合成 result，继续下一条）/ timeout / re-prepare
```

### 25.5 Cancel

```text
cancel() → AbortController.abort()
    ↓ 当前步骤协作式停止
    ↓ 批内未启动 Action → SKIPPED + 合成 result
    ↓ determine side-effect state
    ├── known safe → CANCELLED
    ├── applied    → preserve fact/artifact, then CANCELLED
    └── unknown    → RECOVERY_REQUIRED or CANCELLED with recoveryItems
```

### 25.6 Run 完成

```text
ModelInvocation 完成且无 Tool Call
    ↓ return settleOutcome(state)
    ↓ 结算 outcome.kind（只查事实表）
    ├── 存在未决 RecoveryItem           → RECOVERY_REQUIRED
    ├── 存在失败的 required Verification → COMPLETED_WITH_LIMITS + incompleteItems
    └── 其余                             → SUCCESS
```

### 25.7 Resume

```text
读 transcript，重建 messages（从最后一个 COMPACT_BOUNDARY 之后）
    ↓ revalidate capability / environment / preconditions / endpoint profile（§18.3）
    ↓ 检查末尾是否存在无 result 的 tool_use
    ├── 幂等或只读       → 合成中断 result，重新执行
    ├── 有 Observation   → 先观察外部世界，据结果决定
    └── 非幂等且不可观察  → RECOVERY_REQUIRED，交用户决定
    ↓ 进入主循环第 ⓪ 步
```

**这里没有「不重复已证明完成的副作用」这一步。** 消息级恢复下，「工具跑没跑」在 transcript 上不可区分（§18.2），这个保证做不到——只能靠幂等声明与 Observation 逼近。

### 26.4 SQLite 实现约束【验】

**没有 Run Lock**——一个 Run 一个循环，无并发提交（不变量 4）。多 Run 并发仍需要验证 SQLite 在多 Writer 下的表现，但不再有 lock 表设计问题。

## 31. 最终架构摘要

```text
Workspace 冻结资源、配置与授权证据
        ↓
Session 冻结不可变 ConversationSourceSnapshot
        ↓
Layer 2 生成自包含 RunSpec（含端点能力声明）
        ↓
主循环单线推进，每轮迭代显式构造下一个 LoopState
        ↓
形状适配器构造与解析协议，端点能力声明给出校验强度与常量
        ↓
主循环只消费规范化结果（不读端点声明）
        ↓
一次模型响应的全部 Tool Call 构成 ActionBatch，每个 call 恰好一个 result
        ↓
Context Runtime 管理 ToolResult、Blob、协议组、预算和 Compact
        ↓
Action Runtime 解析真实 Effect，经过 Grant / Lease / Policy / Approval
        ↓
Observation 与 Verification 判断外部世界是否达到目标
        ↓
模型不再请求工具即终止循环，outcome.kind 由事实表结算
        ↓
transcript 逐条落盘，resume 从消息边界继续，Replay 从任意消息位置重放
        ↓
Layer 2 将执行事实投影为 Message、Tool、Approval、Interaction 和 Artifact
```

### 十条执行边界

1. **循环状态与迁移原因必须显式**，恢复粒度必须写明代价；
2. 模型看见的 Context 必须经过可追踪、可预算、协议合法的编译；
3. 所有副作用必须先得到可信的 EffectScope，再谈 Policy、Approval 和重试；
4. 恢复不是重新跑一遍；取消、未知副作用、实时撤权和外部变化都有明确处置；
5. 一次模型响应可能产生多个动作。批的原子性、审批粒度、配对完整性和取消语义必须一起定义；
6. Run 必须知道自己什么时候算做完了。每一步都验证过，不等于整件事做成了；
7. 安全边界在数据离开执行边界的那一刻，而不是在它进入模型的那一刻；
8. **协议不变量没有外部兜底。** 选定端点上缺 tool_result、错 tool_call_id 一律 200 放行。不变量的理据不是「否则接口会报错」，而是「否则模型看到的世界是错的」——执行责任 100% 在 Runtime，且**没有任何东西会替你发现违反**；
9. **端点行为是数据，不是代码。** 第二轮十条结论有六条换端点失效，而变量隔离已经做得很干净。任何「某个 Provider 会怎么表现」的结论只能以端点能力声明的形式存在，冻结进 RunSpec，并在实际行为偏离时 fail fast；
10. **恢复粒度是一个显式取舍，不是一个默认值。** 本版选择消息级：`resume()` 从上一条已落盘的消息继续，代价是崩溃时在跑的工具会重跑。这个代价必须写在架构里，因为它把「Tool 是否幂等」从一个可选属性变成了恢复正确性的前提。

### 两条方法论边界

> **一、证据先于冻结，且证据本身有保质期。**
>
> 【定】/【验】/【议】三种标记强制前半句，【端点】标记强制后半句——把「仅对某端点成立的结论」与「跨端点不变量」在文档层面分开，用 §8.6 让前者以数据形式存在，用 §24.6 让它被定期重新验证。

> **二、「必须存在某个机制」同样需要证据。**
>
> V03 的 15 个决策点里有 3 个被证明**问题本身不该问**。规格在没有运行经验时会长出自己的问题，而这些问题看起来和真问题一模一样。删掉一个拿不出证据的机制，与新增一个有证据的机制，是同一条纪律的两面。

在此基础上，WorkAgent 可以先用单 Agent 主循环、单形状适配器、单端点完成 Walking Skeleton 和真实 Case；换端点是配置变更，换形状是新增一个适配器，都不需要推翻当前三层架构。
