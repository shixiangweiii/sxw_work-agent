## 1. 文档目的

本文档在当前上位讨论基线之下，给出 WorkAgent 第一版完整架构设计初稿，用于回答以下问题：

1. WorkAgent 产品、Application Service 和 Harness Runtime 如何分层；
2. Workspace、Session 和 Run 分别是什么，三者如何协作；
3. Chat 能力如何作为 WorkAgent 的基础能力存在，同时不绑死 Headless Runtime；
4. Workspace 如何成为资源、授权和能力配置的核心边界；
5. Skill、MCP、Plugin、Shell、Browser、CLI、API、Tool 和 Capability 如何区分；
6. Layer 2 与 Layer 3 之间如何建立稳定、可恢复、可评测的 Contract；
7. Message、Transcript、Trace、Audit、Artifact 和 Approval 的事实来源与产品投影如何分开；
8. 同进程部署下如何保持清晰的代码依赖和领域所有权；
9. 后续 Walking Skeleton 应以什么模块结构实现。

本文档是架构设计初稿，不替代上位目标和架构原则基线。若本文档与上位基线冲突，以上位基线为准，并应通过 ADR 记录后续调整。

## 2. 二次反思后的核心结论

### 2.1 三个“中心”不冲突

经过二次反思，Workspace、Session、Run 不应该争夺同一个“核心对象”位置。它们分别处于三个不同维度：

```text
Workspace：资源、授权和工作环境中心
Session：持续交互和意图演进中心
Run：Agent 单次执行和恢复中心
```

因此，最重要的关系不是“谁替代谁”，而是：

```text
Workspace
  └── Session
        └── Run
```

- Workspace 回答：AI 在哪里工作，可以访问什么；
- Session 回答：用户和 AI 围绕什么持续交流；
- Run 回答：Agent 针对一次输入实际执行了什么。

### 2.2 Session 是产品基础能力，但不是 Runtime 强制前提

WorkAgent 必须包含 ChatAgent 的基础能力。真实工作通常不能通过单轮输入完整表达，用户会持续进行：

- 目标澄清；
- 约束补充；
- 方案讨论；
- 执行授权；
- 过程纠偏；
- 结果反馈；
- 基于已有成果的下一轮工作。

因此，Session 是 WorkAgent 产品中的一等领域对象。

但是，Case 无关的 Harness Runtime 仍然必须支持无 Session 的执行：

- CLI 直接执行任务；
- Eval Runner 执行 EvalCase；
- 自动化任务；
- 故障注入；
- Headless Micro Case。

最终结论是：

> Session 是 WorkAgent Application Service 的基础对象；RunSpec 可以携带 Session Context，但 Harness Runtime 不依赖 Session CRUD，也不要求每个 Run 都属于 Session。

### 2.3 v0.1 暂不单独建立 Task Aggregate

在当前产品阶段，Task 与 Session 容易形成高度重叠的双重模型：

- Session 已经包含标题、工作目标、多轮交流、多个 Run 和最终 Artifact；
- 暂无 Deadline、负责人、任务依赖、跨 Session 任务跟踪等独立 Task 需求。

因此，v0.1 使用 `WorkSession` 表达一条持续工作的 Thread，暂不单独引入 Task Aggregate。

未来出现以下需求时再拆出 Task：

- 一个任务跨多个 Session；
- 一个 Session 同时讨论多个独立任务；
- 后台任务脱离聊天持续运行；
- 任务具有期限、优先级、依赖和状态管理；
- 与 TODO、日程、自动化系统集成。

### 2.4 Capability 可以统一产品心智，但不能抹平内部语义

前端可以把 Skill、MCP、Plugin、Shell、Browser、CLI 和 API 统一展示在“能力中心”中。

内部领域模型必须保留区别：

- Capability：对某类资源执行操作的能力和授权语义；
- Tool：模型可调用的具体操作；
- Skill：注入 Context 的版本化指令和知识；
- MCP：Tool、Resource、Prompt 的协议 Provider；
- Plugin：贡献 Skill、Tool、Provider、Adapter 或 UI Renderer 的安装和组装单元；
- Adapter：连接具体外部技术的实现。

### 2.5 Layer 2 和 Layer 3 的职责必须通过 Port 和 Snapshot 解耦

Layer 2 管理长期、可变的产品配置；Layer 3 执行一次不可变的 Run。

```text
Layer 2 Control Plane
    ↓ 解析和冻结
AgentSpecSnapshot + WorkspaceExecutionSnapshot + RunSpec
    ↓
Layer 3 Execution Data Plane
```

Layer 3 不访问 Layer 2 的 Session、Workspace、Skill 或 MCP 数据库。Layer 3 所需的外部能力通过其自己定义的 Port 注入，由 Layer 2 的 Composition Root 完成组装。

## 3. 架构目标与原则

### 3.1 架构目标

本架构需要支持：

1. 面向真实 Workspace 的持续工作；
2. 多轮聊天和意图澄清；
3. 无 Session 的 Headless Run；
4. Case 无关的 Agent Harness；
5. Tool、Skill、MCP、Plugin 和本地能力接入；
6. 可观察、可恢复、可审计的执行；
7. Eval、故障注入和实验对比；
8. 桌面 UI、CLI 和 Eval Runner 复用同一个 Runtime；
9. 后续 Planning、Verifier、Memory、Sub-agent 等策略的可插拔演进。

### 3.2 架构原则

#### 原则一：产品事实、运行事实和产品投影分离

- User Message、Workspace 配置属于产品事实；
- Run、Action、Attempt、Observation、Verification 属于运行事实；
- Assistant Message、Tool Card、Approval Card、Artifact Card 可以是运行事实的产品投影。

#### 原则二：可变配置在 Run 启动时冻结

Workspace、Skill、Plugin、MCP、Tool Schema、Policy 和 Agent 配置变化，不能静默改变已经启动的 Run。

#### 原则三：外部副作用前持久化意图

对文件写入、Shell、Browser 操作、外部消息和 API 调用：

```text
先持久化 PreparedAction / Attempt Intent
再执行副作用
再持久化结果
最后进入下一次决策
```

#### 原则四：Runtime Core 依赖抽象，不依赖产品服务

Layer 3 定义 Port；Adapter 实现 Port；Layer 2 只负责组装。

#### 原则五：Session History 不等于 Model Context

Session 保存完整事实记录，Context Compiler 按策略选择、裁剪、引用和 Compact。

#### 原则六：Trace 是事实，UI 卡片是投影

UI 不直接依赖 Provider 原始 Tool Call 或 Runtime 内部表结构。

#### 原则七：进程边界不等于架构边界

Layer 2 与 Layer 3 初期位于同一个 Node.js 进程，通过类型化的 In-process API 调用，但保持独立模块、单向依赖和独立测试。

```text
│                                                            │

                │                               │
                ▼                               ▼
┌───────────────────────────┐      ┌──────────────────────────┐

                                   └──────────────────────────┘
```

### 4.1 静态依赖方向

```text
WorkAgent UI
    ↓
Application API Contracts
    ↓
WorkAgent Application Service
    ↓
Harness Runtime Public Facade
    ↓
Harness Runtime Internal Modules

Infrastructure Adapters
    → implements Harness Runtime Ports

Case Packages
    → depends on Capability / Tool Extension SDK

Eval Lab
    → depends on Runtime Public Facade
```

禁止出现：

```text
Harness Runtime → WorkAgent Application Service
Harness Runtime → WorkAgent UI
Harness Runtime → Eval Lab
Harness Runtime → 具体 Case Package
Kernel → SQLite / Electron / Chrome / MCP SDK
```

## 5. Layer 1：WorkAgent UI

### 5.1 职责

- Workspace 选择、创建、归档和状态展示；
- Session 创建、切换、重命名和归档；
- 多轮 User/Assistant Message；
- 附件上传、文件选择和 Artifact 引用；
- Assistant 文本流式展示；
- Tool Card、Attempt、Verification 状态展示；
- Approval Request 展示和决策提交；
- Run 暂停、恢复、取消和重新执行；
- Artifact 预览、打开、下载和标记交付；
- Skill、MCP、Plugin 和 Capability 配置 UI；
- Trace 和 Eval Inspector 的后续产品界面。

### 5.2 UI 不拥有的语义

- Action 是否允许执行；
- Capability 是否已经授予；
- Run 合法状态迁移；
- Tool 是否应该重试；
- Postcondition 是否通过；
- Agent 是否继续循环；
- Crash 后从哪个阶段恢复。

### 5.3 Transcript 而非纯 Message List

UI 展示的 Session 内容是 Transcript：

```text
TranscriptEntry
├── UserMessageEntry
├── AssistantMessageEntry
├── ProgressEntry
├── ToolActionEntry
├── ApprovalEntry
├── ArtifactEntry
└── SystemNoticeEntry
```

Tool、Approval、Artifact 不伪装成普通 Assistant Message。

### 5.4 前后端协议

初期建议：

- HTTP Command：创建 Session、发送消息、启动/取消 Run、提交审批；
- HTTP Query：查询 Workspace、Session、Message、Artifact、配置；
- SSE：Assistant Delta、Run 状态、Tool 状态、Approval、Artifact；
- WebSocket：只在终端、浏览器人工接管等明确双向实时场景引入。

不建议初期同时为所有功能维护 SSE 和 WebSocket 两套事件协议。

## 6. Layer 2：WorkAgent Application Service / Harness Host

Layer 2 是产品 Control Plane，也是 Layer 3 的进程宿主和 Composition Root。

### 6.1 逻辑模块

```text
workagent-application/
├── workspace/
├── resources/
├── sessions/
├── capabilities/
├── skills/
├── mcp/
├── plugins/
├── policies/
├── artifacts/
├── approvals/
├── audit/
├── runtime-host/
├── projections/
└── api/
```

### 6.2 Workspace 模块

负责：

- Workspace 生命周期；
- PrimaryFileSpace；
- ResourceScope；
- Workspace 默认 Policy；
- Workspace Revision；
- Workspace 当前配置汇总；
- 归档和恢复。

### 6.3 Resource 模块

负责：

- 本地目录授权；
- Managed Upload；
- ResourceMount；
- ResourceRef 解析；
- 路径规范化与越界检查；
- 文件元数据；
- 输入 Attachment；
- Artifact Storage 的物理实现。

### 6.4 Session 模块

负责：

- WorkSession 生命周期；
- User Message 持久化；
- Assistant Message 产品投影；
- Transcript 查询；
- Session 与 Run 关联；
- Session Context Cursor；
- Pinned Resource；
- Session 归档。

### 6.5 Capability Control Plane

负责：

- Capability Definition Catalog；
- Workspace Capability Binding；
- Provider 配置；
- Scope 配置；
- SecretRef 管理；
- 健康检查；
- 启用、禁用和撤销；
- Run 启动时生成 CapabilityGrant。

### 6.6 Skill、MCP 和 Plugin

- Skill Manager 管理 SkillDefinition、版本、安装和 Workspace Binding；
- MCP Manager 管理 ServerDefinition、连接配置、Tool Discovery 和状态；
- Plugin Manager 管理安装、版本、Workspace 启用和 Contribution；
- Plugin Marketplace 不属于当前阶段目标；
- Layer 3 不访问这些 Manager，只接收冻结后的 Snapshot 和注册后的 Runtime Extension。

### 6.7 Runtime Host

负责：

- 创建并配置 Harness Runtime；
- 注入 Model、Storage、Tool、Artifact、Trace 等 Port；
- 从 Workspace 和 Session 创建 RunSpec；
- 进程启动时恢复未结束 Run；
- 将用户输入和 Approval 转成 RuntimeSignal；
- 接收 RunEvent；
- 将 RunEvent 投影为 Session Transcript 和 UI Event；
- 进程退出时协调暂停或持久化。

Runtime Host 不实现 Agent Loop，也不直接修改 Runtime 内部状态表。

## 7. Layer 3：Harness Runtime

### 7.1 定位

Harness Runtime 是 Case 无关的生产级 Agent 执行核心。

它拥有 Harness 领域语义，但不拥有具体业务语义。

它理解：

- Run；
- AgentSpecSnapshot；
- RunSpec；
- ContextItem；
- ModelInvocation；
- ProposedAction；
- PreparedAction；
- ExecutionAttempt；
- Observation；
- Verification；
- ArtifactRef；
- CapabilityGrant；
- Approval；
- TraceEvent。

它不理解：

- 网页文章和 Markdown 归档；
- Git PR 和某个仓库业务规则；
- 钉钉消息语义；
- Word、Excel、PPT 领域逻辑；
- Session UI 如何展示；
- Electron 生命周期。

### 7.2 内部模块

```text
harness-runtime/
├── facade/
├── coordinator/
├── kernel/
├── context/
├── model/
├── action/
├── tool-runtime/
├── policy/
├── verification/
├── durability/
├── artifact/
├── trace/
└── ports/
```

### 7.3 Runtime Facade

建议最小接口：

```ts
interface HarnessRuntime {
  start(spec: RunSpec): Promise<RunHandle>;
  resume(runId: RunId): Promise<RunHandle>;
  signal(runId: RunId, signal: RuntimeSignal): Promise<void>;
  cancel(runId: RunId, reason?: string): Promise<void>;
  inspect(runId: RunId): Promise<RunSnapshot>;
  subscribe(runId: RunId): AsyncIterable<RunEvent>;
}
```

### 7.4 Run Coordinator

Run Coordinator 是 Layer 3 内部的 durable orchestration shell：

- 获取 Run Lock；
- 加载 RunSnapshot；
- 调用 Kernel 推进；
- 持久化 KernelDirective；
- 调用 Model Runtime 或 Tool Runtime；
- 保存外部结果；
- 将结果重新交给 Kernel；
- 处理 RuntimeSignal；
- 处理 Crash Resume；
- 释放 Run Lock。

Layer 2 的 Runtime Host 管理进程和实例，Layer 3 的 Run Coordinator 管理一次 Run 的可靠推进，两者不可混淆。

### 7.5 Kernel

Kernel 负责最小执行语义：

```text
Observe
   ↓
Assemble Context
   ↓
Decide
   ↓
Prepare Action
   ↓
Act
   ↓
Observe Result
   ↓
Verify
   ↓
Continue / Wait / Complete / Fail
```

推荐接口形态：

```ts
interface AgentKernel {
  advance(
    state: KernelState,
    input: KernelInput,
  ): KernelTransition;
}
```

```ts
type KernelDirective =
  | RequestModelDirective
  | PrepareActionDirective
  | ExecuteActionDirective
  | VerifyActionDirective
  | WaitForApprovalDirective
  | WaitForUserDirective
  | CompleteRunDirective
  | FailRunDirective;
```

Kernel 不直接访问网络、SQLite、文件系统或 Layer 2 Service。

### 7.6 Runtime Ports

建议由 Layer 3 定义以下 Port：

```ts
interface ModelPort {}
interface RunStorePort {}
interface RunLockPort {}
interface ToolHandlerPort {}
interface ArtifactStorePort {}
interface ContextCheckpointStorePort {}
interface TraceSinkPort {}
interface BlobStorePort {}
interface ClockPort {}
interface IdGeneratorPort {}
interface SecretResolverPort {}
```

Adapter 实现这些 Port，由 Layer 2 Composition Root 注入。

## 8. Workspace 领域模型

### 8.1 Workspace 定义

> Workspace 是 AI 被授权完成一组真实工作的持久化工作上下文、资源作用域和能力边界。文件空间是核心锚点，但不是 Workspace 的全部。

```ts
interface Workspace {
  id: WorkspaceId;
  name: string;
  description?: string;

  status: "ACTIVE" | "ARCHIVED";

  resourceScopeId: ResourceScopeId;
  policyBindingId: PolicyBindingId;

  revision: number;

  createdAt: Timestamp;
  updatedAt: Timestamp;
  archivedAt?: Timestamp;
}
```

Workspace 是产品组织和授权边界，不是包含所有子对象的巨型事务聚合。

### 8.2 Workspace 关系

```text
Workspace
├── ResourceScope        1:1
├── CapabilityBinding   1:N
├── SkillBinding        1:N
├── PluginBinding       1:N
├── PolicyBinding       1:1
├── WorkSession         1:N
├── Artifact            1:N
├── Approval            1:N
└── AuditEvent          1:N
```

### 8.3 Workspace 不变量

1. 必须存在一个 PrimaryFileSpace；
2. 只有 ACTIVE Workspace 可以创建 Session 和 Run；
3. 所有写操作必须落在明确授权的 ResourceMount；
4. 执行语义相关变更必须增加 revision；
5. Secret 只保存 SecretRef，不保存明文；
6. 归档后保留历史 Session、Run、Artifact 和 Audit；
7. 归档前必须显式处理 Active Run。

### 8.4 ResourceScope

```ts
interface ResourceScope {
  id: ResourceScopeId;
  workspaceId: WorkspaceId;

  primaryMountId: ResourceMountId;
  mounts: ResourceMount[];

  revision: number;
}
```

```ts
interface ResourceMount {
  id: ResourceMountId;

  kind:
    | "MANAGED_ROOT"
    | "LOCAL_DIRECTORY"
    | "MANAGED_UPLOADS"
    | "ARTIFACT_STORAGE";

  locator: ResourceLocator;
  accessMode: "READ_ONLY" | "READ_WRITE";
  pathRules?: PathScopeRules;

  status: "ACTIVE" | "UNAVAILABLE" | "REVOKED";
  revision: number;
}
```

不要求把 Mount 下的每个普通文件登记为数据库领域对象。

### 8.5 ResourceRef

```ts
interface ResourceRef {
  workspaceId: WorkspaceId;
  mountId: ResourceMountId;
  relativePath: string;

  contentHash?: string;
  size?: number;
  mediaType?: string;
}
```

规则：

- relativePath 必须规范化；
- 禁止路径逃逸；
- 绝对路径只由 Filesystem Adapter 解析；
- 重要输入通过 contentHash 固化版本；
- 外部目录必须先成为 ResourceMount。

## 9. Session 领域模型

### 9.1 WorkSession 定义

> WorkSession 是 Workspace 内围绕一个持续演进的工作意图建立的交互线程。

内部使用 `WorkSession`，UI 和 API 可以简称 `Session`，以避免和 BrowserSession、ProviderSession 混淆。

```ts
interface WorkSession {
  id: SessionId;
  workspaceId: WorkspaceId;

  title: string;
  objective?: string;

  status: "ACTIVE" | "ARCHIVED";

  agentProfileRef?: AgentProfileRef;
  contextPolicyRef?: ContextPolicyRef;

  revision: number;

  createdAt: Timestamp;
  updatedAt: Timestamp;
  archivedAt?: Timestamp;
}
```

### 9.2 Session 职责

- 组织多轮对话；
- 保存 User Message；
- 关联 Assistant Message 投影；
- 关联多个 Run；
- 组织用户可见 Transcript；
- 保存 Pinned Resource；
- 为下一次 Run 提供显式 Conversation History；
- 支持在同一 Workspace 内隔离不同工作线程。

### 9.3 Session 不负责

- Workspace 文件授权；
- Agent Loop；
- Tool 执行；
- Policy 决策；
- Run Crash Recovery；
- Runtime Trace 的内部持久化；
- 跨 Session 长期 Memory。

### 9.4 SessionMessage

```ts
interface SessionMessage {
  id: MessageId;
  workspaceId: WorkspaceId;
  sessionId: SessionId;

  role: "USER" | "ASSISTANT";
  content: MessageContent;
  attachmentRefs: ResourceRef[];

  source:
    | { kind: "USER" }
    | { kind: "RUN"; runId: RunId };

  status: "FINAL" | "INTERRUPTED";
  createdAt: Timestamp;
}
```

User Message 是产品事实；Assistant Message 应关联来源 Run。

流式 Delta 是 Transient Event，最终消息是 Durable Projection。

### 9.5 TranscriptEntry

```ts
type TranscriptEntry =
  | UserMessageEntry
  | AssistantMessageEntry
  | ProgressEntry
  | ToolActionEntry
  | ApprovalEntry
  | ArtifactEntry
  | SystemNoticeEntry;
```

Transcript 是 Layer 2 的可重建读模型。每个投影项应尽量保存 `sourceRunId`、`sourceEventId` 或 `sourceActionId`。

### 9.6 Session 与 Run

```text
WorkSession 1 ── N Run
Run         0..1 ── 1 WorkSession
```

Run 的 Session 是可选的。

普通用户后续输入通常创建新 Run：

```text
User Message 1 → Run 1 → Assistant Message
User Message 2 → Run 2 → Assistant Message
```

当 Run 明确进入 `WAITING_FOR_USER` 时，用户补充输入继续原 Run：

```text
Run WAITING_FOR_USER
    ↓
UserInputSignal
    ↓
Resume same Run
```

Approval Decision 同样不创建新 Run。

### 9.7 Session 并发规则

v0.1 建议一个 Session 同时只允许一个 Foreground Active Run，以保证 Transcript 顺序和交互语义清晰。

后续若引入 Background Run 或 Sub-agent，可显式增加：

- Foreground Run；
- Background Run；
- Parent Run；
- Child Run。

不应在 v0.1 隐式支持多个 Run 同时写入同一 Transcript。

## 10. Session Context 与 Context Compiler

### 10.1 原始历史与模型上下文分离

```text
Session Raw History
├── User / Assistant Messages
├── Run Outcomes
├── Tool Actions
├── Artifacts
└── Approval Records
        │
        ▼
Conversation Context Source
        │
        ▼
Context Compiler
├── Select
├── Filter
├── Order
├── Cite
├── Compact
└── Budget
        │
        ▼
Model Context
```

Session History 是事实记录，Compact 结果是派生对象。Compact 不覆盖或删除原始 Message。

### 10.2 ConversationContextCheckpoint

```ts
interface ConversationContextCheckpoint {
  id: ContextCheckpointId;
  sessionId: SessionId;

  coveredUntilMessageId: MessageId;
  sourceMessageIds: MessageId[];

  summary: string;
  compilerVersion: string;
  modelRef?: ModelRef;
  contentHash: string;

  createdAt: Timestamp;
}
```

同一 Session 可以存在不同 Context Policy、Compiler 或模型产生的多个 Checkpoint，用于 Eval 对比。

Context Checkpoint 是一个跨层对象：Layer 3 的 Context Compiler 产生 Checkpoint Candidate，Layer 2 的 Session 模块通过 `ContextCheckpointStorePort` 保存并关联 Session。Layer 3 只持有 CheckpointRef，不直接访问 Session Repository。

### 10.3 Session History 与 Memory

基础能力：

- 当前 Session 的显式消息历史；
- 当前 Session 的 Artifact；
- 用户显式 Pin 的资源；
- Session 内 Context Compact。

高级 Memory：

- 跨 Session 自动提取偏好；
- 跨 Workspace 知识；
- 自动长期记忆；
- 语义检索历史 Run；
- 自动更新用户画像。

因此 Session History 是基础能力，Cross-session Memory 仍属于后续高级策略。

## 11. AgentSpecSnapshot、WorkspaceExecutionSnapshot 与 RunSpec

### 11.1 AgentSpecSnapshot

```ts
interface AgentSpecSnapshot {
  agentSpecId: AgentSpecId;
  version: string;
  contentHash: string;

  model: ModelConfigurationSnapshot;
  systemPrompt: PromptSnapshot;

  toolSnapshots: ToolSnapshot[];
  skillSnapshots: SkillSnapshot[];

  contextPolicy: ContextPolicySnapshot;
  loopPolicy: LoopPolicySnapshot;
  approvalPolicy: ApprovalPolicySnapshot;
}
```

这里的 AgentSpecSnapshot 是 Run 启动时得到的“有效配置”，不是对可变 Agent Profile 的简单引用。Layer 2 需要把 Agent Profile 的选择与 Workspace 当前启用的 Skill、Tool、Plugin Contribution 进行解析，得到最终可见的 ToolSnapshot 和 SkillSnapshot。

### 11.2 WorkspaceExecutionSnapshot

```ts
interface WorkspaceExecutionSnapshot {
  workspaceId: WorkspaceId;
  workspaceRevision: number;

  resourceGrants: ResourceGrant[];
  capabilityGrants: CapabilityGrant[];

  capabilityBindingVersions: VersionedBindingRef[];
  skillBindingVersions: VersionedBindingRef[];
  pluginContributionVersions: PluginContributionRef[];

  policySnapshot: PolicySnapshot;
  workspaceEnvironmentFingerprint: EnvironmentFingerprint;
}
```

它不是整个文件系统的物理副本，而是 Workspace 权限、Binding 版本和关键环境信息的快照。最终可见的 ToolSnapshot 和 SkillSnapshot 只保存在有效 AgentSpecSnapshot 中，避免同一个 Run 出现两份相互冲突的 Tool/Skill 配置。

### 11.3 RunOrigin

```ts
interface RunOrigin {
  kind: "SESSION" | "CLI" | "EVAL" | "AUTOMATION";

  workspaceId?: WorkspaceId;
  sessionId?: SessionId;
  triggerMessageId?: MessageId;

  evalCaseId?: EvalCaseId;
  automationId?: AutomationId;
}
```

### 11.4 RunSpec

```ts
interface RunSpec {
  id: RunSpecId;
  origin: RunOrigin;

  input: RunInput;

  agentSpec: AgentSpecSnapshot;
  workspace?: WorkspaceExecutionSnapshot;

  conversationContext?: {
    sessionId: SessionId;
    transcriptCursor: MessageId;
    messageSnapshots: MessageSnapshot[];
    contextCheckpointRefs: ContextCheckpointRef[];
    pinnedResourceRefs: ResourceRef[];
  };

  budgets: RunBudgets;
  runtimeEnvironmentFingerprint: EnvironmentFingerprint;

  createdAt: Timestamp;
}
```

`transcriptCursor` 明确本次 Run 启动时看到了 Session 的哪个位置。后续 Message 不得静默进入已经启动的上下文。

## 12. Run 领域模型

### 12.1 Run 状态

```ts
type RunStatus =
  | "CREATED"
  | "RUNNING"
  | "WAITING_FOR_USER"
  | "WAITING_FOR_APPROVAL"
  | "PAUSED"
  | "COMPLETED"
  | "FAILED"
  | "CANCELLED";
```

### 12.2 RunSnapshot

```ts
interface RunSnapshot {
  runId: RunId;
  runSpecId: RunSpecId;
  status: RunStatus;

  currentPhase: RunPhase;
  currentActionId?: ActionId;

  decisionStep: number;
  consecutiveFailures: number;
  progressState: ProgressState;

  lastDurableEventSequence: number;
  updatedAt: Timestamp;
}
```

### 12.3 Run 不变量

1. 一个 Run 绑定一个不可变 RunSpec；
2. 配置变化需要创建新 Run；
3. Approval 和用户补充输入可以恢复原 Run；
4. 每次外部副作用都必须关联 Action 和 Attempt；
5. Terminal Run 不得继续推进；
6. 同一 Run 同时只有一个 Coordinator 持有推进锁；
7. 所有状态迁移必须产生 Durable Event。

```ts
interface CapabilityDefinition {
```

```ts
interface CapabilityBinding {
```

```ts
interface CapabilityGrant {
```

### 13.5 Skill

### 13.6 MCP

### 13.7 Plugin

- Skill；
- CapabilityProvider；
- ToolDefinition；
- Adapter；
- MCP Server Definition；
- Tool UI Renderer。

区分：

- PluginInstallation：机器上安装的版本；
- WorkspacePluginBinding：某 Workspace 是否启用；

- PluginSnapshot：某次 Run 实际使用的贡献版本。

## 14. Tool 和 Action 生命周期

### 14.1 对象区分

```text
Provider Tool Call
       ↓ normalize
ProposedAction
       ↓ schema / capability / policy
PreparedAction
       ↓ execute one or more times
ExecutionAttempt
       ↓
ToolResult
       ↓ observe environment
Observation
       ↓
Verification
       ↓
Succeeded / Retry / Wait / Recover / Fail
```

### 14.2 所有权

- Kernel：ProposedAction、逻辑 Action 状态及后续决策；
- Tool Runtime：Schema、Registry、PreparedAction、Attempt、Retry、Idempotency；
- Policy Runtime：Capability、Effect、Approval 判断；
- Adapter/Handler：具体副作用；
- Verification：执行后环境状态验证；
- Application Service：Approval 产品记录和 UI 投影。

### 14.3 ToolDefinition

```ts
interface ToolDefinition {
  id: ToolId;
  version: string;
  name: string;
  description: string;

  inputSchema: JsonSchema;
  outputSchema?: JsonSchema;

  requiredCapabilities: CapabilityRequirement[];
  effect: EffectDescriptor;

  retryPolicy: RetryPolicy;
  idempotency: IdempotencyDescriptor;
  verification: VerificationDescriptor;
  compensation?: CompensationDescriptor;
}
```

### 14.4 粗粒度 Tool 原则

Tool 应暴露具有 Agent 决策价值的语义动作，确定性细节留在 Handler 内。

例如网页归档优先暴露：

```text
inspect_page
archive_web_page
verify_archive
```

而不是让模型分别决定每一次 mkdir、下载单张图片、写单行 Markdown。

## 15. Artifact 模型

### 15.1 定义

Artifact 是被 Runtime 显式登记、具有来源、版本、验证和交付意义的产物，不等于 Workspace 中的任意普通文件。

```ts
interface Artifact {
  id: ArtifactId;
  workspaceId: WorkspaceId;

  producer: {
    runId: RunId;
    actionId?: ActionId;
    attemptId?: AttemptId;
  };

  kind: ArtifactKind;
  role: "INTERMEDIATE" | "RESULT" | "DELIVERABLE";

  resourceRef: ResourceRef;
  checksum: string;
  mediaType?: string;

  status:
    | "REGISTERED"
    | "VERIFIED"
    | "INVALID"
    | "SUPERSEDED"
    | "DELETED";

  lineage: {
    inputResourceRefs: ResourceRef[];
    parentArtifactIds: ArtifactId[];
  };

  verification?: ArtifactVerification;
  version: number;
  createdAt: Timestamp;
}
```

### 15.2 跨层职责

Layer 3：

- 产生 ArtifactRegistration；
- 关联 Run、Action、Attempt；
- 将 ArtifactRef 写入 Trace；
- 使用 Artifact 进行 Verification。

Layer 2：

- 保存 Artifact 元数据；
- 管理实际文件；
- 归属 Workspace 和 Session；
- 查询、预览、打开、下载；
- 标记 Deliverable；
- 保留、版本和软删除。

通过 `ArtifactStorePort` 连接。

### 15.3 Artifact 不变量

1. 必须属于 Workspace；
2. 必须关联来源 Run；
3. 必须保存 checksum；
4. 内容变化形成新版本；
5. 删除优先 Tombstone；
6. Deliverable 原则上必须 Verified；
7. 临时文件不要求全部登记。

## 16. Policy 与 Approval

### 16.1 PolicyBinding

```text
Layer 3 Policy Engine
    ↓ ApprovalRequired
```


`actionDigest` 确保用户批准的是当时展示的 Action 参数。

## 17. Trace、Audit、Message 和 Event

### 17.1 四类数据

| 类型 | 所有者 | 用途 |
|---|---|---|
| Session Message | Layer 2 | 用户可见对话事实与最终回复 |
| Runtime Trace | Layer 3 | Run 执行事实、诊断、恢复和 Eval |
| Product Audit | Layer 2 | Workspace、能力、审批和产物管理审计 |
| UI Event | Layer 2 Projection | 驱动前端实时展示 |

### 17.2 Durable Event 与 Transient Event

Durable Event：

- RunStarted；
- ModelInvocationCompleted；
- ActionPrepared；
- AttemptStarted/Completed；
- ApprovalRequested/Decided；
- VerificationCompleted；
- ArtifactRegistered；
- RunCompleted/Failed/Cancelled。

Transient Event：

- Model Text Delta；
- Tool Progress；
- Download Progress；
- Heartbeat；
- 临时状态提示。

Transient Event 不参与恢复事实判断；必要的最终结果必须转成 Durable Event。

### 17.3 UI Event Envelope

```ts
interface UiEventEnvelope<T> {
  eventId: string;
  type: string;
  schemaVersion: number;

  workspaceId?: WorkspaceId;
  sessionId?: SessionId;
  runId?: RunId;

  sequence?: number;
  durable: boolean;
  occurredAt: Timestamp;

  payload: T;
}
```

UI 只依赖稳定的产品事件协议，不直接依赖 Runtime 内部 Event Class。

### 17.4 Product Audit

Product Audit 记录：

- Workspace 创建、归档；
- 目录授权和撤销；
- Skill、MCP、Plugin 变化；
- Capability 启停；
- Policy 变化；
- Approval Decision；
- Artifact 导出、删除和标记交付。

Runtime Trace 和 Product Audit 可以在 UI 中统一查询，但不应合并成一张万能事件表。

## 18. Durable Execution 与持久化

### 18.1 混合持久化模型

采用：

```text
事实表 + Durable Event + Snapshot
```

- 事实表提供当前状态查询；
- Durable Event 提供审计、Trace 和恢复证据；
- Snapshot 提供快速恢复；
- 不追求纯 Event Sourcing。

### 18.2 建议的逻辑表所有权

Layer 2 Product Tables：

```text
workspaces
resource_scopes
resource_mounts
capability_bindings
skill_bindings
plugin_bindings
policy_bindings
work_sessions
session_messages
transcript_entries
context_checkpoints
artifacts
approvals
product_audit_events
```

Layer 3 Runtime Tables：

```text
agent_spec_snapshots
run_specs
runs
run_events
run_snapshots
model_invocations
actions
execution_attempts
observations
verifications
runtime_blob_refs
```

初期可以使用同一个 SQLite 文件，但：

- Repository 和 Migration 所有权分开；
- Layer 3 不直接查询 Layer 2 表；
- Layer 2 不直接修改 Layer 3 表；
- 跨边界读取通过 Public API 或 Projection 完成。

### 18.3 Crash Recovery 基本语义

恢复时至少区分：

1. Directive 尚未执行；
2. Attempt Intent 已保存但执行尚未开始；
3. 外部调用可能已发生但结果未知；
4. ToolResult 已获得但尚未持久化；
5. Result 已持久化但尚未 Verification；
6. Verification 已完成但 Kernel 尚未推进。

对于“外部调用是否已经发生”不确定的状态，必须依赖：

- 幂等键；
- 外部状态查询；
- Postcondition Observation；
- 人工恢复；
- Compensation。

不能简单无条件重试。

## 19. 关键运行流程

### 19.1 新 Session 消息启动 Run

```text
User sends message
    ↓
Layer 2 persist UserMessage
    ↓
RunSpecFactory resolves Workspace / Session / Agent snapshots
    ↓
Persist immutable RunSpec
    ↓
Runtime.start(RunSpec)
    ↓
RunEvent stream
    ↓
Layer 2 projects Transcript and AssistantMessage
    ↓
UI receives SSE events
```

### 19.2 Run 内等待用户

```text
Kernel detects missing information
    ↓
Run → WAITING_FOR_USER
    ↓
UserInputRequested Event
    ↓
Layer 2 renders question in Session
    ↓
User replies
    ↓
Layer 2 persists message and sends UserInputSignal
    ↓
Runtime resumes same Run
```

### 19.3 Tool Approval

```text
Model proposes Tool Call
    ↓
Normalize ProposedAction
    ↓
Schema + Capability + Policy
    ↓
Approval required
    ↓
Persist PreparedAction and ApprovalRequested
    ↓
Run waits
    ↓
User decides
    ↓
Validate ActionDigest
    ↓
Execute or reject
```

### 19.4 Artifact 生成

```text
Tool creates file/result
    ↓
ToolResult returns ArtifactCandidate
    ↓
Artifact registration through ArtifactStorePort
    ↓
Persist ArtifactRef in Runtime Trace
    ↓
Postcondition Verification
    ↓
Layer 2 projects Artifact Card
```

### 19.5 同 Workspace 新建 Session

```text
Workspace capabilities and files remain available
        +
New Session starts with empty conversation history
        ↓
Independent Context
```

Workspace 共享资源，不意味着 Session 共享全部聊天上下文。

## 20. Eval Lab 与真实 Case

### 20.1 Eval 依赖边界

Eval Lab 通过 Runtime Facade 创建无 Session Run，或显式构造 Conversation Context 测试多轮能力。

Eval 不依赖：

- WorkSession Repository；
- UI Projection；
- SQLite 具体表；
- Kernel 内部类。

### 20.2 Session Micro Cases

需要为 Session 基础能力增加 Micro Case：

- 第二轮正确引用上一轮事实；
- Session A 和 Session B 上下文隔离；
- Compact 后保留关键约束；
- 用户在 WAITING_FOR_USER 后继续原 Run；
- 普通 Follow-up 创建新 Run；
- Session 归档后拒绝新输入；
- Crash 后恢复等待用户状态；
- 修改 Skill 配置不影响已启动 Run。

### 20.3 Case Package

每个 Case 建议拆分：

```text
cases/<case-name>/
├── runtime/
│   ├── tools
│   ├── handlers
│   ├── skills
│   ├── capabilities
│   ├── artifact-types
│   └── verifiers
└── eval/
    ├── cases
    ├── datasets
    ├── fixtures
    ├── graders
    ├── baselines
    └── fault-scenarios
```

Runtime Core 不 import Case Package。由 CLI、Application Service 或 Eval Runner 的 Composition Root 注册。

## 21. 进程与部署模型

### 21.1 当前方案

```text
Process A：Desktop Renderer / React UI
    ↓ HTTP / SSE
Process B：WorkAgent Application Service + Harness Runtime
```

Layer 2 与 Layer 3 在 Process B 中通过类型化 In-process API 调用。

### 21.2 当前不拆分 Layer 2 / Layer 3 的原因

- 当前没有多用户和独立扩缩容需求；
- 同进程调用便于调试和学习；
- 避免过早引入 RPC、分布式锁和跨服务事务；
- 架构边界可以通过 package、TypeScript project reference 和依赖检查实现；
- Headless Runtime 仍然可以作为独立 Library 被 CLI 和 Eval Runner 使用。

### 21.3 未来拆进程的触发条件

只有出现证据后再考虑：

- Runtime 崩溃隔离；
- 长时间任务需要独立守护；
- Browser、Shell 等资源需要沙箱进程；
- 多个前端客户端共享 Runtime；
- CPU、内存或安全隔离需求。

当前不为假想进程拆分设计 RPC Adapter。

## 23. 安全与凭证边界

### 23.1 Workspace Scope

- 所有文件操作必须通过 ResourceRef；
- 所有 ResourceRef 必须验证 Workspace 和 Mount；
- 禁止路径逃逸；
- 外部目录必须显式授权；
- CapabilityGrant 不能扩大 Workspace Binding 的 Scope。

### 23.2 Secret

- 数据库、RunSpec、Context 和 Trace 只保存 SecretRef；
- Secret 明文仅在 Adapter 执行阶段短暂解析；
- Cookie、Token、浏览器存储不进入模型；
- ToolResult 必须经过脱敏和大结果外置。

### 23.3 不可信内容

- 网页、文件和 Tool Result 都视为不可信输入；
- Context Compiler 标记来源；
- 来自内容的指令不能直接扩大 Capability；
- 高影响副作用继续经过 Policy 和 Approval。

### 23.4 本地前后端通信

即使只监听本机，也需要考虑：

- 随机端口或受控 Socket；
- 会话级鉴权 Token；
- Origin 校验；
- 禁止外部网页调用本地 WorkAgent API；
- SSE/WS 重连和事件游标。

## 26. 最终架构摘要

```text
Workspace 提供真实工作空间、资源和能力授权
        ↓
Session 承载多轮对话、意图演进和工作连续性
        ↓
Layer 2 将可变配置解析为不可变 RunSpec
        ↓
Harness Runtime 在无产品依赖的前提下可靠执行 Run
        ↓
Action、Attempt、Observation、Verification 形成规范化 Trace
        ↓
Layer 2 将 Trace 投影成 Message、Tool Card、Approval 和 Artifact
        ↓
UI 提供 Agentic 交互体验
        ↓
Eval Lab 使用相同 Runtime Contract 验证效果和可靠性
```

本版设计的核心不是把 Chat、Workspace 和 Agent Runtime 混在一起，而是通过明确的对象和 Contract 将它们连接起来：

> Workspace 保证 Agent 知道自己被允许在哪里工作；Session 保证用户和 Agent 可以持续把事情说清楚；Run 保证每一次实际执行都可观察、可恢复、可验证。
