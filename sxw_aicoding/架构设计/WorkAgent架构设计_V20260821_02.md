## 1. 文档目的

本文档在 V01 三层架构和 Workspace / Session / Run 三中心模型之上，吸收二次评审中确认成立的问题，补齐以下关键语义：

1. 纯 Kernel 与异步、流式 Model / Tool Activity 如何协作；
2. RuntimeSignal 如何持久化、排序、幂等处理并中断长 Activity；
3. ToolResult 如何进入 Run 内 Context，以及大结果如何外置、预览、取回和 Compact；
4. Tool 参数如何解析为可信的 EffectScope，并接受 Capability、Policy 和 Adapter 三层校验；
5. 错误如何分类，如何决定重试、模型自纠、等待用户、人工恢复或终止；
6. Cancel、Timeout、Crash Resume、Replay 与外部世界变化分别具有什么语义；
7. Budget、无进展检测、循环检测和优雅停止如何成为 Runtime 不变量；
8. Verification、dry-run、Human Takeover、Eval Testkit 和 Event 演进如何进入架构；
9. 在不实现多 Agent 的前提下，如何避免写死单层 Run 假设。

本文档仍然是总体架构设计，不替代后续精确 TypeScript Contract、状态迁移表、SQLite 事务设计和 ADR。若与上位基线冲突，以上位基线为准。

## 2. V02 核心结论

### 2.1 V01 主架构保持不变

以下结论继续成立：

```text
Workspace：资源、授权和工作环境中心
Session：持续交互和意图演进中心
Run：Agent 单次执行、恢复和评测中心
```

```text
Layer 1  WorkAgent UI
    ↓
Layer 2  Application Service / Harness Host
    ↓ immutable snapshot + typed signal/event
Layer 3  Harness Runtime
```

- Layer 2 是可变产品配置的 Control Plane；
- Layer 3 是一次 Run 的 Execution Data Plane；
- Layer 3 不访问 Layer 2 Repository；
- Eval、CLI 和桌面产品复用相同 Runtime Facade；
- Kernel 保持纯决策，Coordinator 负责 durable orchestration；
- 不引入预定义业务 DAG，不把多 Agent 设为 v0.1 默认架构。

### 2.2 V02 的主要修正

V02 将原来留待详细设计、但会影响 Contract 正确性的内容提升为架构不变量：

1. Model、Tool、Verification 和 Context Compaction 统一视为可异步执行的 `RuntimeActivity`；
2. Kernel 只产生 Activity Directive、消费最终 ActivityOutcome，不直接消费流式 Delta；
3. Signal 使用 durable inbox，状态提交串行化，Cancel 通过 Activity Abort 通道及时生效；
4. Session Context 与 Run Working Context 分离，ToolResult 必须经过 Context Materialization；
5. PreparedAction 必须包含由受信任代码解析出的 `ResolvedEffect`；
6. 错误分类与副作用确定性分开建模，未知副作用不得自动重试；
7. Capability Snapshot 用于复现，执行时 Lease / Revocation Check 用于实时安全；
8. Resume、State Rebuild 和 Replay 成为三种不同语义；
9. Budget 与 Progress Guard 成为 Kernel / Coordinator 的强制停止条件；
10. Event、Signal、Activity 和 Error Contract 全部要求版本化。

### 2.3 不机械采纳的建议

以下建议只采纳目标，不照搬具体实现：

- 不把 JSONPath 作为所有 EffectScope 的唯一提取机制；
- 不把 transient / model-recoverable / user-fixable / fatal 当作完整错误分类学；
- 不现在引入可以绕过不变量的通用 Pre/Post Hook；
- 不用可变的 cursor + delta 替代不可变 Conversation Context Snapshot；
- 不假设 LLM 可以可靠传播“来自不可信内容”的污点标签；
- 不仅添加一个孤立的 `parentRunId` 便宣称已经支持 Sub-agent。

### 2.4 多 Agent 的当前边界

v0.1 不实现 Sub-agent、并行 Agent 或 Run Group，但禁止写死以下假设：

- Runtime 不得要求 Run 必须属于 Session；
- “一个 Session 一个 Foreground Run”只是 Layer 2 产品策略，不是 Layer 3 不变量；
- Run 的因果来源不能只绑定 Session Message；
- Child/Background 执行未来不得直接写入 Session Transcript；
- Context、Budget、Capability 和 Cancel 未来是否继承必须显式决定，不能隐式全量继承。

当前仅预留通用 `correlationId`、`causation` 和 Run 独立执行边界，不定义父子 Run 的预算、取消、权限或生命周期语义。

## 3. 架构目标与原则

### 3.1 架构目标

本架构需要支持：

1. 面向真实 Workspace 的持续工作；
2. 多轮聊天、意图澄清和 Run 内追问；
3. 无 Session 的 Headless Run；
4. Case 无关的 Agent Harness；
5. Tool、Skill、MCP、Plugin 和本地能力接入；
6. 可观察、可取消、可恢复、可审计的执行；
7. Run 内与 Session 间的上下文治理；
8. Eval、故障注入、Record/Replay 和实验对比；
9. 桌面 UI、CLI、Automation 和 Eval Runner 复用同一个 Runtime；
10. 后续 Planning、Verifier、Memory、Sub-agent 等策略的评测驱动演进。

### 3.2 架构原则

#### 原则一：事实、执行状态和产品投影分离

- User Message、Workspace 配置属于产品事实；
- Run、Activity、Action、Attempt、Observation、Verification 属于运行事实；
- Assistant Message、Tool Card、Approval Card、Artifact Card 是可重建产品投影。

#### 原则二：可变配置冻结，实时安全不冻结

Run 启动时冻结 Prompt、Tool Schema、Skill、Policy、Capability Grant 和环境证据，用于恢复和复现。

但是，以下实时安全状态可以阻止后续执行：

- Capability 被撤销；
- Grant 或凭证已过期；
- ResourceMount 不可用；
- 执行目标超出当前授权；
- 宿主触发紧急停止。

冻结快照是证据，不是绕过实时撤权的通行证。

#### 原则三：外部副作用前持久化意图

```text
Resolve Effect
    ↓
Persist PreparedAction / Attempt Intent
    ↓
Acquire Capability Lease and execute
    ↓
Persist outcome and side-effect certainty
    ↓
Observe / Verify
    ↓
Kernel continues
```

#### 原则四：Kernel 纯决策，Activity 异步执行

Kernel 不执行 I/O，不等待网络，不处理流式传输。Coordinator 将 Directive 物化为 Activity，Activity Runtime 通过 Port 执行外部工作。

#### 原则五：状态提交串行，外部工作不长期持锁

同一 Run 的 durable 状态迁移必须串行化；分钟级 Model / Tool 调用不得长期占有数据库推进锁。Coordinator 使用 claim / lease / generation 防止旧结果覆盖新状态。

#### 原则六：Session History 不等于 Model Context

Session 保存事实；RunSpec 冻结不可变 Context Source；Context Runtime 选择、裁剪、外置、取回、压缩并形成每次 ModelInvocation 的 ContextFrame。

#### 原则七：Effect 必须由可信代码解析

Policy 不直接相信模型描述的副作用范围。PreparedAction 的 EffectScope 必须由注册的、版本化的 Effect Resolver 从已校验参数和当前资源状态中解析。

#### 原则八：错误处置服从副作用确定性

任何重试决定都必须同时考虑错误类型、retryability、幂等性和外部副作用是否可能已经发生。

#### 原则九：Trace 是事实，Delta 是旁路

流式 Delta、进度和心跳是 transient 体验事件；最终 Invocation、Activity、Action、Verification 和 Run Outcome 必须形成 durable 事实。

#### 原则十：高级策略不能绕过 Kernel 不变量

未来 Planner、Verifier、Memory 或 Sub-agent 可以改变决策策略，但不能绕过 Capability、Policy、Approval、Budget、Durability、Trace 和 Cancel。

## 5. Layer 1：WorkAgent UI

### 5.1 职责

- Workspace、Session 和配置管理；
- User / Assistant Message；
- Assistant 文本流式展示；
- Tool、Attempt、Verification 和进度展示；
- Approval Request 展示与决策提交；
- Run 暂停、恢复、取消和重新执行；
- ExternalInteractionRequest 展示和人工接管；
- Artifact 预览、打开、下载和标记交付；
- Trace 和 Eval Inspector。

### 5.2 UI 不拥有的语义

- Run 合法状态迁移；
- Action 是否允许执行；
- EffectScope 是否落在 CapabilityGrant 内；
- Tool 是否可安全重试；
- Cancel 后副作用是否已经发生；
- Postcondition 是否通过；
- Signal 是否过期或重复；
- Crash 后从哪个 Activity 恢复。

### 5.3 Transcript

```ts
type TranscriptEntry =
  | UserMessageEntry
  | AssistantMessageEntry
  | ProgressEntry
  | ToolActionEntry
  | ApprovalEntry
  | ExternalInteractionEntry
  | ArtifactEntry
  | SystemNoticeEntry;
```

每个投影项保存 `sourceRunId` 和至少一个 `sourceEventId/sourceActionId/sourceActivityId`。未来 Background/Child Run 不直接写入 Transcript，由 Foreground Run 或 Layer 2 聚合后投影。

### 5.4 前后端协议

- HTTP Command：创建对象、发送消息、启动/取消 Run、提交 Approval 和 Interaction Completion；
- HTTP Query：查询 Workspace、Session、Artifact、配置和 RunSnapshot；
- SSE：Assistant Delta、Run 状态、Tool 状态、Approval、Artifact；
- WebSocket：只用于终端、浏览器人工接管等明确双向实时场景；
- 所有命令携带 idempotency key 或 signalId；
- SSE/WS 重连使用事件游标，不依赖内存订阅状态。

## 6. Layer 2：Application Service / Harness Host

### 6.1 逻辑模块

```text
workagent-application/
├── workspaces/
├── agents/
├── resources/
├── sessions/
├── capabilities/
├── skills/
├── mcp/
├── plugins/
├── policies/
├── artifacts/
├── approvals/
├── interactions/
├── audit/
├── runtime-host/
├── projections/
└── api/
```

`agents/` 拥有 AgentProfile、默认模型/策略选择以及生成 AgentSpecSnapshot 所需的产品配置。

### 6.2 Workspace 与 Resource

Workspace 是资源、能力配置和授权边界。Resource 模块负责：

- PrimaryFileSpace、ResourceMount 和 Managed Upload；
- ResourceRef 解析；
- 路径规范化、symlink/路径逃逸检查；
- 文件元数据与 content hash；
- ResourceMount 可用性和实时撤销；
- Artifact Storage 的物理实现。

所有文件 Tool 应优先接受 `ResourceRef` 或可规范化为 ResourceRef 的输入，不向模型暴露 Adapter 解析后的绝对路径作为授权依据。

### 6.3 Session

Session 模块负责：

- WorkSession 生命周期；
- User Message 和 Assistant Message Projection；
- Transcript、Pinned Resource 和 Context Cursor；
- Session 与 Foreground Run 的产品并发规则；
- immutable ConversationSourceSnapshot 的生成与保存；
- Session 归档。

v0.1 一个 Session 同时只允许一个 Foreground Active Run。这是 Layer 2 的交互一致性策略，不限制 Layer 3 同时执行多个无 Session Run。

### 6.4 Capability Control Plane

负责 Definition Catalog、Workspace Binding、Provider 配置、Scope、SecretRef、健康检查和撤销。Run 启动时生成冻结 CapabilityGrant；执行前由 Adapter 或 Capability Runtime 取得短生命周期 Lease 并检查实时状态。

### 6.5 Runtime Host

负责：

- 创建并配置 Harness Runtime；
- 注入 Model、Storage、Tool、Artifact、Trace、Blob、Clock 等 Port；
- 从 Workspace、Agent 和 Session 创建 RunSpec；
- 恢复未结束 Run；
- 将用户输入、Approval、Cancel、Interaction Completion 转成 RuntimeSignal；
- 接收 RunEvent 并投影为 Transcript/UI Event；
- 监督进程退出和 Activity Abort。

Runtime Host 不实现 Agent Loop，不直接修改 Runtime 内部事实表。

## 7. Workspace、Session 与 Snapshot 模型

### 7.1 Workspace

```ts
interface Workspace {
  id: WorkspaceId;
  name: string;
  description?: string;
  status: "ACTIVE" | "ARCHIVED";
  resourceScopeId: ResourceScopeId;
  policyBindingId: PolicyBindingId;
  revision: number;
  createdAt: Timestamp;
  updatedAt: Timestamp;
  archivedAt?: Timestamp;
}
```

Workspace 不变量：

1. 必须存在一个 PrimaryFileSpace；
2. 只有 ACTIVE Workspace 可以创建新的 Session 和 Run；
3. 所有写操作必须落在明确授权的 ResourceMount；
4. 执行语义相关配置变更增加 revision；
5. Secret 只保存 SecretRef；
6. 归档保留历史 Session、Run、Artifact 和 Audit；
7. 撤权对尚未执行的 Activity 实时生效。

### 7.2 ResourceRef

```ts
interface ResourceRef {
  workspaceId: WorkspaceId;
  mountId: ResourceMountId;
  relativePath: string;
  contentHash?: string;
  size?: number;
  mediaType?: string;
}
```

规则：relativePath 规范化；禁止路径逃逸；重要输入通过 contentHash 固化；执行前重新验证 Mount、路径和必要的 precondition fingerprint。

### 7.3 WorkSession

```ts
interface WorkSession {
  id: SessionId;
  workspaceId: WorkspaceId;
  title: string;
  objective?: string;
  status: "ACTIVE" | "ARCHIVED";
  agentProfileRef?: AgentProfileRef;
  contextPolicyRef?: ContextPolicyRef;
  revision: number;
  createdAt: Timestamp;
  updatedAt: Timestamp;
  archivedAt?: Timestamp;
}
```

普通 follow-up 创建新 Run；只有 Run 已经持久化特定 WaitRequest 时，匹配该 requestId 的用户输入才恢复原 Run。

#### 7.3.1 v0.1 暂不建立 Task Aggregate

v0.1 暂不单独建立 Task Aggregate。当前 WorkSession 已经承载持续目标、多轮交互、多个 Run 和最终 Artifact；只有出现跨 Session 任务、Deadline、负责人、依赖、后台任务或 TODO/日程集成需求时，再通过独立 ADR 引入 Task。该决定不影响 Runtime 的 Run 模型。

### 7.4 AgentSpecSnapshot

```ts
interface AgentSpecSnapshot {
  agentSpecId: AgentSpecId;
  version: string;
  contentHash: string;
  model: ModelConfigurationSnapshot;
  systemPrompt: PromptSnapshot;
  toolSnapshots: ToolSnapshot[];
  skillSnapshots: SkillSnapshot[];
  contextPolicy: ContextPolicySnapshot;
  loopPolicy: LoopPolicySnapshot;
  approvalPolicy: ApprovalPolicySnapshot;
}
```

Snapshot 保存所有可复现内容或 content-addressed 引用；“存在于 Snapshot”不等于“立即全部注入模型 Context”。

### 7.5 WorkspaceExecutionSnapshot

```ts
interface WorkspaceExecutionSnapshot {
  workspaceId: WorkspaceId;
  workspaceRevision: number;
  resourceGrants: ResourceGrant[];
  capabilityGrants: CapabilityGrant[];
  capabilityBindingVersions: VersionedBindingRef[];
  skillBindingVersions: VersionedBindingRef[];
  pluginContributionVersions: PluginContributionRef[];
  policySnapshot: PolicySnapshot;
  workspaceEnvironmentFingerprint: EnvironmentFingerprint;
}
```

### 7.6 ConversationSourceSnapshot

```ts
interface ConversationSourceSnapshotRef {
  snapshotId: ContextSourceSnapshotId;
  sessionId: SessionId;
  transcriptCursor: MessageId;
  contentHash: string;
  blobRef: BlobRef;
  checkpointRefs: ContextCheckpointRef[];
  pinnedResourceRefs: ResourceRef[];
}
```

`blobRef` 指向不可变、内容寻址的消息与必要投影快照。它避免在 RunSpec 中无限内嵌全部历史，也避免 Runtime 通过可变 cursor 回查 Layer 2 数据库。

### 7.7 RunSpec 与通用因果信息

```ts
type RunOrigin =
  | {
      kind: "SESSION";
      workspaceId: WorkspaceId;
      sessionId: SessionId;
      triggerMessageId: MessageId;
    }
  | { kind: "CLI"; workspaceId?: WorkspaceId }
  | { kind: "EVAL"; evalCaseId: EvalCaseId }
  | { kind: "AUTOMATION"; automationId: AutomationId }
  | { kind: "RUNTIME" };
```

`RUNTIME` 是未来由另一个 Run/策略触发独立执行的入口类别，v0.1 RunSpecFactory 不生成该类型。它不隐含父子生命周期或权限继承。

```ts
type RunCausation =
  | { kind: "SESSION_MESSAGE"; sourceId: MessageId }
  | { kind: "CLI_COMMAND"; sourceId: string }
  | { kind: "EVAL_CASE"; sourceId: EvalCaseId }
  | { kind: "AUTOMATION_TRIGGER"; sourceId: string }
  | {
      kind: "RUN_ACTION";
      sourceId: ActionId;
      sourceRunId: RunId;
      sourceActionId: ActionId;
    };
```

```ts
interface RunSpec {
  id: RunSpecId;
  origin: RunOrigin;
  correlationId: string;
  causation: RunCausation;
  input: RunInput;
  agentSpec: AgentSpecSnapshot;
  workspace?: WorkspaceExecutionSnapshot;
  conversationContext?: ConversationSourceSnapshotRef;
  budgets: RunBudgets;
  runtimeEnvironmentFingerprint: EnvironmentFingerprint;
  createdAt: Timestamp;
}
```

`RUN_ACTION` 只预留通用因果表达能力，不代表 v0.1 已支持 Child Run。任何未来的父子预算、取消和权限继承仍需独立 ADR。

`RunOrigin.kind = "RUNTIME"` 时 causation 必须是 `RUN_ACTION`；其他 origin 与 causation 的组合由 RunSpecFactory 校验，避免只记录入口却丢失实际触发原因。

## 8. Harness Runtime 执行模型

### 8.1 内部模块

```text
harness-runtime/
├── facade/
├── coordinator/
├── kernel/
├── activity/
├── signals/
├── context/
├── model/
├── action/
├── tool-runtime/
├── policy/
├── verification/
├── budget/
├── durability/
├── artifact/
├── trace/
└── ports/
```

### 8.2 Runtime Facade

```ts
interface HarnessRuntime {
  start(spec: RunSpec): Promise<RunHandle>;
  resume(runId: RunId): Promise<RunHandle>;
  signal(runId: RunId, signal: RuntimeSignalEnvelope): Promise<SignalReceipt>;
  cancel(runId: RunId, reason?: string): Promise<SignalReceipt>;
  inspect(runId: RunId): Promise<RunSnapshot>;
  subscribe(runId: RunId, after?: EventCursor): AsyncIterable<RunEventEnvelope>;
}
```

`signal()` 成功只表示 Signal 已被 durable 接收，不等于 Run 已完成相应状态迁移。调用方通过 SignalReceipt、RunEvent 或 inspect 查询结果。

### 8.3 纯 Kernel

```ts
interface AgentKernel {
  advance(state: KernelState, input: KernelInput): KernelTransition;
}
```

```ts
type KernelInput =
  | RunStartedInput
  | ActivityOutcomeInput
  | UserInputAcceptedInput
  | ApprovalDecisionAcceptedInput
  | InteractionCompletedInput
  | BudgetSignalInput
  | CancellationAcceptedInput
  | RecoveryDecisionInput;
```

```ts
type KernelDirective =
  | RequestContextFrameDirective
  | RequestModelDirective
  | PrepareActionDirective
  | ExecuteActionDirective
  | VerifyActionDirective
  | CompactContextDirective
  | WaitForApprovalDirective
  | WaitForUserDirective

```

Kernel 只消费最终的、规范化的 ActivityOutcome。Model Delta、Tool Progress、Heartbeat 不进入 KernelState，也不影响可恢复状态。


### 8.5 ModelInvocation 生命周期

1. Kernel 产生 `RequestModelDirective`；
2. Coordinator 持久化 Invocation Intent 和 Activity；
3. ModelPort 开始异步流式调用；
4. Delta 通过 transient event 旁路输出；
5. 正常完成后，Provider 响应被规范化为 `ModelInvocationResult`；
6. 只有完整且协议合法的结果进入 Kernel；
7. Usage、耗时、Provider request ID 和最终内容引用形成 durable event。

流式中断规则：

- Cancel/timeout 后，半截文本默认不进入后续 Model Context；
- 半截内容可以脱敏后外置保存，用于诊断，并标记 `INTERCEPTED/PARTIAL`；
- 未完整闭合的 Tool Call 不得转为 ProposedAction；
- Provider 明确支持的可恢复响应必须先规范化，再由新 Activity 继续；
- UI 可以展示“响应已中断”，但不得把半截输出投影为 FINAL Assistant Message。

## 9. RuntimeSignal 与并发协议

### 9.1 Signal Envelope

```ts
interface RuntimeSignalEnvelope<T extends RuntimeSignal = RuntimeSignal> {
  signalId: SignalId;
  schemaVersion: number;
  runId: RunId;
  type: T["type"];
  correlationId: string;
  targetRequestId?: WaitRequestId | ApprovalId | InteractionRequestId;
  expectedRunRevision?: number;
  createdAt: Timestamp;
  payload: T;
}
```

```ts
type RuntimeSignal =
  | UserInputSignal
  | ApprovalDecisionSignal
  | PauseSignal
  | ResumeSignal
  | CancelSignal
  | ExternalInteractionCompletedSignal
  | HostShutdownSignal;
```

### 9.2 Durable Inbox 不变量

1. Signal 在返回 accepted receipt 前必须持久化；
2. `signalId` 全局幂等，同一 signal 重复提交返回同一处理结果；
3. 同一 Run 的状态迁移按 durable sequence 串行提交；
4. Signal 是否可消费由当前 RunState、targetRequestId 和 expectedRevision 决定；
5. Terminal Run 不消费推进类 Signal，但重复 Cancel 可以幂等返回 terminal 状态；
6. 过期、目标不匹配或已决策的 Signal 形成拒绝记录，不能静默丢弃；
7. ApprovalDecision 必须同时匹配 approvalId、actionId、actionDigest 和有效期；
8. Signal 到达时 Runtime 进程可以不在线，恢复后仍可消费。

### 9.3 Signal 优先级与消费

同一 Run 中建议使用以下优先级：

```text
Host Emergency Stop / Cancel
    > Pause
    > Approval / External Interaction Completion
    > User Input
    > Resume / ordinary wake-up
```

优先级只解决同一推进点的消费次序，不绕过状态机合法性。

### 9.4 用户连续输入

`WAITING_FOR_USER` 必须持有一个 `WaitRequest`：

```ts
interface WaitRequest {
  id: WaitRequestId;
  runId: RunId;
  prompt: string;
  inputSchema?: JsonSchema;
  mode: "SINGLE" | "ACCUMULATE_UNTIL_SUBMIT";
  expiresAt?: Timestamp;
  status: "OPEN" | "FULFILLED" | "EXPIRED" | "CANCELLED";
}
```

- `SINGLE`：第一个合法输入完成请求，之后输入按照普通 follow-up 处理；
- `ACCUMULATE_UNTIL_SUBMIT`：Layer 2 聚合多条草稿，提交时形成一个 Signal；
- 没有匹配 WaitRequest 的消息不得静默进入已启动 Run；
- v0.1 默认使用 `SINGLE`。

### 9.5 长 Activity 的 Cancel

Signal 持久化与 Activity Abort 是两条配合通道：

1. CancelSignal 先写 durable inbox；
2. Runtime Host / Coordinator 通知当前 Activity 的 AbortController；
3. Adapter 应协作式停止并返回取消结果；
4. 若 Adapter 无法确认副作用是否发生，Activity 进入 `OUTCOME_UNKNOWN`；
5. Coordinator 重新持锁，消费 Cancel 并提交 Run 状态；
6. 迟到成功结果不得把 CANCELLED Run 恢复为 RUNNING，但必须作为诊断事实保存。

### 9.6 Pause 与 Resume

- PauseSignal 表示在下一个安全点停止调度新 Activity，默认不等同于 Cancel；
- 是否中断当前 Activity 由 Activity 的 pause/cancellation descriptor 决定；
- 只有当前 Activity Outcome 已安全持久化，或已经明确进入可恢复状态后，Run 才转为 PAUSED；
- ResumeSignal 只唤醒 PAUSED Run，不绕过 Capability、环境和 Budget 重新校验；
- Host Shutdown 可以请求安全 Pause；无法及时安全暂停时保存 Activity 状态，由下次 Crash Resume 协议接管。

## 10. Run 领域模型与状态机

### 10.1 RunStatus


RunStatus 表示生命周期状态，RunOutcome 表示结束质量与原因；不得为了表达所有业务结果无限扩展 RunStatus。

### 10.2 RunSnapshot

```ts

  runId: RunId;
  runSpecId: RunSpecId;
  revision: number;

  updatedAt: Timestamp;
}
```

### 10.3 Run 不变量

1. 一个 Run 绑定一个不可变 RunSpec；
2. 配置变化需要创建新 Run；
3. 每个外部副作用关联 Action、Attempt 和 Activity；
4. 同一 Run 的 durable transition 同时只允许一个 Coordinator 提交；
5. Terminal Run 不得继续产生新 Activity；
6. 所有状态迁移产生有版本、单调 sequence 的 Durable Event；
7. Activity 结果必须匹配当前 generation；
8. 每次 ModelInvocation 前必须形成合法 ContextFrame；
9. 每次 Action 执行前必须具有 ResolvedEffect、Capability Evidence 和实时 Lease；
10. 未知副作用状态不得自动重试；
11. Budget hard limit、Cancel 和 revoked Capability 不得由模型决定忽略；
12. 等待状态必须关联可寻址、可过期的 Request 对象。

### 10.4 Cancel 后事实处置

- 已完成的 Action、Attempt、Event 和 Audit 不删除；
- 已登记 Artifact 保留 lineage，并根据验证结果保持 VERIFIED、标记 PARTIAL/INVALID 或 SUPERSEDED；
- 未完成的临时资源根据 Tool 的 cleanup/compensation policy 处理；
- 自动 Compensation 必须是新的显式 Action，不伪装成“撤销历史”；
- 如果取消时副作用未知，Run 进入 `RECOVERY_REQUIRED` 或以带恢复事项的 CANCELLED 结束；
- 用户可见结果应明确说明完成、未完成和状态未知的部分。

## 11. Run 内 Context 管理

### 11.1 两级 Context

```text

    ↓ freeze
```

### 11.4 ToolResult Materialization

Tool Handler 的原始输出不能直接拼入 prompt：

```text
Raw ToolResult
    ↓ schema validate
    ↓ secret / sensitive-data redaction
    ↓ normalize and hash
    ↓ estimate actual provider tokens
    ├── small result → inline ContextItem
    └── large result → immutable Blob + preview + retrieval reference
                         ↓
                  read_blob_slice / domain retrieval tool
```

规则：

1. 完整原始结果是否保存由数据策略决定，但进入模型前必须脱敏；
2. 大结果阈值属于 ContextPolicy，可按字符、字节和 Provider token 共同判断；
3. 外置后保留结果类型、摘要、hash、大小、来源、取回方式和截断说明；
4. 取回工具必须分页、有硬上限，并继续接受脱敏和 Context Budget；
5. Artifact 与 Runtime Blob 区分：Blob 是执行内部载体，Artifact 是具有交付和 lineage 语义的产物；
6. 具体 20K 等阈值通过 Eval 决定，不写死为跨 Provider 常量。

### 11.5 Tool Call / Result 配对不变量

- 一个模型 Tool Call 与对应 Tool Result 使用同一 `pairGroupId/toolCallId`；
- Provider 要求原子相邻时，Context Compiler 将整个 pair 视为不可拆分单元；
- 不允许只保留 Tool Call 丢弃 Result，或只保留 Result 丢弃 Call；
- Pair 过大时，外置 Result 正文，但保留合法的结构化 Result Stub；
- Compact 必须把 pair 一起保留、一起摘要为合法替代块，或一起移除；
- ContextFrame 构建后执行 Provider-specific protocol validation，失败不得发起模型调用。

### 11.6 Run 内 Compact

ContextPolicy 至少定义：

```ts
interface ContextBudgetPolicy {
  modelWindowTokens: number;
  reservedOutputTokens: number;
  softInputLimitTokens: number;
  hardInputLimitTokens: number;
  compactTargetTokens: number;
  inlineToolResultLimitTokens: number;
  retrievalPageLimitTokens: number;
}
```

触发策略：

1. 优先 Offload 大 Tool Result；
2. 达到 soft limit 后，在下一次 ModelInvocation 前静默 Compact；
3. Compact 目标低于 soft limit，形成滞回区间，避免每步反复压缩；
4. 达到 hard limit 且无法安全 Compact 时，不调用模型，转等待用户、产生 handoff 或失败；
5. Compact 结果是带 source refs、compiler/model version 和 hash 的派生对象；
6. 原始 durable facts 不被 Compact 删除；
7. Compact 必须保留当前目标、用户约束、未完成 Action、Approval/Wait 状态、关键 Artifact 和错误恢复状态。

### 11.7 Skill 渐进披露

```ts
interface SkillSnapshot {
  skillId: SkillId;
  version: string;
  contentHash: string;
  name: string;
  description: string;

  resourceRefs: ResourceRef[];

```

- 初始 Context 默认只注入可用 Skill 的 name/description；
- EAGER Skill 或被选择的 ON_DEMAND Skill 才加载完整 instructions；
- 加载动作形成 ContextItem 和 Trace；
- v0.1 可以只实现 EAGER，但 Contract 不等同于全量注入；
- 渐进披露是否提升效果通过 Eval 比较。


```text
PreparedAction
    ↓ Policy Runtime: ResolvedEffect ⊆ frozen CapabilityGrant
    ↓ Capability Runtime: binding not revoked, lease not expired
    ↓ Adapter: actual normalized target still matches scope/precondition
Execute
```

三层职责不同：

- Policy 判断“是否允许、是否需要 Approval”；
- Capability Runtime 判断“授权现在是否仍有效”；
- Adapter 判断“实际执行目标是否与已批准目标一致”。

### 12.6 dry-run / preview

- 支持 preview 的 Tool 在 APPLY 前可以生成确定性 Plan、Diff、目标列表或外发摘要；
- Preview 本身不得执行声明之外的副作用；
- Approval UI 展示 preview 和 ResolvedEffect；
- APPLY 前重新校验 precondition fingerprint；
- 若目标环境变化导致 actionDigest 改变，必须重新 preview / policy / approval；
- 不支持 preview 的 Tool 必须显式声明，而不是默认假装支持。

### 12.7 Capability 并发与 Lease

```ts
interface ConcurrencyDescriptor {
  mode: "SHARED" | "EXCLUSIVE" | "KEYED";
  keyResolverRef?: VersionedRef<ConcurrencyKeyResolver>;
  maxConcurrency?: number;
}
```

- Browser Session、交互式终端等状态资源通常使用 EXCLUSIVE/KEYED lease；
- 普通只读文件能力可以共享，但仍需限制资源消耗；
- Lease 有 ownerActivityId、期限和 heartbeat；
- Crash 后通过过期与恢复协议释放，不依赖进程内引用计数；
- 多 Session 并发不应破坏同一外部状态资源的一致性。

### 13.3 自动重试规则

1. retryPolicy 允许；
2. retryability 允许当前方式；
3. 未超过 attempt、wall-clock 和 budget 限制；
4. sideEffectState 为 NOT_STARTED/NO_EFFECT，或幂等键与外部查询证明安全；
5. Capability 和 preconditions 仍然有效；
6. Cancel/Pause 未待处理。

`UNKNOWN`、`PARTIALLY_APPLIED` 默认进入 Observation、Recovery 或人工处理，不可仅因错误看起来 transient 就重试。

### 13.4 返回模型的错误

模型可纠正的输入错误以结构化、脱敏 Tool Result 返回，包含：

- 稳定错误 code；
- 哪些字段不合法；
- 允许的修正方向；
- 已执行副作用状态；
- 是否允许再次调用。

内部堆栈、凭证、绝对敏感路径和 Provider 私密响应不得进入模型。

## 14. Policy 与 Approval

Workspace 保存可替换的 PolicyBinding，v0.1 默认使用 `TRUSTED_PERSONAL`，但该 preset 不是 Kernel 中的硬编码假设：

```ts
interface PolicyBinding {
  id: PolicyBindingId;
  workspaceId: WorkspaceId;
  preset: "TRUSTED_PERSONAL";
  overrides: PolicyOverrides;
  revision: number;

```

### 14.1 Policy 输入

Policy Engine 至少消费：

- PreparedAction / ResolvedEffect；
- frozen CapabilityGrant 和 PolicySnapshot；
- live Capability status；
- reversibility、data movement 和 target fingerprint；
- Context source/trust 摘要；
- 当前 Budget、Run 状态和既往 Approval；
- Tool preview/dry-run 结果。

Context trust 只是风险信号，不能取代独立的 Capability/Effect 校验。

### 14.2 Approval 模型

```ts
interface Approval {
  id: ApprovalId;
  workspaceId: WorkspaceId;
  sessionId?: SessionId;
  runId: RunId;
  actionId: ActionId;
  actionDigest: string;
  requestedCapability: CapabilityId;
  effectScope: EffectScope;
  previewRef?: BlobRef;
  reason: string;

  createdAt: Timestamp;
  decidedAt?: Timestamp;
}
```

### 14.3 Approval 生命周期

- Runtime 创建 ApprovalRequested durable event；
- Layer 2 保存产品 Approval 并展示 UI；
- 用户决策以持久化 Signal 回到 Runtime；
- Runtime 校验 approvalId、actionDigest、状态和有效期；
- 过期由 Clock 驱动的 durable timer 或恢复扫描触发；
- Run 已 crash 时 Decision 保留在 Signal Inbox，恢复后处理；
- Run 已 terminal、Action 已变化或 Approval 已决定时，后续 Decision 幂等拒绝；
- Approval 不会覆盖实时撤权或已变化的 target fingerprint。

## 15. Observation 与 Verification

### 15.1 所有权

- Kernel 决定何时需要 Verification；
- Verification Runtime 根据 Descriptor 选择注册的 Verifier；
- Verifier 通过受限 Port 读取环境或调用只读 Tool；
- Case Package 提供业务 verifier，但 Runtime Core 拥有执行、超时、Trace 和处置语义；
- Tool Handler 的“success”不能替代独立 Verification。

### 15.2 VerificationDescriptor

```ts
interface VerificationDescriptor {
  mode: "NONE" | "INLINE_RESULT" | "REOBSERVE" | "CUSTOM_VERIFIER";
  verifierRef?: VersionedRef<Verifier>;
  requiredForSuccess: boolean;
  observationCost: "LOW" | "MEDIUM" | "HIGH";
  timeoutMs?: number;
  staleAfterMs?: number;
  retryPolicy?: RetryPolicy;
}
```

### 15.3 何时重新观察

- 高影响副作用、外部状态写入、Artifact 交付原则上重新观察；
- 纯函数或带可验证返回对象的低风险 Tool 可以使用 inline result；
- Observation 成本高时，Tool Contract 可以指定采样、关键检查或延迟验证；
- Resume 后只要 observation 已超过 staleAfter、precondition 变化或 Grant 变化，就必须重新观察；
- Verification 失败不自动等于 Tool 可重试，先判断副作用状态和补救路径。

## 16. Budget、无进展与优雅停止

### 16.1 RunBudgets

```ts
interface RunBudgets {
  maxDecisionSteps: number;
  maxWallClockMs: number;
  maxModelCalls?: number;
  maxToolCalls?: number;
  maxInputTokens?: number;
  maxOutputTokens?: number;
  maxEstimatedCost?: Money;
  maxConsecutiveFailures: number;
  softLimitRatio: number;
  handoffReserve?: HandoffReserve;
}
```

BudgetUsage 由 durable facts 计算，ModelInvocationCompleted 必须记录 usage；Provider 没有返回精确 usage 时标记为 estimated。

### 16.2 Progress Guard

至少检查：

- 决策步数与连续失败；
- 相同 Tool + normalized input + effect digest 连续重复；
- 多个不同调用但 Observation/Artifact/任务状态没有变化；
- 相同错误和相同模型修正循环；
- Context Compact 后仍无法满足模型窗口；
- 长时间没有 durable progress event。

相同调用 hash 只是一个信号，不单独作为所有场景的循环定义。

### 16.3 Soft 与 Hard Limit

- Soft limit：阻止启动普通新步骤，可使用预留预算生成简短 handoff、请求用户缩小范围或交付部分结果；
- Hard limit：不得再调用模型或有副作用 Tool，立即形成稳定 Outcome；
- 如果没有 handoff reserve，不得为“优雅总结”突破 hard limit；
- Budget exhausted 不总是 FAILED：已产生可用、明确标注的部分交付时可以 `COMPLETED_WITH_LIMITS` 作为 RunOutcome；
- RunStatus 保持有限枚举，完成质量通过 RunOutcome 表达。

## 18. Durable Execution、Resume 与 Replay

### 18.1 混合持久化

采用：

```text
事实表 + Durable Event + Snapshot + immutable Blob
```

- 事实表服务当前状态和约束查询；
- Durable Event 保存执行事实、审计、Trace 和因果关系；
- Snapshot 加速恢复，不是独立真相；
- Blob 保存大输入输出、Context Source、Preview 和诊断数据；
- 不追求纯 Event Sourcing，但关键状态必须能由事实和事件校验。

### 18.2 Crash 窗口

恢复至少区分：

1. Directive 尚未持久化；
2. Directive 已持久化但 Activity 未 claim；
3. Activity 已 STARTED，外部调用尚未发生；
4. 外部调用可能发生但 Outcome 未知；
5. Activity Outcome 已持久化但 Kernel 尚未消费；
6. ToolResult 已保存但 ContextItem 尚未物化；
7. Verification 已完成但 Run 状态尚未推进；
8. Signal 已进入 Inbox 但尚未消费；
9. State Snapshot 落后于 Durable Event。

每个恢复分支必须通过 idempotency、provider request ID、外部查询、Observation、precondition/postcondition、Compensation 或人工恢复决定，不能无条件重试。

### 18.3 外部世界重新校验

Resume 不只判断“副作用是否发生”，还必须检查：

- Capability Binding 是否撤销或降级；
- Grant、Secret、Browser Session 或 Lease 是否过期；
- 输入 Resource contentHash 是否变化；
- Action target fingerprint 是否变化；
- Artifact 或外部对象是否被用户修改；
- Verification 结果是否已过 staleAfter。

处理路径：

```text
unchanged → continue
changed but safely resolvable → re-resolve / re-observe / re-prepare
effect or digest changed → policy + approval again
requires user choice → WAITING_FOR_USER / RECOVERY_REQUIRED
cannot establish safe state → fail or cancel with recovery report
```

### 18.4 Resume、Rebuild、Replay 的区别

#### Resume

继续同一个非 Terminal Run；保留 RunId、RunSpec、已完成副作用和预算使用；不会再次执行已证明完成的 Activity。

#### State Rebuild

从事实表、Durable Event 和最新有效 Snapshot 重建同一个 Run 的 KernelState，用于灾难恢复和一致性校验，不调用真实 Provider 或 Tool。

#### Replay

为调试或 Eval 创建隔离的重放执行：

- 使用 RecordedModelPort / RecordedActivityOutcome；
- 默认不触发真实副作用；
- 可以从某个 ContextFrame 或 Event sequence 开始；
- 产生新的 replay execution identity，引用原 Run，但不改写原 Run；
- 明确区分 exact recorded replay、deterministic simulation 和 live rerun；
- live rerun 必须创建新 RunSpec/Run，并重新经过 Capability 和 Policy。

### 18.5 Snapshot 有效性

```ts
interface StoredRunSnapshot {
  runId: RunId;
  schemaVersion: number;
  stateVersion: number;
  coveredThroughEventSequence: number;
  kernelStateHash: string;
  kernelState: SerializedKernelState;
  createdAt: Timestamp;
}
```

加载 Snapshot 后必须重放其后的事件；hash、sequence 或 schema 不兼容时回退到更早 Snapshot 或完整重建。

## 20. Human Takeover / External Interaction

### 20.1 定位

Human Takeover 不是绕过 Runtime 的隐藏操作，而是一个显式等待—人工操作—重新观察协议。v0.1 主要用于动态页面、验证码、登录态失效和浏览器人工纠偏。

### 20.2 ExternalInteractionRequest

```ts
interface ExternalInteractionRequest {
  id: InteractionRequestId;
  runId: RunId;
  actionId?: ActionId;
  capabilityId: CapabilityId;
  resourceHandleRef: ResourceHandleRef;
  interactionType: "BROWSER_TAKEOVER" | "TERMINAL_TAKEOVER" | "MANUAL_RECOVERY";
  instructions: string;
  expectedCompletion: string;
  expiresAt?: Timestamp;
  status: "OPEN" | "COMPLETED" | "EXPIRED" | "CANCELLED";
}
```

### 20.3 运行语义

```text
Runtime requests interaction
    ↓ persist request and release active automation lease
Run → WAITING_FOR_INTERACTION
    ↓ Layer 2/UI grants scoped human control
User operates external resource
    ↓ completion signal with requestId
Runtime reacquires capability lease
    ↓ re-observe + verify environment
continue / re-plan / ask user / fail
```

- 用户操作不伪装成 Tool Attempt，但应有产品 Audit；
- 人工接管期间自动 Browser Tool 不得并发操作同一 session；
- 完成信号不等于任务成功，必须重新 Observation；
- 过期、资源关闭或目标状态不明进入明确恢复路径。

## 21. Skill、MCP、Plugin 与策略扩展

### 21.1 内部语义保持区分

- Capability：授权对某类资源执行操作；
- Tool：模型可调用的具体操作；
- Skill：版本化 Context 贡献；
- MCP：Tool、Resource、Prompt 的 Provider 协议；
- Plugin：贡献 Skill、Tool、Provider、Adapter 或 UI Renderer 的安装与组装单元；
- Adapter：连接具体外部技术。

Layer 2 管理安装、发现、版本和 Workspace Binding；Layer 3 只接收冻结 Snapshot、标准 ToolDefinition 和注册的 Handler/Resolver/Verifier。

### 21.2 策略扩展边界

当前不提供可以任意修改状态或跳过 Policy 的全局 Hook。稳定扩展点优先使用显式接口：

- ContextPolicy / ContextCompiler；
- LoopPolicy / ProgressDetector；
- EffectResolver；
- PolicyEvaluator；
- Verifier；
- ModelRouter（后续）；
- DelegationStrategy（后续）。

未来若引入 lifecycle hook，必须满足：

1. 触发点语义稳定、输入输出版本化；
2. Hook 不能直接修改事实表；
3. 决定执行行为的 Hook 输出必须持久化并可 Replay；
4. Hook 不能跳过 Capability、Policy、Approval、Budget 和 Trace；
5. Hook 失败具有标准 ErrorDisposition。

## 22. 安全与提示注入边界

### 22.1 Workspace Scope

- 文件操作使用 ResourceRef；
- ResourceRef 验证 Workspace、Mount、规范化路径和 symlink；
- CapabilityGrant 不能扩大 Binding Scope；
- PreparedAction ResolvedEffect 必须是 Grant Scope 的子集；
- Adapter 执行时再验证实际目标；
- Workspace 外写入必须由新的明确授权覆盖，不能由内容或模型声明扩大。

### 22.2 Secret 与敏感数据

- 数据库、RunSpec、Context、Trace 只保存 SecretRef；
- Secret 明文仅在 Adapter 执行阶段短暂解析；
- Cookie、Token、浏览器存储不进入模型；
- ToolResult、Error 和 diagnostic blob 进入模型或长期存储前脱敏；
- 向外发送本地数据时，ResolvedEffect 明确记录 data movement、目的地和数据范围。

### 22.3 不可信内容

- 网页、文件、邮件和 ToolResult 默认是 `EXTERNAL_UNTRUSTED`；
- ContextItem 保存来源和 trust 标记；
- 不可信内容中的文字不能创建 Grant、改变 Policy 或自动批准 Action；
- 高影响副作用独立经过 Effect Resolution、Policy 和 Approval；
- Approval UI 展示真实目标、数据移动和 preview，不只展示模型解释；
- 不把“Policy 能可靠判断每个 Action 参数是否由某段网页导致”作为安全前提；
- 未来 Memory 写入视为需要独立治理的操作，身份、权限和安全声明不得仅因模型抽取而进入 trusted memory。

### 22.4 本地前后端通信

- 随机端口或受控 Socket；
- 会话级鉴权 Token；
- Origin 校验；
- 禁止外部网页调用本地 API；
- SSE/WS 重连游标；
- 人工接管通道绑定 InteractionRequest 和 ResourceHandle，不能成为通用后门。

## 23. Eval Lab 与 Testkit

### 23.1 Eval 边界

Eval Lab 通过 Runtime Facade 创建无 Session Run，或显式提供 ConversationSourceSnapshot。Eval 不依赖 Session Repository、UI Projection、SQLite 具体表或 Kernel 私有类。

### 23.2 Testkit 一等能力

```text
packages/testkit/
├── recorded-model-port/
├── recorded-activity-port/
├── fake-clock/
├── deterministic-id-generator/
├── in-memory-run-store/
├── fault-injector/
├── trace-normalizer/
├── golden-trace/
└── scenario-dsl/
```

#### RecordedModelPort

- 按 request/context hash 记录和回放规范化 ModelResult；
- 保存 usage、finish reason 和必要的 provider metadata；
- 不依赖原 Provider SDK 对象可序列化；
- 明确 unmatched request 是失败、fallback 还是重新录制。

#### FakeClock 与确定性 ID

所有 timeout、Approval expiry、backoff、lease expiry 和 wall-clock budget 通过 ClockPort；测试使用 FakeClock，不执行真实 sleep。ID 可注入，便于比较语义 Trace。

#### GoldenTrace

GoldenTrace 比较规范化语义事件：

- 去除时间戳、随机 ID、Delta 粒度等波动字段；
- 支持不变量断言和部分顺序，而非盲目逐字节相等；
- 对副作用、状态迁移、Approval、ErrorDisposition 和 Artifact lineage 保持严格；
- Schema 变化必须显式升级 fixture。

### 23.3 故障注入集

至少覆盖：

- Model 流式中断、timeout、rate limit；
- Tool 在副作用前/中/后崩溃；
- Outcome 已获但持久化前崩溃；
- Signal 重复、乱序、迟到和 Runtime 离线；
- Approval 到达时 Run crashed 或 Action 已变化；
- Cancel 与 Activity 完成竞态；
- Capability 撤销、Grant/Lease 过期；
- 文件变化、Artifact 冲突、浏览器 Session 失效；
- Context 过大、Tool pair compact、Blob 取回；
- Budget soft/hard limit 和无进展循环；
- State Snapshot 损坏和 Event rebuild。

### 23.4 Eval 记录

- Case、Dataset、AgentSpec、RunSpec；
- Provider、模型、Prompt、Skill、Tool 和 Adapter 版本；
- ContextFrame、Compact 和 retrieval 轨迹；
- Runtime Event、Tool 输入输出、ErrorRecord；
- Capability、ResolvedEffect、Approval；
- Verification、Artifact、BudgetUsage；
- Token、耗时、调用次数、估算成本；
- 确定性检查、LLM Judge 和必要人工评价。

## 24. 关键运行流程

### 24.1 新 Session Message 启动 Run

```text
persist UserMessage
    ↓
freeze ConversationSourceSnapshot
    ↓
resolve AgentSpec + WorkspaceExecutionSnapshot
    ↓
persist immutable RunSpec
    ↓
Runtime.start
    ↓
Kernel emits Context/Model Activity
    ↓
RunEvent stream
    ↓
Layer 2 projects Transcript and final AssistantMessage
```

### 24.2 Tool 调用

```text
complete ModelInvocation
    ↓ normalize complete Tool Call
    ↓ schema validate
    ↓ resolve effect + preconditions
    ↓ persist PreparedAction
    ↓ frozen grant check + live capability check
    ↓ preview / policy / approval
    ↓ persist Attempt Intent
    ↓ execute Activity
    ↓ materialize ToolResult or ErrorRecord
    ↓ Observation / Verification
    ↓ append legal call/result pair to Run Context
    ↓ continue Kernel
```

### 24.3 WAITING_FOR_USER

```text
Kernel creates WaitRequest
    ↓ persist event and Run state
    ↓ Layer 2 projects question
    ↓ User message with target requestId
    ↓ durable UserInputSignal
    ↓ Coordinator validates and consumes signal
    ↓ same Run resumes
```

没有 target requestId 或请求已关闭的用户消息创建普通 follow-up Run，不静默改变旧 Run。

### 24.4 Approval

```text
PreparedAction + preview + actionDigest
    ↓ ApprovalRequested
    ↓ Run WAITING_FOR_APPROVAL
    ↓ user decision persisted as signal
    ↓ validate approval/action/digest/expiry/live capability
    ↓ execute / reject / expire / re-prepare
```

### 24.5 Cancel

```text
persist CancelSignal
    ↓ abort current Activity
    ↓ determine side-effect state
    ├── known safe → CANCELLED
    ├── applied → preserve fact/artifact, then CANCELLED
    └── unknown → RECOVERY_REQUIRED or cancelled with recovery item
```

### 24.6 Crash Resume

```text
acquire run recovery lease
    ↓ load snapshot + replay later events
    ↓ inspect unfinished Activity and pending signals
    ↓ revalidate capability/environment/preconditions
    ↓ resolve outcome or request recovery
    ↓ continue without duplicating proven side effects
```

- 一个 Run transition、对应 Event、Activity Intent 和已消费 Signal 尽量在同一 Layer 3 事务提交；
- Projection 使用 eventId/sequence 幂等处理；
- Blob 写入使用 content hash，事实表只在 Blob durable 后引用。

## 27. 推进顺序与冻结门槛

### 27.1 阶段 1：Headless Walking Skeleton

最小实现：

- 纯 Kernel + Coordinator；
- Fake/Recorded ModelPort；
- In-memory Store、Signal Inbox 和 FakeClock；
- 一个只读 Tool 和一个可验证写 Tool；
- 最小 ResolvedEffect、ErrorRecord 和 ContextFrame；
- WAITING_FOR_USER / APPROVAL；
- 基本 Budget/Cancel；
- 结构化 Trace 和 Micro Cases。

这一阶段允许 Contract 继续迭代，但不得绕过 Effect、错误副作用状态和 Tool call/result 配对不变量。

### 27.2 阶段 2：Durable Runtime

- SQLite 事实表、Event、Snapshot、Blob；
- durable Activity 和 Signal 协议；
- timeout、cancel、retry、error taxonomy；
- Capability live lease、Policy、Approval expiry；
- Crash Resume、State Rebuild、Recorded Replay；
- Artifact Registry；
- 故障注入 Eval。

退出门槛：关键 crash window、cancel race、duplicate signal 和 unknown side effect 均有可重复测试。

### 27.3 阶段 3：Case 01

- Browser Capability 与并发 Lease；
- Chrome 登录态 Bridge；
- Human Takeover；
- 长媒体下载的 cancel/resume；
- 大 Tool Result 外置和 retrieval；
- Markdown、Manifest、Report、ZIP 与 Verification；
- Workflow Baseline 与 Agent 编排对比。

### 27.4 阶段 4 及以后

- Case 02 反证 Tool、Context、Artifact 和 Capability 抽象；
- 桌面产品化与 Trace/Eval Inspector；
- 只有 Eval 证明需要时，引入高级 Context、Memory、Planner、Verifier Strategy 或 Sub-agent；
- Sub-agent 引入前必须单独设计 Run relationship、Context 隔离、Budget/Capability 分配、Cancel 传播和父子 Recovery，不因已有 causation 字段而省略设计。

### 27.5 Contract 冻结门槛

在冻结对应精确 Contract 前必须完成：

| Contract | 必须先回答 |
|---|---|
| KernelInput / Directive | Activity 完成、取消、迟到结果和 Budget 输入语义 |
| RuntimeSignal | 幂等、排序、target request、过期和 terminal 行为 |
| ContextItem / Frame | provenance、Blob、pair、compact 和 provider validation |
| Tool / PreparedAction | effect resolution、preview、precondition、digest |
| Error / Attempt | retryability、side-effect state、disposition |
| RunEvent | schemaVersion、sequence、correlation、causation |
| Snapshot / Replay | event coverage、upcast、recorded vs live side effect |

## 28. 当前决策状态

### 28.1 已对齐

- 三层架构与单向依赖；
- Workspace / Session / Run 三中心；
- Session 是产品基础能力，Runtime 支持无 Session；
- Kernel 纯决策，Coordinator durable orchestration；
- Model/Tool 等外部工作使用 Activity；
- Session Context 与 Run Context 分开治理；
- EffectScope 由可信 Resolver 产生；
- Error 与 side-effect state 分开；
- frozen snapshot 与 live revocation/lease 分开；
- Durable Signal Inbox 与 Activity Abort 配合；
- Resume、Rebuild、Replay 分离；
- Budget、Progress Guard 和 Cancel 是强制语义；
- Eval/Testkit 是 P0 系统能力但不进入 Kernel；
- v0.1 不实现多 Agent，不写死单层 Run 假设。

### 28.2 待精确设计

1. KernelState、KernelInput、Directive 和 Transition TypeScript Contract；
2. Run / Activity / Action / Attempt 完整状态迁移表；
3. SQLite 事务、lease、outbox/inbox 和 crash recovery 算法；
4. Provider-specific Context protocol validation；
5. Declarative Effect Rule 和复杂 Resolver SDK；
6. Error code catalog 与不同 Tool 的 disposition matrix；
7. Budget 默认值、ProgressDetector 与 Compact 阈值实验；
8. Browser takeover 的 ResourceHandle 安全边界；
9. Event upcaster、Trace Normalizer 和 Replay fixture 格式；
10. Case 02 需求与验收轮廓。

### 28.3 当前明确不做

- 预定义业务 DAG；
- 多 Agent 默认架构；
- 通用、无约束的生命周期 Hook；
- 跨 Session 自动长期 Memory；
- 企业多租户、RBAC、计费和云端 Runtime；
- 为假想外部 Agent Engine 设计万能 Adapter；
- 将所有 Provider 原始流或所有 Tool 原始大结果无条件保存。

## 29. 最终架构摘要

```text
Workspace 冻结资源、配置与授权证据
        ↓
Session 冻结不可变 ConversationSourceSnapshot
        ↓
Layer 2 生成自包含 RunSpec
        ↓
Coordinator 串行提交状态，异步执行 RuntimeActivity
        ↓
Kernel 只消费规范化 Outcome 并产生下一条 Directive
        ↓
Context Runtime 管理 ToolResult、Blob、配对、预算和 Compact
        ↓
Action Runtime 解析真实 Effect，经过 Grant / Lease / Policy / Approval
        ↓
Observation 与 Verification 判断外部世界是否达到目标
        ↓
Durable Event / Snapshot / Replay 保证可诊断、可恢复、可评测
        ↓
Layer 2 将事实投影为 Message、Tool、Approval、Interaction 和 Artifact
```

V02 的核心不是增加更多名词，而是明确四条不能含混的执行边界：

1. **纯决策与异步活动分离，但通过 durable Activity 闭环。**
2. **模型看见的 Context 必须经过可追踪、可预算、协议合法的编译。**
3. **所有副作用必须先得到可信的 EffectScope，再谈 Policy、Approval 和重试。**
4. **恢复不是重新跑一遍；取消、未知副作用、实时撤权和外部变化都有明确处置。**

在此基础上，WorkAgent 可以先用单 Agent Loop 完成 Walking Skeleton 和真实 Case；未来若 Eval 证明需要 Sub-agent，再以独立 Run、隔离 Context 和显式资源分配方式演进，而不需要推翻当前三层架构。
