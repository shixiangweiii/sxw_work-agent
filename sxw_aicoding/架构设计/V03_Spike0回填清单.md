## 0. 一句话结论

Spike 0 分两轮完成。第二轮补测了**同平台、同模型、同 Key、仅 API 形状不同**的 Anthropic 兼容端点，构成一个变量隔离极干净的实验。

**最重要的三条：**

1. **D-07 得到决定性答案**：`ModelProtocolPort` 要吸收的是 **API 形状差异**，不是模型家族差异。同一个模型换形状，Port 需要处理的东西几乎全变；换模型（同形状）只影响能力，不影响协议。
2. **协议不变量在两个形状上都没有外部兜底**，必须由 Runtime 100% 自持。这不降低不变量的重要性，反而提高了。
3. **同一个模型，Anthropic 形状严格更适合做 Harness**（精确 token 计数、显式闭合事件、校验 tool 定义、有带外拒绝字段）。这是一条可执行的架构建议。

## 2. 需要改写的条款

### 2.1 §8.5 流式中断规则 —— 放宽默认

**现状**：「半截响应中已闭合的 Tool Call 是否可用……在结论出来前默认整体丢弃」。

**改为**：已闭合的 Tool Call 可以保留，闭合判据为二者之一：

1. 该 call 的参数 JSON 可完整解析；
2. **后继 index 已开始接收增量**（更强判据——流式增量按 index 顺序推进）。

**必须同时写明**：该 API 形状没有独立的「内容块闭合」事件，闭合完全由 Runtime 推断，不是 Provider 的保证。

### 2.2 §8.6 不变量 2 —— 理据改写（结论不变）

**现状理据**隐含「否则 Provider 会 400」。实测该实现缺 3 个 tool result 仍返回 200。

**改为**：

> 批内每个 Tool Call 必须有且只有一个 result。理据不是协议校验，而是**否则模型看到的世界失真**——它会以为某个工具未被调用，或把 A 的结果当成 B 的。目标运行环境不提供任何校验兜底，本不变量的执行责任 100% 在 Runtime。

同样处理 §12.5：`toolCallId` 作为锚点是 Runtime 的自我约定，不是外部契约。

**§11.5 可补一条**：实测组间顺序不受约束，protocolGroup 只需保证「成组」，不需保证「组间有序」。

### 2.3 §12.2 `REJECTED_*` —— 补充合成形态

该 API 形状没有 `is_error` 之类带外字段，拒绝语义只能写进 `content`。需要约定一个结构化 payload（实测模型能正确理解并如实转述）。建议字段：`code / message / sideEffectState / retryAllowed`。

### 2.4 §11.8 —— 初版判定撤回，维持【验】

**初版写的是「张力被证实且更极端，可升【定】」。那是单次采样的结论，多次采样后无法复现。**

真实情况：

| 形状 | 基线（前缀不变，4 次采样） | 改写前缀后**第一次** |
|---|---|---|
| OpenAI · 运行 A | `4352/4224/4224/4352`（4/4 命中） | **0** → 支持 §11.8 |
| OpenAI · 运行 B | `0/4224/4224/4352`（基线就不稳定） | 探针拒绝下结论 |
| Anthropic | `378/378/378/378`（稳定） | **378，仍命中** → 不支持 |

三点事实：

1. 该端点的缓存**在连续相同请求之间就已非确定**；
2. Anthropic 形状的显式 `cache_control` 断点基本没生效——命中恒为 378 tokens，远小于约 4900 的前缀，被缓存的只是 tools+system 那段固定小前缀；
3. 只有 OpenAI 形状的运行 A 给出了教科书式结果，一次观测不足以升【定】。

**对架构的实际输入**（比原结论更重要）：

> **缓存命中在该端点上不可预期，不能作为延迟或成本的可依赖假设。**

这反而**降低**了 §11.8 张力的严重性。§11.6 的「追加式外置优于重写式压缩」仍是合理倾向，但**理据要从「保住缓存」改为「减少重复计费的确定性收益」**。

### 2.5 §13.1 错误分类 —— 判别式按形状分别维护

两个形状的判别式**完全不同，且都不能只看一个字段**：

| 形状 | `type` | `code` | 可用判别式 |
|---|---|---|---|
| OpenAI | 恒为 `invalid_request_error`，**无区分度** | 有区分度（`model_not_found` / `invalid_api_key` / `invalid_parameter_error`） | status + code |
| Anthropic | 无该字段 | **粒度太粗**——`InvalidParameter` 同时覆盖「模型不存在」「请求体格式错」「tool schema 非法」 | status + message 文本 |

**改写**：映射基于 **HTTP status + code + SDK 异常类名**的组合，**且映射表按形状分别维护**。

**tool 定义 schema 的校验是形状差异**：同一个非法 schema，OpenAI 形状返回 200，Anthropic 形状返回 400 并给出精确诊断（`'properties' should be a dict but got str`）。

**但 tool 入参的校验是共性**：两个形状都放行了模型产出的 `{cityName}`（schema 要求 `city`）。因此 `source: TOOL_INPUT` 的错误**永远不会**来自 Provider——入参校验 100% 是 Runtime 职责；定义校验在部分形状上有兜底，但不能依赖。

### 2.6 §13.1 缺一个错误来源：SDK 层【新增】

`max_tokens: 99999999` 被 Anthropic SDK **自己拦截**（提示需要流式），根本没发出请求。

V03 的 `RuntimeErrorRecord.source` 枚举没有能表达「错误来自 SDK 而非 Provider 或 Runtime」的取值，这类错误会被误归类为 `MODEL_PROVIDER`——进而影响 retryability 判断（SDK 层的参数校验错误重试多少次都没用）。

**建议**：`source` 增加 `MODEL_SDK`，或在现有取值上补充说明。

## 3. V03 完全没有的新约束

### 3.1 §16.1 缺一个预算轴：tool schema 固定开销

**实测**：2 个只有一个字符串参数的工具 = **359 tokens**；每请求另有约 11 token 的 chat 模板底数。

20 个工具即约 3600 token 起步价，与任务内容无关。

**建议**：`RunBudgets` 与 `ContextBudgetPolicy` 显式区分「固定开销」与「可变内容」，§11.6 的阈值判断必须先扣除固定开销，否则「还剩多少上下文」算错。

### 3.2 §16.1 `reservedOutputTokens` 必须覆盖推理

**实测**（P4 / P7 两个探针独立复现）：

```
max_completion_tokens=64 → finish_reason="length", content="", reasoning_tokens=64
```

推理优先消耗输出预算，正文为空，**接口成功、无错误码**。

**建议两处修改**：

1. §16.1：`reservedOutputTokens` 必须同时覆盖推理与正文；
2. §8.5 / §13.1：Kernel 消费 `ModelInvocationResult` 时，把「`finish_reason=length` 且无内容且无 tool call」识别为明确错误条件（`source: MODEL_PROVIDER, category: CAPACITY`），而不是正常完成。否则 Runtime 会把空回复当作模型的正常回答继续推进，产生静默的错误决策。

## 4. 决策点的处置

### D-01　ActionBatch 是否支持批内并发 → **可拍板，但理据要改**

**证据**：两个形状都稳定返回 4 个 tool call。强制单条开关**只在 OpenAI 形状生效**：

| 形状 | 开关 | 实际效果 |
|---|---|---|
| OpenAI | `parallel_tool_calls: false` | **生效**，返回 1 个 |
| Anthropic | `disable_parallel_tool_use` | **被接受但无效**，仍 4 个 |

**建议**：仍选 **C**——接口按并发设计（`ActionBatch.executionMode`），v0.1 只实现 `SEQUENTIAL`。

**但理据必须改**：初版写的是「协议侧强制单条可用，为串行提供额外保障」。在推荐使用的 Anthropic 形状上这个保障**不存在**。因此：

> 批内串行必须由 Runtime 自己保证，协议开关只是可有可无的加成，**不得作为设计前提**。

这与 §8.6 不变量 2 的处境一致：外部兜底不可依赖。

→ 落 ADR-0002。

### D-05　上下文不可压缩时的默认动作 → **候选 A 重获触发点（形状相关）**

**初版判定基于 OpenAI 形状**（无预检端点，只能本地估算，误差无法量化）。第二轮改变了结论：

| 形状 | 能否提前判定「即将超限」 |
|---|---|
| OpenAI | **否**——无预检端点，只能本地估算，误差未量化 |
| Anthropic | **能，且精确**——`count_tokens` 5/5 项 0.00% 误差 |

**在推荐使用的 Anthropic 形状上，`COMPACTION_INSUFFICIENT` 有精确可靠的触发点**，D-05 的候选 A（先做更激进的 Compact）完全可行。

其余事实不变：窗口 ≥ 60 万 token 未测到上界；**未静默截断**（专门验证过——静默截断比报错危险得多，因为模型看到残缺输入而 Runtime 无从察觉）。

**建议**：D-05 可以按候选 A 拍板，但需在 ADR 中写明**该结论依赖形状**：若将来切到无预检端点的形状，触发点退化为本地估算，策略需相应放宽阈值。

### D-07　重述后**已有决定性证据，可拍板**

**原表述不成立**：「v0.1 单 Provider 还是双 Provider（Anthropic / OpenAI）」——本项目的运行环境就是第三方兼容端点，官方 API 成本不可承受，这两个候选都不存在。

**重述为**：`ModelProtocolPort` 应当吸收哪一类差异？

**第二轮实验直接回答了它。** 同平台、同模型、同 Key，仅 API 形状不同：

| 类别 | 内容 |
|---|---|
| **共性**（模型/平台层面） | 多 tool call 是默认行为；不校验配对、call id、顺序、tool 入参；推理块可删可改；计费口径完全一致（tool 开销 359、200KB result 计 34576，分毫不差） |
| **差异**（协议形状层面） | 有无 token 预估端点；有无流式闭合事件；有无带外拒绝字段；tool 定义是否被校验；强制单条开关是否真生效；错误判别式；缓存机制；usage 字段名 |

**结论**：

> `ModelProtocolPort` 的抽象边界按 **API 形状**切分，不按模型家族切分。
> 一个「形状适配器」对应一套 `countTokens / validateFrame / identifyProtocolElements / normalize` 实现；
> 同形状下换模型只需替换**能力声明**，不换适配器。

**附带的可执行建议**：**v0.1 优先走 Anthropic 形状端点。** 四条直接收益——

| 能力 | 对 V03 的价值 |
|---|---|
| `count_tokens` 精确（0.00%） | §11.6 阈值可精确判定；`:2383` 在此形状可解除；D-05 候选 A 重获触发点 |
| `content_block_stop` 显式闭合事件 | §8.5 的放宽有协议依据，不靠推断 |
| 校验 tool 定义 schema | Runtime 少一类自持责任 |
| `is_error` 带外字段 | §12.2 的 `REJECTED_*` 可结构化表达 |

唯一代价：`disable_parallel_tool_use` 在该形状上**被接受但无效**，强制串行拿不到协议保障（见 D-01）。

→ 落 ADR-0001，标题改为「ModelProtocolPort 的抽象边界：按 API 形状切分」。

**仍建议补测**：换模型（同形状）跑一遍，验证「换模型只影响能力不影响协议」这一推论。成本极低。
