## 0. 本版说明与阅读约定

### 0.1 本版的性质

V01 的问题是「重控制面、轻数据面」，V02 已经修复。V02 的问题不再是语义留白，而是**规格跑到了证据前面**：在零行运行代码、零次真实 Provider 调用的前提下，已经命名了 50 个 interface、14 个 type union、15 个 Port、33 张逻辑表、13 条 Directive、约 25 类 Durable Event。

二次评审发现的三个 P0（一次响应多个 Tool Call、Provider 必须原样回传的协议块、token 会计归属）有同一个成因：**它们只有在真正调用过一次带工具的流式 Provider 之后才会暴露**，而 V02 的阶段 1 只使用 Fake/Recorded ModelPort。按那条路线，这类问题会在 Contract 冻结之后才被发现。

因此 V03 做三件事：

1. 修正二次评审确认成立的 6 个 P0 与 16 个 P1；
2. 引入**状态标记约定**，把「已拍板的不变量」与「已命名但未验证的假设」在文档层面分开，防止未验证内容被当作既成事实实现；
3. 增加 **Spike 0（Provider 协议现实核对）** 与 **第 30 章关键决策点**，把「想清楚」升级为「跑出来 + 拍下来」。

本文档仍然是总体架构设计，不替代精确 TypeScript Contract、状态迁移表、SQLite 事务设计和 ADR。**若与上位基线冲突，以上位基线为准。**

### 0.2 状态标记约定

本文所有具有约束力的条目使用以下三种标记之一。**未标记的段落是说明性文字，不构成约束。**

| 标记 | 含义 | 处理方式 |
|---|---|---|
| **【定】** | 已拍板不变量 | 不再反复讨论；实现违反即架构错误；变更需要独立 ADR |
| **【验】** | 当前方向，待证据验证 | 有明确倾向，但必须由 Spike / Micro Case / Eval 证据确认后才能冻结；实现时允许迭代 |
| **【议】D-xx** | 待决策 | 见第 30 章对应决策点；在拍板前**不得**在代码中固化任一候选方案 |

这条约定本身是【定】。它的目的是回答一个具体风险：一份 2000 行、术语自洽的架构文档极容易被后续实现整体当成"已经定好了"，从而在没有任何运行证据的情况下把假设固化进 33 张表。

## 1. 文档目的

本文档回答以下问题：

1. 纯 Kernel 与异步、流式 Model / Tool Activity 如何协作；
2. **一次模型响应产生多个 Tool Call 时，批的原子性、审批、取消与配对如何成立**；
3. **模型上下文中哪些结构必须原样回传，Compact 不得触碰**；
4. RuntimeSignal 如何持久化、排序、幂等处理并中断长 Activity；
5. **Run 正常完成的判定条件是什么，交付由谁验收**；
6. **Run 执行期间用户插话如何安放，而不造成产品死锁**；
7. ToolResult 如何进入 Run 内 Context，大结果如何外置、预览、取回和 Compact；
8. **脱敏发生在哪一个点，才能满足"凭证不进入模型上下文与 Trace"的已拍板要求**；
9. Tool 参数如何解析为可信 EffectScope，并接受 Capability、Policy 和 Adapter 三层校验；
10. 错误如何分类，如何决定重试、模型自纠、等待用户、人工恢复或终止；
11. Cancel、Timeout、Crash Resume、Replay 与外部世界变化分别具有什么语义；
12. Budget、无进展检测、循环检测和优雅停止如何成为 Runtime 不变量；
13. **执行事实与产品聚合跨层时，权威状态归谁，一致性协议是什么**；
14. **哪些数据永不删除，哪些可以回收**；
15. 在不实现多 Agent 的前提下，如何避免写死单层 Run 假设；
16. **哪些内容已经可以冻结，哪些必须先有证据，哪些必须先拍板**。

## 2. V03 核心结论

### 2.1 主架构保持不变【定】

```text
Workspace：资源、授权和工作环境中心
Session：持续交互和意图演进中心
Run：Agent 单次执行、恢复和评测中心
```

```text
Layer 1  WorkAgent UI
    ↓
Layer 2  Application Service / Harness Host
    ↓ immutable snapshot + typed signal/event
Layer 3  Harness Runtime
```

- Layer 2 是可变产品配置的 Control Plane；
- Layer 3 是一次 Run 的 Execution Data Plane；
- Layer 3 不访问 Layer 2 Repository；
- Eval、CLI 和桌面产品复用相同 Runtime Facade；
- Kernel 保持纯决策，Coordinator 负责 durable orchestration；
- 不引入预定义业务 DAG，不把多 Agent 设为 v0.1 默认架构。

### 2.2 V03 的实质修正

| # | 修正 | 性质 |
|---|---|---|
| 1 | 一次 ModelInvocation 的全部 Tool Call 构成 **ActionBatch**，批未结算不得发起下一次模型调用 | 新不变量 |
| 2 | Context 的不可拆分单元从「call/result 对」泛化为 **protocolGroup**，并引入 `REQUIRED_VERBATIM` 角色 | 修正不变量 |
| 3 | 循环终止规则显式化：**模型不再请求工具 → 进入 Completion Check → 评估 RunAcceptance** | 补缺失核心语义 |
| 4 | 新增 **InterjectSignal**，解决执行/等待期间用户输入无处安放的死锁 | 新语义 |
| 5 | Compact 分层归属：**soft 由 Context Runtime 自治，hard 由 Kernel 决策**；Handoff 分 MODEL_AUTHORED 与 DETERMINISTIC 两类 | 消除二义 |
| 6 | 脱敏点从 Context Materialization **下沉到离开 Adapter 边界的第一个持久化点** | 安全边界修正 |
| 7 | 跨层聚合（Artifact / Approval / ExternalInteraction）统一为「Layer 3 拥有执行事实，Layer 2 拥有产品聚合，单向投影」 | 新章节 |
| 8 | 墙钟拆分为 **activeWallClock / totalWallClock**；长 Activity 强制 durable heartbeat | 修正失控保护 |
| 9 | 新增 **Durable Timer** 子系统与 **ModelProtocolPort**、**RedactionPort** | 补基础设施 |
| 10 | 新增**数据保留与回收**语义 | 补运行现实 |
| 11 | 新增 **Spike 0**，并把冻结门槛从"必须先回答"升级为"必须先有证据" | 方法论修正 |

### 2.3 只采纳目标、不照搬实现的建议

以下继续成立（继承自 V02，本版确认）：

- 不把 JSONPath 作为所有 EffectScope 的唯一提取机制；
- 不把 transient / model-recoverable / user-fixable / fatal 当作完整错误分类学；
- 不引入可以绕过不变量的通用 Pre/Post Hook；
- 不假设 LLM 可以可靠传播「来自不可信内容」的污点标签；
- 不仅添加一个孤立的 `parentRunId` 便宣称已经支持 Sub-agent。

本版新增两条：

- **不用可变 cursor + delta 替代不可变 Conversation Context Snapshot**，但必须承认其存储代价并用**分段内容寻址**消解，而不是假装没有代价（§7.6）；
- **不把 AG-UI 等外部 UI 协议作为线上协议引入**，但采纳其经过大规模生产验证的事件语义作为参照，并把渲染层留在适配器之后（§5.5）。

### 2.4 多 Agent 的当前边界【定】

v0.1 不实现 Sub-agent、并行 Agent 或 Run Group，但禁止写死以下假设：

- Runtime 不得要求 Run 必须属于 Session；
- 「一个 Session 一个 Foreground Run」是 Layer 2 产品策略，不是 Layer 3 不变量【议】D-09；
- Run 的因果来源不能只绑定 Session Message；
- Child/Background 执行未来不得直接写入 Session Transcript；
- Context、Budget、Capability 和 Cancel 未来是否继承必须显式决定，不能隐式全量继承。

当前仅预留通用 `correlationId`、`causation` 和 Run 独立执行边界。

**注意区分**：本条约束的是**多 Agent**。「一次模型响应产生多个 Tool Call」不属于多 Agent，它是 Provider 的默认行为，必须在 v0.1 建模（§8.6）。V02 把两者混为一谈是本版修正的首要问题。

### 2.5 规格纪律【定】

1. 任何 Contract 冻结前，必须能指出支撑它的证据来源（Spike、Micro Case、故障注入用例或 Eval 结果）；
2. 无法指出证据来源的条目一律标记【验】或【议】，不得进入冻结门槛表的"已完成"列；
3. 阶段 1 只实现能被当阶段 Micro Case 覆盖的最小表集与最小 Contract 面，其余保持"已设计未实现"；
4. 每新增一个 Port，必须同时指出强制它存在的不变量。仅为"可扩展"而增加的 Port 不予接受。

#### 关于本版规格规模的说明

必须坦白：**V03 的规格面比 V02 更大，不是更小**。

| 指标 | V02 | V03 |
|---|---|---|
| 逻辑表 | 33 | 38 |
| Port | 15 | 19 |
| Directive | 13 | 16 |

二次评审批评的是"规格跑到证据前面"，而不是"规格太多"。本版新增的部分（ActionBatch、Acceptance、Timer、Redaction、Interject）每一项都对应一个**必然会在第一次真实运行时发生**的问题，删掉它们不会让项目更轻，只会让问题推迟暴露。

真正的纠偏机制不是砍条目，而是三条：

1. **状态标记**（§0.2）——把"已拍板"与"已命名但没验证过"在文档层面分开；
2. **Spike 0**（§28.1）——在冻结前先拿到 Provider 协议的真实事实；
3. **实现切面**（D-14）——明确阶段 1 只实现 38 张表里的哪几张，其余保持"已设计未实现"。

没有这三条，规格规模本身就是风险；有了这三条，规格是设计资产。

## 3. 架构原则

### 原则一：事实、执行状态和产品投影分离【定】

- User Message、Workspace 配置属于产品事实；
- Run、Activity、ActionBatch、Action、Attempt、Observation、Verification 属于运行事实；
- Assistant Message、Tool Card、Approval Card、Artifact Card 是可重建产品投影。

### 原则二：可变配置冻结，实时安全不冻结【定】

Run 启动时冻结 Prompt、Tool Schema、Skill、Policy、Capability Grant 和环境证据，用于恢复和复现。

以下实时安全状态仍可阻止后续执行：Capability 被撤销；Grant 或凭证过期；ResourceMount 不可用；执行目标超出当前授权；宿主触发紧急停止。

冻结快照是证据，不是绕过实时撤权的通行证。

### 原则三：外部副作用前持久化意图【定】

```text
Resolve Effect
    ↓
Persist PreparedAction / Attempt Intent
    ↓
Acquire Capability Lease and execute
    ↓
Redact at boundary, then persist outcome and side-effect certainty
    ↓
Observe / Verify
    ↓
Kernel continues
```

### 原则四：Kernel 纯决策，Activity 异步执行【定】

Kernel 不执行 I/O，不等待网络，不处理流式传输。Coordinator 将 Directive 物化为 Activity，Activity Runtime 通过 Port 执行外部工作。

### 原则五：状态提交串行，外部工作不长期持锁【定】

同一 Run 的 durable 状态迁移必须串行化；分钟级 Model / Tool 调用不得长期占有数据库推进锁。Coordinator 使用 claim / lease / generation 防止旧结果覆盖新状态。

### 原则六：Session History 不等于 Model Context【定】

Session 保存事实；RunSpec 冻结不可变 Context Source；Context Runtime 选择、裁剪、外置、取回、压缩并形成每次 ModelInvocation 的 ContextFrame。

### 原则七：Effect 必须由可信代码解析【定】

Policy 不直接相信模型描述的副作用范围。PreparedAction 的 EffectScope 必须由注册的、版本化的 Effect Resolver 从已校验参数和当前资源状态中解析。

### 原则八：错误处置服从副作用确定性【定】

任何重试决定都必须同时考虑错误类型、retryability、幂等性和外部副作用是否可能已经发生。

### 原则九：Trace 是事实，Delta 是旁路【定】

流式 Delta、进度和心跳是 transient 体验事件；最终 Invocation、Activity、Action、Verification 和 Run Outcome 必须形成 durable 事实。

**本版补充**：长时运行的 Activity 必须周期性产出**低频 durable heartbeat**，否则无进展检测无法区分"卡死"和"正在下载 4GB 媒体"（§16.2）。

### 原则十：高级策略不能绕过 Kernel 不变量【定】

未来 Planner、Verifier、Memory 或 Sub-agent 可以改变决策策略，但不能绕过 Capability、Policy、Approval、Budget、Durability、Trace 和 Cancel。

### 原则十一：模型协议要素不可被上下文治理破坏【定·新增】

Context Runtime 的裁剪、外置、Compact 与重排，**不得**破坏 Provider 协议要求的结构完整性。哪些结构属于此类由 `ModelProtocolPort` 声明，而非由 Context 模块猜测。已知的两类是 tool_call/tool_result 配对与必须原样回传的推理块；具体清单以 Spike 0 结论为准（§28.1）。

### 原则十二：脱敏发生在离开执行边界的第一个持久化点【定·新增】

未脱敏的原始 Tool 输出、Provider 原始响应和诊断数据，**不得**离开 Adapter 边界写入任何 Blob、事实表或 Event。Context Materialization 的过滤是预算边界，不是安全边界。

此条直接来自上位基线 §9.3 / §13.1 的已拍板项：「Cookie、Token 和浏览器凭证不进入模型上下文与 Trace」。

### 原则十三：证据先于冻结【定·新增】

未经运行证据支持的 Contract 不得冻结。Provider 协议、token 计数口径、上下文阈值与预算默认值属于必须先有证据的一类（§28.1、§28.7）。

```text
  → depends on Runtime Public Facade and Testkit
```

禁止：

```text
Harness Runtime → Application Service Repository
Harness Runtime → UI
Harness Runtime → Eval Dataset / Grader
Harness Runtime → 具体 Case Package
Kernel → SQLite / Electron / Browser / Provider SDK
Context 模块 → Provider SDK（必须经 ModelProtocolPort）
```

## 5. Layer 1：WorkAgent UI

### 5.1 职责

- Workspace、Session 和配置管理；
- User / Assistant Message；
- Assistant 文本流式展示；
- Tool、ActionBatch、Attempt、Verification 和进度展示；
- Approval Request 展示与决策提交；
- Run 暂停、恢复、取消、插话和重新执行；

- Trace 和 Eval Inspector。

### 5.2 UI 不拥有的语义【定】

- Run 合法状态迁移；
- Action 是否允许执行；
- EffectScope 是否落在 CapabilityGrant 内；
- Tool 是否可安全重试；
- Cancel 后副作用是否已经发生；
- Postcondition 是否通过；
- Run 是否达成 Acceptance；
- Signal 是否过期或重复；
- Crash 后从哪个 Activity 恢复。

### 5.3 Transcript

```ts
type TranscriptEntry =
  | UserMessageEntry
  | AssistantMessageEntry
  | InterjectionEntry
  | ProgressEntry
  | ToolActionEntry
  | ActionBatchEntry
  | ApprovalEntry
  | ExternalInteractionEntry
  | ArtifactEntry
  | SystemNoticeEntry;
```

每个投影项保存 `sourceRunId` 和至少一个 `sourceEventId / sourceActionId / sourceActivityId`。未来 Background/Child Run 不直接写入 Transcript，由 Foreground Run 或 Layer 2 聚合后投影。

`InterjectionEntry` 是本版新增：用户在 Run 执行期间的插话必须在 Transcript 中可见，且必须与"启动新 Run 的消息"在视觉上可区分，否则用户无法理解为什么有些话触发了新任务、有些话只是被采纳。

### 5.4 前后端协议

- HTTP Command：创建对象、发送消息、启动/取消/暂停 Run、插话、提交 Approval 和 Interaction Completion；
- HTTP Query：查询 Workspace、Session、Artifact、配置和 RunSnapshot；
- SSE：Assistant Delta、Run 状态、ActionBatch/Tool 状态、Approval、Artifact；
- WebSocket：只用于终端、浏览器人工接管等明确双向实时场景；
- 所有命令携带 idempotency key 或 signalId；
- SSE/WS 重连使用事件游标，不依赖内存订阅状态。

### 5.5 决策记录 A-01：不引入外部 Agentic UI 协议【定】

**决策**：v0.1 不把 AG-UI、A2UI、MCP Apps 作为线上协议引入，自研 RunEvent 协议。

**理由**：

1. 自研事件语义本身就是学习目标（上位基线 §7.1 把「规范化 Trace Contract」列为必须亲自实现）；
2. 单人桌面场景不存在跨前端互操作需求，引入外部协议只增加映射层；
3. 该层标准之战未定局，AG-UI 治理由单一商业公司主导，核心采纳数据为厂商自述（见调研 §四）。

**采纳其语义参照**（不引入依赖）：

- ToolCall 生命周期四段事件建模；
- 重连语义采用 StateSnapshot + 增量的思路（本文以 `RunSnapshot` + 事件游标实现）；
- human-in-the-loop 中断的事件建模（本文以 Approval / ExternalInteraction 实现）。

**架构约束**：渲染层保持在适配器之后，RunEvent 与 UI 组件之间保留一层映射，使未来输出 AG-UI 适配器不需要改动 Runtime。

**重新评估触发条件**：需要被外部前端消费；或需要向 IDE / 聊天宿主交付 UI（届时评估 MCP Apps 路线）。

`agents/` 拥有 AgentProfile、默认模型/策略选择以及生成 AgentSpecSnapshot 所需的产品配置。

### 6.2 Workspace 与 Resource

Workspace 是资源、能力配置和授权边界。Resource 模块负责：

- PrimaryFileSpace、ResourceMount 和 Managed Upload；
- ResourceRef 解析；
- 路径规范化、symlink / 路径逃逸检查；
- 文件元数据与 content hash；

Session 模块负责：

- WorkSession 生命周期；
- User Message 和 Assistant Message Projection；
- Transcript、Pinned Resource 和 Context Cursor；
- **用户输入的路由决策**（新 Run / 恢复原 Run / 插话，见 §9.7）；
- immutable ConversationSourceSnapshot 的生成与保存；
- Session 归档。

v0.1 一个 Session 同时只允许一个 Foreground Active Run【议】D-09。这是 Layer 2 的交互一致性策略，不限制 Layer 3 同时执行多个无 Session Run。

### 6.4 Capability Control Plane

负责 Definition Catalog、Workspace Binding、Provider 配置、Scope、SecretRef、健康检查和撤销。Run 启动时生成冻结 CapabilityGrant；执行前由 Adapter 或 Capability Runtime 取得短生命周期 Lease 并检查实时状态。

### 6.5 Runtime Host

负责：

- 创建并配置 Harness Runtime；
- 注入 Model、ModelProtocol、Storage、Tool、Redaction、Timer、Artifact、Trace、Blob、Clock 等 Port；
- 从 Workspace、Agent 和 Session 创建 RunSpec；
- 恢复未结束 Run；
- 将用户输入、插话、Approval、Cancel、Interaction Completion、Recovery Decision 转成 RuntimeSignal；
- 接收 RunEvent 并投影为 Transcript / UI Event 与产品聚合（§23）；
- 监督进程退出和 Activity Abort。

Runtime Host 不实现 Agent Loop，不直接修改 Runtime 内部事实表。

### 7.1 Workspace

```ts
interface Workspace {
```

Workspace 不变量【定】：

### 7.6 ConversationSourceSnapshot：分段内容寻址【修正】

V02 把整个会话历史冻结为单个不可变 blob。不可变性是对的，但每条新消息都会改变整体 hash，导致每个 Run 全量重存历史，长 Session 呈 O(n²) 增长。本版保留不可变语义，改为分段：

```ts
interface ConversationSourceSnapshotRef {
  snapshotId: ContextSourceSnapshotId;
  sessionId: SessionId;
  transcriptCursor: MessageId;
  segments: ConversationSegmentRef[];
  manifestHash: string;
  checkpointRefs: ContextCheckpointRef[];
  pinnedResourceRefs: ResourceRef[];
}

interface ConversationSegmentRef {
  segmentIndex: number;
  fromMessageId: MessageId;
  toMessageId: MessageId;
  contentHash: string;
  blobRef: BlobRef;
  messageCount: number;
}
```

规则【定】：

1. Segment 一旦封闭即不可变，其 `contentHash` 与 `blobRef` 永不改变；
2. 新消息只追加到开放 segment；开放 segment 达到阈值后封闭并开启新 segment；
3. Snapshot 是 segment 列表 + manifestHash，Run 之间共享已封闭 segment；
4. Runtime 仍然只看见不可变引用，**不通过可变 cursor 回查 Layer 2 数据库**；
5. 分段大小属于 ContextPolicy【验】，需要观测真实 Session 长度分布后确定。

### 7.7 RunSpec、RunOrigin 与因果信息

#### RunOrigin 改为开放式驱动标签【修正】

V02 的 `RunOrigin` 是闭合联合，把 `EvalCaseId`、`AutomationId` 写进 Layer 3 类型，既与「Runtime 不依赖 Eval」的依赖规则相悖，也导致每新增一种驱动方都要改 Runtime 核心类型。

```ts
interface RunOrigin {
  driver: string;
  driverRef?: string;
  workspaceId?: WorkspaceId;
  sessionId?: SessionId;
}
```

【定】Layer 3 **只**对 `workspaceId` / `sessionId` 是否存在做行为区分（决定是否有 Workspace 授权与会话上下文）；`driver` 与 `driverRef` 对 Layer 3 是不透明标签，仅用于 Trace 与 Eval 归类。driver 与 causation 的合法组合由 Layer 2 的 RunSpecFactory 校验。

v0.1 使用的 driver 值：`session` / `cli` / `eval` / `automation`。保留 `runtime` 表示未来由另一个 Run 触发的独立执行。

```ts
type RunCausation =
  | { kind: "SESSION_MESSAGE"; sourceId: MessageId }
  | { kind: "CLI_COMMAND"; sourceId: string }
  | { kind: "EVAL_CASE"; sourceId: string }
  | { kind: "AUTOMATION_TRIGGER"; sourceId: string }
  | { kind: "RUN_ACTION"; sourceRunId: RunId; sourceActionId: ActionId };
```

`RUN_ACTION` 去掉了 V02 中与 `sourceActionId` 重复的 `sourceId` 字段。

```ts
interface RunSpec {
  id: RunSpecId;
  origin: RunOrigin;
  correlationId: string;
  causation: RunCausation;
  input: RunInput;
  agentSpec: AgentSpecSnapshot;
  workspace?: WorkspaceExecutionSnapshot;
  conversationContext?: ConversationSourceSnapshotRef;
  acceptance: RunAcceptance;
  budgets: RunBudgets;
  runtimeEnvironmentFingerprint: EnvironmentFingerprint;
  createdAt: Timestamp;
}
```

`correlationId`【定】：由最初的用户意图或外部触发生成，在由此派生的全部 Run、Signal、Event 中原样传递，用于跨 Run 追踪一次完整的用户诉求。

`RUN_ACTION` 只预留通用因果表达能力，不代表 v0.1 已支持 Child Run。任何未来的父子预算、取消和权限继承仍需独立 ADR。

### 8.2 Runtime Facade

```ts
interface HarnessRuntime {

  recover(runId: RunId): Promise<RunHandle>;
  signal(runId: RunId, signal: RuntimeSignalEnvelope): Promise<SignalReceipt>;

  inspect(runId: RunId): Promise<RunSnapshot>;
  subscribe(runId: RunId, after?: EventCursor): AsyncIterable<RunEventEnvelope>;

```

**命名修正**：V02 的 `resume()`（崩溃恢复）与 `ResumeSignal`（解除暂停）同名不同义，是典型的实现期 bug 源。本版统一为：

| 概念 | 名称 | 语义 |
|---|---|---|

```ts
  | "OBSERVATION"
  | "VERIFICATION"
  | "ACCEPTANCE_EVALUATION"
  | "CONTEXT_COMPACTION";
```

```ts
type ActivityStatus =
  | "PLANNED"
  | "STARTED"
  | "SUCCEEDED"
  | "FAILED"
  | "CANCELLED"
  | "SKIPPED"
  | "OUTCOME_UNKNOWN";
```

```ts
interface RuntimeActivity {
  id: ActivityId;
  runId: RunId;
  kind: ActivityKind;
  directiveId: DirectiveId;
  batchId?: ActionBatchId;
  generation: number;
  inputDigest: string;

  error?: RuntimeErrorRecord;

```

`CONTEXT_FRAME_COMPILATION` 提升为一等 ActivityKind，因为它的 Outcome 承载 token 会计，必须回传给 Kernel（§11.6）。`SKIPPED` 用于批内被跳过的 Action。`lastHeartbeatAt` 支撑无进展检测（§16.2）。

Coordinator 的推进协议【定】：

```text
Acquire Run Lock
    ↓
load state + consume eligible signals
    ↓
Kernel.advance
    ↓
persist transition + Activity PLANNED/STARTED + generation
    ↓
Release Run Lock
    ↓
execute Activity through Port
  ├── emit transient progress
  └── emit low-frequency durable heartbeat
    ↓
Redact at adapter boundary
    ↓
Acquire Run Lock
    ↓
verify activity generation is still current
    ↓
persist outcome and feed Kernel
    ↓
Release Run Lock
```

外部 Activity 不长期持有 Run Lock。旧 generation 的迟到结果只能作为诊断事件保存，不得覆盖 Cancel、Retry 或新 Activity 已提交的状态。

### 8.5 ModelInvocation 生命周期

1. Kernel 产生 `RequestModelDirective`；
2. Coordinator 持久化 Invocation Intent 和 Activity；
3. ModelPort 开始异步流式调用；
4. Delta 通过 transient event 旁路输出；
5. 正常完成后，Provider 响应经 `ModelProtocolPort.normalize()` 规范化为 `ModelInvocationResult`；
6. **规范化结果保留 Provider 要求原样回传的协议块**（§11.5），并识别其中的全部 Tool Call；
7. 只有完整且协议合法的结果进入 Kernel；
8. Usage、耗时、Provider request ID 和最终内容引用形成 durable event。

流式中断规则【定】：

- Cancel/timeout 后，半截文本默认不进入后续 Model Context；
- 半截内容脱敏后可外置保存用于诊断，标记 `INTERCEPTED/PARTIAL`；
- 未完整闭合的 Tool Call 不得转为 ProposedAction；
- **半截响应中已闭合的 Tool Call 是否可用，取决于 Provider 是否保证其完整性**【验】，以 Spike 0 结论为准；在结论出来前默认整体丢弃；
- Provider 明确支持的可恢复响应必须先规范化，再由新 Activity 继续；
- UI 可以展示"响应已中断"，但不得把半截输出投影为 FINAL Assistant Message。

### 8.6 ActionBatch：一次 ModelInvocation 的多个 Tool Call【新增·P0-1】

#### 问题

Anthropic 与 OpenAI 在单个 assistant turn 内返回 tool call 数组是**默认行为**。V02 的模型是严格单 Action 管道（`currentActionId` 单值、线性生命周期），若只执行第一条，§11.5 的配对不变量当场被违反——其余 call 没有 result，下一次请求协议非法。

这不属于 §2.4 约束的「多 Agent」范畴，而是 v0.1 第一次真实调用就会撞上的协议现实。

#### 模型

```ts
interface ActionBatch {
  id: ActionBatchId;
  runId: RunId;
  invocationId: ModelInvocationId;
  actionIds: ActionId[];
  executionMode: "SEQUENTIAL" | "CONCURRENT_LIMITED";
  maxConcurrency?: number;
  approvalMode: "PER_ACTION" | "BATCH_SINGLE";
  batchDigest: string;
  settlement: BatchSettlementPolicy;
  status: "PLANNED" | "IN_PROGRESS" | "SETTLED";
  settledAt?: Timestamp;
}

interface BatchSettlementPolicy {
  onActionFailure: "CONTINUE_REMAINING" | "SKIP_REMAINING" | "ABORT_BATCH";
  onApprovalRejected: "SKIP_REMAINING" | "CONTINUE_REMAINING";
  onCancel: "ABORT_UNSTARTED";
}
```

#### 不变量【定】

1. 一次 ModelInvocation 产出的**全部** Tool Call 构成一个 ActionBatch；
2. **批内每个 Tool Call 在返回模型前必须拥有恰好一个协议合法的 result**。成功、失败、被 Policy 拒绝、被用户拒绝、被跳过、被取消——每一种终局都必须合成结构化 result，不允许任何 call 无 result；
3. 批未 `SETTLED` 前，不得发起下一次 ModelInvocation；
4. 批内每个 Action **独立**经过 Effect Resolution、Capability 三层校验与 Policy 判定，不因同批而共享授权；
5. `approvalMode = BATCH_SINGLE` 时，一次批准覆盖整批，但 `batchDigest`（全部 `actionDigest` 的有序摘要）任一变化即失效；
6. 批内存在 EXCLUSIVE / KEYED lease 冲突时，冲突子集自动降级为串行，不得并发争抢；
7. Cancel 落在批中间时：已完成 Action 的事实与副作用保留，未启动 Action 标记 `SKIPPED` 并合成 result，进行中的 Action 按 §9.5 处理；
8. 批的 token 与预算计入按 Action 逐条累计，`decisionStep` 按批计一次（§16.5）。

#### v0.1 默认

【验】v0.1 默认 `executionMode = SEQUENTIAL`、`approvalMode = PER_ACTION`。这是**显式的产品策略选择**，不是协议限制——文档必须记录这一点，否则未来放开并发时会误以为在突破架构约束。

【议】D-01：是否在 v0.1 就支持批内并发（只读 Tool 并发收益明显，但会显著增加取消与恢复的状态空间）。

## 9. RuntimeSignal 与并发协议

### 9.1 Signal Envelope

```ts
interface RuntimeSignalEnvelope<T extends RuntimeSignal = RuntimeSignal> {
  signalId: SignalId;
  schemaVersion: number;
  runId: RunId;
  type: T["type"];
  correlationId: string;
  targetRequestId?: WaitRequestId | ApprovalId | InteractionRequestId | RecoveryRequestId;
  expectedRunRevision?: number;
  createdAt: Timestamp;
  payload: T;
}
```

### 9.2 Signal 类型

```ts
type RuntimeSignal =
  | UserInputSignal
  | InterjectSignal
  | ApprovalDecisionSignal
  | RecoveryDecisionSignal
  | ExternalInteractionCompletedSignal
  | PauseSignal
  | UnpauseSignal
  | CancelSignal
  | HostShutdownSignal;
```

相对 V02 的变化：

- 新增 `InterjectSignal`（§9.7），解决执行期间用户输入死锁；
- 新增 `RecoveryDecisionSignal`。V02 的 `KernelInput` 有 `RecoveryDecisionInput`、事件表有 `RecoveryDecisionApplied`，但**信号联合里没有对应类型**，恢复链路是断的；
- `ResumeSignal` → `UnpauseSignal`，与 `recover()` 解耦（§8.2）。

### 9.3 Durable Inbox 不变量【定】

1. Signal 在返回 accepted receipt 前必须持久化；
2. `signalId` 全局幂等，同一 signal 重复提交返回同一处理结果；
3. 同一 Run 的状态迁移按 durable sequence 串行提交；
4. Signal 是否可消费由当前 RunStatus、targetRequestId 和 expectedRunRevision 决定；
5. Terminal Run 不消费推进类 Signal，但重复 Cancel 可以幂等返回 terminal 状态；
6. 过期、目标不匹配或已决策的 Signal 形成拒绝记录，不能静默丢弃；
7. ApprovalDecision 必须同时匹配 approvalId、actionId 或 batchDigest、以及有效期；
8. Signal 到达时 Runtime 进程可以不在线，恢复后仍可消费。

### 9.4 Signal 优先级

```text
Host Emergency Stop / Cancel
    > Pause
    > Approval / External Interaction Completion / Recovery Decision
    > User Input（匹配 WaitRequest）
    > Interject
    > Unpause / ordinary wake-up
```

优先级只解决同一推进点的消费次序，不绕过状态机合法性。

### 9.5 长 Activity 的 Cancel

1. CancelSignal 先写 durable inbox；
2. Runtime Host / Coordinator 通知当前 Activity 的 AbortController；
3. Adapter 应协作式停止并返回取消结果；
4. 若 Adapter 无法确认副作用是否发生，Activity 进入 `OUTCOME_UNKNOWN`；
5. 若 Cancel 落在 ActionBatch 中间，按 §8.6 不变量 7 处理，并为未启动 Action 合成 result；
6. Coordinator 重新持锁，消费 Cancel 并提交 Run 状态；
7. 迟到成功结果不得把 CANCELLED Run 恢复为 RUNNING，但必须作为诊断事实保存。

### 9.6 Pause 与 Unpause

- PauseSignal 表示在下一个安全点停止调度新 Activity，默认不等同于 Cancel；
- 是否中断当前 Activity 由 Activity 的 pause/cancellation descriptor 决定；
- **ActionBatch 进行中时，Pause 的安全点是批结算之后**，不得让批停在半途（否则配对不变量需要在 PAUSED 状态下长期挂账）；
- 只有当前 Activity Outcome 已安全持久化，或已经明确进入可恢复状态后，Run 才转为 PAUSED；
- UnpauseSignal 只唤醒 PAUSED Run，不绕过 Capability、环境和 Budget 重新校验；
- Host Shutdown 可以请求安全 Pause；无法及时安全暂停时保存 Activity 状态，由下次 Crash Recover 协议接管。

### 9.7 执行期间的用户输入：WaitRequest、Interject 与新 Run【新增·P0-4】

#### 问题

V02 同时成立两条规则：一个 Session 只允许一个 Foreground Active Run；没有匹配 `targetRequestId` 的用户消息创建新 follow-up Run。当 Run 处于 `RUNNING` / `WAITING_FOR_APPROVAL` / `WAITING_FOR_INTERACTION` 时，用户消息既不能进入当前 Run，也不能开新 Run——**现实中最高频的一句交互「等等，别写那个目录」在架构里无处安放**。

#### WaitRequest

```ts
interface WaitRequest {
  id: WaitRequestId;
  runId: RunId;
  prompt: string;
  inputSchema?: JsonSchema;
  mode: "SINGLE" | "ACCUMULATE_UNTIL_SUBMIT";
  expiresAt?: Timestamp;
  status: "OPEN" | "FULFILLED" | "EXPIRED" | "CANCELLED";
}
```

- `SINGLE`：第一个合法输入完成请求；
- `ACCUMULATE_UNTIL_SUBMIT`：Layer 2 聚合多条草稿，提交时形成一个 Signal；
- v0.1 默认 `SINGLE`。

#### InterjectSignal

```ts
interface InterjectSignal {
  type: "INTERJECT";
  content: string;
  intent: "ADD_CONTEXT" | "CONSTRAIN" | "REDIRECT";
  urgency: "NEXT_FRAME" | "NEXT_SAFE_POINT";
}
```

语义【定】：

1. 插话写入 Run Working Context，成为 `USER_MESSAGE` ContextItem（`trust = USER_PROVIDED`），在下一次 ContextFrame 编译时生效；
2. 插话**不改变 RunStatus**，不解除任何等待，不满足任何 WaitRequest；
3. `urgency = NEXT_SAFE_POINT` 时，Coordinator 在当前 Activity 完成后、下一次 `PrepareActionBatchDirective` 之前，插入一次 ModelInvocation 让模型重新决策；
4. 插话必须在 Transcript 中可见（`InterjectionEntry`），且与"启动新 Run 的消息"视觉可区分；
5. 插话不得创建 Grant、改变 Policy、批准 Action——它只是上下文，不是授权通道；
6. 插话计入 Budget（它触发额外模型调用）。

【议】D-02：`intent = REDIRECT` 且当前存在 PENDING Approval 时，是否自动撤回该 Approval 并让模型重新决策。收益是符合直觉（用户说"别这么干"时不应还等着他批准），代价是 Approval 的生命周期多出一条由内容语义驱动的路径，而 `intent` 来自用户选择而非可信解析。

#### Layer 2 路由表【定】

| 当前 Run 状态 | 消息带匹配的 targetRequestId | 不带或不匹配 |
|---|---|---|
| `RUNNING` | — | `InterjectSignal` |
| `WAITING_FOR_USER` | `UserInputSignal`（恢复原 Run） | `InterjectSignal` |
| `WAITING_FOR_APPROVAL` | `ApprovalDecisionSignal` | `InterjectSignal` |
| `WAITING_FOR_INTERACTION` | `ExternalInteractionCompletedSignal` | `InterjectSignal` |
| `RECOVERY_REQUIRED` | `RecoveryDecisionSignal` | `InterjectSignal` |
| `PAUSED` | — | 入队，Unpause 时作为 Interject 消费 |
| Terminal | — | 创建新 follow-up Run |

这张表是 Layer 2 的产品语义，Layer 3 只保证：**没有匹配 WaitRequest 的输入不得静默改变 Run 的等待状态**。

## 10. Run 领域模型与状态机

### 10.1 RunStatus 与 RunOutcome

```ts
type RunStatus =
  | "CREATED"
  | "RUNNING"
  | "WAITING_FOR_USER"
  | "WAITING_FOR_APPROVAL"
  | "WAITING_FOR_INTERACTION"
  | "RECOVERY_REQUIRED"
  | "PAUSED"
  | "COMPLETED"
  | "FAILED"
  | "CANCELLED";
```

【定】终态性明确（V02 未说明，与 §10.3 不变量 5 冲突）：

- **非终态**：`CREATED` / `RUNNING` / `WAITING_FOR_*` / `RECOVERY_REQUIRED` / `PAUSED`；
- **终态**：`COMPLETED` / `FAILED` / `CANCELLED`；
- `RECOVERY_REQUIRED` 是**非终态**：它等待 `RecoveryDecisionSignal`，决策后可回到 `RUNNING` 或走向任一终态；
- `RECOVERY_REQUIRED` 期间不得启动新 Activity（等价于 §10.3 不变量 5 的约束效果），但 Run 本身未结束；
- `RECOVERY_REQUIRED` 有过期定时器；过期后自动转为带 `recoveryItems` 的 `FAILED` 或 `CANCELLED`【验】。

```ts
interface RunOutcome {
  kind:
    | "SUCCESS"
    | "COMPLETED_WITH_LIMITS"
    | "USER_REJECTED"
    | "BUDGET_EXHAUSTED"
    | "CONTEXT_EXHAUSTED"
    | "CANCELLED"
    | "FAILED";
  summary?: string;
  acceptanceResult?: AcceptanceResult;
  deliveredArtifactIds: ArtifactId[];
  incompleteItems: IncompleteItem[];
  recoveryItems: RecoveryItem[];
  error?: RuntimeErrorRecord;
}

interface IncompleteItem {
  code: string;
  description: string;
  relatedActionIds?: ActionId[];
  relatedArtifactIds?: ArtifactId[];
}

interface RecoveryItem {
  code: string;
  description: string;
  sideEffectState: SideEffectState;
  suggestedAction: "VERIFY_MANUALLY" | "COMPENSATE" | "ACCEPT_AS_IS" | "RETRY_LATER";
  relatedActionId?: ActionId;
  relatedResourceRefs?: ResourceRef[];
}
```

V02 的 `incompleteItems: string[]` 与未定义的 `RecoveryItem` 在本版补齐为结构化类型——它们是 Eval Grader 与 Layer 2 恢复 UI 的直接输入，自由文本不可用。

新增 `CONTEXT_EXHAUSTED`：上下文窗口耗尽与预算耗尽是两种不同的失败，处置路径也不同（§16.4）。

【定】RunStatus 表示生命周期状态，RunOutcome 表示结束质量与原因；不得为了表达业务结果无限扩展 RunStatus。

### 10.2 RunSnapshot

```ts
interface RunSnapshot {
  runId: RunId;
  runSpecId: RunSpecId;

  status: RunStatus;
```

相对 V02 的修正：

- **删除 `currentPhase: RunPhase`**。V02 同时存在 `status` 与 `currentPhase` 两个状态维度，而 `RunPhase` 全文从未定义。两个状态维度必然产生同步 bug，且既然从未被定义就说明并非必要。当前阶段信息由 `currentDirectiveId` 指向的 Directive 类型表达；
- `currentActivityId` → `currentActivityIds`（批内可能多个在途 Activity）；
- `openWaitRequestId` → `openRequestRef`（V02 只有 WaitRequest 的句柄，Approval 与 Interaction 的等待没有落在快照里）；
- 新增 `completionAttempts`，支撑 §10.4 的完成重试上限。

### 10.3 Run 不变量【定】

1. 一个 Run 绑定一个不可变 RunSpec；
2. 配置变化需要创建新 Run；
3. 每个外部副作用关联 Action、Attempt 和 Activity；
4. 同一 Run 的 durable transition 同时只允许一个 Coordinator 提交；
5. Terminal Run 不得继续产生新 Activity；`RECOVERY_REQUIRED` / `PAUSED` / `WAITING_*` 期间同样不得启动新 Activity；
6. 所有状态迁移产生有版本、单调 sequence 的 Durable Event；
7. Activity 结果必须匹配当前 generation；
8. 每次 ModelInvocation 前必须形成通过协议校验的 ContextFrame；
9. **上一个 ActionBatch 未结算前不得发起新的 ModelInvocation**；
10. **批内每个 Tool Call 必须有且只有一个 result**；
11. 每次 Action 执行前必须具有 ResolvedEffect、Capability Evidence 和实时 Lease；
12. 未知副作用状态不得自动重试；
13. Budget hard limit、Cancel 和 revoked Capability 不得由模型决定忽略；
14. 等待状态必须关联可寻址、可过期的 Request 对象；
15. **Run 进入 `COMPLETED` 前必须有一次 Acceptance 评估结果**（§10.4）；
16. **未脱敏内容不得写入任何 durable 存储**（§22.2）。

### 10.4 Run 完成判定与交付验收【新增·P0-3】

#### 问题

V02 的 `CompleteRunDirective` 全文出现一次，**没有任何触发条件**。Agent Loop 最核心的「模型不再请求工具即完成」这条规则在一份以不变量为主题的文档里缺席；`RunOutcome.deliveredArtifactIds` 没有产生者；§15 的 Verification 全部是 Action 级 postcondition，上位基线 §8.2「Tool 返回执行成功不自动等于任务状态已经正确改变」在 Run 层没有对应机制。

这同时是 Eval 的支点：§24.5 要求评「任务最终是否完成」，但 Runtime 不产出可判定的完成断言。

#### 循环终止规则【定】

```text
ModelInvocation 完成
    ↓
响应中是否包含 Tool Call？
    ├── 是 → PrepareActionBatchDirective（§8.6）
    └── 否 → EvaluateAcceptanceDirective
                ↓
        评估 RunAcceptance
        ├── 全部满足                    → CompleteRunDirective(SUCCESS)
        ├── 存在未决 RecoveryItem        → RECOVERY_REQUIRED
        ├── 未满足，且 completionAttempts < maxCompletionAttempts
        │      → 把未满足项作为 SYSTEM_NOTICE 回灌 Context，继续循环
        │        （completionAttempts += 1）
        └── 未满足，且已达 maxCompletionAttempts
               → CompleteRunDirective(COMPLETED_WITH_LIMITS) + incompleteItems
```

`maxCompletionAttempts` 防止「你还没做完」的无限循环，属于 `RunBudgets`。

#### RunAcceptance

```ts
interface RunAcceptance {
  mode: "MODEL_DECLARED" | "DECLARATIVE" | "HYBRID";
  criteria: AcceptanceCriterion[];
  requireDeliverablesVerified: boolean;
}

type AcceptanceCriterion =
  | { kind: "ARTIFACT_PRESENT"; artifactKind: ArtifactKind; minCount: number }
  | { kind: "ARTIFACT_VERIFIED"; artifactKind: ArtifactKind }
  | { kind: "NO_OPEN_RECOVERY_ITEMS" }
  | { kind: "NO_FAILED_REQUIRED_VERIFICATION" }
  | { kind: "CUSTOM_CHECK"; checkerRef: VersionedRef<AcceptanceChecker> };

interface AcceptanceResult {
  mode: RunAcceptance["mode"];
  evaluatedAt: Timestamp;
  satisfied: AcceptanceCriterionResult[];
  unsatisfied: AcceptanceCriterionResult[];
  checkerVersions: string[];
}
```

三种模式：

- `MODEL_DECLARED`：模型不再调用工具即视为完成。最弱，但对纯问答类 Run 是正确的；
- `DECLARATIVE`：必须满足声明式 criteria。适用于 Case 01 这类有确定性产物的任务；
- `HYBRID`：模型声明完成后再评估 criteria，未满足则回灌一次。

【验】v0.1 默认：无 Workspace 的 Run 用 `MODEL_DECLARED`；有明确 Artifact 预期的 Run 用 `HYBRID`。

【议】D-03：`RunAcceptance` 从哪里来——RunSpec（由 Layer 2 从 AgentProfile + 用户意图生成）、Case Package（由 Case 声明）、还是模型在 Run 开始时自己提出并冻结。三者的可行性与"Case 无关"约束的兼容性差异很大。

#### 三层验证的关系【定】

| 层 | 问题 | 触发点 | 归属 |
|---|---|---|---|
| Action 级 Verification | 这一步的副作用是否达成 | Attempt 完成后 | §15 |
| Artifact 级 Verification | 这个产物本身是否完整合法 | ArtifactRegistered 之后 | §17 |
| Run 级 Acceptance | 整个任务是否完成 | 模型不再请求工具时 | 本节 |

Action 级 Verification 可以引用 Artifact Verification 的结果作为证据；Run 级 Acceptance 可以引用前两者的结果。三者不得互相替代——V02 只有第一层，是 Run 级判定缺失的根因。

### 10.5 Cancel 后事实处置【定】

- 已完成的 Action、Attempt、Event 和 Audit 不删除；
- 已登记 Artifact 保留 lineage，并根据验证结果保持 VERIFIED、标记 PARTIAL/INVALID 或 SUPERSEDED；
- 未完成的临时资源根据 Tool 的 cleanup/compensation policy 处理；
- 自动 Compensation 必须是新的显式 Action，不伪装成"撤销历史"；
- 如果取消时副作用未知，Run 进入 `RECOVERY_REQUIRED`，或以带 `recoveryItems` 的 CANCELLED 结束；
- 用户可见结果必须明确区分**已完成**、**未完成**和**状态未知**三部分。

```ts
  trust: ContextTrust;
  protocolRole: ContextProtocolRole;
  protocolGroupId?: string;
  content?: ModelContent;
  verbatimPayloadRef?: BlobRef;
  blobRef?: BlobRef;
  preview?: string;
  contentHash: string;
  estimatedTokens: number;
  actualTokens?: number;
  redactionApplied: boolean;
  createdAt: Timestamp;
}
```

相对 V02 的修正：

- 新增 `MODEL_REASONING` 与 `USER_INTERJECTION` 两个 Kind；
- `trust` 补 `MODEL_GENERATED`——V02 的三值枚举无法表达模型自产内容，而 Assistant Message 与 Tool Call 既非系统可信、非用户提供、也非外部不可信；
- `pairGroupId` 泛化为 `protocolGroupId` + `protocolRole`（§11.5）；
- 新增 `verbatimPayloadRef`，保存必须原样回传的原始块；
- 新增 `redactionApplied`，使"是否已脱敏"可断言（§22.2）。

`source` 至少包含 sourceRunId、sourceEventId，并在适用时包含 messageId、batchId、actionId、attemptId、activityId、toolCallId、resourceRef。

### 11.3 ContextFrame

```ts
interface ContextFrame {
  id: ContextFrameId;
  runId: RunId;
  invocationId: ModelInvocationId;
  compilerVersion: string;
  policyVersion: string;
  protocolValidatorVersion: string;
  itemIds: ContextItemId[];

```

`trustSummary` 补齐了 V02 的缺口：§14.1 要求 Policy 消费"Context source/trust 摘要"，但从未定义如何从 item 级 trust 汇总到 frame 级。

`irreducibleTokens` = 所有 `REQUIRED_VERBATIM` 与不可移除项的 token 之和，是判断"还能不能压缩"的依据（§11.6）。

【定】每次 ModelInvocation 都保存 ContextFrame 或可重建引用，用于 Eval 判断遗漏、污染和 Compact 影响。

### 11.4 ToolResult Materialization

```text
Raw ToolResult（仅存在于 Adapter 进程内存）
    ↓ RedactionPort.redact()          ← 强制，§22.2
    ↓ schema validate
    ↓ normalize and hash
    ↓ ModelProtocolPort.countTokens()
    ├── small result → inline ContextItem
    └── large result → immutable Blob + preview + retrieval reference
                         ↓
                  read_blob_slice / domain retrieval tool
```

规则【定】：

1. **脱敏在进入本流程之前已经完成**（§22.2）。本流程不再是安全边界，只做预算与表示裁剪；
2. 大结果阈值属于 ContextPolicy，可按字符、字节和 Provider token 共同判断【验】；
3. 外置后保留结果类型、摘要、hash、大小、来源、取回方式和截断说明；
4. 取回工具必须分页、有硬上限，并继续接受 Context Budget；
5. Artifact 与 Runtime Blob 区分：Blob 是执行内部载体，Artifact 是具有交付和 lineage 语义的产物；
6. 具体阈值（如 20K token）通过 Eval 决定，不写死为跨 Provider 常量。

### 11.5 Provider 协议要素不变量【修正·P0-2】

#### 问题

V02 §11.5 把「绝不拆 tool_call/tool_result 对」提升为不变量，方向正确但**覆盖面不足**。同一失效类里至少还有：Provider 要求原样回传的推理块（回传时可能带签名校验）、缓存断点的放置约束、部分 Provider 对首块/系统块的位置约束。V02 的 `ContextItemKind` 甚至没有推理块的类目，而 `ModelUsage` 里已经有 `reasoningTokens`——说明设计知道这类 token 存在，却没意识到它是 Context 的一等公民。

Compact 一旦把推理块当普通 assistant 文本摘要掉，会与丢弃 tool_result 触发同一类协议错误。

#### 不变量【定】

1. 属于同一 `protocolGroupId` 的 ContextItem 构成**不可拆分单元**：一起保留、一起摘要为合法替代块、或一起移除；
2. `protocolRole = REQUIRED_VERBATIM` 的项**不得被改写、摘要、截断或重排**，只能整组保留或整组移除；其内容从 `verbatimPayloadRef` 原样取出；
3. 一个模型 Tool Call 与其 result 属于同一 protocolGroup；批内每个 call 必须有恰好一个 result（§8.6 不变量 2）；
4. Pair 过大时，外置 result 正文，但必须保留协议合法的结构化 result stub；
5. **哪些结构属于 `REQUIRED_VERBATIM` 由 `ModelProtocolPort` 声明，不由 Context 模块猜测**；
6. ContextFrame 构建后必须执行 `ModelProtocolPort.validateFrame()`，失败不得发起模型调用，并作为 `source: MODEL_PROVIDER, category: PROTOCOL` 的错误处理。

【验】已知需要 `REQUIRED_VERBATIM` 的候选：Anthropic 扩展思考在带工具使用时的推理块及其签名。**具体规则以 Spike 0 实测为准**（§28.1），在结论出来前不得在代码中固化任何一种具体形态。

### 11.6 Compact 的决策归属与触发【修正·P0-5】

#### 问题

V02 同时存在两套机制：§8.3 有 `CompactContextDirective`（Kernel 决策），§11.6 又说"达到 soft limit 后在下一次 ModelInvocation 前**静默** Compact"（Context Runtime 自决）。冻结 Directive 前必须定分工。

#### 分工【定】

| 情形 | 归属 | 理由 |
|---|---|---|
| 大 ToolResult Offload | Context Runtime 自治 | 只改变同一事实的表示，不改变可决策信息 |
| soft limit 下的常规 Compact | Context Runtime 自治 | 同上；且需要在编译帧时立即完成，走 Kernel 会多一个往返 |
| Compact 后仍超限 | **Kernel 决策** | 此时必须在"更激进压缩 / 请求用户缩小范围 / 产生 handoff / 失败"之间取舍，是决策而非编译 |

因此 `CONTEXT_FRAME_COMPILATION` Activity 的 Outcome 必须把 token 会计回传 Kernel：

```ts
interface ContextFrameOutcome {
  status: "READY" | "COMPACTED_READY" | "COMPACTION_INSUFFICIENT" | "PROTOCOL_INVALID";
  frameId?: ContextFrameId;
  totalTokens: number;
  irreducibleTokens: number;
  compactionApplied: CompactionRecord[];
  protocolError?: RuntimeErrorRecord;
}
```

只有 `COMPACTION_INSUFFICIENT` 才产生 `CompactContextDirective` 或后续处置。这解决了 V02 中"Kernel 若要决策 Compact，就必须持有 token 会计，但没有任何 Outcome 回传它"的悬空问题。

#### ContextBudgetPolicy

```ts
interface ContextBudgetPolicy {
  modelWindowTokens: number;
  reservedOutputTokens: number;
  softInputLimitTokens: number;
  hardInputLimitTokens: number;
  compactTargetTokens: number;
  inlineToolResultLimitTokens: number;
  retrievalPageLimitTokens: number;
}
```

触发策略【定】：

1. 优先 Offload 大 Tool Result；
2. 达到 soft limit 后，在下一次 ModelInvocation 前由 Context Runtime 自治 Compact；
3. Compact 目标低于 soft limit，形成滞回区间，避免每步反复压缩；
4. 达到 hard limit 且 `irreducibleTokens` 已超出可用窗口时，返回 `COMPACTION_INSUFFICIENT`，由 Kernel 决策；
5. Compact 结果是带 source refs、compiler/model version 和 hash 的派生对象；
6. 原始 durable facts 不被 Compact 删除；
7. Compact 必须保留：当前目标、用户约束与插话、未完成 Action、Approval/Wait 状态、关键 Artifact、错误恢复状态、以及全部 `REQUIRED_VERBATIM` 组。

【验】所有阈值默认值需由 Eval 确定，不得凭直觉写死。

【议】D-05：`COMPACTION_INSUFFICIENT` 时 Kernel 的默认动作（更激进压缩 / 请求用户缩小范围 / 直接 DETERMINISTIC handoff）。

### 11.7 Skill 渐进披露

```ts
interface SkillSnapshot {
  skillId: SkillId;
  version: string;
  contentHash: string;
  name: string;
  description: string;
  activation: "EAGER" | "ON_DEMAND";
  instructionBlobRef: BlobRef;
  resourceRefs: ResourceRef[];
}
```

- 初始 Context 默认只注入可用 Skill 的 name/description；
- EAGER Skill 或被选择的 ON_DEMAND Skill 才加载完整 instructions；
- 加载动作形成 ContextItem 和 Trace；
- v0.1 可以只实现 EAGER，但 Contract 不等同于全量注入；
- 【验】渐进披露是否提升效果通过 Eval 比较。

### 11.8 Prompt Cache 与 Compact 的张力【新增·P2-1】

`ModelUsage.cachedInputTokens` 的存在说明设计已知有缓存，但 §11.6 的 Compact 会破坏稳定前缀，两者存在结构性张力：

- Compact 越激进，缓存命中越低，延迟越高；
- 稳定前缀要求「只在尾部追加」，而 Compact 恰恰重写中部。

本项目不以省 token 为目标（上位基线 §4.1），但缓存命中影响**延迟**与 **Eval 轨迹可比性**（同一 Case 两次运行的缓存状态不同，耗时不可比）。

【验】处置方向：把 `CACHE_BREAKPOINT` 作为 ContextProtocolRole 的一种，Compact 时优先在断点之后动刀，保持断点之前的前缀稳定；具体断点放置规则以 Spike 0 结论为准。当前只登记这一约束，不做实现承诺。

## 12. Tool、Action 与 Effect

### 12.1 生命周期

```text
ModelInvocationResult
    ↓ 识别全部 Tool Call → ActionBatch（§8.6）
    ↓ 逐条 normalize / schema validate
ProposedAction（stage = PROPOSED，落库）

PreparedAction（stage = PREPARED）

Verification
    ↓
Succeeded / Retry / Model Recover / Wait / Recovery / Fail
    ↓

```

### 12.2 Action 的持久化阶段【修正·P2-5】

【定】`actions` 表以 `stage` 字段表达生命周期，**所有** ProposedAction 落库，包括被拒绝的：

### 12.3 ToolDefinition


### 12.7 dry-run / preview

- 支持 preview 的 Tool 在 APPLY 前可以生成确定性 Plan、Diff、目标列表或外发摘要；

- 若目标环境变化导致 actionDigest 改变，必须重新 preview / policy / approval；
- 不支持 preview 的 Tool 必须显式声明，而不是默认假装支持。

### 12.8 Capability 并发与 Lease


【定】

【定】「重试、模型自纠、等待用户、终止」是**处置结果**，不足以表达错误事实。Runtime 使用多维记录：

```ts
    | "AUTHORIZATION"

```

```ts
type Retryability =
  | "NEVER"
  | "SAME_INPUT_IMMEDIATE"

  | "AFTER_MODEL_CORRECTION"
  | "AFTER_USER_ACTION"
  | "AFTER_ENVIRONMENT_CHANGE";

  | "NOT_STARTED"
  | "NO_EFFECT"
  | "APPLIED"
  | "PARTIALLY_APPLIED"
  | "UNKNOWN";
```

本版新增：`source: ACCEPTANCE / CONTEXT`（Run 级验收失败与上下文编译失败需要可区分）；`category: REDACTION`（脱敏失败，§22.2）、`CAPACITY`（磁盘/存储水位，§22.5）。

### 13.2 ErrorDisposition

```ts
type ErrorDisposition =
  | "RETRY_AUTOMATICALLY"
  | "RETURN_TO_MODEL"
  | "SKIP_REMAINING_BATCH"
  | "WAIT_FOR_USER"
  | "WAIT_FOR_RECOVERY"
  | "DEGRADE"
  | "FAIL_RUN"
  | "CANCEL_RUN";
```

【定】Disposition 由 Tool Contract、ErrorRecord、Attempt 历史、Batch Settlement Policy、Budget 和 Idempotency 共同计算，不能由 Handler 单方面指定。

新增 `SKIP_REMAINING_BATCH`，对应 §8.6 的批结算策略。

### 13.3 自动重试规则【定】

只有同时满足以下条件才可自动重试：

1. retryPolicy 允许；
2. retryability 允许当前方式；
3. 未超过 attempt、wall-clock 和 budget 限制；
4. sideEffectState 为 `NOT_STARTED` / `NO_EFFECT`，或幂等键与外部查询证明安全；
5. Capability 和 preconditions 仍然有效；
6. Cancel/Pause 未待处理。

`UNKNOWN`、`PARTIALLY_APPLIED` 默认进入 Observation、Recovery 或人工处理，**不可仅因错误看起来 transient 就重试**。

### 13.4 返回模型的错误

模型可纠正的输入错误以结构化、脱敏 Tool Result 返回，包含：稳定错误 code；哪些字段不合法；允许的修正方向；已执行副作用状态；是否允许再次调用。

【定】内部堆栈、凭证、绝对敏感路径和 Provider 私密响应不得进入模型。

## 14. Policy 与 Approval


v0.1 默认 `TRUSTED_PERSONAL`，但【定】该 preset 不是 Kernel 中的硬编码假设。

### 14.1 Policy 输入

```ts
  status: "PENDING" | "APPROVED" | "REJECTED" | "EXPIRED" | "CANCELLED";
  expiresAt?: Timestamp;
  createdAt: Timestamp;
  decidedAt?: Timestamp;
}
```

`scope` 与 `digest` 是本版新增，用于表达批级审批（§8.6 不变量 5）：`scope = ACTION` 时 `digest` 是 `actionDigest`，`scope = BATCH` 时是 `batchDigest`。

### 14.3 Approval 生命周期【定】

- Runtime 创建 ApprovalRequested durable event；
- Layer 2 投影为产品 Approval 并展示 UI（权威执行状态在 Layer 3，见 §23）；
- 用户决策以持久化 Signal 回到 Runtime；
- Runtime 校验 approvalId、digest、状态和有效期；
- 过期由 `TimerPort` 注册的 durable timer 触发，恢复扫描作为兜底（§18.6）；
- Run 已 crash 时 Decision 保留在 Signal Inbox，恢复后处理；
- Run 已 terminal、Action 已变化或 Approval 已决定时，后续 Decision 幂等拒绝；
- Approval 不会覆盖实时撤权或已变化的 target fingerprint；
- 【议】D-02：`InterjectSignal(intent=REDIRECT)` 是否可撤回 PENDING Approval。

## 15. Observation 与 Verification

### 15.1 所有权【定】

- Kernel 决定何时需要 Observation 与 Verification（`ObserveDirective` / `VerifyActionDirective`）；
- Verification Runtime 根据 Descriptor 选择注册的 Verifier；
- Verifier 通过受限 Port 读取环境或调用只读 Tool；
- Case Package 提供业务 verifier，但 Runtime Core 拥有执行、超时、Trace 和处置语义；
- Tool Handler 的 "success" 不能替代独立 Verification。

V02 中 `OBSERVATION` 是一等 ActivityKind、有 `observations` 表、有 `ObservationCompleted` 事件，却没有对应 Directive——本版补 `ObserveDirective`。

### 15.2 VerificationDescriptor

```ts
interface VerificationDescriptor {
  mode: "NONE" | "INLINE_RESULT" | "REOBSERVE" | "CUSTOM_VERIFIER";
  verifierRef?: VersionedRef<Verifier>;
  requiredForSuccess: boolean;
  observationCost: "LOW" | "MEDIUM" | "HIGH";
  timeoutMs?: number;
  staleAfterMs?: number;
  retryPolicy?: RetryPolicy;
}
```

### 15.3 何时重新观察【定】

- 高影响副作用、外部状态写入、Artifact 交付原则上重新观察；
- 纯函数或带可验证返回对象的低风险 Tool 可以使用 inline result；
- Observation 成本高时，Tool Contract 可以指定采样、关键检查或延迟验证；
- Recover 后只要 observation 已超过 `staleAfterMs`、precondition 变化或 Grant 变化，就必须重新观察（由 `TimerPort` 的 `OBSERVATION_STALE` 定时器与恢复扫描共同保证）；
- Verification 失败不自动等于 Tool 可重试，先判断副作用状态和补救路径。

### 15.4 三层验证的边界【定】

见 §10.4「三层验证的关系」。要点重申：

- Action 级 Verification 回答「这一步的副作用是否达成」；
- Artifact 级 Verification 回答「这个产物本身是否完整合法」，在 `ArtifactRegistered` 之后由 Verification Runtime 触发；
- Run 级 Acceptance 回答「整个任务是否完成」；
- 三者不得互相替代。Artifact 未通过验证时，引用它的 Action 级 Verification 应视为失败；Run 级 Acceptance 的 `ARTIFACT_VERIFIED` criterion 直接消费 Artifact 验证结果。

## 16. Budget、进展与优雅停止

### 16.1 RunBudgets

```ts
interface RunBudgets {
  maxDecisionSteps: number;
  maxActiveWallClockMs: number;
  maxTotalWallClockMs?: number;
  maxModelCalls?: number;
  maxToolCalls?: number;
  maxInputTokens?: number;
  maxOutputTokens?: number;
  maxEstimatedCost?: Money;
  maxConsecutiveFailures: number;
  maxCompletionAttempts: number;
  softLimitRatio: number;
  handoffReserve?: HandoffReserve;
}
```

**墙钟拆分【定·修正】**：V02 的单个 `maxWallClockMs` 未区分执行时间与等待时间——一个 Run 等待审批过夜，第二天恢复即刻爆预算。本版：

- `maxActiveWallClockMs`：只累计 `RUNNING` 且有在途 Activity 的时间。`WAITING_*` / `PAUSED` / `RECOVERY_REQUIRED` 期间**不累计**；
- `maxTotalWallClockMs`：含等待的兜底上限，默认很大或不设，用于防止 Run 无限期挂账。

`maxCompletionAttempts` 见 §10.4。

【定】BudgetUsage 由 durable facts 计算，`ModelInvocationCompleted` 必须记录 usage；Provider 没有返回精确 usage 时标记为 estimated，**不得伪装为零**。

【验】所有默认值需要由 Micro Case 与 Eval 确定。

### 16.2 Progress Guard

至少检查：

- 决策步数与连续失败；
- 相同 Tool + normalized input + effect digest 连续重复；
- 多个不同调用但 Observation/Artifact/任务状态没有变化；
- 相同错误和相同模型修正循环；
- Context Compact 后仍无法满足模型窗口；
- **长时间没有 durable progress 证据**。

【定·修正】最后一条在 V02 中是无法工作的：Download Progress 被明确归为 **transient**，因此 Case 01 的长媒体下载会被误判为无进展。本版规定：

```ts
interface ProgressReportingDescriptor {
  mode: "NONE" | "HEARTBEAT" | "MONOTONIC_PROGRESS";
  intervalMs?: number;
}
```

- 声明 `HEARTBEAT` / `MONOTONIC_PROGRESS` 的长时 Tool **必须**周期性产出 `ActivityProgressCheckpoint` durable event；
- 该事件载荷极小（activityId、progressToken、可选单调计数），低频（默认 30s 量级），不构成事件表膨胀；
- Progress Guard 基于 durable heartbeat 与 `RuntimeActivity.lastHeartbeatAt`，**不基于 transient event**；
- 声明 `NONE` 的 Tool 必须有较短的 `timeoutPolicy`，否则不允许注册。

【定】相同调用 hash 只是一个信号，不单独作为所有场景的循环定义。

### 16.3 Soft 与 Hard Limit【定】

- Soft limit：阻止启动普通新步骤，可使用预留预算生成简短 handoff、请求用户缩小范围或交付部分结果；
- Hard limit：不得再调用模型或有副作用 Tool，立即形成稳定 Outcome；
- 如果没有 handoff reserve，不得为"优雅总结"突破 hard limit；
- Budget exhausted 不总是 FAILED：已产生可用、明确标注的部分交付时可以 `COMPLETED_WITH_LIMITS`；
- RunStatus 保持有限枚举，完成质量通过 RunOutcome 表达。

### 16.4 两类 Handoff【新增·P0-5】

#### 问题

V02 §11.6 规则 4 说 hard context limit 且无法安全 Compact 时可"产生 handoff"，但 `ProduceHandoffDirective` 需要一次模型调用——而这正是不能调模型的状态。§16.3 的 `handoffReserve` 解决的是 **Budget 耗尽**，预留 token 在**上下文窗口塞不下**时毫无用处。这两种耗尽必须分开。

#### 模型【定】

```ts
type HandoffKind = "MODEL_AUTHORED" | "DETERMINISTIC";
```

| 类型 | 触发场景 | 生成方式 | 前提 |
|---|---|---|---|
| `MODEL_AUTHORED` | Budget soft limit | 使用 `handoffReserve` 发起一次受限模型调用 | 上下文窗口仍可用 |
| `DETERMINISTIC` | Context hard limit、模型不可用、Provider 持续失败 | 由模板从 durable facts 生成，**不经模型** | 无 |

`DETERMINISTIC` handoff 的内容来源全部是事实表：已完成 Action 列表、已注册 Artifact 及其验证状态、未满足的 Acceptance criteria、`incompleteItems`、`recoveryItems`、错误摘要。它不需要理解任务语义，只需要如实报告状态。

对应的 RunOutcome：Budget 耗尽 → `BUDGET_EXHAUSTED`；上下文耗尽 → `CONTEXT_EXHAUSTED`。

### 16.5 计数口径【定·修正】

V02 的 `decisionStep` 与 `consecutiveFailures` 都没有定义，直接影响 Eval 跨实验可比性。本版明确：

**decisionStep**：一个 decisionStep = **一次成功完成的 ModelInvocation**，无论其后产生 0 个还是 N 个 Action。

- ContextFrame 编译、Compact、Observation、Verification、Acceptance 评估**不计入** decisionStep；
- 上述活动各有独立的次数上限，防止在单个 decisionStep 内无限循环；
- 失败后重试的 ModelInvocation 计入（否则重试循环不受 maxDecisionSteps 约束）。

**consecutiveFailures**：连续失败计数，归零条件为——**任一 Action 执行成功且其 required Verification 通过**。

- Context 编译失败、Compact 失败不计入（它们有独立计数）；
- 模型协议错误计入；
- 被 Policy/用户拒绝的 Action 不计入失败（那是正常的控制流，不是故障）。

## 18. Durable Execution、Recover 与 Replay

### 18.1 混合持久化【定】

```text
事实表 + Durable Event + Snapshot + immutable Blob
```

- 事实表服务当前状态和约束查询；
- Durable Event 保存执行事实、审计、Trace 和因果关系；
- Snapshot 加速恢复，不是独立真相；
- Blob 保存大输入输出、Context Source、Preview 和诊断数据（**全部已脱敏**，§22.2）；
- 不追求纯 Event Sourcing，但关键状态必须能由事实和事件校验。

### 18.2 Crash 窗口

恢复至少区分：

1. Directive 尚未持久化；
2. Directive 已持久化但 Activity 未 claim；
3. Activity 已 STARTED，外部调用尚未发生；
4. 外部调用可能发生但 Outcome 未知；
5. Activity Outcome 已持久化但 Kernel 尚未消费；
6. ToolResult 已保存但 ContextItem 尚未物化；
7. **ActionBatch 部分 Action 已结算，批未 SETTLED**；
8. Verification 已完成但 Run 状态尚未推进；
9. Acceptance 已评估但 Run 未进入终态；
10. Signal 已进入 Inbox 但尚未消费；
11. State Snapshot 落后于 Durable Event；
12. Blob 已写入但事实表引用未提交（孤儿 Blob，交由 §22.5 回收）。

【定】每个恢复分支必须通过 idempotency、provider request ID、外部查询、Observation、precondition/postcondition、Compensation 或人工恢复决定，**不能无条件重试**。

第 7 条是本版新增：批未结算时恢复，必须为已结算 Action 保留事实、为未启动 Action 合成 `SKIPPED` result，并让整批达成结算状态后才允许继续——否则会出现"部分 call 没有 result"的协议非法状态。

### 18.3 外部世界重新校验【定】

Recover 不只判断"副作用是否发生"，还必须检查：

- Capability Binding 是否撤销或降级；
- Grant、Secret、Browser Session 或 Lease 是否过期；
- 输入 Resource contentHash 是否变化；
- Action target fingerprint 是否变化；
- Artifact 或外部对象是否被用户修改；
- Verification 结果是否已过 `staleAfterMs`。

处理路径：

```text
unchanged                      → continue
changed but safely resolvable  → re-resolve / re-observe / re-prepare
effect or digest changed       → policy + approval again
requires user choice           → WAITING_FOR_USER / RECOVERY_REQUIRED
cannot establish safe state    → fail or cancel with recovery report
```

### 18.4 Recover、Rebuild、Replay 的区别【定】

#### Recover（原 Resume）

继续同一个非 Terminal Run；保留 RunId、RunSpec、已完成副作用和预算使用；不会再次执行已证明完成的 Activity。**与 `UnpauseSignal`（解除暂停）是不同的机制**，见 §8.2 命名表。

#### State Rebuild

从事实表、Durable Event 和最新有效 Snapshot 重建同一个 Run 的 KernelState，用于灾难恢复和一致性校验，不调用真实 Provider 或 Tool。

#### Replay

为调试或 Eval 创建隔离的重放执行：

- 使用 RecordedModelPort / RecordedToolHandlerPort；
- 默认不触发真实副作用；
- 可以从某个 ContextFrame 或 Event sequence 开始；
- 产生新的 replay execution identity，引用原 Run，但不改写原 Run；
- 明确区分 exact recorded replay、deterministic simulation 和 live rerun；
- live rerun 必须创建新 RunSpec/Run，并重新经过 Capability 和 Policy。

### 18.5 Snapshot 有效性

```ts
interface StoredRunSnapshot {
  runId: RunId;
  schemaVersion: number;
  stateVersion: number;
  coveredThroughEventSequence: number;
  kernelStateHash: string;
  kernelState: SerializedKernelState;
  createdAt: Timestamp;
}
```

【定】加载 Snapshot 后必须重放其后的事件；hash、sequence 或 schema 不兼容时回退到更早 Snapshot 或完整重建。

### 18.6 Durable Timer【新增·P1-4】

V02 只在 §14.3 提过一次"Clock 驱动的 durable timer"，没有 Port、没有表、没有装载协议。但 Approval expiry、WaitRequest expiry、Interaction expiry、Lease expiry、Activity timeout、wall-clock budget、observation staleAfter **全部依赖它**。

```ts
interface DurableTimer {
  id: TimerId;
  runId?: RunId;
  kind:
    | "APPROVAL_EXPIRY"
    | "WAIT_EXPIRY"
    | "INTERACTION_EXPIRY"
    | "RECOVERY_EXPIRY"
    | "LEASE_EXPIRY"
    | "ACTIVITY_TIMEOUT"
    | "ACTIVE_WALL_CLOCK"
    | "OBSERVATION_STALE";
  targetRef?: string;
  fireAt: Timestamp;
  status: "SCHEDULED" | "FIRED" | "CANCELLED";
  payload: JsonValue;
  createdAt: Timestamp;
}
```

【定】

1. Timer 与其触发原因在同一事务内提交（如 Approval 创建与其过期 timer）；
2. 进程启动时装载全部 `SCHEDULED` timer；已过期未触发的立即执行一次补偿扫描；
3. Timer 触发产生 durable event，再转为 Signal 或 KernelInput，**不直接修改状态**；
4. Timer 通过 `ClockPort` 获取时间；FakeClock 下由测试推进，**不执行真实 sleep**；
5. 恢复扫描是兜底而非主路径——只依赖扫描会让过期精度受轮询周期限制。

【议】D-08：v0.1 是否实现真定时器，还是先只做恢复扫描 + 惰性判定（读取时检查是否已过期）。惰性判定实现成本低得多，但"过期"这件事不会主动通知 UI。

## 20. Human Takeover / External Interaction

### 20.1 定位【定】

Human Takeover 不是绕过 Runtime 的隐藏操作，而是一个显式的**等待—人工操作—重新观察**协议。v0.1 主要用于动态页面、验证码、登录态失效和浏览器人工纠偏。

### 20.2 ExternalInteractionRequest

```ts
interface ExternalInteractionRequest {
  id: InteractionRequestId;
  runId: RunId;
  actionId?: ActionId;
  capabilityId: CapabilityId;
  resourceHandleRef: ResourceHandleRef;
  parkedLeaseId: LeaseId;
  interactionType: "BROWSER_TAKEOVER" | "TERMINAL_TAKEOVER" | "MANUAL_RECOVERY";
  instructions: string;
  expectedCompletion: string;
  expiresAt?: Timestamp;
  status: "OPEN" | "COMPLETED" | "EXPIRED" | "CANCELLED";
}
```

### 20.3 运行语义【定·修正】

```text
Runtime requests interaction
    ↓ persist request
    ↓ PARK the capability lease（不释放回池，绑定 interactionRequestId）
Run → WAITING_FOR_INTERACTION
    ↓ Layer 2/UI grants scoped human control
User operates external resource（进入 Product Audit）
    ↓ completion signal with requestId
Runtime UNPARKS the lease（原 owner 重获）
    ↓ re-observe + verify environment
continue / re-plan / ask user / fail
```

**V02 的竞态修正**：V02 写的是"release active automation lease"，但释放与重获之间另一个 Run 可以抢占 EXCLUSIVE lease，接管完成后原 Run 无法收回。本版改为 `PARKED` 状态（§12.8）：lease 不回池，其他 Activity 不可获取，同时 PARKED 有独立过期定时器——接管超时则释放 lease 并让 Run 进入恢复路径，避免 lease 永久挂账。

其余规则：

- 用户操作不伪装成 Tool Attempt，但必须有 Product Audit 记录；
- 人工接管期间自动 Browser Tool 不得并发操作同一 session（由 PARKED lease 保证）；
- 完成信号不等于任务成功，**必须重新 Observation**；
- 过期、资源关闭或目标状态不明进入明确恢复路径。

## 21. Skill、MCP、Plugin 与策略扩展

### 21.1 内部语义保持区分【定】

- **Capability**：授权对某类资源执行操作；
- **Tool**：模型可调用的具体操作；
- **Skill**：版本化 Context 贡献；
- **MCP**：Tool、Resource、Prompt 的 Provider 协议；
- **Plugin**：贡献 Skill、Tool、Provider、Adapter 或 UI Renderer 的安装与组装单元；
- **Adapter**：连接具体外部技术。

Layer 2 管理安装、发现、版本和 Workspace Binding；Layer 3 只接收冻结 Snapshot、标准 ToolDefinition 和注册的 Handler/Resolver/Verifier/AcceptanceChecker。

### 21.2 策略扩展边界【定】

当前不提供可以任意修改状态或跳过 Policy 的全局 Hook。稳定扩展点优先使用显式接口：

- ContextPolicy / ContextCompiler；
- LoopPolicy / ProgressDetector；
- EffectResolver；
- PolicyEvaluator；
- Verifier；
- AcceptanceChecker；
- RedactionProfile；
- ModelRouter（后续）；

## 22. 安全、脱敏与数据边界

### 22.1 Workspace Scope【定】

- 文件操作使用 ResourceRef；
- ResourceRef 验证 Workspace、Mount、规范化路径和 symlink；
- CapabilityGrant 不能扩大 Binding Scope；
- PreparedAction 的 ResolvedEffect 必须是 Grant Scope 的子集；
- Adapter 执行时再验证实际目标；
- Workspace 外写入必须由新的明确授权覆盖，不能由内容或模型声明扩大。

### 22.2 脱敏发生点【修正·P0-6】

#### 问题

V02 把脱敏放在 Context Materialization（§11.4），但 `RuntimeActivity.outcomeRef: BlobRef` 说明原始 outcome 在物化之前已经落盘，§18.2 的 crash window 第 6 条「ToolResult 已保存但 ContextItem 尚未物化」直接确认了这个顺序。同时 V02 §11.4 规则 1（"完整原始结果是否保存由数据策略决定"）与 §22.2（"进入模型**或长期存储**前脱敏"）自相矛盾。

上位基线 §9.3 与 §13.1 是**已拍板**项：「Cookie、Token 和浏览器凭证不进入模型上下文**与 Trace**」。Case 01 是登录态网页归档，这条路径上的 ToolResult 天然携带 Cookie 和 Token，脱敏点错位不是理论风险。

#### 规则【定】

```text
Tool Handler 原始输出（仅存在于 Adapter 进程内存）
    ↓ RedactionPort.redact(raw, profile)     ← 强制，不可跳过
    ↓
RedactedOutcome + RedactionReport
    ├── 持久化为 Activity outcomeRef Blob        ← 已脱敏
    ├── 进入 Context Materialization（§11.4）    ← 预算与表示裁剪
    ├── 进入 Trace / 诊断 Blob                   ← 已脱敏
    └── 进入 Event payload                       ← 已脱敏
```

1. **未脱敏原文不得离开 Adapter 边界**，不得写入任何 Blob、事实表或 Event；
2. `RedactionProfile` 来自 `CapabilityBinding.redactionProfileRef` 与 `ToolDefinition.redaction` 的合并——知道"哪些字段是凭证"的是配置了凭证的 Capability Binding，不是 Tool；
3. Tool **必须**声明 `redaction`；未声明者走默认最严格 profile，而非默认放行；
4. **脱敏失败 = Tool 失败**（`source: TOOL_HANDLER, category: REDACTION`），不得降级为"原样保存"；
5. `RedactionReport` 记录脱敏了多少字段与字节，进入 `RedactionApplied` durable event 便于诊断，**但不记录被脱敏的内容本身**；
6. `ContextItem.redactionApplied` 使"是否已脱敏"可断言，作为 §10.3 不变量 16 的检查点；
7. Context Materialization 保留二次过滤，但它是**预算边界，不是安全边界**。

【议】D-06：是否允许在任何情况下保留未脱敏原文（例如仅本机、加密、短 TTL 的调试模式）。可调试性与已拍板的安全约束在此直接冲突，需要明确表态，不能靠"数据策略决定"这种含混表述留白。

### 22.3 Secret 与敏感数据【定】

- 数据库、RunSpec、Context、Trace 只保存 SecretRef；
- Secret 明文仅在 Adapter 执行阶段短暂解析；
- Cookie、Token、浏览器存储不进入模型；
- 向外发送本地数据时，ResolvedEffect 明确记录 data movement、目的地和数据范围。

### 22.4 不可信内容【定】

- 网页、文件、邮件和 ToolResult 默认是 `EXTERNAL_UNTRUSTED`；
- ContextItem 保存来源和 trust 标记，ContextFrame 汇总为 `trustSummary`；
- 不可信内容中的文字不能创建 Grant、改变 Policy 或自动批准 Action；
- **用户插话同样不能创建 Grant 或批准 Action**（§9.7 语义 5）；
- 高影响副作用独立经过 Effect Resolution、Policy 和 Approval；
- Approval UI 展示真实目标、数据移动和 preview，不只展示模型解释；
- 不把"Policy 能可靠判断每个 Action 参数是否由某段网页导致"作为安全前提；
- 未来 Memory 写入视为需要独立治理的操作；身份、权限和安全声明不得仅因模型抽取而进入 trusted memory。

### 22.5 数据保留与回收【新增·P1-9】

V02 全文没有保留策略与 GC。个人桌面长期使用、长媒体下载、每个 Run 冻结 Context 快照——存储只增不减会很快成为真实问题，且 GC 必须与 §18 的恢复/重放可读性协调。

#### 分类【定】

| 类别 | 策略 | 理由 |
|---|---|---|
| Durable Event、事实表行 | **永不删除** | 恢复、审计、Replay 的真相基础 |
| Artifact lineage | **永不物理删除**，使用 Tombstone | §17 不变量 |
| Deliverable Artifact 内容 | 永久保留，除非用户显式删除 | 用户交付物 |
| 非交付 Runtime Blob（ToolResult 正文、中间 preview） | 超期可回收，**必须留 hash + size + 摘要 stub** | 体积主要来源；stub 保证 Trace 仍可解释 |
| 诊断 Blob（半截响应、错误详情） | 按 `maxAgeDays` 回收 | 时效性强 |
| Transcript 投影 | 可重建，可回收 | 由事件重放恢复 |
| 孤儿 Blob（§18.2 窗口 12） | 定期扫描回收 | 无引用 |

#### 规则【定】

1. 参与 Eval fixture 或 GoldenTrace 的 Run 与 Artifact 标记 `PINNED`，**不进 GC**；
2. Blob 回收后其 stub 必须保留 hash、size、mediaType、来源与"已回收"标记，使旧 Trace 可读而非报错；
3. Replay 依赖 recorded outcome，因此 Replay 目标 Run 必须 `PINNED` 或在 GC 前显式导出 fixture；
4. Runtime Host 监测 Workspace 存储水位；低于阈值时进入 `DEGRADED`，**拒绝启动新 Run** 并产生 SYSTEM_NOTICE，而不是在执行中途写盘失败；
5. 磁盘空间不足纳入故障注入集（§24.3）。

【议】D-10：默认保留窗口的具体数值，以及"默认激进回收 + 用户显式 PIN"还是"默认全保留 + 用户显式清理"。

### 22.6 本地前后端通信【定】

- 随机端口或受控 Socket；
- 会话级鉴权 Token；
- Origin 校验；
- 禁止外部网页调用本地 API；
- SSE/WS 重连游标；
- 人工接管通道绑定 InteractionRequest 和 ResourceHandle，不能成为通用后门。

## 23. 跨层聚合的所有权与一致性【新增·P1-1】

### 23.1 问题

V02 把 `artifacts`、`approvals`、`external_interactions` 三张表放在 Layer 2，但它们的状态迁移由 Layer 3 决定（如 §10.5 取消时把 Artifact 标 PARTIAL/INVALID）。同时 §25.3 只说"一个 Run transition、对应 Event、Activity Intent 和已消费 Signal **尽量**在同一 Layer 3 事务提交"——"尽量"不能出现在不变量里。

结果是三个跨层对象的权威状态归属不明，且没有一致性协议。

### 23.2 原则【定】

> **Layer 3 拥有执行事实，Layer 2 拥有产品聚合，通过 outbox 单向投影。**

| 对象 | Layer 3（权威执行状态） | Layer 2（权威产品状态） | 冲突裁决 |
|---|---|---|---|
| Approval | ApprovalRequested / Decided / Expired 事件 + 校验用 digest | `approvals` 表：UI 展示、历史、审计 | 执行语义以 Runtime 事件为准；Layer 2 滞后即重放事件 |
| Artifact | ArtifactRegistered / Verified / Superseded 事件 + producer 溯源 | `artifacts` 表：版本、lineage、交付标记、用户操作 | 注册与验证状态以 Runtime 事件为准；**用户手工标记（交付、删除、PIN）以 Layer 2 为准** |
| ExternalInteraction | InteractionRequested / Completed / Expired 事件 | `external_interactions` 表 | 同 Approval |

### 23.3 一致性协议【定】

1. **Layer 3 在同一事务内提交**：Run transition + Durable Event + Activity Intent + 已消费 Signal + 相关 Timer。这是不变量，不是"尽量"；
2. 跨层投影通过 `run_events.sequence` 游标拉取，幂等，至少一次语义；
3. Layer 2 聚合中的**执行语义字段是投影结果**，Layer 2 不得独立推进；
4. Layer 2 允许拥有的独立字段：用户可见标题、用户手工标记、归档状态、UI 排序、retention PIN；
5. Runtime 需要读取 Layer 2 状态时（如"Artifact 是否已被用户删除"），只能通过 Port，且只能作为 **precondition fingerprint**，不能作为状态机输入——否则 Layer 3 的可恢复性会依赖 Layer 2 的当前状态，破坏 Replay。

【议】D-04：Artifact 的用户手工操作（删除、重命名、标记交付）如何回流到 Runtime 的 precondition 校验，以及用户删除了一个正在被引用的 Artifact 时的处置。

## 25. 关键运行流程

### 25.1 新 Session Message 启动 Run

```text
persist UserMessage
    ↓
extend / freeze ConversationSourceSnapshot（分段内容寻址）
    ↓
resolve AgentSpec + WorkspaceExecutionSnapshot + RunAcceptance
    ↓
persist immutable RunSpec
    ↓
Runtime.start
    ↓
Kernel → RequestContextFrameDirective → RequestModelDirective
    ↓
RunEvent stream
    ↓
Layer 2 projects Transcript and final AssistantMessage
```

### 25.2 ActionBatch 执行

```text
ModelInvocation 完成
    ↓ ModelProtocolPort 识别全部 Tool Call
    ↓ 形成 ActionBatch（PLANNED）
    ↓ 逐条：normalize → schema validate → 落库 PROPOSED
    ↓ 逐条：resolve effect + preconditions → PREPARED
    ↓ 逐条：frozen grant check → live capability check → lease
    ↓ preview / policy / approval（PER_ACTION 或 BATCH_SINGLE）
    ↓ 逐条（或受限并发）：persist Attempt Intent → execute Activity
    ↓ 边界脱敏 → materialize ToolResult or ErrorRecord
    ↓ Observation / Verification
    ↓ 为每个 call 合成恰好一个 result
    ↓ ActionBatchSettled
    ↓ continue Kernel
```

### 25.3 WAITING_FOR_USER

```text
Kernel creates WaitRequest（+ WAIT_EXPIRY timer）
    ↓ persist event and Run state
    ↓ Layer 2 projects question
    ↓ User message with target requestId
    ↓ durable UserInputSignal
    ↓ Coordinator validates and consumes signal
    ↓ same Run resumes
```

没有 target requestId 的用户消息按 §9.7 路由表处理——**在非终态 Run 上成为 Interject，而不是静默丢弃或强行创建新 Run**。

### 25.4 Approval

```text
PreparedAction / ActionBatch + preview + digest
    ↓ ApprovalRequested（+ APPROVAL_EXPIRY timer）
    ↓ Run WAITING_FOR_APPROVAL
    ↓ user decision persisted as signal
    ↓ validate approval / target / digest / expiry / live capability
    ↓ execute / reject（合成 result）/ expire / re-prepare
```

### 25.5 Cancel

```text
persist CancelSignal
    ↓ abort current Activity
    ↓ 批内未启动 Action → SKIPPED + 合成 result
    ↓ determine side-effect state
    ├── known safe → CANCELLED
    ├── applied    → preserve fact/artifact, then CANCELLED
    └── unknown    → RECOVERY_REQUIRED or CANCELLED with recoveryItems
```

### 25.6 Run 完成

```text
ModelInvocation 完成且无 Tool Call
    ↓ EvaluateAcceptanceDirective
    ↓ AcceptanceCheckerPort 评估 criteria
    ├── 满足                     → CompleteRunDirective(SUCCESS)
    ├── 未满足且未达重试上限       → SYSTEM_NOTICE 回灌 Context，继续
    ├── 未满足且已达上限           → COMPLETED_WITH_LIMITS + incompleteItems
    └── 存在未决 RecoveryItem      → RECOVERY_REQUIRED
```

### 25.7 Crash Recover

```text
acquire run recovery lease
    ↓ load snapshot + replay later events
    ↓ 重新装载 durable timers
    ↓ inspect unfinished Activity / unsettled ActionBatch / pending signals
    ↓ revalidate capability / environment / preconditions
    ↓ 结算未完成批（为未启动 Action 合成 result）
    ↓ resolve outcome or request recovery decision
    ↓ continue without duplicating proven side effects
```

### 26.3 一致性规则【定】

- 两层可以初期共享 SQLite 文件，但 Repository 和 Migration 所有权分开；
- **Migration 由单一 runner 按固定顺序执行**（先 Layer 3 后 Layer 2 或相反，需固定），避免两个 owner 并发迁移同一文件；
- Layer 3 不查询 Layer 2 表，Layer 2 不修改 Layer 3 表；
- 跨层通过 Public API、Port、Snapshot、Signal 和 Projection；
- **一个 Run transition、对应 Event、Activity Intent、已消费 Signal 和相关 Timer 必须在同一 Layer 3 事务提交**（§23.3，不再是"尽量"）；
- Projection 使用 eventId/sequence 幂等处理；
- Blob 写入使用 content hash，事实表只在 Blob durable 后引用；写入与引用之间的窗口产生的孤儿 Blob 由 §22.5 回收。

### 26.4 SQLite 实现约束【新增·P2-2】

记录为已知实现约束与风险，不在本文解决：

- SQLite 单写者语义：多 Run 并发 + lease heartbeat + timer 写入会产生持续写压力，需要 WAL 模式与合理的 `busy_timeout`；
- Run Lock（§8.4）与 SQLite 事务的关系需要明确：是数据库行锁、独立 lock 表，还是进程内互斥 + 数据库 generation 校验；
- heartbeat 与 timer 的写频率必须显式设计（§16.2 定为 30s 量级即为此考虑）；
- 【验】上述约束需在阶段 2 通过并发压力用例验证，而不是假设 SQLite 够用。


## 28. 推进顺序与冻结门槛

每个阶段除工程交付物外，必须产出上位基线 §12 要求的学习证据。**阶段完成不以写了多少代码判断，而以是否真正回答了该阶段的研究问题判断。**

### 28.1 Spike 0：Provider 协议现实核对【新增】

> **性质**：一次性、明确可丢弃、不进主干依赖（放在 `spikes/s0-provider-protocol/`）
> **时间盒**：2 天

**为什么必须在阶段 1 之前**：二次评审的三个 P0（多 Tool Call、必须原样回传的协议块、token 会计归属）有同一个成因——它们只在真正调用过一次带工具的流式 Provider 之后才会暴露。V02 的阶段 1 只用 Fake/Recorded ModelPort，意味着这类问题会在 Contract 冻结之后才被发现。这是本项目当前最大的**顺序性风险**。

**最小脚本**：2 个工具 × 多轮 × 流式 × 触发并行 tool call × 扩展思考 × 中途取消 × usage 读数 × 一次故意的 schema 错误 × 一次超长结果。

**必须产出《Provider Protocol Facts》**，逐条附可运行脚本与日志证据：

| 待答问题 | 影响的 Contract |
|---|---|
| 一次响应最多返回几个 tool call；是否可通过参数强制单条 | §8.6 ActionBatch、D-01 |
| 哪些块必须原样回传；是否有签名/校验；被改写会怎样 | §11.5 `REQUIRED_VERBATIM`、原则十一 |
| 流式中断后已产出部分的结构；已闭合的 tool call 是否可用 | §8.5 中断规则 |
| token 计数口径：请求前估算 vs 响应实际、缓存命中如何计、误差范围 | §11.6、§16.1、`ModelProtocolPort` |
| 错误响应的结构与可区分性 | §13.1 错误分类 |
| 缓存断点的放置约束 | §11.8 `CACHE_BREAKPOINT` |
| 上下文超限时的报错形态（能否提前判定） | §11.6 `COMPACTION_INSUFFICIENT` |

**退出证据**：上述每一条有脚本 + 日志。超时未答的条目记录为未解答项，对应 Contract **保持【验】标记，不得默认冻结**。

**学习产出**：一份 Provider 协议事实笔记，可直接用于面试中解释"为什么 Agent Harness 的 Context 层不能与 Provider 解耦得太干净"。

### 28.2 阶段 1：Headless Walking Skeleton

**研究问题**：纯决策 Kernel 与异步 Activity 的边界是否成立？Observe → Decide → Act → Verify 闭环能否在没有持久化的前提下跑通并被评测？

最小实现：

- 纯 Kernel + Coordinator（`KernelTransition.directives` 为数组）；

- In-memory Store、Signal Inbox、FakeClock、FakeTimer；
- 一个只读 Tool 和一个可验证写 Tool；

- WAITING_FOR_USER / APPROVAL / Interject；
- 基本 Budget/Cancel；
- 结构化 Trace 和 Micro Cases。

【定】这一阶段允许 Contract 继续迭代，但**不得绕过**：Effect 解析、错误副作用状态、批内配对不变量、边界脱敏、Run 级 Acceptance 评估。

### 28.3 阶段 2：Durable Runtime

**预期 ADR**：Run Lock 与 SQLite 事务的关系；Timer 实现路径（D-08）；保留策略（D-10）。

## 29. 当前决策状态

### 29.1 已对齐【定】

- 三层架构与单向依赖；
- Workspace / Session / Run 三中心；
- Session 是产品基础能力，Runtime 支持无 Session；
- Kernel 纯决策，Coordinator durable orchestration；
- Model/Tool/Context/Verification/Acceptance 等外部工作统一为 Activity；
- **一次 ModelInvocation 的全部 Tool Call 构成 ActionBatch，批内每个 call 恰好一个 result**；
- **Context 的不可拆分单元是 protocolGroup，`REQUIRED_VERBATIM` 不可被 Compact 触碰**；
- **循环终止规则：模型不再请求工具 → Acceptance 评估 → 完成 / 回灌 / 恢复**；
- **执行期间用户输入通过 Interject 进入 Working Context，不改变状态机**；
- Session Context 与 Run Context 分开治理；Compact 分层归属；
- **脱敏发生在离开 Adapter 边界的第一个持久化点**；
- EffectScope 由可信 Resolver 产生；
- Error 与 side-effect state 分开；
- frozen snapshot 与 live revocation/lease 分开；PARKED lease 保护人工接管；
- Durable Signal Inbox、Durable Timer 与 Activity Abort 配合；
- Recover / Rebuild / Replay / Unpause 四者命名与语义分离；
- Budget（双墙钟）、Progress Guard（durable heartbeat）和 Cancel 是强制语义；
- 两类 Handoff：MODEL_AUTHORED 与 DETERMINISTIC；
- **Layer 3 拥有执行事实，Layer 2 拥有产品聚合，单向投影**；
- 数据保留分类明确，Durable Event 与事实表永不删除；
- Eval/Testkit 是 P0 系统能力但不进入 Kernel；
- 不引入外部 Agentic UI 协议，采纳其事件语义参照（A-01）；
- v0.1 不实现多 Agent，不写死单层 Run 假设；

### D-01　ActionBatch 是否支持批内并发

**问题**：一次模型响应返回多个 Tool Call 时，v0.1 是串行执行全部，还是允许对无冲突的只读 Tool 并发执行？

**为什么现在必须决**：它决定 `ActionBatch`、`RuntimeActivity`、`RunSnapshot.currentActivityIds`、Cancel 语义与恢复协议的形状。事后从串行改并发要动整个恢复分支集。

**候选**：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 全串行（`SEQUENTIAL`） | 状态空间最小；恢复分支最少；调试直观 | 多个独立读操作的延迟线性叠加；Case 01 的多媒体下载体验差 |
| B. 按 `batchAffinity` 受限并发 | 只读并发收益明显；写操作仍串行 | 取消落在并发中间的状态组合暴涨；lease 争用需要额外仲裁 |
| C. 先做 A，把 B 作为 `executionMode` 的第二个取值预留 | 兼顾；接口不返工 | 需要现在就把接口设计成能容纳 B（本文已按此设计） |

**影响面**：§8.6 全部不变量、§9.5 Cancel、§18.2 crash window 7、§24.3 故障注入集规模。

**本文倾向**：**C**。接口按并发设计，v0.1 实现只支持 `SEQUENTIAL`，并在文档中明确这是产品策略而非协议限制。

**拍板需要的证据**：Spike 0 中"一次响应最多返回几个 tool call、能否强制单条"的实测结果。如果 Provider 支持强制单条且效果损失可接受，A 的吸引力会大幅上升。

### D-02　Interject 能否撤回 PENDING Approval

**问题**：Run 处于 `WAITING_FOR_APPROVAL`，用户插话说"别这么干，换个方式"。是否自动撤回该 Approval 并让模型重新决策？

**为什么现在必须决**：它给 Approval 生命周期增加一条由**内容语义**驱动的路径，而 `intent` 来自用户在 UI 上的选择，不是可信解析。

**候选**：

- A. 不撤回。插话只入 Context，用户仍需显式拒绝 Approval。语义最干净，但反直觉；
- B. `intent = REDIRECT` 时自动撤回 Approval，Run 回到 `RUNNING` 并重新决策；
- C. 不自动撤回，但 UI 在检测到插话时提示用户"是否同时拒绝当前审批"，由用户显式操作。

**影响面**：§14.3 Approval 生命周期、§9.7 插话语义、Approval 的幂等与过期逻辑。

**本文倾向**：**C**。把语义判断交回用户，避免 Runtime 依赖对自然语言意图的推断，同时不牺牲直觉。

**拍板需要的证据**：一个 Micro Case 走查三种方案下的用户操作序列，看 C 是否显得啰嗦。

### D-03　RunAcceptance 从哪里来

**问题**：Run 级验收标准的来源是什么？

**为什么现在必须决**：`RunSpec.acceptance` 是必填字段，它的来源决定了 Layer 2、AgentProfile 与 Case Package 的职责边界，也直接关系到"Case 无关"这条依赖规则是否被破坏。

**候选**：

| 方案 | 说明 | 风险 |
|---|---|---|
| A. AgentProfile 默认 + Layer 2 生成 | Layer 2 根据 AgentProfile 和用户意图生成 acceptance | Layer 2 需要理解任务语义，可能变成一个隐形的规划器 |
| B. Case Package 声明 | Case 提供 acceptance criteria 模板 | 最符合"Case 通过 Contract 接入"，但只覆盖已知 Case；自由任务没有 acceptance |
| C. 模型在 Run 开始时提出并冻结 | 模型读完任务后自述验收标准，冻结进 RunSpec | 优雅但自证；模型可以给自己定低标准 |
| D. 分层：默认 `MODEL_DECLARED`，Case 可覆盖为 `DECLARATIVE/HYBRID` | 混合 | 需要明确覆盖优先级 |

**影响面**：§10.4、§7.4 `acceptancePolicy`、§24.6 Grader 接口、Case Package 结构。

**本文倾向**：**D**。它保证 Harness Core 不依赖 Case 语义（默认可用），同时让有确定性产物的 Case 能提供强验收。

**拍板需要的证据**：讨论即可；但 Case 01 的 acceptance criteria 草案会是很好的检验——如果写不出来，说明 B/D 不可行。

### D-04　Artifact 的用户手工操作如何回流

**问题**：用户在 UI 里删除、重命名或标记了一个 Artifact，而某个 Run 正在引用它。Runtime 如何得知？

**为什么现在必须决**：§23.2 规定"用户手工标记以 Layer 2 为准"，但 Layer 3 不能查询 Layer 2 表。回流路径不明会导致 Run 在恢复时基于失效的 Artifact 继续。

**候选**：

- A. 只在 precondition fingerprint 校验时发现（被动）。简单，但发现得晚；
- B. Layer 2 通过 Signal 主动通知 Runtime（如 `ResourceInvalidatedSignal`）。及时，但增加信号类型与竞态；
- C. Artifact 一旦被 Run 引用即在 Layer 2 加"使用中"标记，用户操作时先警告。

**影响面**：§23.3 规则 5、§18.3 外部世界重新校验、RuntimeSignal 联合。

**本文倾向**：**A + C**。被动校验保证正确性，UI 警告降低发生概率，不引入新信号类型。

**拍板需要的证据**：阶段 3 有真实 Artifact 后观察这种情况的实际频率。

### D-05　上下文不可压缩时的默认动作

**问题**：`ContextFrameOutcome.status = COMPACTION_INSUFFICIENT` 时，Kernel 默认做什么？

**候选**：

- A. 触发更激进的 Compact 策略（丢弃更多历史，只保留 irreducible + 最近 N 轮）；
- B. 请求用户缩小范围（`WAITING_FOR_USER`）；
- C. 直接产出 `DETERMINISTIC` handoff 并以 `CONTEXT_EXHAUSTED` 结束。

**影响面**：§11.6、§16.4、`RunOutcome.kind`。

**本文倾向**：**A → 若仍不足则 C**。B 在无人值守（Eval、Automation）场景不可用，不能作为默认路径，但可作为有 Session 的 Run 的可配置策略。

**拍板需要的证据**：Spike 0 的"上下文超限报错形态"（能否提前判定决定了 A 是否有机会执行）+ Eval 中激进 Compact 对任务效果的实际影响。

### D-06　是否允许在任何情况下保留未脱敏原文

**问题**：原则十二禁止未脱敏内容离开 Adapter 边界。是否为调试保留例外（例如仅本机、加密、短 TTL 的 debug 模式）？

**为什么现在必须决**：这是安全边界，事后开口子比一开始就设计好难得多。V02 用"由数据策略决定"留白，正是本次评审判定为与上位基线冲突的地方。

**候选**：

- A. 完全禁止。任何情况下都不落未脱敏原文；
- B. 允许 `debug` 模式：仅本机、独立加密存储、TTL ≤ 24h、启动时显式告警、永不进入 Trace/Event/Context；
- C. 允许，但仅对已知不含凭证的 Capability（如本地只读文件）。

**影响面**：§22.2、`RedactionPort` 接口、故障排查效率。

**本文倾向**：**A**，除非 Spike 或阶段 3 出现"脱敏后完全无法定位问题"的具体案例。理由：上位基线是已拍板项；且脱敏报告（脱了几个字段、什么类型）通常已足够定位。

**拍板需要的证据**：讨论即可。若选 B，需要同时定义 debug 模式的开启方式与审计要求。

### D-07　v0.1 单 Provider 还是双 Provider

**问题**：`ModelProtocolPort` 的抽象强度取决于是否有第二个 Provider 来反证。v0.1 是先做一个，还是一开始就做两个？

**为什么现在必须决**：这与上位基线 §6.2「第二个差异化 Case 出现后，再验证和抽取更高层抽象」是同一类问题——**一个实现无法证明抽象正确**。而 Provider 协议差异恰恰是 §11.5 全部不变量的来源。

**候选**：

- A. 单 Provider（Anthropic）。最快，但 `ModelProtocolPort` 会长成那个 Provider 的形状；
- B. 双 Provider（Anthropic + OpenAI），只在 Spike 0 与阶段 1 各跑一遍最小链路，不做完整适配；
- C. 双 Provider 完整支持。

**影响面**：`ModelProtocolPort` 抽象质量、§11.5 不变量的普适性、Eval 的模型对比能力。

**本文倾向**：**B**。成本接近 A，但能在抽象成型前就暴露"哪些是协议共性、哪些是某家特性"。这与项目"通过差异化 Case 反证抽象"的方法论一致。

**拍板需要的证据**：Spike 0 若在两家上同时跑，B 的额外成本几乎为零，届时可直接确认。

### D-08　Timer：真定时器 vs 惰性判定

**问题**：v0.1 实现完整的 durable timer 子系统，还是先用"恢复扫描 + 读取时惰性判定是否已过期"？

**候选**：

- A. 完整 durable timer（§18.6）。精确，能主动通知 UI"审批已过期"；
- B. 惰性判定：不注册 timer，只在读取 Approval/Lease/Observation 时检查 `expiresAt`；定期扫描作为兜底。实现成本低得多，但"过期"不会主动发生，UI 会一直显示 PENDING；
- C. 混合：内存定时器（进程内精确）+ 启动时扫描（跨重启兜底），不持久化 timer 表。

**影响面**：§18.6、`durable_timers` 表、§14.3 Approval 过期、UI 体验。

**本文倾向**：**C**。它在实现成本与体验之间取平衡，且不需要 `durable_timers` 表；但需要接受"进程崩溃期间过期的对象要等到重启扫描才被标记"。

**拍板需要的证据**：讨论即可。若选 C，§26.2 的 `durable_timers` 表应从 v0.1 表集中移除。

### D-09　一个 Session 一个 Foreground Run 是否继续成立

**问题**：v0.1 限制一个 Session 同时只有一个前台 Run。有了 Interject 之后，这条限制是否还必要？

**为什么现在必须决**：它是 §9.7 路由表的前提。如果放开，路由表要处理"消息该进哪个 Run"。

**候选**：

- A. 保持限制。Transcript 顺序清晰，路由表简单；
- B. 允许多个并行 Run，Transcript 按 Run 分组展示；
- C. 保持限制，但允许"后台 Run"（不写 Transcript，只在完成时投影一条汇总）。

**影响面**：§6.3、§9.7 路由表、Transcript 投影、§2.4 的多 Agent 边界。

**本文倾向**：**A**（v0.1），把 C 作为阶段 5 的产品化选项。

**拍板需要的证据**：真实使用体感——当一个 Run 跑 10 分钟时，是否强烈需要同时开另一个任务。

### D-10　数据保留窗口与默认倾向

**问题**：默认"激进回收 + 用户显式 PIN"，还是"默认全保留 + 用户显式清理"？各类数据的保留窗口是多少？

**候选**：

- A. 激进回收：非交付 Blob 默认 7 天，诊断 Blob 3 天。磁盘友好，但可能在需要复盘时已经没了；
- B. 全保留：只在磁盘水位告警时提示用户清理。学习项目更需要历史样本，但个人 Mac 磁盘有限；
- C. 分层：Eval/Micro Case 相关永久 PIN，真实任务 30 天，诊断 7 天。

**影响面**：§22.5、§18.4 Replay 可行性、故障复盘能力。

**本文倾向**：**C**。项目第一目标是学习，失败样本是核心资产，不能被 GC 吃掉；但真实任务的媒体下载体积不可控。

**拍板需要的证据**：阶段 3 跑几个真实归档任务后的实际磁盘占用数据。

### D-11　Case 02 的具体选择

**问题**：选哪个与网页归档差异明显、推理和决策更重的任务作为架构反证 Case？

**为什么现在必须决**：上位基线 §10.3 要求「在冻结更高层通用接口前」选定 Case 02。V03 的多个抽象（Acceptance criteria、EffectResolver、Artifact kind、Context 治理）都只被 Case 01 检验过。

**候选**（来自上位基线 §3.3）：

| 候选 | 反证价值 | 风险 |
|---|---|---|
| 本地多文件搜索、分析、编辑 | 强验证 Effect Resolution 与可逆写；Artifact 形态完全不同 | 与网页归档同属"文件操作"，差异可能不够大 |
| Git 仓库分析与技术方案生成 | 强验证多来源信息取舍、动态规划、Context 治理；Artifact 是文档 | 验收标准偏主观，需要 LLM Judge |

### D-12　Eval Grader 最小可用集与 Baseline 形态

**问题**：Case 01 要回答"Agent 是否真实带来增益"，需要一个确定性 Workflow Baseline。这个 Baseline 做到什么程度？Grader 最小集是什么？

**为什么现在必须决**：Baseline 太弱则 Agent"赢"得没有意义；太强则等于先写了一遍确定性程序。这个尺度直接决定阶段 3 结论的可信度。

**候选**：

- A. Baseline 是完整的确定性 Pipeline（能独立完成 80% 的正常页面）；
- B. Baseline 只覆盖 happy path，异常一律失败；
- C. 两个 Baseline：happy-path 版 + 带简单重试的健壮版。

**影响面**：§28.4 退出证据、上位基线 §10.1 的评测要求。

**本文倾向**：**A**。上位基线明确说"网页归档的大部分步骤可以由确定性 Pipeline 完成"，只有 Baseline 足够强，"Agent 在哪些环节产生价值"这个结论才有说服力。

**拍板需要的证据**：讨论。同时需要定义 Grader 最小集（Artifact 完整性、正文提取准确率、媒体缺失率、异常场景成功率）。

### D-14　阶段 1 的规格切面

**问题**：本文设计了 38 张逻辑表（Layer 2 19 张 + Layer 3 19 张）、19 个 Port、16 条 Directive。阶段 1 实际实现哪些？

**为什么现在必须决**：这是 §2.5 规格纪律第 3 条的直接落地。**不明确切面，阶段 1 会不自觉地实现全部设计，从而在没有任何运行证据的情况下固化所有假设**——这正是 V02 被本次评审判定的元问题。

**候选切面**：

- A. 最小闭环：In-memory Store（不建表）、5 个 Port（Model / ModelProtocol / ToolHandler / Clock / IdGenerator）、8 条核心 Directive；
- B. 中等：加 Redaction、EffectResolver、Verification、Acceptance 四个 Port，仍不落 SQLite；
- C. 完整 Contract 面 + In-memory 实现。

**影响面**：阶段 1 工期、错误抽象的暴露速度、返工成本。

**本文倾向**：**B**。理由：Redaction 与 EffectResolver 是安全不变量，阶段 1 就绕过它们会形成"以后再补"的技术债；Acceptance 是本版新增的核心语义，必须在阶段 1 被 Micro Case 检验。SQLite 与 Timer 留给阶段 2 是合理的。

**拍板需要的证据**：讨论即可。产出物应是一份明确的"阶段 1 实现清单 / 不实现清单"。

### D-15　KernelState 的序列化边界

**问题**：KernelState 包含哪些字段？哪些是可序列化的纯数据，哪些是运行时引用？

**为什么现在必须决**：`StoredRunSnapshot.kernelState: SerializedKernelState`（§18.5）与 Replay（§18.4）的可行性完全取决于此。如果 KernelState 持有任何不可序列化的引用（Port、闭包、Provider 对象），Snapshot 与 Replay 都不成立。

**候选**：

- A. KernelState 只含 ID 与标量（决策步数、状态、未决请求 ID、Budget 用量、Context item ID 列表）；实际内容通过 ID 从事实表加载；
- B. KernelState 含完整 Context 快照，自包含但体积大；
- C. 分层：热状态（A）+ 冷引用（按需加载）。

**影响面**：§18.5 Snapshot、§18.4 Replay、Kernel 纯度、恢复性能。

**本文倾向**：**A**。它是 Kernel 纯度的自然推论：Kernel 是纯函数，其状态就应该是纯数据。所有内容通过 Coordinator 在 `KernelInput` 中喂入，而不是由 Kernel 自己持有。

**拍板需要的证据**：阶段 1 实现 KernelState 的第一版后，尝试序列化并重建，看是否有字段无法表达。

## 31. 最终架构摘要

```text
Workspace 冻结资源、配置与授权证据
        ↓
Session 冻结不可变 ConversationSourceSnapshot（分段内容寻址）
        ↓
Layer 2 生成自包含 RunSpec（含 RunAcceptance）
        ↓
Coordinator 串行提交状态，异步执行 RuntimeActivity
        ↓
Kernel 只消费规范化 Outcome 并产生下一批 Directive
        ↓
一次模型响应的全部 Tool Call 构成 ActionBatch，每个 call 恰好一个 result
        ↓
Context Runtime 管理 ToolResult、Blob、协议组、预算和 Compact
        ↓
Action Runtime 解析真实 Effect，经过 Grant / Lease / Policy / Approval
        ↓
Observation 与 Verification 判断外部世界是否达到目标
        ↓
Acceptance 判断整个任务是否完成
        ↓
Durable Event / Snapshot / Timer / Replay 保证可诊断、可恢复、可评测
        ↓
Layer 2 将执行事实投影为 Message、Tool、Approval、Interaction 和 Artifact
```

V03 在 V02 的四条执行边界之上，补齐了三条同样不能含混的边界：

**V02 已确立的四条**

1. 纯决策与异步活动分离，但通过 durable Activity 闭环；
2. 模型看见的 Context 必须经过可追踪、可预算、协议合法的编译；
3. 所有副作用必须先得到可信的 EffectScope，再谈 Policy、Approval 和重试；
4. 恢复不是重新跑一遍；取消、未知副作用、实时撤权和外部变化都有明确处置。

**V03 补齐的三条**

5. **一次模型响应可能产生多个动作。批的原子性、审批粒度、配对完整性和取消语义必须一起定义，不能假装每次只有一个 Tool Call。**
6. **Run 必须知道自己什么时候算做完了。每一步都验证过，不等于整件事做成了。**
7. **安全边界在数据离开执行边界的那一刻，而不是在它进入模型的那一刻。**

同时确立一条方法论边界：

> **证据先于冻结。** 未经真实运行验证的 Contract 不进入冻结门槛的"已完成"列。本版用状态标记（【定】/【验】/【议】）在文档层面强制这一点，用 Spike 0 在流程层面强制这一点。

在此基础上，WorkAgent 可以先用单 Agent Loop 完成 Walking Skeleton 和真实 Case；未来若 Eval 证明需要 Sub-agent，再以独立 Run、隔离 Context 和显式资源分配方式演进，而不需要推翻当前三层架构。
