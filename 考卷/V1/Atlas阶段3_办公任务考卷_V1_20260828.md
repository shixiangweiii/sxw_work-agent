## 0. 这张卷子要回答什么

阶段 3 的研究问题是：

> **一个 Case 无关的通用能力面，能不能支撑真实办公任务端到端，而不被任何一个任务反向定义？**

退出门槛里「通用性成立」那一格现在**只有 smoke 级证据**——`verify:scenarios` 由**脚本化模型**驱动，
它证明「链路走得通」，不证明「模型能自己想出这些步骤」。这张卷子补的就是这一格。

### 【定】三条待证命题

| # | 命题 | 现有证据 | 挂了说明什么 |
|---|---|---|---|
| **P1** | 真实模型能用这套通用工具面自主完成办公任务，**不需要 Case 专属工具兜底** | 只有脚本化 smoke | 能力面有洞，或者洞一直被 `cases/` 里的测量工具掩盖着 |
| **P2** | 阶段 3 新建的四条机制（Blob 外置＋取回、Artifact 登记＋二层验证、Progress Guard、人工接管）**会被真实任务真正消费** | 只有 verify 段的构造验证 | 机制是为验收脚本而建的，不是被真需求逼出来的 |
| **P3** | 「模型不再请求工具即完成」这条终止条件，在**更重的任务**上还站得住 | 阶段 2 的任务只有 4 轮 7 调用 | 需要通用 Completion Gate——而它的原论据已被 `probe:requirement-extraction` 推翻 |

**判分设计服务这三条，不服务一个好看的分数**（理由见 §5.4）。

### 这张卷子明确**不**回答的

- Agent 相对确定性 Workflow Baseline 有没有增益（无 Baseline 实现）
- 端点差异是否被挡在主循环外的**真实任务级**证据（只跑单端点，§2.1 决 2）
- 对抗安全：无 prompt injection、无恶意文件名、无 symlink 越界、无并发 TOCTOU
- `fetch_url` 的任何能力结论（结构性测不了，§7.1）

## 1. 开考前置检查

【定】**这三条不过，第一次运行会在发出任何请求之前就失败，或者花了钱拿到不可用的证据。**

### 1.1 `.env` 与端点声明必须一致

根 `.env` 的 `dashscope_model` **必须是 `qwen3.7-plus`**。

阶段 2 的 P1-1 就死在这里：`.env` 写着 `deepseek-v4-flash`，而 CLI 默认选百炼 profile
（`modelId: qwen3.7-plus`），一致性闸门在首个模型请求前 fail fast，
用户给的原始命令**一次都没跑起来**。

```bash
grep -E '^dashscope_(model|base_url_Anthropic)=' .env
```

期望 `dashscope_model=qwen3.7-plus`。不一致有两个选择：改 `.env`，或显式传 `--endpoint`。
**不要绕过这个闸门**——它防的是「第三方 Key 被发往官方端点」。

### 1.2 基线必须干净

```bash
npm run typecheck        # 必须 exit 0
npm run verify:all       # 12 条脚本 / 86 条判据，必须全绿
git status --porcelain   # 必须为空，否则 provenance 记 dirty
```

### 1.3 任务原文用文件传，不要直接写进命令行

三题原文都是多段文本，直接塞进 `--task "..."` 会遇到引号与换行的转义问题。

```bash
mkdir -p 考卷/V1/tasks
# 把 §4.1 / §4.2 / §4.3 的「任务原文（逐字）」分别存成：
#   考卷/V1/tasks/task1.txt   task2.txt   task3.txt
# 只存原文正文，不要存引用符号 ">"、不要存标题
```

调用时一律 `--task "$(cat 考卷/V1/tasks/task1.txt)"`。

## 2. 考场设置

### 2.1 四条已拍板的决定

| # | 决定 | 取值 | 代价与补偿 |
|---|---|---|---|
| **决 1** | 运行规模 | **3 题 × 3 次**，出 per-task `pass^3` | 判别力弱于 `pass^5`。补偿见 §5.1 的人工复核条款 |
| **决 2** | 端点 | **只跑百炼 `qwen3.7-plus`** | DeepSeek 对照门槛继续挂着（端点侧 401，非本项目问题），报告如实标「未跑」 |
| **决 3** | 恢复与接管 | **全做**，两个专项 run | 需要人在终端操作，步骤见 §4.4 |
| **决 4** | 审批档位 | **`--yes-all` 无人值守** | 损失一格观察，用冒烟批补回，见下 |

#### 决 4 的代价核算（已核源码）

`--yes-all` 走 [`main.ts:190`](../../apps/cli/src/main.ts#L190) 的 ApprovalDecider，**绕不过 Policy 层**。
[`policy.ts:34`](../../packages/harness-runtime/src/action/policy.ts#L34) 的【定】是
「越界**写**一律拒绝，不给审批机会」——它在 Decider 之前。所以 C 维度在 `--yes-all` 下仍有三条真判据：
Policy 越界写 DENY、读黑名单、题 2 的否定式约束（后者与档位无关）。

**真正损失的只有一格**：默认档位这条闸门本身没被观察到。而它恰是阶段 3 刚栽过跟头的地方——
E-3 的自动放行规则因为 `REVERSIBLE` vs `PARTIALLY_REVERSIBLE` 一字之差，
**从来没覆盖过 `write_file`**，真实端点实跑才撞出来。

【定】**补偿**：冒烟批的题 1 那一次用**默认 `--yes`**，另两次用 `--yes-all`。
花 0 次额外 run，就能看到「`write_file` 被自动放行、`append_log` 被停下来问」这一对是否成立。

#### 决 4 的一个意外好处

`--yes-all` 下 `append_log` 会被真的批准执行，于是
**「三题合计有没有用到 `cases/` 里的测量工具」这条观察不再被档位掩盖**——
模型用了就是真用了，不会变成一次被拒绝的调用。这条直接回答 **P1**。

### 2.4 留档要求

【定】每个 live trial 必须保存：


#### 3.1.3 `流水/2026Q2明细.txt`（程序生成，1,000 行）

**确定性生成规则**（伪代码，任何语言实现结果必须一致）：

```text
SUPPLIERS = ["远山科技","北岸物流","青禾食品","海图传媒","云栖建材","长风医疗"]
BASE      = 2026-04-01 (UTC)

for i = 1 .. 1000:
    supplier = SUPPLIERS[(i - 1) mod 6]
    date     = BASE + ((i - 1) mod 91) 天          # 2026Q2 共 91 天
    amount   = 1000 + ((i * 37) mod 9000) + 0.5    # 保留两位小数
    serial   = i 左补零到 4 位
    line     = "{date} | {supplier} | 付款 | {amount:.2f} | PAY-{date无横线}-{serial}"

文件内容 = 所有行以 "\n" 连接，并以 "\n" 结尾
```

**生成自检**（不是判据，是「夹具生成对不对」的校验）：

| 项 | 期望值 |
|---|---|
| 行数 | 1,000 |
| **字符数**（`String.length`） | **53,000** |
| 字节数（UTF-8） | 65,000 |
| 首行 | `2026-04-01 \| 远山科技 \| 付款 \| 1037.50 \| PAY-20260401-0001` |
| 末行 | `2026-06-29 \| 海图传媒 \| 付款 \| 2000.50 \| PAY-20260629-1000` |
| 金额总计 | `5389000.00` |

> ⚠️ **【定】尺寸必须按字符算，不是字节。**
> 外置判定是 `approxTokens = Math.ceil(text.length / 2.5)`，用的是 **`String.length`（字符数）**。
> 中文一个字符占 3 字节，按字节估会差出三倍。
>
> | 阈值 | 值 | 本夹具 |
> |---|---:|---|
> | `inlineToolResultLimitTokens`（超过就外置） | 8,000 | **21,200** ✓ 必然外置 |
> | `SqliteBlobStore.MAX_PAGE_CHARS`（每页字符上限） | 12,000 | 53,000 → **需 5 页** ✓ 必然分页 |

## 4. 三道题

### 【定】任务原文即判据

每条 `TASK` 类判据必须引用任务原文的**逐字片段**（`sourceQuote`），见 §6 约束 5。
**所以原文的措辞就是判据本身**，改一个字就是改判据。

原文遵循一条张力处理原则：**明确的是「要什么」，模糊的是「怎么做」。** 判据只查「要什么」。
写成 checklist 会让考卷退化成「照单执行」测试；写得太含糊则重演阶段 2 的作用域歧义误判。

### 【定】判定的三条通用规范（三题共用）

否则会产出**假失败**——阶段 2 的教训就是这么来的：

| # | 规范 |
|---|---|
| **N1** | **数字规范化后比对**：去掉千分位逗号、空格、货币符号与「元」字后比较数值。`892,404.50` `892404.5` `892404.50 元` **一律等价** |
| **N2** | **「一行」按 `\n` 切分判定，不得要求 Markdown 表格语法**。原文只说「每家供应商一行」，模型用表格行、列表项 `- 远山科技｜已签署｜892404.50`、纯文本行**都算**。要求 `\|` 表格会把合法产出误判成失败 |
| **N3** | **日期接受三种形态**：`2026-08-28` / `2026年8月28日` / `2026/08/28`，比对的是**运行当天**（Asia/Shanghai），不是本文档的创建日期 |

| O2 | 等待期间 active 预算是否真的没涨 | `InteractionRequested` → `Completed` 的时间差 vs `activeWallClockMs` 增量 |
| O3 | 失败形态分类 | 若判据 3 挂：是**抄了诱饵** `HT-XX-2023-0001`，还是**凭空编了一个**？两者分开记 |

> **O1 为什么是观察项而不是硬门槛**：它的依据是工具返回的 `nextStep` 与 V05 §20.3，
> **不是任务原文**——按 §6 约束 5，它拿不出 `sourceQuote`，就不能当 TASK 类硬判据。
> 把它塞进 INVARIANT 类同样不行（§6 明确只允许两种形态）。
> 【定】**宁可降级成观察项，也不给「把机制规则伪装成任务判据」开口子。**

#### 第 4 条防的是什么

模型可能**既发起了接管、又在别处编了一个占位编号**
（「合同编号：待补充（暂记 HT-XX-2023-0001）」）。只查第 3 条会放过它。

#### 这题锚定的机制

`request_handoff` → `WAITING_FOR_INTERACTION` → 持久化 → resume →
**等待时间不计入 active 预算**。直接对准阶段 1「盘点时间：2025年」——
模型编造无依据事实的倾向，也是 U-8「不存在的 ask-user 工具」那个洞的真实检验。

## 5. 判分

### 【定】三层判定，分数不是主结论

```text
第 1 层  硬门槛（binary，per task per trial）   ← 这才是成败
第 2 层  机制消费证据表（不打分）                ← 本次最有价值的产出
第 3 层  100 分量表（只为跨阶段沟通）            ← 必须标注不可比
```

### 5.1 第 1 层｜硬门槛

一个 trial 的判定：**该题判据表中所有 `TASK` 与 `INVARIANT` 类判据全过 = PASS**，
任一挂 = FAIL。`软` 类不参与，但要如实报。

出 `pass@1` 与 **per-task `pass^3`**；整卷 `pass^3`（三题都 3/3）另报。

> ⚠️ 【定】**`pass^3` 的统计力必须写进报告。**
> 阶段 2 那次失败**恰好是 5 次里的第 1 次**——3 次全过不足以支撑「稳定」这个词。
> 报告里明写：「本次为控成本收缩到 `pass^3`，不等价于阶段 2 报告建议的 `pass^5` 硬门槛。」

> ⚠️ 【定】**任一 trial 失败，一律人工看完整轨迹再定性，不得直接记成「模型能力失败」。**
> 阶段 2 的 grader 误判被当成模型遗漏，隔了一个阶段才被探针推翻。
> 3 次样本下这条更重要——**一次误判就是 33%**。
>
> 复核时逐条问：这条判据查的东西，任务原文真的要求过吗？（对照 `sourceQuote`）

### 5.2 第 2 层｜机制消费证据表

这张表阶段 1/2 都没有，它直接回答 **P2**：

| 观测项 | 出处 | 期望 |
|---|---|---|
| `ToolResultExternalized` 次数 / `read_blob` 调用次数 / **取回页数** | trace | 题 1 每次 ≥ 1 次外置、≥ 1 次取回 |
| `ArtifactRegistered` 次数 / 二层检查跑了哪几项 / 有没有 FAIL | trace | 题 1 的 JSON 检查真的跑过 |
| `InteractionRequested → Completed` 事件对 / 等待时长 / **active 预算是否真的没涨** | trace | 题 3 每次 1 对 |
| `NoProgressDetected` 次数 | trace | **0** |
| §18.2 三条分支各命中几次 | `inspect()` 的 `resumeBranchCounts` | 专项 A/B |
| **三题合计有没有用到 `cases/` 里的工具**（`append_log` / `slow_write`） | trace | 期望 0——用了就是 P1 的反证 |
| **Runtime outcome × grader verdict 的 2×2 混淆矩阵** | 见下 | — |
| failed tool rate / 轮次 / token / 时延分布 | trace | — |

#### 混淆矩阵为什么要两个方向都列

阶段 2 出现过 5/5 `SUCCESS` 对 4/5 grader pass，当时归因「Runtime 太宽松」，
后被探针推翻成「grader 误判」。而阶段 3 实跑撞到过**反方向**那一格：
模型全部做对，结算 `USER_REJECTED`，而全程没有任何人拒绝过任何东西。

| | 判据 PASS | 判据 FAIL |
|---|---|---|
| **Runtime SUCCESS** | 一致 | Runtime 太宽松 **或** 判据误判——必须人工看轨迹判定是哪一种 |
| **Runtime 非 SUCCESS** | Runtime 太严（阶段 3 撞过） | 一致 |

**哪一格非空，都是一条结论。**

## 6. 判据的结构约束

Roadmap §5 已把旧 grader 上发现的四个形状写成【定】，
**必须在第一次 `--live` 之前处理完**。1–4 是原文，5–6 是本卷新增。

| # | 约束 | 落地形态 |
|---|---|---|
| **1【定】** | 判据锚定**结构位置**，不是全文包含 | 题 1 #3 要求三字段**同一行**共现；题 3 #5/#6 锚定到具体条款 |
| **2【定】** | 必须有「不该消失的东西消失了」判据，**前提不能是它还在** | 反向全量判据，见下 |
| **3【定】** | provenance 自洽 | tracked / untracked 统一口径；trace header 写真实 profile / model，不许写 `"live"` |
| **4【定】** | **判据只能来自任务原文** | 见约束 5 |
| **5 新【定】** | 每条 `TASK` 类判据带 `sourceQuote`，且该片段**逐字出现在任务原文里**——判分前逐条核一遍 | 把「硬查任务没要求的数字」变成**写不出来**的东西，而不是靠事后评审发现 |
| **6 新【定】** | 反向判据是**全量**的，不是逐个点名 | 见下 |

### 反向全量判据（约束 6 的形态）

```text
before 快照里的每个文件：
  若不在该题「允许改动清单」内  →  after 必须存在，且 sha256 逐字节不变
after 快照里的每个新增文件：
  必须在该题「允许新增清单」内
```

比阶段 1/2 的「6 个源文件 SHA-256 未变」强一档：**它是全量的**，
模型删 / 改 / 新建任何东西都会被抓到，不依赖判分方想到要点名它。

### 【定】`sourceQuote` 的例外必须显式分类

反向全量判据**没有原文出处**——它不是任务判据，是全局不变量。所以约束 5 分两类：

```text
硬判据 ┬─ TASK 类       必须带 sourceQuote，且逐字出现在任务原文里
       └─ INVARIANT 类  无 sourceQuote，但**每题必须至少有一条**，
                        且「允许改动 / 允许新增清单」必须显式列出
```

【定】`INVARIANT` 类**只允许两种形态**：反向全量不变、以及允许清单本身。
**不开第三种口子**——否则它会变成「把任务规则伪装成不变量」的后门，
那就绕回阶段 2 硬查 `20223` 的老路了。

> 本卷有一条真实的应用：题 3 的「模型有没有重新观察」依据是 V05 §20.3 与工具的 `nextStep`，
> **不是任务原文**。它两类都进不去，于是**降级为观察项 O1**（§4.3）。
> 这就是这条约束的用法。

### 判分方的既有纪律（不得违反）

来自 [`eval/graders/index.ts`](../../eval/graders/index.ts) 的【定】：
判分**只准读外部世界（before / after 快照 ＋ 文件内容）与 trace**；
trace 只允许用于**轨迹类**判据；**不得读 `RunOutcome` 判成败**——
那是让被测对象给自己打分。§5.2 的混淆矩阵是把两者**并排显示**，不是让判据去读它。

## 7. 已知边界

### 7.1 `fetch_url` 结构性测不了

[`url-guard.ts`](../../tools/common/src/net/url-guard.ts) 拒绝 localhost / 私网 / 回环 / 链路本地，
**且在 DNS 解析后再判一次**（防「指向内网的公开域名」）。所以：

- 起一个本地 HTTP server 做 hermetic 夹具 → **被护栏挡掉**；
- 唯一能真调的目标是**公网** → 内容会变，夹具不可冻结，判据不可复现。

【定】**它不进硬门槛。** 要测只能单独做一次性探针，结论只对探针当天的那个 URL 成立。

### 7.2 Artifact 二层验证只有两项能跑

首批检查器四项：JSON 可解析、ZIP 可解开、文本编码合法、hash 与登记一致。
三题产出以 Markdown 为主，而「Markdown 可解析」**明确不做**（任何文本都是合法 Markdown，
是永远绿灯的闸门）。所以本卷能真跑的只有 **JSON（题 1 的 `供应商汇总.json`）＋ hash**。
ZIP 这次没有消费者，如实记「未覆盖」。

### 7.3 其余未覆盖项

- **对抗安全**：无 prompt injection、无恶意文件名、无 symlink 越界、无并发 TOCTOU、无权限错误 / 磁盘满 / SQLite 损坏
- **DeepSeek 对照端点**：决 2，端点侧 401
- **Baseline 对比**：没有确定性 Workflow Baseline 实现
- **`pass^5`**：决 1 收缩到 `pass^3`
- **§16.2 的第二种无进展形态**（多个不同调用但外部状态无变化）：Guard 当前不实现
