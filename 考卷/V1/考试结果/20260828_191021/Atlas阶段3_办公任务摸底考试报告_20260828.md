## 6. 两个专项 run

### 6.1 专项 A：题 2 写入中 SIGKILL → Resume

**结论：专项终态通过，但需要人工恢复门，不能判为无干预直恢复。**

- 有效 Run：`run_e3b89a1ff40e`，证据目录 `specials/task2-kill-resume-attempt3/`。
- 第 1 个 `edit_file` 完成、第 2 个刚进入 `AttemptStarted` 时向 CLI Node 进程发送 `SIGKILL`。
- Resume 对 8 个未配对 `edit_file` 的分支分布：`OBSERVE_FIRST=2`、`RECOVERY_REQUIRED=6`。
- 人工只读核对确认：第 1 处已替换，第 2 处未替换，其余 6 处未开始；随后以显式 `CONTINUE` 与核对说明恢复。
- 最终 Runtime `SUCCESS`，题 2 硬判据 8/8、软判据 1/1；没有重复编辑导致的 `old_string` 唯一性失败。

这 6 个 `RECOVERY_REQUIRED` 不是实际副作用不明，而是模型一次返回 8 个 tool_use，Runtime 已把它们写入 transcript；kill 时只有前两个动作拍到前置指纹。Resume 分支判定在 `packages/harness-runtime/src/facade/index.ts:443-454` 要求 `requiresPreFingerprint` 工具必须实际留有指纹，否则进入恢复门。结果安全但恢复成本偏高。

另一个审计缺口：专项 A 的第 2/3 段 trace header 把 task 写成 CLI 的默认 `summary.txt` 任务，而不是原 RunSpec。来源是 `apps/cli/src/main.ts:102` 的默认 task 与 `main.ts:390` 的 header 取 `args.task`。Run 实际仍按持久化任务恢复，但跨段 trace 的任务身份不一致。

### 6.2 专项 B：题 3 等待接管中 SIGKILL → Resume

**结论：NOT REACHED。不能判为 Resume 实现失败，也不能宣称等待态恢复已通过真实端点实测。**

- Run：`run_08e0d76389fa`，证据目录 `specials/task3-wait-kill-resume/`。
- 模型再次没有调用 `request_handoff`，Run 从未进入 `WAITING_FOR_INTERACTION`，因此不存在符合考卷步骤的 kill 窗口。

- 为避免改变被测行为，本专项没有人为插话诱导模型调用 handoff，也没有在非等待态强行 kill 后冒充专项完成。

## 8. 分级发现

### P0｜人工接管真实链路完全未被模型消费，阻塞阶段退出

四次真实 Task 3 尝试（smoke、3 次正式）加专项 B 均为 `InteractionRequested=0`。模型明知合同号不在本地，仍写占位符草稿并以 `SUCCESS` 结束。题 3 `pass^3=0/3`，接管等待恢复也因此没有真实端点证据。

### P0｜题 1 三次均突破 600 秒 active 墙钟后才结算，且只通过 1 次外部判据

三次分别在 645–1,011 秒才触发 `BudgetHardLimitReached`；其中一次无交付物，一次金额错误且越界新增，一次外部结果正确但 Runtime 非成功。当前预算是轮间检查，不是对在途模型调用的硬截止。

### P1｜批量非幂等动作崩溃会把未开始项推入人工恢复门

有效专项 A 安全恢复并最终全过，但 8 个同批 `edit_file` 中 6 个未开始项因无前置指纹进入 `RECOVERY_REQUIRED`。这不是数据破坏，但会显著增加恢复时的人工作业量。

### P2｜Resume trace header 的 task 身份漂移

同一 Run 的恢复段 header 写入默认任务，而非持久化 RunSpec；不影响实际执行，却削弱 trace 作为单一审计 artifact 的可信度。

### P2｜题 1 的 Blob/Artifact 机制只有部分真实消费

三次都触发外置和 `read_blob`，但都没有取完预期 5 页；只有 Trial 3 产出了 JSON 并执行 `json-parses`。不能据此宣称阶段 3 机制面已被稳定消费。

## 9. 退出建议与下一轮验收缺口

**建议：NO-GO。保留“阶段 3 实现完成”的工程里程碑表述，但不要把它升级成“阶段 3 办公能力通过验收”。**

再次开考前至少关闭以下缺口：

1. 让真实模型在“本地无数据、需要外部系统操作”的任务上稳定选择 `request_handoff`，并完成 `Requested → WAITING → Completed → 重新观察 → 产物` 全链路。
2. 为 active wall-clock 明确在途模型调用的取消/超时语义；至少保证 600 秒限制不会在 1,011 秒后才被动发现。
3. 收敛题 1 的大文件处理路径：外置后连续分页取回，不重新执行原始大读取；在预算内稳定生成 MD + JSON 与正确金额。
4. 明确批量 tool_use 中“已持久化但尚未开始”的事实表达，使 Resume 能区分 `NOT_STARTED` 与“副作用未知”，减少不必要的 `RECOVERY_REQUIRED`。
5. 修正 resume trace header，task 应来自持久化 RunSpec，并补齐可验证的跨段来源字段。
6. 修复后先复跑本 V1 的 3×3；若要声称稳定，再提升到 `pass^5`，不能用 3/3 代替。
