## 这是什么

V03 架构设计已经命名了 38 张逻辑表、19 个 Port、16 条 Directive，但**零次真实 Provider 调用**。
二次评审的三个 P0（多 Tool Call、必须原样回传的推理块、token 会计归属）只在真正调过一次
带工具的流式 Provider 之后才会暴露。

本 Spike 的唯一产出是**一份带证据的事实文档**，用来解锁 V03 中被挂起的 4 个【验】标记
和 3 个决策点。**代码本身没有价值，跑完即弃。**

## 硬约束

- 不建 monorepo，不做任何工程基线决策（包管理、构建、测试框架、Schema 方案、ID 形态）
- 不实现任何 Port、Kernel、Contract 或 V03 中的类型
- 不写单测、不做错误处理、不追求代码质量
- **阶段 1 不得 import 本目录任何代码**

**第一步永远是 P0**——它确认模型 ID 是否有效、计数端点是否存在、扩展思考+工具能否组合。

```

```
必答（P1 并行 Tool Call、P2 原样回传的块、P3 流式中断）——直接阻塞三个 P0 的 Contract 冻结。

```bash

```
应答（P4 token 口径、P6 错误分类、P7 上下文超限）——阻塞 Port 设计与阈值机制。

```bash

```

## 证据

每次运行在 `raw/` 下生成 `<探针>-<provider>-<时间戳>.jsonl`，每行一个 JSON：

| kind | 含义 |
|---|---|
| `meta` | **首行**。SDK 版本、模型 ID、日期、探针参数。事实会过期，没有版本号的证据等于没有证据 |
| `step` | 实验步骤 |
| `request` / `response` / `error` | 完整请求体与响应体（含错误体——错误结构本身就是 P6 的观测对象） |
| `stream_event` | 流式事件逐条 |
| `note` / `finding` / `unanswered` | 观测、结论、未解答项 |
| `summary` | 末行汇总 |

API Key 写盘前被 scrub，永不落盘。超长字符串截断并记录原长度。

`raw/` **要提交进 git**——它是 Facts 文档的引用来源。

**至少要有一个 V03 条款被证伪或需要改写。**

如果七个问题全部「证实了原设想」，说明探针设计得太温和——负向实验没做到位，需要补做。

### 负向实验的自检：失败原因必须被独立确认

第三轮抓到四处探针缺陷，全是同一个形状：**探针拿到一个 400，就当成「我的假设被证实了」**。
实际那个 400 来自完全无关的原因——推理块缺失、或账号配额用尽。写进文档就是：

| 探针会说 | 真相 |
|---|---|
| 「单块上限 < 200KB」 | 200KB 正常接受，400 是因为 assistant 回合缺推理块 |
| 「Provider 校验了 tool 入参完整性」 | 同上 |
| 「countTokens 偏差 -600%」 | 偏差 0.00%，是探针漏算了命中缓存的 tokens |
| 「单块上限 < 200KB」（百炼） | 429 `quota exceeded` 同时命中 `exceed` 和 `limit` 两个词 |

因此新增探针时：**一个负向实验只有在能说清「为什么失败」时才算数。**
判不出原因就调 `unansweredItem()`，不要默认归因到你想验证的那件事上。
