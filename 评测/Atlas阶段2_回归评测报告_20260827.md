## 2. 公开评测口径与本次量表

本轮沿用阶段 1 两份报告的 100 分量表和等级阈值，以保证项目内口径连续；同时把阶段 2 新增的持久化、重启恢复和测量装置放进“可靠性、恢复与验证”维度。

公开方法依据：

1. [GAIA](https://arxiv.org/abs/2311.12983)：用真实助手任务检验多步推理、工具使用和可验证答案；
2. [AgentBench](https://arxiv.org/abs/2308.03688)：关注交互环境中的多轮决策和工具使用；
3. [τ-bench](https://arxiv.org/abs/2406.12045)：以会话结束后的环境状态对照目标状态，并用 `pass^k` 衡量重复运行可靠性；
4. [OSWorld](https://arxiv.org/abs/2404.07972)：冻结初始环境，任务结束后用执行式脚本检查文件系统、应用和配置状态；
5. Anthropic [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)：明确区分 outcome 与 transcript/trajectory，客观任务优先使用确定性 grader，并要求阅读失败轨迹校验 grader 是否公平；
6. [AgentDojo](https://arxiv.org/abs/2406.13352)：工具返回也是不可信输入。本轮未植入 prompt injection，所以安全结论只覆盖路径、审批、源文件保护和协议边界，不外推到对抗安全。

本轮判定顺序为：

```text
冻结初始 workspace
  → 真实模型多轮执行
  → 外部环境终态与差分 grader
  → 失败 trial 的完整 trajectory 审阅
  → SQLite / Trace / 源码边界交叉核验
```

Runtime 的 `SUCCESS` 只是一项被测输出，不是真值来源。

等级阈值保持不变：90–100 通过；80–89 有条件通过；70–79 有限通过；低于 70 不通过。

## 8. 代码层问题定位与优化方向

以下只做分析，没有修改产品代码。

### P1-1：官方 CLI 与 live suite 无法使用 `.env` 中可用的 DeepSeek 配置

**现象**

用户给出的原始命令和 `npm run eval:suite -- --live 5` 都在首个网络请求前退出：

```text
.env 的 dashscope_model（deepseek-v4-flash）与端点声明里的 modelId（qwen3.7-plus）不一致
```

**代码原因**

- [`compose.ts`](../apps/cli/src/compose.ts#L114-L151) 同时定义 Bailian / DeepSeek 配置；[`compose.ts`](../apps/cli/src/compose.ts#L220-L269) 的 model/profile 和 baseUrl/profile 一致性 fail-fast 是正确的安全措施，不应删除或放松；
- `compose()` 已有 `endpoint?: "bailian" | "deepseek"`，但 [`main.ts`](../apps/cli/src/main.ts#L53-L85) 的参数结构没有 `--endpoint`，[`main.ts`](../apps/cli/src/main.ts#L287-L292) 调用 `compose()` 时也未传 endpoint；
- [`eval/suite/index.ts`](../eval/suite/index.ts#L215-L222) 的 live 路径同样使用默认 Bailian，参数解析只有 `--live`/次数，没有 endpoint；
- 本轮只能用隔离 runner 显式传 `endpoint: "deepseek"`，才能按 `.env` 的有效 DeepSeek 组合运行。

**优化建议**

1. 给 CLI 和 eval suite 增加同一个、受枚举约束的 `--endpoint bailian|deepseek`；
2. 把解析后的 endpoint、profile id、model id 写入统一 provenance，不允许 trace header 写泛化值 `live`；
3. 启动时打印“最终解析后的端点/Profile/模型”，但绝不打印 key；
4. 保留现有 fail-fast：修的是可选择性和诊断，不是绕过能力声明。

### P1-2：真实任务 `pass^5` 不成立，完成前缺少显式 requirements closure

**现象**

1/5 的清单漏掉总字节数，但 Runtime `SUCCESS`。这表明动作级 Verification 已能证明“文件确实写了”，仍不能证明“用户所有显式要求都满足”。

**原因边界**

- 直接原因是模型在一个 trial 中遗漏了整体合计；
- Runtime 不应硬编码“归档清单”业务规则，现有 outcome 也不应冒充 Eval；
- 但 Agent harness 在结束前没有一个通用的“逐项回看任务要求—观察最终产物—再决定结束”的 closure 机制，使模型的偶发遗漏直接进入终态。

**优化建议**

1. 在能力评测层继续用环境终态 hard grader，稳定门槛至少设为同题 `pass^5=true`；
2. 在通用 harness 层考虑可配置的 completion checklist / postcondition port，而不是把业务 grader import 到 Runtime Core；
3. 让模型在 final 前获得一次受预算约束的“验证目标产物”机会，验证依据必须来自工具 observation，不得仅重读自己的 summary；
4. 扩展 suite 到更多失败形状，避免只对这一份清单 prompt 过拟合。

### P1-3：旧 grader 和 live artifact 仍不够支持高置信度真实评测

仓库 Roadmap 已经正确记录了这些问题，但当前 `archive-inventory@1.0.0` 仍存在：

1. [`archive-inventory.ts`](../eval/graders/archive-inventory.ts#L103-L116) 将“文件名出现”和“对应字节数出现”分开判断；[`containsNumber`](../eval/graders/archive-inventory.ts#L214-L216) 只查数字是否在全文任意位置出现，错位表格可能通过；
2. 日志检查以 `logBefore && logAfter` 为前提，日志被删除时该检查静默跳过；
3. 官方 suite 的 live trace header 把 `modelId` 写成 `live`，见 [`eval/suite/index.ts`](../eval/suite/index.ts#L202-L212)；
4. suite 只保存 manifest，然后关闭 DB、删除 workspace；失败 trial 的正文和持久状态无法事后复读，见 [`eval/suite/index.ts`](../eval/suite/index.ts#L258-L270)；
5. `gitDirty` 包括 untracked，而 `diffHash` 只哈希 tracked diff，二者不是同一口径。本轮报告里的 `gitDirty=true` 来自评测前已存在的一份用户删除，不能证明评测 runner 被 provenance 覆盖。

本轮通过自建隔离 runner 记录了真实 model/profile，并在 Resume 样本中保留正文与 DB；这只是本次评测补证，尚未修复产品化 eval 管路。

**优化建议**

- grader 使用结构锚定：解析 Markdown 表格/分组，断言“文件名—字节数”同一行、目录小计在对应 section；
- 无条件断言日志存在，并核验原内容是 after 的字节前缀、恰追加一行；
- 每个 live trial 保存目标产物正文或密封 workspace、SQLite、trace、grader report；
- provenance 对 tracked/untracked 使用统一快照口径，或要求正式运行从 clean commit 启动；
- grader 版本升级后保留旧结果，不把不同 grader 版本的分数直接混算。

### P2-1：`--yes` 的安全语义正确，但与原始无人值守评测命令不再一致

[`main.ts`](../apps/cli/src/main.ts#L126-L183) 现在只让 `--yes` 自动批准 workspace 内可逆写；`append_log` 是不可逆追加，因此即使端点配置对齐，原命令仍会在日志追加处要求人工确认。无条件授权必须显式使用 `--yes-all`。

这是安全改进，不建议恢复旧的“`--yes` 批准一切”。需要优化的是接口与文档：

- 无人值守验收若已在冻结临时 workspace 内明确授权全部动作，应使用并醒目标注 `--yes-all`；
- 面向普通用户的 `--yes` 保持有限授权；
- AGENTS/README/评测命令必须写清二者差异，否则“headless CLI + `--yes`”会在不可逆动作处等待输入。

### P2-2：工具误用可自愈，但 `list_dir` 契约还可以更易判别

Trial 3 把日志文件传给 `list_dir`。当前失败是安全的 `NO_EFFECT`，Runtime 后续 pairing 和自愈均正确；问题主要在模型工具选择，而不是执行器。

可考虑：

- 工具描述与错误结果明确写“仅目录；目标是文件”，提供结构化错误码；
- 阶段 3 有更多文件工具后，提供统一的 `stat`/观察入口，减少模型用目录工具探测文件的诱因；
- 不把这类自愈 trial 判成任务硬失败，但持续统计 failed tool rate、额外轮次和 token。
